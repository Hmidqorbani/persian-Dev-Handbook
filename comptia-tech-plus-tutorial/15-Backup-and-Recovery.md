## فصل ۶۵: چرا پشتیبان‌گیری — RPO، RTO و انواع خرابی

### مقدمه

پشتیبان‌گیری، «کاری است که همه می‌دانند لازم است و هیچ‌کس به‌موقع انجام نمی‌دهد» — تا روزی که دیسک می‌میرد و همه‌چیز از دست می‌رود.

این فصل، دو عدد کلیدی را معرفی می‌کند که تصمیم‌های فنی را می‌سازند.

### مفاهیم اساسی

**انواع خرابی**

| نوع | مثال | قابل پیش‌بینی؟ |
|---|---|---|
| **سخت‌افزار** | مرگ دیسک، RAM خراب | تا حدی |
| **نرم‌افزار** | باگ، آپدیت خراب | تا حدی |
| **انسانی** | حذف اشتباهی، فرمت | ❌ |
| **بدافزار** | باج‌گیر | ❌ |
| **فاجعه** | آتش، سیل، سرقت | ❌ |
| **طبیعی** | زلزله، برق | ❌ |

**نکتهٔ مهم:** باج‌گیرها **پشتیبان‌های متصل** را هم رمز می‌کنند. پشتیبان باید **آفلاین** یا **غیرقابل‌تغییر (immutable)** باشد.

**دو عدد کلیدی**

| مفهوم | معنی | سؤال |
|---|---|---|
| **RPO** | Recovery Point Objective | چقدر داده می‌توانم از دست بدهم؟ |
| **RTO** | Recovery Time Objective | چقدر می‌توانم قطع باشم؟ |

**مثال:**

```
RPO = ۱ ساعت  → حداکثر ۱ ساعت داده از دست می‌رود
RTO = ۴ ساعت  → حداکثر ۴ ساعت قطعی
```

| RPO | روش |
|---|---|
| ۲۴ ساعت | پشتیبان روزانه |
| ۱ ساعت | پشتیبان ساعتی / snapshot |
| ~۰ | Replication همزمان |

| RTO | روش |
|---|---|
| روزها | بازیابی از نوار/ابر |
| ساعت‌ها | snapshot + VM |
| دقیقه‌ها | failover خودکار |

**هزینه در برابر محافظت**

```
هزینهٔ پشتیبان‌گیری ↑  →  RPO/RTO ↓  (بهتر)
```

**تعادل:** RPO/RTO را بر اساس ارزش داده تعیین کن، نه بر اساس «بهترین».

**محاسبهٔ ارزش داده**

```
هزینهٔ از دست دادن = (درآمد روزانه × روزهای قطعی) + (هزینهٔ بازسازی) + (اعتماد از دست رفته)
```

**قاعده:** هزینهٔ پشتیبان‌گیری باید کمتر از هزینهٔ از دست دادن باشد.

**پشتیبان در برابر آرشیو**

| معیار | پشتیبان | آرشیو |
|---|---|---|
| هدف | بازیابی سریع | نگه‌داری بلندمدت |
| دسترسی | مکرر | کم |
| محل | نزدیک/ابر | ارزان |
| مدت | هفته/ماه | سال |

**پشتیبان در برابر RAID**

| معیار | RAID | پشتیبان |
|---|---|---|
| خرابی دیسک | ✅ | ✅ |
| حذف اشتباهی | ❌ | ✅ |
| باج‌گیر | ❌ | ✅ (اگر آفلاین) |
| آتش/سیل | ❌ | ✅ (اگر دور) |

**جملهٔ کلیدی:** RAID پشتیبان نیست.

### مثال‌های عملی

**سناریوی Lab: تعیین RPO/RTO**

**کسب‌وکار: دفتر حسابداری ۵ نفره**

| داده | ارزش | RPO | RTO |
|---|---|---|---|
| فاکتورها | بالا | ۲۴ ساعت | ۸ ساعت |
| ایمیل | متوسط | ۲۴ ساعت | ۲۴ ساعت |
| فایل‌های موقت | کم | — | — |

**راه‌حل:**

```
فاکتورها: پشتیبان روزانه + نسخهٔ ابری + نسخهٔ آفلاین هفتگی
ایمیل: پشتیبان خودکار ارائه‌دهنده
فایل موقت: بدون پشتیبان
```

**سناریوی دوم: محاسبهٔ هزینه**

**سناریو:** شرکت با درآمد ۵۰٬۰۰۰ دلار در روز.

| RTO | هزینهٔ قطعی | هزینهٔ راه‌حل |
|---|---|---|
| ۲۴ ساعت | ۵۰٬۰۰۰ | ۲۰۰/ماه |
| ۴ ساعت | ۸٬۳۰۰ | ۸۰۰/ماه |
| ۱ ساعت | ۲٬۱۰۰ | ۲٬۵۰۰/ماه |

**تحلیل:** تفاوت ۲۴ ساعت و ۴ ساعت، ۴۱٬۷۰۰ دلار صرفه‌جویی در هر حادثه است — در برابر ۶۰۰ دلار هزینهٔ ماهانه. ارزش دارد.

**سناریوی سوم: سناریوی باج‌گیر**

```
روز ۱: کارمند روی فایل پیوست کلیک می‌کند
روز ۱ (۲ ساعت بعد): فایل‌ها رمز می‌شوند
روز ۱ (۳ ساعت بعد): پشتیبان متصل هم رمز می‌شود
روز ۲: درخواست باج
```

**دفاع:**

| لایه | کار |
|---|---|
| آگاهی کاربر | عدم کلیک |
| آنتی‌ویروس | شناسایی |
| پشتیبان آفلاین | بازیابی |
| Immutable backup | تغییرناپذیر |
| جداسازی شبکه | محدود کردن انتشار |

### مقایسه و الگوهای مختلف

**سه سطح پشتیبان**

| سطح | RPO | هزینه |
|---|---|---|
| پایه | ۲۴ ساعت | کم |
| متوسط | ۱ ساعت | متوسط |
| بالا | دقیقه | بالا |

**الگوی «لایه‌ای»**

```
لایه ۱: snapshot روزانه (سریع)
لایه ۲: پشتیبان کامل هفتگی (آفلاین)
لایه ۳: نسخهٔ ابری (خارج از محل)
```

### اشکال شایع

**۱) RAID به‌عنوان پشتیبان**
حذف اشتباهی روی RAID هم اعمال می‌شود.

**۲) پشتیبان فقط در همان دستگاه**
خرابی دیسک = از دست رفتن هر دو.

**۳) پشتیبان متصل همیشه**
باج‌گیر آن را رمز می‌کند.

**۴) بدون تست بازیابی**
پشتیبان خراب، بی‌فایده است.

**۵) RPO/RTO تعیین‌نشده**
نمی‌دانی چه می‌خواهی.

**۶) پشتیبان بدون رمزنگاری**
افشا در انتقال/ذخیره.

**۷) فقط یک نسخه**
یک خطا = همه‌چیز.

**۸) فراموش کردن پشتیبان تنظیمات**
سرور بازیابی شد، ولی تنظیمات نه.

### نکات مهم (Tips & Tricks)

- **RPO/RTO را بنویس.**
- **RAID پشتیبان نیست.**
- **پشتیبان آفلاین یا immutable.**
- **۳-۲-۱ را رعایت کن.**
- **بازیابی را تست کن.**
- **رمزنگاری کن.**
- **تنظیمات را هم پشتیبان بگیر.**

### خلاصه فصل

- شش نوع خرابی وجود دارد؛ همه قابل پیش‌بینی نیستند.
- RPO = حداکثر دادهٔ از دست رفتنی؛ RTO = حداکثر قطعی.
- هزینهٔ محافظت باید کمتر از هزینهٔ از دست دادن باشد.
- RAID و آرشیو، جای پشتیبان را نمی‌گیرند.
- باج‌گیر، پشتیبان متصل را هم رمز می‌کند.
- پشتیبان بدون تست، پشتیبان نیست.

<a name="ch-66"></a>
## فصل ۶۶: انواع پشتیبان — کامل، افزایشی، تفاضلی

### مقدمه

در فصل قبل دیدیم که پشتیبان چرا لازم است. اما «پشتیبان» یک چیز واحد نیست: می‌توانی هر شب همه‌چیز را کپی کنی، یا فقط تغییرات را. انتخاب اشتباه، یا فضا را می‌بلعد یا بازیابی را غیرممکن می‌کند. این فصل، سه نوع اصلی و کاربرد هرکدام را نشان می‌دهد.

### مفاهیم اساسی

**سه نوع اصلی**

| نوع | چه چیزی | حجم | زمان بازیابی |
|---|---|---|---|
| **Full** | همه‌چیز | زیاد | سریع |
| **Incremental** | تغییرات از آخرین پشتیبان (هر نوع) | کم | کند |
| **Differential** | تغییرات از آخرین Full | متوسط | متوسط |

**نمودار**

```
روز:      ۱     ۲     ۳     ۴     ۵
Full:     F
Inc:            I1    I2    I3    I4
Diff:           D1    D2    D3    D4
```

**بازیابی Incremental:**

```
F + I1 + I2 + I3 + I4   ← همه لازم‌اند
```

**بازیابی Differential:**

```
F + D4                   ← فقط آخرین
```

**جدول مقایسه**

| معیار | Full | Incremental | Differential |
|---|---|---|---|
| فضای ذخیره | زیاد | کم | متوسط |
| زمان پشتیبان | زیاد | کم | متوسط |
| زمان بازیابی | کم | زیاد | متوسط |
| پیچیدگی | کم | بالا | متوسط |

**استراتژی ترکیبی**

```
شنبه:     Full
یکشنبه:   Incremental
دوشنبه:   Incremental
...
جمعه:     Incremental
```

یا:

```
شنبه:     Full
هر روز:   Differential
```

**پشتیبان تصویری (Image)**

کپی کامل از دیسک، شامل سیستم‌عامل و تنظیمات.

| مزیت | عیب |
|---|---|
| بازیابی کامل | حجم زیاد |
| بدون نصب مجدد | سخت‌افزار مشابه |

**Snapshot**

عکس لحظه‌ای از وضعیت، معمولاً در سطح فایل‌سیستم/VM.

| مزیت | عیب |
|---|---|
| سریع | وابسته به همان ذخیره‌سازی |
| بدون توقف | **پشتیبان نیست** |

**پشتیبان در سطح فایل در برابر سطح بلوک**

| نوع | واحد | مزیت |
|---|---|---|
| File-level | فایل | بازیابی انتخابی |
| Block-level | بلوک | سریع، کامل |

**پشتیبان پایگاه داده**

| نوع | کار |
|---|---|
| **Logical** (dump) | `pg_dump`، `mysqldump` |
| **Physical** | کپی فایل‌های داده |
| **Point-in-time** | بازیابی به لحظهٔ مشخص (WAL) |

**نکته:** برای پایگاه دادهٔ فعال، فقط کپی فایل کافی نیست — باید dump یا snapshot سازگار بگیری.

**پشتیبان ایمیل و فایل**

| نوع | روش |
|---|---|
| ایمیل | export PST/MBOX یا پشتیبان ارائه‌دهنده |
| فایل اشتراکی | نسخه‌بندی + پشتیبان |
| OneDrive/Drive | نسخه‌های قبلی |

**Retention — چند نسخه نگه داریم؟**

| سیاست | توضیح |
|---|---|
| **GFS** | Grandfather-Father-Son: روزانه، هفتگی، ماهانه |
| **Sliding window** | N نسخهٔ آخر |
| **Legal hold** | نگه‌داری قانونی |

**مثال GFS:**

```
۷ نسخهٔ روزانه
۴ نسخهٔ هفتگی
۱۲ نسخهٔ ماهانه
```

### مثال‌های عملی

**سناریوی Lab: برنامهٔ پشتیبان هفتگی**

```markdown
## برنامه

| روز | نوع | مقصد | نگه‌داری |
|---|---|---|---|
| شنبه | Full | NAS + ابر | ۴ هفته |
| یکشنبه | Incremental | NAS | ۷ روز |
| دوشنبه | Incremental | NAS | ۷ روز |
| سه‌شنبه | Incremental | NAS | ۷ روز |
| چهارشنبه | Incremental | NAS | ۷ روز |
| پنجشنبه | Incremental | NAS | ۷ روز |
| جمعه | Incremental | NAS + ابر | ۴ هفته |
```

**سناریوی دوم: محاسبهٔ فضا**

```
داده: ۵۰۰ GB
Full: ۵۰۰ GB
Incremental روزانه: ۲۰ GB
Differential روزانه: ۵۰ GB (رشد می‌کند)

سیاست: ۱ Full + ۶ Incremental
= ۵۰۰ + (۶ × ۲۰) = ۶۲۰ GB
```

با Differential:

```
= ۵۰۰ + (۵۰ + ۱۰۰ + ۱۵۰ + ...) = بیشتر
```

**نکته:** Incremental فضا کمتری می‌خواهد ولی بازیابی پیچیده‌تر است.

**سناریوی سوم: بازیابی Incremental**

```
۱. Full شنبه را بازیابی کن
۲. Incremental یکشنبه
۳. Incremental دوشنبه
۴. Incremental سه‌شنبه
۵. Incremental چهارشنبه
```

**اگر یکی خراب باشد، بازیابی متوقف می‌شود.** به همین دلیل، دورهٔ Full منظم لازم است.

**سناریوی چهارم: پشتیبان پایگاه داده**

```bash
# PostgreSQL — logical
pg_dump -Fc mydb > mydb_$(date +%F).dump

# بازیابی
pg_restore -d mydb mydb_2026-11-11.dump

# MySQL
mysqldump --single-transaction mydb > mydb.sql
```

**نکته:** `--single-transaction` برای سازگاری در حین کار.

### مقایسه و الگوهای مختلف

**سه استراتژی**

| استراتژی | مناسب |
|---|---|
| Full روزانه | دادهٔ کوچک |
| Full هفتگی + Incremental | دادهٔ متوسط |
| Full هفتگی + Differential | تعادل |

**الگوی «Full هفتگی، Incremental روزانه»**

رایج‌ترین ترکیب برای کسب‌وکار کوچک.

### اشکال شایع

**۱) فقط Incremental**
بازیابی پیچیده و شکننده.

**۲) Full روزانه برای دادهٔ بزرگ**
زمان و فضا.

**۳) بدون Full دوره‌ای**
زنجیرهٔ Incremental بی‌پایان.

**۴) کپی فایل پایگاه دادهٔ فعال**
فایل ناسازگار.

**۵) Snapshot به‌عنوان پشتیبان**
روی همان دیسک.

**۶) بدون Retention**
فضا پر می‌شود یا نسخه‌های لازم پاک می‌شوند.

**۷) پشتیبان بدون تاریخ در نام**
نمی‌دانی کدام چیست.

**۸) بدون لاگ پشتیبان**
نمی‌دانی موفق بود یا نه.

### نکات مهم (Tips & Tricks)

- **سه نوع** را با بازیابی حفظ کن.
- **Full دوره‌ای** برای کاهش زنجیره.
- **`pg_dump`/`mysqldump`** برای پایگاه داده.
- **GFS برای Retention.**
- **تاریخ در نام فایل.**
- **لاگ پشتیبان** را بررسی کن.
- **Snapshot پشتیبان نیست.**

### خلاصه فصل

- Full کامل، Incremental تغییرات از آخرین هر نوع، Differential از آخرین Full.
- Incremental فضا کم، بازیابی پیچیده.
- Differential تعادل.
- پشتیبان پایگاه داده با dump یا snapshot سازگار.
- GFS سیاست نگه‌داری استاندارد.
- Full دوره‌ای، زنجیره را کوتاه می‌کند.

<a name="ch-67"></a>
## فصل ۶۷: استراتژی ۳-۲-۱ و پشتیبان ابری

### مقدمه

داشتن یک نسخهٔ پشتیبان، بهتر از هیچ است — ولی کافی نیست. اگر همان دیسک بسوزد، اگر باج‌گیر همان پوشه را رمز کند، اگر دفتر تعطیل شود، یک نسخه هیچ کمکی نمی‌کند. این فصل، قاعده‌ای را می‌سازد که از سال ۲۰۰۰ تا امروز استاندارد صنعت است.

### مفاهیم اساسی

**قاعدهٔ ۳-۲-۱**

> **۳** نسخه از داده، روی **۲** نوع رسانهٔ مختلف، با **۱** نسخه خارج از محل.

**نسخهٔ مدرن ۳-۲-۱-۱-۰**

| عدد | معنی |
|---|---|
| ۳ | نسخه |
| ۲ | رسانه |
| ۱ | خارج از محل |
| ۱ | آفلاین یا immutable |
| ۰ | صفر خطا در بازیابی (تست‌شده) |

**مثال عملی**

```
نسخه ۱: دیسک اصلی (سرور)
نسخه ۲: NAS محلی (روزانه)
نسخه ۳: ابر (هفتگی)
```

| نسخه | رسانه | محل | آفلاین |
|---|---|---|---|
| ۱ | SSD | دفتر | ❌ |
| ۲ | HDD NAS | دفتر | ❌ |
| ۳ | ابر | خارج | ✅ (immutable) |

**رسانه‌ها**

| رسانه | مزیت | عیب |
|---|---|---|
| HDD اکسترنال | ارزان، سریع | قابل سرقت |
| NAS | اشتراکی | وابسته به شبکه |
| نوار (Tape) | ارزان بلندمدت، آفلاین | کند |
| ابر | خارج از محل | وابسته به اینترنت |
| DVD/Blu-ray | آفلاین | ظرفیت کم |

**پشتیبان ابری — سه مدل**

| مدل | توضیح |
|---|---|
| **Backup to cloud** | از محل به ابر |
| **Cloud-to-cloud** | بین سرویس‌ها |
| **Hybrid** | محلی + ابر |

**رمزنگاری پشتیبان**

| مرحله | کار |
|---|---|
| **In transit** | TLS |
| **At rest** | AES-256 |
| **کلید** | جدا از داده |

**نکتهٔ حیاتی:** کلید رمزنگاری را **جدا** نگه دار. اگر کلید روی همان پشتیبان باشد، رمزنگاری بی‌فایده است.

**Immutable Backup**

پشتیبان در بازهٔ مشخصی **قابل تغییر یا حذف نیست** — حتی توسط ادمین.

| مزیت | عیب |
|---|---|
| مقاوم به باج‌گیر | هزینهٔ بیشتر |
| مقاوم به خطای انسانی | انعطاف کمتر |

**پشتیبان و حریم خصوصی**

| نکته | کار |
|---|---|
| دادهٔ شخصی | رمزنگاری |
| محل ذخیره | مقررات محلی |
| دسترسی | حداقل |
| نگه‌داری | طبق قانون |

**Cloud Tier**

| لایه | دسترسی | هزینه |
|---|---|---|
| Hot | فوری | بالا |
| Cool | دقیقه‌ها | متوسط |
| Archive | ساعت‌ها | کم |

**محاسبهٔ هزینهٔ ابر**

```
هزینه = (ذخیره‌سازی × قیمت) + (بازیابی × قیمت) + (ترافیک × قیمت)
```

**تله:** بازیابی از لایهٔ Archive می‌تواند ساعت‌ها طول بکشد و هزینهٔ قابل‌توجهی داشته باشد.

### مثال‌های عملی

**سناریوی Lab: طراحی ۳-۲-۱ برای یک دفتر**

**داده:** ۲ TB (اسناد، پایگاه داده، ایمیل).

**طراحی:**

| نسخه | محل | فرکانس | رمزنگاری |
|---|---|---|---|
| ۱ | سرور | لحظه‌ای | — |
| ۲ | NAS محلی | روزانه | ✅ |
| ۳ | ابر (immutable) | هفتگی | ✅ |
| ۴ | دیسک آفلاین در گاوصندوق | ماهانه | ✅ |

**چک‌لیست:**

```markdown
- [ ] ۳ نسخه دارم
- [ ] حداقل ۲ رسانه
- [ ] ۱ نسخه خارج از محل
- [ ] ۱ نسخه آفلاین/immutable
- [ ] رمزنگاری فعال
- [ ] کلید جدا
- [ ] بازیابی تست شده
```

**سناریوی دوم: مقایسهٔ گزینه‌ها**

| گزینه | هزینهٔ سالانه | RTO | مقاوم به باج‌گیر |
|---|---|---|---|
| فقط NAS | کم | ساعت | ❌ |
| NAS + ابر | متوسط | ساعت | ✅ |
| NAS + ابر + آفلاین | بیشتر | ساعت | ✅✅ |

**سناریوی سوم: کلید رمزنگاری**

```
❌ بد:  backup.enc + key.txt در همان پوشه
✅ خوب: backup.enc در ابر، کلید در password manager جدا
```

**درس:** رمزنگاری بدون مدیریت کلید، امنیت نیست.

### مقایسه و الگوهای مختلف

**سه سطح بلوغ**

| سطح | ویژگی |
|---|---|
| ۱ | پشتیبان منظم، بدون تست |
| ۲ | ۳-۲-۱ + تست دوره‌ای |
| ۳ | ۳-۲-۱-۱-۰ + immutable + اتوماسیون |

**الگوی «پشتیبان به‌عنوان کد»**

```yaml
backup:
  schedule: "0 2 * * *"
  source: /data
  targets:
    - nas:/backups/daily
    - s3://bucket/backups
  encryption: aes-256
  retention:
    daily: 7
    weekly: 4
    monthly: 12
```

### اشکال شایع

**۱) ۳ نسخه روی یک دیسک**
یک خرابی = همه.

**۲) همهٔ نسخه‌ها آنلاین**
باج‌گیر همه را رمز می‌کند.

**۳) کلید کنار داده**
رمزنگاری بی‌فایده.

**۴) بدون immutable**
ادمین/باج‌گیر می‌تواند حذف کند.

**۵) ابر بدون محاسبهٔ بازیابی**
هزینهٔ خروج غافلگیرکننده.

**۶) Archive برای بازیابی فوری**
ساعت‌ها انتظار.

**۷) بدون مستندات**
در حادثه نمی‌دانی چه کنی.

**۸) فراموش کردن نسخهٔ آفلاین**
بدون آن، ۳-۲-۱ ناقص است.

### نکات مهم (Tips & Tricks)

- **۳-۲-۱** را حفظ کن.
- **۱ نسخه آفلاین/immutable.**
- **کلید جدا از داده.**
- **Archive برای بازیابی فوری نیست.**
- **هزینهٔ بازیابی را حساب کن.**
- **مستندات بازیابی** بنویس.
- **تست دوره‌ای.**

### خلاصه فصل

- ۳-۲-۱: سه نسخه، دو رسانه، یک خارج از محل.
- نسخهٔ مدرن: + یک آفلاین/immutable، + صفر خطا در بازیابی.
- رمزنگاری at rest و in transit، با کلید جدا.
- Immutable backup مقاوم به باج‌گیر است.
- لایهٔ Archive ارزان ولی کند.
- مستندات و تست، بخشی از استراتژی‌اند.

<a name="ch-68"></a>
## فصل ۶۸: بازیابی — تست، رویه و Lab

### مقدمه

پشتیبان بدون بازیابی، فقط امید است. این فصل، رویهٔ بازیابی و تست آن را می‌سازد.

### مفاهیم اساسی

**تفاوت Restore و Recovery**

| اصطلاح | معنی |
|---|---|
| **Restore** | بازگرداندن فایل از پشتیبان |
| **Recovery** | بازگرداندن سرویس به کار |

**مراحل بازیابی**

```
۱) تشخیص (چه چیزی، چه زمانی)
۲) توقف سرویس (جلوگیری از نوشتن)
۳) انتخاب نسخهٔ پشتیبان
۴) بازیابی به محیط موقت (اگر ممکن)
۵) بررسی صحت
۶) بازگرداندن به تولید
۷) تأیید و مستندسازی
```

**محیط موقت — چرا؟**

بازیابی مستقیم روی تولید، ریسک دارد. اول در محیط تست بازیابی کن، بررسی کن، بعد منتقل کن.

**تست بازیابی — چهار سطح**

| سطح | کار | فرکانس |
|---|---|---|
| **File-level** | بازیابی یک فایل | ماهانه |
| **Full restore** | بازیابی کامل | فصلی |
| **Bare-metal** | بازیابی روی سخت‌افزار خالی | سالانه |
| **DR drill** | تمرین فاجعه | سالانه |

**معیار موفقیت**

```markdown
- [ ] فایل‌ها کامل‌اند (تعداد/حجم)
- [ ] فایل‌ها باز می‌شوند (بدون خرابی)
- [ ] داده با نسخهٔ اصلی می‌خواند (checksum)
- [ ] برنامه‌ها کار می‌کنند
- [ ] مجوزها درست‌اند
- [ ] زمان بازیابی < RTO
```

**Checksum**

```bash
sha256sum backup.tar.gz
# مقایسه با مقدار ثبت‌شده
```

**Runbook بازیابی**

```markdown
# Runbook: بازیابی سرور فایل

## پیش‌نیاز
- دسترسی به NAS
- کلید رمزنگاری
- مستندات شبکه

## مراحل
۱. سرویس اشتراک فایل را متوقف کن
۲. آخرین Full را از NAS بردار
۳. رمزگشایی کن
۴. به مسیر اصلی بازیابی کن
۵. Incrementalها را به ترتیب اعمال کن
۶. مجوزها را بررسی کن
۷. سرویس را راه‌اندازی کن
۸. تست دسترسی با کاربر نمونه

## زمان تخمینی
۲ ساعت

## تماس
- مسئول: ...
- پشتیبان: ...
```

**سناریوهای رایج**

| سناریو | رویه |
|---|---|
| حذف فایل | بازیابی از نسخهٔ قبلی |
| خرابی دیسک | Image restore |
| باج‌گیر | بازیابی از immutable |
| فاجعهٔ سایت | بازیابی در سایت دوم |

**DR (Disaster Recovery)**

| سطح | توضیح |
|---|---|
| **Cold site** | فضا، بدون تجهیزات فعال |
| **Warm site** | تجهیزات، بدون دادهٔ جاری |
| **Hot site** | آماده، با replication |

**RTO بر اساس سایت:**

```
Cold: روزها
Warm: ساعت‌ها
Hot:  دقیقه‌ها
```

### مثال‌های عملی

**سناریوی Lab: تست بازیابی فایل**

```bash
# ۱) فایل نمونه بساز
echo "test data" > /data/test.txt

# ۲) پشتیبان بگیر
tar -czf /backup/test-$(date +%F).tar.gz /data

# ۳) شبیه‌سازی حذف
rm /data/test.txt

# ۴) بازیابی
tar -xzf /backup/test-$(date +%F).tar.gz -C /

# ۵) بررسی
cat /data/test.txt
```

**سناریوی دوم: تست بازیابی پایگاه داده**

```bash
# پشتیبان
pg_dump -Fc mydb > /backup/mydb.dump

# بازیابی در دیتابیس تست
createdb mydb_test
pg_restore -d mydb_test /backup/mydb.dump

# بررسی تعداد ردیف
psql -d mydb_test -c "SELECT COUNT(*) FROM orders;"
```

**نکته:** هرگز بازیابی را مستقیم روی تولید تست نکن.

**سناریوی سوم: محاسبهٔ زمان بازیابی**

```
حجم داده: ۵۰۰ GB
سرعت شبکه: ۱۰۰ MB/s
زمان انتقال: ۵۰۰٬۰۰۰ / ۱۰۰ = ۵٬۰۰۰ ثانیه ≈ ۸۳ دقیقه
+ رمزگشایی: ۲۰ دقیقه
+ بررسی: ۳۰ دقیقه
────────────────────────
جمع: ~۲.۲ ساعت
```

اگر RTO = ۱ ساعت باشد، این راه‌حل کافی نیست.

**سناریوی چهارم: چک‌لیست DR**

```markdown
- [ ] RPO/RTO مستند
- [ ] پشتیبان‌ها در محل دوم
- [ ] رویهٔ اعلام فاجعه
- [ ] لیست تماس
- [ ] دسترسی به کلیدها
- [ ] تمرین سالانه
- [ ] درس‌های تمرین ثبت شد
```

### مقایسه و الگوهای مختلف

**سه سطح تست**

| سطح | زمان | ریسک |
|---|---|---|
| File restore | دقیقه | کم |
| Full restore | ساعت | متوسط |
| DR drill | روز | بالا |

**الگوی «تست بدون اعلام»**

گاهی تست بازیابی را بدون اطلاع تیم انجام بده تا آمادگی واقعی سنجیده شود. (با هماهنگی مدیریت.)

### اشکال شایع

**۱) پشتیبان بدون تست**
ممکن است خراب باشد.

**۲) تست روی تولید**
ریسک.

**۳) بدون Runbook**
در حادثه، سردرگمی.

**۴) بدون محاسبهٔ زمان**
RTO رعایت نمی‌شود.

**۵) کلید در دسترس نیست**
بازیابی غیرممکن.

**۶) بدون بررسی checksum**
دادهٔ ناقص.

**۷) تست فقط فایل**
بازیابی کامل تست نشده.

**۸) بدون درس‌آموخته**
اشتباه تکرار می‌شود.

### نکات مهم (Tips & Tricks)

- **تست بازیابی، بخشی از پشتیبان است.**
- **محیط موقت** برای تست.
- **Runbook بنویس.**
- **زمان بازیابی را محاسبه کن.**
- **Checksum برای صحت.**
- **DR drill سالانه.**
- **درس‌آموخته را ثبت کن.**

### خلاصه فصل

- Restore بازگرداندن فایل، Recovery بازگرداندن سرویس.
- بازیابی هفت مرحله دارد.
- چهار سطح تست: فایل، کامل، bare-metal، DR.
- Runbook، تفاوت بین سردرگمی و بازیابی است.
- زمان بازیابی باید کمتر از RTO باشد.
- تست بدون اعلام، آمادگی واقعی را می‌سنجد.
