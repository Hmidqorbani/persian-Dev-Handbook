## فصل ۳۳: مجازی‌سازی — هایپروایزر، VM، کانتینر

### مقدمه

قبل از مجازی‌سازی، هر سرویس یک سرور فیزیکی می‌خواست: یک سرور برای وب، یکی برای دیتابیس، یکی برای ایمیل. نتیجه: ۱۰ سرور با ۱۰٪ استفاده از منابع.

مجازی‌سازی این معادله را عوض کرد: **یک سرور فیزیکی، چند ماشین مجازی**. این فصل، مکانیزم و انواعش را می‌دهد.

### مفاهیم اساسی

**مجازی‌سازی چیست؟**

لایه‌ای نرم‌افزاری که منابع سخت‌افزاری را بین چند سیستم‌عامل تقسیم می‌کند.

```
بدون مجازی‌سازی:          با مجازی‌سازی:
┌──────────┐              ┌──────────────────────────┐
│  App A   │              │  VM1   │  VM2   │  VM3   │
├──────────┤              ├────────┼────────┼────────┤
│  OS A    │              │ OS A   │ OS B   │ OS C   │
├──────────┤              ├────────┴────────┴────────┤
│ سخت‌افزار │              │      Hypervisor          │
└──────────┘              ├──────────────────────────┤
                          │      سخت‌افزار           │
                          └──────────────────────────┘
```

**هایپروایزر (Hypervisor)**

| نوع | محل | مثال | کاربرد |
|---|---|---|---|
| **Type 1 (Bare-metal)** | مستقیم روی سخت‌افزار | VMware ESXi، Hyper-V، Proxmox | سرور تولید |
| **Type 2 (Hosted)** | روی سیستم‌عامل | VirtualBox، VMware Workstation | دسکتاپ، آموزش |

**تفاوت:** Type 1 کارایی و امنیت بالاتر؛ Type 2 ساده‌تر.

**ماشین مجازی (VM)**

| مشخصه | معنی |
|---|---|
| **vCPU** | پردازندهٔ مجازی |
| **vRAM** | حافظهٔ مجازی |
| **vDisk** | دیسک مجازی (VMDK، VHDX، qcow2) |
| **vNIC** | کارت شبکهٔ مجازی |
| **Snapshot** | عکس لحظه‌ای از وضعیت |

**Snapshot — تلهٔ مهم**

Snapshot برای **تست و بازگشت سریع** است، نه پشتیبان‌گیری.

| چرا پشتیبان نیست | توضیح |
|---|---|
| روی همان دیسک است | خرابی دیسک = از دست رفتن هر دو |
| کند می‌شود | زنجیرهٔ snapshot رشد می‌کند |
| وابسته به هایپروایزر | مهاجرت سخت |

**کانتینر (Container)**

| معیار | VM | Container |
|---|---|---|
| سیستم‌عامل | کامل، جدا | مشترک (کرنل میزبان) |
| حجم | GB | MB |
| زمان راه‌اندازی | دقیقه | ثانیه |
| جداسازی | قوی | متوسط |
| مناسب | سرویس‌های مختلف OS | میکروسرویس |

**تشبیه:** VM = خانهٔ مستقل با آشپزخانهٔ خودش. Container = آپارتمان با آشپزخانهٔ مشترک.

**Docker و Kubernetes**

| ابزار | کار |
|---|---|
| **Docker** | ساخت و اجرای کانتینر |
| **Kubernetes** | ارکستراسیون کانتینر در مقیاس |

**Virtual Desktop Infrastructure (VDI)**

دسکتاپ کامل روی سرور اجرا می‌شود و کاربر از راه دور وصل می‌شود.

| مزیت | عیب |
|---|---|
| مدیریت متمرکز | هزینهٔ سرور |
| امنیت داده | وابسته به شبکه |
| دستگاه ارزان | تجربهٔ کاربری |

**مزایای مجازی‌سازی**

| مزیت | توضیح |
|---|---|
| کاهش هزینه | سرور کمتر، برق کمتر |
| جداسازی | یک VM خراب، بقیه را نمی‌کشد |
| Snapshot | بازگشت سریع |
| مهاجرت زنده | بدون قطعی |
| تست | محیط ایزوله |

**معایب**

| عیب | توضیح |
|---|---|
| پیچیدگی | نیاز به تخصص |
| Sprawl | VMهای فراموش‌شده |
| کارایی | سربار هایپروایزر |
| امنیت | اگر هایپروایزر نفوذ شود، همه لو می‌روند |

### مثال‌های عملی

**سناریوی Lab: تثبیت سرورها**

**وضعیت قبل:**

| سرور | CPU | RAM | استفاده |
|---|---|---|---|
| وب | ۸ هسته | ۳۲ GB | ۱۲٪ |
| دیتابیس | ۸ هسته | ۶۴ GB | ۲۵٪ |
| ایمیل | ۴ هسته | ۱۶ GB | ۸٪ |
| فایل | ۴ هسته | ۸ GB | ۵٪ |

**جمع:** ۲۴ هسته، ۱۲۰ GB RAM، استفادهٔ متوسط ۱۲٪.

**بعد از مجازی‌سازی:**

```
۲ سرور فیزیکی (هر کدام ۱۶ هسته، ۱۲۸ GB)
├── VM وب
├── VM دیتابیس
├── VM ایمیل
└── VM فایل
```

**نتیجه:**

| معیار | قبل | بعد |
|---|---|---|
| سرور فیزیکی | ۴ | ۲ |
| مصرف برق | ۱۰۰٪ | ۵۵٪ |
| زمان راه‌اندازی سرویس جدید | روزها | دقیقه |
| بازگشت در خرابی | ساعت‌ها | دقیقه (snapshot) |

**سناریوی دوم: VM یا Container؟**

| نیاز | انتخاب |
|---|---|
| اجرای ویندوز و لینوکس روی یک سرور | VM |
| میکروسرویس با استقرار مکرر | Container |
| نرم‌افزار قدیمی با نیاز به OS خاص | VM |
| CI/CD و تست سریع | Container |
| جداسازی امنیتی قوی | VM |

**سناریوی سوم: Snapshot در برابر Backup**

| سناریو | Snapshot | Backup |
|---|---|---|
| قبل از آپدیت | ✅ | ✅ |
| خرابی دیسک | ❌ | ✅ |
| بازیابی فایل | ❌ | ✅ |
| بازگشت سریع | ✅ | کند |

**قاعده:** Snapshot برای «اگر آپدیت خراب شد»، Backup برای «اگر سرور سوخت».

### مقایسه و الگوهای مختلف

**سه سطح مجازی‌سازی**

| سطح | مثال | جداسازی |
|---|---|---|
| سخت‌افزار کامل (VM) | ESXi | قوی |
| سیستم‌عامل (Container) | Docker | متوسط |
| فرآیند (Sandbox) | Firejail | ضعیف |

**الگوی «VM برای پایه، Container برای اپ»**

```
سرور فیزیکی
└── VM (لینوکس)
    └── Docker
        ├── app
        ├── db
        └── cache
```

این ترکیب، هم جداسازی VM را دارد هم سرعت Container.

### اشکال شایع

**۱) Snapshot به‌عنوان پشتیبان**
خرابی دیسک = از دست رفتن همه. Backup جدا.

**۲) VM Sprawl**
VMهای فراموش‌شده، منابع را می‌بلعند. مستندسازی و بازبینی.

**۳) Overcommit بیش از حد**
RAM بیشتر از فیزیکی → swap → کندی شدید.

**۴) Type 2 در تولید**
کارایی کم. Type 1.

**۵) Container برای همه‌چیز**
برای نرم‌افزار قدیمی یا نیاز به OS متفاوت، VM.

**۶) نادیده گرفتن امنیت هایپروایزر**
نفوذ به هایپروایزر = نفوذ به همه VMها.

**۷) مهاجرت بدون تست**
سازگاری درایور و شبکه.

**۸) بدون مانیتورینگ منابع**
نمی‌دانی کدام VM گلوگاه است.

### نکات مهم (Tips & Tricks)

- **Type 1 برای سرور، Type 2 برای دسکتاپ.**
- **Snapshot ≠ Backup.**
- **VM برای جداسازی، Container برای سرعت.**
- **Overcommit را کنترل کن.**
- **VDI برای مدیریت متمرکز دسکتاپ.**
- **هایپروایزر را آپدیت نگه دار.**
- **VM Sprawl را بازبینی کن.**

### خلاصه فصل

- مجازی‌سازی، منابع یک سرور را بین چند سیستم تقسیم می‌کند.
- Type 1 روی سخت‌افزار، Type 2 روی سیستم‌عامل.
- VM سیستم‌عامل کامل دارد؛ Container کرنل مشترک.
- Snapshot برای بازگشت سریع است، نه پشتیبان‌گیری.
- VDI دسکتاپ را متمرکز می‌کند.
- VM و Container مکمل‌اند، نه جایگزین.

## فصل ۳۴: مدل‌های ابر و استقرار — انتخاب درست

### مقدمه

فایل ۰۳ ابر را معرفی کرد. این فصل، عمیق‌تر می‌رود: مسئولیت‌ها، هزینه‌ها، و تصمیم‌های واقعی.

### مفاهیم اساسی

**مسئولیت مشترک — جدول کامل**

| لایه | IaaS | PaaS | SaaS |
|---|---|---|---|
| داده و دسترسی | **تو** | **تو** | **تو** |
| اپلیکیشن | **تو** | **تو** | ارائه‌دهنده |
| Runtime | **تو** | ارائه‌دهنده | ارائه‌دهنده |
| سیستم‌عامل | **تو** | ارائه‌دهنده | ارائه‌دهنده |
| مجازی‌سازی | ارائه‌دهنده | ارائه‌دهنده | ارائه‌دهنده |
| سخت‌افزار | ارائه‌دهنده | ارائه‌دهنده | ارائه‌دهنده |

**نکتهٔ کلیدی:** در همهٔ مدل‌ها، **داده** مسئولیت توست. حتی در SaaS.

**چهار مدل استقرار**

| مدل | مالکیت | مناسب برای |
|---|---|---|
| **Public** | ارائه‌دهنده | استارتاپ، بار متغیر |
| **Private** | سازمان | بانک، دولت، دادهٔ حساس |
| **Hybrid** | ترکیب | دادهٔ حساس + بار متغیر |
| **Community** | چند سازمان | دانشگاه، پژوهش |

**چرا Hybrid؟**

```
دادهٔ مشتری (حساس) → Private
وب‌سایت و API (بار متغیر) → Public
پشتیبان → Public (ارزان)
```

**مفهوم Region و Availability Zone**

| مفهوم | معنی |
|---|---|
| **Region** | منطقهٔ جغرافیایی (مثلاً فرانکفورت) |
| **AZ** | مرکز دادهٔ جدا در همان منطقه |
| **Edge** | نقطهٔ نزدیک کاربر |

**قاعده:** برای تحمل خرابی، حداقل دو AZ.

**SLA — عدد را بخوان**

| SLA | قطعی مجاز در ماه |
|---|---|
| ۹۹٪ | ۷.۲ ساعت |
| ۹۹.۹٪ | ۴۳ دقیقه |
| ۹۹.۹۹٪ | ۴.۳ دقیقه |
| ۹۹.۹۹۹٪ | ۲۶ ثانیه |

**تله:** SLA معمولاً **جبران مالی** می‌دهد، نه **جلوگیری از قطعی**. برای کسب‌وکار، قطعی ۴۳ دقیقه‌ای می‌تواند گران‌تر از جریمه باشد.

**هزینه‌های پنهان ابر**

| هزینه | توضیح |
|---|---|
| **Egress** | خروج داده |
| **IOPS** | عملیات دیسک |
| **Snapshot** | ذخیره‌سازی snapshot |
| **Support** | پشتیبانی |
| **Idle resources** | منابع فراموش‌شده |

**تخمین هزینه**

```
محاسبهٔ ساده:
هزینهٔ ماهانه = (تعداد VM × قیمت) + (ذخیره‌سازی × قیمت) + (ترافیک × قیمت)
```

**بهینه‌سازی:**

| روش | اثر |
|---|---|
| Reserved Instance | ۳۰–۶۰٪ ارزان‌تر |
| Spot Instance | ۷۰–۹۰٪ ارزان‌تر (قابل قطع) |
| Autoscaling | فقط به‌اندازهٔ نیاز |
| Storage tiering | دادهٔ سرد ارزان‌تر |

### مثال‌های عملی

**سناریوی Lab: انتخاب مدل برای سه سازمان**

**۱) استارتاپ SaaS با ۵ کارمند**
- نیاز: سرعت راه‌اندازی، هزینهٔ کم.
- **Public Cloud (PaaS)** + SaaS برای ایمیل و مدیریت.

**۲) بیمارستان**
- نیاز: دادهٔ بیمار، مقررات، کنترل.
- **Private Cloud** + اتصال ابری برای پشتیبان رمزنگاری‌شده.

**۳) شرکت تولیدی با کارخانه**
- نیاز: سیستم‌های قدیمی روی سرور محلی، گزارش‌های ابری.
- **Hybrid**: تولید on-prem، تحلیل در ابر.

**جدول تصمیم**

| معیار | Public | Private | Hybrid |
|---|---|---|---|
| هزینهٔ اولیه | کم | بالا | متوسط |
| کنترل | کم | کامل | متوسط |
| مقیاس | سریع | کند | متوسط |
| مقررات | متوسط | بالا | بالا |
| تیم IT | کم | زیاد | متوسط |

**سناریوی دوم: محاسبهٔ TCO سه‌ساله**

| مورد | On-Prem | Public Cloud |
|---|---|---|
| سخت‌افزار | ۱۵٬۰۰۰ | ۰ |
| برق و فضا | ۴٬۵۰۰ | ۰ |
| نگه‌داری | ۶٬۰۰۰ | ۰ |
| ابر ماهانه | ۰ | ۶۰۰ × ۳۶ = ۲۱٬۶۰۰ |
| کارکنان | ۱ نفر | ۰.۵ نفر |
| **جمع** | **~۳۰٬۰۰۰** | **~۲۵٬۰۰۰** |

**نتیجه:** برای این اندازه، ابر ارزان‌تر است. برای بار بزرگ‌تر و پایدارتر، معادله برعکس می‌شود.

**سناریوی سوم: طراحی برای تحمل خرابی**

```
Region A
├── AZ 1: VM اصلی
└── AZ 2: VM پشتیبان (replica)

Region B (اختیاری): بازیابی فاجعه
```

| سطح | RPO | RTO |
|---|---|---|
| Backup روزانه | ۲۴ ساعت | ساعت‌ها |
| Replica همزمان | ~۰ | دقیقه |
| Multi-region | ~۰ | ثانیه |

**RPO** = حداکثر دادهٔ قابل از دست رفتن.
**RTO** = حداکثر زمان بازگشت.

### مقایسه و الگوهای مختلف

**سه استراتژی ابر**

| استراتژی | توضیح | ریسک |
|---|---|---|
| Cloud-first | همه‌چیز در ابر | وابستگی |
| Cloud-only | بدون on-prem | قفل شدن |
| **Hybrid** | ترکیب | پیچیدگی |

**الگوی «Workload Placement»**

| بار | محل |
|---|---|
| دادهٔ حساس | Private |
| وب و API | Public |
| تحلیل دسته‌ای | Public (Spot) |
| سیستم قدیمی | On-prem |

### اشکال شایع

**۱) «ابر ارزان است» بدون محاسبه**
Egress و منابع فراموش‌شده، هزینه را چند برابر می‌کنند.

**۲) نادیده گرفتن Region**
مقررات محلی و تأخیر.

**۳) Single AZ**
یک خرابی = قطعی کامل.

**۴) SLA به‌عنوان تضمین**
جبران مالی، نه جلوگیری.

**۵) Vendor lock-in**
سرویس‌های اختصاصی، مهاجرت را سخت می‌کنند.

**۶) بدون برچسب‌گذاری منابع (Tagging)**
نمی‌دانی هزینهٔ کدام تیم است.

**۷) فراموش کردن منابع خاموش**
VMهای بی‌استفاده، هزینه می‌دهند.

**۸) بدون برنامهٔ خروج**
اگر لازم شد مهاجرت کنی، چه می‌کنی؟

### نکات مهم (Tips & Tricks)

- **داده همیشه مسئولیت توست.**
- **SLA را عددی بخوان.**
- **Egress را حساب کن.**
- **حداقل دو AZ.**
- **Reserved/Spot برای صرفه‌جویی.**
- **Tagging برای شفافیت هزینه.**
- **برنامهٔ خروج داشته باش.**

### خلاصه فصل

- IaaS/PaaS/SaaS سه سطح مسئولیت‌اند؛ داده همیشه با توست.
- چهار مدل استقرار: عمومی، خصوصی، ترکیبی، جامعه‌ای.
- Region و AZ برای تحمل خرابی.
- SLA جبران مالی می‌دهد، نه تضمین.
- Egress و منابع فراموش‌شده، هزینهٔ پنهان‌اند.
- Hybrid بهترین تعادل برای بسیاری از سازمان‌هاست.

<a name="ch-35"></a>
## فصل ۳۵: مرکز داده و زیرساخت سازمانی

### مقدمه

مرکز داده، «کارخانهٔ» فناوری است: برق، خنک‌سازی، شبکه، امنیت فیزیکی. حتی اگر همه‌چیز ابری باشد، دانستن این مفاهیم لازم است — چون ابر هم روی مرکز داده اجرا می‌شود.

### مفاهیم اساسی

**اجزای مرکز داده**

| جزء | کار |
|---|---|
| **Rack** | قفسهٔ ۱۹ اینچی استاندارد |
| **PDU** | توزیع برق |
| **UPS** | برق اضطراری |
| **ژنراتور** | برق بلندمدت |
| **CRAC/CRAH** | خنک‌سازی |
| **Hot/Cold Aisle** | چیدمان هوا |
| **Structured Cabling** | کابل‌کشی استاندارد |

**واحد Rack Unit (U)**

```
۱ U = ۱.۷۵ اینچ (۴۴.۴۵ mm)
رک استاندارد: ۴۲ U
سرور ۲U: دو واحد ارتفاع
```

**مدل‌های برق**

| سطح | افزونگی | تحمل |
|---|---|---|
| N | بدون افزونگی | هیچ |
| N+1 | یک اضافه | یک خرابی |
| 2N | دو برابر | یک خرابی کامل |
| 2N+1 | دو برابر + یک | دو خرابی |

**UPS — چقدر کافی است؟**

```
زمان پشتیبانی = (ظرفیت باتری × ولتاژ) / بار
```

معمولاً ۵–۱۵ دقیقه، برای «یا ژنراتور روشن شود یا خاموشی تمیز».

**خنک‌سازی**

| روش | کاربرد |
|---|---|
| Air cooling | اکثر مراکز |
| In-row cooling | تراکم بالا |
| Liquid cooling | GPU، HPC |

**دما و رطوبت توصیه‌شده (ASHRAE)**

| معیار | محدوده |
|---|---|
| دما | ۱۸–۲۷°C |
| رطوبت | ۴۰–۶۰٪ |

**Hot/Cold Aisle**

```
[سرد] [گرم] [سرد] [گرم]
  ↑      ↑     ↑
سرورها رو به سرد
```

اگر چیدمان اشتباه باشد، برق خنک‌سازی دو برابر می‌شود.

**امنیت فیزیکی**

| لایه | ابزار |
|---|---|
| محیط | حصار، نگهبانی |
| ورود | کارت، بیومتریک |
| رک | قفل |
| مانیتورینگ | دوربین |
| ردیابی | لاگ ورود |

**مدیریت کابل**

| اصل | چرا |
|---|---|
| برچسب دو سر | عیب‌یابی سریع |
| رنگ‌بندی | تفکیک نقش |
| مسیر جدا برای برق و داده | کاهش نویز |
| طول مناسب | جریان هوا |

**Tier — سطح مرکز داده**

| Tier | افزونگی | در دسترس بودن |
|---|---|---|
| I | پایه | ۹۹.۶۷۱٪ |
| II | اجزای افزونه | ۹۹.۷۴۱٪ |
| III | قابل نگه‌داری همزمان | ۹۹.۹۸۲٪ |
| IV | تحمل خرابی کامل | ۹۹.۹۹۵٪ |

### مثال‌های عملی

**سناریوی Lab: طراحی یک اتاق سرور کوچک**

**نیازمندی:**
- ۲ رک ۴۲U.
- ۱۰ سرور، ۲ سوئیچ، ۱ فایروال، ۱ UPS.
- بار تخمینی: ۴ کیلووات.

**گام ۱ — برق**

```
۱۰ سرور × ۳۰۰W = ۳٬۰۰۰W
سوئیچ و فایروال = ۳۰۰W
جمع = ۳٬۳۰۰W
+ ۳۰٪ حاشیه = ۴٬۳۰۰W
```

| تجهیز | ظرفیت |
|---|---|
| PDU | ۲ × ۳۲A |
| UPS | ۶ kVA |
| ژنراتور | ۱۰ kVA (اختیاری) |

**گام ۲ — خنک‌سازی**

```
بار حرارتی ≈ بار برق = ۴.۳ kW
ظرفیت خنک‌کننده = ۴.۳ × ۱.۳ ≈ ۵.۶ kW
```

**گام ۳ — چیدمان**

```
رک ۱: سرورها (رو به سرد)
رک ۲: شبکه + UPS
فاصلهٔ رک‌ها: ۱.۲ متر (جریان هوا)
```

**گام ۴ — امنیت**

```markdown
- [ ] در قفل‌دار
- [ ] کارت ورود
- [ ] دوربین
- [ ] لاگ ورود
- [ ] رک‌ها قفل
```

**سناریوی دوم: محاسبهٔ UPS**

بار ۴.۳ kW، UPS ۶ kVA با ضریب توان ۰.۹:

```
توان واقعی = ۶ × ۰.۹ = ۵.۴ kW
زمان با باتری ۹ Ah، ۴۸V:
≈ ۸–۱۲ دقیقه (بسته به باتری)
```

**نکته:** UPS برای «پل زدن تا ژنراتور» است، نه کار طولانی.

**سناریوی سوم: برچسب‌گذاری کابل**

| رنگ | کاربرد |
|---|---|
| آبی | داده (LAN) |
| زرد | داده (WAN/فیبر) |
| قرمز | برق اضطراری |
| مشکی | برق معمولی |
| سبز | مدیریت (iLO/iDRAC) |

### مقایسه و الگوهای مختلف

**سه اندازهٔ مرکز داده**

| اندازه | رک | کاربرد |
|---|---|---|
| اتاق سرور | ۱–۵ | دفتر کوچک |
| مرکز داده کوچک | ۱۰–۵۰ | سازمان متوسط |
| هایپراسکیل | ۱۰٬۰۰۰+ | ابر |

**الگوی «Colocation»**

به‌جای ساخت مرکز داده، رک خود را در مرکز دادهٔ دیگران اجاره می‌کنی.

| مزیت | عیب |
|---|---|
| هزینهٔ کم | کنترل کمتر |
| برق و خنک‌سازی آماده | وابستگی |
| اتصال اینترنت خوب | فاصله |

### اشکال شایع

**۱) خنک‌سازی ناکافی**
سرورها Throttle می‌کنند و عمر کم می‌شود.

**۲) چیدمان Hot/Cold اشتباه**
هزینهٔ برق دو برابر.

**۳) UPS بدون تست**
باتری مرده، در قطعی معلوم می‌شود.

**۴) کابل بدون برچسب**
عیب‌یابی ساعت‌ها طول می‌کشد.

**۵) برق و داده در یک مسیر**
نویز و خطر.

**۶) بدون امنیت فیزیکی**
دسترسی فیزیکی = دسترسی کامل.

**۷) بدون مانیتورینگ دما**
گرما، بی‌صدا خراب می‌کند.

**۸) بدون مستندات رک**
نمی‌دانی کدام سرور کجاست.

### نکات مهم (Tips & Tricks)

- **U = ۱.۷۵ اینچ؛ رک ۴۲U.**
- **N+1 حداقل برای تولید.**
- **UPS برای پل زدن، نه کار طولانی.**
- **Hot/Cold Aisle را رعایت کن.**
- **برچسب دو سر کابل.**
- **دما ۱۸–۲۷°C، رطوبت ۴۰–۶۰٪.**
- **امنیت فیزیکی را جدی بگیر.**

### خلاصه فصل

- مرکز داده: رک، برق، خنک‌سازی، شبکه، امنیت.
- افزونگی برق با N+1 یا 2N.
- UPS برای زمان کوتاه؛ ژنراتور برای بلندمدت.
- چیدمان Hot/Cold Aisle مصرف برق را کم می‌کند.
- Tier سطح در دسترس بودن را تعیین می‌کند.
- مستندسازی و برچسب‌گذاری، پایهٔ نگه‌داری است.

## فصل ۳۶: انتخاب زیرساخت — Lab تصمیم‌گیری

### مقدمه

این فصل، همهٔ فایل را در یک تصمیم عملی جمع می‌کند: برای یک کسب‌وکار مشخص، کدام ترکیب زیرساخت؟

### مفاهیم اساسی

**چارچوب تصمیم پنج‌مرحله‌ای**

```
۱) نیازها را بنویس (بار، SLA، مقررات)
۲) گزینه‌ها را فهرست کن
۳) هزینهٔ کل مالکیت (TCO) را حساب کن
۴) ریسک را بسنج
۵) انتخاب و مستندسازی
```

**معیارهای ارزیابی**

| معیار | وزن نمونه |
|---|---|
| هزینه | ۲۵٪ |
| پایداری | ۲۵٪ |
| امنیت/مقررات | ۲۰٪ |
| مقیاس‌پذیری | ۱۵٪ |
| سادگی مدیریت | ۱۵٪ |

**TCO — هزینهٔ کل مالکیت**

```
TCO = هزینهٔ اولیه
    + هزینهٔ جاری (برق، فضا، لایسنس، پشتیبانی)
    + هزینهٔ نیروی انسانی
    + هزینهٔ خرابی ( downtime )
    + هزینهٔ مهاجرت/خروج
```

**هزینهٔ خرابی**

```
هزینهٔ هر ساعت قطعی = درآمد ساعتی × ضریب
```

مثال: فروشگاه آنلاین با درآمد ۱۰٬۰۰۰ دلار در روز:

```
۱۰٬۰۰۰ ÷ ۲۴ ≈ ۴۱۷ دلار در ساعت
با ضریب ۳ (اعتماد از دست رفته) ≈ ۱٬۲۵۰ دلار در ساعت
```

### مثال‌های عملی

**سناریوی Lab: سه کسب‌وکار، سه تصمیم**

**۱) کلینیک کوچک (۵ کاربر)**

| نیاز | مقدار |
|---|---|
| نرم‌افزار | حسابداری، پرونده |
| داده | اطلاعات بیمار (حساس) |
| SLA | ۹۹٪ |
| بودجه | محدود |

**تحلیل:**

| گزینه | هزینه | ریسک |
|---|---|---|
| On-prem | متوسط | نگه‌داری |
| Private Cloud | بالا | — |
| Public + رمزنگاری | کم | مقررات |

**انتخاب:** Public Cloud با رمزنگاری at rest + پشتیبان رمزنگاری‌شده + قرارداد پردازش داده.

**۲) شرکت نرم‌افزاری (۵۰ کاربر)**

| نیاز | مقدار |
|---|---|
| بار | متغیر (release) |
| محیط | dev/staging/prod |
| SLA | ۹۹.۹٪ |

**انتخاب:** Public Cloud + Container + Autoscaling. محیط dev ارزان، prod پایدار.

**۳) کارخانه (۲۰۰ کاربر)**

| نیاز | مقدار |
|---|---|
| سیستم قدیمی | روی سرور محلی |
| تأخیر | کم برای خط تولید |
| اینترنت | ممکن است قطع شود |

**انتخاب:** On-prem برای خط تولید + ابر برای گزارش و پشتیبان. **Hybrid**.

**سناریوی دوم: محاسبهٔ TCO**

**گزینهٔ A: On-Prem**

| مورد | سالانه |
|---|---|
| سخت‌افزار (۵ ساله) | ۴٬۰۰۰ |
| برق | ۱٬۲۰۰ |
| فضا | ۱٬۸۰۰ |
| نگه‌داری | ۲٬۰۰۰ |
| نیروی انسانی (۰.۵ FTE) | ۳۰٬۰۰۰ |
| **جمع** | **۳۹٬۰۰۰** |

**گزینهٔ B: Public Cloud**

| مورد | سالانه |
|---|---|
| محاسبه | ۶٬۰۰۰ |
| ذخیره‌سازی | ۱٬۲۰۰ |
| ترافیک | ۸۰۰ |
| پشتیبانی | ۲٬۴۰۰ |
| نیروی انسانی (۰.۲ FTE) | ۱۲٬۰۰۰ |
| **جمع** | **۲۲٬۴۰۰** |

**نتیجه:** برای این اندازه، ابر ۴۳٪ ارزان‌تر.

**سناریوی سوم: ماتریس تصمیم**

| معیار | وزن | On-Prem | Cloud |
|---|---|---|---|
| هزینه | ۲۵ | ۲ | ۴ |
| پایداری | ۲۵ | ۳ | ۴ |
| امنیت | ۲۰ | ۴ | ۳ |
| مقیاس | ۱۵ | ۲ | ۵ |
| سادگی | ۱۵ | ۲ | ۴ |
| **امتیاز** | | **۲.۶۵** | **۳.۹۵** |

**نتیجه:** Cloud.

### مقایسه و الگوهای مختلف

**سه الگوی ترکیبی**

| الگو | توضیح |
|---|---|
| **Data gravity** | داده سنگین on-prem، پردازش ابری |
| **Burst** | پایه on-prem، اوج در ابر |
| **DR** | اصلی on-prem، بازیابی در ابر |

**الگوی «Burst»**

```
بار عادی: سرور محلی
بار اوج (حراج): ابر
```

مزیت: هزینهٔ کم در حالت عادی، مقیاس در اوج.

### اشکال شایع

**۱) تصمیم احساسی**
«همه ابری می‌روند.» نیاز را بسنج.

**۲) نادیده گرفتن نیروی انسانی**
TCO بدون حقوق، گمراه‌کننده است.

**۳) فرض «ابر مقیاس‌پذیر است، پس ارزان است»**
مقیاس خودکار، هزینهٔ خودکار.

**۴) بدون برنامهٔ خروج**
مهاجرت بعدی سخت می‌شود.

**۵) نادیده گرفتن هزینهٔ خرابی**
SLA ارزان، می‌تواند گران تمام شود.

**۶) انتخاب بدون تست**
Pilot کوچک انجام بده.

**۷) نادیده گرفتن مقررات**
داده در کدام کشور؟

**۸) تصمیم یک‌باره**
هر سال بازبینی کن.

### نکات مهم (Tips & Tricks)

- **نیاز را قبل از فناوری بنویس.**
- **TCO کامل، نه قیمت اولیه.**
- **هزینهٔ خرابی را حساب کن.**
- **Pilot قبل از مهاجرت کامل.**
- **برنامهٔ خروج داشته باش.**
- **ماتریس تصمیم با وزن.**
- **سالانه بازبینی کن.**

### خلاصه فصل

- چارچوب پنج‌مرحله‌ای: نیاز، گزینه، TCO، ریسک، انتخاب.
- TCO شامل نیروی انسانی و خرابی است، نه فقط سخت‌افزار.
- ماتریس تصمیم با وزن، انتخاب را شفاف می‌کند.
- Hybrid برای دادهٔ حساس + بار متغیر.
- Burst برای بار اوج.
- تصمیم را سالانه بازبینی کن.
