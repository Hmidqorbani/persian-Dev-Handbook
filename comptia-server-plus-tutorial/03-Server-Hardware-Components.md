## فصل ۱۰: پردازنده (CPU) در سرور

### مقدمه

پردازنده، مغز سرور است. اما در دنیای سرور، انتخاب CPU با دنیای دسکتاپ فرق دارد: در دسکتاپ «سریع‌ترین» مهم است؛ در سرور «**قابل اعتمادترین در بار پیوسته**» و «**تعداد هستهٔ کافی برای بار هم‌زمان**».

یک سرور وب با ۱۶ هستهٔ متوسط، بهتر از یک سرور وب با ۴ هستهٔ سریع کار می‌کند — چون ۲۰۰ درخواست هم‌زمان، به موازات پردازش نیاز دارند. این فصل منطق انتخاب و نگهداری CPU در سرور را توضیح می‌دهد.

### مفاهیم اساسی

**اجزای اصلی CPU:**

- **Core (هسته)** — واحد اجرای دستور. هر هسته یک رشتهٔ دستور را در لحظه اجرا می‌کند.
- **Thread (رشته)** — با **SMT/Hyper-Threading**، هر هستهٔ فیزیکی می‌تواند دو رشتهٔ منطقی را هم‌زمان نگه دارد. ۱۶ هسته = ۳۲ رشته.
- **Clock speed (فرکانس)** — گیگاهرتز. فرکانس پایه و فرکانس turbo.
- **Cache** — حافظهٔ بسیار سریع روی CPU: L1 (کوچک‌ترین، سریع‌ترین)، L2، L3 (مشترک بین هسته‌ها).
- **TDP** — Thermal Design Power، توان حرارتی طراحی. مبنای انتخاب خنک‌کننده و محاسبهٔ گرما.
- **Socket** — سوکت فیزیکی روی مادربرد. تعداد سوکت = تعداد CPU فیزیکی.
- **PCIe lanes** — خطوط ارتباطی با کارت‌های expansion و دیسک. **منبع محدود و حیاتی.**

**چند مفهوم سروری که در دسکتاپ کمتر می‌بینی:**

**۱. Multi-socket (چند سوکتی).** سرورهای ۲ سوکتی (dual-socket) رایج‌اند. ۲ CPU یعنی ۲ برابر هسته، اما:

- حافظه بین دو سوکت تقسیم می‌شود.
- دسترسی CPU به حافظهٔ سوکت دیگر، کندتر است (**NUMA**).
- لایسنس بعضی نرم‌افزارها بر اساس سوکت است (نه هسته) — هزینهٔ دو سوکت می‌تواند جهش کند.

**۲. NUMA (Non-Uniform Memory Access).** در سیستم چندسوکتی، هر CPU حافظهٔ محلی خودش را سریع‌تر می‌بیند. اگر یک پردازش روی CPU-0 اجرا شود و داده‌اش در حافظهٔ CPU-1 باشد، تأخیر بیشتر است. سیستم‌عامل سعی می‌کند محلی نگه دارد، اما بارهای سنگین (دیتابیس) به تنظیم نیاز دارند.

**۳. ECC در CPU.** برای استفاده از حافظهٔ ECC، **هم CPU و هم مادربرد** باید پشتیبانی کنند. اکثر CPUهای سروری (Intel Xeon، AMD EPYC) پشتیبانی می‌کنند؛ بسیاری از CPUهای مصرفی نه.

**۴. Instruction sets.** دستورهای ویژه برای بار خاص:

| مجموعه | کاربرد |
|---|---|
| **AES-NI** | رمزنگاری سریع (برای TLS، دیسک رمز) |
| **AVX-512 / AVX2** | محاسبات برداری، ML، فشرده‌سازی |
| **VT-x / AMD-V** | مجازی‌سازی سخت‌افزاری |
| **VT-d / AMD-Vi** | passthrough دستگاه به VM (IOMMU) |
| **SGX / SEV** | اجرای محرمانه (confidential computing) |

**۵. TDP و سرمایش.** CPU با TDP ۲۰۵ وات، گرمای زیادی تولید می‌کند. هیت‌سینک سروری، بزرگ و فلزی است و فن‌های شاسی با سرعت بالا کار می‌کنند. اگر هیت‌سینک اشتباه نصب شود (پیچ‌ها نامتقارن)، دما بالا می‌رود و CPU throttle می‌کند.

**۶. Stepping و microcode.** سازنده گاهی باگ‌های CPU را با **microcode update** رفع می‌کند (مثل Spectre/Meltdown). این به‌روزرسانی از طریق BIOS/firmware می‌آید — یعنی **firmware سرور، بخشی از امنیت CPU است**.

**۷. سرور در برابر دسکتاپ — جدول مقایسه:**

| معیار | CPU دسکتاپ | CPU سرور |
|---|---|---|
| هسته | ۴–۱۶ | ۸–۱۲۸ |
| پشتیبانی ECC | معمولاً نه | بله |
| PCIe lanes | ۱۶–۲۴ | ۶۴–۱۲۸ |
| سوکت چندگانه | نه | بله (۲ یا ۴) |
| TDP | ۶۵–۱۲۵W | ۱۰۰–۴۰۰W |
| عمر طراحی | ۲–۳ سال | ۵+ سال (برای ثبات) |
| هدف | فرکانس بالا | throughput و قابلیت اعتماد |

### مثال‌های عملی

**Lab Scenario 1 — انتخاب CPU برای سه workload**

> **وظیفه:** برای هر مورد، معیار اصلی انتخاب را تعیین کن.
>
> الف) سرور وب با ۳۰۰۰ درخواست در ثانیه
> ب) سرور دیتابیس PostgreSQL با ۵۰۰ تراکنش در ثانیه
> ج) سرور محاسباتی برای آموزش مدل ML
>
> **پاسخ:**
>
> | مورد | معیار اصلی | دلیل |
> |---|---|---|
> | الف | تعداد هسته + کش | بار موازی و سبک؛ throughput مهم است |
> | ب | فرکانس + IOPS دیسک | تراکنش‌ها تک‌رشته‌ای و حساس به latency‌اند |
> | ج | هسته + AVX + پهنای باند حافظه + GPU | محاسبات برداری، نیاز به throughput حافظه |
>
> **درس:** «CPU سریع‌تر» جواب نیست؛ «CPU متناسب با الگوی بار» جواب است.

**Lab Scenario 2 — محاسبهٔ ظرفیت CPU برای مجازی‌سازی**

> **وضعیت:** ۲۰ VM داری. مجموع vCPU = ۴۰. نسبت overcommit قابل قبول ۳:۱. چند هستهٔ فیزیکی لازم است؟
>
> **پاسخ:**
> - هستهٔ فیزیکی لازم = ۴۰ ÷ ۳ ≈ **۱۳.۳**
> - با در نظر گرفتن hypervisor و سربار: **۱۶ هستهٔ فیزیکی**
> - با SMT (۲ رشته به ازای هسته): ۱۶ هسته = ۳۲ رشتهٔ منطقی؛ که ۴۰ vCPU را راحت‌تر پوشش می‌دهد
>
> **اما:** اگر VMها هم‌زمان اوج بگیرند (مثلاً همه ساعت ۹ صبح)، overcommit ۳:۱ باعث صف انتظار CPU می‌شود. برای بارهای حساس، ۲:۱ امن‌تر است.

### مقایسه و الگوهای مختلف

**تک‌سوکت پرقدرت در برابر دو‌سوکت:**

| معیار | ۱ CPU با ۳۲ هسته | ۲ CPU با ۱۶ هسته |
|---|---|---|
| هزینهٔ لایسنس (per-socket) | کم | ۲ برابر |
| پهنای باند حافظه | یک مجموعه | دو مجموعه (بیشتر) |
| NUMA | ندارد | دارد (پیچیدگی) |
| افزونگی | ندارد (CPU می‌میرد = سرور می‌میرد) | کمی بهتر (با ۱ CPU هم بوت می‌شود) |
| مناسب برای | اکثر بارها | بارهای حافظه‌بر و محاسباتی سنگین |

**نکتهٔ عملی:** بسیاری از سازمان‌ها به‌خاطر لایسنس، تک‌سوکت با هستهٔ زیاد را ترجیح می‌دهند. اما برای دیتابیس‌های بزرگ، دو‌سوکت پهنای باند حافظهٔ بیشتری می‌دهد.

**سه رویکرد به عملکرد CPU:**

| رویکرد | روش | مزیت | عیب |
|---|---|---|---|
| **Scale up** | CPU قوی‌تر بخری | ساده | سقف دارد، گران |
| **Scale out** | سرور بیشتر | افقی، تحمل خرابی | پیچیدگی برنامه‌نویسی |
| **Offload** | کار را به GPU/FPGA بدهی | بسیار سریع برای بار خاص | تخصصی، گران |

**مقایسهٔ نسل‌های سرور (نمونه):**

| نسل | نمونه | ویژگی |
|---|---|---|
| قدیمی | Xeon E5 v4 | DDR4، PCIe 3.0 |
| متوسط | Xeon Scalable Gen2 | DDR4، PCIe 3.0، امنیت بهتر |
| جدید | Xeon Scalable Gen4/5، EPYC 9004 | DDR5، PCIe 5.0، CXL |

**نکته:** خرید سرور نسل قدیم دست‌دوم برای آزمایشگاه عالی است، اما برای تولید، مصرف برق و نبود پشتیبانی firmware ریسک است.

### اشکال شایع

**۱. خرید CPU بدون توجه به PCIe lanes.**
اگر ۲۴ دیسک NVMe و ۲ کارت شبکهٔ ۱۰۰GbE می‌خواهی، CPU با ۳۲ lane کافی نیست. lane تمام‌شده یعنی دیسک‌ها با سرعت کمتر کار می‌کنند.

**۲. نصب هیت‌سینک اشتباه.**
پیچ‌ها باید به‌ترتیب قطری و یکنواخت بسته شوند. فشار نامتقارن، تماس حرارتی را خراب می‌کند و دما ۱۰–۲۰ درجه بالا می‌رود.

**۳. فراموش کردن خمیر حرارتی.**
هیت‌سینک بدون خمیر (یا با خمیر خشک‌شده) = throttle. اگر CPU را جدا کردی، خمیر را تازه کن.

**۴. فرض اینکه «هستهٔ بیشتر همیشه بهتر».**
برای بار تک‌رشته‌ای (بعضی دیتابیس‌ها، بعضی اپلیکیشن‌های قدیمی)، فرکانس بالاتر از هستهٔ بیشتر مهم‌تر است.

**۵. بی‌توجهی به سازگاری سوکت.**
CPU نسل جدید در مادربرد نسل قبل کار نمی‌کند، حتی اگر سوکت اسمش یکی باشد. همیشه **لیست سازگاری سازنده (compatibility matrix)** را چک کن.

**۶. نادیده گرفتن microcode و BIOS.**
CPU جدید روی BIOS قدیم بوت نمی‌شود. قبل از نصب CPU نسل جدید، BIOS را آپدیت کن.

### نکات مهم (Tips & Tricks)

- **قبل از خرید، «پروفایل بار» بنویس:** تعداد رشتهٔ هم‌زمان، حساسیت به latency، نیاز به AVX.
- **برای دیتابیس، فرکانس بالا + کش بزرگ**؛ برای وب و مجازی‌سازی، هستهٔ بیشتر.
- **دما را پایش کن.** در لینوکس `sensors`، در ویندوز HWiNFO. دمای پایدار بالای ۸۵ درجه یعنی مشکل سرمایش.
- **در سرور دو‌سوکتی، اگر یک CPU خراب شد، بعضی سرورها با یک CPU هم بوت می‌شوند** — این را در طراحی DR در نظر بگیر.
- **TDP را در محاسبهٔ توان رک حساب کن** (فصل ۸). CPU پرتوان، برق و سرمایش بیشتری می‌خواهد.
- **در آزمون:** اگر سؤال «VM performance poor despite low CPU utilization» داد، به **NUMA**، **حافظه** یا **I/O** فکر کن، نه CPU.

### خلاصه فصل

- CPU سرور بر پایهٔ **هسته، lane، ECC و پایداری** انتخاب می‌شود، نه فرکانس تنها.
- **SMT** رشتهٔ منطقی می‌سازد؛ ۱۶ هسته = ۳۲ رشته.
- **NUMA** در سیستم چندسوکتی، تأخیر حافظه می‌سازد.
- **PCIe lanes** منبع محدود است؛ دیسک و NIC زیاد، lane زیاد می‌خواهد.
- **TDP** مبنای سرمایش و برق است.
- BIOS و microcode بخشی از امنیت و سازگاری CPU هستند.

## فصل ۱۱: حافظهٔ سرور — ECC، RDIMM و ظرفیت

### مقدمه

حافظه، جایی است که سرور بیشترین حساسیت را به «خطای نامرئی» دارد. یک بیت که در RAM دسکتاپ برعکس شود، ممکن است فقط یک بار برنامه کرش کند و کسی نفهمد. همان بیت در RAM سرور، می‌تواند یک تراکنش بانکی را خراب کند یا یک دیتابیس را corrupt کند.

به همین دلیل سرور از **ECC** استفاده می‌کند. این فصل دربارهٔ ECC، انواع ماژول، قواعد چیدمان و محاسبهٔ ظرفیت است.

### مفاهیم اساسی

**ECC (Error-Correcting Code):** حافظه‌ای که می‌تواند **خطای تک‌بیتی را تشخیص و اصلاح** کند و **خطای دوبیتی را تشخیص** دهد (بدون اصلاح).

- **Single-bit error** — با ECC اصلاح می‌شود، سیستم ادامه می‌دهد، رویداد لاگ می‌شود.
- **Multi-bit error** — قابل اصلاح نیست؛ سیستم معمولاً halt می‌کند (machine check exception) تا داده خراب نشود.

**چرا مهم است؟** بر اساس مطالعات صنعتی، خطای حافظه در سرورهای با RAM زیاد، پدیده‌ای نادر ولی واقعی است. در مقیاس بزرگ (هزاران سرور)، هر روز چند خطا رخ می‌دهد. بدون ECC، این خطاها بی‌صدا داده را خراب می‌کنند.

**انواع ماژول حافظه:**

| نوع | توضیح | کاربرد |
|---|---|---|
| **UDIMM** (Unbuffered) | بدون بافر، ارزان | دسکتاپ، سرورهای کوچک |
| **RDIMM** (Registered) | دارای رجیستر بین کنترلر و تراشه‌ها | **استاندارد سرور** |
| **LRDIMM** (Load-Reduced) | بافر اضافی، ظرفیت بالاتر | سرورهای با RAM بسیار زیاد |
| **NVDIMM** | DRAM + flash (persistent) | کاربردهای خاص |
| **SODIMM** | کوچک | لپ‌تاپ، بعضی سرورهای کوچک |

**تفاوت RDIMM و LRDIMM:**

- RDIMM تا ظرفیت معینی در هر کانال پشتیبانی می‌شود و ارزان‌تر است.
- LRDIMM بار الکتریکی را کاهش می‌دهد و اجازهٔ ظرفیت بالاتر (مثلاً ۲۵۶GB در یک ماژول) می‌دهد، اما گران‌تر و کمی کندتر است.

**مشخصات کلیدی یک ماژول:**

```
32GB 2Rx4 PC4-3200AA-R
│    │ │  │         │
│    │ │  │         └─ Registered
│    │ │  └─ سرعت (3200 MT/s)
│    │ └─ سازمان‌دهی (4 بیت عرض هر تراشه)
│    └─ تعداد rank (2)
└─ ظرفیت
```

**Rank چیست؟** گروهی از تراشه‌ها که با هم انتخاب می‌شوند. rank بیشتر (2R، 4R) یعنی ظرفیت بیشتر در همان ماژول، اما بار الکتریکی بیشتر و سرعت ممکن است کاهش یابد.

**کانال حافظه و قواعد چیدمان:**

- مادربرد سرور معمولاً **۶ یا ۸ یا ۱۲ اسلات** در هر CPU دارد، در **۴ یا ۶ یا ۸ کانال**.
- برای بهترین عملکرد، اسلات‌ها باید **متوازن بین کانال‌ها** پر شوند.
- **قاعدهٔ طلایی:** همهٔ کانال‌ها پر باشند، با ظرفیت مساوی. مثلاً ۸ اسلات، ۸ ماژول ۳۲GB = ۲۵۶GB با پهنای باند کامل.
- پر کردن نامتوازن (مثلاً ۳ ماژول در ۸ اسلات) باعث **کاهش پهنای باند** و گاهی **بوت نشدن** می‌شود.

**نکتهٔ حیاتی:** ترتیب پر کردن اسلات‌ها در دفترچهٔ مادربرد نوشته شده (مثلاً A1, B1, C1, D1 اول، بعد A2...). **اشتباه در این ترتیب، رایج‌ترین دلیل «RAM را اضافه کردم، سرور بوت نشد» است.**

**ظرفیت و محاسبه:**

```
ظرفیت کل = تعداد ماژول × ظرفیت هر ماژول
```

اما محدودیت‌های واقعی:

- حداکثر ظرفیت مادربرد (مثلاً ۴TB)
- حداکثر ظرفیت هر کانال
- حداکثر ظرفیت هر اسلات (مثلاً ۱۲۸GB)
- محدودیت OS (نسخهٔ Home vs Datacenter)

**DDR4 در برابر DDR5:**

| معیار | DDR4 | DDR5 |
|---|---|---|
| سرعت | ۲۱۳۳–۳۲۰۰ MT/s | ۴۸۰۰–۶۴۰۰+ MT/s |
| ولتاژ | ۱.۲V | ۱.۱V |
| کانال در هر ماژول | ۱ (۶۴ بیت) | ۲ (۲×۳۲ بیت) |
| PMIC | روی مادربرد | **روی ماژول** |
| ECC داخلی | ندارد (فقط ECC خارجی) | on-die ECC + ECC خارجی |
| سازگاری | با DDR4 فقط | با DDR5 فقط |

**نکتهٔ مهم:** DDR5 و DDR4 **با هم کار نمی‌کنند**. سوکت و کلید مکانیکی متفاوت است. ارتقای DDR4 به DDR5 یعنی تعویض مادربرد و CPU.

### مثال‌های عملی

**Lab Scenario 1 — چیدمان بهینهٔ حافظه**

> **وضعیت:** مادربرد با ۲ CPU و ۸ اسلات برای هر CPU (۴ کانال در هر CPU، ۲ اسلات در هر کانال). ۱۲۸GB RAM می‌خواهی.
>
> **وظیفه:** چه ترکیبی بچینی؟
>
> **پاسخ:**
> - گزینهٔ الف: ۱۶ ماژول ۸GB → همهٔ اسلات‌ها پر، پهنای باند کامل، اما ارتقای بعدی نیاز به تعویض دارد.
> - گزینهٔ ب: ۸ ماژول ۱۶GB → یک اسلات در هر کانال پر (۴ در هر CPU). پهنای باند کامل کانال، با فضای ارتقا.
> - **انتخاب: گزینهٔ ب.** همان پهنای باند، با امکان ارتقا.
>
> **درس:** «همهٔ اسلات پر» هدف نیست؛ «همهٔ کانال‌ها پر» هدف است.

**Lab Scenario 2 — خطای حافظه**

> **وضعیت:** سرور به‌طور تصادفی ری‌استارت می‌شود. در لاگ BMC این خطا ثبت شده:
> `Correctable memory error on DIMM A2, count: 47`
>
> **وظیفه:** این یعنی چه؟ چه می‌کنی؟
>
> **پاسخ:**
> - **Correctable** یعنی ECC خطا را اصلاح کرده؛ سیستم ادامه داده. اما ۴۷ بار در یک بازهٔ کوتاه، الگوی بدی است.
> - **اقدام:** بررسی کنید خطا در حال افزایش است یا نه (BMC log trend). اگر افزایشی است، ماژول را **پیشگیرانه** تعویض کنید.
> - **علت ممکن:** ماژول معیوب، اسلات معیوب، نصب ناقص (درست جا نرفته)، یا گرمای موضعی.
>
> **درس:** خطای correctable را نادیده نگیر. این هشدار پیش از خطای uncorrectable است — و خطای uncorrectable یعنی crash.

### مقایسه و الگوهای مختلف

**سه استراتژی ظرفیت حافظه:**

| استراتژی | توضیح | مزیت | عیب |
|---|---|---|---|
| **پر کردن کامل از ابتدا** | همهٔ اسلات‌ها با ماژول کوچک | حداکثر پهنای باند | ارتقا نیاز به تعویض دارد، هزینهٔ اولیه بالا |
| **حداقل کافی + ارتقا** | فقط کانال‌ها پر، ظرفیت متوسط | ارزان، انعطاف | ممکن است بعداً ماژول کمیاب شود |
| **حداکثر ظرفیت** | ماژول‌های بزرگ | فضای رشد | گران، گاهی کاهش سرعت |

**مقایسهٔ ECC و non-ECC:**

| معیار | non-ECC | ECC |
|---|---|---|
| هزینه | کم | ۱۰–۲۰٪ بیشتر |
| اصلاح خطا | ندارد | تک‌بیتی |
| مناسب برای | دسکتاپ، تست | هر سرور تولیدی |
| نیاز به پشتیبانی CPU+MB | — | بله |

**نکته:** استفاده از non-ECC در سرور تولیدی، یک تصمیم «صرفه‌جویی» است که می‌تواند به قیمت از دست رفتن داده تمام شود. در آزمون، این همیشه جواب غلط است.

**Memory interleaving:** وقتی کانال‌ها متوازن پر شوند، کنترلر می‌تواند دسترسی‌ها را بین کانال‌ها پخش کند و پهنای باند را چند برابر کند. این ویژگی خودکار است، اما **فقط با چیدمان متوازن**.

### اشکال شایع

**۱. مخلوط کردن ماژول‌های مختلف.**
ماژول ۱۶GB با ۳۲GB، یا RDIMM با UDIMM، یا سرعت‌های متفاوت — ممکن است کار کند، اما در سرعت پایین‌تر و با ریسک ناپایداری. همیشه یکسان بخر.

**۲. پر کردن نامتوازن کانال‌ها.**
مثلاً ۳ ماژول در ۴ کانال. پهنای باند کم می‌شود یا سرور بوت نمی‌شود.

**۳. نصب ناقص ماژول.**
اگر کلیپس‌ها کامل بسته نشوند، ماژول درست تماس نمی‌گیرد. علامت: خطای حافظه یا شناسایی نشدن.

**۴. بی‌توجهی به حداکثر ظرفیت.**
مادربرد ۱۲۸GB پشتیبانی می‌کند و تو ۲۵۶GB می‌خری. سرور بوت می‌شود اما فقط بخشی را می‌بیند — یا بوت نمی‌شود.

**۵. فرض اینکه «RAM بیشتر همیشه بهتر».**
اگر workload حافظه‌بر نیست، RAM اضافه فقط هزینه است. برای فایل سرور، ۳۲GB کافی است؛ ۲۵۶GB هدر.

**۶. نادیده گرفتن NUMA در تخصیص VM.**
در سرور دو‌سوکتی، اگر یک VM با ۳۲ vCPU روی دو NUMA node پخش شود، عملکردش افت می‌کند. تنظیم `numa affinity` یا اندازهٔ VM متناسب با NUMA node مهم است.

### نکات مهم (Tips & Tricks)

- **همیشه از دفترچهٔ مادربرد، ترتیب اسلات را چک کن.** این ۵ دقیقه، از ۲ ساعت عیب‌یابی جلوگیری می‌کند.
- **ماژول‌ها را با یک برند و یک مدل بخر.** در خرید اول، تعداد بیشتری بخر تا بعداً همان مدل را داشته باشی.
- **خطای correctable را در مانیتورینگ هشدار بگذار.** آستانه: مثلاً >۱۰ در ۲۴ ساعت.
- **قبل از تعویض ماژول، اسلات را هم تست کن.** گاهی اسلات خراب است، نه ماژول.
- **در سرورهای با RAM زیاد، بوت طولانی‌تر است** (memory training). ۲–۵ دقیقه طبیعی است.
- **در آزمون:** اگر سؤال «server won't boot after adding RAM» داد، جواب اول: **چیدمان/سازگاری ماژول**، نه «RAM خراب است».

### خلاصه فصل

- **ECC** در سرور الزامی است: خطای تک‌بیتی را اصلاح، دوبیتی را تشخیص می‌دهد.
- **RDIMM** استاندارد سرور؛ **LRDIMM** برای ظرفیت بالا.
- هدف چیدمان: **پر کردن همهٔ کانال‌ها با ظرفیت مساوی**، نه همهٔ اسلات‌ها.
- DDR4 و DDR5 ناسازگارند؛ ارتقا = تعویض مادربرد.
- خطای correctable را جدی بگیر؛ پیش‌درآمد خطای uncorrectable است.

## فصل ۱۲: مادربرد، باس و اسلات‌های توسعه

### مقدمه

مادربرد، صفحهٔ اصلی است که همه چیز را به هم وصل می‌کند. در سرور، مادربرد خیلی بیشتر از یک «بورد» است: مسیرهای PCIe، کنترلر حافظه، پورت‌های مدیریت، و گاهی کنترلر RAID روی برد.

این فصل دربارهٔ چیزی است که کمتر دیده می‌شود اما بیشترین اثر را روی قابلیت ارتقا دارد: **اسلات‌ها، laneها و riserها**.

### مفاهیم اساسی

**اجزای مادربرد سرور:**

- **سوکت CPU** (۱، ۲ یا ۴)
- **اسلات حافظه** (۶–۲۴)
- **اسلات PCIe** (برای کارت شبکه، HBA، GPU)
- **کنترلر ذخیره‌سازی** (onboard یا کارت جدا)
- **پورت‌های مدیریت** (BMC، iDRAC، iLO)
- **پورت‌های USB/سریال** (برای نصب و کنسول)
- **باتری CMOS** (نگه داشتن تنظیمات BIOS)
- **VRM** (تنظیم ولتاژ CPU)

**PCIe — نسل‌ها و پهنای باند:**

| نسل | پهنای باند هر lane | x16 | x8 | x4 |
|---|---|---|---|---|
| **PCIe 3.0** | ~۱ GB/s | ~۱۶ GB/s | ~۸ GB/s | ~۴ GB/s |
| **PCIe 4.0** | ~۲ GB/s | ~۳۲ GB/s | ~۱۶ GB/s | ~۸ GB/s |
| **PCIe 5.0** | ~۴ GB/s | ~۶۴ GB/s | ~۳۲ GB/s | ~۱۶ GB/s |
| **PCIe 6.0** | ~۸ GB/s | ~۱۲۸ GB/s | ~۶۴ GB/s | ~۳۲ GB/s |

**نکتهٔ مهم:** کارت PCIe 4.0 در اسلات 3.0 کار می‌کند، اما با سرعت 3.0. **سازگاری عقب‌رو وجود دارد، سازگاری جلو‌رو نه.**

**انواع اسلات فیزیکی:**

- **x16** — برای GPU، NIC پرسرعت، HBA
- **x8** — برای NIC معمولی، HBA
- **x4** — برای کارت‌های کم‌پهنای‌باند
- **x1** — به‌ندرت در سرور

**Riser card:** یک برد کوچک که اسلات PCIe را **چرخانده** و به شکل افقی در می‌آورد تا کارت در ارتفاع ۱U/۲U جا شود. سرورهای رکی تقریباً همیشه riser دارند.

```
[مادربرد] --PCIe--> [Riser] --x16--> [کارت شبکه]
```

**نکتهٔ حیاتی:** riser می‌تواند **تعداد lane را کاهش دهد**. یک riser که x16 را به دو x8 تقسیم می‌کند، دو کارت می‌دهد اما هر کدام نصف پهنای باند. در خرید سرور، **map اسلات‌ها** را از دفترچه بخوان.

**Chipset / PCH:** پل ارتباطی بین CPU و دستگاه‌های کم‌سرعت‌تر (USB، SATA، LAN onboard). در سرورهای مدرن، بیشتر PCIe مستقیم به CPU وصل است و chipset فقط لوازم جانبی را مدیریت می‌کند.

**Bifurcation:** تقسیم یک اسلات x16 به دو x8 یا چهار x4. برای NVMe carrier card ضروری است. باید در BIOS فعال شود و مادربرد پشتیبانی کند.

**CMOS و BIOS/UEFI:**

- **BIOS/UEFI** — firmware پایه.
- **CMOS battery** — تنظیمات و ساعت را نگه می‌دارد. عمر ۵–۱۰ سال. علامت تمام شدن: ساعت عقب می‌رود، تنظیمات ری‌ست می‌شود.
- **Secure Boot** — جلوگیری از بوت کد امضانشده.

**فرم‌فاکتور مادربرد:** در سرور، مادربرد معمولاً **اختصاصی سازنده** است (proprietary)، نه استاندارد ATX. یعنی ارتقای مادربرد بین برندها ممکن نیست. این نکتهٔ مهمی در خرید است.

### مثال‌های عملی

**Lab Scenario 1 — کمبود lane**

> **وضعیت:** سرور با CPU که ۴۰ lane PCIe دارد. می‌خواهی:
> - ۲ کارت شبکهٔ ۱۰۰GbE (هر کدام x16)
> - ۱ HBA ذخیره‌سازی (x8)
> - ۲۴ دیسک NVMe
>
> **وظیفه:** آیا ممکن است؟
>
> **پاسخ:**
> - ۲×۱۶ = ۳۲ lane
> - ۱×۸ = ۸ lane
> - جمع: **۴۰ lane** — دقیقاً پر
> - ۲۴ NVMe: هر NVMe معمولاً x4 = ۹۶ lane. **غیرممکن.**
>
> **راه‌حل‌ها:**
> ۱. استفاده از **backplane با PCIe switch** — یک سوئیچ روی backplane که ۲۴ درایو را با چند lane مدیریت می‌کند (اما پهنای باند اشتراکی).
> ۲. کاهش تعداد NVMe یا استفاده از SAS/SATA برای بخشی.
> ۳. CPU با lane بیشتر (مثلاً ۸۰ یا ۱۲۸).
>
> **درس:** در ذخیره‌سازی all-flash، lane معادل ظرفیت است.

**Lab Scenario 2 — کارت در اسلات اشتباه**

> **وضعیت:** کارت شبکهٔ ۲۵GbE در اسلات x4 نصب شده. سرور کار می‌کند اما throughput از ۱۰Gbps بالاتر نمی‌رود.
>
> **وظیفه:** چرا؟
>
> **پاسخ:**
> - اسلات x4 با PCIe 3.0: ۴ × ۱ GB/s ≈ **۴ GB/s ≈ ۳۲ Gbps** تئوری
> - اما کارت ۲۵GbE به x8 نیاز دارد (۲۵Gbps دوطرفه + سربار)
> - در x4، کارت در حالت کاهش‌یافته کار می‌کند یا bottleneck ایجاد می‌شود.
>
> **درس:** همیشه **نقشهٔ اسلات** را چک کن. اسلات فیزیکی x16 ممکن است الکتریکی x4 باشد.

### مقایسه و الگوهای مختلف

**سه رویکرد به expansion:**

| رویکرد | توضیح | مزیت | عیب |
|---|---|---|---|
| **Onboard** | NIC/RAID روی مادربرد | ارزان، بدون اسلات | انعطاف کم، تعویض سخت |
| **Add-in card** | کارت جدا در اسلات | انعطاف، ارتقا | مصرف اسلات و lane |
| **Riser + carrier** | چند دستگاه روی یک اسلات | تراکم | پیچیدگی، کاهش lane هر دستگاه |

**مقایسهٔ RAID onboard و کارت جدا:**

| معیار | Onboard | کارت جدا (HBA/RAID) |
|---|---|---|
| هزینه | صفر (شامل سرور) | ۲۰۰–۱۰۰۰ دلار |
| cache | کوچک یا بدون | بزرگ (۱–۴GB) با battery |
| پشتیبانی از دیسک زیاد | محدود | بالا |
| تعویض بین سرورها | نه | بله |
| مناسب برای | ۲–۴ دیسک | ۸+ دیسک، RAID پیشرفته |

**نکتهٔ مهم دربارهٔ cache و battery:** کارت RAID با cache و **battery backup unit (BBU)** می‌تواند write-back کند (سریع). اگر باتری تمام شود، کارت به write-through می‌رود (کند). این یکی از دلایل «سرور بعد از دو سال کند شد» است.

### اشکال شایع

**۱. فرض اینکه اسلات x16 همیشه x16 است.**
خیلی از مادربردها اسلات فیزیکی x16 با **مسیر الکتریکی x4** دارند. در دفترچه چک کن.

**۲. نصب کارت در اسلاتی که با riser اشتراک دارد.**
دو اسلات ممکن است lane را تقسیم کنند. پر کردن یکی، دیگری را کند می‌کند.

**۳. بی‌توجهی به bifurcation.**
کارت carrier با ۴ NVMe، بدون فعال کردن bifurcation در BIOS، فقط یک دیسک را می‌بیند.

**۴. فراموش کردن براکت و ارتفاع کارت.**
کارت full-height در سرور ۱U جا نمی‌شود. باید low-profile باشد.

**۵. تعویض مادربرد بین برندها.**
مادربرد سرور proprietary است. مادربرد Dell در شاسی HPE نصب نمی‌شود.

**۶. نادیده گرفتن باتری CMOS.**
سروری که بعد از هر قطعی برق، تاریخ و تنظیمات بوت را از دست می‌دهد، باتری CMOS مرده دارد.

### نکات مهم (Tips & Tricks)

- **نقشهٔ اسلات را روی کاغذ بکش.** کدام اسلات از کدام CPU می‌آید، چند lane، چه ارتفاعی. این سند در ارتقا و عیب‌یابی طلاست.
- **برای کارت‌های حساس (HBA، NIC)، اسلاتی انتخاب کن که مستقیم به CPU وصل است**، نه از chipset.
- **BIOS را قبل از نصب کارت جدید آپدیت کن.** گاهی کارت جدید در BIOS قدیم شناسایی نمی‌شود.
- **در سرور ۱U، فقط کارت low-profile.** ارتفاع را از قبل چک کن.
- **باتری CMOS را هر ۵ سال پیشگیرانه عوض کن.** هزینهٔ ناچیز، جلوگیری از دردسر.
- **در آزمون:** کلیدواژهٔ «card not detected» → **اسلات، riser، BIOS، سازگاری** — نه «کارت خراب».

### خلاصه فصل

- **PCIe lane** منبع محدود است؛ نقشهٔ اسلات را از دفترچه بخوان.
- اسلات فیزیکی x16 ممکن است الکتریکی x4 باشد.
- **Riser** کارت را می‌چرخاند اما ممکن است lane را کاهش دهد.
- **Bifurcation** برای NVMe carrier ضروری است.
- مادربرد سرور proprietary است؛ ارتقا بین برندها ممکن نیست.
- باتری CMOS عمر ۵–۱۰ سال دارد.

## فصل ۱۳: منبع تغذیه و افزونگی برق

### مقدمه

PSU (Power Supply Unit) قطعه‌ای است که وقتی کار می‌کند، کسی به آن فکر نمی‌کند — و وقتی نمی‌کند، همه چیز می‌خوابد. در سرور، PSU تنها منبع تغذیه نیست؛ یک **سیستم افزونه** است.

این فصل دربارهٔ توان، بازدهی، افزونگی و تعویض hot-swap است.

### مفاهیم اساسی

**مشخصات PSU سرور:**

- **توان نامی (Wattage)** — مثلاً ۸۰۰W، ۱۱۰۰W، ۱۶۰۰W. این **حداکثر** است، نه مصرف واقعی.
- **بازدهی (Efficiency)** — نسبت توان خروجی به ورودی. با استاندارد **80 PLUS** اندازه‌گیری می‌شود:

| سطح | بازدهی در ۵۰٪ بار |
|---|---|
| 80 PLUS White | ۸۰٪ |
| Bronze | ۸۵٪ |
| Silver | ۸۸٪ |
| Gold | ۹۰٪ |
| Platinum | ۹۴٪ |
| Titanium | ۹۶٪ |

**نکتهٔ مهم:** بازدهی ۹۰٪ یعنی ۱۰٪ توان به گرما تبدیل می‌شود. PSU با بازدهی پایین‌تر، گرمای بیشتری تولید می‌کند و سرمایش بیشتری می‌خواهد. در رک پر، این تفاوت محسوس است.

**منحنی بازدهی:** PSU در ۵۰٪ بار، بهترین بازدهی را دارد. در ۱۰٪ بار یا ۱۰۰٪ بار، بازدهی کمتر است. به همین دلیل، PSU بزرگ برای بار کم، **ناکارآمد** است.

**انواع افزونگی:**

| پیکربندی | توضیح | تحمل خرابی |
|---|---|---|
| **۱ PSU** | بدون افزونگی | صفر |
| **1+1** | دو PSU، هر کدام توان کل | یک PSU |
| **2+1** | سه PSU، دو تا کافی | یک PSU |
| **2+2** | چهار PSU، دو مسیر مستقل | دو PSU (یک مسیر) |

**نکتهٔ کلیدی:** در 1+1، **هر PSU باید بتواند به‌تنهایی کل بار را تأمین کند**. اگر دو PSU ۸۰۰W داشته باشی و بار ۹۰۰W باشد، خرابی یکی یعنی خاموشی.

**Hot-swap:** PSU را می‌شود بدون خاموش کردن سرور تعویض کرد — به شرطی که PSU دوم سالم و بار کافی باشد. مراحل:

۱. کابل PSU معیوب را از PDU جدا کن (یا بریکر آن را قطع کن).
۲. دستهٔ PSU را باز کن.
۳. PSU را بیرون بکش.
۴. PSU جدید را وارد کن تا کلیک شود.
۵. کابل را وصل کن.
۶. LED و BMC را چک کن.

> ⚠️ **هشدار:** در بعضی سرورها، اگر هر دو PSU را هم‌زمان بکشی، سرور خاموش می‌شود. همیشه یکی‌یکی.

**Load balancing بین دو PSU:** در حالت فعال-فعال، بار بین دو PSU تقسیم می‌شود (۵۰/۵۰). در حالت فعال-غیرفعال، یکی تمام بار را می‌برد و دیگری standby است. حالت اول رایج‌تر است، چون هر دو در بار بهینه‌تر کار می‌کنند.

**مصرف واقعی — تخمین:**

```
مصرف واقعی ≈ (تعداد CPU × TDP × 0.7) + (تعداد دیسک × 8W) + (RAM × 3W/16GB) + 50W پایه
```

این فرمول تقریبی است. بهترین راه، خواندن از BMC یا PDU metered است.

**Redundant power feed:** دو مسیر برق مستقل از دو UPS و دو بریکر. اگر یک مسیر برق قطع شود، مسیر دیگر کار می‌کند. این تفاوت **افزونگی PSU** و **افزونگی مسیر** است — هر دو لازم‌اند.

### مثال‌های عملی

**Lab Scenario 1 — انتخاب توان PSU**

> **وضعیت:** سرور با ۲ CPU (TDP ۲۰۵W)، ۱۶ دیسک ۲.۵ اینچی، ۵۱۲GB RAM. می‌خواهی افزونگی 1+1 با حاشیهٔ ۳۰٪.
>
> **وظیفه:** توان هر PSU؟
>
> **پاسخ:**
> - CPU: ۲ × ۲۰۵ × ۰.۷ = **۲۸۷W**
> - دیسک: ۱۶ × ۸ = **۱۲۸W**
> - RAM: ۵۱۲ ÷ ۱۶ × ۳ = **۹۶W**
> - پایه (فن، مادربرد، NIC): **۵۰W**
> - جمع: **۵۶۱W**
> - با حاشیهٔ ۳۰٪: ۵۶۱ × ۱.۳ = **۷۲۹W**
> - انتخاب: **PSU ۸۰۰W** (یا ۱۱۰۰W برای رشد)
>
> **درس:** در 1+1، هر PSU باید کل بار را با حاشیه تحمل کند. ۸۰۰W درست است، نه ۴۰۰W.

**Lab Scenario 2 — تشخیص خرابی PSU**

> **وضعیت:** سرور روشن است، اما در BMC دو هشدار:
> `PSU 2: Input lost`
> `PSU 1: 92% load`
>
> **وظیفه:** وضعیت را تحلیل کن.
>
> **پاسخ:**
> - PSU 2 برق ورودی ندارد (کابل، PDU، یا بریکر).
> - PSU 1 با ۹۲٪ بار کار می‌کند — **بحرانی**، بالای آستانهٔ ۸۰٪.
> - اگر PSU 1 هم برق از دست بدهد، سرور خاموش می‌شود.
>
> **اقدام فوری:**
> ۱. مسیر برق PSU 2 را چک کن (کابل، PDU، UPS).
> ۲. اگر PSU 2 مرده، تعویض hot-swap.
> ۳. تا حل شدن، بار را کم کن (VM غیرضروری را خاموش کن).
>
> **درس:** هشدار «input lost» را با «PSU failed» اشتباه نگیر. اول مسیر برق را چک کن.

### مقایسه و الگوهای مختلف

**سه پیکربندی برق در رک:**

| پیکربندی | توضیح | هزینه | تحمل خرابی |
|---|---|---|---|
| **Single PDU** | یک PDU، یک UPS | کم | صفر |
| **A/B PDU** | دو PDU از دو UPS | متوسط | یک PDU/UPS |
| **A/B + ژنراتور** | دو مسیر + ژنراتور | بالا | قطعی برق شهری |

**مقایسهٔ حالت‌های PSU:**

| حالت | توضیح | مزیت | عیب |
|---|---|---|---|
| **Active/Active** | هر دو بار می‌برند | بازدهی بهتر، عمر یکسان | در بار کم، بازدهی پایین‌تر |
| **Active/Standby** | یکی بار، یکی آماده | ساده | PSU standby ممکن است خراب شود و کسی نداند |

**نکته:** در Active/Standby، باید **دوره‌ای PSUها را جابه‌جا کنی** تا هر دو تست شوند. بعضی سرورها این را خودکار انجام می‌دهند.

**مقایسهٔ PSU ماژولار و ثابت:**

| معیار | ماژولار (hot-swap) | ثابت |
|---|---|---|
| تعویض بدون خاموشی | ✅ | ❌ |
| هزینه | بیشتر | کمتر |
| تعمیرپذیری | آسان | نیاز به باز کردن سرور |
| در سرور رکی | استاندارد | نادر |

### اشکال شایع

**۱. محاسبهٔ توان با جمع وات نامی PSU.**
دو PSU ۸۰۰W یعنی حداکثر ۸۰۰W برای سرور (در 1+1)، نه ۱۶۰۰W.

**۲. بار کردن PSU بالای ۸۰٪.**
بازدهی افت می‌کند، گرما زیاد می‌شود، عمر باتری UPS کم می‌شود.

**۳. وصل کردن هر دو PSU به یک PDU.**
افزونگی PSU بی‌فایده می‌شود. باید به دو PDU مستقل (از دو UPS) وصل شوند.

**۴. کشیدن هر دو PSU هم‌زمان.**
سرور خاموش می‌شود. یکی‌یکی.

**۵. نادیده گرفتن «input lost».**
این هشدار یعنی مسیر برق مشکل دارد — اغلب کابل یا PDU، نه خود PSU. اگر تعویض کنی و مشکل حل نشود، وقت تلف کرده‌ای.

**۶. خرید PSU با توان بسیار بالا برای بار کم.**
بازدهی در ۱۰٪ بار، بدترین است. PSU متناسب بخر.

### نکات مهم (Tips & Tricks)

- **قاعدهٔ ۸۰٪** برای بار PSU و PDU.
- **در 1+1، هر PSU باید کل بار + ۳۰٪ را تحمل کند.**
- **برچسب بزن:** PSU-1 → PDU-A، PSU-2 → PDU-B. در بحران، این برچسب نجات‌دهنده است.
- **مصرف واقعی را از BMC بخوان، نه از حدس.** iDRAC/iLO و IPMI توان ورودی را گزارش می‌کنند.
- **PSU یدکی در انبار داشته باش.** مدل دقیق را یادداشت کن؛ PSU سرورها با هم سازگار نیست.
- **در آزمون:** اگر سؤال «redundant PSU but server shut down on PSU failure» داد، جواب: **هر دو PSU به یک منبع/PDU وصل بوده‌اند** یا **بار بیش از توان یک PSU بوده**.

### خلاصه فصل

- PSU توان **نامی** دارد، نه مصرف واقعی.
- بازدهی با **80 PLUS** سنجیده می‌شود؛ بهترین بازدهی در ۵۰٪ بار.
- **1+1** یعنی هر PSU باید کل بار را تحمل کند.
- **Hot-swap** فقط با PSU سالم دوم ممکن است؛ یکی‌یکی.
- افزونگی PSU بدون **افزونگی مسیر (A/B)** بی‌فایده است.
- «Input lost» اول مشکل مسیر برق است، نه PSU.

## فصل ۱۴: رسانه‌های ذخیره‌سازی داخلی — HDD، SSD، NVMe

### مقدمه

ذخیره‌سازی، کندترین بخش هر سرور است و بیشترین تأثیر را روی تجربهٔ کاربر دارد. یک سرور با CPU متوسط و NVMe، از یک سرور با CPU قوی و HDD سریع‌تر است — برای بیشتر workloadها.

این فصل دربارهٔ سه نسل رسانه و انتخاب درست آن‌هاست. در آزمون، سؤال‌های مربوط به انواع دیسک، interface و محاسبهٔ ظرفیت/عملکرد می‌آید.

### مفاهیم اساسی

**سه نوع رسانه:**

**۱. HDD (Hard Disk Drive)** — دیسک مغناطیسی چرخان.

- **RPM** (دور در دقیقه): ۵۴۰۰، ۷۲۰۰، ۱۰۰۰۰، ۱۵۰۰۰.
- **IOPS تقریبی:** ۷۲۰۰ RPM ≈ ۷۵–۱۰۰ IOPS؛ ۱۵K RPM ≈ ۱۸۰–۲۱۰ IOPS.
- **مزیت:** ظرفیت بالا با قیمت کم (مثلاً ۲۰TB).
- **عیب:** کند، حساس به ضربه، مصرف برق بیشتر، تولید صدا و گرما.
- **کاربرد:** backup، آرشیو، فایل سرور با حجم زیاد.

**۲. SSD (Solid State Drive)** — حافظهٔ فلش (NAND).

- **IOPS:** هزاران تا صدها هزار (بسته به نوع).
- **مزیت:** سریع، بی‌صدا، کم‌مصرف، مقاوم به ضربه.
- **عیب:** گران‌تر به ازای هر GB، عمر محدود (TBW/DWPD).
- **انواع سلول:**

| نوع | بیت در سلول | عمر | هزینه | کاربرد |
|---|---|---|---|---|
| **SLC** | ۱ | بالاترین | بالاترین | enterprise حیاتی |
| **MLC** | ۲ | بالا | بالا | enterprise |
| **TLC** | ۳ | متوسط | متوسط | رایج امروز |
| **QLC** | ۴ | پایین‌تر | پایین | خواندن‌محور |

- **DWPD (Drive Writes Per Day)** — چند بار در روز می‌شود کل ظرفیت را نوشت. مثلاً ۱ DWPD روی ۱TB = ۱TB نوشتن در روز به مدت ۵ سال.
- **TBW (Total Bytes Written)** — مجموع نوشتن تا پایان عمر.

**۳. NVMe (Non-Volatile Memory Express)** — پروتکل جدید روی PCIe.

- **سرعت:** تا ۷۰۰۰+ MB/s (PCIe 4.0) و بیشتر.
- **IOPS:** صدها هزار تا میلیون.
- **مزیت:** کمترین latency، بالاترین throughput، صف عمیق (۶۴K صف، ۶۴K دستور در صف).
- **عیب:** مصرف برق و گرما (به‌خصوص Gen4/Gen5)، نیاز به خنک‌کننده.
- **فرم‌فاکتور:** U.2 (۲.۵ اینچ)، M.2، E1.S/E3.S (EDSFF)، add-in card.

**مقایسهٔ interface:**

| Interface | پروتکل | حداکثر سرعت | فرم‌فاکتور |
|---|---|---|---|
| **SATA** | AHCI | ~۶۰۰ MB/s | ۲.۵"، ۳.۵" |
| **SAS** | SCSI | ~۲۴۰۰ MB/s (12G) | ۲.۵"، ۳.۵" |
| **NVMe** | PCIe | ۳۵۰۰–۱۴۰۰۰ MB/s | U.2، M.2، EDSFF |

**نکتهٔ مهم:** SATA و SAS **سازگاری محدود** دارند: دیسک SATA را می‌شود به کنترلر SAS وصل کرد، اما برعکس نه. و NVMe فقط با کنترلر/backplane سازگار NVMe کار می‌کند.

**مفاهیم عملکردی:**

- **Sequential** (ترتیبی) — خواندن/نوشتن پیوسته. مهم برای backup و فایل بزرگ.
- **Random** (تصادفی) — دسترسی پراکنده. مهم برای دیتابیس و VM.
- **Latency** — تأخیر هر عملیات. HDD: ۵–۱۰ms؛ SSD SATA: ۰.۱ms؛ NVMe: ۰.۰۲ms.
- **Queue depth** — تعداد درخواست هم‌زمان در صف. NVMe تا ۶۴K، SATA تا ۳۲.

**نکتهٔ حیاتی:** یک SSD SATA در دسترسی تصادفی، حدود ۱۰۰ برابر HDD سریع‌تر است. NVMe حدود ۵–۱۰ برابر SSD SATA در throughput و ۲–۳ برابر در IOPS تصادفی. برای بیشتر workloadها، **SSD کافی است**؛ NVMe برای بارهای سنگین.

**Wear leveling و TRIM:** SSD سلول‌ها را یکنواخت مصرف می‌کند. **TRIM** به SSD می‌گوید کدام بلوک آزاد است. بدون TRIM، عملکرد و عمر کاهش می‌یابد. در ویندوز خودکار است؛ در لینوکس باید `fstrim.timer` فعال باشد.

### مثال‌های عملی

**Lab Scenario 1 — انتخاب رسانه برای سه نقش**

> **وظیفه:** برای هر نقش، رسانه پیشنهاد بده.
>
> الف) آرشیو backup با ۵۰TB
> ب) دیتابیس PostgreSQL با ۲۰۰۰ IOPS
> ج) میزبانی ۳۰ VM
>
> **پاسخ:**
>
> | نقش | رسانه | دلیل |
> |---|---|---|
> | الف | HDD ۷۲۰۰ RPM در RAID 6 | هزینهٔ هر TB پایین، دسترسی ترتیبی |
> | ب | SSD NVMe (TLC با ۳+ DWPD) | IOPS و latency پایین |
> | ج | NVMe یا SSD SATA در RAID 10 | IOPS بالا، تحمل خرابی |
>
> **درس:** «بهترین رسانه» وجود ندارد؛ «مناسب‌ترین برای الگوی I/O» وجود دارد.

**Lab Scenario 2 — محاسبهٔ عمر SSD**

> **وضعیت:** SSD با ظرفیت ۱.۹۲TB و ۱ DWPD، در یک سرور دیتابیس که روزانه ۱.۵TB می‌نویسد.
>
> **وظیفه:** عمر تخمینی؟
>
> **پاسخ:**
> - ظرفیت نوشتن روزانهٔ طراحی: ۱.۹۲TB × ۱ = ۱.۹۲ TB/day
> - نوشتن واقعی: ۱.۵ TB/day
> - نسبت: ۱.۵ ÷ ۱.۹۲ ≈ **۷۸٪ از بودجهٔ روزانه**
> - عمر گارانتی معمولاً ۵ سال: ۱.۹۲ × ۳۶۵ × ۵ = **۳٬۵۰۴ TB** (TBW)
> - مصرف واقعی سالانه: ۱.۵ × ۳۶۵ = ۵۴۷.۵ TB
> - عمر تخمینی: ۳٬۵۰۴ ÷ ۵۴۷.۵ ≈ **۶.۴ سال**
>
> **درس:** DWPD را با نوشتن واقعی مقایسه کن، نه با حدس. اگر نوشتن بالای ۱ DWPD باشد، SSD زودتر می‌میرد.

### مقایسه و الگوهای مختلف

**سه سطح ذخیره‌سازی (tiering):**

| سطح | رسانه | کاربرد | هزینه/GB |
|---|---|---|---|
| **Tier 0/1** | NVMe | دیتابیس، VM پرترافیک | بالا |
| **Tier 2** | SSD SATA/SAS | فایل سرور، VM متوسط | متوسط |
| **Tier 3** | HDD (Nearline) | آرشیو، backup | کم |

**مقایسهٔ RAID با رسانه (اشاره به فصل ۱۸):**

| ترکیب | مناسب برای |
|---|---|
| HDD + RAID 6 | آرشیو، ظرفیت بالا |
| SSD + RAID 5 | تعادل عملکرد/ظرفیت |
| NVMe + RAID 10 | دیتابیس پرترافیک |

**مقایسهٔ U.2 و M.2 در سرور:**

| معیار | U.2 | M.2 |
|---|---|---|
| hot-swap | ✅ (با backplane) | ❌ |
| محل نصب | بای جلو | اسلات روی مادربرد |
| خنک‌سازی | بهتر | محدود |
| ظرفیت | بالا | متوسط |
| مناسب برای | سرور تولیدی | سرور کوچک، boot drive |

**نکته:** M.2 برای boot عالی است، اما برای دادهٔ تولیدی، U.2 با hot-swap امن‌تر است.

### اشکال شایع

**۱. استفاده از SSD مصرفی در سرور.**
SSDهای consumer DWPD پایین (۰.۱–۰.۳) دارند و در نوشتن پیوسته سریع می‌میرند. همیشه enterprise/read-intensive یا mixed-use.

**۲. فرض اینکه NVMe همیشه بهتر است.**
NVMe گرمای زیادی تولید می‌کند و در ۲U با ۲۴ درایو، سرمایش چالش است. گاهی SSD SATA کافی و خنک‌تر است.

**۳. نادیده گرفتن TRIM.**
SSD بدون TRIM، بعد از پر شدن، به‌شدت کند می‌شود.

**۴. RAID روی SSDهای بدون power-loss protection.**
SSD مصرفی ممکن است در قطعی برق، دادهٔ cache را از دست بدهد. SSD enterprise دارای **PLP** است.

**۵. مخلوط کردن HDD و SSD در یک آرایه بدون برنامه.**
RAID 5 از ۴ HDD و ۱ SSD، عملکرد را به کندترین عضو می‌رساند.

**۶. بی‌توجهی به فرم‌فاکتور.**
دیسک ۳.۵ اینچی در بای ۲.۵ اینچی جا نمی‌شود (بدون interposer). قبل از خرید، بای و backplane را چک کن.

### نکات مهم (Tips & Tricks)

- **برای boot، دو دیسک کوچک در RAID 1** جدا از آرایهٔ داده. این کار بازیابی را ساده می‌کند.
- **درایو یدکی (spare) داشته باش.** دیسک هم‌مدل، در انبار.
- **SMART را پایش کن.** `smartctl -a /dev/sda` — دنبال `Reallocated_Sector_Ct` و `Media_Wearout`.
- **دمای NVMe را پایش کن.** بالای ۷۰ درجه throttle می‌کند.
- **برای backup، HDD Nearline با RAID 6.** برای restore سریع، یک لایه SSD cache.
- **در آزمون:** کلیدواژهٔ «high IOPS» → SSD/NVMe؛ «large capacity low cost» → HDD؛ «random read heavy» → NVMe.

### خلاصه فصل

- سه رسانه: **HDD** (ظرفیت ارزان)، **SSD** (تعادل)، **NVMe** (حداکثر عملکرد).
- **SATA ≈ ۶۰۰MB/s، SAS ≈ ۲۴۰۰MB/s، NVMe = هزاران MB/s**.
- **DWPD/TBW** عمر SSD را تعیین می‌کند؛ مصرفی را در سرور استفاده نکن.
- **TRIM** برای حفظ عملکرد SSD ضروری است.
- Tiering: NVMe برای داغ‌ترین، HDD برای سردترین داده.
- فرم‌فاکتور و سازگاری backplane را قبل از خرید چک کن.

## فصل ۱۵: کارت شبکه، HBA و اتصال ذخیره‌سازی

### مقدمه

سرور بدون شبکه، یک جزیره است. و سرور بدون اتصال ذخیره‌سازی، محدود به دیسک داخلی. این فصل دربارهٔ دو کارت مهم است که اغلب اشتباه گرفته می‌شوند: **NIC** (شبکه) و **HBA** (اتصال ذخیره‌سازی).

تفاوت را از الان بگویم: NIC بسته‌های شبکه را جابه‌جا می‌کند؛ HBA دستورهای ذخیره‌سازی را. گاهی یکی هر دو کار را می‌کند (مثل iSCSI HBA یا CNA)، اما مفهومشان متفاوت است.

### مفاهیم اساسی

**NIC (Network Interface Card):**

- **سرعت:** 1GbE، 10GbE، 25GbE، 40GbE، 100GbE، 200/400GbE.
- **پورت:** ۱، ۲ یا ۴ پورت در یک کارت.
- **Interface:** PCIe x4/x8/x16.
- **ویژگی‌های سروری:**
  - **Teaming/Bonding** — چند پورت به‌عنوان یک رابط منطقی (افزونگی یا تجمیع پهنای باند).
  - **SR-IOV** — اختصاص مستقیم NIC به VM برای عملکرد بالا.
  - **RDMA** (RoCE/iWARP) — دسترسی مستقیم به حافظهٔ سرور دیگر، با latency بسیار کم.
  - **TOE** (TCP Offload Engine) — پردازش TCP روی کارت.
  - **Wake-on-LAN / PXE** — بوت از شبکه.

**انواع teaming/bonding:**

| حالت | توضیح | افزونگی | تجمیع |
|---|---|---|---|
| **Active/Backup** (mode 1) | یکی فعال، یکی standby | ✅ | ❌ |
| **LACP / 802.3ad** (mode 4) | تجمیع با سوئیچ | ✅ | ✅ |
| **Balance-XOR** (mode 2) | توزیع بر اساس hash | ✅ | ✅ (بدون پشتیبانی سوئیچ) |
| **Broadcast** (mode 3) | ارسال روی همه | ✅ | ❌ |
| **Adaptive load balancing** (mode 6) | توزیع + افزونگی | ✅ | ✅ |

**نکتهٔ مهم:** LACP باید در **هر دو طرف** (سرور و سوئیچ) پیکربندی شود. اگر فقط در سرور فعال کنی، کار نمی‌کند.

**HBA (Host Bus Adapter):**

- **FC HBA** — اتصال به SAN با Fibre Channel. سرعت ۸/۱۶/۳۲/۶۴ GFC.
- **iSCSI HBA** — اتصال به SAN با Ethernet، اما با offload.
- **SAS HBA** — اتصال دیسک‌های SAS داخلی یا JBOD.
- **CNA (Converged Network Adapter)** — ترکیب NIC و FC HBA (FCoE).

**تفاوت HBA و RAID controller:**

| ویژگی | HBA | RAID Controller |
|---|---|---|
| RAID | ندارد (pass-through) | دارد |
| cache | ندارد | دارد (با BBU) |
| مناسب برای | ZFS، Storage Spaces، vSAN | RAID سخت‌افزاری سنتی |
| هزینه | کمتر | بیشتر |

**نکتهٔ مهم:** برای **ZFS** و **vSAN**، باید HBA در حالت **IT mode** (pass-through) باشد، نه RAID. RAID سخت‌افزاری، اطلاعات دیسک را از نرم‌افزار پنهان می‌کند و ZFS نمی‌تواند کار کند.

**مفاهیم اتصال:**

- **SFP/SFP+** — ترنسیور (فرستنده-گیرندهٔ نوری) برای فیبر یا DAC.
- **QSFP/QSFP28** — برای ۴۰/۱۰۰GbE.
- **DAC** — کابل مسی مستقیم، ارزان، کوتاه.
- **AOC** — کابل نوری فعال، برای فاصلهٔ متوسط.
- **Transceiver compatibility** — ماژول باید با برند سوئیچ/کارت سازگار باشد (بعضی برندها قفل vendor دارند).

**Multipath I/O (MPIO):** در اتصال به SAN، دو مسیر فیزیکی جدا (دو HBA، دو سوئیچ) به یک LUN. اگر یک مسیر قطع شود، مسیر دیگر کار می‌کند. این افزونگی در سطح **مسیر** است، نه دیسک.

### مثال‌های عملی

**Lab Scenario 1 — طراحی شبکهٔ افزونه**

> **وضعیت:** سرور با ۴ پورت 10GbE. می‌خواهی افزونگی + حداکثر پهنای باند برای ترافیک VM.
>
> **وظیفه:** چه پیکربندی؟
>
> **پاسخ:**
> - **گزینهٔ الف: LACP با ۴ پورت** — ۴۰Gbps تجمیعی، تحمل خرابی یک پورت. نیاز به پیکربندی سوئیچ.
> - **گزینهٔ ب: دو bond جدا** — دو پورت برای VM traffic، دو پورت برای iSCSI/backup. جداسازی ترافیک.
> - **توصیه: گزینهٔ ب** برای محیط تولیدی، چون ترافیک ذخیره‌سازی و مدیریت را جدا می‌کند.
>
> **درس:** «همهٔ پورت‌ها در یک bond» ساده است اما جداسازی ترافیک را از دست می‌دهی.

**Lab Scenario 2 — تشخیص bottleneck شبکه**

> **وضعیت:** سرور با NIC 25GbE، اما انتقال فایل از ۲.۵Gbps بالاتر نمی‌رود.
>
> **وظیفه:** سه احتمال، به ترتیب احتمال.
>
> **پاسخ:**
> ۱. **اسلات PCIe**: کارت در اسلات x4 نصب شده (فصل ۱۲). بررسی: `lspci -vv` و پهنای باند link.
> ۲. **سوئیچ/کابل**: پورت سوئیچ 10G است، یا کابل Cat5e.
> ۳. **دیسک**: منبع فایل روی HDD کند است؛ شبکه سالم اما دیسک گلوگاه.
>
> **درس:** همیشه زنجیره را از منبع تا مقصد چک کن: دیسک → PCIe → NIC → کابل → سوئیچ → مقصد.

### مقایسه و الگوهای مختلف

**مقایسهٔ پروتکل‌های ذخیره‌سازی شبکه‌ای:**

| پروتکل | لایه | سرعت | کاربرد |
|---|---|---|---|
| **NFS** | فایل | خوب | لینوکس، فایل share |
| **SMB/CIFS** | فایل | خوب | ویندوز |
| **iSCSI** | بلوک | خوب (10–25GbE) | SAN روی Ethernet |
| **FC** | بلوک | عالی | SAN اختصاصی |
| **NVMe-oF** | بلوک | بالاترین | SAN نسل جدید |

**مقایسهٔ NIC و CNA:**

| معیار | NIC | CNA |
|---|---|---|
| شبکهٔ IP | ✅ | ✅ |
| FC | ❌ | ✅ |
| هزینه | کم | بالا |
| پیچیدگی | کم | زیاد (FCoE) |
| رایج امروز | ✅ | کم‌کاربرد |

**نکته:** FCoE (Fibre Channel over Ethernet) محبوبیتش کم شده؛ امروز بیشتر iSCSI یا FC خالص استفاده می‌شود.

**مقایسهٔ ۱GbE، ۱۰GbE، ۲۵GbE:**

| سرعت | کاربرد |
|---|---|
| 1GbE | مدیریت، سرور کوچک |
| 10GbE | استاندارد امروز برای سرور |
| 25GbE | مجازی‌سازی، ذخیره‌سازی |
| 100GbE | ستون فقرات، storage شبکه‌ای |

### اشکال شایع

**۱. پیکربندی LACP فقط در سرور.**
کار نمی‌کند. باید در سوئیچ هم باشد.

**۲. استفاده از HBA در RAID mode برای ZFS.**
ZFS دیسک‌ها را نمی‌بیند یا اطلاعات SMART را از دست می‌دهد. باید IT mode.

**۳. وصل کردن هر دو HBA به یک سوئیچ.**
افزونگی مسیر از بین می‌رود. باید دو سوئیچ مستقل (fabric A/B).

**۴. استفاده از ماژول SFP ناسازگار.**
بعضی سوئیچ‌ها فقط ماژول برند خود را قبول می‌کنند. قبل از خرید، compatibility list را چک کن.

**۵. فراموش کردن MTU در iSCSI.**
Jumbo frame (۹۰۰۰) باید در هر دو طرف (سرور و سوئیچ) یکسان باشد. اگر نباشد، عملکرد بدتر می‌شود.

**۶. بی‌توجهی به گرمای ماژول نوری.**
SFPهای 100G گرمای زیادی تولید می‌کنند؛ در رک پر، دمای سوئیچ بالا می‌رود.

### نکات مهم (Tips & Tricks)

- **همیشه حداقل دو مسیر شبکه داشته باش** — برای مدیریت، برای داده، برای ذخیره‌سازی.
- **پورت مدیریت (OOB) را از پورت داده جدا کن.** اگر شبکهٔ داده خراب شد، OOB راه نجات است.
- **برچسب پورت بزن:** `eth0 → SW01-P12`. در عیب‌یابی، این طلاست.
- **در iSCSI، MPIO را فعال کن** حتی اگر یک سوئیچ داری — برای آینده.
- **برای VM، SR-IOV را در نظر بگیر** اگر latency حیاتی است (مثلاً دیتابیس).
- **در آزمون:** کلیدواژهٔ «redundant network path» → **دو NIC + دو سوئیچ**، نه «یک NIC با دو پورت به یک سوئیچ».

### خلاصه فصل

- **NIC** بسته شبکه، **HBA** دستور ذخیره‌سازی.
- **Teaming** افزونگی/تجمیع می‌دهد؛ LACP در هر دو طرف لازم است.
- **HBA در IT mode** برای ZFS/vSAN ضروری است.
- **MPIO** افزونگی مسیر ذخیره‌سازی است.
- جداسازی ترافیک (مدیریت، داده، ذخیره‌سازی) یک اصل طراحی است.
- سازگاری ماژول نوری و اسلات PCIe را قبل از خرید چک کن.

## فصل ۱۶: مدیریت خارج از باند — IPMI، iDRAC، iLO

### مقدمه

فرض کن ساعت ۳ بامداد پیام می‌آید: «سرور در دیتاسنتر تهران پاسخ نمی‌دهد». سرور در شهری ۸۰۰ کیلومتر دورتر است. نمی‌توانی بروی. باید از راه دور بوت کنی، BIOS را ببینی، حتی سیستم‌عامل را نصب کنی.

این کار با **مدیریت خارج از باند (out-of-band)** ممکن است. این فصل دربارهٔ مهم‌ترین ابزاری است که یک مدیر سرور دارد — و در آزمون، بخش صریحی از دامنهٔ سخت‌افزار («out-of-band management»).

### مفاهیم اساسی

**In-band در برابر Out-of-band:**

| ویژگی | In-band | Out-of-band |
|---|---|---|
| مسیر | از طریق OS و شبکهٔ اصلی | مسیر مستقل (BMC) |
| نیاز به OS سالم | ✅ | ❌ |
| کار وقتی سرور خاموش است | ❌ | ✅ |
| سرعت | بالا | متوسط |
| نمونه | SSH، RDP، agent | IPMI، iDRAC، iLO |

**BMC (Baseboard Management Controller):** یک میکروکنترلر مستقل روی مادربرد که **برق مستقل** (standby power) دارد. حتی وقتی سرور خاموش است، BMC روشن است و به شبکه وصل است.

**سه پیاده‌سازی تجاری:**

| برند | نام | پروتکل پایه |
|---|---|---|
| Dell | **iDRAC** (Integrated Dell Remote Access Controller) | IPMI + Redfish |
| HPE | **iLO** (Integrated Lights-Out) | IPMI + Redfish |
| Lenovo | **XClarity Controller (XCC)** | IPMI + Redfish |
| Supermicro | **IPMI/BMC** | IPMI |
| استاندارد باز | **Redfish** (DMTF) | REST API |

**IPMI (Intelligent Platform Management Interface):** استاندارد قدیمی (۱۹۹۸) برای مدیریت. از UDP پورت **۶۲۳** استفاده می‌کند. نسخهٔ ۲.۰ رمزنگاری ضعیف دارد و **نباید روی اینترنت در معرض دسترس قرار گیرد**.

**Redfish:** استاندارد جدید (DMTF) با REST API روی HTTPS. جایگزین IPMI است. امن‌تر، قابل‌خواندن‌تر (JSON).

**قابلیت‌های کلیدی OOB:**

- **Power control** — روشن/خاموش/ری‌ست، حتی وقتی OS هنگ است.
- **Console redirection** — دیدن صفحهٔ BIOS و OS از راه دور (KVM over IP).
- **Virtual media** — mount کردن ISO از راه دور برای نصب OS.
- **Sensor monitoring** — دما، فن، ولتاژ، توان.
- **Event log** — لاگ سخت‌افزاری مستقل از OS.
- **Firmware update** — آپدیت BIOS و firmware بدون OS.
- **Alerting** — SNMP trap، email، syslog.

**پورت‌ها و شبکه:**

- BMC معمولاً **پورت Ethernet اختصاصی** دارد (با برچسب `iDRAC`، `iLO`، `MGMT`).
- بعضی سرورها **shared mode** دارند (BMC از NIC اصلی استفاده می‌کند). این حالت ارزان‌تر است اما امنیت کمتر و در قطعی شبکهٔ اصلی، OOB هم قطع می‌شود.
- **توصیه: همیشه dedicated port.**

**امنیت BMC — نکات حیاتی:**

- BMC یک کامپیوتر مستقل با دسترسی کامل به سخت‌افزار است. اگر هک شود، مهاجم می‌تواند سرور را ری‌ست کند، رسانه mount کند، firmware را عوض کند.
- **تغییر رمز پیش‌فرض** (مهم‌ترین کار).
- **قرار دادن BMC در شبکهٔ مدیریت جدا (VLAN).**
- **هرگز BMC را مستقیم روی اینترنت نگذار.**
- **آپدیت firmware BMC** — آسیب‌پذیری‌های شناخته‌شده دارد.
- **غیرفعال کردن IPMI 1.5 و cipherهای ضعیف.**

### مثال‌های عملی

**Lab Scenario 1 — بازیابی سرور از راه دور**

> **وضعیت:** سرور در دیتاسنتر دور، ساعت ۳ بامداد، پاسخ ping نمی‌دهد. تیم محلی در دسترس نیست.
>
> **وظیفه:** مراحل بازیابی از طریق iDRAC.
>
> **پاسخ:**
> ۱. به iDRAC وصل شو (VPN → شبکهٔ مدیریت).
> ۲. **Console** را باز کن — آیا صفحه نمایش چیزی نشان می‌دهد؟ (kernel panic؟ صفحهٔ آبی؟)
> ۳. **Power state** را چک کن — روشن است یا خاموش؟
> ۴. اگر هنگ است: **Power Cycle** (نه reset، چون reset ممکن است در حالت hang کار نکند).
> ۵. اگر بوت نمی‌شود: **Virtual Media** با ISO بازیابی mount کن و از آن بوت کن.
> ۶. **Lifecycle log** را بخوان — شاید خطای سخت‌افزاری (دیسک، حافظه) ثبت شده.
> ۷. بعد از بازیابی، **مستند کن** (فصل ۷۶).
>
> **درس:** OOB تنها راه بازیابی سرور دور است. بدون آن، هر رخداد یعنی سفر.

**Lab Scenario 2 — BMC ناامن**

> **وضعیت:** در یک ممیزی، متوجه می‌شوی BMC یک سرور با رمز پیش‌فرض `calvin` (رمز پیش‌فرض قدیمی Dell) روی شبکهٔ عمومی است.
>
> **وظیفه:** ریسک را توضیح بده و اقدام کن.
>
> **پاسخ:**
> - **ریسک:** هر کسی می‌تواند سرور را ری‌ست کند، ISO مخرب mount کند، یا firmware را عوض کند. این یعنی **تصاحب کامل سخت‌افزار**، بدون نیاز به رمز OS.
> - **اقدام فوری:** تغییر رمز، انتقال به VLAN مدیریت، بستن پورت ۶۲۳ از خارج، فعال کردن HTTPS-only، آپدیت firmware.
> - **اقدام بلندمدت:** اسکن دوره‌ای شبکه برای BMCهای با رمز پیش‌فرض؛ ثبت BMCها در CMDB.
>
> **درس:** BMC یک «درِ پشتی» قانونی است. اگر محافظت نشود، درِ پشتی برای مهاجم می‌شود.

### مقایسه و الگوهای مختلف

**مقایسهٔ IPMI و Redfish:**

| معیار | IPMI | Redfish |
|---|---|---|
| سن | ۱۹۹۸ | ۲۰۱۵ |
| پروتکل | UDP 623 | HTTPS/JSON |
| امنیت | ضعیف (cipher قدیمی) | خوب (TLS) |
| خوانایی | باینری/پیچیده | JSON |
| پشتیبانی | همه | نسل جدید |
| توصیه | فقط در شبکهٔ مدیریت | ✅ استاندارد آینده |

**مقایسهٔ dedicated و shared port:**

| معیار | Dedicated | Shared |
|---|---|---|
| هزینه | پورت و کابل اضافه | صفر |
| امنیت | بالا (جداسازی) | کمتر |
| در دسترس بودن | مستقل از OS | وابسته به NIC اصلی |
| توصیه | ✅ تولیدی | فقط آزمایشگاه |

**ابزارهای مدیریت چند سرور:**

| ابزار | کاربرد |
|---|---|
| **Dell OpenManage / iDRAC Enterprise** | مدیریت گروهی Dell |
| **HPE OneView / iLO Amplifier** | مدیریت گروهی HPE |
| **Redfish scripts** | خودکارسازی با Python |
| **Ansible modules** (idrac, ilo) | خودکارسازی |
| **Nagios/Zabbix + IPMI plugin** | پایش |

### اشکال شایع

**۱. گذاشتن BMC روی شبکهٔ عمومی یا اینترنت.**
بزرگ‌ترین اشتباه امنیتی. BMC باید در VLAN مدیریت باشد.

**۲. نگه داشتن رمز پیش‌فرض.**
رمزهای پیش‌فرض (`calvin`، `admin`، `root`) در لیست مهاجمان است.

**۳. فراموش کردن آپدیت firmware BMC.**
BMC خودش یک سیستم است و آسیب‌پذیری دارد.

**۴. استفاده از shared mode در تولید.**
در قطعی NIC، OOB هم قطع می‌شود — دقیقاً وقتی که بیشترین نیاز را داری.

**۵. بی‌توجهی به Lifecycle log.**
لاگ BMC مستقل از OS است و خطاهای سخت‌افزاری را ثبت می‌کند که OS نمی‌بیند.

**۶. نداشتن مستندات BMC.**
اگر IP یا رمز BMC را ندانی، OOB وجود ندارد. در CMDB ثبت کن.

### نکات مهم (Tips & Tricks)

- **BMC را در همان روز نصب، تنظیم کن:** رمز قوی، VLAN مدیریت، SNMP trap، NTP.
- **NTP برای BMC مهم است** — بدون زمان درست، لاگ بی‌فایده است.
- **Alert را به تیکتینگ وصل کن.** هشدار fan failure باید تیکت بسازد، نه ایمیل در صندوق.
- **با Redfish خودکارسازی کن:** یک اسکریپت Python می‌تواند وضعیت ۱۰۰ سرور را جمع کند.
- **در آزمون:** کلیدواژهٔ «server is unresponsive, no OS access» → **out-of-band / iDRAC / iLO / IPMI**.
- **برای نصب OS از راه دور، Virtual Media** جواب استاندارد است.

### خلاصه فصل

- **BMC** یک کامپیوتر مستقل با برق standby است؛ وقتی سرور خاموش است، کار می‌کند.
- **iDRAC** (Dell)، **iLO** (HPE)، **XCC** (Lenovo) پیاده‌سازی‌های تجاری‌اند.
- **IPMI** استاندارد قدیمی (UDP 623)، **Redfish** استاندارد جدید (HTTPS/JSON).
- قابلیت‌ها: power control، console، virtual media، sensors، event log، firmware update.
- **امنیت BMC حیاتی است:** رمز پیش‌فرض را عوض کن، در VLAN جدا بگذار، آپدیت کن.
- همیشه **dedicated port**، نه shared.
