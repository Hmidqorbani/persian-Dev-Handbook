## فصل ۵۷: سخت‌سازی سیستم‌عامل سرور

### مقدمه

نصب پیش‌فرض یک سیستم‌عامل، برای **راحتی** طراحی شده، نه امنیت. سرویس‌های اضافه، حساب‌های پیش‌فرض، پورت‌های باز، و تنظیمات سهل‌گیرانه — همه برای این هستند که کاربر سریع شروع کند.

سخت‌سازی (Hardening) یعنی **کاهش سطح حمله**: هر چیزی که لازم نیست، حذف یا غیرفعال شود.

### مفاهیم اساسی

**سطح حمله (Attack Surface) — چهار لایه:**

| لایه | مثال | کاهش |
|---|---|---|
| **Network** | پورت باز، سرویس | فایروال، حذف سرویس |
| **Application** | نسخهٔ آسیب‌پذیر | patch، hardening |
| **OS** | سرویس اضافه، حساب پیش‌فرض | حذف، غیرفعال |
| **Physical** | دسترسی فیزیکی | قفل، کنترل ورود |

**اصل پایه:** **اگر لازم نیست، نصب نکن. اگر نصب است و لازم نیست، غیرفعال کن. اگر غیرفعال است، حذف کن.**

**چک‌لیست سخت‌سازی — لینوکس:**

| # | اقدام |
|---|---|
| ۱ | حذف سرویس‌های غیرضروری |
| ۲ | غیرفعال کردن حساب‌های پیش‌فرض/بی‌استفاده |
| ۳ | SSH: بدون root login، بدون رمز |
| ۴ | فایروال (firewalld/ufw/nftables) |
| ۵ | SELinux/AppArmor در حالت enforcing |
| ۶ | به‌روزرسانی خودکار امنیتی |
| ۷ | تنظیم `/etc/sysctl.conf` (network hardening) |
| ۸ | مجوز فایل‌های حساس |
| ۹ | لاگ و audit |
| ۱۰ | حذف ابزارهای کامپایلر از تولید (gcc، make) |

**چک‌لیست سخت‌سازی — ویندوز:**

| # | اقدام |
|---|---|
| ۱ | حذف نقش‌های غیرضروری |
| ۲ | غیرفعال کردن سرویس‌های بی‌استفاده (SMBv1، Print Spooler اگر لازم نیست) |
| ۳ | تغییر رمز Administrator، غیرفعال کردن حساب‌های پیش‌فرض |
| ۴ | فایروال ویندوز با پروفایل |
| ۵ | Windows Update / WSUS |
| ۶ | Group Policy سخت‌گیرانه |
| ۷ | AppLocker / WDAC |
| ۸ | Credential Guard / LSA Protection |
| ۹ | audit policy |
| ۱۰ | غیرفعال کردن PowerShell v2 |

**تنظیمات شبکه (sysctl) — نمونه:**

```bash
# /etc/sysctl.d/99-hardening.conf
# جلوگیری از IP forwarding (اگر روتر نیستی)
net.ipv4.ip_forward = 0

# جلوگیری از پاسخ به ICMP redirect
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0

# جلوگیری از source routing
net.ipv4.conf.all.accept_source_route = 0

# فعال کردن SYN cookies (ضد SYN flood)
net.ipv4.tcp_syncookies = 1

# جلوگیری از log martians
net.ipv4.conf.all.log_martians = 1

# ASLR
kernel.randomize_va_space = 2
```

**اعمال:**

```bash
sysctl --system
```

**SSH hardening — `/etc/ssh/sshd_config`:**

```
Port 22
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
MaxSessions 4
ClientAliveInterval 300
ClientAliveCountMax 2
AllowUsers deploy admin
X11Forwarding no
AllowAgentForwarding no
Banner /etc/issue.net
```

**نکتهٔ حیاتی:** قبل از restart، در یک session دیگر تست کن. اگر کلید کار نکند، از سرور قفل می‌شوی.

**حساب‌ها:**

```bash
# غیرفعال کردن حساب
usermod -L olduser
usermod -s /sbin/nologin olduser

# قفل کردن حساب‌های سیستمی
passwd -l daemon
passwd -l bin

# بررسی حساب‌های بدون رمز
awk -F: '($2 == "") {print $1}' /etc/shadow

# بررسی UID 0 (root-like)
awk -F: '($3 == 0) {print $1}' /etc/passwd
```

**نکته:** هر حسابی با UID 0، معادل root است. باید فقط `root` باشد.

**سرویس‌ها:**

```bash
# سرویس‌های فعال
systemctl list-units --type=service --state=running

# پورت‌های باز
ss -tulpn

# غیرفعال کردن
systemctl disable --now cups
systemctl mask cups
```

**نکته:** `mask` قوی‌تر از `disable` است — حتی نمی‌شود دستی شروع کرد.

**ویندوز — PowerShell:**

```powershell
# سرویس‌های در حال اجرا
Get-Service | Where-Object {$_.Status -eq 'Running'}

# غیرفعال کردن SMBv1
Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol -NoRestart

# غیرفعال کردن PowerShell v2
Disable-WindowsOptionalFeature -Online -FeatureName MicrosoftWindowsPowerShellV2Root

# بررسی حساب‌های محلی
Get-LocalUser

# غیرفعال کردن حساب
Disable-LocalUser -Name "Guest"

# فایروال
Get-NetFirewallProfile | Select-Object Name, Enabled
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled True
```

**نکتهٔ مهم:** **SMBv1** باید غیرفعال شود. آسیب‌پذیری‌های بزرگی (EternalBlue/WannaCry) از آن آمد.

**Group Policy — تنظیمات کلیدی:**

| سیاست | مقدار |
|---|---|
| **Account lockout threshold** | ۵ تلاش |
| **Account lockout duration** | ۱۵ دقیقه |
| **Minimum password length** | ۱۴ |
| **Password complexity** | (NIST توصیه نمی‌کند، اما در AD رایج) |
| **Screen lock** | ۱۵ دقیقه |
| **SMB signing** | Required |
| **NTLM** | محدود |
| **Anonymous enumeration** | Disabled |

**Banners:** پیام ورود باید هشدار دهد که دسترسی غیرمجاز ممنوع است. این هم بازدارنده است هم در برخی حوزه‌ها الزام قانونی.

### مثال‌های عملی

**Lab Scenario 1 — سخت‌سازی یک سرور تازه نصب‌شده**

> **وظیفه:** یک اسکریپت Bash بنویس که ۵ اقدام اول را انجام دهد.
>
> **پاسخ:**
>
> ```bash
> #!/usr/bin/env bash
> set -euo pipefail
>
> echo "=== ۱. به‌روزرسانی ==="
> apt update && apt -y upgrade
>
> echo "=== ۲. حذف سرویس‌های غیرضروری ==="
> for svc in cups avahi-daemon bluetooth; do
>     systemctl disable --now "$svc" 2>/dev/null || true
>     systemctl mask "$svc" 2>/dev/null || true
> done
>
> echo "=== ۳. SSH hardening ==="
> cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
> sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
> sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
> sshd -t && systemctl reload sshd
>
> echo "=== ۴. فایروال ==="
> ufw --force enable
> ufw default deny incoming
> ufw default allow outgoing
> ufw allow 22/tcp
>
> echo "=== ۵. بررسی ==="
> ss -tulpn
> ufw status verbose
> ```
>
> **درس:** `sshd -t` قبل از reload، از قفل شدن جلوگیری می‌کند.

**Lab Scenario 2 — سرویس ناشناس روی پورت باز**

> **وضعیت:** `ss -tulpn` نشان می‌دهد پورت ۹۲۰۰ باز است و کسی نمی‌داند چیست.
>
> **وظیفه:** چه می‌کنی؟
>
> **پاسخ:**
> ۱. **شناسایی:** `ss -tulpn | grep 9200` → کدام PID؟ `ps -fp <PID>`.
> ۲. **مالکیت:** با تیم/مستندات چک کن (احتمالاً Elasticsearch).
> ۳. **ارزیابی:** آیا لازم است؟ آیا باید از بیرون در دسترس باشد؟
> ۴. **محدود کردن:** bind به `127.0.0.1` یا فایروال.
> ۵. **مستندسازی:** در CMDB ثبت کن.
>
> **درس:** پورت باز بدون مالک مشخص = ریسک. هر پورت باید دلیل داشته باشد.

### مقایسه و الگوهای مختلف

**مقایسهٔ رویکردهای hardening:**

| رویکرد | توضیح | مناسب |
|---|---|---|
| **Manual checklist** | دستی، مورد به مورد | سرور کم |
| **Scripted** | اسکریپت (Bash/PowerShell) | متوسط |
| **Config Management** | Ansible role | مقیاس |
| **Benchmark tool** | CIS-CAT، OpenSCAP | انطباق |

**مقایسهٔ SELinux و AppArmor:**

| معیار | SELinux | AppArmor |
|---|---|---|
| مدل | برچسب (label) | مسیر (path) |
| پیچیدگی | بالا | متوسط |
| دقت | بالا | خوب |
| توزیع | RHEL family | Ubuntu/SUSE |

**مقایسهٔ فایروال‌ها در لینوکس:**

| ابزار | سطح | مناسب |
|---|---|---|
| **ufw** | ساده | Ubuntu، شروع |
| **firewalld** | zone-based | RHEL |
| **nftables** | مستقیم | حرفه‌ای |
| **iptables** | قدیمی | میراثی |

### اشکال شایع

**۱. غیرفعال کردن SELinux برای «حل مشکل».**
لایهٔ امنیتی حذف می‌شود. راه‌حل: `setsebool` یا context درست.

**۲. SSH با root و رمز.**
هدف اول brute force.

**۳. باز گذاشتن SMBv1.**
آسیب‌پذیری‌های بحرانی.

**۴. نصب ابزار توسعه روی تولید.**
کامپایلر روی سرور = ابزار مهاجم.

**۵. حساب پیش‌فرض فعال.**
`guest`، `admin` با رمز پیش‌فرض.

**۶. فایروال بدون default deny.**
فقط allow، بدون deny پیش‌فرض = همه چیز باز.

**۷. hardening بدون مستندسازی.**
بعداً کسی نمی‌داند چرا سرویسی خاموش است.

**۸. hardening یک‌باره.**
تنظیمات با آپدیت برمی‌گردند. باید دوره‌ای بررسی شود.

### نکات مهم (Tips & Tricks)

- **CIS Benchmark** — راهنمای رایگان و دقیق برای هر OS.
- **OpenSCAP** — بررسی خودکار انطباق.
- **`ss -tulpn`** اولین دستور بعد از نصب.
- **`systemctl mask`** برای سرویس‌هایی که هرگز لازم نیستند.
- **قبل از هر تغییر، snapshot/backup.**
- **در آزمون:** کلیدواژهٔ «reduce attack surface» → **remove/disable unnecessary services**.

### خلاصه فصل

- سخت‌سازی = **کاهش سطح حمله**.
- اصل: **نصب نکن، غیرفعال کن، حذف کن**.
- SSH: بدون root، بدون رمز.
- **SMBv1** و **PowerShell v2** را غیرفعال کن.
- فایروال با **default deny**.
- **SELinux/AppArmor** را غیرفعال نکن؛ تنظیم کن.

## فصل ۵۸: مدیریت وصله (Patch Management)

### مقدمه

بیشتر نفوذهای موفق، از آسیب‌پذیری‌های **شناخته‌شده و وصله‌شده** استفاده می‌کنند. یعنی مهاجم از یک حفرهٔ بسته‌شده وارد شده — چون کسی وصله نکرده بود.

این فصل دربارهٔ چرخهٔ وصله است: کشف، ارزیابی، تست، استقرار و تأیید.

### مفاهیم اساسی

**چرخهٔ مدیریت وصله:**

```
[کشف] → [ارزیابی] → [تست] → [استقرار] → [تأیید] → [گزارش]
```

| مرحله | اقدام |
|---|---|
| **کشف** | فهرست نرم‌افزار و نسخه‌ها (inventory) |
| **ارزیابی** | کدام وصله، چه اولویتی، چه ریسکی |
| **تست** | در محیط آزمایشی |
| **استقرار** | مرحله‌ای (pilot → wave → all) |
| **تأیید** | آیا نصب شد؟ آیا سرویس کار می‌کند؟ |
| **گزارش** | انطباق، متریک |

**نکتهٔ حیاتی:** بدون **inventory دقیق**، نمی‌دانی چه چیزی وصله لازم دارد. «نمی‌دانم چه دارم» = «نمی‌توانم وصله کنم».

**انواع وصله:**

| نوع | توضیح | فوریت |
|---|---|---|
| **Security patch** | رفع آسیب‌پذیری | بالا |
| **Critical update** | رفع باگ بحرانی | بالا |
| **Feature update** | قابلیت جدید | کم |
| **Driver/firmware** | سخت‌افزار | متوسط |
| **Service pack / rollup** | مجموعه | متوسط |

**اولویت‌بندی بر اساس CVSS:**

| امتیاز | شدت | زمان هدف (نمونه) |
|---|---|---|
| ۹.۰–۱۰.۰ | Critical | ۲۴–۷۲ ساعت |
| ۷.۰–۸.۹ | High | ۷–۱۴ روز |
| ۴.۰–۶.۹ | Medium | ۳۰ روز |
| ۰.۱–۳.۹ | Low | ۹۰ روز |

**نکتهٔ مهم:** CVSS تنها معیار نیست. باید **قابلیت بهره‌برداری واقعی** (EPSS، در لیست CISA KEV) و **حساسیت دارایی** را هم در نظر بگیری. یک آسیب‌پذیری ۷.۵ که در حال بهره‌برداری فعال است، فوری‌تر از ۹.۵ تئوریک است.

**ابزارهای وصله:**

| پلتفرم | ابزار |
|---|---|
| **ویندوز** | WSUS، SCCM/MECM، Intune |
| **لینوکس** | dnf-automatic، unattended-upgrades، Satellite، Landscape |
| **چندسکویی** | Ansible، Tanium، Ivanti |
| **سوم‌شخص** | Patch My PC، Chocolatey |

**نکتهٔ حیاتی:** **سرور تولیدی نباید خودکار ری‌استارت کند.** دانلود خودکار خوب است، نصب/ری‌استارت باید در پنجرهٔ تغییر باشد.

**پیکربندی unattended-upgrades (Ubuntu):**

```bash
# /etc/apt/apt.conf.d/50unattended-upgrades
Unattended-Upgrade::Allowed-Origins {
    "${distro_id}:${distro_codename}-security";
};
Unattended-Upgrade::Automatic-Reboot "false";
Unattended-Upgrade::Mail "admin@corp.example.com";
```

**نکته:** فقط `-security` را مجاز کن، نه `-updates`. و reboot خودکار را غیرفعال کن.

**dnf-automatic (RHEL):**

```ini
# /etc/dnf/automatic.conf
[commands]
upgrade_type = security
apply_updates = yes

[emitters]
emit_via = stdio
```

```bash
systemctl enable --now dnf-automatic.timer
```

**WSUS — نکات:**

- **گروه‌بندی:** pilot، production، test.
- **Approval:** دستی برای production، خودکار برای test.
- **Deadline:** اجبار نصب تا تاریخ مشخص.
- **Reporting:** کدام سرور patch نشده.

**استقرار مرحله‌ای (Phased Rollout):**

```
هفته ۱: ۵٪ سرورها (pilot)
هفته ۲: ۲۵٪
هفته ۳: ۱۰۰٪
```

**نکته:** اگر وصله مشکل‌ساز باشد، در pilot کشف می‌شود، نه در ۱۰۰٪.

**Rollback:** برای وصله‌های مشکوک، نسخهٔ قبلی را در دسترس داشته باش:

```bash
# Debian/Ubuntu
apt install nginx=1.24.0-1ubuntu1

# RHEL
dnf downgrade nginx-1.24.0

# ویندوز
wusa /uninstall /kb:5000000
```

**نکتهٔ حیاتی:** بعضی وصله‌ها uninstall نمی‌شوند. برای آن‌ها، **snapshot قبل از patch** بهترین rollback است.

**Firmware و patch:**

- **BIOS/UEFI** — آسیب‌پذیری‌های firmware (مثل LogoFAIL).
- **BMC** — خودش یک سیستم است.
- **RAID controller** — باگ‌های عملکردی.
- **NIC firmware** — سازگاری.

**نکته:** firmware را هم در چرخهٔ patch بگذار. بسیاری از سازمان‌ها فقط OS را وصله می‌کنند.

**پچ‌های خارج از چرخه (Out-of-band):** برای آسیب‌پذیری‌های بحرانی (zero-day)، فوراً — با تأیید مدیریت و ریسک‌پذیری مستند.

### مثال‌های عملی

**Lab Scenario 1 — برنامهٔ patch ماهانه**

> **وظیفه:** یک برنامهٔ سالانه بنویس.
>
> **پاسخ:**
>
> | بازه | فعالیت |
> |---|---|
> | هفتگی | بررسی بولتن امنیتی (Microsoft، distro)، اولویت‌بندی |
> | ماهانه (هفته ۱) | تست در محیط آزمایشی |
> | ماهانه (هفته ۲) | استقرار pilot (۵٪) |
> | ماهانه (هفته ۳) | استقرار ۱۰۰٪ در پنجرهٔ تغییر |
> | ماهانه (هفته ۴) | تأیید، گزارش انطباق |
> | فصلی | firmware، بازبینی فرآیند |
> | فوری | out-of-band برای critical |
>
> **درس:** patch یک رویداد نیست؛ یک **چرخه** است.

**Lab Scenario 2 — وصله سرویس را شکست**

> **وضعیت:** بعد از نصب وصله، یک اپلیکیشن داخلی کار نمی‌کند.
>
> **وظیفه:** مراحل.
>
> **پاسخ:**
> ۱. **تأیید علت:** آیا وصله مقصر است؟ (آزمایش rollback در یک سرور)
> ۲. **Rollback فوری** روی سرورهای آسیب‌دیده (یا snapshot).
> ۳. **گزارش به vendor** — باگ وصله.
> ۴. **Exclusion** — این وصله را در WSUS/Ansible مسدود کن.
> ۵. **مستندسازی** — در درس‌آموخته‌ها.
> ۶. **پایش** — vendor وصلهٔ اصلاحی می‌دهد؟
>
> **درس:** pilot، دقیقاً برای همین است.

### مقایسه و الگوهای مختلف

**مقایسهٔ WSUS و Intune:**

| معیار | WSUS | Intune |
|---|---|---|
| محیط | on-prem | cloud |
| کلاینت | domain-joined | هر دستگاه |
| پیچیدگی | متوسط | کم |
| مناسب | سازمان سنتی | مدرن/دورکار |

**مقایسهٔ patch خودکار و دستی:**

| معیار | خودکار | دستی |
|---|---|---|
| سرعت | بالا | کم |
| ریسک | متوسط (اگر بدون تست) | کم |
| بار عملیاتی | کم | زیاد |
| توصیه | دانلود خودکار، نصب کنترل‌شده | — |

**مقایسهٔ CVSS و EPSS:**

| معیار | CVSS | EPSS |
|---|---|---|
| می‌سنجد | شدت تئوریک | احتمال بهره‌برداری واقعی |
| مقیاس | ۰–۱۰ | ۰–۱ |
| کاربرد | اولویت اولیه | اولویت واقعی |

### اشکال شایع

**۱. بدون inventory.**
نمی‌دانی چه داری، نمی‌توانی وصله کنی.

**۲. patch خودکار با reboot در تولید.**
قطعی در ساعت تصادفی.

**۳. بدون تست.**
وصله سرویس را می‌شکند.

**۴. بدون rollback plan.**
اگر وصله مشکل‌ساز باشد، گیر می‌کنی.

**۵. firmware فراموش‌شده.**
OS وصله است، BIOS نه.

**۶. اولویت‌بندی فقط با CVSS.**
آسیب‌پذیری در حال بهره‌برداری با CVSS ۷، فوری‌تر است.

**۷. patch فقط ویندوز.**
لینوکس و اپلیکیشن‌ها هم لازم دارند.

**۸. بدون گزارش.**
نمی‌دانی چند درصد وصله شده‌اند.

### نکات مهم (Tips & Tricks)

- **Inventory اول.** SCCM، Ansible، یا حتی یک اسکریپت.
- **CISA KEV** را هفتگی چک کن — لیست آسیب‌پذیری‌های در حال بهره‌برداری.
- **pilot همیشه.**
- **snapshot قبل از patch‌های بزرگ.**
- **پنجرهٔ تغییر مشخص** و اطلاع‌رسانی.
- **در آزمون:** کلیدواژهٔ «patch management process» → **identify → test → deploy → verify**.

### خلاصه فصل

- چرخه: **کشف → ارزیابی → تست → استقرار → تأیید**.
- **Inventory** پیش‌نیاز است.
- اولویت: **CVSS + EPSS + KEV + حساسیت دارایی**.
- **Phased rollout** ریسک را کم می‌کند.
- **Rollback plan** الزامی است.
- **firmware** هم بخشی از patch است.

## فصل ۵۹: بدافزار و محافظت نقطه‌پایان

### مقدمه

«آنتی‌ویروس» تصویر قدیمی است. امروز محافظت نقطه‌پایان (Endpoint Protection) شامل چند لایه است: امضامحور، رفتارمحور، EDR و پاسخ خودکار.

این فصل دربارهٔ آن لایه‌ها و محدودیت‌هایشان است.

### مفاهیم اساسی

**انواع بدافزار:**

| نوع | رفتار |
|---|---|
| **Virus** | نیاز به فایل میزبان، تکثیر |
| **Worm** | خودتکثیر بدون میزبان |
| **Trojan** | ظاهر مشروع، رفتار مخرب |
| **Ransomware** | رمزنگاری داده + باج |
| **Spyware** | جمع‌آوری اطلاعات |
| **Rootkit** | مخفی‌سازی در سطح کرنل |
| **Botnet agent** | عضویت در شبکهٔ ربات |
| **Cryptominer** | استخراج ارز دیجیتال |
| **Fileless malware** | در حافظه، بدون فایل |

**نکتهٔ مهم:** **Fileless malware** امضامحور را دور می‌زند (چون فایلی نیست). برای آن، **رفتارمحور** و **EDR** لازم است.

**لایه‌های محافظت:**

| لایه | توضیح |
|---|---|
| **Signature-based** | امضای فایل شناخته‌شده |
| **Heuristic** | الگوی مشکوک |
| **Behavior-based** | رفتار غیرعادی (مثلاً رمزنگاری انبوه) |
| **Sandbox** | اجرا در محیط ایزوله |
| **EDR** | ثبت و تحلیل رفتار، پاسخ |
| **XDR** | EDR + شبکه + ایمیل + ابر |

**مقایسهٔ آنتی‌ویروس و EDR:**

| معیار | آنتی‌ویروس سنتی | EDR |
|---|---|---|
| تمرکز | جلوگیری | تشخیص + پاسخ |
| روش | امضا | رفتار + تلمتری |
| دید | فایل | فرآیند، شبکه، رجیستری |
| پاسخ | قرنطینه | ایزوله، kill، investigate |
| مناسب | پایه | سازمانی |

**نکته:** EDR جای آنتی‌ویروس را می‌گیرد، نه اینکه کنارش باشد. EDR مدرن شامل امضامحور هم هست.

**Ransomware — دفاع چندلایه:**

| لایه | کنترل |
|---|---|
| **ورود** | ایمیل filter، MFA، patch |
| **اجرا** | application control، macro blocking |
| **گسترش** | segmentation، least privilege |
| **رمزنگاری** | EDR behavior detection |
| **بازیابی** | backup immutable/offline |
| **کاهش اثر** | immutable storage، air-gap |

**نکتهٔ حیاتی:** **backup تنها دفاع نهایی در برابر ransomware است** — به شرطی که:
- **offline** یا **immutable** باشد.
- **تست بازیابی** شده باشد.
- **credential جدا** داشته باشد (ransomware به AD وصل نباشد).

**Application Control (AppLocker/WDAC):** فقط برنامه‌های مجاز اجرا شوند.

- **مزیت:** حتی malware ناشناخته هم اجرا نمی‌شود.
- **عیب:** مدیریت سخت، نیاز به inventory.

**نکته:** AppLocker برای سرورهای با نقش ثابت (مثلاً DNS) عالی است — فقط یک برنامه لازم دارد.

**Microsegmentation:** جداسازی شبکه در سطح VM/سرویس. اگر یک سرور آلوده شد، به بقیه گسترش نمی‌یابد.

**Email Security:** فیلتر ایمیل، sandbox پیوست، DMARC/SPF/DKIM.

**نکته:** بیشتر ransomware از ایمیل (phishing) وارد می‌شود. ایمیل، دروازهٔ اصلی است.

**پایش علائم آلودگی:**

| علامت | احتمال |
|---|---|
| CPU/RAM بالا بدون دلیل | cryptominer |
| فایل‌های با پسوند عجیب | ransomware |
| ترافیک خروجی به IP ناشناس | C2 |
| تغییر ناگهانی فایل‌های سیستمی | rootkit |
| حساب‌های جدید ناشناس | persistence |
| لاگ‌های پاک‌شده | پاک‌سازی رد پا |

### مثال‌های عملی

**Lab Scenario 1 — طراحی دفاع در برابر ransomware**

> **وظیفه:** یک طرح چندلایه بنویس.
>
> **پاسخ:**
>
> | لایه | کنترل مشخص |
> |---|---|
> | ایمیل | فیلتر + sandbox پیوست + DMARC |
> | هویت | MFA برای همه، least privilege |
> | نقطه‌پایان | EDR با behavior detection |
> | شبکه | segmentation، بستن SMB بین کلاینت‌ها |
> | داده | backup روزانه + **immutable** هفتگی + آفلاین ماهانه |
> | بازیابی | تست ماهانه، RTO مستند |
> | آموزش | phishing simulation فصلی |
>
> **درس:** ransomware یک حملهٔ تک‌لایه نیست؛ دفاع هم تک‌لایه نیست.

**Lab Scenario 2 — سرور آلوده**

> **وضعیت:** EDR هشدار می‌دهد: `powershell.exe` در حال رمزنگاری فایل‌ها در `/srv/data`.
>
> **وظیفه:** اقدام فوری.
>
> **پاسخ:**
> ۱. **ایزولهٔ شبکه** (نه خاموشی — حافظه ممکن است شواهد داشته باشد).
> ۲. **جلوگیری از گسترش:** غیرفعال کردن حساب‌های درگیر، قطع share.
> ۳. **ارزیابی دامنه:** کدام سرورها؟ کدام فایل‌ها؟
> ۴. **بازیابی از backup** (پس از پاک‌سازی).
> ۵. **تحقیق:** نقطهٔ ورود (ایمیل؟ VPN؟ حساب لو رفته؟).
> ۶. **مستندسازی** و گزارش.
>
> **درس:** «خاموش کردن» همیشه درست نیست؛ شواهد در RAM است.

### مقایسه و الگوهای مختلف

**مقایسهٔ آنتی‌ویروس، EDR، XDR:**

| معیار | AV | EDR | XDR |
|---|---|---|---|
| دامنه | endpoint | endpoint | endpoint+network+email+cloud |
| تشخیص | امضا | رفتار | correlation چندمنبع |
| پاسخ | خودکار محدود | خودکار + manual | orchestration |
| هزینه | کم | متوسط | بالا |

**مقایسهٔ allowlist و blocklist:**

| معیار | Allowlist | Blocklist |
|---|---|---|
| منطق | فقط مجازها | فقط ممنوع‌ها |
| امنیت | بالا | پایین |
| مدیریت | سخت | آسان |
| مناسب | سرور با نقش ثابت | کلاینت عمومی |

**مقایسهٔ backup immutable و offline:**

| معیار | Immutable | Offline (air-gap) |
|---|---|---|
| دسترسی | آنلاین | فیزیکی |
| محافظت | ransomware نمی‌تواند تغییر دهد | ransomware نمی‌بیند |
| بازیابی | سریع | کند |
| توصیه | ✅ لایهٔ اول | ✅ لایهٔ دوم |

### اشکال شایع

**۱. اتکای کامل به آنتی‌ویروس.**
malware ناشناخته (zero-day) رد می‌شود.

**۲. backup آنلاین و قابل نوشتن.**
ransomware آن را هم رمز می‌کند.

**۳. backup با credential دامنه.**
ransomware به آن دسترسی دارد.

**۴. غیرفعال کردن EDR برای «عملکرد».**
دقیقاً همان چیزی که مهاجم می‌خواهد.

**۵. بدون segmentation.**
یک آلودگی، کل شبکه را می‌گیرد.

**۶. بدون تست بازیابی.**
backup وجود دارد اما کار نمی‌کند.

**۷. نادیده گرفتن ایمیل.**
دروازهٔ اصلی ورود.

**۸. خاموش کردن سرور آلوده بلافاصله.**
شواهد حافظه از دست می‌رود.

### نکات مهم (Tips & Tricks)

- **3-2-1-1-0**: ۳ نسخه، ۲ رسانه، ۱ offsite، ۱ immutable، ۰ خطا در تست.
- **EDR را در سرورها هم نصب کن**، نه فقط کلاینت.
- **AppLocker برای سرور نقش‌ثابت.**
- **phishing simulation** فصلی.
- **backup credential جدا** از دامنه.
- **در آزمون:** کلیدواژهٔ «ransomware protection» → **immutable/offline backup**.

### خلاصه فصل

- بدافزار: virus، worm، trojan، ransomware، rootkit، fileless.
- لایه‌ها: **signature، heuristic، behavior، sandbox، EDR**.
- **EDR** جای AV را می‌گیرد.
- ransomware: دفاع چندلایه + **backup immutable/offline**.
- **AppLocker** برای سرور نقش‌ثابت.
- ایزوله کن، خاموش نکن (شواهد).

## فصل ۶۰: جلوگیری از نشت داده (DLP)

### مقدمه

DLP (Data Loss Prevention) پاسخ به یک سؤال است: «دادهٔ حساس کجاست و به کجا می‌رود؟»

بدون DLP، سازمان نمی‌داند کارمندی یک فایل مشتری را به ایمیل شخصی می‌فرستد — تا وقتی که خبرش در رسانه‌ها بیاید.

### مفاهیم اساسی

**سه حالت DLP:**

| حالت | توضیح | مثال |
|---|---|---|
| **At rest** | دادهٔ ذخیره‌شده | اسکن فایل‌سرور برای شماره کارت |
| **In motion** | دادهٔ در حال انتقال | ایمیل، HTTP، USB |
| **In use** | دادهٔ در حال استفاده | کپی به USB، چاپ |

**چهار مرحلهٔ DLP:**

```
[کشف] → [طبقه‌بندی] → [پایش] → [جلوگیری]
```

| مرحله | اقدام |
|---|---|
| **Discovery** | کجا دادهٔ حساس داریم؟ |
| **Classification** | چه نوعی؟ (کارت، کد ملی، پزشکی) |
| **Monitoring** | چه کسی، چه چیزی، به کجا؟ |
| **Enforcement** | اجازه/هشدار/مسدود |

**الگوهای تشخیص:**

| روش | توضیح | دقت |
|---|---|---|
| **Regex / Pattern** | شماره کارت، کد ملی | متوسط |
| **Keyword** | کلمات کلیدی | پایین |
| **Fingerprint** | اثر انگشت سند | بالا |
| **Exact Data Match (EDM)** | تطابق دقیق با دیتابیس | بالا |
| **Machine Learning** | الگوهای پیچیده | متوسط–بالا |

**نکتهٔ مهم:** **regex تنها کافی نیست.** شماره کارت با Luhn check، شماره ملی با الگوریتم، و EDM برای دقت بالاتر.

**کانال‌های DLP:**

| کانال | کنترل |
|---|---|
| **Email** | اسکن پیوست و متن |
| **Web** | upload، فرم، cloud storage |
| **Endpoint** | USB، چاپ، clipboard |
| **Network** | پروتکل‌های خروجی |
| **Cloud** | CASB، API |

**نکتهٔ حیاتی:** DLP بدون **طبقه‌بندی داده** (فصل ۵۴) کار نمی‌کند. نمی‌توانی چیزی را محافظت کنی که نمی‌شناسی.

**سیاست DLP — سه سطح اقدام:**

| سطح | رفتار | مناسب |
|---|---|---|
| **Monitor** | فقط ثبت | شروع، سنجش |
| **Notify** | هشدار به کاربر | آموزش |
| **Block** | مسدود | دادهٔ بحرانی |

**نکته:** از **Monitor** شروع کن، نه Block. DLP با false positive زیاد، کاربران را عصبانی می‌کند و دور زده می‌شود.

**False Positive و False Negative:**

| نوع | معنی | اثر |
|---|---|---|
| **False positive** | دادهٔ بی‌خطر، مسدود | اختلال کاری |
| **False negative** | دادهٔ حساس، عبور | نشت |

**نکته:** در DLP، معمولاً false positive بیشتر مشکل‌ساز است (چون کاربران دور می‌زنند).

**CASB (Cloud Access Security Broker):** کنترل استفاده از ابر (SaaS).

- **Discovery** — کدام SaaS استفاده می‌شود (shadow IT).
- **DLP** — دادهٔ حساس به ابر نرود.
- **Access control** — چه کسی، چه سرویسی.

**Insider Threat:** تهدید داخلی — کارمند ناراضی، جاسوس، یا فرد سهل‌انگار.

| نوع | نشانه |
|---|---|
| **Negligent** | اشتباه، بدون سوءنیت |
| **Malicious** | عمدی |
| **Compromised** | حساب لو رفته |

**نکته:** بیشتر نشت‌ها از **negligent** است، نه malicious. آموزش و سادگی فرآیند، مؤثرتر از کنترل سخت است.

### مثال‌های عملی

**Lab Scenario 1 — سیاست DLP برای دادهٔ مشتری**

> **وظیفه:** یک سیاست برای شماره کارت و کد ملی بنویس.
>
> **پاسخ:**
>
> | کانال | اقدام | آستانه |
> |---|---|---|
> | Email خارجی | Block اگر >۱ شماره کارت | فوری |
> | Email داخلی | Notify | — |
> | USB | Block (بدون رمز) | همه |
> | Cloud upload | Block برای سرویس غیرمجاز | — |
> | Print | Log + notify | >۱۰ رکورد |
> | Endpoint copy | Log | — |
>
> **تشخیص:** regex شماره کارت + Luhn check؛ کد ملی با الگوریتم؛ EDM برای دیتابیس مشتریان.
>
> **درس:** هر کانال، سیاست خودش را دارد.

**Lab Scenario 2 — false positive زیاد**

> **وضعیت:** DLP روزی ۵۰۰ هشدار می‌دهد و ۹۵٪ آن‌ها فایل‌های آموزشی هستند که شماره کارت نمونه دارند.
>
> **وظیفه:** اصلاح.
>
> **پاسخ:**
> ۱. **Exclusion** برای پوشهٔ آموزشی/تست.
> ۲. **EDM** به‌جای regex — فقط شماره‌های واقعی دیتابیس.
> ۳. **آستانه** — فقط >۵ شماره در یک فایل.
> ۴. **آموزش** — به تیم محتوا بگو از شماره‌های جعلی استفاده کنند.
> ۵. **اندازه‌گیری** — هدف: <۲۰ هشدار/روز با >۷۰٪ واقعی.
>
> **درس:** DLP بدون tuning، به «خستگی هشدار» می‌رسد.

### مقایسه و الگوهای مختلف

**مقایسهٔ DLP شبکه‌ای و Endpoint:**

| معیار | Network DLP | Endpoint DLP |
|---|---|---|
| نقطهٔ کنترل | خروجی شبکه | دستگاه |
| کانال | ایمیل، وب | USB، چاپ، clipboard |
| رمزنگاری | نمی‌بیند | می‌بیند (قبل از رمز) |
| مناسب | سازمانی | دورکار |

**مقایسهٔ DLP و CASB:**

| معیار | DLP | CASB |
|---|---|---|
| تمرکز | داده | ابر/SaaS |
| کانال | همه | cloud |
| کشف shadow IT | ❌ | ✅ |
| مکمل | ✅ | ✅ |

**مقایسهٔ رویکردهای اجرا:**

| رویکرد | مزیت | عیب |
|---|---|---|
| **Monitor** | بدون اختلال | بدون جلوگیری |
| **Notify** | آموزش | نادیده گرفته می‌شود |
| **Block** | جلوگیری | اختلال، دور زدن |

### اشکال شایع

**۱. DLP بدون طبقه‌بندی داده.**
نمی‌دانی چه محافظت کنی.

**۲. Block از روز اول.**
کاربران دور می‌زنند، پروژه شکست می‌خورد.

**۳. فقط regex.**
false positive و negative زیاد.

**۴. بدون exclusion.**
فایل‌های تست، هشدار بی‌پایان.

**۵. نادیده گرفتن insider.**
DLP فقط نشت خارجی را می‌بیند.

**۶. DLP بدون رمزنگاری.**
اگر داده رمز شود، DLP نمی‌بیند (مگر endpoint).

**۷. بدون مستندسازی.**
کاربر نمی‌داند چرا مسدود شد.

**۸. سیاست بدون مالک.**
هیچ‌کس مسئول tuning نیست.

### نکات مهم (Tips & Tricks)

- **Monitor → Notify → Block** به‌ترتیب.
- **EDM** دقیق‌تر از regex.
- **Exclusion list** را زنده نگه دار.
- **آموزش** بخشی از DLP است.
- **گزارش ماهانه** به مدیریت.
- **در آزمون:** کلیدواژهٔ «prevent sensitive data leaving» → **DLP**.

### خلاصه فصل

- DLP سه حالت: **at rest، in motion، in use**.
- مراحل: **کشف → طبقه‌بندی → پایش → جلوگیری**.
- تشخیص: **regex، keyword، fingerprint، EDM، ML**.
- از **Monitor** شروع کن، نه Block.
- **CASB** برای ابر.
- بیشتر نشت‌ها از **negligent insider** است.

## فصل ۶۱: SIEM و همبستگی رویداد

### مقدمه

یک سرور، روزی هزاران لاگ تولید می‌کند. صد سرور، صدها هزار. در این حجم، یک رویداد مهم مثل «۵۰۰ ورود ناموفق و بعد یک ورود موفق» گم می‌شود — مگر اینکه کسی **همبستگی** برقرار کند.

SIEM همان کسی است.

### مفاهیم اساسی

**SIEM = SIM + SEM:**

| جزء | کار |
|---|---|
| **SIM** (Security Information Management) | ذخیره، نگهداشت، گزارش |
| **SEM** (Security Event Management) | پایش لحظه‌ای، هشدار |

**چهار عملکرد SIEM:**

```
[جمعآوری] → [نرمال‌سازی] → [همبستگی] → [هشدار/گزارش]
```

| مرحله | توضیح |
|---|---|
| **Collection** | از سرور، شبکه، اپلیکیشن، ابر |
| **Normalization** | تبدیل فرمت‌های مختلف به یک مدل |
| **Correlation** | پیدا کردن الگو بین رویدادها |
| **Alerting** | هشدار به تیم |

**منابع داده:**

| منبع | مثال |
|---|---|
| **Windows Event Log** | 4624، 4625، 4672 |
| **Linux syslog** | auth، sudo، kernel |
| **Firewall** | allow/deny |
| **IDS/IPS** | تشخیص نفوذ |
| **EDR** | رفتار endpoint |
| **AD** | تغییر گروه، حساب |
| **VPN** | ورود از راه دور |
| **Database** | دسترسی، خطا |
| **Cloud** | CloudTrail، Activity Log |
| **Application** | خطا، دسترسی |

**Event IDهای مهم ویندوز:**

| ID | معنی |
|---|---|
| **4624** | ورود موفق |
| **4625** | ورود ناموفق |
| **4634** | خروج |
| **4648** | ورود با credential صریح |
| **4672** | دسترسی ویژه (admin) |
| **4720** | ایجاد حساب |
| **4726** | حذف حساب |
| **4732** | افزودن به گروه |
| **1102** | پاک شدن audit log |

**نکتهٔ حیاتی:** **1102** (پاک شدن audit log) یکی از مهم‌ترین هشدارهاست. مهاجم رد پا را پاک می‌کند — این خودش یک نشانه است.

**قواعد همبستگی — نمونه:**

```
قاعده ۱: ۵ ورود ناموفق در ۵ دقیقه از یک IP → هشدار brute force
قاعده ۲: ورود موفق بعد از ۵ ناموفق → هشدار احتمالی موفقیت حمله
قاعده ۳: ایجاد حساب + افزودن به Domain Admins در ۱۰ دقیقه → بحرانی
قاعده ۴: 1102 (پاک شدن لاگ) → بحرانی
قاعده ۵: دسترسی به ۱۰۰ فایل در ۱ دقیقه → احتمال ransomware
قاعده ۶: ترافیک خروجی به IP جدید، حجم بالا → احتمال exfiltration
```

**نکتهٔ مهم:** قاعده باید **context** داشته باشد. «۵ ورود ناموفق» در یک سازمان با ۵۰۰۰ کارمند، عادی است؛ در یک سرور با ۳ کاربر، مشکوک.

**Use Caseهای رایج:**

| Use Case | منبع |
|---|---|
| **Brute force** | auth log |
| **Privilege escalation** | AD، sudo |
| **Lateral movement** | SMB، RDP |
| **Data exfiltration** | firewall، proxy |
| **Malware** | EDR |
| **Insider threat** | file access |
| **Compliance** | همه |

**ابزارهای SIEM:**

| ابزار | نوع |
|---|---|
| **Splunk** | تجاری، رهبر بازار |
| **Microsoft Sentinel** | ابری |
| **IBM QRadar** | تجاری |
| **Elastic Security** | متن‌باز/تجاری |
| **Wazuh** | متن‌باز |
| **Graylog** | متن‌باز |

**نکته:** برای سازمان کوچک، **Wazuh** یا **Elastic** شروع خوبی است. Splunk قدرتمند اما گران.

**SOAR (Security Orchestration, Automation and Response):** لایهٔ بالای SIEM برای پاسخ خودکار.

- **Playbook** — مراحل پاسخ.
- **Automation** — مسدود کردن IP، غیرفعال کردن حساب.
- **Case management** — پیگیری.

**نکته:** SOAR بدون SIEM خوب، بی‌فایده است. اول داده، بعد خودکارسازی.

**MTTD و MTTR:**

| متریک | معنی | هدف |
|---|---|---|
| **MTTD** (Mean Time To Detect) | زمان تشخیص | کمتر از ۲۴ ساعت |
| **MTTR** (Mean Time To Respond) | زمان پاسخ | کمتر از ۴ ساعت |
| **MTTC** (Contain) | زمان مهار | کمتر از ۱ ساعت |

**نکته:** بدون SIEM، MTTD می‌تواند **ماه‌ها** باشد (کشف توسط شخص ثالث).

### مثال‌های عملی

**Lab Scenario 1 — طراحی یک use case**

> **وظیفه:** یک قاعده برای «نفوذ به حساب سرویس» بنویس.
>
> **پاسخ:**
>
> ```
> نام: Suspicious Service Account Activity
>
> منابع: Windows 4624 (type 3/10)، 4672، EDR process
>
> شرط:
>   - حساب سرویس (پایان با $ یا لیست مشخص)
>   - ورود تعاملی (type 2 یا 10)  ← غیرعادی
>   - یا اجرای PowerShell/cmd  ← غیرعادی
>
> آستانه: ۱ رویداد (چون سرویس نباید تعاملی باشد)
>
> شدت: High
>
> اقدام: هشدار به SOC + غنی‌سازی با owner حساب
> ```
>
> **درس:** بهترین قواعد، **رفتار غیرعادی** را می‌گیرند، نه امضای حمله.

**Lab Scenario 2 — هشدارهای زیاد SIEM**

> **وضعیت:** SIEM روزی ۳۰۰۰ هشدار می‌دهد و تیم فقط ۱۰۰ تا را بررسی می‌کند.
>
> **وظیفه:** اصلاح.
>
> **پاسخ:**
> ۱. **اندازه‌گیری:** کدام قواعد بیشترین هشدار را می‌دهند؟
> ۲. **Tuning:** آستانه، exclusion، context.
> ۳. **حذف قواعد بی‌ارزش** — اگر هیچ‌وقت true positive نداده، حذف.
> ۴. **گروه‌بندی** — یک incident برای ۵۰ هشدار مرتبط.
> ۵. **اولویت‌بندی** — critical به بالا، low به گزارش.
> ۶. **اتوماسیون** — پاسخ خودکار برای موارد ساده.
>
> **درس:** SIEM بدون tuning، یک ماشین تولید نویز است.

### مقایسه و الگوهای مختلف

**مقایسهٔ SIEM و EDR:**

| معیار | SIEM | EDR |
|---|---|---|
| دامنه | کل زیرساخت | endpoint |
| همبستگی | چندمنبع | یک endpoint |
| دید شبکه | ✅ | محدود |
| دید فرآیند | محدود | ✅ عمیق |
| مکمل | ✅ | ✅ |

**نکته:** SIEM و EDR مکمل‌اند. EDR جزئیات endpoint می‌دهد؛ SIEM تصویر کلان.

**مقایسهٔ SIEM خودساخته و تجاری:**

| معیار | خودساخته (ELK) | تجاری |
|---|---|---|
| هزینه | کم (نیروی انسانی) | بالا |
| زمان راه‌اندازی | ماه‌ها | هفته‌ها |
| قواعد آماده | ❌ | ✅ |
| انعطاف | بالا | متوسط |
| مناسب | تیم فنی قوی | سازمان معمولی |

**مقایسهٔ log management و SIEM:**

| معیار | Log Mgmt | SIEM |
|---|---|---|
| تمرکز | ذخیره و جست‌وجو | تشخیص |
| همبستگی | ❌ | ✅ |
| هشدار | محدود | ✅ |
| مناسب | انطباق | SOC |

### اشکال شایع

**۱. SIEM بدون tuning.**
نویز، خستگی هشدار.

**۲. فقط جمع‌آوری، بدون use case.**
داده زیاد، بینش صفر.

**۳. نادیده گرفتن منابع مهم.**
AD، VPN، cloud.

**۴. بدون NTP.**
ترتیب رویدادها گم می‌شود (فصل ۳۲).

**۵. بدون retention مناسب.**
بعد از ۷ روز، لاگ پاک می‌شود.

**۶. هشدار بدون runbook.**
کسی نمی‌داند چه کند.

**۷. بدون اندازه‌گیری MTTD.**
نمی‌دانی SIEM مؤثر است یا نه.

**۸. فقط لاگ سرور، بدون شبکه.**
حرکت جانبی (lateral movement) دیده نمی‌شود.

### نکات مهم (Tips & Tricks)

- **NTP اول، SIEM بعد.**
- **از use case شروع کن، نه از داده.**
- **Event ID 1102** را بحرانی کن.
- **Baseline بساز** — رفتار عادی را بشناس.
- **Retention:** ۹۰ روز آنلاین، ۱ سال آرشیو.
- **در آزمون:** کلیدواژهٔ «correlate events from multiple sources» → **SIEM**.

### خلاصه فصل

- SIEM: **جمع‌آوری → نرمال‌سازی → همبستگی → هشدار**.
- منابع: OS، شبکه، EDR، AD، ابر.
- **Event ID 1102** (پاک شدن لاگ) بحرانی است.
- قواعد باید **context** داشته باشند.
- **MTTD/MTTR** متریک اثربخشی‌اند.
- SIEM بدون tuning = نویز.

## فصل ۶۲: خط پایه، اسکن و انطباق

### مقدمه

«امن» یک وضعیت نیست؛ یک **فرآیند** است. برای اینکه بدانی امن هستی، باید بدانی **چه چیزی باید باشد** (baseline)، **چه چیزی هست** (scan)، و **چقدر فاصله** داری (gap).

این فصل دربارهٔ این سه است.

### مفاهیم اساسی

**Baseline (خط پایه):** وضعیت مرجع و تأییدشدهٔ یک سیستم.

- **Configuration baseline** — تنظیمات (سرویس‌ها، پورت‌ها، پارامترها).
- **Security baseline** — کنترل‌های امنیتی حداقلی.
- **Golden image** — تصویر مرجع برای استقرار.

**نکتهٔ حیاتی:** baseline بدون **نسخه‌بندی** و **بازبینی** می‌پوسد. یک baseline دو ساله، دیگر مرجع نیست.

**مفاهیم کلیدی:**

| اصطلاح | معنی |
|---|---|
| **Baseline** | وضعیت مرجع |
| **Drift** | انحراف از baseline |
| **Benchmark** | استاندارد مرجع (CIS، STIG) |
| **Compliance** | انطباق با استاندارد |
| **Remediation** | اصلاح انحراف |

**استانداردهای benchmark:**

| استاندارد | صاحب | کاربرد |
|---|---|---|
| **CIS Benchmarks** | Center for Internet Security | تنظیمات سخت‌سازی |
| **DISA STIG** | وزارت دفاع آمریکا | سخت‌گیرانه، نظامی |
| **NIST 800-53** | NIST | کنترل‌های امنیتی |
| **ISO 27001** | ISO | سیستم مدیریت |
| **PCI DSS** | شورای PCI | دادهٔ کارت |
| **HIPAA** | آمریکا | دادهٔ پزشکی |

**نکته:** CIS Benchmark رایگان و عملی است. STIG سخت‌گیرانه‌تر است و ممکن است عملکرد را تحت تأثیر بگذارد.

**انواع اسکن:**

| نوع | هدف | اثر |
|---|---|---|
| **Vulnerability scan** | پیدا کردن آسیب‌پذیری | غیرتهاجمی (معمولاً) |
| **Configuration scan** | انحراف از baseline | غیرتهاجمی |
| **Compliance scan** | انطباق با استاندارد | غیرتهاجمی |
| **Authenticated scan** | با credential، عمیق‌تر | دقیق‌تر |
| **Unauthenticated scan** | از بیرون، مثل مهاجم | سطحی‌تر |
| **Penetration test** | بهره‌برداری واقعی | تهاجمی، مجوز لازم |

> ⚠️ **مرز قانونی:** اسکن آسیب‌پذیری و تست نفوذ فقط روی سیستم‌هایی مجاز است که **مالکیت یا اجازهٔ کتبی** داری. اسکن بدون مجوز، در بسیاری از کشورها تخلف قانونی است.

**اسکنرهای رایج:**

| ابزار | نوع |
|---|---|
| **Nessus / Tenable** | تجاری، جامع |
| **Qualys** | ابری |
| **OpenVAS / Greenbone** | متن‌باز |
| **Nmap** | کشف، اسکریپت |
| **Lynis** | لینوکس hardening |
| **OpenSCAP** | انطباق با SCAP |
| **CIS-CAT** | انطباق با CIS |

**نکته:** اسکن بدون **credential** نتایج ناقص می‌دهد. اسکن authenticated دقیق‌تر است اما نیاز به حساب سرویس دارد.

**مدیریت آسیب‌پذیری — چرخه:**

```
[کشف] → [اولویت‌بندی] → [اصلاح] → [تأیید] → [گزارش]
```

**اولویت‌بندی:**

| معیار | وزن |
|---|---|
| **CVSS** | شدت فنی |
| **EPSS** | احتمال بهره‌برداری |
| **KEV** | در حال بهره‌برداری فعال |
| **حساسیت دارایی** | اهمیت سیستم |
| **قابلیت دسترسی** | از اینترنت؟ |

**نکته:** یک آسیب‌پذیری متوسط روی سرور اینترنتی، فوری‌تر از یک آسیب‌پذیری بحرانی روی سیستم ایزوله است.

**Drift Detection:** تشخیص تغییر غیرمجاز.

- **File Integrity Monitoring (FIM)** — تغییر فایل سیستمی.
- **Configuration drift** — تغییر تنظیمات.
- **Baseline comparison** — مقایسهٔ دوره‌ای.

**ابزار FIM:** AIDE، Tripwire، OSSEC، Wazuh.

```bash
# AIDE — نمونه
aide --init
mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db
aide --check
```

**نکته:** FIM بدون baseline اولیه، بی‌فایده است. و baseline باید روی سیستم **تمیز** ساخته شود.

**گزارش انطباق:**

| متریک | معنی |
|---|---|
| **% compliant** | درصد سیستم‌های منطبق |
| **Open findings** | موارد باز |
| **Mean time to remediate** | زمان متوسط اصلاح |
| **Exception count** | استثناها |

**نکته:** استثنا (exception) باید **مستند، تأییدشده و زمان‌دار** باشد. «استثنای دائمی» یعنی کنترل وجود ندارد.

### مثال‌های عملی

**Lab Scenario 1 — ساخت baseline**

> **وظیفه:** برای یک سرور وب لینوکس، baseline بساز.
>
> **پاسخ:**
>
> ```bash
> #!/usr/bin/env bash
> set -euo pipefail
> OUT="/var/lib/baseline/$(hostname)-$(date +%Y%m%d)"
> mkdir -p "$OUT"
>
> # ۱. بسته‌های نصب‌شده
> dpkg -l > "$OUT/packages.txt"
>
> # ۲. سرویس‌های فعال
> systemctl list-units --type=service --state=running > "$OUT/services.txt"
>
> # ۳. پورت‌های باز
> ss -tulpn > "$OUT/ports.txt"
>
> # ۴. کاربران
> getent passwd > "$OUT/users.txt"
> getent group > "$OUT/groups.txt"
>
> # ۵. sudoers
> cp /etc/sudoers "$OUT/sudoers.txt"
>
> # ۶. sysctl
> sysctl -a > "$OUT/sysctl.txt" 2>/dev/null
>
> # ۷. SSH config
> cp /etc/ssh/sshd_config "$OUT/sshd_config.txt"
>
> # ۸. cron
> crontab -l > "$OUT/crontab.txt" 2>/dev/null || true
> ls -la /etc/cron.* > "$OUT/cron_dirs.txt" 2>/dev/null || true
>
> echo "baseline saved: $OUT"
> ```
>
> **درس:** baseline باید **قابل مقایسه** باشد. فرمت متنی، diff را ساده می‌کند.

**Lab Scenario 2 — drift کشف شد**

> **وضعیت:** FIM هشدار می‌دهد `/etc/ssh/sshd_config` تغییر کرده، اما هیچ change request ثبت نشده.
>
> **وظیفه:** اقدام.
>
> **پاسخ:**
> ۱. **diff با baseline:** چه چیزی عوض شده؟
> ۲. **زمان تغییر:** `stat` فایل.
> ۳. **لاگ دسترسی:** چه کسی در آن زمان وارد شده؟ (`last`، auth.log)
> ۴. **ارزیابی:** تغییر مجاز (فراموش‌شده در ثبت) یا مخرب؟
> ۵. **اگر مخرب:** incident response (فصل ۹۳).
> ۶. **اگر مجاز:** baseline به‌روزرسانی + ثبت change.
>
> **درس:** FIM بدون فرآیند بررسی، فقط نویز تولید می‌کند.

### مقایسه و الگوهای مختلف

**مقایسهٔ اسکن و تست نفوذ:**

| معیار | Vulnerability Scan | Pen Test |
|---|---|---|
| هدف | فهرست آسیب‌پذیری | اثبات بهره‌برداری |
| تهاجمی | کم | زیاد |
| فرکانس | ماهانه | سالانه |
| نیاز به مجوز | ✅ | ✅ (کتبی) |
| خروجی | گزارش فنی | گزارش + ریسک کسب‌وکار |

**مقایسهٔ CIS و STIG:**

| معیار | CIS | STIG |
|---|---|---|
| سخت‌گیری | متوسط | بالا |
| اثر عملکرد | کم | متوسط–بالا |
| مناسب | تجاری | دولتی/نظامی |
| انعطاف | بالا (سطح ۱/۲) | کم |

**مقایسهٔ اسکن authenticated و unauthenticated:**

| معیار | Authenticated | Unauthenticated |
|---|---|---|
| دید | عمیق (بسته‌ها، تنظیمات) | سطحی (سرویس‌های باز) |
| false positive | کم | زیاد |
| نیاز به credential | ✅ | ❌ |
| مناسب | انطباق | دید مهاجم |

### اشکال شایع

**۱. baseline بدون نسخه‌بندی.**
نمی‌دانی چه زمانی چه چیزی عوض شد.

**۲. اسکن بدون credential.**
نتایج ناقص و پر از false positive.

**۳. اسکن بدون مجوز.**
تخلف قانونی و قطعی سرویس.

**۴. اسکن در ساعت اوج.**
سرویس کند می‌شود یا crash.

**۵. گزارش بدون اصلاح.**
«۵۰۰ آسیب‌پذیری» روی کاغذ، بدون اقدام.

**۶. استثنای دائمی.**
کنترل وجود ندارد.

**۷. FIM بدون بررسی.**
نویز.

**۸. baseline قدیمی.**
مرجع غلط، انحراف واقعی دیده نمی‌شود.

### نکات مهم (Tips & Tricks)

- **CIS Benchmark سطح ۱** را اول بزن (کم‌ریسک)، بعد سطح ۲.
- **اسکن authenticated** برای انطباق.
- **اولویت با KEV/EPSS**، نه فقط CVSS.
- **FIM روی `/etc`، `/bin`، `/usr/bin`** — نه کل دیسک.
- **گزارش ماهانه به مدیریت** — با روند، نه فقط عدد.
- **در آزمون:** کلیدواژهٔ «deviation from baseline» → **drift**؛ «benchmark» → **CIS/STIG**.

### خلاصه فصل

- **Baseline** = وضعیت مرجع، با نسخه‌بندی.
- **Drift** = انحراف؛ با FIM و مقایسه کشف می‌شود.
- Benchmark: **CIS، STIG، NIST**.
- اسکن **authenticated** دقیق‌تر است.
- اولویت: **CVSS + EPSS + KEV + حساسیت دارایی**.
- استثنا باید **مستند و زمان‌دار** باشد.
