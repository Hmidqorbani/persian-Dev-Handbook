## فصل ۲۳: خانواده‌های سیستم‌عامل سرور

### مقدمه

سیستم‌عامل سرور، لایه‌ای است که سخت‌افزار را به سرویس تبدیل می‌کند. انتخاب آن، تصمیمی است که سال‌ها اثر دارد: روی مهارت لازم، هزینهٔ لایسنس، ابزارهای مدیریت و اکوسیستم نرم‌افزاری.

این فصل، خانواده‌های اصلی را معرفی می‌کند. هدف حفظ کردن نسخه‌ها نیست — چون نسخه‌ها عوض می‌شوند. هدف شناخت **منطق هر خانواده** و **معیار انتخاب** است.

### مفاهیم اساسی

**۱. خانوادهٔ Windows Server**

- **نسخه‌ها (تاریخی):** 2012 R2، 2016، 2019، 2022، 2025.
- **دو حالت نصب:**
  - **Desktop Experience** — با رابط گرافیکی کامل.
  - **Server Core** — بدون GUI، فقط PowerShell و مدیریت از راه دور. **کمتر آسیب‌پذیر، کمتر نیازمند patch، کمتر مصرف‌کنندهٔ منابع.**
- **نقش‌ها (Roles):** Active Directory Domain Services، DNS، DHCP، File Server، Hyper-V، IIS، Print Server، Remote Desktop Services.
- **مدیریت:** Server Manager (GUI)، PowerShell، Windows Admin Center، RSAT.
- **مزیت:** یکپارچگی با اکوسیستم مایکروسافت، AD، Group Policy، پشتیبانی گستردهٔ نرم‌افزاری.
- **عیب:** هزینهٔ لایسنس (به‌ویژه CAL)، منابع بیشتر، وابستگی به GUI در تیم‌های قدیمی.

**۲. خانوادهٔ Linux**

توزیع‌های سروری اصلی:

| توزیع | خانواده | مدیریت بسته | چرخهٔ انتشار | مناسب برای |
|---|---|---|---|---|
| **RHEL** | Red Hat | dnf/rpm | ۱۰ سال | enterprise، پشتیبانی تجاری |
| **Ubuntu Server** | Debian | apt/deb | ۵ سال LTS (۱۰ با ESM) | ابر، DevOps، عمومی |
| **Debian** | مستقل | apt/deb | ~۵ سال | پایدار، بدون پشتیبانی تجاری |
| **SUSE SLES** | SUSE | zypper/rpm | ۱۰–۱۳ سال | enterprise، SAP |
| **Rocky / AlmaLinux** | RHEL-compatible | dnf/rpm | ۱۰ سال | جایگزین بدون هزینهٔ RHEL |
| **Oracle Linux** | RHEL-compatible | dnf/rpm | ۱۰ سال | Oracle DB |

- **مزیت:** بدون هزینهٔ لایسنس (اکثراً)، انعطاف، سبک، ابزارهای قدرتمند، اکوسیستم ابری.
- **عیب:** نیاز به مهارت خط فرمان، پشتیبانی تجاری اختیاری، تنوع توزیع‌ها (سردرگمی).

**۳. خانوادهٔ Unix تجاری**

- **IBM AIX** — روی Power. برای بارهای حیاتی سازمانی (بانک، بیمه).
- **Oracle Solaris** — ZFS، Zones. در حال کاهش سهم.
- **HP-UX** — روی Itanium. میراثی.

**مزیت:** پایداری اثبات‌شده، پشتیبانی سازنده. **عیب:** گران، اکوسیستم بسته، مهارت کمیاب.

**۴. سیستم‌عامل‌های تخصصی**

- **VMware ESXi** — hypervisor نوع ۱، برای مجازی‌سازی.
- **Proxmox VE** — متن‌باز، KVM + LXC.
- **TrueNAS** — ذخیره‌سازی (ZFS).
- **pfSense/OPNsense** — فایروال/روتر.

**معیارهای انتخاب سیستم‌عامل:**

| معیار | سؤال کلیدی |
|---|---|
| **نرم‌افزار مورد نیاز** | آیا اپلیکیشن روی این OS اجرا می‌شود؟ (مهم‌ترین) |
| **مهارت تیم** | تیم با چه چیزی راحت است؟ |
| **هزینه** | لایسنس + CAL + پشتیبانی |
| **پشتیبانی** | آیا vendor پشتیبانی ۲۴×۷ می‌دهد؟ |
| **انطباق** | آیا استاندارد/مقررهٔ خاصی لازم است؟ |
| **چرخهٔ عمر** | چند سال patch امنیتی می‌گیرد؟ |
| **ابزار مدیریت** | آیا با ابزارهای موجود یکپارچه می‌شود؟ |

**نکتهٔ مهم:** «بهترین سیستم‌عامل» وجود ندارد. انتخاب، تابع **اپلیکیشن** است، نه ترجیح شخصی.

**GUI در برابر Core — یک تصمیم امنیتی:**

| معیار | GUI | Core / Minimal |
|---|---|---|
| سطح حمله | بیشتر (مرورگر، سرویس‌های گرافیکی) | کمتر |
| مصرف RAM | ۲–۴GB بیشتر | حداقل |
| patch | بیشتر | کمتر |
| مدیریت | راحت‌تر برای تازه‌کار | نیاز به PowerShell/SSH |
| توصیه | سرور مدیریت، RDS | سرور تولیدی، DMZ |

### مثال‌های عملی

**Lab Scenario 1 — انتخاب OS برای سه سناریو**

> **وظیفه:** برای هر مورد، OS پیشنهاد بده و دلیل بیاور.
>
> الف) شرکت با ۲۰۰ کاربر ویندوز، نیاز به Group Policy و اشتراک فایل
> ب) استارتاپ با تیم DevOps که اپلیکیشن Node.js و PostgreSQL دارد
> ج) سرور مجازی‌سازی با ۴۰ VM
>
> **پاسخ:**
>
> | مورد | OS | دلیل |
> |---|---|---|
> | الف | **Windows Server** (با AD DS + File Server) | یکپارچگی با کلاینت‌های ویندوز، GPO |
> | ب | **Ubuntu Server LTS** یا **Rocky Linux** | بدون هزینهٔ لایسنس، ابزار DevOps، پشتیبانی از Node/Postgres |
> | ج | **VMware ESXi** یا **Proxmox** | hypervisor اختصاصی، مدیریت VM |
>
> **درس:** انتخاب OS از **اپلیکیشن و اکوسیستم** می‌آید، نه از علاقه.

**Lab Scenario 2 — Server Core در برابر Desktop Experience**

> **وضعیت:** یک سرور DNS/DHCP در DMZ. تیم می‌گوید «GUI راحت‌تر است».
>
> **وظیفه:** تحلیل کن.
>
> **پاسخ:**
> - **Server Core بهتر است:** سطح حملهٔ کمتر در DMZ حیاتی است؛ DNS/DHCP نیازی به GUI ندارند؛ patch کمتر.
> - **اما:** تیم باید با PowerShell و RSAT کار کند. اگر مهارت ندارد، ریسک عملیاتی بالا می‌رود.
> - **راه‌حل میانی:** Server Core + Windows Admin Center برای مدیریت گرافیکی از راه دور.
>
> **درس:** امنیت و راحتی، trade-off هستند. راه میانی وجود دارد.

### مقایسه و الگوهای مختلف

**Windows در برابر Linux — مقایسهٔ جامع:**

| معیار | Windows Server | Linux |
|---|---|---|
| هزینهٔ لایسنس | بالا (+CAL) | صفر یا کم |
| منحنی یادگیری | متوسط (GUI) | تند (CLI) |
| Active Directory | بومی | نیاز به Samba/FreeIPA |
| وب سرور | IIS | Nginx/Apache |
| مجازی‌سازی | Hyper-V | KVM/Xen |
| پایداری uptime | خوب (با reboot ماهانه) | عالی |
| اکوسیستم نرم‌افزاری | تجاری | متن‌باز + تجاری |
| ابزار مدیریت | GUI-centric | CLI-centric |
| مناسب برای | سازمان با اکوسیستم MS | ابر، وب، DevOps |

**مقایسهٔ توزیع‌های لینوکس از دید «پایداری در برابر تازگی»:**

| توزیع | پایداری | تازگی بسته | مناسب |
|---|---|---|---|
| Debian Stable | بسیار بالا | کم | سرور بدون تغییر |
| Ubuntu LTS | بالا | متوسط | عمومی، ابر |
| RHEL | بسیار بالا | کم | enterprise |
| Fedora | متوسط | بالا | آزمایش |
| Arch | کم | بسیار بالا | شخصی |

**نکته:** برای سرور، **LTS یا نسخهٔ enterprise** انتخاب کن، نه rolling release. rolling release یعنی تغییر مداوم، یعنی ریسک.

**مقایسهٔ حالت‌های نصب لینوکس:**

| حالت | توضیح | مناسب |
|---|---|---|
| **Minimal** | فقط بسته‌های ضروری | سرور تولیدی |
| **Standard** | ابزارهای رایج | عمومی |
| **Full** | همه چیز (شامل GUI) | آموزش، آزمایش |

### اشکال شایع

**۱. انتخاب OS بر اساس ترجیح شخصی.**
«من لینوکس دوست دارم» دلیل کافی نیست اگر اپلیکیشن مالی شرکت فقط ویندوز است.

**۲. نصب GUI روی سرور تولیدی.**
سطح حمله و مصرف منابع بیشتر، بدون فایدهٔ عملیاتی.

**۳. استفاده از rolling release در تولید.**
هر آپدیت، ریسک شکستن است. برای سرور، LTS.

**۴. بی‌توجهی به چرخهٔ عمر.**
CentOS 8 در ۲۰۲۱ EOL شد و هزاران سرور را در وضعیت ناامن گذاشت. قبل از انتخاب، **تاریخ EOL** را چک کن.

**۵. فرض اینکه «لینوکس رایگان است».**
رایگان است، اما مهارت، پشتیبانی و زمان شما رایگان نیست. RHEL با اشتراک، برای بسیاری ارزان‌تر از «رایگان + خرابی» است.

**۶. نادیده گرفتن سازگاری سخت‌افزار.**
درایور RAID یا NIC ممکن است در توزیع جدید پشتیبانی نشود. همیشه **hardware compatibility list** را چک کن.

### نکات مهم (Tips & Tricks)

- **قبل از انتخاب، «ماتریس سازگاری اپلیکیشن» بساز:** اپلیکیشن → OS پشتیبانی‌شده → نسخه.
- **تاریخ EOL را در تقویم بگذار** — ۱۲ ماه قبل.
- **یک OS استاندارد انتخاب کن، نه سه تا.** تنوع، هزینهٔ عملیاتی می‌سازد.
- **برای سرور جدید، Server Core یا Minimal** — مگر دلیل مشخص.
- **در آزمون:** اگر سؤال «least attack surface» داد، جواب: **Server Core / minimal install**.
- **نسخهٔ LTS را با kernel HWE (Hardware Enablement) بشناس** — برای سخت‌افزار جدید.

### خلاصه فصل

- چهار خانواده: **Windows Server، Linux، Unix تجاری، تخصصی**.
- انتخاب OS تابع **اپلیکیشن** است، نه ترجیح.
- **Server Core / Minimal** سطح حملهٔ کمتر، مصرف کمتر.
- برای سرور، **LTS یا enterprise**، نه rolling release.
- چرخهٔ عمر و EOL را قبل از انتخاب چک کن.
- لایسنس، فقط هزینهٔ نرم‌افزار نیست؛ مهارت و پشتیبانی هم هزینه است.

## فصل ۲۴: روش‌های نصب سیستم‌عامل

### مقدمه

نصب یک سرور، ساده به نظر می‌رسد: ISO را mount کن، Next بزن. اما در مقیاس، نصب ۵۰ سرور دستی یعنی ۵۰ بار ریسک اشتباه.

این فصل روش‌های نصب را از ساده به خودکار مرتب می‌کند — و در آزمون، بخش «installation methods» صریحاً در اهداف است.

### مفاهیم اساسی

**۱. نصب از رسانهٔ محلی**

- **USB** — رایج‌ترین روش برای یک سرور.
- **DVD** — قدیمی، در سرورهای جدید نادر.
- **مراحل:** ساخت رسانهٔ bootable (Rufus، `dd`، Ventoy) → تنظیم boot order در BIOS → بوت → نصب.

**۲. نصب از شبکه (PXE)**

**PXE (Preboot eXecution Environment)** — سرور از شبکه بوت می‌شود، بدون رسانهٔ محلی.

```
[کلاینت] --DHCP (IP + TFTP address)--> [DHCP server]
[کلاینت] --TFTP (bootloader)---------> [TFTP server]
[کلاینت] --HTTP/NFS (ISO/kernel)-----> [Web/NFS server]
```

**اجزا:**

- **DHCP** با option 66 (TFTP server) و 67 (boot filename).
- **TFTP** برای انتقال bootloader (pxelinux، grub، iPXE).
- **HTTP/NFS/SMB** برای فایل‌های نصب.

**مزیت:** نصب هم‌زمان ده‌ها سرور، بدون رسانه.
**عیب:** نیاز به زیرساخت (DHCP/TFTP)، پیچیدگی اولیه، ریسک امنیتی (PXE در شبکهٔ اشتباه).

**۳. نصب خودکار (Unattended)**

| ابزار | OS | فایل پاسخ |
|---|---|---|
| **Kickstart** | RHEL/Rocky/Alma | `ks.cfg` |
| **Autoinstall (subiquity)** | Ubuntu | `user-data` (YAML) |
| **Preseed** | Debian (قدیمی) | `preseed.cfg` |
| **Autounattend.xml** | Windows | XML |
| **Windows Deployment Services (WDS)** | Windows | image + answer file |
| **Microsoft Deployment Toolkit (MDT)** | Windows | task sequence |

**نمونهٔ Kickstart (حداقلی):**

```bash
#version=RHEL9
ignoredisk --only-use=sda
autopart --type=lvm
# پارتیشن‌بندی خودکار LVM
rootpw --iscrypted $6$...
# شبکه
network --bootproto=dhcp --device=ens192 --activate
# بسته‌ها
%packages
@^minimal-environment
%end
# اجرای پس از نصب
%post
systemctl enable sshd
%end
```

**نمونهٔ Autoinstall اوبونتو (خلاصه):**

```yaml
#cloud-config
autoinstall:
  version: 1
  identity:
    hostname: srv01
    username: admin
    password: "$6$..."
  storage:
    layout:
      name: lvm
  packages:
    - openssh-server
```

**۴. نصب از طریق OOB (Virtual Media)**

با iDRAC/iLO، یک ISO از راه دور mount می‌شود. مناسب برای سرور دور.

**۵. کلون کردن (Imaging)**

- **Clonezilla** — تصویربرداری از دیسک.
- **Acronis / Veeam Agent** — backup و restore به سخت‌افزار جدید.
- **Sysprep** (ویندوز) — حذف اطلاعات یکتا قبل از کلون.

**نکتهٔ مهم:** کلون کردن بدون `sysprep` در ویندوز، باعث **SID تکراری** می‌شود و مشکلات دامنه می‌سازد.

**۶. نصب در VM**

- **Template** — یک VM آماده که کلون می‌شود.
- **Cloud-init** — پیکربندی اولیه در بوت (hostname، کاربر، SSH key، شبکه).
- **Sysprep** برای ویندوز.

**مقایسهٔ روش‌ها:**

| روش | زمان برای ۱ سرور | زمان برای ۲۰ سرور | نیاز به زیرساخت |
|---|---|---|---|
| USB دستی | ۳۰–۶۰ دقیقه | ۱۰–۲۰ ساعت | هیچ |
| PXE + Kickstart | ۱۵–۳۰ دقیقه | ۱–۲ ساعت | DHCP/TFTP/HTTP |
| Imaging | ۱۰–۲۰ دقیقه | ۱–۳ ساعت | سرور تصویر |
| Template (VM) | ۵ دقیقه | ۱۵ دقیقه | پلتفرم مجازی‌سازی |

### مثال‌های عملی

**Lab Scenario 1 — نصب ۲۵ سرور جدید**

> **وضعیت:** ۲۵ سرور فیزیکی جدید، همه یک مدل، همه با یک نقش (web server). می‌خواهی یکنواخت و سریع نصب کنی.
>
> **وظیفه:** روش را انتخاب کن و مراحل را بنویس.
>
> **پاسخ:**
> **روش: PXE + Kickstart (یا Autoinstall)**
>
> ۱. یک سرور «نصب» بساز با DHCP، TFTP، HTTP.
> ۲. یک فایل پاسخ استاندارد بنویس (hostname به‌صورت پارامتر از MAC).
> ۳. BIOS سرورها را روی **PXE boot** بگذار (یا boot order: PXE اول).
> ۴. سرورها را روشن کن — همه به‌طور موازی نصب می‌شوند.
> ۵. بعد از نصب، با Ansible پیکربندی نهایی (web server، monitoring agent).
>
> **درس:** نصب دستی ۲۵ سرور، ۲۵ بار فرصت اشتباه است. خودکارسازی، یکنواختی می‌سازد.

**Lab Scenario 2 — نصب سرور در دیتاسنتر دور**

> **وضعیت:** سرور در شهری دیگر. تکنسین محلی فقط می‌تواند کابل وصل کند و برق بزند.
>
> **وظیفه:** چطور OS نصب می‌کنی؟
>
> **پاسخ:**
> ۱. BMC (iDRAC/iLO) را از قبل پیکربندی کن (IP، کاربر، دسترسی).
> ۲. با **Virtual Media** یک ISO mount کن.
> ۳. با **console redirection** نصب را پیش ببر (یا unattended با answer file).
> ۴. اگر network boot ممکن است، PXE هم گزینه است.
>
> **درس:** OOB (فصل ۱۶) تنها راه نصب از راه دور است.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه ابزار خودکارسازی نصب لینوکس:**

| ابزار | OS | فرمت | مزیت |
|---|---|---|---|
| **Kickstart** | RHEL family | متن ساده | ساده، مستند |
| **Autoinstall** | Ubuntu | YAML | مدرن، خوانا |
| **cloud-init** | چند OS | YAML | استاندارد ابری |

**مقایسهٔ WDS و MDT:**

| معیار | WDS | MDT |
|---|---|---|
| تصویربرداری شبکه | ✅ | ✅ (با WDS) |
| task sequence | محدود | ✅ |
| نصب اپلیکیشن | ❌ | ✅ |
| پیچیدگی | کم | زیاد |
| مناسب برای | نصب سریع | استقرار کامل سازمانی |

**نکته:** امروز Microsoft Intune و Autopilot جایگزین بخشی از MDT شده‌اند، اما برای سرور، MDT/WDS هنوز رایج است.

**مقایسهٔ نصب «تمیز» و «ارتقا»:**

| معیار | Clean install | In-place upgrade |
|---|---|---|
| پایداری | بالا | متوسط |
| زمان | بیشتر | کمتر |
| ریسک | کم | متوسط (نرم‌افزار قدیمی) |
| توصیه برای سرور | ✅ | فقط با دلیل |

### اشکال شایع

**۱. نصب دستی در مقیاس.**
۲۰ سرور دستی = ۲۰ پیکربندی متفاوت. بعداً عیب‌یابی جهنم است.

**۲. PXE در شبکهٔ اشتباه.**
اگر PXE روی VLAN عمومی فعال باشد، هر دستگاهی می‌تواند بوت شود. خطر امنیتی.

**۳. فراموش کردن sysprep در کلون ویندوز.**
SID تکراری، مشکلات دامنه، WSUS ناسازگار.

**۴. نصب بدون ثبت تنظیمات.**
اگر ندانید چه پارتیشن‌بندی و چه بسته‌هایی نصب شده، بازسازی سرور غیرممکن است.

**۵. بی‌توجهی به درایور storage.**
ویندوز سرور روی کنترلر RAID جدید، بدون درایور، دیسک را نمی‌بیند. باید درایور را در نصب load کنی (F6/floppy emulation یا در ISO).

**۶. نصب از ISO قدیمی.**
ISO قدیمی، patchهای امنیتی سال‌ها را ندارد. بعد از نصب، آپدیت طولانی و پرخطر است.

**۷. نصب روی سخت‌افزار بدون چک سازگاری.**
نصب موفق، اما NIC یا RAID بدون درایور. سرور بوت می‌شود اما بی‌فایده است.

### نکات مهم (Tips & Tricks)

- **قبل از نصب، «برگهٔ نصب» بنویس:** hostname، IP، پارتیشن‌بندی، بسته‌ها، نقش. یک صفحه.
- **ISO را با checksum تأیید کن** (`sha256sum`). ISO خراب، نصب شکست‌خورده می‌دهد.
- **در BIOS، حالت storage را چک کن:** RAID یا AHCI. اشتباه، دیسک را پنهان می‌کند.
- **UEFI در برابر Legacy:** UEFI با GPT، امن‌تر (Secure Boot). برای سرور جدید، UEFI.
- **برای ویندوز، `Autounattend.xml` را با Windows SIM بساز**، نه دستی.
- **در آزمون:** کلیدواژهٔ «install many servers simultaneously» → **PXE / network installation**.

### خلاصه فصل

- روش‌ها: **USB، PXE، unattended، virtual media، imaging، template**.
- **PXE** = DHCP + TFTP + HTTP/NFS.
- **Kickstart** (RHEL)، **Autoinstall** (Ubuntu)، **Autounattend** (Windows).
- **sysprep** برای کلون ویندوز الزامی است.
- OOB + Virtual Media برای سرور دور.
- نصب در مقیاس = خودکارسازی + یکنواختی.

## فصل ۲۵: پارتیشن‌بندی و فایل‌سیستم‌ها

### مقدمه

پارتیشن‌بندی، تصمیمی است که بعداً تغییرش سخت و پرخطر است. اگر `/var` را کوچک بگیری، لاگ‌ها فضا را پر می‌کنند و سرور می‌خوابد. اگر `/boot` را جدا نکنی، آپدیت kernel ممکن است شکست بخورد.

این فصل دربارهٔ MBR/GPT، پارتیشن‌های استاندارد، فایل‌سیستم‌ها و الگوهای چیدمان است. در آزمون، بخش «partition types» و «file systems» صریحاً در اهداف است.

### مفاهیم اساسی

**MBR در برابر GPT:**

| معیار | MBR | GPT |
|---|---|---|
| حداکثر دیسک | ۲TB | ۹.۴ ZB (عملاً نامحدود) |
| حداکثر پارتیشن | ۴ (primary) | ۱۲۸ |
| جدول پارتیشن | یک نسخه | دو نسخه (backup) |
| CRC | ندارد | دارد (تشخیص خرابی) |
| Boot | BIOS/Legacy | UEFI (و BIOS با hybrid) |
| توصیه امروز | ❌ | ✅ |

**نکتهٔ حیاتی:** دیسک بالای ۲TB با MBR، فقط ۲TB اول را می‌بیند. برای دیسک بزرگ، **GPT الزامی** است.

**پارتیشن‌های استاندارد لینوکس:**

| مسیر | اندازهٔ پیشنهادی | چرا جدا |
|---|---|---|
| `/` (root) | ۲۰–۵۰GB | سیستم پایه |
| `/boot` | ۱GB | kernel و initramfs؛ باید قبل از LVM باشد |
| `/boot/efi` | ۵۱۲MB (FAT32) | برای UEFI |
| `/var` | ۲۰–۵۰GB یا بیشتر | لاگ‌ها می‌توانند رشد انفجاری کنند |
| `/var/log` | ۱۰GB | جدا کردن لاگ از `/var` |
| `/home` | متغیر | دادهٔ کاربر |
| `/tmp` | ۵–۱۰GB | جلوگیری از پر شدن root |
| `swap` | = RAM (برای hibernation) یا ۲–۸GB | حافظهٔ مجازی |
| `/opt` | متغیر | نرم‌افزار third-party |
| `/srv` | متغیر | دادهٔ سرویس (web، ftp) |

**چرا `/var` جدا؟** چون اگر لاگ‌ها فضا را پر کنند و `/var` روی root باشد، **کل سیستم** از کار می‌افتد. اگر جدا باشد، فقط لاگ‌ها مشکل می‌شوند.

**پارتیشن‌های استاندارد ویندوز:**

| پارتیشن | اندازه | توضیح |
|---|---|---|
| **System Reserved / EFI** | ۱۰۰MB (BIOS) / ۱۰۰–۵۰۰MB (UEFI) | boot files |
| **Recovery** | ۵۰۰MB–۱GB | WinRE |
| **C:** | ۱۰۰GB+ | OS و برنامه‌ها |
| **Data** | متغیر | داده |

**نکته:** در ویندوز سرور، `C:` را بزرگ بگیر (حداقل ۱۰۰GB) چون Windows Update و log می‌توانند ده‌ها گیگابایت بگیرند.

**LVM (Logical Volume Manager) در لینوکس:**

```
[دیسک فیزیکی] → [PV (Physical Volume)] → [VG (Volume Group)] → [LV (Logical Volume)]
```

**مزیت LVM:**

- **تغییر اندازهٔ آنلاین** (با فایل‌سیستم مناسب).
- **snapshot** برای backup.
- **تجمیع چند دیسک** در یک pool.
- **thin provisioning**.

**مثال:**

```bash
# ساخت PV
pvcreate /dev/sdb /dev/sdc

# ساخت VG
vgcreate vg_data /dev/sdb /dev/sdc

# ساخت LV
lvcreate -L 500G -n lv_var vg_data

# فرمت
mkfs.xfs /dev/vg_data/lv_var

# گسترش آنلاین
lvextend -L +100G /dev/vg_data/lv_var
xfs_growfs /mnt/var
```

**نکتهٔ حیاتی:** LVM انعطاف می‌دهد، اما **`/boot` نباید روی LVM باشد** (GRUB قدیمی نمی‌تواند بخواند؛ گرچه GRUB2 پشتیبانی دارد، اما توصیهٔ عمومی جداسازی است).

**Storage Spaces (ویندوز):** معادل LVM در ویندوز. امکان pool، thin provisioning، resiliency (mirror/parity).

**فایل‌سیستم‌ها — مقایسه:**

| فایل‌سیستم | OS | حداکثر فایل | حداکثر حجم | ویژگی‌ها |
|---|---|---|---|---|
| **NTFS** | ویندوز | ۱۶EB | ۲۵۶TB | journaling، ACL، فشرده‌سازی، encryption |
| **ReFS** | ویندوز سرور | ۳۵PB | ۱YB | integrity streams، block cloning، مقاوم‌تر |
| **ext4** | لینوکس | ۱۶TB | ۱EB | journaling، پایدار، عمومی |
| **XFS** | لینوکس | ۸EB | ۸EB | عملکرد بالا، گسترش آنلاین (بدون کوچک‌شدن) |
| **Btrfs** | لینوکس | ۱۶EB | ۱EB | snapshot، checksum، RAID |
| **ZFS** | لینوکس/FreeBSD | ۱۶EB | ۲۵۶ZB | checksum، snapshot، RAID، dedup |

**نکتهٔ مهم:** **XFS نمی‌تواند کوچک شود** (فقط گسترش). ext4 می‌تواند هر دو (با unmount برای کوچک‌کردن).

**ReFS در برابر NTFS:**

| معیار | NTFS | ReFS |
|---|---|---|
| boot | ✅ | ❌ (فقط داده) |
| integrity | محدود | ✅ |
| block cloning | ❌ | ✅ (سریع برای VM) |
| سازگاری | همه‌جا | ویندوز سرور جدید |
| مناسب برای | OS | داده، Hyper-V |

**مفاهیم پیشرفته:**

- **Journaling** — ثبت تغییرات قبل از اعمال، برای بازیابی پس از crash.
- **Copy-on-write (CoW)** — ZFS، Btrfs. داده جدید در جای جدید نوشته می‌شود.
- **Checksum** — تشخیص خرابی داده (ZFS، ReFS، Btrfs).
- **Quota** — محدودیت فضا برای کاربر/گروه.
- **ACL** — کنترل دسترسی دقیق.

### مثال‌های عملی

**Lab Scenario 1 — طراحی پارتیشن‌بندی برای یک سرور وب**

> **وضعیت:** سرور با ۲ دیسک ۵۰۰GB (RAID 1)، ۳۲GB RAM، نقش web + database.
>
> **وظیفه:** چیدمان پارتیشن پیشنهاد بده.
>
> **پاسخ:**
>
> ```
> /boot      1GB      (ext4، خارج از LVM)
> /boot/efi  512MB    (FAT32)
> swap       16GB     (نصف RAM)
> /          40GB     (xfs)
> /var       100GB    (xfs) — لاگ‌ها
> /var/lib/mysql یا /var/lib/pgsql  150GB  — دیتابیس
> /home      20GB
> /tmp       10GB
> باقی‌مانده (~۱۶۰GB) — فضای آزاد برای گسترش
> ```
>
> **درس:** دیتابیس را جدا کن (هم برای عملکرد هم برای backup)، لاگ را جدا کن (برای جلوگیری از پر شدن root)، و فضای آزاد نگه دار (برای رشد).

**Lab Scenario 2 — سرور پر شد**

> **وضعیت:** هشدار: `/` با ۱۰۰٪ پر است. سرور پاسخ نمی‌دهد.
>
> **وظیفه:** چه می‌کنی و چه درسی می‌گیری؟
>
> **پاسخ:**
> ۱. **دسترسی اضطراری:** از console (iDRAC/iLO) وارد شو، چون SSH ممکن است کار نکند (نیاز به نوشتن در `/tmp`).
> ۲. **پیدا کردن مقصر:** `du -xh / --max-depth=1 | sort -h` — کدام پوشه بزرگ است؟
> ۳. **معمولاً:** `/var/log` (لاگ پرنشده)، `/var/cache`، فایل حذف‌شده که هنوز باز است (`lsof +L1`).
> ۴. **پاک‌سازی:** حذف لاگ‌های قدیمی، `journalctl --vacuum-size=500M`.
> ۵. **ریشه:** `logrotate` تنظیم نبوده یا `/var` جدا نبوده.
>
> **درس:** پارتیشن `/var` جدا + `logrotate` + هشدار در ۸۵٪ = جلوگیری از این رخداد.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه الگوی پارتیشن‌بندی:**

| الگو | توضیح | مزیت | عیب |
|---|---|---|---|
| **همه در `/`** | ساده | ساده، فضای انعطاف | یک پر شدن = کل سیستم |
| **تقسیم استاندارد** | `/`، `/var`، `/home`، swap | جداسازی ریسک | نیاز به برنامه‌ریزی |
| **LVM همه‌جا** | همه در LVM | انعطاف حداکثری | پیچیدگی، نیاز به initramfs |

**توصیه:** تقسیم استاندارد + LVM برای داده. `/boot` جدا و خارج از LVM.

**مقایسهٔ swap:**

| اندازه | مناسب برای |
|---|---|
| ۲× RAM | hibernation |
| = RAM | عمومی سنتی |
| ۲–۸GB | سرور با RAM زیاد (فقط برای اضطراری) |
| صفر | Kubernetes (اگر تنظیم شده) |

**نکته:** در سرور با ۱۲۸GB RAM، swap ۲۵۶GB معمولاً هدر است. ۸–۱۶GB برای اضطراری کافی است — مگر hibernation بخواهی.

**مقایسهٔ RAID سخت‌افزاری و LVM:**

| معیار | RAID سخت‌افزاری | LVM |
|---|---|---|
| افزونگی | ✅ | ❌ (LVM خودش RAID نیست، مگر با dm-raid) |
| انعطاف حجم | محدود | بالا |
| snapshot | بستگی به کنترلر | ✅ |
| مناسب برای | افزونگی | مدیریت فضا |

**نکته:** LVM جای RAID را نمی‌گیرد. اول RAID (سخت‌افزاری)، بعد LVM روی آن.

### اشکال شایع

**۱. MBR روی دیسک بالای ۲TB.**
۲TB هدر می‌رود. همیشه GPT.

**۲. `/var` روی root.**
یک لاگ پرنشده، کل سرور را می‌خواباند.

**۳. `/boot` روی LVM.**
GRUB ممکن است نتواند بوت کند (بستگی به نسخه). توصیه: جدا و ext4.

**۴. swap خیلی کوچک یا صفر بدون برنامه.**
OOM killer پروسه‌ها را می‌کشد. در سرور با RAM زیاد، ۸GB کافی است — اما صفر نکن مگر بدانی چه می‌کنی.

**۵. فرمت کردن دیسک اشتباه.**
`mkfs` روی دیسک داده، فاجعه است. همیشه `lsblk` و `blkid` قبل از فرمت.

**۶. کوچک کردن XFS.**
XFS نمی‌تواند کوچک شود. اگر نیاز داری، باید backup/restore کنی.

**۷. بی‌توجهی به alignment.**
در SSD و LUN، پارتیشن باید روی ۱MB align شود. `parted` مدرن خودکار انجام می‌دهد.

### نکات مهم (Tips & Tricks)

- **قبل از فرمت، `lsblk -f` بزن.** یک ثانیه، از فاجعه جلوگیری می‌کند.
- **`/boot` را ۱GB بگیر** — با چند kernel، ۵۰۰MB کم می‌آید.
- **برای دیتابیس، فایل‌سیستم و block size را با page size هم‌تراز کن.**
- **LVM snapshot برای backup کوتاه‌مدت، نه بلندمدت** (پر می‌شود).
- **`logrotate` را از روز اول تنظیم کن.**
- **در آزمون:** کلیدواژهٔ «disk larger than 2TB» → **GPT**؛ «resize online» → **LVM**؛ «cannot shrink» → **XFS**.

### خلاصه فصل

- **GPT** برای دیسک بالای ۲TB و UEFI؛ MBR منسوخ است.
- پارتیشن‌های استاندارد: `/`، `/boot`، `/var`، `/home`، swap.
- **`/var` جدا** = جلوگیری از خوابیدن کل سیستم با پر شدن لاگ.
- **LVM** انعطاف و snapshot می‌دهد؛ جای RAID نیست.
- **XFS** گسترش آنلاین دارد اما کوچک نمی‌شود؛ ext4 هر دو.
- **ReFS** برای داده و Hyper-V، نه boot.

## فصل ۲۶: پیکربندی اولیه و نقش‌های سرور

### مقدمه

بعد از نصب، سرور یک «ماشین خالی» است. این فصل دربارهٔ تبدیل آن به یک سرویس‌دهنده است: hostname، شبکه، به‌روزرسانی، نقش‌ها و سرویس‌ها.

این کارها ساده به نظر می‌رسند، اما ترتیب و جزئیاتشان مهم است. یک hostname اشتباه یا NTP تنظیم‌نشده، بعداً دردسر می‌سازد.

### مفاهیم اساسی

**چک‌لیست پیکربندی اولیه (ترتیب پیشنهادی):**

۱. **Hostname و domain** — نام‌گذاری استاندارد.
۲. **شبکه** — IP، subnet، gateway، DNS.
۳. **زمان (NTP)** — قبل از هر چیز دیگری که به زمان وابسته است.
۴. **به‌روزرسانی** — patchهای امنیتی.
۵. **کاربران و دسترسی** — کاربر مدیریتی، SSH key، غیرفعال کردن root login.
۶. **فایروال** — حداقل پورت‌های لازم.
۷. **ابزار مدیریت** — agent مانیتورینگ، backup agent.
۸. **نقش‌ها** — نصب سرویس مورد نظر.
۹. **مستندسازی** — ثبت همهٔ موارد بالا.

**نام‌گذاری (naming convention):**

```
[نقش][شماره].[domain]
dc01.corp.example.com
web02.corp.example.com
db01.corp.example.com
```

**قواعد:**

- کوتاه، خوانا، قابل پیش‌بینی.
- بدون اطلاعات حساس (مثل `finance-server` که هدف را لو می‌دهد).
- سازگار با DNS (حروف کوچک، خط تیره، بدون فاصله).
- حداکثر ۱۵ کاراکتر برای NetBIOS در ویندوز.

**شبکه — تنظیمات ضروری:**

| مورد | نکته |
|---|---|
| IP | static برای سرور (نه DHCP، مگر رزرو) |
| Subnet mask / CIDR | دقت در محاسبه |
| Gateway | معمولاً یک عدد |
| DNS | حداقل دو سرور DNS |
| Search domain | برای resolve نام کوتاه |
| MTU | پیش‌فرض ۱۵۰۰، jumbo در iSCSI |

**NTP — چرا اول؟**

- Kerberos (Active Directory) به اختلاف زمان <۵ دقیقه نیاز دارد.
- لاگ‌ها بدون زمان درست، بی‌فایده‌اند.
- گواهی‌های TLS به زمان وابسته‌اند.
- backup و scheduled task به زمان وابسته‌اند.

**تنظیم NTP در لینوکس (chrony):**

```bash
# /etc/chrony.conf
pool 2.pool.ntp.org iburst
# یا سرور داخلی
server ntp1.corp.example.com iburst

# بررسی
chronyc sources -v
chronyc tracking
timedatectl
```

**در ویندوز:**

```powershell
w32tm /config /manualpeerlist:"ntp1.corp.example.com" /syncfromflags:manual /update
Restart-Service w32time
w32tm /query /status
```

**به‌روزرسانی — دو رویکرد:**

| رویکرد | توضیح | مناسب |
|---|---|---|
| **بدون کنترل** | هر سرور خودش آپدیت می‌کند | کوچک، پرخطر |
| **مدیریت‌شده** | WSUS/SCCM (ویندوز)، Satellite/Landscape (لینوکس)، Ansible | سازمانی |

**نکتهٔ مهم:** سرور تولیدی نباید **خودکار ری‌استارت** کند. آپدیت دانلود شود، اما نصب/ری‌استارت در پنجرهٔ تغییر.

**نقش‌های سرور — تعریف:**

**نقش (Role)** = مجموعه‌ای از سرویس‌ها که یک عملکرد را ارائه می‌دهند.

| نقش | سرویس | پورت‌ها |
|---|---|---|
| **Domain Controller** | AD DS | 53، 88، 389، 445، 636 |
| **DNS** | named/bind یا DNS Server | 53 (TCP/UDP) |
| **DHCP** | dhcpd | 67/68 |
| **File Server** | SMB/NFS | 445 / 2049 |
| **Web Server** | IIS/Nginx/Apache | 80، 443 |
| **Database** | MSSQL/PostgreSQL/MySQL | 1433 / 5432 / 3306 |
| **Mail** | Exchange/Postfix | 25، 143، 587، 993 |
| **Virtualization** | Hyper-V/KVM | 5985/5986، 443 |
| **Backup** | Veeam/Bacula | متغیر |

**اصل کمینه:** فقط نقش‌هایی را نصب کن که لازم است. هر نقش اضافه = سطح حملهٔ بیشتر + patch بیشتر + مصرف منابع.

**سرویس‌ها (Services) در برابر نقش‌ها:**

- **Role** — مجموعه (مثلاً File Server شامل SMB، Share، Quota).
- **Service** — یک پروسهٔ مستقل (مثلاً `sshd`، `httpd`).
- **Feature** — قابلیت (مثلاً .NET Framework، BitLocker).

**مدیریت سرویس در لینوکس (systemd):**

```bash
systemctl status nginx
systemctl enable --now nginx    # فعال + شروع
systemctl disable nginx
systemctl list-units --type=service --state=running
journalctl -u nginx -f
```

**در ویندوز:**

```powershell
Get-Service | Where-Object {$_.Status -eq "Running"}
Start-Service -Name "W3SVC"
Set-Service -Name "W3SVC" -StartupType Automatic
```

> **پاسخ:**

**Lab Scenario 2 — سرور به دامنه نمی‌پیوندد**

>
> **وظیفه:** پنج چیز را چک کن.
>
> **پاسخ:**

### مقایسه و الگوهای مختلف

**مقایسهٔ روش‌های پیکربندی:**

| روش | توضیح | مقیاس | تکرارپذیری |
|---|---|---|---|
| **دستی** | GUI یا CLI روی هر سرور | ۱–۳ | کم |
| **اسکریپت** | Bash/PowerShell | ۵–۲۰ | متوسط |
| **Configuration Management** | Ansible، Puppet، Chef | ۲۰+ | بالا |
| **Image/Template** | VM template + cloud-init | بالا | بالا |

**توصیه:** برای بیش از ۵ سرور، از همان اول Ansible. حتی اگر فقط `hostname` و `NTP` را مدیریت کند.

**مقایسهٔ نقش‌های متمرکز و توزیع‌شده:**

| نقش | متمرکز | توزیع‌شده |
|---|---|---|
| DNS | یک سرور | دو سرور (primary/secondary) |
| DHCP | یک سرور | split scope یا failover |
| File | یک سرور | DFS/GlusterFS |
| Database | یک سرور | replica/cluster |

**اصل:** هر نقش حیاتی، حداقل دو نمونه داشته باشد (فصل ۳۸).

**مقایسهٔ Server Core و Desktop Experience در مدیریت نقش:**

| معیار | Core | Desktop |
|---|---|---|
| نصب نقش | PowerShell / Server Manager از راه دور | GUI |
| عیب‌یابی | RSAT، WinRM | محلی |
| امنیت | بالاتر | پایین‌تر |

### اشکال شایع

**۱. IP از DHCP برای سرور.**
اگر DHCP قطع شود، سرور IP عوض می‌کند و سرویس می‌خوابد. همیشه static یا reservation.

**۲. فقط یک DNS.**
اگر DNS بخوابد، resolve نام ممکن نیست و بسیاری از سرویس‌ها می‌خوابند. حداقل دو.

**۳. NTP تنظیم‌نشده.**
لاگ‌ها بی‌ترتیب، Kerberos شکسته، گواهی‌ها معتبر نیستند.

**۴. نصب نقش‌های اضافه.**
هر نقش اضافه، سطح حمله است. فقط لازم‌ها.

**۵. hostname پیش‌فرض.**
`localhost` یا `ubuntu-server` در شبکه با ۵۰ سرور دیگر، عیب‌یابی را جهنم می‌کند.

**۶. فعال بودن root login با رمز.**
SSH با root و رمز، هدف اول brute force است.

**۷. بی‌توجهی به فایروال محلی.**
حتی اگر فایروال شبکه هست، فایروال محلی لایهٔ دوم است.

**۸. آپدیت خودکار با ری‌استارت.**
سرور تولیدی در ساعت ۳ بامداد ری‌استارت می‌شود و سرویس قطع.

### نکات مهم (Tips & Tricks)

- **یک اسکریپت «bootstrap» بنویس** که همهٔ مراحل اولیه را انجام دهد. ۳۰ دقیقه سرمایه‌گذاری، ساعت‌ها صرفه‌جویی.
- **قبل از join دامنه، `nslookup` و `w32tm /query /status`.**
- **SSH key به‌جای رمز.** و `PasswordAuthentication no`.
- **در ویندوز، `sconfig`** ابزار سریع پیکربندی Server Core است.
- **در لینوکس، `nmcli` یا `netplan`** — یکی را استاندارد کن.
- **در آزمون:** کلیدواژهٔ «cannot join domain» → **DNS**؛ «time skew» → **NTP**.

### خلاصه فصل

- ترتیب پیکربندی: **hostname → شبکه → NTP → آپدیت → امنیت → نقش‌ها**.
- **NTP اول**، چون همه چیز به زمان وابسته است.
- سرور، IP **static** و حداقل **دو DNS**.
- فقط نقش‌های لازم را نصب کن.
- برای بیش از ۵ سرور، **Configuration Management**.
- هر نقش حیاتی، حداقل دو نمونه.

## فصل ۲۷: لایسنس، فعال‌سازی و انطباق

### مقدمه

لایسنس، خشک‌ترین بخش این کتابچه است — و یکی از پرهزینه‌ترین. یک سازمان می‌تواند سال‌ها بدون اطلاع، غیرقانونی کار کند و در یک ممیزی، جریمهٔ سنگین بدهد.

این فصل دربارهٔ مدل‌های لایسنس، فعال‌سازی و انطباق است. در آزمون، بخش «licensing» زیرمجموعهٔ دامنهٔ مدیریت است.

### مفاهیم اساسی

**مدل‌های لایسنس ویندوز سرور:**

| مدل | توضیح | مناسب |
|---|---|---|
| **Per-Core** | لایسنس بر اساس هستهٔ فیزیکی (حداقل ۸ هسته در هر سوکت، حداقل ۱۶ در هر سرور) | استاندارد امروز |
| **Per-User CAL** | هر کاربر یک CAL | کاربران مشخص |
| **Per-Device CAL** | هر دستگاه یک CAL | شیفت‌کاری، دستگاه مشترک |
| **Datacenter** | لایسنس نامحدود VM روی یک سرور | مجازی‌سازی سنگین |
| **Standard** | ۲ VM (یا ۲ OSE) | مجازی‌سازی سبک |

**نکتهٔ حیاتی:** لایسنس ویندوز سرور = **لایسنس OS** + **CAL**. CAL جداگانه خریداری می‌شود. بدون CAL، دسترسی کاربران غیرقانونی است.

**مثال محاسبه:**

> سرور با ۲ سوکت، هر کدام ۱۶ هسته. ۱۰۰ کاربر.
>
> - لایسنس هسته: ۲ × ۱۶ = ۳۲ هسته (بالای حداقل ۱۶، پس ۳۲ لایسنس core)
> - CAL: ۱۰۰ کاربر × User CAL (یا ۱۰۰ Device CAL)
> - اگر ۲۰ VM روی این سرور باشد: **Datacenter** (Standard فقط ۲ VM می‌دهد)

**مدل‌های لایسنس لینوکس:**

| توزیع | مدل | هزینه |
|---|---|---|
| **RHEL** | اشتراک (subscription) per socket/pair | سالانه |
| **Ubuntu Pro** | اشتراک per node | سالانه |
| **SUSE** | اشتراک | سالانه |
| **Debian/Rocky/Alma** | رایگان | صفر |
| **Oracle Linux** | رایگان (پشتیبانی اختیاری) | صفر یا اشتراک |

**نکتهٔ مهم:** «رایگان» به معنای «بدون تعهد» نیست. اگر RHEL می‌خواهی و اشتراک نمی‌خری، از Rocky/Alma استفاده کن (سازگار با RHEL) — نه اینکه RHEL بدون لایسنس اجرا کنی.

**GPL و متن‌باز — یک نکتهٔ حقوقی:**

- GPL می‌گوید اگر نرم‌افزار GPL را **توزیع** کنی، باید سورس را هم بدهی.
- استفادهٔ داخلی سازمانی، «توزیع» نیست.
- اما اگر محصولی بر پایهٔ GPL بسازی و بفروشی، تعهدات داری.

> ⚠️ **مرز قانونی:** این کتابچه مشاورهٔ حقوقی نیست. برای تصمیم‌های لایسنس در سازمان، با واحد حقوقی یا مشاور مجوز مشورت کن.

**فعال‌سازی (Activation):**

| روش | توضیح | مناسب |
|---|---|---|
| **MAK (Multiple Activation Key)** | یک کلید برای چند نصب، با سقف | سازمان کوچک |
| **KMS (Key Management Service)** | سرور داخلی، فعال‌سازی خودکار | سازمان بزرگ (۲۵+ کلاینت) |
| **AD-based Activation** | فعال‌سازی با دامنه | سازمان با AD |
| **AVMA** | فعال‌سازی خودکار VM روی Hyper-V | مجازی‌سازی |

**نکتهٔ KMS:** کلاینت هر ۱۸۰ روز باید تمدید کند (renewal interval ۷ روز). اگر KMS در دسترس نباشد، بعد از ۱۸۰ روز، ویندوز به حالت «غیرفعال» می‌رود.

**انطباق (Compliance) — سه سطح:**

- **قانونی** — لایسنس داری، مطابق قرارداد عمل می‌کنی.
- **فنی** — نسخه‌ها و patchها مطابق سیاست.
- **ممیزی‌پذیر** — می‌توانی اثبات کنی (مستندات، شمارش).

**ابزارهای مدیریت لایسنس:**

| ابزار | کاربرد |
|---|---|
| **Microsoft Volume Licensing Service Center (VLSC)** | مدیریت کلیدها و تعداد |
| **Azure Arc / Defender for Cloud** | نمای لایسنس ابری |
| **Red Hat Subscription Manager** (`subscription-manager`) | مدیریت اشتراک RHEL |
| **Landscape** (Ubuntu) | مدیریت Ubuntu |
| **SAM (Software Asset Management)** | ابزارهای تجاری (Snow، Flexera) |

**مفاهیم مهم انطباق:**

- **True-up** — گزارش دوره‌ای تعداد واقعی به vendor و پرداخت مابه‌التفاوت.
- **Audit clause** — حق vendor برای ممیزی.
- **Over-deployment** — نصب بیش از لایسنس، ریسک جریمه.
- **License mobility** — انتقال لایسنس بین سرورها (محدودیت دارد).

### مثال‌های عملی

**Lab Scenario 1 — محاسبهٔ لایسنس**

> **وضعیت:** ۴ سرور فیزیکی، هر کدام ۲ سوکت ۱۲ هسته. ۱۵۰ کاربر. ۳۰ VM روی دو سرور مجازی‌سازی.
>
> **وظیفه:** لایسنس ویندوز لازم؟
>
> **پاسخ:**
> - **سرورهای مجازی‌سازی (۲ سرور، ۲۴ هسته هر کدام):**
>   - هر سرور: ۲۴ هسته → ۲۴ core license
>   - ۳۰ VM → نیاز به **Datacenter** (Standard فقط ۲ VM)
> - **سرورهای دیگر (۲ سرور، ۲۴ هسته):**
>   - اگر نقش سبک دارند (فایل، DNS) → **Standard**
> - **CAL:** ۱۵۰ User CAL (یا Device CAL اگر شیفت‌کاری)
>
> **جمع:**
> - ۲ × Datacenter (۲۴ core)
> - ۲ × Standard (۲۴ core)
> - ۱۵۰ CAL
>
> **درس:** Datacenter برای مجازی‌سازی سنگین اقتصادی است؛ برای ۲ VM، Standard.

**Lab Scenario 2 — ممیزی ناگهانی**

> **وضعیت:** vendor اعلام ممیزی کرده. ۵ سرور داری، اما فقط ۳ لایسنس داری. ۴۰ کاربر، ۲۵ CAL.
>
> **وظیفه:** چه می‌کنی؟
>
> **پاسخ:**
> ۱. **فهرست دقیق:** همهٔ سرورها، نسخه‌ها، هسته‌ها، VMها.
> ۲. **مقایسه با لایسنس:** کسری را مشخص کن.
> ۳. **خرید مابه‌التفاوت** قبل از پایان ممیزی (معمولاً جریمهٔ کمتری دارد).
> ۴. **ریشه‌یابی:** چرا شمارش از دست رفت؟ (نبود SAM، خرید بدون ثبت)
> ۵. **اصلاح فرآیند:** CMDB + بازبینی فصلی.
>
> **درس:** ممیزی، رویداد نیست؛ نتیجهٔ سال‌ها بی‌توجهی است.

### مقایسه و الگوهای مختلف

**Standard در برابر Datacenter:**

| معیار | Standard | Datacenter |
|---|---|---|
| VM مجاز | ۲ | نامحدود |
| هزینه | پایه | ~۵–۷ برابر |
| مناسب برای | نقش تک، ۱–۲ VM | مجازی‌سازی، ابر خصوصی |
| نقطهٔ سربه‌سر | حدود ۱۰–۱۲ VM | بالای آن |

**مقایسهٔ MAK و KMS:**

| معیار | MAK | KMS |
|---|---|---|
| نیاز به سرور | ❌ | ✅ |
| فعال‌سازی خودکار | ❌ | ✅ |
| مناسب برای | <۲۵ کلاینت | ۲۵+ کلاینت |
| ریسک | شمارش دستی | وابسته به KMS |

**مقایسهٔ مدل‌های خرید:**

| مدل | توضیح | مناسب |
|---|---|---|
| **Perpetual** | خرید دائمی + Software Assurance | بلندمدت |
| **Subscription** | اشتراک سالانه | انعطاف، ابری |
| **Cloud (PAYG)** | پرداخت مصرفی | بار متغیر |

**نکته:** روند صنعت به سمت subscription است. برای سازمان با رشد نامشخص، subscription انعطاف بیشتری می‌دهد.

### اشکال شایع

**۱. فراموش کردن CAL.**
لایسنس OS داری، اما CAL نه. این رایج‌ترین نقض است.

**۲. محاسبهٔ هسته بر اساس هستهٔ مجازی.**
لایسنس per-core بر اساس **هستهٔ فیزیکی** است، نه vCPU.

**۳. استفاده از Standard برای ۱۰ VM.**
Standard فقط ۲ VM می‌دهد. برای ۱۰ VM باید ۵ لایسنس Standard بخری — که از Datacenter گران‌تر می‌شود.

**۴. KMS بدون برنامهٔ پشتیبان.**
اگر KMS بخوابد و ۱۸۰ روز بگذرد، کلاینت‌ها غیرفعال می‌شوند.

**۵. نصب RHEL بدون اشتراک.**
اشتراک RHEL شامل دسترسی به مخازن است. بدون آن، `dnf update` کار نمی‌کند.

**۶. بی‌توجهی به license mobility در ابر.**
بعضی لایسنس‌ها در ابر مجاز نیستند یا محدودیت دارند.

**۷. نداشتن مستندات لایسنس.**
در ممیزی، «فکر می‌کنم خریدیم» کافی نیست. فاکتور و کلید لازم است.

### نکات مهم (Tips & Tricks)

- **CMDB بساز** و هر سرور را با لایسنس مرتبط کن. این پایهٔ انطباق است.
- **بازبینی فصلی:** تعداد واقعی در برابر تعداد لایسنس.
- **قبل از مجازی‌سازی سنگین، محاسبهٔ Standard/Datacenter** انجام بده — تفاوت هزینه زیاد است.
- **کلیدها را در یک vault امن** نگه دار، نه در فایل متنی روی سرور.
- **در قرارداد، audit clause را بخوان** — بدان چه تعهدی دادی.
- **در آزمون:** کلیدواژهٔ «unlimited VMs» → **Datacenter**؛ «2 VMs» → **Standard**.

### خلاصه فصل

- ویندوز: **Per-Core + CAL**؛ Standard (۲ VM) در برابر Datacenter (نامحدود).
- لینوکس: RHEL/Ubuntu Pro اشتراکی؛ Debian/Rocky/Alma رایگان.
- **MAK** برای کوچک، **KMS** برای بزرگ (۲۵+).
- انطباق = قانونی + فنی + ممیزی‌پذیر.
- **CAL** رایج‌ترین نقطهٔ نقض است.
- مستندات لایسنس، بخشی از انطباق است.
