## فصل ۹۴: شکست پشتیبان‌گیری

### مقدمه

backup، وقتی کار می‌کند، دیده نمی‌شود. وقتی کار نمی‌کند، **کسی نمی‌داند** — تا روزی که لازمش داری.

این فصل دربارهٔ آن دسته از خرابی‌هاست: backup که اجرا نمی‌شود، نیمه‌کاره می‌ماند، یا «موفق» گزارش می‌دهد اما بی‌فایده است.

### مفاهیم اساسی

**انواع شکست backup:**

| نوع | علامت |
|---|---|
| **اجرا نمی‌شود** | job در زمان مقرر شروع نشده |
| **شروع و شکست** | خطا در لاگ |
| **نیمه‌کاره** | بعضی فایل‌ها/سیستم‌ها نه |
| **کند** | از پنجرهٔ backup بیرون می‌زند |
| **موفق اما ناقص** | «success» با warning |
| **موفق اما غیرقابل بازیابی** | تست نشده |

**نکتهٔ حیاتی:** **«Success» در گزارش backup، یعنی «بدون خطا اجرا شد»، نه «قابل بازیابی است».** تفاوت را فقط تست بازیابی نشان می‌دهد.

**علل رایج — اجرا نمی‌شود:**

| علت | بررسی |
|---|---|
| **زمان‌بندی (schedule)** | cron/task فعال است؟ |
| **سرویس backup** | اجرا و enable است؟ |
| **اعتبارنامه (credential)** | رمز منقضی؟ |
| **فضای repository** | پر است؟ |
| **قفل (lock)** | job قبلی هنوز اجراست؟ |
| **license** | منقضی؟ |
| **اتصال شبکه** | به repository می‌رسد؟ |

**نکته:** **credential منقضی** یکی از رایج‌ترین علل است — و بی‌صدا شکست می‌خورد. اگر رمز حساب سرویس هر ۹۰ روز عوض می‌شود، backup هم باید آپدیت شود.

**علل رایج — نیمه‌کاره:**

| علت | بررسی |
|---|---|
| **فایل باز (locked)** | VSS/fsfreeze کار می‌کند؟ |
| **خطای خواندن** | bad sector |
| **timeout** | فایل بزرگ، شبکه کند |
| **مسیر حذف‌شده** | فایل‌های orphaned |
| **مجوز** | فایلی که backup نمی‌تواند بخواند |
| **آنتی‌ویروس** | فایل قرنطینه |

**نکتهٔ مهم:** **فایل باز** رایج‌ترین علت «نیمه‌کاره» است. VSS در ویندوز و `fsfreeze`/snapshot در لینوکس این را حل می‌کنند.

**علل رایج — کند:**

| علت | بررسی |
|---|---|
| **شبکه** | 1GbE به‌جای 10GbE |
| **دیسک** | HDD، IOPS کم |
| **dedup/compression** | CPU گلوگاه |
| **تعداد فایل زیاد** | overhead |
| **full در پنجرهٔ کوتاه** | نیاز به synthetic |
| **همزمانی** | چند job روی یک repository |

**نکته:** **تعداد فایل** مهم‌تر از حجم است. ۱ میلیون فایل کوچک، کندتر از ۱۰۰ فایل بزرگ با همان حجم.

**پایش backup — چه چیزی را:**

| متریک | آستانه |
|---|---|
| **Job success rate** | <۱۰۰٪ = هشدار |
| **Duration** | رشد >۲۰٪ = بررسی |
| **Data backed up** | افت ناگهانی = مشکوک |
| **Repository free space** | <۲۰٪ |
| **Last successful backup** | >۲۴ ساعت = هشدار |
| **Verify status** | خطا |

**نکتهٔ حیاتی:** **«Last successful backup»** مهم‌ترین متریک است. اگر ۳ روز است موفق نبوده، الان بدان — نه در حادثه.

**Backup chain — شکستن زنجیره:**

```
Full (شنبه) → Inc (یکشنبه) → Inc (دوشنبه) → Inc (سه‌شنبه)
                  ↑
              این شکست = زنجیره قطع
```

**نکته:** در incremental، شکست یک حلقه، همهٔ بعدی‌ها را بی‌فایده می‌کند. **synthetic full** دوره‌ای، این ریسک را کم می‌کند.

**Verify — سه سطح:**

| سطح | روش |
|---|---|
| **Synthetic verify** | بررسی checksum metadata |
| **Sample restore** | بازیابی نمونه |
| **Full restore** | بازیابی کامل |

**نکته:** verify در سطح نوار/فایل، **خرابی منطقی** (مثلاً backup از فایل‌سیستم خراب) را نمی‌گیرد. فقط restore واقعی.

### مثال‌های عملی

**Lab Scenario 1 — backup سه روز است اجرا نمی‌شود**

> **وظیفه:** ترتیب بررسی.
>
> **پاسخ:**
> ۱. **سرویس:** `systemctl status veeamservice` / `Get-Service`
> ۲. **زمان‌بندی:** cron/task فعال؟
> ۳. **لاگ job:** آخرین خطا؟
> ۴. **credential:** رمز حساب سرویس منقضی؟
> ۵. **فضا:** repository پر؟
> ۶. **قفل:** job قبلی hang کرده؟
>
> **درس:** از بیرون به داخل: سرویس → زمان‌بندی → اعتبارنامه → فضا.

**Lab Scenario 2 — backup موفق، بازیابی شکست**

> **وضعیت:** گزارش می‌گوید success، اما restore خطا می‌دهد.
>
> **وظیفه:** علت.
>
> **پاسخ:**
> - **backup ناقص:** بعضی فایل‌ها skip شده (locked).
> - **verify نشده:** خرابی رسانه/فایل.
> - **نسخهٔ نرم‌افزار:** backup از نسخهٔ قدیمی.
> - **کلید رمز:** در دسترس نیست.
> - **نتیجه:** «success» به معنای «قابل بازیابی» نیست.
>
> **درس:** بدون تست بازیابی، backup فقط یک امید است.

### مقایسه و الگوهای مختلف

**مقایسهٔ full و incremental از دید شکست:**

| معیار | Full | Incremental |
|---|---|---|
| اثر شکست | یک نسخه | کل زنجیره بعدی |
| بازیابی | مستقل | وابسته |
| ریسک | کم | بالا |

**مقایسهٔ agent و agentless:**

| معیار | Agent | Agentless |
|---|---|---|
| نصب | روی هر سرور | فقط سرور backup |
| دسترسی | local | شبکه/API |
| مشکل رایج | agent قدیمی | credential |
| مناسب | مقیاس | سادگی |

**مقایسهٔ VSS و fsfreeze:**

| معیار | VSS (ویندوز) | fsfreeze (لینوکس) |
|---|---|---|
| نوع | framework | دستور |
| application-aware | ✅ | با hook |
| مناسب | ویندوز | لینوکس |

### اشکال شایع

**۱. بدون پایش backup.**
سه هفته شکست، کسی نمی‌داند.

**۲. اعتماد به «success».**
بدون تست بازیابی.

**۳. credential منقضی.**
بی‌صدا شکست.

**۴. پنجرهٔ کوتاه.**
backup کامل نمی‌شود.

**۵. repository پر.**
job بعدی شکست.

**۶. بدون synthetic full.**
زنجیرهٔ شکننده.

**۷. نادیده گرفتن warning.**
«success with warnings» نادیده گرفته می‌شود.

**۸. فایل باز بدون VSS.**
backup ناقص.

### نکات مهم (Tips & Tricks)

- **«Last successful backup»** را هشدار کن.
- **credential rotation** را با backup همگام کن.
- **warning را مثل error ببین.**
- **synthetic full** دورهای.
- **verify** هفتگی، **restore** ماهانه.
- **در آزمون:** کلیدواژهٔ «backup job fails silently» → **credential/monitoring**.

### خلاصه فصل

- شکست: **اجرا نمی‌شود، نیمه‌کاره، کند، موفق اما غیرقابل بازیابی**.
- **credential منقضی** رایج‌ترین علت بی‌صدا است.
- **فایل باز** رایج‌ترین علت ناقص.
- **«success» ≠ «قابل بازیابی»**.
- **زنجیرهٔ incremental** شکننده است.
- **پایش** بخشی از backup است.

## فصل ۹۵: شکست بازیابی

### مقدمه

این فصل، بدترین سناریو است: فاجعه رخ داده، backup هست، و **بازیابی کار نمی‌کند**.

در این لحظه، هر دقیقه گران است. و آمادگی، همه چیز است.

### مفاهیم اساسی

**دسته‌بندی شکست بازیابی:**

| دسته | علامت |
|---|---|
| **backup قابل دسترس نیست** | repository/media خطا |
| **backup خراب** | checksum error |
| **نرم‌افزار** | نسخه، سازگاری |
| **کلید رمز** | در دسترس نیست |
| **فضا** | کافی نیست |
| **زمان** | از RTO بیرون |
| **داده** | بازیابی شد اما ناقص |
| **اپلیکیشن** | فایل هست، سرویس کار نمی‌کند |

**نکتهٔ حیاتی:** دسته را تعیین کن. هر دسته، مسیر متفاوتی دارد و **بعضی قابل رفع نیستند** (مثلاً backup خراب بدون نسخهٔ دوم).

**علل رایج و رفع:**

| علت | رفع |
|---|---|
| **checksum error** | نسخهٔ دیگر backup، یا RAID recovery |
| **media failure** | نسخهٔ offsite/secondary |
| **نسخهٔ نرم‌افزار** | نصب نسخهٔ سازگار |
| **کلید رمز گم** | **غیرقابل رفع** (بدون کلید) |
| **فضای ناکافی** | گسترش یا restore انتخابی |
| **timeout** | افزایش timeout، restore مرحله‌ای |
| **مجوز** | حساب با دسترسی کافی |

**نکتهٔ حیاتی:** **کلید رمز گم‌شده = داده غیرقابل بازیابی.** هیچ ابزاری این را حل نمی‌کند. تنها راه: کلید backup جدا (فصل ۵۳).

**بازیابی انتخابی (Granular Restore):**

به‌جای کل سیستم، فقط بخش لازم:

| سطح | مثال |
|---|---|
| **فایل** | یک سند |
| **پوشه** | یک share |
| **دیتابیس** | یک جدول |
| **میلباکس** | یک کاربر |
| **شیء AD** | یک کاربر/گروه |

**نکته:** بازیابی انتخابی، RTO را به‌شدت کم می‌کند. برای «فایل حذف‌شده»، بازیابی کل سرور، اتلاف است.

**Point-in-Time Recovery (PITR):**

برای دیتابیس: full + log تا لحظهٔ مشخص.

```bash
# PostgreSQL — نمونه
# ۱. restore از base backup
pg_basebackup -D /var/lib/pgsql/restore -h backup_host

# ۲. تنظیم recovery
# postgresql.conf:
# restore_command = 'cp /archive/%f %p'
# recovery_target_time = '2026-11-12 14:30:00'

# ۳. شروع
pg_ctl start -D /var/lib/pgsql/restore
```

**نکته:** PITR نیاز به **archive log** دارد. بدون آن، فقط تا آخرین full می‌توانی برگردی.

**بازیابی به سخت‌افزار متفاوت:**

| مشکل | رفع |
|---|---|
| **کنترلر RAID متفاوت** | درایور در رسانهٔ بازیابی |
| **NIC متفاوت** | درایور |
| **UEFI vs Legacy** | بوت سازگار |
| **دیسک کوچک‌تر** | بازیابی انتخابی |

**نکته:** **Bare-Metal Recovery به سخت‌افزار متفاوت**، رایج‌ترین شکست است. همیشه درایور storage را در رسانهٔ بازیابی داشته باش.

**تأیید بازیابی — چک‌لیست:**

```
□ فایلها موجودند؟
□ تعداد/حجم درست است؟
□ checksum درست است؟
□ مجوزها/مالکیت درست است؟
□ سرویس بالا میآید؟
□ کاربر میتواند کار کند؟
□ دادهٔ وابسته (DNS، AD) درست است؟
□ عملکرد قابل قبول است؟
```

**نکتهٔ حیاتی:** **بازیابی موفق = سرویس کار کند**، نه «فایل کپی شد».

**وقتی بازیابی شکست می‌خورد — رویه:**

```
۱. توقف تلاشهای تکراری (ممکن است backup را خراب کند)
۲. ثبت دقیق خطا
۳. بررسی نسخهٔ دیگر backup
۴. بررسی سختافزار/نرمافزار
۵. تماس با vendor (با لاگ)
۶. اطلاع به کسبوکار (تخمین جدید)
۷. گزینههای جایگزین (دادهٔ دستی، سیستم قدیمی)
```

**نکته:** **تلاش تکراری بدون تغییر**، معمولاً همان نتیجه را می‌دهد و وقت می‌برد. هر تلاش باید یک متغیر تغییر دهد.

**گزینه‌های جایگزین در بحران:**

| گزینه | توضیح |
|---|---|
| **نسخهٔ قدیمی‌تر** | RPO بدتر، اما بازیابی می‌شود |
| **backup offsite** | اگر local خراب است |
| **replica** | اگر سالم است |
| **بازسازی دستی** | از مستندات، بدون داده |
| **سیستم موقت** | سرویس حداقلی |

**نکته:** در بحران، **«بهترین» دشمن «کافی» است**. سرویس حداقلی در ۲ ساعت، بهتر از سرویس کامل در ۲ روز.

### مثال‌های عملی

**Lab Scenario 1 — backup خراب**

> **وضعیت:** restore با `checksum mismatch` شکست می‌خورد. تنها نسخهٔ local است.
>
> **وظیفه:** گزینه‌ها.
>
> **پاسخ:**
> ۱. **نسخهٔ offsite:** tape یا cloud (اگر داری).
> ۲. **نسخهٔ قدیمی‌تر:** RPO بدتر، اما بازیابی.
> ۳. **بازیابی از RAID:** اگر backup روی دیسک معیوب است، ابزار recovery.
> ۴. **بازسازی دستی:** بدون داده، سرویس را بالا بیاور.
>
> **درس:** یک نسخه، نسخه نیست (3-2-1).

**Lab Scenario 2 — بازیابی شد، سرویس کار نمی‌کند**

> **وضعیت:** فایل‌ها بازیابی شدند، اما اپلیکیشن خطا می‌دهد.
>
> **وظیفه:** پنج علت.
>
> **پاسخ:**
> ۱. **مجوز/مالکیت:** فایل‌ها با کاربر اشتباه.
> ۲. **پیکربندی:** config به سرور قدیمی اشاره می‌کند.
> ۳. **وابستگی:** دیتابیس/DNS/AD.
> ۴. **کلید/گواهی:** گواهی منقضی یا کلید گم.
> ۵. **cache:** cache قدیمی، سازگار نیست.
>
> **درس:** بازیابی داده، نیمی از کار است؛ بازیابی **سرویس** تمام کار.

### مقایسه و الگوهای مختلف

**مقایسهٔ full restore و granular:**

| معیار | Full | Granular |
|---|---|---|
| زمان | ساعت | دقیقه |
| ریسک | بالا | کم |
| مناسب | فاجعه | حذف فایل |

**مقایسهٔ PITR و snapshot:**

| معیار | PITR | Snapshot |
|---|---|---|
| دقت | ثانیه | لحظه |
| نیاز به | archive log | storage |
| مناسب | دیتابیس | VM |

**مقایسهٔ restore به همان سخت‌افزار و متفاوت:**

| معیار | همان | متفاوت |
|---|---|---|
| پیچیدگی | کم | بالا |
| درایور | موجود | لازم |
| ریسک | کم | بالا |

### اشکال شایع

**۱. یک نسخه backup.**
خراب شد، تمام.

**۲. کلید رمز جدا نگرفتن.**
داده غیرقابل بازیابی.

**۳. بدون درایور در رسانهٔ بازیابی.**
BMR شکست.

**۴. بازیابی بدون تأیید سرویس.**
فایل هست، سرویس نه.

**۵. تلاش تکراری بدون تغییر.**
وقت تلف.

**۶. بدون اطلاع به کسب‌وکار.**
انتظار غلط.

**۷. فراموش کردن مجوز.**
فایل‌ها با owner اشتباه.

**۸. بدون گزینهٔ جایگزین.**
همه چیز به یک backup وابسته.

### نکات مهم (Tips & Tricks)

- **حداقل دو نسخه** در دو محل.
- **کلید رمز جدا و آفلاین.**
- **درایور storage** در رسانهٔ بازیابی.
- **تأیید سرویس**، نه فقط فایل.
- **گزینهٔ جایگزین** از قبل تعریف کن.
- **در آزمون:** کلیدواژهٔ «restore fails, checksum» → **use another backup copy**.

### خلاصه فصل

- دسته‌ها: **دسترسی، خرابی، نرم‌افزار، کلید، فضا، زمان، داده، اپلیکیشن**.
- **کلید گم = داده گم.**
- **Granular restore** RTO را کم می‌کند.
- **BMR به سخت‌افزار متفاوت** نیاز به درایور دارد.
- بازیابی موفق = **سرویس کار کند**.
- در بحران، **«کافی» بهتر از «کامل»** است.

## فصل ۹۶: failover که کار نمی‌کند

### مقدمه

کلاستر ساخته‌ای، تست هم کرده‌ای — اما در فاجعهٔ واقعی، failover رخ نداد. چرا؟

این فصل دربارهٔ **شکاف بین «کلاستر ساخته شد» و «کلاستر کار می‌کند»** است.

### مفاهیم اساسی

**علل رایج شکست failover:**

| دسته | علت |
|---|---|
| **Quorum** | نودها رأی کافی ندارند |
| **Fencing** | STONITH شکست، failover متوقف |
| **Heartbeat** | شبکهٔ heartbeat قطع، تشخیص نادرست |
| **Storage** | LUN روی نود دوم mount نمی‌شود |
| **Network** | VIP منتقل نمی‌شود |
| **Service** | سرویس روی نود دوم بالا نمی‌آید |
| **Config** | تنظیمات نودها یکسان نیست |
| **Split-brain** | هر دو نود فعال |

**نکتهٔ حیاتی:** failover **زنجیره‌ای** است: quorum → fencing → storage → service → VIP → DNS. شکست در هر حلقه، کل زنجیره را می‌شکند.

**Quorum — مشکل کلاسیک:**

```
۲ نود، بدون witness:
Node1: «Node2 مرده» → من اکثریت دارم (۱ از ۲؟ نه)
Node2: «Node1 مرده» → من اکثریت دارم (۱ از ۲؟ نه)
نتیجه: هیچکدام فعال نمیشود (یا هر دو فعال = split-brain)
```

**نکته:** کلاستر ۲ نودی **بدون witness**، در قطعی ارتباط، قفل می‌کند یا split-brain می‌سازد (فصل ۳۹).

**Fencing — چرا failover را متوقف می‌کند؟**

کلاستر نمی‌تواند مطمئن شود نود قدیمی مرده است. اگر fencing (STONITH) کار نکند، کلاستر **برای ایمنی** failover نمی‌کند.

**نکتهٔ حیاتی:** اگر `pcs status` می‌گوید «STONITH failed»، failover انجام نمی‌شود — **و این درست است**. بدون fencing، failover خطرناک‌تر از عدم failover است.

**Heartbeat — تشخیص نادرست:**

| علامت | علت |
|---|---|
| **failover الکی** | heartbeat قطع، نود سالم |
| **failover نشد** | heartbeat وصل، نود مرده |
| **نوسان** | heartbeat ناپایدار |

**نکته:** heartbeat باید روی **شبکهٔ جدا** باشد. اگر روی شبکهٔ داده باشد، ازدحام باعث failover الکی می‌شود.

**Storage — مشکل رایج:**

| علامت | علت |
|---|---|
| **LUN روی نود دوم نیست** | zoning/masking |
| **LUN دو بار دیده می‌شود** | multipath غیرفعال |
| **mount شکست** | lock، fsck، مجوز |
| **دادهٔ ناسازگار** | هر دو نود نوشتند |

**نکته:** در کلاستر، **cluster filesystem** یا **LUN اختصاصی** لازم است. دو نود با یک LUN و فایل‌سیستم معمولی = خرابی داده.

**Service — چرا روی نود دوم بالا نمی‌آید؟**

| علت | بررسی |
|---|---|
| **پیکربندی نبود** | فایل config روی نود دوم نیست |
| **مسیر** | مسیر داده mount نشده |
| **مجوز** | کاربر/گروه وجود ندارد |
| **پورت** | پورت در حال استفاده |
| **وابستگی** | سرویس پایه فعال نیست |
| **نسخه** | نسخهٔ نرم‌افزار متفاوت |

**نکتهٔ حیاتی:** **نودها باید یکسان باشند.** اگر فقط روی نود اول نرم‌افزار نصب شده، failover کار نمی‌کند. ابزار: Ansible برای یکسان‌سازی.

**VIP — انتقال:**

| علامت | علت |
|---|---|
| **VIP منتقل نشد** | resource در گروه نیست |
| **VIP دو جا** | split-brain |
| **VIP هست، پاسخ نه** | ARP cache، سرویس |
| **DNS** | رکورد به IP قدیمی |

**نکته:** VIP باید در **همان resource group** با سرویس باشد، وگرنه ممکن است روی نود A باشد و سرویس روی نود B.

**DNS و ARP cache:**

- **DNS:** TTL بلند = تأخیر در failover.
- **ARP:** کلاینت‌ها MAC قدیمی را cache می‌کنند.

**نکته:** بعد از failover، `arp -d` روی کلاینت یا `gratuitous ARP` از سرور.

**تست failover — چک‌لیست:**

```
□ quorum سالم
□ fencing تست شده (و کار میکند)
□ storage روی هر دو نود قابل دسترس
□ سرویس روی هر دو نود نصب و پیکربندی
□ VIP در resource group
□ DNS به‌روز
□ health check
□ سرویس از دید کلاینت کار میکند
□ failback تست شده
```

**نکته:** اگر یکی از این‌ها تست نشده، failover **فرض** است.

### مثال‌های عملی

**Lab Scenario 1 — failover رخ نداد**

> **وظیفه:** ترتیب بررسی.
>
> **پاسخ:**
> ۱. **`pcs status` / `Get-ClusterGroup`** — وضعیت resource و quorum.
> ۲. **Quorum:** آیا کلاستر «quorate» است؟
> ۳. **Fencing:** آیا STONITH خطا دارد؟
> ۴. **Storage:** آیا LUN روی نود دوم قابل دسترس؟
> ۵. **Service:** آیا سرویس نصب است؟
> ۶. **VIP:** آیا منتقل شد؟
>
> **درس:** از quorum شروع کن — بدون آن، هیچ failover رخ نمی‌دهد.

**Lab Scenario 2 — failover شد، کلاینت‌ها وصل نمی‌شوند**

> **وظیفه:** سه علت.
>
> **پاسخ:**
> ۱. **ARP cache:** کلاینت MAC قدیمی.
> ۲. **DNS:** رکورد به IP قدیمی یا TTL بلند.
> ۳. **سرویس:** روی نود دوم پیکربندی ناقص.
>
> **درس:** failover فنی ≠ failover از دید کاربر.

### مقایسه و الگوهای مختلف

**مقایسهٔ quorum majority و disk witness:**

| معیار | Majority | Witness |
|---|---|---|
| کلاستر ۲ نودی | ❌ بن‌بست | ✅ |
| نیاز به | ۳+ نود | دیسک/share |
| مناسب | بزرگ | کوچک |

**مقایسهٔ failover خودکار و دستی:**

| معیار | خودکار | دستی |
|---|---|---|
| سرعت | ثانیه | دقیقه |
| ریسک | false positive | تصمیم انسانی |
| مناسب | Tier 0 | Tier 1 |

**مقایسهٔ STONITH و SBD:**

| معیار | STONITH (IPMI) | SBD |
|---|---|---|
| روش | برق | دیسک مشترک |
| نیاز | BMC | shared disk |
| مناسب | همه | SAN |

### اشکال شایع

**۱. کلاستر بدون witness.**
بن‌بست در ۲ نود.

**۲. fencing غیرفعال.**
failover انجام نمی‌شود (یا خطرناک).

**۳. نودها ناهمسان.**
سرویس روی نود دوم نیست.

**۴. VIP در گروه نیست.**
روی نود اشتباه.

**۵. بدون تست failback.**
بازگشت شکست می‌خورد.

**۶. heartbeat روی شبکهٔ داده.**
failover الکی.

**۷. DNS TTL بلند.**
تأخیر در failover.

**۸. بدون تست واقعی.**
کلاستر «کاغذی».

### نکات مهم (Tips & Tricks)

- **از quorum شروع کن.**
- **fencing را تست کن** — اگر کار نکند، failover امن نیست.
- **نودها را یکسان نگه دار** (Ansible).
- **VIP در resource group.**
- **failback را هم تست کن.**
- **در آزمون:** کلیدواژهٔ «cluster did not fail over» → **quorum/fencing**.

### خلاصه فصل

- failover **زنجیره‌ای** است: quorum → fencing → storage → service → VIP → DNS.
- **بدون quorum**، failover رخ نمی‌دهد.
- **بدون fencing**، failover امن نیست.
- **نودها باید یکسان باشند.**
- **VIP در گروه** و **DNS TTL کم**.
- **failback** بخشی از تست است.

## فصل ۹۷: بازیابی پس از ransomware

### مقدمه

ransomware، بدترین نوع فاجعه است: داده **خراب** نشده، بلکه **رمز** شده. و مهاجم ممکن است هنوز در شبکه باشد.

این فصل، رویهٔ بازیابی است — با تمرکز بر **عدم بازگشت آلودگی**.

> ⚠️ **مرز قانونی:** پرداخت باج، در برخی کشورها و برای برخی نهادها ممنوع یا محدود است. و پرداخت، تضمین بازیابی نیست. این کتابچه توصیهٔ پرداخت نمی‌کند.

### مفاهیم اساسی

**چرا ransomware با فاجعهٔ معمولی فرق دارد؟**

| ویژگی | فاجعهٔ معمولی | ransomware |
|---|---|---|
| داده | از بین رفته | رمز شده (قابل بازگشت با کلید) |
| مهاجم | ❌ | ✅ ممکن است هنوز حاضر باشد |
| backup | سالم | ممکن است هدف بوده باشد |
| زمان | فوری | فوری + تحقیق |
| اعتماد | بالا | **صفر** |

**نکتهٔ حیاتی:** **بازیابی قبل از پاکسازی = آلودگی مجدد.** باید مطمئن شوی مهاجم رفته، قبل از restore.

**مراحل بازیابی — ترتیب حیاتی:**

```
۱. مهار (isolate)
۲. ارزیابی دامنه (چند سرور؟)
۳. حفظ شواهد
۴. شناسایی نقطهٔ ورود
۵. پاکسازی (حساب، malware، آسیبپذیری)
۶. تأیید پاکسازی
۷. بازیابی از backup تمیز
۸. پایش تشدیدشده
۹. درسآموخته
```

**نکتهٔ حیاتی:** مرحلهٔ **۶ (تأیید پاکسازی)** اغلب رد می‌شود. اگر malware باقی باشد، restore دوباره آلوده می‌شود — و این بار backup هم در خطر است.

**کدام backup؟**

| معیار | الزام |
|---|---|
| **قبل از آلودگی** | timestamp قبل از رخداد |
| **immutable/offline** | دست‌نخورده |
| **verify شده** | سالم |
| **بدون credential آلوده** | جدا |

**نکته:** اگر مطمئن نیستی backup آلوده است یا نه، **فرض کن آلوده است**. اسکن کن، یا از نسخهٔ قدیمی‌تر استفاده کن.

**پاکسازی — چک‌لیست:**

```
□ malware حذف شده (EDR scan تمیز)
□ حسابهای ناشناس حذف
□ رمز همهٔ حسابهای ممتاز عوض
□ Krbtgt (در AD) دو بار عوض
□ persistence حذف (scheduled task، service، startup)
□ آسیبپذیری ورود patch شده
□ پیکربندی بازگردانده به baseline
□ گواهیهای مشکوک باطل
```

**نکتهٔ حیاتی در AD:** حساب **Krbtgt** باید **دو بار** عوض شود (با فاصله) — چون تاریخچهٔ رمز نگه داشته می‌شود. یک بار کافی نیست.

**بازیابی — ترتیب:**

```
۱. زیرساخت پایه (DNS، DHCP، AD)
۲. سرویسهای احراز هویت
۳. دیتابیسها
۴. اپلیکیشنها
۵. سرویسهای ثانویه
```

**نکته:** اگر AD را از backup قدیمی برگردانی، حساب‌هایی که بعداً ساخته شده‌اند از دست می‌روند. باید هماهنگ کنی.

**پایش تشدیدشده (Enhanced Monitoring):**

| مورد | مدت |
|---|---|
| **لاگ EDR** | ۳۰ روز |
| **ترافیک خروجی** | ۳۰ روز |
| **ورودها** | ۳۰ روز |
| **تغییرات فایل** | ۳۰ روز |

**نکته:** مهاجم ممکن است هفته‌ها بعد برگردد. پایش تشدیدشده، تشخیص بازگشت است.

**چرا پرداخت توصیه نمی‌شود؟**

| دلیل | توضیح |
|---|---|
| **تضمین ندارد** | بسیاری پس از پرداخت، کلید نمی‌گیرند |
| **تأمین مالی** | جریمهٔ جرایم بیشتر |
| **هدف بعدی** | سازمان پرداخت‌کننده، هدف جذاب‌تر |
| **قانونی** | در برخی حوزه‌ها ممنوع |

**نکته:** تصمیم پرداخت، **تصمیم مدیریتی و حقوقی** است، نه فنی.

**Decryption key — گزینه‌ها:**

- **No More Ransom** (پروژهٔ مشترک پلیس و صنعت) — برای برخی خانواده‌ها کلید رایگان.
- **ابزار سازندهٔ آنتی‌ویروس** — گاهی کلید.
- **تحلیل نمونه** — اگر کلید در کد باشد.

**نکته:** این‌ها **قبل از پرداخت** بررسی شوند.

### مثال‌های عملی

**Lab Scenario 1 — بازیابی پس از ransomware**

> **وظیفه:** ترتیب ۹ مرحله را روی یک سناریو (۵ سرور آلوده) اجرا کن.
>
> **پاسخ:**
> ۱. **مهار:** قطع شبکهٔ ۵ سرور (VLAN قرنطینه).
> ۲. **دامنه:** اسکن بقیهٔ شبکه با EDR.
> ۳. **شواهد:** memory dump، لاگ، نمونهٔ فایل رمزشده.
> ۴. **نقطهٔ ورود:** ایمیل phishing؟ VPN؟ حساب لو رفته؟
> ۵. **پاکسازی:** حذف حساب‌ها، patch، حذف persistence.
> ۶. **تأیید:** EDR scan تمیز روی همه.
> ۷. **بازیابی:** از immutable backup هفتهٔ قبل.
> ۸. **پایش:** ۳۰ روز.
> ۹. **درس:** phishing training، MFA، immutable backup.
>
> **درس:** ترتیب مهم است — restore قبل از پاکسازی، آلودگی مجدد.

**Lab Scenario 2 — backup هم رمز شده**

> **وضعیت:** ransomware فایل‌های backup روی share را هم رمز کرد.
>
> **وظیفه:** چه چیزی نجات می‌دهد؟
>
> **پاسخ:**
> - **immutable/offline copy** (tape، object lock).
> - **اگر نداری:** فاجعهٔ کامل — بازیابی ممکن نیست.
> - **درس:** 3-2-1-1-0 (فصل ۶۴).
>
> **درس:** backup آنلاین و قابل نوشتن، backup نیست.

### مقایسه و الگوهای مختلف

**مقایسهٔ ransomware و خرابی دیسک:**

| معیار | ransomware | خرابی دیسک |
|---|---|---|
| داده | رمز | از بین |
| بازیابی | با کلید/backup | با backup |
| مهاجم | ✅ | ❌ |
| زمان | طولانی (تحقیق) | کوتاه |

**مقایسهٔ restore و rebuild:**

| معیار | Restore | Rebuild |
|---|---|---|
| سرعت | متوسط | کند |
| اطمینان | بالا (اگر تمیز) | بالا |
| مناسب | دادهٔ زیاد | سیستم آلوده |

**نکته:** اگر سیستم به‌شدت آلوده است، **rebuild** امن‌تر از پاکسازی است.

**مقایسهٔ پایش عادی و تشدیدشده:**

| معیار | عادی | تشدیدشده |
|---|---|---|
| مدت | همیشه | ۳۰ روز |
| حساسیت | متوسط | بالا |
| هشدار | آستانه | هر رویداد مشکوک |

### اشکال شایع

**۱. restore قبل از پاکسازی.**
آلودگی مجدد.

**۲. بازیابی از backup آلوده.**
ransomware برمی‌گردد.

**۳. تغییر رمز بدون حذف persistence.**
مهاجم دوباره وارد.

**۴. Krbtgt یک بار.**
کلید طلایی هنوز کار می‌کند.

**۵. بدون پایش تشدیدشده.**
بازگشت دیده نمی‌شود.

**۶. پرداخت بدون بررسی کلید رایگان.**
هزینهٔ بی‌دلیل.

**۷. بدون گزارش قانونی.**
تخلف انطباق.

**۸. بازگشت سریع به حالت عادی.**
درس‌آموخته فراموش.

### نکات مهم (Tips & Tricks)

- **مهار، بعد تحقیق، بعد restore.**
- **backup قبل از آلودگی** را تأیید کن.
- **Krbtgt دو بار.**
- **پایش ۳۰ روز.**
- **No More Ransom** را چک کن.
- **در آزمون:** کلیدواژهٔ «restore after ransomware» → **verify clean backup before restore**.

### خلاصه فصل

- ransomware: **داده رمز + مهاجم حاضر**.
- ترتیب: **مهار → ارزیابی → شواهد → ریشه → پاکسازی → تأیید → restore → پایش**.
- **restore قبل از پاکسازی = آلودگی مجدد.**
- **immutable/offline backup** تنها نجات‌دهنده.
- **Krbtgt دو بار** عوض شود.
- پرداخت، **تصمیم حقوقی** است، نه فنی.

## فصل ۹۸: تحلیل ریشه‌ای و پس‌مرگ

### مقدمه

بعد از هر رخداد، یک سؤال باقی می‌ماند: **چرا؟** و یک سؤال مهم‌تر: **چطور تکرار نشود؟**

این فصل دربارهٔ تبدیل یک رخداد به **بهبود سازمانی** است.

### مفاهیم اساسی

**RCA در برابر Postmortem:**

| معیار | RCA | Postmortem |
|---|---|---|
| تمرکز | علت فنی | کل رخداد |
| دامنه | سیستم | فرآیند + انسان + فنی |
| خروجی | علت ریشه‌ای | اقدامات بهبود |
| مخاطب | تیم فنی | سازمان |

**نکته:** RCA بخشی از postmortem است، نه جایگزین آن.

**چهار سطح علت:**

| سطح | مثال |
|---|---|
| **علت مستقیم (Direct)** | دیسک خراب شد |
| **علت contributing** | هشدار SMART نادیده گرفته شد |
| **علت ریشه‌ای (Root)** | فرآیند پایش SMART وجود نداشت |
| **عامل سیستمی** | تیم منابع کافی نداشت |

**نکتهٔ حیاتی:** اگر فقط **علت مستقیم** را رفع کنی، رخداد **تکرار** می‌شود. رفع دیسک، مشکل پایش را حل نمی‌کند.

**تکنیک‌های RCA:**

| تکنیک | توضیح |
|---|---|
| **5 Whys** | زنجیرهٔ چرا |
| **Fishbone (Ishikawa)** | علل چندعاملی |
| **Fault Tree Analysis** | درخت خطا |
| **Timeline analysis** | ترتیب زمانی |
| **Change analysis** | تغییرات اخیر |

**5 Whys — مثال:**

```
سرور از دسترس خارج شد
چرا؟ → دیسک RAID خراب
چرا؟ → دو دیسک خراب شد
چرا؟ → rebuild اول کامل نشده بود
چرا؟ → پنجرهٔ rebuild کافی نبود (بار زیاد)
چرا؟ → ظرفیت I/O برای rebuild طراحی نشده بود
→ علت ریشه‌ای: طراحی ظرفیت، rebuild را در نظر نگرفته
```

**نکته:** ۵ چرا باید با **شواهد** همراه باشد، نه حدس زنجیره‌ای.

**Fishbone — شش شاخه (6M):**

| شاخه | مثال |
|---|---|
| **Machine** | سخت‌افزار |
| **Method** | فرآیند |
| **Material** | داده، رسانه |
| **Measurement** | پایش |
| **Man** | انسان |
| **Milieu** | محیط |

**نکته:** Fishbone برای رخدادهای چندعاملی بهتر از 5 Whys است.

```markdown

## اثر
- کاربران: ۲۰۰
- مدت: ۲۰ دقیقه
- درآمد: تخمین ...

## خط زمانی
02:15 هشدار
02:20 تأیید
...

## علت ریشهای
...

## اقدامات
| اقدام | مالک | تاریخ |
|---|---|---|
| ... | ... | ... |
```

**نکتهٔ حیاتی:** بخش **«چه چیزی خوب کار کرد»** را حذف نکن. postmortem فقط برای سرزنش نیست؛ برای تقویت نقاط قوت هم هست.

**Blameless — چرا؟**

| اگر سرزنش کنی | نتیجه |
|---|---|
| افراد پنهان می‌کنند | اطلاعات ناقص |
| ریسک‌پذیری صفر | نوآوری صفر |
| «مقصر» پیدا می‌شود | علت واقعی پنهان می‌ماند |

**نکته:** هدف، **یادگیری** است. جملهٔ درست: «فرآیند اجازه داد این اتفاق بیفتد»؛ نه «فلانی اشتباه کرد».

**اقدامات — SMART:**

| حرف | معنی |
|---|---|
| **S**pecific | مشخص |
| **M**easurable | قابل اندازه‌گیری |
| **A**chievable | قابل انجام |
| **R**elevant | مرتبط |
| **T**ime-bound | زمان‌دار |

**مثال بد:** «پایش را بهتر کنیم»
**مثال خوب:** «هشدار SMART برای همهٔ دیسک‌ها تا ۳۰ آبان، مالک: تیم زیرساخت»

**نکته:** اقدام بدون **مالک و تاریخ**، انجام نمی‌شود.

**متریک‌های بلوغ:**

| متریک | معنی |
|---|---|
| **MTTD** | زمان تشخیص |
| **MTTR** | زمان رفع |
| **Repeat rate** | درصد رخدادهای تکراری |
| **Action completion** | درصد اقدامات انجام‌شده |
| **Postmortem coverage** | درصد رخدادهای با postmortem |

**نکته:** **Repeat rate** مهم‌ترین است. اگر رخدادها تکرار می‌شوند، اقدامات سطحی بوده‌اند.

**Knowledge base — از رخداد به دانش:**

```
تیکت (رخداد خاص)
   ↓ استخراج الگو
KB article (راهحل عمومی)
   ↓ تکرار
Runbook (رویهٔ خودکار/نیمهخودکار)
```

**نکته:** بدون این زنجیره، هر رخداد از صفر شروع می‌شود.

### مثال‌های عملی

**Lab Scenario 1 — RCA یک قطعی**

> **وضعیت:** قطعی ۲ ساعته در سرویس ایمیل. علت مستقیم: دیسک پر شد.
>
> **وظیفه:** چهار سطح علت.
>
> **پاسخ:**
>
> | سطح | علت |
> |---|---|
> | **مستقیم** | دیسک `/var` پر شد |
> | **Contributing** | logrotate تنظیم نبود |
> | **ریشه‌ای** | سرور بدون baseline استاندارد نصب شده بود |
> | **سیستمی** | فرآیند استقرار، چک‌لیست اجباری نداشت |
>
> **اقدامات:**
> - logrotate در baseline (مالک: تیم سیستم، ۲ هفته)
> - چک‌لیست استقرار (مالک: مدیر IT، ۱ ماه)
> - هشدار فضای دیسک (مالک: تیم پایش، ۱ هفته)
>
> **درس:** رفع «دیسک پر» بدون baseline، تکرار را تضمین می‌کند.

**Lab Scenario 2 — postmortem سرزنش‌آمیز**

> **وضعیت:** postmortem می‌گوید «اپراتور اشتباهاً سرور اشتباه را ری‌استارت کرد».
>
> **وظیفه:** چه چیزی غایب است؟
>
> **پاسخ:**
> - **علت ریشه‌ای:** چرا سیستم اجازه داد سرور اشتباه ری‌استارت شود؟ (بدون تأیید، بدون برچسب، بدون قفل)
> - **اقدام درست:** تأیید دو مرحله‌ای، برچسب واضح، محدودیت دسترسی.
> - **نتیجه:** سرزنش، تکرار را متوقف نمی‌کند؛ طراحی، می‌کند.
>
> **درس:** «خطای انسانی» علت نیست؛ **شرایطی که خطا را ممکن کرد** علت است.

### مقایسه و الگوهای مختلف

**مقایسهٔ 5 Whys و Fishbone:**

| معیار | 5 Whys | Fishbone |
|---|---|---|
| سرعت | سریع | متوسط |
| علل چندگانه | ضعیف | ✅ |
| مناسب | علت خطی | رخداد پیچیده |

**مقایسهٔ postmortem و RCA:**

| معیار | Postmortem | RCA |
|---|---|---|
| دامنه | کل رخداد | علت |
| خروجی | اقدامات | علت ریشه‌ای |
| مخاطب | سازمان | تیم فنی |

**مقایسهٔ اقدام اصلاحی و پیشگیرانه:**

| معیار | اصلاحی | پیشگیرانه |
|---|---|---|
| هدف | رفع فعلی | جلوگیری |
| زمان | فوری | برنامه‌ریزی |
| مثال | restart | پایش |

### اشکال شایع

**۱. توقف در علت مستقیم.**
تکرار رخداد.

**۲. سرزنش افراد.**
اطلاعات پنهان.

**۳. اقدام بدون مالک.**
انجام نمی‌شود.

**۴. postmortem بدون خط زمانی.**
علت گم می‌شود.

**۵. بدون «چه خوب کار کرد».**
فقط منفی‌بینی.

**۶. بدون KB.**
هر رخداد از صفر.

**۷. postmortem فقط برای رخدادهای بزرگ.**
رخدادهای کوچک، الگو می‌سازند.

**۸. بدون اندازه‌گیری repeat rate.**
نمی‌دانی بهبود یافته یا نه.

### نکات مهم (Tips & Tricks)

- **چهار سطح علت** را جدا کن.
- **Blameless** — همیشه.
- **اقدام SMART** با مالک و تاریخ.
- **خط زمانی** دقیقه‌ای.
- **Repeat rate** را اندازه بگیر.
- **در آزمون:** کلیدواژهٔ «root cause analysis» → **why it happened, prevent recurrence**.

### خلاصه فصل

- RCA: **مستقیم، contributing، ریشه‌ای، سیستمی**.
- **5 Whys** برای خطی؛ **Fishbone** برای چندعاملی.
- **Blameless** — هدف یادگیری است.
- **اقدام SMART** با مالک و تاریخ.
- **Repeat rate** متریک بلوغ است.
- تیکت → KB → runbook.
