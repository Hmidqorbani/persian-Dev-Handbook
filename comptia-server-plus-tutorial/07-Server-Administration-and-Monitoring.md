## فصل ۳۳: مدیریت نقش‌ها و سرویس‌ها

### مقدمه

یک سرور تولیدی، مجموعه‌ای از سرویس‌های درهم‌تنیده است. اگر یکی از آن‌ها را بدون شناخت وابستگی‌ها متوقف کنی، سه سرویس دیگر می‌خوابند.

این فصل دربارهٔ **چرخهٔ عمر سرویس** است: نصب، پیکربندی، شروع، توقف، به‌روزرسانی و حذف — با در نظر گرفتن وابستگی‌ها.

### مفاهیم اساسی

**چرخهٔ عمر یک سرویس:**

```
[نصب] → [پیکربندی] → [شروع] → [فعال‌سازی در بوت] → [پایش] → [به‌روزرسانی] → [توقف] → [حذف]
```

**هر مرحله، یک ریسک دارد:**

| مرحله | ریسک رایج |
|---|---|
| نصب | وابستگی گم‌شده، پورت اشغال |
| پیکربندی | سینتکس غلط، مسیر اشتباه |
| شروع | پورت در حال استفاده، مجوز فایل |
| فعال‌سازی | سرویس وابسته فعال نیست |
| به‌روزرسانی | تغییر رفتار، از دست رفتن config |
| حذف | باقی ماندن داده و پورت باز |

**وابستگی سرویس (Dependency):** سرویس A برای کار کردن به B نیاز دارد.

```bash
# در systemd
systemctl list-dependencies nginx
```

```powershell
# در ویندوز
Get-Service -Name "W3SVC" -DependentServices
Get-Service -Name "W3SVC" -RequiredServices
```

**نکتهٔ مهم:** اگر سرویس وابسته را `disable` کنی، سرویس اصلی هم ممکن است بالا نیاید. همیشه `list-dependencies` را چک کن.

**مدیریت سرویس در systemd:**

```bash
systemctl start nginx
systemctl stop nginx
systemctl restart nginx          # stop + start (قطع سرویس)
systemctl reload nginx           # بازخوانی config بدون قطع
systemctl enable nginx           # فعال در بوت
systemctl enable --now nginx     # فعال + شروع
systemctl disable nginx
systemctl status nginx
systemctl is-active nginx
systemctl is-enabled nginx
systemctl mask nginx             # جلوگیری از شروع (حتی دستی)
systemctl unmask nginx
```

**تفاوت `restart` و `reload`:**

| دستور | اثر | قطع سرویس |
|---|---|---|
| `restart` | پروسه می‌میرد و جدید شروع | ✅ |
| `reload` | config بازخوانی، پروسه می‌ماند | ❌ (معمولاً) |

**نکته:** `reload` فقط اگر سرویس پشتیبانی کند کار می‌کند. برای nginx، apache، postgresql معمولاً بله؛ برای بعضی سرویس‌ها نه.

**مدیریت سرویس در ویندوز:**

```powershell
Get-Service
Get-Service -Name "W3SVC" | Format-List *
Start-Service -Name "W3SVC"
Stop-Service -Name "W3SVC" -Force
Restart-Service -Name "W3SVC"
Set-Service -Name "W3SVC" -StartupType Automatic
Set-Service -Name "W3SVC" -StartupType Manual
Set-Service -Name "W3SVC" -StartupType Disabled
```

**حالت‌های Startup:**

| حالت | توضیح |
|---|---|
| **Automatic** | در بوت شروع |
| **Automatic (Delayed)** | با تأخیر (کاهش رقابت در بوت) |
| **Manual** | دستی یا توسط سرویس دیگر |
| **Disabled** | هرگز |

**پورت و سرویس — ارتباط:**

```bash
ss -tulpn | grep :80        # چه چیزی روی ۸۰ گوش می‌دهد
lsof -i :80
netstat -ano | findstr :80  # ویندوز
Get-NetTCPConnection -LocalPort 80
```

**نکتهٔ رایج:** «پورت در حال استفاده» یعنی سرویس قدیمی هنوز پروسه دارد. `ss -tulpn` مقصر را نشان می‌دهد.

**پیکربندی به‌عنوان کد (Configuration as Code):** سرویس‌ها را با فایل config مدیریت کن، نه با GUI. مزیت: نسخه‌بندی، بازبینی، تکرارپذیری.

**مدیریت تغییر (Change Management):**

| نوع تغییر | مثال | تأیید |
|---|---|---|
| **Standard** | افزودن کاربر | از پیش تأییدشده |
| **Normal** | آپدیت سرویس | نیاز به CAB |
| **Emergency** | رفع خرابی | تأیید پس‌از‌واقع |

**نکتهٔ حیاتی:** هر تغییر باید **Rollback plan** داشته باشد. اگر نداری، تغییر نده.

### مثال‌های عملی

**Lab Scenario 1 — سرویس بالا نمی‌آید**

> **وضعیت:** `systemctl start myapp` خطا می‌دهد: `Job for myapp.service failed`.
>
> **وظیفه:** پنج قدم عیب‌یابی.
>
> **پاسخ:**
> ۱. **`systemctl status myapp`** — پیام خطا و exit code.
> ۲. **`journalctl -xeu myapp`** — لاگ کامل با context.
> ۳. **config:** `myapp -t` یا `nginx -t` (تست سینتکس).
> ۴. **مجوز فایل:** `ls -l` روی فایل config و دایرکتوری داده.
> ۵. **پورت:** `ss -tulpn | grep :8080` — آیا چیز دیگری گرفته؟
>
> **درس:** `journalctl -xeu` بهترین دوست مدیر لینوکس است.

**Lab Scenario 2 — به‌روزرسانی بدون قطع سرویس**

> **وضعیت:** باید nginx را آپدیت کنی، اما سرویس ۲۴×۷ است.
>
> **وظیفه:** رویکرد.
>
> **پاسخ:**
> ۱. **config را backup کن:** `cp /etc/nginx/nginx.conf{,.bak}`
> ۲. **در محیط staging تست کن.**
> ۳. **اگر دو سرور داری:** یکی‌یکی (rolling) — سرور از LB خارج، آپدیت، تست، برگشت به LB.
> ۴. **اگر یک سرور:** پنجرهٔ تغییر + `reload` به‌جای `restart` (اگر نسخه پشتیبانی کند).
> ۵. **Rollback plan:** نسخهٔ قبلی بسته در دسترس (`apt install nginx=1.24...`).
>
> **درس:** بدون rollback plan، آپدیت = ریسک.

### مقایسه و الگوهای مختلف

**systemd در برابر init.d (SysV):**

| معیار | systemd | SysV |
|---|---|---|
| وابستگی | ✅ declarative | ضعیف |
| موازی‌سازی | ✅ | ❌ |
| لاگ | journald | فایل متنی |
| وضعیت | ✅ | ❌ |
| توصیه | ✅ | میراثی |

**مقایسهٔ روش‌های استقرار سرویس:**

| روش | توضیح | مناسب |
|---|---|---|
| **بستهٔ OS** (apt/dnf) | مدیریت‌شده | عمومی |
| **Container** | ایزوله | میکروسرویس |
| **Binary دستی** | کنترل کامل | نسخهٔ خاص |
| **IaC** (Ansible) | تکرارپذیر | مقیاس |

**مقایسهٔ systemctl و service:**

| دستور | معادل |
|---|---|
| `service nginx start` | `systemctl start nginx` |
| `service nginx status` | `systemctl status nginx` |
| `chkconfig nginx on` | `systemctl enable nginx` |

**نکته:** `service` و `chkconfig` در توزیع‌های مدرن، wrapper هستند.

### اشکال شایع

**۱. `enable` بدون `start`.**
سرویس در بوت فعال است اما الان نه. `systemctl enable --now` هر دو را انجام می‌دهد.

**۲. `restart` به‌جای `reload`.**
قطع سرویس بی‌دلیل. اگر reload ممکن است، استفاده کن.

**۳. تغییر config بدون backup.**
اگر سینتکس غلط باشد و restart کنی، سرویس بالا نمی‌آید. همیشه `.bak`.

**۴. نادیده گرفتن وابستگی.**
توقف سرویس پایه، چند سرویس دیگر را می‌خواباند.

**۵. پورت باز بعد از حذف سرویس.**
سرویس حذف شده اما پروسه یا سرویس دیگری پورت را گرفته.

**۶. اجرای سرویس با root.**
هر سرویس باید با کاربر اختصاصی و کم‌دسترسی اجرا شود.

**۷. نبود مستندات config.**
شش ماه بعد، هیچ‌کس نمی‌داند چرا این تنظیم هست.

### نکات مهم (Tips & Tricks)

- **`systemctl edit`** برای override بدون دست زدن به فایل اصلی — تغییرات در `drop-in` می‌ماند و آپدیت آن را پاک نمی‌کند.
- **`journalctl -u <service> -f`** برای دنبال کردن زنده.
- **`nginx -t` / `apachectl configtest`** قبل از reload.
- **همیشه `ss -tulpn`** قبل از نصب سرویس جدید (پورت آزاد است؟).
- **سرویس‌ها را با کاربر غیر root اجرا کن** و `NoNewPrivileges=true` در unit بگذار.
- **در آزمون:** کلیدواژهٔ «service fails to start after reboot» → **not enabled**؛ «port already in use» → **conflicting service**.

### خلاصه فصل

- چرخهٔ سرویس: نصب → پیکربندی → شروع → enable → پایش → حذف.
- **`enable` ≠ `start`**؛ `enable --now` هر دو.
- **`reload`** بدون قطع، **`restart`** با قطع.
- وابستگی‌ها را با `list-dependencies` چک کن.
- هر تغییر، **Rollback plan** لازم دارد.
- `journalctl -xeu` بهترین ابزار عیب‌یابی سرویس است.

## فصل ۳۴: متریک‌های عملکرد سرور

### مقدمه

«سرور کند است» یک شکایت است، نه یک تشخیص. برای تبدیل آن به تشخیص، باید بدانی **چه چیزی را اندازه بگیری** و **عدد سالم چیست**.

این فصل، چهار منبع اصلی (CPU، RAM، دیسک، شبکه) و متریک‌های کلیدی هر کدام را معرفی می‌کند.

### مفاهیم اساسی

**چهار منبع و گلوگاه‌هایشان:**

```
[CPU] ── [RAM] ── [Disk I/O] ── [Network]
   ↑        ↑          ↑             ↑
  صف اجرا  swap      صف I/O      صف ارسال
```

**۱. CPU — متریک‌ها:**

| متریک | معنی | آستانهٔ هشدار |
|---|---|---|
| **% Processor Time** | درصد استفاده | >۸۰٪ پایدار |
| **Run queue / Load average** | تعداد پروسهٔ منتظر CPU | > تعداد هسته |
| **Context switches/sec** | تعداد سوئیچ | بسیار بالا = overhead |
| **% Privileged Time** | زمان در kernel | بالا = درایور/سیستم |
| **Steal time** (VM) | زمانی که hypervisor CPU نداد | >۵٪ |

**نکتهٔ مهم:** ۱۰۰٪ CPU همیشه بد نیست. اگر workload batch است و شبانه ۱۰۰٪ می‌رود، طبیعی است. **صف انتظار** مهم‌تر از درصد است.

**Load average (لینوکس):**

```bash
uptime
# load average: 2.15, 1.80, 1.20
```

سه عدد: ۱، ۵ و ۱۵ دقیقه. اگر سیستم ۴ هسته دارد و load = ۲، یعنی نصف ظرفیت. اگر load = ۸، یعنی صف انتظار.

**نکته:** load در لینوکس شامل I/O wait هم می‌شود. load بالا با CPU پایین = احتمالاً I/O.

**۲. حافظه — متریک‌ها:**

| متریک | معنی | آستانه |
|---|---|---|
| **Available MBytes** | حافظهٔ قابل استفاده | <۱۰٪ |
| **Pages/sec** | نرخ page fault | بالا = فشار حافظه |
| **Swap in/out** | تبادل با دیسک | هر مقدار پایدار = بد |
| **Cache/Buffers** | حافظهٔ cache | کم بودن = مشکل |

**تلهٔ بزرگ:** در لینوکس، `free -h` نشان می‌دهد «free» کم است — اما این **طبیعی** است، چون لینوکس RAM آزاد را cache می‌کند. باید **`available`** را نگاه کنی، نه `free`.

```bash
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           62Gi        18Gi       1.2Gi       0.3Gi        43Gi        43Gi
```

اینجا `free` = ۱.۲GB اما `available` = ۴۳GB. سیستم سالم است.

**۳. دیسک — متریک‌ها:**

| متریک | معنی | آستانه |
|---|---|---|
| **% Disk Time** | درصد زمان مشغول | >۸۰٪ |
| **Avg. Disk Queue Length** | صف I/O | >۲ به ازای هر دیسک |
| **IOPS** | عملیات در ثانیه | بستگی به دیسک |
| **Latency (ms)** | تأخیر | >۲۰ms نگران‌کننده (HDD)، >۵ms (SSD) |
| **Free space** | فضای آزاد | <۲۰٪ |

**نکتهٔ حیاتی:** `% Disk Time` در ویندوز می‌تواند بالای ۱۰۰٪ باشد (چون چند I/O هم‌زمان). **Disk Queue Length** معیار بهتر است.

**لینوکس:**

```bash
iostat -xz 1
# r/s, w/s, rkB/s, wkB/s, await, %util
```

- `await` = latency متوسط (ms)
- `%util` = درصد زمان مشغول

**تله:** `%util` در SSD/NVMe می‌تواند ۱۰۰٪ باشد بدون گلوگاه واقعی (چون دیسک می‌تواند چند I/O موازی داشته باشد). `await` و `aqu-sz` معیار بهترند.

**۴. شبکه — متریک‌ها:**

| متریک | معنی | آستانه |
|---|---|---|
| **Throughput** | Mbps | نزدیک ظرفیت لینک |
| **Packet loss** | درصد بستهٔ گم‌شده | >۰.۱٪ |
| **Latency (RTT)** | تأخیر رفت‌وبرگشت | >۱۰۰ms (داخلی) |
| **Retransmits** | ارسال مجدد TCP | >۱٪ |
| **Errors/discards** | خطای رابط | >۰ |

```bash
ip -s link
sar -n DEV 1
ss -s
```

**متریک‌های ترکیبی:**

| متریک | معنی |
|---|---|
| **Response time** | زمان پاسخ سرویس (از دید کاربر) |
| **Requests/sec** | نرخ درخواست |
| **Error rate** | درصد خطا |
| **Apdex** | امتیاز رضایت (۰–۱) |

**نکتهٔ طلایی:** متریک‌های سیستم (CPU، RAM) با تجربهٔ کاربر فرق دارند. سرور می‌تواند CPU ۳۰٪ داشته باشد اما کاربران کندی حس کنند (چون دیسک یا دیتابیس گلوگاه است). **همیشه از دید کاربر شروع کن.**

### مثال‌های عملی

**Lab Scenario 1 — تحلیل یک سرور کند**

> **وضعیت:** سرور وب کند است. CPU ۳۵٪، RAM ۶۰٪، دیسک `%util` ۹۸٪، `await` ۴۵ms.
>
> **وظیفه:** گلوگاه کجاست؟
>
> **پاسخ:**
> - **گلوگاه: دیسک.** `%util` ۹۸٪ و `await` ۴۵ms (برای HDD هم بالا).
> - CPU و RAM آزادند، پس مسئله پردازش نیست.
> - **علت‌های احتمالی:** لاگ‌نویسی زیاد، کوئری بدون ایندکس، swap، backup در حال اجرا.
> - **اقدام:** `iotop -o` برای پیدا کردن پروسهٔ پرترافیک.
>
> **درس:** کم‌بودن CPU به معنای سالم بودن نیست.

**Lab Scenario 2 — load average بالا با CPU پایین**

> **وضعیت:** `uptime` می‌گوید load = ۱۲ روی سرور ۸ هسته‌ای، اما `top` می‌گوید CPU ۲۵٪.
>
> **وظیفه:** تفسیر.
>
> **پاسخ:**
> - load ۱۲ روی ۸ هسته = صف انتظار ۱.۵ برابر.
> - CPU ۲۵٪ = پردازنده بیکار است.
> - **نتیجه: پروسه‌ها منتظر I/O هستند، نه CPU.**
> - بررسی: `iostat -x 1` (await بالا؟)، `ps aux | grep " D "` (پروسهٔ در حالت uninterruptible sleep).
>
> **درس:** load در لینوکس، I/O را هم می‌شمارد.

### مقایسه و الگوهای مختلف

**ابزارهای پایش در لینوکس:**

| ابزار | کاربرد |
|---|---|
| `top` / `htop` | نمای کلی زنده |
| `vmstat` | CPU، RAM، I/O، swap |
| `iostat` | دیسک |
| `sar` | تاریخی (sysstat) |
| `iotop` | I/O به تفکیک پروسه |
| `ss` / `netstat` | شبکه |
| `pidstat` | به تفکیک پروسه |

**ابزارهای ویندوز:**

| ابزار | کاربرد |
|---|---|
| **Task Manager** | نمای سریع |
| **Performance Monitor (perfmon)** | متریک دقیق و تاریخی |
| **Resource Monitor** | تفکیک پروسه |
| **Get-Counter** (PowerShell) | اسکریپت‌پذیر |

**مقایسهٔ `% Disk Time` و `Queue Length`:**

| متریک | مزیت | عیب |
|---|---|---|
| `% Disk Time` | ساده | می‌تواند >۱۰۰٪، گمراه‌کننده |
| `Queue Length` | دقیق‌تر | نیاز به تفسیر (به ازای هر دیسک) |

**مقایسهٔ monitoring و observability:**

| رویکرد | توضیح |
|---|---|
| **Monitoring** | «آیا چیزی خراب است؟» (متریک، هشدار) |
| **Observability** | «چرا خراب است؟» (لاگ، trace، متریک) |

**نکته:** Server+ در سطح monitoring است، اما درک تفاوت کمک می‌کند.

### اشکال شایع

**۱. نگاه کردن فقط به CPU.**
بیشتر گلوگاه‌ها دیسک یا حافظه‌اند.

**۲. تفسیر `free` به‌جای `available` در لینوکس.**
«RAM تمام شده» اشتباه است؛ cache قابل آزادسازی است.

**۳. میانگین‌گیری به‌جای نگاه به اوج.**
میانگین ۴۰٪ می‌تواند پشتش اوج ۱۰۰٪ در ساعت ۹ باشد.

**۴. بی‌توجهی به baseline.**
بدون «حالت عادی»، نمی‌توانی «غیرعادی» را تشخیص بدهی.

**۵. اندازه‌گیری در بازهٔ کوتاه.**
۳۰ ثانیه نمونه، الگوی روزانه را نشان نمی‌دهد.

**۶. نادیده گرفتن steal time در VM.**
VM کند است اما داخل VM همه چیز نرمال — مشکل در hypervisor است.

**۷. متریک بدون زمینه.**
`await = 20ms` برای HDD خوب، برای NVMe فاجعه. آستانه باید نسبت به نوع رسانه باشد.

### نکات مهم (Tips & Tricks)

- **Baseline بساز:** یک هفته متریک در حالت عادی، بعد آستانه تعیین کن.
- **از دید کاربر شروع کن:** response time، بعد به داخل برو.
- **`vmstat 1 5`** سریع‌ترین نمای کلی در لینوکس است.
- **در ویندوز، `perfmon` با Data Collector Set** برای تاریخی.
- **`iotop -o`** فقط پروسه‌های فعال I/O را نشان می‌دهد — عالی برای پیدا کردن مقصر.
- **در آزمون:** اگر سؤال «high disk queue, low CPU» داد → **I/O bottleneck**.

### خلاصه فصل

- چهار منبع: **CPU، RAM، Disk، Network**.
- **Load average** در لینوکس شامل I/O است.
- در لینوکس، **`available`** مهم است نه `free`.
- **Disk Queue Length** بهتر از `% Disk Time`.
- **Baseline** بدون آن، هشدار بی‌معناست.
- از **response time** شروع کن، بعد به منابع برو.

## فصل ۳۵: پایش، هشدار و آستانه

### مقدمه

پایش بدون هشدار، فقط یک داشبورد زیباست که کسی نگاهش نمی‌کند. و هشدار بدون آستانهٔ درست، «خستگی هشدار» می‌سازد: کسی دیگر به آن‌ها نگاه نمی‌کند.

این فصل دربارهٔ طراحی پایش **مؤثر** است: چه چیزی را، با چه آستانه‌ای، به چه کسی.

### مفاهیم اساسی

**سه نوع پایش:**

| نوع | سؤال | مثال |
|---|---|---|
| **Availability** | آیا سرویس بالاست؟ | ping، HTTP 200، port check |
| **Performance** | آیا سریع است؟ | response time، IOPS |
| **Capacity** | آیا فضا کافی است؟ | disk free، RAM، growth rate |

**چهار سطح پایش:**

```
۱. سخت‌افزار (BMC): دما، فن، PSU، دیسک
۲. سیستم‌عامل: CPU، RAM، دیسک، شبکه
۳. سرویس: port، response، error rate
۴. کسب‌وکار: تراکنش، کاربر فعال، درآمد
```

**نکته:** هر سطح، ابزار خودش را دارد. BMC برای سطح ۱، agent برای ۲ و ۳، APM برای ۴.

**آستانه — سه نوع:**

| نوع | توضیح | مثال |
|---|---|---|
| **Static** | عدد ثابت | disk > ۸۵٪ |
| **Dynamic / Baseline** | نسبت به رفتار عادی | CPU > ۲ برابر میانگین ۷ روز |
| **Rate of change** | سرعت تغییر | دیسک ۵٪ در ساعت |

**نکتهٔ مهم:** آستانهٔ ثابت برای همهٔ سرورها غلط است. سرور دیتابیس با ۷۰٪ CPU نرمال است؛ سرور فایل با ۷۰٪ غیرعادی.

**هشدار — سه سطح:**

| سطح | معنی | اقدام |
|---|---|---|
| **Info** | اطلاع | لاگ، بدون اطلاع |
| **Warning** | نزدیک به مشکل | تیکت، بررسی در ساعات کاری |
| **Critical** | مشکل فعال | تماس، اقدام فوری |

**قاعده:** هر هشدار باید **Actionable** باشد. اگر هیچ کاری نمی‌شود کرد، هشدار نیست؛ نویز است.

**خستگی هشدار (Alert Fatigue):** وقتی هشدارها زیاد و بی‌فایده باشند، افراد آن‌ها را نادیده می‌گیرند — و هشدار واقعی هم گم می‌شود.

**راه‌های کاهش:**

- حذف هشدارهای تکراری (deduplication).
- گروه‌بندی (grouping) — یک هشدار برای ۱۰ سرور، نه ۱۰ هشدار.
- **Maintenance window** — در زمان تغییر، هشدارها خاموش.
- آستانه‌های واقع‌بینانه.
- **Runbook** برای هر هشدار.

**ابزارهای پایش:**

| ابزار | نوع | مناسب |
|---|---|---|
| **Zabbix** | agent-based + SNMP | سازمانی، جامع |
| **Prometheus + Grafana** | pull-based، متریک | ابری، container |
| **Nagios / Icinga** | check-based | سنتی، ساده |
| **PRTG** | agent + sensor | ویندوز-محور |
| **Datadog / New Relic** | SaaS | ابری |
| **Checkmk** | ترکیبی | سازمانی |

**پروتکل‌های جمع‌آوری:**

- **SNMP** — تجهیزات شبکه، سرور.
- **Agent** — نصب روی OS.
- **WMI** — ویندوز.
- **IPMI** — سخت‌افزار.
- **Prometheus exporter** — HTTP endpoint.
- **Synthetic check** — از بیرون تست می‌کند.

**Synthetic monitoring:** یک ربات که هر دقیقه یک URL را چک می‌کند. مزیت: تجربهٔ کاربر واقعی را می‌سنجد. عیب: هزینه و پیچیدگی.

**نکتهٔ حیاتی:** پایش باید **از بیرون** هم باشد. اگر فقط از داخل شبکه چک کنی، قطعی مسیر کاربر را نمی‌بینی.

### مثال‌های عملی

**Lab Scenario 1 — طراحی پایش برای یک سرور وب**

> **وظیفه:** چه چیزهایی را با چه آستانه‌ای پایش کنی؟
>
> **پاسخ:**
>
> | سطح | متریک | آستانه | سطح هشدار |
> |---|---|---|---|
> | سخت‌افزار | دما | >۳۵°C ورودی | Warning |
> | سخت‌افزار | PSU/فن | هر خطا | Critical |
> | سخت‌افزار | RAID | degraded | Critical |
> | OS | CPU | >۸۵٪ برای ۱۰ دقیقه | Warning |
> | OS | RAM available | <۱۰٪ | Warning |
> | OS | Disk free | <۲۰٪ / <۱۰٪ | Warning/Critical |
> | OS | Load | >۲× هسته برای ۵ دقیقه | Warning |
> | سرویس | HTTP 200 | هر خطا ۲ بار متوالی | Critical |
> | سرویس | Response time | >۲s برای ۵ دقیقه | Warning |
> | سرویس | Error rate | >۵٪ | Critical |
> | کسب‌وکار | تراکنش/دقیقه | افت >۵۰٪ نسبت به baseline | Critical |
>
> **درس:** پایش سرویس مهم‌تر از پایش CPU است.

**Lab Scenario 2 — هشدارهای زیاد**

> **وضعیت:** تیم روزی ۲۰۰ هشدار می‌گیرد و ۱۹۵ تای آن‌ها «خودبه‌خود حل می‌شوند».
>
> **وظیفه:** چطور اصلاح کنی؟
>
> **پاسخ:**
> ۱. **دسته‌بندی ۳۰ روز اخیر:** کدام متریک‌ها بیشترین هشدار را می‌دهند؟
> ۲. **حذف هشدارهای غیرقابل‌اقدام:** اگر runbook ندارد، حذف یا تبدیل به info.
> ۳. **افزایش duration:** «CPU > ۹۰٪ برای ۳۰ ثانیه» → «برای ۱۰ دقیقه».
> ۴. **گروه‌بندی:** یک هشدار برای «۵ سرور در VLAN 20»، نه ۵ هشدار.
> ۵. **Maintenance window** برای backup و patch.
> ۶. **اندازه‌گیری نتیجه:** هدف، <۲۰ هشدار در روز با >۸۰٪ اقدام واقعی.
>
> **درس:** کیفیت هشدار مهم‌تر از تعداد آن است.

### مقایسه و الگوهای مختلف

**Pull در برابر Push:**

| معیار | Pull (Prometheus) | Push (Zabbix agent) |
|---|---|---|
| کشف سرویس | ✅ (service discovery) | ❌ |
| شبکهٔ بسته | ❌ (سرور باید scrape کند) | ✅ |
| مقیاس | بالا | متوسط |
| مناسب | container، ابری | سنتی، DMZ |

**مقایسهٔ Zabbix و Prometheus:**

| معیار | Zabbix | Prometheus |
|---|---|---|
| مدل | push/pull | pull |
| ذخیره‌سازی | SQL | TSDB |
| هشدار | built-in قوی | Alertmanager |
| یادگیری | متوسط | متوسط |
| مناسب | سازمانی سنتی | cloud-native |

**مقایسهٔ آستانهٔ ثابت و پویا:**

| معیار | ثابت | پویا |
|---|---|---|
| سادگی | بالا | کم |
| دقت | کم | بالا |
| نیاز به baseline | نه | بله |
| مناسب | شروع | بلوغ |

### اشکال شایع

**۱. پایش فقط CPU و RAM.**
گلوگاه‌های واقعی (دیسک، دیتابیس، شبکه) دیده نمی‌شوند.

**۲. هشدار بدون runbook.**
کسی نمی‌داند چه کند. هشدار بی‌فایده است.

**۳. آستانهٔ یکسان برای همه.**
سرور دیتابیس و فایل سرور، رفتار متفاوت دارند.

**۴. پایش فقط از داخل.**
قطعی مسیر کاربر دیده نمی‌شود.

**۵. نداشتن maintenance window.**
هر backup، ۲۰ هشدار می‌سازد.

**۶. هشدار روی میانگین.**
میانگین، اوج را پنهان می‌کند. از percentile (p95، p99) استفاده کن.

**۷. بی‌توجهی به روند (trend).**
دیسک ۷۰٪ امروز، ۹۵٪ ماه بعد. روند مهم‌تر از عدد است.

### نکات مهم (Tips & Tricks)

- **هر هشدار = یک runbook.** حتی یک پاراگراف.
- **از p95 استفاده کن، نه میانگین** برای latency.
- **Synthetic check از بیرون** برای تجربهٔ کاربر.
- **روند (trend) را پایش کن** — «چند روز تا پر شدن؟»
- **هشدار را به تیکت وصل کن**، نه ایمیل شخصی.
- **در آزمون:** کلیدواژهٔ «alert fatigue» → **too many non-actionable alerts / thresholds too low**.

### خلاصه فصل

- سه نوع پایش: **availability، performance، capacity**.
- چهار سطح: **سخت‌افزار، OS، سرویس، کسب‌وکار**.
- آستانه: **ثابت، پویا، نرخ تغییر**.
- هر هشدار باید **actionable** و دارای **runbook** باشد.
- **خستگی هشدار** با dedup، grouping و maintenance window کاهش می‌یابد.
- پایش **از بیرون** هم لازم است.

## فصل ۳۶: مدیریت لاگ

### مقدمه

لاگ، حافظهٔ سیستم است. بدون آن، هر رخداد یک «داستان شنیده‌شده» است؛ با آن، یک «پرونده».

اما لاگ بدون مدیریت، خودش مشکل می‌سازد: دیسک را پر می‌کند، حاوی دادهٔ حساس است، و در حجم زیاد غیرقابل جست‌وجو می‌شود.

### مفاهیم اساسی

**منابع لاگ:**

| منبع | مسیر (لینوکس) | محتوا |
|---|---|---|
| **System** | `/var/log/syslog`، `/var/log/messages` | رخدادهای سیستم |
| **Auth** | `/var/log/auth.log`، `/var/log/secure` | ورود، sudo |
| **Kernel** | `dmesg`، `/var/log/kern.log` | سخت‌افزار، درایور |
| **Web** | `/var/log/nginx/` | access، error |
| **Database** | `/var/log/postgresql/` | کوئری، خطا |
| **Application** | متغیر | منطق برنامه |
| **Audit** | `/var/log/audit/audit.log` | فراخوانی سیستم |
| **journald** | `journalctl` | لاگ ساخت‌یافته systemd |

**در ویندوز:**

| لاگ | محتوا |
|---|---|
| **Application** | برنامه‌ها |
| **System** | درایور، سرویس |
| **Security** | ورود، دسترسی (نیاز به audit policy) |
| **Setup** | نصب و آپدیت |
| **ForwardedEvents** | از سرورهای دیگر |

**سطوح لاگ (syslog):**

```
emerg(0) > alert(1) > crit(2) > err(3) > warning(4) > notice(5) > info(6) > debug(7)
```

**قاعده:** در تولید، `info` یا `warning`؛ `debug` فقط برای عیب‌یابی موقت.

**ساختار یک خط لاگ خوب:**

```
2026-11-12T22:15:03.421Z host01 sshd[1234]: Failed password for invalid user admin from 203.0.113.45 port 51234 ssh2
│                        │      │     │          │                                                      │
└─ timestamp (ISO 8601)   └─ host └─ proc    └─ message                                            └─ source IP
```

**اجزای ضروری:** timestamp با timezone، hostname، process، severity، message، و در صورت امکان correlation ID.

**چرخش لاگ (Log rotation):**

```bash
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 www-data adm
    postrotate
        systemctl reload myapp > /dev/null 2>&1 || true
    endscript
}
```

**معنی:**

- `daily` — چرخش روزانه.
- `rotate 14` — ۱۴ نسخه نگه دار.
- `compress` — فشرده‌سازی.
- `create` — فایل جدید با مجوز.
- `postrotate` — دستور بعد از چرخش (سرویس باید فایل جدید را باز کند).

**نکتهٔ حیاتی:** بدون `postrotate`، سرویس همچنان به فایل قدیمی (حذف‌شده) می‌نویسد و فضای دیسک آزاد نمی‌شود. علامت: `lsof +L1` فایل حذف‌شدهٔ باز را نشان می‌دهد.

**journald — مدیریت حجم:**

```bash
journalctl --disk-usage
journalctl --vacuum-size=1G
journalctl --vacuum-time=30d
# /etc/systemd/journald.conf
# SystemMaxUse=2G
```

**لاگ متمرکز — معماری:**

```
[سرورها] --syslog/agent--> [Log collector] --> [Indexer] --> [Search UI]
                                                  │
                                            [Retention/Archive]
```

**ابزارها:** rsyslog، Fluentd/Fluent Bit، Filebeat، Logstash، Graylog، Loki، Elasticsearch/OpenSearch، Splunk.

**نکتهٔ مهم:** لاگ متمرکز باید **TLS** داشته باشد. لاگ می‌تواند حاوی رمز، توکن و دادهٔ شخصی باشد.

**لاگ و امنیت:**

- **Audit policy** — ثبت ورود موفق/ناموفق، تغییر حساب، دسترسی به فایل حساس.
- **Windows Event IDهای مهم:** 4624 (ورود موفق)، 4625 (ورود ناموفق)، 4720 (ایجاد کاربر)، 4672 (دسترسی ویژه).
- **Linux:** `/var/log/auth.log`، `auditd`.
- **NTP** — بدون زمان درست، لاگ بی‌فایده است (فصل ۳۲).

**نگهداشت (Retention):**

| نوع داده | نگهداشت معمول | دلیل |
|---|---|---|
| لاگ سیستم | ۳۰–۹۰ روز | عیب‌یابی |
| لاگ امنیتی | ۱ سال+ | انطباق، تحقیق |
| لاگ مالی | ۵–۷ سال | مقررات |
| لاگ دیباگ | روزها | حجم |

> ⚠️ **مرز قانونی:** مدت نگهداشت لاگ، تابع مقررات صنعت و کشور است (مثلاً PCI DSS حداقل ۱ سال با ۳ ماه آنلاین). این کتابچه مشاورهٔ حقوقی نیست.

### مثال‌های عملی

**Lab Scenario 1 — دیسک با لاگ پر شده**

> **وضعیت:** `/var` ۱۰۰٪ پر است. `du` نشان می‌دهد `/var/log` بزرگ است، اما `ls` فایل‌های بزرگ نشان نمی‌دهد.
>
> **وظیفه:** علت؟
>
> **پاسخ:**
> - **فایل حذف‌شده اما باز:** `lsof +L1 | grep deleted`
> - سرویس (مثلاً nginx) فایل لاگ را باز نگه داشته، logrotate آن را حذف کرده، اما فضای دیسک آزاد نشده.
> - **راه‌حل فوری:** `systemctl reload nginx` یا `kill -HUP <pid>` — فایل جدید باز می‌شود.
> - **راه‌حل دائمی:** `postrotate` در logrotate.
>
> **درس:** حذف فایل، فضای فایل باز را آزاد نمی‌کند.

**Lab Scenario 2 — پیدا کردن علت یک رخداد**

> **وضعیت:** سرور ساعت ۳:۱۲ بامداد ری‌استارت شده. کسی کاری نکرده.
>
> **وظیفه:** از کجا شروع می‌کنی؟
>
> **پاسخ:**
> ۱. **`last -x | head`** — آیا reboot ثبت شده؟
> ۲. **`journalctl --since "03:00" --until "03:20"`** — رخدادهای اطراف.
> ۳. **`dmesg -T | tail -50`** — خطای سخت‌افزاری؟
> ۴. **BMC log** (iDRAC/iLO) — power event، thermal event.
> ۵. **`/var/log/kern.log`** — OOM killer؟ panic؟
> ۶. **UPS/PDU log** — قطعی برق؟
>
> **درس:** لاگ OS + لاگ BMC + لاگ برق = تصویر کامل.

### مقایسه و الگوهای مختلف

**syslog در برابر journald:**

| معیار | syslog (rsyslog) | journald |
|---|---|---|
| ساختار | متن | ساخت‌یافته (binary) |
| فیلتر | grep | `journalctl -u`، `-p`، `--since` |
| ارسال به remote | ✅ بومی | نیاز به rsyslog |
| حجم | بیشتر | فشرده |
| توصیه | ارسال متمرکز | جست‌وجوی محلی |

**نکته:** بهترین ترکیب: journald برای محلی + rsyslog برای ارسال به SIEM.

**مقایسهٔ ابزارهای متمرکز:**

| ابزار | وزن | مناسب |
|---|---|---|
| **rsyslog** | سبک | syslog خالص |
| **Fluent Bit** | بسیار سبک | container، edge |
| **Filebeat** | سبک | Elastic stack |
| **Logstash** | سنگین | پردازش پیچیده |
| **Graylog** | متوسط | جایگزین Splunk |
| **Loki** | سبک | با Grafana |

**مقایسهٔ سطح لاگ:**

| سطح | حجم | مناسب |
|---|---|---|
| debug | بسیار زیاد | عیب‌یابی موقت |
| info | زیاد | تولید معمولی |
| warning | متوسط | تولید با تمرکز خطا |
| error | کم | فقط خطا |

### اشکال شایع

**۱. logrotate بدون postrotate.**
فضای دیسک آزاد نمی‌شود.

**۲. debug روشن در تولید.**
دیسک در چند ساعت پر می‌شود و عملکرد افت می‌کند.

**۳. لاگ بدون timestamp استاندارد.**
جست‌وجو و correlation غیرممکن.

**۴. timezone مختلف بین سرورها.**
ترتیب رخدادها گم می‌شود. راه‌حل: UTC.

**۵. لاگ متمرکز بدون TLS.**
لاگ حاوی دادهٔ حساس روی شبکهٔ عمومی.

**۶. نگهداشت بی‌پایان.**
هزینهٔ ذخیره‌سازی و ریسک انطباق (نگه داشتن دادهٔ شخصی بیش از حد).

**۷. لاگ نکردن رخدادهای امنیتی.**
بدون audit policy، تحقیق پس از رخداد غیرممکن است.

**۸. حذف لاگ برای «آزاد کردن فضا» بدون بررسی.**
شواهد رخداد از دست می‌رود.

### نکات مهم (Tips & Tricks)

- **`journalctl -xeu <unit>`** — بهترین دستور عیب‌یابی سرویس.
- **`journalctl --since "1 hour ago" -p err`** — فقط خطاهای یک ساعت اخیر.
- **logrotate را از روز اول تنظیم کن**، نه بعد از پر شدن دیسک.
- **همه لاگ‌ها UTC** — تبدیل فقط در نمایش.
- **Correlation ID** در اپلیکیشن — ردیابی یک درخواست در چند سرویس.
- **در آزمون:** کلیدواژهٔ «log file grows too large» → **logrotate/retention**؛ «disk full but no large files» → **deleted open file**.

### خلاصه فصل

- منابع لاگ: system، auth، kernel، web، app، audit.
- سطح‌ها: **emerg → debug**؛ در تولید info/warning.
- **logrotate** با `postrotate` ضروری است.
- **journald** برای محلی، **rsyslog/SIEM** برای متمرکز.
- لاگ متمرکز باید **TLS** داشته باشد.
- زمان استاندارد = **UTC**.

## فصل ۳۷: مهاجرت داده، مستندسازی و مدیریت دارایی

### مقدمه

سه موضوع این فصل، «کارهای دفتری» به نظر می‌رسند — و دقیقاً به همین دلیل نادیده گرفته می‌شوند. اما در آزمون، بخش **Asset management** صریحاً در اهداف است، و در کار واقعی، تفاوت بین تیم حرفه‌ای و آماتور همین‌جاست.

مهاجرت داده، مستندسازی و مدیریت دارایی، سه ستون **قابلیت نگهداری** هستند.

### مفاهیم اساسی

**۱. مهاجرت داده (Data Migration)**

انواع:

| نوع | توضیح | مثال |
|---|---|---|
| **P2V** | فیزیکی به مجازی | سرور قدیمی → VM |
| **V2V** | مجازی به مجازی | VMware → Hyper-V |
| **V2P** | مجازی به فیزیکی | نادر |
| **P2P** | فیزیکی به فیزیکی | سخت‌افزار جدید |
| **Cloud migration** | on-prem → ابر | lift-and-shift |

**روش‌ها:**

| روش | توضیح | downtime |
|---|---|---|
| **Cold** | خاموش، کپی، روشن | بالا |
| **Warm** | کپی اولیه، sync، cutover کوتاه | کم |
| **Live / Hot** | replication مداوم، cutover لحظه‌ای | نزدیک صفر |

**مراحل مهاجرت:**

```
۱. ارزیابی (assessment) — چه چیزی، چقدر، چه وابستگی
۲. برنامه‌ریزی — زمان، منابع، rollback
۳. تست در محیط آزمایشی
۴. کپی اولیه (seed)
۵. sync (delta)
۶. cutover
۷. تست پس از مهاجرت
۸. پاک‌سازی منبع (بعد از تأیید)
```

**نکتهٔ حیاتی:** **rollback plan** بدون آن، مهاجرت یک قمار است. اگر cutover شکست خورد، چطور برمی‌گردی؟

**۲. مستندسازی (Documentation)**

**چه چیزی مستند شود:**

| نوع سند | محتوا |
|---|---|
| **Network diagram** | توپولوژی، VLAN، IP |
| **Server inventory** | نام، IP، نقش، OS، لایسنس |
| **Rack elevation** | چه چیزی در کدام U |
| **Runbook** | مراحل عملیات روزمره |
| **DR plan** | مراحل بازیابی |
| **Change log** | چه تغییر، کِی، توسط کِی |
| **Credentials vault** | رمزها (در ابزار امن، نه فایل) |

**قاعدهٔ طلایی:** مستندات باید به‌روز باشند، وگرنه **بدتر از نبودشان** هستند (اطلاعات غلط، تصمیم غلط).

**مستندات به‌عنوان کد (Docs as Code):** مستندات در Git، با نسخه‌بندی و بازبینی. مزیت: تاریخ تغییر، همکاری، جست‌وجو.

**۳. مدیریت دارایی (Asset Management)**

**چرخهٔ عمر دارایی:**

```
[برنامه‌ریزی] → [خرید] → [استقرار] → [نگهداشت] → [ارتقا] → [بازنشستگی] → [امحا]
```

**اطلاعات هر دارایی:**

- **شناسه** — asset tag
- **سریال و مدل**
- **محل** — دیتاسنتر، رک، U
- **مالک** — تیم/فرد
- **لایسنس و گارانتی** — تاریخ انقضا
- **ارزش و استهلاک**
- **وضعیت** — فعال، انبار، تعمیر، بازنشسته

**ابزارها:** Snipe-IT، GLPI، NetBox (برای شبکه)، Excel (برای شروع).

**نکتهٔ مهم:** **CMDB** (Configuration Management Database) نسخهٔ پیشرفته‌تر است: روابط بین دارایی‌ها (کدام سرور روی کدام host، کدام اپلیکیشن روی کدام سرور).

**چرا مهم است؟**

- **امنیت:** نمی‌توانی چیزی را که نمی‌شناسی محافظت کنی. سرور «فراموش‌شده» = درِ باز.
- **انطباق:** ممیزی لایسنس نیاز به شمارش دارد.
- **DR:** برای بازیابی، باید بدانی چه چیزی داشتی.
- **هزینه:** دارایی‌های بی‌استفاده، پول هدر رفته.

**نگهداشت پیشگیرانه (Preventive Maintenance):**

| بازه | کار |
|---|---|
| هفتگی | بررسی هشدارها، فضای دیسک |
| ماهانه | بررسی firmware، لاگ خطا، backup test |
| فصلی | بررسی ظرفیت، به‌روزرسانی مستندات |
| سالانه | بازبینی چرخهٔ عمر، تست DR، ممیزی لایسنس |

### مثال‌های عملی

**Lab Scenario 1 — برنامهٔ مهاجرت یک سرور فایل**

> **وضعیت:** سرور فایل ویندوز ۲۰۱۲ با ۲TB داده، ۳۰۰ کاربر. باید به سرور جدید (Windows Server 2022) مهاجرت کنی. SLA: حداکثر ۴ ساعت قطعی.
>
> **وظیفه:** برنامه بنویس.
>
> **پاسخ:**
>
> | مرحله | زمان | اقدام |
> |---|---|---|
> | T-۱۴ روز | — | ارزیابی: حجم، shareها، مجوزها، اپلیکیشن‌های وابسته |
> | T-۷ | — | ساخت سرور جدید، join دامنه، تست دسترسی |
> | T-۳ | — | کپی اولیه (robocopy /MIR) — ۲TB، چند ساعت |
> | T-۱ | — | sync delta (robocopy مجدد) — سریع |
> | T-0 (شب) | ۲ ساعت | قطع دسترسی، sync نهایی، تغییر DNS/DFS، تست |
> | T+۰ | ۱ ساعت | تست کاربران کلیدی |
> | T+۱ روز | — | پایش، رفع مشکلات |
> | T+۷ روز | — | بازنشستگی سرور قدیم (read-only برای مدتی) |
>
> **Rollback:** اگر cutover شکست خورد، DNS به سرور قدیم برگردد (سرور قدیم تا ۷ روز دست‌نخورده).
>
> **درس:** کپی اولیه + delta = downtime کمینه. rollback = بیمه.

**Lab Scenario 2 — مستندات نداریم**

> **وضعیت:** وارد سازمانی می‌شوی که هیچ مستندی ندارد. ۱۵ سرور، ۳ سوئیچ، ۲ فایروال.
>
> **وظیفه:** از کجا شروع می‌کنی؟
>
> **پاسخ:**
> ۱. **کشف (discovery):** `nmap -sn 10.0.0.0/16` برای پیدا کردن دستگاه‌های فعال.
> ۲. **فهرست سرورها:** نام، IP، OS، نقش (از سرویس‌های در حال اجرا).
> ۳. **نقشهٔ شبکه:** ARP table، CDP/LLDP روی سوئیچ‌ها.
> ۴. **مصاحبه:** با قدیمی‌ترین کارمند فنی.
> ۵. **اولویت:** اول چیزهایی که در DR لازم‌اند (نقشهٔ شبکه، فهرست سرور، رمزها).
> ۶. **ابزار:** NetBox برای شبکه، Snipe-IT برای دارایی.
>
> **درس:** مستندسازی کامل ماه‌ها طول می‌کشد؛ اما «حداقل حیاتی» در یک هفته ممکن است.

### مقایسه و الگوهای مختلف

**مقایسهٔ روش‌های مهاجرت:**

| روش | downtime | پیچیدگی | مناسب |
|---|---|---|---|
| Cold | بالا | کم | سرور غیرحیاتی |
| Warm | کم | متوسط | اکثر موارد |
| Live | صفر | بالا | سرویس ۲۴×۷ |
| Rebuild | متوسط | متوسط | وقتی پیکربندی قابل بازسازی است |

**نکته:** گاهی «rebuild از صفر» بهتر از مهاجرت است — اگر سرور قدیمی «آشغال» دارد (نرم‌افزار اضافه، تنظیمات فراموش‌شده).

**مقایسهٔ ابزارهای مستندسازی:**

| ابزار | نوع | مناسب |
|---|---|---|
| **NetBox** | IPAM/DCIM | شبکه، رک، IP |
| **Snipe-IT** | asset | دارایی فیزیکی |
| **GLPI** | ITSM + asset | سازمانی |
| **Wiki (Confluence/BookStack)** | دانش | runbook |
| **Git + Markdown** | docs as code | فنی |

**مقایسهٔ CMDB و inventory:**

| معیار | Inventory | CMDB |
|---|---|---|
| محتوا | لیست دارایی | دارایی + روابط |
| پیچیدگی | کم | بالا |
| مناسب | شروع | سازمان بالغ |

### اشکال شایع

**۱. مهاجرت بدون rollback plan.**
اگر شکست بخورد، ساعت‌ها downtime.

**۲. کپی داده بدون حفظ مجوزها.**
`robocopy` بدون `/COPYALL` یا `rsync` بدون `-a` → ACL از دست می‌رود.

**۳. حذف منبع قبل از تأیید.**
داده از دست می‌رود. همیشه مدتی read-only نگه دار.

**۴. مستندات قدیمی.**
بدتر از نبودشان. باید تاریخ بازبینی داشته باشند.

**۵. رمزها در فایل متنی.**
از password manager یا vault استفاده کن.

**۶. دارایی‌های «فراموش‌شده».**
سروری که کسی نمی‌داند وجود دارد، patch نمی‌شود و در معرض حمله است.

**۷. نداشتن asset tag.**
در انبار، دو سرور هم‌مدل قابل تفکیک نیستند.

**۸. نگهداشت پیشگیرانه فراموش‌شده.**
خرابی در بدترین زمان.

### نکات مهم (Tips & Tricks)

- **`robocopy /MIR /COPYALL /DCOPY:DAT /R:1 /W:1`** برای کپی ویندوز با مجوز.
- **`rsync -avAX --delete`** برای لینوکس (ACL و xattr).
- **قبل از مهاجرت، یک تست بازیابی انجام بده** — نه فقط کپی.
- **NetBox را از روز اول راه بینداز** — حتی برای ۱۰ دستگاه.
- **هر سند، تاریخ «آخرین بازبینی» داشته باشد.**
- **در آزمون:** کلیدواژهٔ «migrate with minimal downtime» → **replication / live migration**.

### خلاصه فصل

- مهاجرت: **P2V، V2V، cold/warm/live**.
- مراحل: ارزیابی → برنامه → تست → seed → sync → cutover → تست → پاک‌سازی.
- **rollback plan** الزامی است.
- مستندات: نقشه، inventory، rack elevation، runbook، DR plan.
- **CMDB** = دارایی + روابط.
- دارایی ناشناخته = ریسک امنیتی.
