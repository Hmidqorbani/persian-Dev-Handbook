## فصل ۵۶: اندازه‌گیری و عیب‌یابی مصرف منابع

### مقدمه

برای مدیریت یک سرور، باید بدانید چه منابعی چقدر مصرف می‌شوند. تصور کنید سرور کند شده و کاربران شکایت دارند — باید سریع بفهمید گلوگاه کجاست: CPU، حافظه، دیسک یا شبکه؟

**برنامه‌ریزی ظرفیت (Capacity Planning)** یعنی اندازه‌گیری مصرف فعلی و پیش‌بینی نیاز آینده. اولین گام، پایش دقیق منابع است.

### مفاهیم اساسی

**چهار منبع اصلی:**

| منبع | ابزارهای پایش |
|---|---|
| **CPU** | top, mpstat, sar, uptime |
| **Memory** | free, vmstat, sar |
| **Disk I/O** | iostat, iotop, sar |
| **Network** | iftop, nload, sar -n |

**Load Average:** میانگین تعداد فرآیندهای در انتظار. سه عدد: ۱، ۵ و ۱۵ دقیقه.

**تفسیر load:**

| Load (۴ هسته) | وضعیت |
|---|---|
| < 4 | سالم |
| = 4 | اشباع |
| > 4 | تحت فشار |

**نکته:** load شامل انتظار I/O هم می‌شود، نه فقط CPU.

**ابزار sar (System Activity Reporter):** بخشی از `sysstat`، تاریخچهٔ مصرف را ثبت می‌کند.

**ابزارهای پایش:**

| ابزار | کار |
|---|---|
| `top`/`htop` | لحظه‌ای |
| `vmstat` | حافظه، CPU، I/O |
| `iostat` | I/O دیسک |
| `mpstat` | CPU per-core |
| `sar` | تاریخی |
| `free` | حافظه |
| `df`/`du` | دیسک |

### مثال‌های عملی

**پایش CPU:**

```bash
# load average
uptime
cat /proc/loadavg

# آمار CPU per-core
mpstat -P ALL 1
mpstat 1 5           # ۵ نمونه

# top/htop
top
htop

# sar (تاریخی)
sar -u 1 5           # ۵ نمونه هر ۱ ثانیه
sar -u -f /var/log/sysstat/sa16
sar -u -s 10:00:00 -e 11:00:00
```

**پایش حافظه:**

```bash
free -h
free -m
vmstat 1 5
cat /proc/meminfo

# sar
sar -r 1 5
sar -r -f /var/log/sysstat/sa16

# ستون‌های vmstat: r, b, swpd, free, buff, cache, si, so
```

**پایش دیسک:**

```bash
# فضای دیسک
df -h
df -i                # inodeها
df -hT               # با نوع

# I/O
iostat -x 1 5
iotop                # نیاز به نصب
sar -d 1 5

# ستون %util اشباع دیسک را نشان می‌دهد
```

**پایش شبکه:**

```bash
# آمار رابط
ip -s link
sar -n DEV 1 5

# ابزارهای نصب‌شدنی
iftop
nload
nethogs

# سرعت
speedtest-cli
```

**نصب و فعال‌سازی sysstat:**

```bash
sudo apt install sysstat
sudo systemctl enable --now sysstat

# پیکربندی /etc/default/sysstat
# ENABLED="true"

# تاریخچه
ls /var/log/sysstat/
sar -f /var/log/sysstat/sa16
```

### مقایسه و الگوهای مختلف

**ابزارهای لحظه‌ای در برابر تاریخی:**

| نوع | ابزار | کاربرد |
|---|---|---|
| لحظه‌ای | top, free, iostat | عیب‌یابی فوری |
| تاریخی | sar, sysstat | تحلیل روند |

**ابزارهای جامع:**

| ابزار | ویژگی |
|---|---|
| `atop` | لاگ تاریخی جامع |
| `nmon` | جامع، تعاملی |
| `glances` | مدرن، رنگی |
| `dstat` | ترکیبی |

**ستون‌های مهم:**

| ابزار | ستون | معنا |
|---|---|---|
| `free` | available | حافظهٔ واقعاً آزاد |
| `vmstat` | si/so | swap in/out |
| `iostat` | %util | اشباع دیسک |
| `mpstat` | %iowait | انتظار I/O |

**نصب ابزارها:**

| ابزار | پکیج |
|---|---|
| `iostat`, `mpstat`, `sar` | sysstat |
| `htop` | htop |
| `iotop` | iotop |
| `iftop` | iftop |
| `nmon` | nmon |

### اشکال شایع

**اشکال ۱: اشتباه load با مصرف CPU.**
load شامل انتظار I/O هم می‌شود. راه‌حل: `vmstat` را ببینید.

**اشکال ۲: نادیده گرفتن inode.**
دیسک فضا دارد ولی inode تمام است. راه‌حل: `df -i`.

**اشکال ۳: نبود sysstat.**
sar کار نمی‌کند؛ باید نصب و فعال شود. راه‌حل: نصب + enable.

**اشکال ۴: تفسیر نادرست cache.**
حافظهٔ cache در `free` اشغال نیست. راه‌حل: ستون `available`.

**اشکال ۵: نادیده گرفتن %iowait.**
انتظار I/O باعث کندی است. راه‌حل: `iostat`.

**اشکال ۶: پایش بدون baseline.**
بدون مبنای مقایسه، نمی‌دانید «زیاد» چیست. راه‌حل: baseline.

### نکات مهم (Tips & Tricks)

- **در `free`، ستون `available` مهم‌تر از `free` است.**
- **`vmstat` ستون `si`/`so` (swap in/out) را ببینید.**
- **`iostat -x` ستون `%util` اشباع دیسک را نشان می‌دهد.**
- **`sar` برای تحلیل روند هفتگی/ماهانه.**
- **`nmon` ابزار جامع پایش است.**
- **`atop` لاگ تاریخی جامع می‌دهد.**
- **`mpstat -P ALL` هر هسته را جدا نشان می‌دهد.**
- **`iotop` I/O هر فرآیند را نشان می‌دهد.**
- **`watch -n1 cmd` پایش دوره‌ای.**
- **`pidstat` آمار هر فرآیند.**
- **`turbostat` فرکانس CPU.**
- **baseline بگیرید و ماهانه مقایسه کنید.**

### خلاصه فصل

پایش منابع (CPU، حافظه، دیسک، شبکه) پایهٔ برنامه‌ریزی ظرفیت است. Load average فشار کلی را نشان می‌دهد (شامل I/O). `top`, `free`, `iostat`, `vmstat`, `sar` ابزارهای اصلی‌اند. sar (sysstat) تاریخچه را ثبت می‌کند. حافظهٔ cache در `free` مصرف واقعی نیست؛ ستون `available` را ببینید. `%iowait` و `%util` گلوگاه‌های پنهان را نشان می‌دهند.

## فصل ۵۷: پیش‌بینی نیازهای آیندهٔ منابع

### مقدمه

بعد از اندازه‌گیری، باید پیش‌بینی کنید چه زمانی به منابع بیشتری نیاز خواهید داشت. تصور کنید دیسک سرور ماهانه ۵ گیگ رشد می‌کند — چه زمانی پر می‌شود؟ با تحلیل روند، قبل از بحران اقدام می‌کنید.

این فصل به تحلیل روند و برنامه‌ریزی می‌پردازد.

### مفاهیم اساسی

**مفاهیم کلیدی:**

- **Baseline:** وضعیت پایهٔ مصرف.
- **Trend:** روند تغییر مصرف در زمان.
- **Threshold:** آستانهٔ هشدار.
- **Headroom:** فضای اضافی برای رشد.
- **Growth rate:** نرخ رشد.

**منابع کلیدی برای پیش‌بینی:**

- رشد دادهٔ دیسک.
- افزایش تعداد کاربران/اتصالات.
- روند مصرف حافظه.
- پهنای باند شبکه.

**قاعدهٔ کلی:** ظرفیت را برای ۱.۵ تا ۲ برابر بار فعلی برنامه‌ریزی کنید.

### مثال‌های عملی

**تحلیل روند دیسک:**

```bash
# ثبت روزانهٔ مصرف
df -h > /var/log/disk-usage-$(date +%Y%m%d).txt

# اسکریپت پایش روند
#!/bin/bash
THRESHOLD=80
df -h | awk 'NR>1 {gsub("%","",$5); if ($5 > '$THRESHOLD') print $0}' \
  | mail -s "Disk Alert" admin@example.com
```

**پیش‌بینی رشد:**

```bash
# مقایسهٔ مصرف در زمان
sar -r -f /var/log/sysstat/sa15   # ۱۵ ماه
sar -r -f /var/log/sysstat/sa16   # ۱۶ ماه

# روند I/O
sar -d -f /var/log/sysstat/sa16

# محاسبهٔ growth rate
# اگر ۱۰ گیگ در ۳۰ روز رشد → ۰.۳۳ گیگ/روز
# اگر ۱۰۰ گیگ آزاد → ~۳۰۰ روز
```

**پایش خودکار با آستانه:**

```bash
#!/bin/bash
# capacity-check.sh
CPU_LOAD=$(cat /proc/loadavg | cut -d' ' -f1)
MEM_USED=$(free | awk '/Mem:/ {print $3/$2*100}')
DISK_USED=$(df / | awk 'NR==2 {print $5}' | tr -d '%')

echo "Load: $CPU_LOAD"
echo "Memory: ${MEM_USED}%"
echo "Disk: ${DISK_USED}%"

if [ "${DISK_USED%.*}" -gt 85 ]; then
  echo "هشدار: دیسک تقریباً پر است!"
fi

if [ "${MEM_USED%.*}" -gt 90 ]; then
  echo "هشدار: حافظه تقریباً پر است!"
fi
```

```yaml
# Prometheus + Grafana
# prometheus.yml
scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['localhost:9100']
```

```bash

curl localhost:9100/metrics
```

### مقایسه و الگوهای مختلف

**روش‌های پیش‌بینی:**

| روش | توضیح |
|---|---|
| **Trend analysis** | تحلیل روند تاریخی |
| **Baseline** | مقایسه با پایه |
| **Threshold alerting** | هشدار در آستانه |
| **Linear projection** | پیش‌بینی خطی |
| **Seasonal analysis** | الگوهای فصلی |

**ابزارهای مانیتورینگ متمرکز:**

| ابزار | نوع | مناسب |
|---|---|---|
| Prometheus + Grafana | مدرن، محبوب | همه‌جا |
| Zabbix | جامع | سازمانی |
| Nagios | کلاسیک | سنتی |
| Munin | ساده | کوچک |
| Netdata | Real-time | سریع |

**آستانه‌های پیشنهادی:**

| منبع | هشدار | بحرانی |
|---|---|---|
| Disk | ۸۰٪ | ۹۰٪ |
| Memory | ۸۵٪ | ۹۵٪ |
| CPU load | ۱.۵×هسته | ۲×هسته |
| Swap | ۵۰٪ | ۸۰٪ |

### اشکال شایع

**اشکال ۱: نبود baseline.**
بدون پایه، مقایسه ناممکن است. راه‌حل: baseline بگیرید.

**اشکال ۲: آستانه‌های خیلی بالا/پایین.**
هشدار بی‌موقع یا دیر. راه‌حل: آستانهٔ منطقی.

**اشکال ۳: نادیده گرفتن الگوهای فصلی.**
مصرف در زمان‌های خاص بالا می‌رود. راه‌حل: تحلیل فصلی.

**اشکال ۴: نبود هشدار خودکار.**
باید سیستم هشدار داشته باشد. راه‌حل: مانیتورینگ.

**اشکال ۵: نادیده گرفتن روند I/O.**
CPU کم است ولی دیسک گلوگاه. راه‌حل: پایش I/O.

**اشکال ۶: نبود headroom.**
سرور در اوج بار می‌افتد. راه‌حل: ۱.۵–۲× ظرفیت.

### نکات مهم (Tips & Tricks)

- **از Prometheus + Grafana برای مانیتورینگ مدرن استفاده کنید.**
- **baseline بگیرید و ماهانه مقایسه کنید.**
- **هشدارها را به ایمیل/Slack وصل کنید.**
- **برای دیسک، growth rate را محاسبه کنید (مثلاً GB در ماه).**
- **ظرفیت را برای ۱.۵ تا ۲ برابر بار فعلی برنامه‌ریزی کنید (headroom).**
- **`logrotate` و پاک‌سازی منظم، رشد لاگ را کنترل می‌کند.**
- **`ncdu` تحلیل تعاملی فضاست.**
- **Zabbix برای سازمان‌های بزرگ.**
- **Netdata برای real-time سریع.**
- **آستانه‌ها را بر اساس تجربه تنظیم کنید.**
- **روند را در نمودار ثبت کنید.**
- **برای رشد پیش‌بینی‌نشده، auto-scaling (ابر).**

### خلاصه فصل

پیش‌بینی نیاز آینده بر پایهٔ baseline، تحلیل روند و آستانه‌ها انجام می‌شود. با sar روند تاریخی را تحلیل کنید، هشدار خودکار (ایمیل/Slack) بگذارید و growth rate را محاسبه کنید. برای مانیتورینگ متمرکز از Prometheus/Grafana یا Zabbix استفاده کنید. همیشه headroom برای رشد در نظر بگیرید و آستانه‌های هشدار منطقی تنظیم کنید.
