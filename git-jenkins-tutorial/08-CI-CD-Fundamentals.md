## فصل ۱: CI، CD و تفاوت‌ها

### مقدمه

**CI/CD** سه مفهوم مرتبط اما متفاوت است که اغلب اشتباه گرفته می‌شوند. درک دقیق این تفاوت‌ها پایه کار با Jenkins است.

### مفاهیم اساسی

**CI (Continuous Integration) — ادغام مداوم:**
توسعه‌دهندگان تغییرات را مرتب (چند بار در روز) در شاخه اصلی ادغام می‌کنند. هر ادغام با **Build و تست خودکار** تأیید می‌شود.

**Continuous Delivery — تحویل مداوم:**
بعد از CI، نسخه همیشه آماده انتشار است. اما **انتشار به تولید دستی** است (یک تأیید انسانی).

**Continuous Deployment — استقرار مداوم:**
مانند تحویل مداوم، اما **انتشار به تولید هم خودکار** است؛ هیچ تأیید دستی وجود ندارد.

```
کد → Build → Test → [CI]
         ↓
      Staging → [Continuous Delivery: تأیید دستی]
         ↓
      Production → [Continuous Deployment: خودکار]
```

### مقایسه و الگوهای مختلف

| مفهوم | خودکار تا کجا | تأیید انسانی |
|-------|----------------|---------------|
| CI | تست | - |
| Continuous Delivery | آماده انتشار | برای انتشار |
| Continuous Deployment | انتشار کامل | ندارد |

### اشکال شایع

- **اشتباه رایج**: یکی دانستن Delivery و Deployment. تفاوت در تأیید دستی است.
- **اشتباه رایج**: پیاده‌سازی Deployment خودکار بدون تست قوی. فاجعه‌بار است.

### نکات مهم (Tips & Tricks)

- از CI شروع کنید، سپس به Delivery و در نهایت Deployment بروید.
- Continuous Deployment نیازمند فرهنگ تست و مانیتورینگ قوی است.

### خلاصه فصل

CI ادغام و تست خودکار است. Continuous Delivery نسخه را آماده انتشار می‌کند (تأیید دستی). Continuous Deployment انتشار را هم خودکار می‌کند.

## فصل ۲: آناتومی یک Pipeline

### مقدمه

**Pipeline** زنجیره‌ای از مراحل خودکار است که کد را از commit تا تولید می‌برد. شناخت اجزای آن ضروری است.

### مفاهیم اساسی

اجزای اصلی:

- **Stage (مرحله)**: بخش منطقی Pipeline (مثل Build، Test، Deploy).
- **Step (گام)**: یک دستور یا کار خاص درون Stage.
- **Job**: واحد کاری که روی یک Agent اجرا می‌شود.
- **Agent/Node**: ماشینی که Job روی آن اجرا می‌شود.
- **Artifact**: خروجی یک مرحله (مثل فایل jar، image).
- **Workspace**: فضای کاری روی Agent.

```
Pipeline
├── Stage: Checkout
│   └── Step: git clone
├── Stage: Build
│   └── Step: mvn package
├── Stage: Test
│   ├── Step: unit tests
│   └── Step: integration tests
└── Stage: Deploy
    └── Step: deploy to staging
```

### مثال‌های عملی

نمای ساده یک Pipeline:

```
[Checkout] → [Build] → [Test] → [Package] → [Deploy]
```

هر مرحله فقط اگر مرحله قبل موفق باشد اجرا می‌شود.

### اشکال شایع

- **اشتباه رایج**: مراحل خیلی بزرگ. هر Stage باید یک مسئولیت داشته باشد.
- **اشتباه رایج**: نادیده گرفتن Artifact؛ هر بار از صفر build کردن.

### نکات مهم (Tips & Tricks)

- Pipeline را **Fail Fast** طراحی کنید: تست‌های سریع اول.
- Artifactها را بین Stageها منتقل کنید تا دوباره کاری نشود.
- Workspace را تمیز نگه دارید.

### خلاصه فصل

Pipeline از Stage، Step، Job و Agent ساخته می‌شود. Artifactها خروجی مراحل‌اند. طراحی Fail Fast و انتقال Artifact، Pipeline را کارآمد می‌کند.

## فصل ۳: چرا اتوماسیون؟

### مقدمه

چرا به‌جای انجام دستی، از CI/CD استفاده کنیم؟ پاسخ در هزینه، سرعت و کیفیت است.

### مفاهیم اساسی

مزایای اتوماسیون:
- **سرعت**: فرآیند دستی ساعت‌ها طول می‌کشد؛ خودکار دقیقه‌ها.
- **تکرارپذیری**: هر بار یکسان اجرا می‌شود؛ خطای انسانی حذف می‌شود.
- **بازخورد سریع**: توسعه‌دهنده فوراً از باگ باخبر می‌شود.
- **کیفیت**: تست‌ها همیشه اجرا می‌شوند.
- **مستندسازی**: Pipeline خودش مستند فرآیند است.
- **آرامش تیم**: انتشار از یک رویداد پراسترس به یک کار روتین تبدیل می‌شود.

هزینه‌های اتوماسیون:
- زمان راه‌اندازی اولیه
- نگهداری Pipeline
- نیاز به زیرساخت (سرور/Agent)

### مقایسه و الگوهای مختلف

| فرآیند دستی | فرآیند خودکار |
|--------------|----------------|
| کند و پرخطا | سریع و دقیق |
| وابسته به فرد | مستقل |
| بدون مستند | مستندشده در کد |

### اشکال شایع

- **اشتباه رایج**: اتوماسیون فرآیند خراب. اول فرآیند را اصلاح کنید، بعد خودکار کنید.
- **اشتباه رایج**: اتوماسیون بدون تست. فقط خرابی را سریع‌تر می‌کنید.

### نکات مهم (Tips & Tricks)

- قانون: «اگر دو بار دستی انجامش دادی، خودکارش کن.»
- از فرآیندهای ساده شروع کنید.

### خلاصه فصل

اتوماسیون سرعت، کیفیت و تکرارپذیری می‌آورد و خطای انسانی را حذف می‌کند. هزینه اولیه دارد اما در بلندمدت به‌شدت سودآور است.

## فصل ۴: ابزارهای CI/CD و جایگاه Jenkins

### مقدمه

ابزارهای CI/CD زیادی وجود دارد. Jenkins یکی از قدیمی‌ترین و انعطاف‌پذیرترین آن‌هاست.

### مفاهیم اساسی

**Jenkins**: متن‌باز، خودمیزبان، بسیار انعطاف‌پذیر، اکوسیستم عظیم افزونه‌ها (۱۸۰۰+).

**GitHub Actions**: یکپارچه با GitHub، YAML-based، ابری.

**GitLab CI**: یکپارچه با GitLab، بسیار قدرتمند، YAML-based.

**CircleCI، Travis CI، TeamCity، Bamboo**: گزینه‌های دیگر.

**چرا Jenkins؟**
- کاملاً رایگان و متن‌باز
- خودمیزبان (کنترل کامل داده)
- انعطاف‌پذیری بی‌نظیر
- اکوسیستم افزونه غنی
- مناسب هر زبان و پلتفرم

### مقایسه و الگوهای مختلف

| ابزار | میزبانی | پیکربندی | هزینه |
|-------|---------|-----------|-------|
| Jenkins | خودمیزبان | Groovy/YAML | رایگان |
| GitHub Actions | ابری | YAML | محدود رایگان |
| GitLab CI | هر دو | YAML | محدود رایگان |

### اشکال شایع

- **اشتباه رایج**: انتخاب ابزار بدون توجه به نیاز. Jenkins برای سازمان‌هایی که کنترل کامل می‌خواهند عالی است.

### نکات مهم (Tips & Tricks)

- Jenkins نگهداری بیشتری از سرویس‌های ابری نیاز دارد.
- در بخش ۲۰ مقایسه جامع‌تری خواهیم داشت.

### خلاصه فصل

ابزارهای CI/CD متنوع‌اند. Jenkins با خودمیزبانی، رایگان بودن و انعطاف‌پذیری، انتخابی عالی برای سازمان‌هایی است که کنترل کامل می‌خواهند.

## فصل ۵: مفاهیم Build تا Rollback

### مقدمه

در یک Pipeline، چند مفهوم کلیدی تکرار می‌شوند. این فصل آن‌ها را یکجا مرور می‌کند.

### مفاهیم اساسی

- **Build**: تبدیل سورس‌کد به خروجی قابل اجرا (compile، bundle).
- **Test**: اجرای تست‌های واحد، یکپارچگی و end-to-end.
- **Lint**: بررسی سبک و کیفیت کد.
- **Package**: بسته‌بندی خروجی (jar، wheel، image).
- **Artifact**: فایل خروجی ذخیره‌شده.
- **Deploy**: استقرار در محیط (dev/staging/prod).
- **Rollback**: بازگشت به نسخه قبلی در صورت خطا.
- **Smoke Test**: تست سریع بعد از استقرار.
- **Blue-Green Deployment**: دو محیط موازی برای استقرار بی‌وقفه.
- **Canary Release**: انتشار به درصد کوچکی از کاربران.

### مثال‌های عملی

چرخه یک Pipeline واقعی:

```
1. Checkout کد
2. نصب وابستگی‌ها
3. Lint
4. Unit Test
5. Build
6. Integration Test
7. Package (Docker image)
8. Push to Registry
9. Deploy to Staging
10. Smoke Test
11. Deploy to Production (Blue-Green)
12. Monitor & Rollback if needed
```

### اشکال شایع

- **اشتباه رایج**: نداشتن استراتژی Rollback. همیشه باید بتوانید برگردید.
- **اشتباه رایج**: نادیده گرفتن Smoke Test.

### نکات مهم (Tips & Tricks)

- هر استقرار باید قابل بازگشت باشد.
- Blue-Green و Canary ریسک استقرار را کم می‌کنند.

### خلاصه فصل

از Build تا Rollback، هر مفهوم نقشی در Pipeline دارد. استقرار بی‌وقفه (Blue-Green/Canary) و Rollback آماده، استقرار مطمئن را ممکن می‌کنند.

## فصل ۶: اصول طراحی Pipeline مؤثر

### مقدمه

Pipeline خوب، سریع، قابل اعتماد و قابل نگهداری است. این فصل اصول طراحی را مرور می‌کند.

### مفاهیم اساسی

اصول کلیدی:
1. **Fail Fast**: تست‌های سریع اول اجرا شوند.
2. **موازی‌سازی**: مراحل مستقل همزمان اجرا شوند.
3. **Pipeline as Code**: در فایل `Jenkinsfile` نگه‌داری شود.
4. **تکرارپذیری**: نتیجه در هر اجرا یکسان.
5. **ایزولاسیون**: هر Build در محیط تمیز.
6. **قابل مشاهده بودن**: لاگ، نمودار، اعلان.
7. **امنیت**: مدیریت درست Secretها.
8. **سادگی**: از پیچیدگی غیرضروری پرهیز کنید.

### مثال‌های عملی

موازی‌سازی تست‌ها:

```
Stage: Test
├── Job: unit-tests     (موازی)
├── Job: lint           (موازی)
└── Job: integration    (موازی)
```

### اشکال شایع

- **اشتباه رایج**: Pipelineهای غول‌پیکر و پیچیده. به مراحل کوچک بشکنید.
- **اشتباه رایج**: Hardcode کردن Secretها. از Credentials استفاده کنید.

### نکات مهم (Tips & Tricks)

- زمان اجرای Pipeline را اندازه بگیرید و بهینه کنید.
- کش کردن وابستگی‌ها زمان را کم می‌کند.
- Pipeline را مثل کد بازبینی کنید (Code Review).

### خلاصه فصل

Pipeline مؤثر Fail Fast، موازی و به‌صورت کد نوشته می‌شود. تکرارپذیری، ایزولاسیون و امنیت اصول کلیدی‌اند. Pipeline را مثل کد نگه‌داری و بازبینی کنید.
