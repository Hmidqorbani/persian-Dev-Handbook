## فصل ۱: چرا استراتژی مهم است؟

### مقدمه

استراتژی شاخه‌بندی (Branching Strategy) مجموعه قواعدی است که تعیین می‌کند تیم چگونه شاخه بسازد، کد را ادغام کند و منتشر کند. انتخاب درست، همکاری را روان و انتشار را قابل پیش‌بینی می‌کند.

### اهمیت این موضوع

بدون استراتژی، هرکس به سلیقه خود کار می‌کند؛ نتیجه: شاخه‌های گیج‌کننده، تعارض‌های مداوم و انتشارهای پر از باگ. استراتژی، زبان مشترک تیم است.

### مفاهیم اساسی

هر استراتژی به سه سؤال پاسخ می‌دهد:
1. کدام شاخه «حقیقت» است؟ (main/trunk/develop)
2. تغییرات چطور به آن می‌رسند؟ (PR/merge/rebase)
3. چطور منتشر می‌شوند؟ (tag/release branch/deploy)

### اشکال شایع

- **اشتباه رایج**: تقلید کورکورانه از استراتژی شرکت‌های بزرگ بدون توجه به اندازه تیم.
- **اشتباه رایج**: نداشتن استراتژی مکتوب.

### نکات مهم (Tips & Tricks)

- استراتژی باید با **سرعت انتشار** و **اندازه تیم** هماهنگ باشد.
- برای تیم‌های کوچک، سادگی برنده است.

### خلاصه فصل

استراتژی شاخه‌بندی قواعد همکاری تیم است. باید با اندازه تیم و سرعت انتشار هماهنگ باشد و مکتوب شود.

## فصل ۲: GitFlow

### مقدمه

**GitFlow** که توسط Vincent Driessen معرفی شد، جامع‌ترین استراتژی است. برای پروژه‌هایی با چرخه انتشار مشخص و نسخه‌بندی رسمی مناسب است.

### مفاهیم اساسی

شاخه‌های GitFlow:
- **main**: نسخه تولید (همیشه پایدار).
- **develop**: شاخه ادغام توسعه.
- **feature/***: ویژگی‌های جدید (از develop).
- **release/***: آماده‌سازی انتشار (از develop).
- **hotfix/***: رفع فوری باگ تولید (از main).

```
main     ──●────────────●────────●──── (tag v1.0, v1.1)
            \          /  \      /
hotfix       \        ●    \    /
              \      /      \  /
release        \    ●        ●
                \  /          \
develop  ──●──●──●────●───●────●──●
            \    /        \  /
feature      ●──●          ●──●
```

### مثال‌های عملی

```bash
# شروع feature
git switch develop
git switch -c feature/payment

# اتمام feature
git switch develop
git merge --no-ff feature/payment

# آماده‌سازی release
git switch -c release/1.2.0 develop
# تست، رفع باگ...
git switch main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop
git merge --no-ff release/1.2.0

# hotfix فوری
git switch -c hotfix/1.2.1 main
# رفع باگ
git switch main
git merge --no-ff hotfix/1.2.1
git tag -a v1.2.1 -m "Hotfix 1.2.1"
```

### مقایسه و الگوهای مختلف

| مزایا | معایب |
|-------|-------|
| ساختار شفاف | پیچیده برای CI/CD |
| مناسب نسخه‌بندی رسمی | ادغام‌های زیاد |
| کنترل دقیق انتشار | کند برای استقرار مداوم |

### اشکال شایع

- **اشتباه رایج**: استفاده از GitFlow در پروژه‌های web با استقرار روزانه. GitFlow برای آن‌ها بیش از حد سنگین است.
- **اشتباه رایج**: merge کردن اشتباه release به main و فراموش کردن develop.

### نکات مهم (Tips & Tricks)

- ابزار `git-flow` (افزونه) این دستورات را خودکار می‌کند.
- GitFlow برای نرم‌افزارهای دسکتاپ، کتابخانه‌ها و نسخه‌بندی‌شده عالی است.

### خلاصه فصل

GitFlow با شاخه‌های main، develop، feature، release و hotfix، کنترل دقیقی بر انتشار می‌دهد. برای پروژه‌های نسخه‌بندی‌شده مناسب است، اما برای استقرار مداوم سنگین است.

## فصل ۳: GitHub Flow

### مقدمه

**GitHub Flow** ساده‌ترین استراتژی است: فقط یک شاخه اصلی (`main`) و شاخه‌های feature کوتاه‌مدت. هر تغییر از طریق PR وارد main می‌شود و main همیشه قابل استقرار است.

### مفاهیم اساسی

قواعد GitHub Flow:
1. `main` همیشه قابل انتشار است.
2. برای هر تغییر شاخه‌ای با نام توصیفی بسازید.
3. مرتب commit و push کنید.
4. PR باز کنید.
5. بعد از بازبینی و CI موفق، merge کنید.
6. بلافاصله مستقر کنید.

```
main ──●──────●──────────●──────●──
        \    /  \        /  \  /
feature  ●──●    ●──────●    ●●
```

### مثال‌های عملی

```bash
git switch main
git pull
git switch -c feature/add-search
# ... کار و commit ...
git push -u origin feature/add-search
gh pr create --title "Add search" --body "Closes #10"
# بعد از تأیید و CI
gh pr merge --squash
```

### مقایسه و الگوهای مختلف

| مزایا | معایب |
|-------|-------|
| ساده و سریع | نیاز به تست قوی |
| مناسب CI/CD | نسخه‌بندی رسمی ندارد |
| بازخورد سریع | مدیریت release سخت‌تر |

### اشکال شایع

- **اشتباه رایج**: شاخه‌های طولانی‌مدت. شاخه‌ها باید کوتاه باشند (چند روز).
- **اشتباه رایج**: merge بدون تست خودکار.

### نکات مهم (Tips & Tricks)

- شاخه‌های feature را حداکثر چند روز زنده نگه دارید.
- از feature flag برای ویژگی‌های نیمه‌کاره استفاده کنید.
- GitHub Flow برای SaaS و وب‌اپلیکیشن‌ها ایده‌آل است.

### خلاصه فصل

GitHub Flow ساده، سریع و مناسب CI/CD است. با یک شاخه اصلی و شاخه‌های feature کوتاه کار می‌کند. برای استقرار مداوم بهترین انتخاب است.

## فصل ۴: Trunk-Based Development

### مقدمه

**Trunk-Based Development (TBD)** پیشرفته‌ترین و در عین حال سخت‌گیرانه‌ترین استراتژی است: همه توسعه‌دهندگان مستقیماً روی `trunk` (main) یا شاخه‌های بسیار کوتاه‌مدت (کمتر از یک روز) کار می‌کنند.

### مفاهیم اساسی

اصول TBD:
- شاخه‌ها بسیار کوتاه‌عمر (ساعت‌ها، نه روزها).
- commitهای کوچک و مکرر به trunk.
- **Feature Flags** برای پنهان کردن ویژگی‌های نیمه‌کاره.
- تست خودکار قوی (CI/CD حیاتی است).

```
trunk ──●──●──●──●──●──●──●──●──  (commitهای کوچک مکرر)
         \_/  \_/  \_/
        شاخه‌های بسیار کوتاه
```

### مثال‌های عملی

```bash
# کار کوچک، سریع merge
git switch main
git pull --rebase
git switch -c quick-fix
# تغییر کوچک
git commit -am "fix: null check"
git push -u origin quick-fix
# PR فوری و merge در همان روز
```

با feature flag:

```python
if feature_flags.is_enabled("new_checkout"):
    return new_checkout_flow()
return legacy_checkout_flow()
```

### مقایسه و الگوهای مختلف

| مزایا | معایب |
|-------|-------|
| ادغام مداوم و بدون درد | نیاز به تست قوی |
| استقرار بسیار سریع | نیاز به feature flag |
| تعارض‌های حداقلی | انضباط بالا |

### اشکال شایع

- **اشتباه رایج**: پیاده‌سازی TBD بدون CI/CD قوی. فاجعه‌بار است.
- **اشتباه رایج**: commit مستقیم به trunk بدون بازبینی.

### نکات مهم (Tips & Tricks)

- TBD نیازمند **CI/CD قوی** است؛ پس این کتابچه مسیر درستی را پیش می‌برد.
- از feature flag برای جداسازی انتشار از استقرار استفاده کنید.
- شرکت‌های بزرگی مثل Google و Facebook از TBD استفاده می‌کنند.

### خلاصه فصل

TBD با commitهای کوچک مکرر به trunk و feature flag کار می‌کند. سریع‌ترین استراتژی برای استقرار است، اما نیازمند تست خودکار قوی و انضباط تیمی است.

## فصل ۵: Release Branch و Hotfix

### مقدمه

مستقل از استراتژی، دو مفهوم کلیدی وجود دارد: **Release Branch** (آماده‌سازی نسخه) و **Hotfix** (رفع فوری باگ تولید).

### مفاهیم اساسی

**Release Branch**: شاخه‌ای که از main/develop جدا می‌شود تا نسخه جدید آماده شود. در آن فقط رفع باگ و تثبیت انجام می‌شود، نه ویژگی جدید.

**Hotfix**: شاخه‌ای که مستقیماً از نسخه تولید (main/tag) جدا می‌شود تا باگ بحرانی را سریع رفع کند.

```
main     ──●─────────●──────────●
            \       /  \        /
release      ●──●──●    \      /
                          \    /
hotfix                     ●──●
```

### مثال‌های عملی

```bash
# Release branch
git switch -c release/2.0 main
# تثبیت نسخه، رفع باگ‌های آخر
git switch main
git merge --no-ff release/2.0
git tag -a v2.0.0 -m "Release 2.0.0"

# Hotfix
git switch -c hotfix/crash main
git commit -am "fix: resolve startup crash"
git switch main
git merge --no-ff hotfix/crash
git tag -a v2.0.1 -m "Hotfix 2.0.1"
```

### اشکال شایع

- **اشتباه رایج**: افزودن ویژگی جدید به release branch. فقط تثبیت.
- **اشتباه رایج**: فراموش کردن merge کردن hotfix به develop (اگر دارید).

### نکات مهم (Tips & Tricks)

- release branch را کوتاه نگه دارید (چند روز).
- hotfix را سریع merge و tag کنید.
- بعد از hotfix، حتماً به همه شاخه‌های مرتبط merge کنید.

### خلاصه فصل

Release branch برای تثبیت نسخه و hotfix برای رفع فوری باگ تولید است. هر دو از شاخه‌های پایدار جدا می‌شوند و باید سریع merge شوند.

## فصل ۶: مقایسه و انتخاب

### مقدمه

حالا که استراتژی‌ها را شناختیم، کدام را انتخاب کنیم؟ پاسخ به شرایط تیم بستگی دارد.

### مفاهیم اساسی

**جدول مقایسه جامع:**

| معیار | GitFlow | GitHub Flow | Trunk-Based |
|-------|---------|-------------|-------------|
| پیچیدگی | بالا | پایین | متوسط |
| تعداد شاخه‌های بلندمدت | چند | یک | یک |
| سرعت انتشار | کم | بالا | بسیار بالا |
| نیاز به CI/CD | متوسط | بالا | بسیار بالا |
| اندازه تیم | متوسط/بزرگ | هر اندازه | تیم‌های منضبط |
| نسخه‌بندی رسمی | عالی | ضعیف | ضعیف |
| استقرار مداوم | ضعیف | عالی | عالی |

**راهنمای انتخاب:**

- **GitFlow**: نرم‌افزار دسکتاپ، کتابخانه، محصولات نسخه‌بندی‌شده، تیم‌های متوسط/بزرگ با انتشار دوره‌ای.
- **GitHub Flow**: SaaS، وب‌اپلیکیشن، تیم‌های کوچک تا متوسط، استقرار مکرر.
- **Trunk-Based**: تیم‌های بالغ با CI/CD قوی، استقرار چندبار در روز.

### اشکال شایع

- **اشتباه رایج**: تغییر استراتژی هر ماه. یک استراتژی را انتخاب و به آن پایبند باشید.
- **اشتباه رایج**: ترکیب نامنظم چند استراتژی.

### نکات مهم (Tips & Tricks)

- با GitHub Flow شروع کنید؛ اگر نیاز به نسخه‌بندی رسمی داشتید، به GitFlow مهاجرت کنید.
- هر استراتژی را در تیم مستند کنید.
- ابزار CI/CD (مثل Jenkins) را با استراتژی هماهنگ کنید (بخش ۱۷).

### خلاصه فصل

انتخاب استراتژی به اندازه تیم، سرعت انتشار و نیاز به نسخه‌بندی بستگی دارد. GitFlow برای نسخه‌بندی رسمی، GitHub Flow برای استقرار مداوم و TBD برای سرعت حداکثری مناسب است.
