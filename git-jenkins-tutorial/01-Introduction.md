## فصل ۱: کنترل نسخه چیست و چرا به آن نیاز داریم؟

### مقدمه

تصور کنید روی یک پروژه نرم‌افزاری کار می‌کنید. روز اول فایل‌ها را می‌نویسید، روز دوم تغییراتی می‌دهید و روز سوم متوجه می‌شوید تغییر دیروزتان یک باگ جدید ساخته است. چطور می‌خواهید به حالت دیروز برگردید؟ اگر فایل‌ها را با نام‌هایی مثل `project_final.docx`، `project_final_v2.docx` و `project_final_ok_ok.docx` ذخیره کنید، خیلی زود در دریایی از نسخه‌های تکراری غرق می‌شوید.

**کنترل نسخه (Version Control)** راه‌حل حرفه‌ای این مشکل است: یک سیستم که تمام تغییرات فایل‌ها را در طول زمان ثبت می‌کند تا بتوانید هر لحظه به هر نسخه‌ای برگردید، ببینید چه کسی چه تغییری داده، و به‌صورت همزمان با دیگران کار کنید.

### اهمیت این موضوع

- **تاریخچه کامل**: هر تغییر با تاریخ، نویسنده و پیام ثبت می‌شود.
- **امکان بازگشت**: اگر چیزی خراب شد، به نسخه سالم برمی‌گردید.
- **همکاری تیمی**: چند نفر بدون اینکه کار همدیگر را خراب کنند، روی یک پروژه کار می‌کنند.
- **شاخه‌بندی (Branching)**: می‌توانید ویژگی جدید را جدا از نسخه اصلی توسعه دهید.
- **ردیابی مسئولیت**: مشخص می‌شود هر خط کد توسط چه کسی و چه زمانی نوشته شده است.

### کاربردهای عملی در دنیای واقعی

تقریباً هیچ پروژه نرم‌افزاری حرفه‌ای بدون کنترل نسخه اداره نمی‌شود. از یک اسکریپت کوچک پایتونی تا سیستم‌عامل Linux (که خودش با Git مدیریت می‌شود)، همه از این ابزار استفاده می‌کنند. حتی تیم‌های غیرنرم‌افزاری مثل نویسندگان، وکلا و محققان هم برای مدیریت اسناد خود از Git استفاده می‌کنند.

### مفاهیم اساسی

**کنترل نسخه** یعنی ثبت و مدیریت تغییرات. سه سطح کاربردی دارد:

1. **سطح فایل محلی**: نگه‌داشتن کپی‌های متعدد (روش آماتور).
2. **سطح مخزن محلی**: استفاده از ابزارهایی مثل Git روی کامپیوتر خودتان.
3. **سطح مخزن راه دور**: همگام‌سازی با سروری مثل GitHub تا تیم با شما کار کند.

### اشکال شایع

- **اشتباه رایج**: فکر کردن اینکه «پروژه من کوچک است، نیازی به Git ندارم.» حتی پروژه‌های کوچک هم از مزایای Git بهره می‌برند.
- **اشتباه رایج**: نگه‌داشتن نسخه‌های متعدد با نام‌گذاری دستی. این کار به‌سرعت گیج‌کننده می‌شود.
- **اشتباه رایج**: عدم استفاده از پیام‌های معنادار برای commitها (به فصل‌های بعدی مراجعه کنید).

### نکات مهم (Tips & Tricks)

- از همان ابتدای پروژه Git را فعال کنید، نه وقتی که پروژه بزرگ شد.
- یاد بگیرید قبل از هر commit، با `git status` و `git diff` تغییرات را مرور کنید.
- به‌جای حفظ کردن دستورات، مفهوم را بفهمید.

### خلاصه فصل

کنترل نسخه سیستمی است که تاریخچه تغییرات را ثبت می‌کند. Git پرکاربردترین ابزار آن است و به شما امکان بازگشت، همکاری و شاخه‌بندی می‌دهد. هر پروژه‌ای، هرچقدر هم کوچک، از کنترل نسخه سود می‌برد.

## فصل ۲: انواع سیستم‌های کنترل نسخه (متمرکز vs توزیع‌شده)

### مقدمه

سیستم‌های کنترل نسخه در طول تاریخ دو معماری اصلی داشته‌اند: **متمرکز (Centralized)** و **توزیع‌شده (Distributed)**. درک این تفاوت به شما کمک می‌کند بفهمید چرا Git انقلابی بود.

### مفاهیم اساسی

**سیستم متمرکز (CVCS):**
- یک سرور مرکزی وجود دارد که تمام تاریخچه روی آن است.
- هر توسعه‌دهنده فقط یک کپی از آخرین نسخه (Working Copy) دارد.
- برای هر عملیات (commit، log، diff) باید به سرور متصل باشید.
- مثال‌ها: SVN، CVS، Perforce.

**سیستم توزیع‌شده (DVCS):**
- هر توسعه‌دهنده یک کپی **کامل** از مخزن با تمام تاریخچه دارد.
- عملیات محلی سریع‌اند و نیازی به اتصال نیست.
- سرور مرکزی فقط نقش «هماهنگ‌کننده» را دارد، نه منبع یگانه.
- مثال‌ها: Git، Mercurial.

### مقایسه و الگوهای مختلف

| ویژگی | متمرکز (SVN) | توزیع‌شده (Git) |
|-------|--------------|-----------------|
| محل تاریخچه | فقط سرور | هر کلاینت |
| سرعت عملیات | وابسته به شبکه | بسیار سریع (محلی) |
| کار آفلاین | غیرممکن | کاملاً ممکن |
| شاخه‌بندی | سنگین و کند | سبک و سریع |
| اگر سرور از دست برود | تاریخچه از بین می‌رود | هر کپی یک پشتیبان است |
| منحنی یادگیری | ساده‌تر | کمی پیچیده‌تر |

### مثال‌های عملی

فرض کنید می‌خواهید تاریخچه پروژه را ببینید:

```bash
# در Git — کاملاً محلی و سریع
git log --oneline

# در SVN — نیاز به اتصال به سرور
svn log
```

در Git حتی اگر اینترنت قطع باشد، می‌توانید commit بزنید، شاخه بسازید و تاریخچه را ببینید.

### اشکال شایع

- **اشتباه رایج**: تصور اینکه در Git «سرور مرکزی» وجود ندارد. در عمل تیم‌ها از GitHub/GitLab به عنوان مخزن مرکزی استفاده می‌کنند، اما این یک انتخاب سازمانی است، نه محدودیت فنی.

### نکات مهم (Tips & Tricks)

- درک توزیع‌شده بودن Git کلید فهم رفتارهایی مثل `fetch`، `push` و `pull` است.
- هر clone یک نسخه کامل و مستقل است؛ پس Git به‌طور طبیعی مقاوم در برابر خرابی است.

### خلاصه فصل

سیستم‌های متمرکز به یک سرور وابسته‌اند؛ سیستم‌های توزیع‌شده مثل Git، یک کپی کامل روی هر دستگاه دارند. این تفاوت باعث سرعت، کار آفلاین و مقاومت بالا در Git می‌شود.

## فصل ۳: Git چیست و چه تفاوتی با SVN دارد؟

### مقدمه

**Git** یک سیستم کنترل نسخه توزیع‌شده است که در سال ۲۰۰۵ توسط **Linus Torvalds** (خالق Linux) برای مدیریت سورس‌کد هسته Linux ساخته شد. هدف او ساخت سیستمی بود که سریع، توزیع‌شده و مقاوم باشد.

### اهمیت این موضوع

Git امروزه استاندارد صنعت است. بیش از ۹۰٪ پروژه‌های نرم‌افزاری از Git استفاده می‌کنند و پلتفرم‌هایی مثل GitHub، GitLab و Bitbucket همه حول Git ساخته شده‌اند.

### مفاهیم اساسی

تفاوت‌های کلیدی Git با SVN:

1. **توزیع‌شده بودن**: هر کپی کامل است (توضیح داده شد).
2. **ذخیره‌سازی snapshot به‌جای diff**: Git هر commit را به‌صورت یک «عکس فوری» از کل پروژه ذخیره می‌کند (نه فقط تفاوت‌ها). این باعث کارایی بالاتر می‌شود.
3. **یکپارچگی با هش**: Git از هش SHA-1 (و امروزه SHA-256) برای شناسایی هر commit استفاده می‌کند. هر تغییر، هش را تغییر می‌دهد؛ پس دستکاری تاریخچه قابل تشخیص است.
4. **شاخه‌بندی سبک**: شاخه در Git فقط یک اشاره‌گر است، پس ساخت آن تقریباً بی‌هزینه است.
5. **Staging Area**: Git یک ناحیه میانی به نام Staging دارد که در SVN وجود ندارد (در فصل‌های بعدی کامل توضیح می‌دهیم).

### مقایسه و الگوهای مختلف

| معیار | Git | SVN |
|-------|-----|-----|
| معماری | توزیع‌شده | متمرکز |
| ذخیره‌سازی | Snapshot | Diff |
| شاخه‌بندی | بسیار سبک | سنگین |
| سرعت | بالا | متوسط |
| محبوبیت امروز | غالب | در حال کاهش |

### اشکال شایع

- **اشتباه رایج**: فکر کردن Git و GitHub یکی هستند. **Git** ابزار است، **GitHub** یک سرویس میزبانی مخزن Git است.
- **اشتباه رایج**: ترس از شاخه‌بندی. در Git شاخه‌ها ارزان و بی‌خطرند.

### نکات مهم (Tips & Tricks)

- Git را به‌عنوان یک «پایگاه‌داده گراف» ببینید؛ commitها گره‌ها و والدها یال‌ها هستند.
- یاد بگیرید `git help <command>` را بزنید؛ مستندات داخلی عالی هستند.

### خلاصه فصل

Git یک DVCS سریع، توزیع‌شده و مبتنی بر snapshot است. تفاوت‌های بنیادی آن با SVN (معماری، ذخیره‌سازی، شاخه‌بندی) دلیل محبوبیت امروز آن است.

## فصل ۴: اکوسیستم Git (GitHub، GitLab، Bitbucket)

### مقدمه

Git به‌تنهایی یک ابزار خط فرمان است. برای همکاری تیمی، بازبینی کد و CI/CD، به یک **پلتفرم میزبانی** نیاز دارید. این پلتفرم‌ها Git را با امکانات اضافه‌ای مثل Pull Request، Issue، CI/CD و مدیریت دسترسی ترکیب می‌کنند.

### مفاهیم اساسی

**GitHub**: محبوب‌ترین پلتفرم، مالکیت Microsoft، خانه اکثر پروژه‌های متن‌باز. CI/CD آن GitHub Actions است.

**GitLab**: یک پلتفرم کامل DevOps با قابلیت نصب روی سرور خودتان (Self-hosted). CI/CD آن GitLab CI بسیار قدرتمند است.

**Bitbucket**: محصول Atlassian، یکپارچه با Jira و Trello. CI/CD آن Bitbucket Pipelines است.

**سایر گزینه‌ها**: Gitea، Gogs (سبک و خودمیزبان)، Azure DevOps.

### مقایسه و الگوهای مختلف

| پلتفرم | میزبانی | CI/CD | متن‌باز | مناسب برای |
|--------|---------|-------|---------|-------------|
| GitHub | ابری + Enterprise | Actions | خیر (سرویس) | متن‌باز، عمومی |
| GitLab | ابری + Self-hosted | GitLab CI | بله (CE) | سازمانی، خودمیزبان |
| Bitbucket | ابری + Server | Pipelines | خیر | تیم‌های Atlassian |
| Gitea | Self-hosted | Actions/Drone | بله | سبک، خصوصی |

### مثال‌های عملی

اتصال یک مخزن محلی به GitHub:

```bash
# ساخت مخزن محلی
git init

# افزودن فایل و commit اول
git add .
git commit -m "Initial commit"

# اتصال به مخزن راه دور
git remote add origin https://github.com/username/repo.git
git push -u origin main
```

### اشکال شایع

- **اشتباه رایج**: انتخاب پلتفرم فقط بر اساس محبوبیت، بدون توجه به نیاز سازمان (مثلاً نیاز به Self-hosting).
- **اشتباه رایج**: نادیده گرفتن مسائل امنیتی و دسترسی‌ها در مخازن عمومی.

### نکات مهم (Tips & Tricks)

- برای پروژه‌های متن‌باز، GitHub بهترین انتخاب است.
- اگر داده‌های حساس دارید یا نیاز قانونی به نگهداری داده در داخل کشور دارید، GitLab Self-hosted گزینه مناسب است.
- در این کتابچه از **GitHub** برای مثال‌ها استفاده می‌کنیم، اما مفاهیم مشترک‌اند.

### خلاصه فصل

GitHub، GitLab و Bitbucket پلتفرم‌های میزبانی Git هستند که امکانات همکاری و CI/CD اضافه می‌کنند. انتخاب بین آن‌ها به نیاز سازمان (ابر/خودمیزبان، ابزار CI/CD، هزینه) بستگی دارد.

## فصل ۵: CI/CD چیست و چرا Git + Jenkins مکمل هم‌اند؟

### مقدمه

**CI/CD** قلب توسعه نرم‌افزار مدرن است. **CI (Continuous Integration)** یعنی ادغام مکرر کد تغییرات در یک شاخه مشترک و اجرای خودکار تست‌ها. **CD** می‌تواند **Continuous Delivery** (تحویل مداوم) یا **Continuous Deployment** (استقرار مداوم) باشد.

### اهمیت این موضوع

بدون CI/CD، فرآیند ساخت، تست و استقرار نرم‌افزار دستی، کند و پرخطا است. با CI/CD، هر بار که کد را push می‌کنید، سیستم به‌طور خودکار تست‌ها را اجرا می‌کند و در صورت موفقیت، نسخه جدید را می‌سازد و مستقر می‌کند.

### مفاهیم اساسی

- **Git**: منبع حقیقت (Source of Truth). کد اینجا زندگی می‌کند.
- **Jenkins**: موتور اتوماسیون. تغییرات Git را می‌بیند و Pipeline را اجرا می‌کند.
- **Pipeline**: زنجیره‌ای از مراحل (Build → Test → Deploy).

**چرا مکمل هم‌اند؟**
Git فقط کد را نگه می‌دارد. Jenkins فقط اتوماسیون را اجرا می‌کند. اما وقتی Git تغییر جدید را ثبت می‌کند، Jenkins آن را تشخیص می‌دهد و فرآیند خودکار را شروع می‌کند. این ترکیب، ستون فقرات DevOps است.

### مقایسه و الگوهای مختلف

| مفهوم | توضیح | ابزار نمونه |
|-------|-------|-------------|
| CI | ادغام و تست مداوم | Jenkins، GitHub Actions |
| Continuous Delivery | نسخه همیشه آماده انتشار | Jenkins + Artifactory |
| Continuous Deployment | انتشار خودکار به تولید | ArgoCD، Jenkins |

### مثال‌های عملی

یک چرخه ساده:

1. توسعه‌دهنده کد را push می‌کند.
2. Git تغییر را ثبت می‌کند.
3. Jenkins (از طریق Webhook) تغییر را می‌بیند.
4. Pipeline اجرا می‌شود: نصب وابستگی → تست → Build → استقرار.
5. نتیجه به GitHub گزارش می‌شود.

### اشکال شایع

- **اشتباه رایج**: فکر کردن CI/CD فقط برای پروژه‌های بزرگ است. حتی یک پروژه کوچک هم از آن سود می‌برد.
- **اشتباه رایج**: پیاده‌سازی CI بدون تست. CI بدون تست خودکار، فقط Build خودکار است.

### نکات مهم (Tips & Tricks)

- هرچه Pipeline سریع‌تر، بازخورد سریع‌تر و کیفیت بالاتر.
- Pipeline را به‌صورت کد (Pipeline as Code) نگه دارید تا نسخه‌بندی شود.
- شکست‌های Pipeline را جدی بگیرید؛ «شکست قرمز» باید سریع رفع شود.

### خلاصه فصل

CI/CD فرآیند خودکار ادغام، تست و استقرار است. Git منبع کد و Jenkins موتور اتوماسیون است؛ ترکیب آن‌ها پایه DevOps مدرن را می‌سازد.

## فصل ۶: نقشه راه یادگیری و آماده‌سازی محیط کار

### مقدمه

حالا که مفاهیم پایه را می‌شناسید، وقت آن است که محیط کارتان را آماده کنید و بدانید مسیر پیش رو چگونه است.

### مفاهیم اساسی

**نقشه راه:**

```
پایه‌های Git → Git حرفه‌ای → مبانی CI/CD → Jenkins مقدماتی
   → Pipeline حرفه‌ای → یکپارچگی → پروژه‌های واقعی
```

**ابزارهایی که نیاز دارید:**
- **Git** (نسخه ۲.۳۰ یا بالاتر)
- **یک ادیتور** (VS Code توصیه می‌شود)
- **Java** (نسخه ۱۱ یا ۱۷) برای Jenkins
- **Docker** (برای اجرای Jenkins و پروژه‌ها)
- **حساب GitHub**

### مثال‌های عملی

بررسی نصب ابزارها:

```bash
git --version          # باید نسخه Git را نشان دهد
java -version          # باید نسخه Java را نشان دهد
docker --version       # باید نسخه Docker را نشان دهد
code --version         # نسخه VS Code
```

### اشکال شایع

- **اشتباه رایج**: پریدن مستقیم به Jenkins بدون تسلط بر Git. Jenkins بدون Git مثل ماشین بدون سوخت است.
- **اشتباه رایج**: نصب نکردن Docker و مواجهه با پیچیدگی‌های نصب دستی.

### نکات مهم (Tips & Tricks)

- یک مخزن تمرینی بسازید و همه دستورات این کتابچه را در آن اجرا کنید.
- از همان ابتدا عادت کنید Pipeline را در فایل `Jenkinsfile` نگه دارید.
- برای هر پروژه یک محیط مجازی/کانتینر جدا بسازید.

### خلاصه فصل

محیط کار شامل Git، Java، Docker و یک ادیتور است. مسیر یادگیری پیش‌رونده است: از Git شروع می‌کنیم، به CI/CD و Jenkins می‌رسیم و در نهایت پروژه‌های واقعی می‌سازیم. آماده‌اید شروع کنیم!
