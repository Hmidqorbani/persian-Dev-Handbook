## فصل ۵۰: غنی‌سازی و خلاصه‌سازی CTI

### مقدمه

**CTI** (Cyber Threat Intelligence) یعنی تبدیل دادهٔ خام تهدید به **دانش قابل اقدام**. مشکل: حجم زیاد، منابع پراکنده، و زمان کم.

AI اینجا دو کار می‌کند: **خلاصه‌سازی** و **نگاشت به TTP**.

### مفاهیم اساسی

**چهار سطح CTI**

| سطح | چه چیزی | مصرف‌کننده |
|---|---|---|
| **استراتژیک** | روند کلان | مدیریت |
| **عملیاتی** | کمپین، بازیگر | تیم امنیت |
| **تاکتیکی** | TTP | Detection engineer |
| **فنی** | IOC | SIEM، فایروال |

**نکته:** AI بیشتر در سطح **عملیاتی و تاکتیکی** کمک می‌کند. سطح استراتژیک، نیاز به قضاوت انسانی دارد.

**چهار کار CTI**

| کار | ورودی | خروجی |
|---|---|---|
| **جمع‌آوری** | گزارش، فید | دادهٔ خام |
| **نرمال‌سازی** | قالب‌های مختلف | ساختار یکسان |
| **تحلیل** | داده | ارتباط، معنا |
| **انتشار** | تحلیل | گزارش قابل اقدام |

**مفهوم «IOC به TTP»**

| سطح | دوام | ارزش |
|---|---|---|
| **IOC** (IP، hash) | ساعت تا روز | کم |
| **TTP** | ماه تا سال | **بالا** |

**درس:** AI می‌تواند از IOC به TTP برسد — و این، ارزشمندترین کارش در CTI است.

**مفهوم «خلاصهٔ قابل اقدام»**

خلاصهٔ خوب، چهار بخش دارد:

```text
۱) چه اتفاقی افتاد؟ (۲ جمله)
۲) چه کسی؟ (بازیگر، اگر شناخته شده)
۳) چه چیزی مهم است برای ما؟ (ارتباط با دارایی‌های ما)
۴) چه اقدامی؟ (detection، patch، آموزش)
```

**نکته:** خلاصهٔ بدون بخش ۳ و ۴، فقط «خبر» است، نه «اطلاعات تهدید».

### مثال‌های عملی

**Lab Scenario 50-A: پرامپت خلاصهٔ CTI**

```text
[نقش]
تو تحلیلگر CTI هستی.

[زمینه]
گزارش زیر از یک فروشندهٔ تهدید است. سازمان ما: فروشگاه آنلاین،
۳۰۰ کارمند، زیرساخت ابری.

[وظیفه]
خروجی را در چهار بخش بده:
۱) خلاصه (۲ جمله)
۲) TTPها (نگاشت به ATT&CK، فقط آنچه در گزارش آمده)
۳) ارتباط با سازمان ما (کدام دارایی؟ چرا؟)
۴) سه اقدام پیشنهادی (detection / patch / آموزش)

[محدودیت]
- فقط از گزارش. اگر چیزی نیست، «ذکر نشده».
- هیچ IOC یا TTP حدسی نساز.
- اگر نگاشت مطمئن نیستی، بنویس «نگاشت نامشخص».

[قالب]
مارک‌داون با چهار هدر

[گزارش]
[متن]
```

**Lab Scenario 50-B: نگاشت به ATT&CK**

```python
"""
نگاشت سادهٔ توصیف به تاکتیک — نمونهٔ آموزشی
توجه: این یک جدول کلیدواژه است، نه مدل. برای تولید، از مدل با
مجموعهٔ مرجع و بازبینی انسانی استفاده کن.
"""
KEYWORDS = {
    "spearphishing": ("Initial Access", "T1566"),
    "powershell": ("Execution", "T1059.001"),
    "scheduled task": ("Persistence", "T1053.005"),
    "credential dumping": ("Credential Access", "T1003"),
    "lateral movement": ("Lateral Movement", "TA0008"),
    "exfiltration": ("Exfiltration", "TA0010"),
    "encrypt": ("Impact", "T1486"),
}

def map_ttps(text: str) -> list[tuple[str, str, str]]:
    low = text.lower()
    return [(k, v[0], v[1]) for k, v in KEYWORDS.items() if k in low]

report = "The actor used spearphishing, then PowerShell for execution, and finally exfiltration."
for kw, tactic, tid in map_ttps(report):
    print(f"{kw:20s} → {tactic:18s} {tid}")
```

**هشدار:** نگاشت کلیدواژه‌ای، **پرخطا** است. در تولید، از مدل با مجموعهٔ مرجع و بازبینی انسانی استفاده کن.

**Lab Scenario 50-C: اولویت‌بندی بر اساس ارتباط**

| تهدید | ارتباط با ما | اولویت |
|---|---|---|
| کمپین علیه فروشگاه‌های آنلاین | بالا | 🔴 |
| کمپین علیه زیرساخت انرژی | کم | 🟢 |
| TTP مشترک با بخش ما | متوسط | 🟠 |
| بازیگر با انگیزهٔ مالی | بالا | 🔴 |

**درس:** CTI بدون **زمینهٔ سازمان**، فقط سرگرمی است.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه منبع CTI**

| منبع | کیفیت | هزینه |
|---|---|---|
| **تجاری** | بالا | زیاد |
| **جامعه (OSINT)** | متغیر | کم |
| **داخلی** | بالا (مرتبط) | متوسط |

**مقایسهٔ دو رویکرد**

| | خلاصهٔ خودکار | تحلیل انسانی |
|---|---|---|
| سرعت | بالا | کم |
| عمق | کم | بالا |
| مناسب | غربال | تصمیم |

### اشکال شایع

**اشتباه ۱: خلاصه بدون اقدام**
«خبر» است، نه CTI.

**اشتباه ۲: نگاشت حدسی**
TTP جعلی، بدتر از نبود TTP.

**اشتباه ۳: نادیده گرفتن زمینهٔ سازمان**
همه‌چیز «مهم» می‌شود.

**اشتباه ۴: اعتماد به IOC تنها**
دوام کم.

**اشتباه ۵: نبود بازبینی انسانی**
خلاصهٔ غلط، تصمیم غلط.

### نکات مهم (Tips & Tricks)

- **چهار بخش خلاصه** را همیشه بخواه.
- **«نگاشت نامشخص»** را مجاز کن.
- **زمینهٔ سازمان** را در پرامپت بده.
- **IOC را به TTP تبدیل کن.**
- **هر خلاصه، بازبینی انسانی.**

### خلاصه فصل

- چهار سطح CTI؛ AI در **عملیاتی/تاکتیکی** کمک می‌کند.
- **TTP** ارزش بیشتری از IOC دارد.
- خلاصهٔ خوب: **چه، که، اهمیت، اقدام**.
- نگاشت حدسی، خطرناک است.
- زمینهٔ سازمان، فیلتر اصلی.

## فصل ۵۱: مهندسی تشخیص با AI

### مقدمه

**Detection Engineering** یعنی نوشتن قاعده‌ای که تهدید را با دقت و کم‌نویز تشخیص بدهد. این کار، ترکیبی از هنر و علم است — و AI می‌تواند در بخش‌های مکانیکی کمک کند.

### مفاهیم اساسی

**چرخهٔ تشخیص**

```
۱. انتخاب تهدید (از CTI)
۲. طراحی قاعده
۳. آزمون با داده
۴. تنظیم آستانه
۵. استقرار
۶. پایش و بهبود
```

**چهار جای کمک AI**

| مرحله | کمک |
|---|---|
| **۱. انتخاب** | اولویت‌بندی TTP |
| **۲. طراحی** | پیشنهاد منطق |
| **۳. آزمون** | تولید دادهٔ تست |
| **۶. بهبود** | تحلیل FP |

**مفهوم «قاعدهٔ خوب»**

| ویژگی | معیار |
|---|---|
| **دقت** | FP کم |
| **حساسیت** | FN کم |
| **قابل توضیح** | تحلیلگر می‌فهمد |
| **قابل نگهداری** | تغییر آسان |

**نکته:** AI در «طراحی» خوب است، ولی **قاعدهٔ نهایی** باید قابل خواندن و بازبینی باشد. قاعدهٔ تولیدشده که کسی نمی‌فهمد، بدهی است.

**مفهوم «دادهٔ تست»**

| نوع | کاربرد |
|---|---|
| **مثبت** | باید هشدار بدهد |
| **منفی** | نباید هشدار بدهد |
| **مرزی** | سخت‌ترین |

**AI می‌تواند دادهٔ تست تولید کند** — و این، یکی از کم‌ریسک‌ترین کاربردهاست.

### مثال‌های عملی

**Lab Scenario 51-A: تولید قاعده از TTP**

```text
[نقش]
تو detection engineer هستی.

[زمینه]
TTP: T1053.005 — Scheduled Task/Job (Windows)
محیط: Windows Server 2019/2022، Sysmon، Splunk

[وظیفه]
۱) سه منطق تشخیص پیشنهاد بده (از ساده به پیچیده)
۲) برای هر کدام: فیلدهای لازم، نویز مورد انتظار، FP محتمل
۳) برای هر کدام، دو نمونهٔ دادهٔ تست (مثبت/منفی) پیشنهاد بده

[محدودیت]
- منطق را به‌صورت شبه‌کد یا SPL قابل خواندن بده.
- هیچ قاعده‌ای که به دادهٔ غیرموجود وابسته است نده.
- FP محتمل را صادقانه بگو، نه «نویز کم».

[قالب]
سه بخش، هر کدام: منطق، فیلدها، نویز، FP، تست
```

**چرا این کار می‌کند؟** چون AI، الگوهای رایج را می‌شناسد — و تو **انتخاب و بازبینی** می‌کنی.

**Lab Scenario 51-B: نمونهٔ قاعده**

```text
# SPL نمونه — شبه‌کد، نیاز به تطبیق با محیط
index=windows sourcetype=WinEventLog:Security EventCode=4698
| eval task_name=coalesce(TaskName, 'unknown')
| where NOT match(task_name, "(?i)(microsoft|windows|update|onedrive)")
| stats count min(_time) as first_seen by ComputerName, task_name, SubjectUserName
| where count < 3
```

**تحلیل:**

| بخش | چرا |
|---|---|
| `EventCode=4698` | ایجاد task |
| `NOT match(...)` | حذف taskهای مشروع |
| `count < 3` | task نادر، مشکوک‌تر |

**نکته:** قاعدهٔ نهایی، باید **قابل خواندن** برای تحلیلگر باشد.

**Lab Scenario 51-C: ارزیابی قاعده**

```python
"""
محاسبهٔ معیارهای قاعده
"""
def evaluate(tp: int, fp: int, fn: int, tn: int) -> dict:
    precision = tp / (tp + fp) if (tp + fp) else 0
    recall = tp / (tp + fn) if (tp + fn) else 0
    f1 = 2 * precision * recall / (precision + recall) if (precision + recall) else 0
    fpr = fp / (fp + tn) if (fp + tn) else 0
    return {
        "precision": round(precision, 3),
        "recall": round(recall, 3),
        "f1": round(f1, 3),
        "fpr": round(fpr, 4),
    }

print(evaluate(tp=80, fp=40, fn=20, tn=9860))
print("قاعدهٔ قابل قبول برای SOC: recall بالا، fpr < 0.01")
```

### مقایسه و الگوهای مختلف

**مقایسهٔ سه نوع قاعده**

| نوع | مثال | نگهداری |
|---|---|---|
| **امضا** | hash، رشته | کم |
| **رفتار** | توالی | متوسط |
| **ناهنجاری** | انحراف | زیاد |

**مقایسهٔ دو رویکرد**

| | AI طراحی می‌کند | انسان طراحی می‌کند |
|---|---|---|
| سرعت | بالا | کم |
| کیفیت اولیه | متوسط | بالا |
| نیاز به بازبینی | زیاد | کم |

### اشکال شایع

**اشتباه ۱: استقرار قاعدهٔ تولیدشده بدون آزمون**
FP زیاد، خستگی تحلیلگر.

**اشتباه ۲: قاعدهٔ غیرقابل خواندن**
کسی نمی‌تواند نگه‌داری کند.

**اشتباه ۳: نادیده گرفتن FP**
قاعدهٔ «همه‌چیز را بگیر» بی‌فایده است.

**اشتباه ۴: نبود دادهٔ تست**
نمی‌دانی کار می‌کند یا نه.

**اشتباه ۵: نبود مالک**
قاعدهٔ بدون مالک، فراموش می‌شود.

### نکات مهم (Tips & Tricks)

- **AI پیشنهاد، انسان تصمیم.**
- **دادهٔ تست، بخشی از قاعده است.**
- **FP را صادقانه گزارش کن.**
- **قاعدهٔ قابل خواندن، الزامی.**
- **هر قاعده: مالک، تاریخ، بازبینی.**

### خلاصه فصل

- چرخهٔ شش‌مرحله‌ای تشخیص.
- AI در **طراحی و تست** کمک می‌کند.
- قاعدهٔ نهایی باید **قابل خواندن** باشد.
- دادهٔ تست مثبت/منفی/مرزی.
- هر قاعده: مالک و بازبینی.

## فصل ۵۲: تحلیل لاگ و تولید کوئری

### مقدمه

تحلیل لاگ، کاری زمان‌بر و تکراری است: نوشتن کوئری، خواندن نتیجه، اصلاح. AI می‌تواند این چرخه را کوتاه کند — با محدودیت‌های مشخص.

### مفاهیم اساسی

**سه کاربرد**

| کاربرد | مثال | ریسک |
|---|---|---|
| **تولید کوئری** | NL → SPL/KQL | خطای نحوی |
| **خلاصهٔ نتیجه** | ۱۰۰۰ خط → ۵ نکته | توهم |
| **تفسیر** | «این خطا یعنی چه؟» | تفسیر غلط |

**مفهوم «زبان طبیعی به کوئری» (NL2Query)**

| مزیت | عیب |
|---|---|
| سرعت | خطای نحوی |
| کاهش مانع یادگیری | منطق اشتباه |

**نکتهٔ حیاتی:** کوئری تولیدشده باید **قبل از اجرا** بازبینی شود. یک `| delete` یا `| outputlookup` می‌تواند داده را تغییر دهد.

**مفهوم «حالت فقط خواندن»**

| کنترل | چرا |
|---|---|
| اتصال با نقش read-only | جلوگیری از تغییر |
| محدودیت بازهٔ زمانی | هزینه |
| سقف نتیجه | عملکرد |

**مفهوم «خلاصهٔ لاگ»**

| ورودی | خروجی مطلوب |
|---|---|
| ۵۰۰۰ خط | ۵ الگوی اصلی + تعداد + نمونه |
| خطاهای متنوع | گروه‌بندی بر اساس پیام |
| توالی | ترتیب زمانی رخداد |

### مثال‌های عملی

**Lab Scenario 52-A: تولید کوئری**

```text
[نقش]
تو مهندس SIEM هستی.

[زمینه]
پلتفرم: Splunk. ایندکس: windows.
هدف: پیدا کردن تلاش‌های ناموفق ورود که بعد از ۵ بار، موفق شده‌اند.

[وظیفه]
۱) کوئری SPL بنویس
۲) هر بخش را در یک خط توضیح بده
۳) دو خطای رایج این کوئری را بگو
۴) یک نسخهٔ ساده‌تر (اگر ممکن) پیشنهاد بده

[محدودیت]
- فقط دستورهای خواندنی. هیچ دستور تغییردهنده (delete/outputlookup/collect).
- از فیلدهای استاندارد Windows Security استفاده کن.
- بازهٔ زمانی را پارامتر کن، نه ثابت.

[قالب]
کد + توضیح + خطاها
```

**Lab Scenario 52-B: بازبینی کوئری قبل از اجرا**

```python
"""
بازبینی سادهٔ کوئری — جلوگیری از دستورهای خطرناک
"""
import re

DANGEROUS = [
    r"\|\s*delete\b",
    r"\|\s*outputlookup\b",
    r"\|\s*collect\b",
    r"\|\s*script\b",
    r"\|\s*sendalert\b",
]

def review(query: str) -> tuple[bool, list[str]]:
    issues = [p for p in DANGEROUS if re.search(p, query, re.I)]
    return (len(issues) == 0, issues)

tests = [
    'index=windows EventCode=4625 | stats count by src',
    'index=windows | delete',
    'index=windows | outputlookup evil.csv',
]
for q in tests:
    ok, issues = review(q)
    print(f"{'OK ' if ok else 'BLOCK'} | {issues} | {q}")
```

**درس:** یک فیلتر ساده، جلوی فاجعه را می‌گیرد.

**Lab Scenario 52-C: خلاصهٔ لاگ**

```text
[دستور]
این ۲۰۰ خط لاگ را تحلیل کن.

خروجی:
۱) پنج الگوی اصلی (پیام نرمال‌شده + تعداد)
۲) سه خطای نادر (با شماره خط)
۳) یک توالی زمانی مشکوک (اگر هست)
۴) سه سؤال که برای ریشه‌یابی باید بپرسی

محدودیت:
- هیچ خطی را بازنویسی نکن؛ نقل‌قول کوتاه بده.
- اگر الگویی کمتر از ۳ بار تکرار شده، «نادر» است.
- هیچ تفسیری دربارهٔ علت نده، مگر با شاهد در لاگ.
```

**نکته:** «هیچ تفسیری بدون شاهد» — بهترین محافظ در برابر توهم.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه رویکرد**

| رویکرد | مزیت | عیب |
|---|---|---|
| **دستی** | کنترل | کند |
| **AI-assisted** ⭐ | سرعت | نیاز به بازبینی |
| **AI-automated** | سرعت بالا | ریسک بالا |

**مقایسهٔ دو نوع کوئری**

| | ساده | پیچیده |
|---|---|---|
| خطا | کم | زیاد |
| خوانایی | بالا | کم |
| توصیه | شروع | بعد از آزمون |

### اشکال شایع

**اشتباه ۱: اجرای کوئری بدون بازبینی**
دستور مخرب یا سنگین.

## فصل ۵۳: کمک به تحلیل بدافزار و رفتار

### مقدمه

تحلیل بدافزار، تخصصی و پرریسک است. AI می‌تواند در بخش‌های **کم‌ریسک** کمک کند — ولی جای sandbox و تحلیل دستی را نمی‌گیرد.

### مفاهیم اساسی

**چهار سطح تحلیل**

| سطح | چه چیزی | AI |
|---|---|---|
| **سطح ۱: هش** | hash، نام | ✅ کمک |
| **سطح ۲: رشته** | strings، import | ✅ کمک |
| **سطح ۳: رفتار** | sandbox | ⚠️ تفسیر |
| **سطح ۴: کد** | disassembly | ❌ تخصصی |

**نکته:** AI در سطح ۱ و ۲ خوب است، در سطح ۳ فقط **تفسیر** می‌کند، و در سطح ۴ جای متخصص را نمی‌گیرد.

**مفهوم «خطر اجرا»**

| خطر | کنترل |
|---|---|
| اجرای نمونه | sandbox جدا |
| نشت نمونه | محیط ایزوله |
| آلودگی | عدم اتصال شبکه |

**قاعده:** هرگز نمونه را روی سیستم تحلیل اجرا نکن. AI هم اجرا نمی‌کند — ولی توصیه‌اش می‌تواند خطرناک باشد.

**مفهوم «IOC از تحلیل»**

| نوع | مثال | دوام |
|---|---|---|
| **hash** | SHA256 | کم |
| **دامنه** | C2 | متوسط |
| **TTP** | persistence | بالا |

**AI می‌تواند از رشته‌ها و رفتار، IOC پیشنهاد بدهد** — ولی هر IOC باید **تأیید** شود.

### مثال‌های عملی

**Lab Scenario 53-A: تحلیل رشته‌ها**

```text
[نقش]
تو تحلیلگر بدافزار هستی.

[زمینه]
این خروجی `strings` از یک نمونهٔ ناشناس است (محیط sandbox، بدون اجرا).

[وظیفه]
۱) پنج رشتهٔ مشکوک را جدا کن (URL، IP، مسیر، کلید رجیستری)
۲) برای هر کدام بگو چرا مشکوک است
۳) سه فرضیهٔ رفتار (بدون قطعیت)
۴) سه IOC پیشنهادی برای بررسی

[محدودیت]
- فقط از رشته‌های داده‌شده. هیچ IOC نساز.
- فرضیه، نه نتیجه.
- اگر رشته‌ای خوانا نیست، ذکر کن.

[خروجی]
جدول + سه فرضیه
```

**Lab Scenario 53-B: طبقه‌بندی IOC**

```python
"""
استخراج و طبقه‌بندی IOC از متن — نمونهٔ منطق
"""
import re

PATTERNS = {
    "url":    r"https?://[^\s\"'<>]+",
    "ipv4":   r"\b(?:\d{1,3}\.){3}\d{1,3}\b",
    "domain": r"\b[a-z0-9-]+\.(?:com|net|org|io|ru|cn)\b",
    "sha256": r"\b[a-f0-9]{64}\b",
    "regkey": r"HKEY_[A-Z_]+\\[^\s\"']+",
}

def extract(text: str) -> dict[str, list[str]]:
    out = {}
    for name, pat in PATTERNS.items():
        found = sorted(set(re.findall(pat, text, re.I)))
        if found:
            out[name] = found[:10]
    return out

sample = """
GET http://evil.example/c2
connect 203.0.113.45
HKEY_CURRENT_USER\\Software\\Microsoft\\Windows\\CurrentVersion\\Run
hash 3f786850e387550fdab836ed7e6dc881de23001b...
"""
import json
print(json.dumps(extract(sample), indent=2, ensure_ascii=False))
```

**نکته:** `203.0.113.x` یک محدودهٔ **مستندات** است (RFC 5737) — در مثال‌ها استفاده از آن درست است، نه IP واقعی.

**Lab Scenario 53-C: تفسیر رفتار sandbox**

| رفتار | تفسیر ممکن | تأیید لازم |
|---|---|---|
| ایجاد task | persistence | مسیر، دستور |
| تماس با IP | C2 | reputation |
| رمزگذاری فایل | ransomware | پسوند، کلید |
| تزریق به پروسه | evasion | هدف |

**درس:** هر رفتار، **چند تفسیر** دارد. AI یکی را پیشنهاد می‌دهد؛ تو باید alternatives را ببینی.

### مقایسه و الگوهای مختلف

**مقایسهٔ دو رویکرد**

| | AI-assisted | تحلیل دستی |
|---|---|---|
| سرعت | بالا | کم |
| عمق | سطح ۱–۲ | همه |
| ریسک | تفسیر غلط | زمان |

**مقایسهٔ سه ابزار**

| ابزار | کاربرد |
|---|---|
| **Sandbox** | رفتار |
| **YARA** | امضا |
| **AI** | خلاصه و تفسیر |

### اشکال شایع

**اشتباه ۱: اجرای نمونه برای «تست»**
خطر واقعی.

**اشتباه ۲: اعتماد به فرضیهٔ AI**
بدون تأیید.

**اشتباه ۳: ساخت IOC از حدس**
آلودگی پایگاه داده.

**اشتباه ۴: نادیده گرفتن سطح ۴**
کد، نیاز به متخصص.

**اشتباه ۵: نبود ایزولاسیون**
آلودگی محیط تحلیل.

### نکات مهم (Tips & Tricks)

- **هرگز نمونه را اجرا نکن.**
- **فرضیه را از نتیجه جدا کن.**
- **IOC را تأیید کن، قبل از انتشار.**
- **از IP مستندات (RFC 5737) در مثال استفاده کن.**
- **سطح ۴ را به متخصص بسپار.**

### خلاصه فصل

- چهار سطح تحلیل؛ AI در **۱ و ۲** کمک می‌کند.
- sandbox، جایگزین ندارد.
- **فرضیه ≠ نتیجه**.
- IOC باید تأیید شود.
- ایزولاسیون، الزامی.

## فصل ۵۴: ریسک توهم در CTI — و راستی‌آزمایی

### مقدمه

در CTI، توهم خطرناک‌تر از حوزه‌های دیگر است. چرا؟ چون خروجی به **تصمیم امنیتی** تبدیل می‌شود: مسدودسازی، هشدار، تغییر قاعده.

یک TTP جعلی، می‌تواند هفته‌ها وقت تیم را بگیرد. یک IOC جعلی، می‌تواند ترافیک مشروع را مسدود کند.

### مفاهیم اساسی

**چهار نوع توهم در CTI**

| نوع | مثال | اثر |
|---|---|---|
| **IOC جعلی** | IP/hash ساختگی | مسدودسازی اشتباه |
| **TTP جعلی** | نگاشت نادرست | قاعدهٔ بی‌فایده |
| **بازیگر جعلی** | انتساب نادرست | تصمیم اشتباه |
| **منبع جعلی** | گزارش ناموجود | اعتبار از دست |

**مفهوم «عدم‌تقارن هزینه»**

| خطا | هزینه |
|---|---|
| **IOC جعلی (FP)** | مسدودسازی مشروع |
| **IOC ازدست‌رفته (FN)** | نفوذ |

**نکته:** در CTI، FP و FN **هر دو** گران‌اند. نمی‌توان یکی را قربانی کرد.

**چهار کنترل**

| کنترل | چطور |
|---|---|
| **الزام منبع** | هر ادعا، منبع |
| **مسیر «نامشخص»** | مجاز بودن عدم‌قطعیت |
| **تأیید دوگانه** | IOC در دو منبع مستقل |
| **بازبینی انسانی** | قبل از انتشار |

**مفهوم «اعتبار منبع»**

| منبع | اعتبار |
|---|---|
| **CISA/CERT** | بالا |
| **فروشندهٔ معتبر** | بالا |
| **تحلیل داخلی** | بالا (مرتبط) |
| **وبلاگ ناشناس** | کم |
| **مدل زبانی** | **صفر** (بدون منبع) |

**درس:** مدل زبانی، **منبع** نیست. ابزار **خلاصه‌سازی** است.

### مثال‌های عملی

**Lab Scenario 54-A: پرامپت با استناد اجباری**

```text
قواعد سخت:
۱) هر IOC (IP، دامنه، hash) باید عیناً از متن گزارش باشد.
۲) اگر IOC در متن نیست، ننویس. حدس نزن.
۳) برای هر TTP، جملهٔ مرجع را نقل کن (حداکثر ۱۵ کلمه).
۴) اگر نگاشت مطمئن نیستی: «نگاشت نامشخص».
۵) در پایان، بخش «ادعاهای بدون منبع» را جدا بنویس.

خروجی:
- IOCها (فقط از متن)
- TTPها + نقل‌قول
- ادعاهای بدون منبع
```

**نکته:** بند ۵، شفافیت می‌سازد. مدل مجبور می‌شود اعتراف کند.

**Lab Scenario 54-B: تأیید دوگانه IOC**

```python
"""
تأیید IOC در دو منبع مستقل — منطق ساده
"""
from dataclasses import dataclass

@dataclass
class Indicator:
    value: str
    sources: set[str]

def confidence(ind: Indicator) -> str:
    n = len(ind.sources)
    if n >= 2:
        return "بالا (۲+ منبع)"
    if n == 1:
        return "متوسط (تک‌منبع)"
    return "صفر"

items = [
    Indicator("203.0.113.45", {"vendor-a", "cisa"}),
    Indicator("evil.example", {"vendor-a"}),
    Indicator("deadbeef" * 8, set()),
]

for i in items:
    print(f"{i.value[:24]:26s} {confidence(i)}")
```

**درس:** تک‌منبع = متوسط. برای مسدودسازی خودکار، دو منبع لازم است.

**Lab Scenario 54-C: چک‌لیست انتشار**

```markdown
□ هر IOC در متن منبع وجود دارد
□ هر TTP، نقل‌قول مرجع دارد
□ منابع نامشخص، علامت‌گذاری شده
□ IOCها در دو منبع تأیید شده (برای مسدودسازی)
□ بازبین انسانی، تأیید کرده
□ تاریخ انقضا دارد
```

### مقایسه و الگوهای مختلف

**مقایسهٔ سه سطح اطمینان**

| سطح | معنا | اقدام |
|---|---|---|
| **بالا** | ۲+ منبع | مسدودسازی |
| **متوسط** | ۱ منبع | پایش |
| **پایین** | بدون منبع | بررسی |

**مقایسهٔ دو رویکرد**

| | سرعت | دقت |
|---|---|---|
| انتشار سریع | بالا | کم |
| تأیید دوگانه | کم | بالا |

### اشکال شایع

**اشتباه ۱: IOC از حافظهٔ مدل**
مدل، IP واقعی را «یادش» نیست.

**اشتباه ۲: نگاشت خوش‌بینانه**
هر تکنیک، شبیه یک TTP.

**اشتباه ۳: نبود تاریخ انقضا**
IOC قدیمی، نویز.

**اشتباه ۴: مسدودسازی تک‌منبع**
FP گران.

**اشتباه ۵: نبود بازبینی**
انتشار خطا در مقیاس.

### نکات مهم (Tips & Tricks)

- **«اگر نیست، ننویس»** — بهترین قاعده.
- **بخش «بدون منبع» را همیشه بخواه.**
- **تأیید دوگانه برای مسدودسازی.**
- **تاریخ انقضا برای هر IOC.**
- **مدل، منبع نیست.**

### خلاصه فصل

- چهار نوع توهم: **IOC، TTP، بازیگر، منبع**.
- FP و FN، هر دو گران.
- چهار کنترل: **منبع، نامشخص، تأیید دوگانه، بازبینی**.
- مدل زبانی، منبع صفر است.
- IOC بدون تاریخ انقضا، نویز است.
