## فصل ۷۹: ارزیابی ریسک AI — روش‌ها

### مقدمه

ارزیابی ریسک AI، ترکیبی از دو چیز است: **ریسک سنتی** (محرمانگی، یکپارچگی، دسترس‌پذیری) و **ریسک اختصاصی AI** (سوگیری، توهم، خودمختاری، شفافیت).

این فصل، روش‌های عملی را می‌دهد.

### مفاهیم اساسی

**پنج بُعد ریسک AI**

| بُعد | پرسش | مثال |
|---|---|---|
| **فنی** | آیا سیستم کار می‌کند؟ | خطا، توهم |
| **امنیتی** | آیا می‌شود شکست؟ | Injection، نشت |
| **اخلاقی** | آیا منصفانه است؟ | سوگیری |
| **حقوقی** | آیا قانونی است؟ | GDPR، AI Act |
| **عملیاتی** | آیا قابل اداره است؟ | هزینه، وابستگی |

**سه روش ارزیابی**

| روش | مناسب | خروجی |
|---|---|---|
| **چک‌لیست** | شروع سریع | فهرست شکاف |
| **ماتریس ریسک** | اکثر موارد | اولویت |
| **سناریومحور** | سیستم پیچیده | تحلیل عمیق |

**ماتریس ریسک**

```
        اثر
       کم  متوسط  بالا
احتمال
بالا   🟠   🔴    🔴
متوسط  🟢   🟠    🔴
کم     🟢   🟢    🟠
```

**نکته:** در AI، «اثر» باید **اثر بر افراد** را هم شامل شود، نه فقط سازمان.

**مفهوم «ارزیابی اثر بر افراد»**

```text
□ چه کسانی متأثر می‌شوند؟
□ چه حقوقی ممکن است نقض شود؟
□ گروه آسیب‌پذیر خاص؟
□ اثر برگشت‌پذیر است؟
□ مسیر اعتراض وجود دارد؟
```

**این بخش، تفاوت ارزیابی AI با ارزیابی IT است.**

**روش سناریومحور**

```text
۱. سناریو را بنویس (چه کسی، چه کاری، چه زمانی)
۲. زنجیرهٔ اثر را بکش
۳. نقاط مداخله را مشخص کن
۴. کنترل را به هر نقطه وصل کن
```

**Lab Scenario 79-C: محاسبهٔ ریسک**

```python
"""
امتیازدهی ریسک با وزن‌های قابل تنظیم
"""
WEIGHTS = {"prob": 0.4, "impact": 0.4, "detectability": 0.2}

def score(prob: int, impact: int, detectability: int) -> float:
    """prob/impact: 1..5 ؛ detectability: 1 (سخت) .. 5 (آسان)"""
    s = (prob * WEIGHTS["prob"]
         + impact * WEIGHTS["impact"]
         + (6 - detectability) * WEIGHTS["detectability"])
    return round(s, 2)

def level(s: float) -> str:
    return "🔴 بالا" if s >= 4 else ("🟠 متوسط" if s >= 2.5 else "🟢 کم")

risks = [
    ("R1 پاسخ نادرست", 4, 3, 4),
    ("R2 نشت داده", 3, 5, 2),
    ("R3 Injection", 3, 5, 2),
    ("R6 هزینه", 5, 2, 5),
]
for name, p, i, d in sorted(risks, key=lambda r: score(r[1], r[2], r[3]), reverse=True):
    s = score(p, i, d)
    print(f"{name:20s} {s:.2f} {level(s)}")
```

**نکته:** «قابلیت تشخیص» (detectability) مهم است: ریسکی که سخت تشخیص داده می‌شود، خطرناک‌تر است.

- زنجیرهٔ اثر، نقاط مداخله را نشان می‌دهد.
- قابلیت تشخیص، ضریب ریسک است.

## فصل ۸۰: ثبت ریسک و راهبردهای درمان

### مقدمه

ارزیابی بدون **ثبت**، فراموش می‌شود. و ثبت بدون **درمان**، فهرست آرزوست.

### مفاهیم اساسی

**ساختار ثبت ریسک**

| ستون | مثال |
|---|---|
| شناسه | R-001 |
| عنوان | نشت داده در پرامپت |
| دسته | امنیتی |
| احتمال | متوسط |
| اثر | بالا |
| سطح | 🔴 |
| کنترل موجود | فیلتر PII |
| شکاف | فیلتر ناقص |
| اقدام | تکمیل فیلتر |
| مالک | تیم امنیت |
| مهلت | ۱۴۰۴/۱۰/۰۱ |
| ریسک باقی‌مانده | 🟠 |

**چهار راهبرد درمان**

| راهبرد | چه وقت | مثال |
|---|---|---|
| **کاهش (Mitigate)** | قابل کنترل | Guardrail، بازبینی |
| **انتقال (Transfer)** | مالی | بیمه، قرارداد |
| **پذیرش (Accept)** | کم، مستند | ثبت + پایش |
| **اجتناب (Avoid)** | غیرقابل قبول | حذف قابلیت |

**مفهوم «ریسک باقی‌مانده»**

```
ریسک اولیه − اثر کنترل = ریسک باقی‌مانده
```

**اگر ریسک باقی‌مانده بالاتر از آستانه است، کنترل کافی نیست.**

**مفهوم «پذیرش مستند»**

پذیرش ریسک، باید **مکتوب** باشد:

```text
ریسک: R-007 (هزینهٔ غیرقابل پیش‌بینی)
سطح: 🟢 کم
تصمیم: پذیرش
دلیل: سقف مصرف تعیین شده؛ حداکثر ضرر قابل تحمل است.
تأیید: [نام، نقش، تاریخ]
بازبینی: ۶ ماه
```

**بدون این سند، «پذیرش» یعنی «فراموشی».**

**مفهوم «آستانهٔ تحمل»**

| سطح | آستانهٔ نمونه |
|---|---|
| نرخ توهم | < ۲٪ (محتوای بیرونی) |
| شکاف انصاف | < ۰٫۱۰ |
| زمان تشخیص رخداد | < ۲۴ ساعت |
| پوشش بازبینی پرریسک | ۱۰۰٪ |

### مثال‌های عملی

**Lab Scenario 80-A: ثبت ریسک کامل**

```markdown
# ثبت ریسک — دستیار تیکت

| ID | ریسک | سطح | کنترل | شکاف | اقدام | مالک | مهلت | باقی‌مانده |
|---|---|---|---|---|---|---|---|---|
| R-001 | نشت داده در پرامپت | 🔴 | فیلتر PII | ناقص | تکمیل regex + آموزش | امنیت | ۱۰/۰۱ | 🟠 |
| R-002 | Injection غیرمستقیم | 🔴 | جداسازی | فقط ورودی | فیلتر سند | محتوا | ۱۰/۱۵ | 🟠 |
| R-003 | پاسخ نادرست | 🔴 | بازبینی ۲۵٪ | نمونه‌گیری کم | افزایش به ۵۰٪ | سرپرست | ۰۹/۳۰ | 🟠 |
| R-004 | سوگیری | 🟠 | آزمون ماهانه | آزمون سطحی | آزمون تفکیکی | انطباق | ۱۱/۰۱ | 🟢 |
| R-005 | وابستگی فروشنده | 🟠 | قرارداد | بدون جایگزین | تست مدل جایگزین | IT | ۱۲/۰۱ | 🟢 |
| R-006 | هزینه | 🟢 | سقف مصرف | — | پذیرش مستند | مالی | — | 🟢 |
```

**Lab Scenario 80-B: محاسبهٔ باقی‌مانده**

```python
"""
محاسبهٔ ریسک باقی‌مانده
"""
def residual(initial: float, control_effect: float) -> float:
    """control_effect: 0..1 (۱ = حذف کامل)"""
    return round(initial * (1 - control_effect), 2)

def verdict(res: float, threshold: float = 3.0) -> str:
    return "قابل قبول" if res <= threshold else "کنترل ناکافی"

cases = [
    ("R-001", 4.2, 0.5),
    ("R-002", 4.0, 0.3),
    ("R-003", 3.8, 0.6),
]
for name, init, eff in cases:
    r = residual(init, eff)
    print(f"{name} اولیه={init} اثر={eff:.0%} → باقی‌مانده={r} | {verdict(r)}")
```

```markdown
| آموزش ۱ ساعته | HR | ۱۰/۲۰ | حضور |
| بازبینی اثر | امنیت | ۱۱/۰۱ | گزارش |
```

## فصل ۸۱: ریسک ثالث و ارزیابی فروشنده

### مقدمه

در AI، بیشتر قابلیت از فروشنده می‌آید — و بیشتر ریسک هم. این فصل، چارچوب ارزیابی را می‌دهد، با تمرکز بر آنچه **واقعاً** تفاوت می‌سازد.

### مفاهیم اساسی

**پنج بُعد**

| بُعد | وزن | پرسش |
|---|---|---|
| **داده و حریم خصوصی** | 🔴 | آموزش روی دادهٔ ما؟ |
| **امنیت** | 🔴 | گواهی، کنترل، رخداد |
| **انطباق** | 🟠 | DPA، منطقه، زیرپردازنده |
| **قابلیت** | 🟠 | برای کار ما کافی است؟ |
| **تداوم** | 🟢 | طرح خروج |

**ده بند قراردادی**

| # | بند |
|---|---|
| ۱ | عدم استفاده از داده برای آموزش |
| ۲ | مدت و محل نگهداری |
| ۳ | حذف به درخواست (SLA) |
| ۴ | DPA و زیرپردازنده |
| ۵ | منطقهٔ پردازش |
| ۶ | مالکیت خروجی |
| ۷ | مسئولیت در نقض |
| ۸ | SLA دسترس‌پذیری |
| ۹ | بند خروج |
| ۱۰ | اطلاع تغییر |

**مفهوم «شاهد، نه ادعا»**

| ادعا | شاهد |
|---|---|
| «امن هستیم» | SOC 2 / ISO 27001 |
| «آموزش نمی‌دهیم» | بند + صفحهٔ سیاست |
| «۹۹٫۹٪» | گزارش وضعیت |
| «GDPR» | DPA + فهرست زیرپردازنده |

**مفهوم «امتیازدهی وزن‌دار»**

```
امتیاز = Σ (وزن × امتیاز)
زیر ۳ = رد | ۳–۴ = کنترل | بالای ۴ = قبول
```

### مثال‌های عملی

| خروج | ۱۰٪ | ۲ | ۴ |
| **امتیاز** | | **۴٫۱۵** | **۳٫۴۵** |

**تحلیل:** A برای دادهٔ حساس، B برای محتوای عمومی. **یک ابزار برای همه، جواب نمی‌دهد.**

### مقایسه و الگوهای مختلف

**سه رویکرد خرید**

| رویکرد | مزیت | عیب |
|---|---|---|

| **هسته + مکمل** | تعادل | مدیریت |

**مقایسهٔ دو قرارداد**

| | استاندارد | مذاکره‌شده |
|---|---|---|
| تغییر بند | ❌ | ✅ |
| DPA | شاید | ✅ |
| مناسب | کم‌ریسک | حساس |

### اشکال شایع

**اشتباه ۱: اعتماد به بازاریابی**
تعهد حقوقی نیست.

**اشتباه ۲: نادیده گرفتن زیرپردازنده**
زنجیرهٔ نامشخص.

**اشتباه ۳: نبود بند خروج**
مهاجرت فلج‌کننده.

**اشتباه ۴: SLA بدون جریمه**
توصیه است.

**اشتباه ۵: ارزیابی یک‌باره**
شرایط عوض می‌شود.

### نکات مهم (Tips & Tricks)

- **شاهد بخواه، نه ادعا.**
- **پنج بند حداقلی.**
- **امتیازدهی وزن‌دار.**
- **برای حساس، قرارداد مذاکره‌شده.**
- **بازبینی سالانه.**

### خلاصه فصل

- پنج بُعد: **داده، امنیت، انطباق، قابلیت، تداوم**.
- ده بند حیاتی؛ پنج حداقلی.
- **شاهد**، نه ادعا.
- امتیازدهی وزن‌دار، دفاع‌پذیر.
- بند خروج، فراموش‌شده.

## فصل ۸۲: مستندسازی، ممیزی و رخداد AI

### مقدمه

اگر نتوانی **ثابت** کنی که کنترل داری، کنترل نداری. مستندسازی، پل بین «ادعا» و «شاهد» است.

### مفاهیم اساسی

**چهار نوع سند**

| سند | مخاطب | محتوا |
|---|---|---|
| **خط‌مشی** | همه | اصول، دامنه |
| **رویه** | اجراکننده | گام‌ها |
| **دستورالعمل** | متخصص | جزئیات فنی |
| **شاهد** | ممیز | لاگ، گزارش |

**مفهوم «هر کنترل، سه سند»**

```text
۱. تعریف: چه کنترلی؟
۲. اجرا: چطور انجام می‌شود؟
۳. شاهد: کجا ثابت می‌شود؟
```

**بدون سند ۳، دو سند اول بی‌ارزش‌اند.**

**ممیزی: پنج گام**

| گام | کار |
|---|---|
| **۱. دامنه** | چه چیزی، چه دوره |
| **۲. معیار** | کدام استاندارد |
| **۳. شاهد** | نمونه‌گیری |
| **۴. یافته** | انطباق/عدم‌انطباق |
| **۵. گزارش** | اقدام اصلاحی |

**مفهوم «نمونه‌گیری در ممیزی»**

| رویکرد | مناسب |
|---|---|
| تصادفی | کنترل عمومی |
| هدفمند | ریسک بالا |
| کامل | پرریسک |

**رخداد AI: پنج مرحله**

```
شناسایی → مهار → ریشه‌یابی → بازیابی → درس‌آموزی
```

| نوع رخداد | مثال |
|---|---|
| **نشت داده** | پرامپت حاوی PII |
| **خروجی آسیب‌زا** | توصیهٔ خطرناک |
| **سوءاستفاده** | Shadow AI |
| **قطع سرویس** | API قطع |

### مثال‌های عملی

**Lab Scenario 82-A: بستهٔ شواهد**

```markdown
# شواهد کنترل PR-AI-07 (نظارت انسانی)

| نوع | سند | محل | دوره |
|---|---|---|---|
| تعریف | رویهٔ PR-AI-07 v1.2 | sharepoint | جاری |
| اجرا | لاگ تصمیم‌ها | SIEM | ۹۰ روز |
| آموزش | سابقهٔ آموزش بازبین | LMS | ۱ سال |
| سنجش | گزارش نمونه‌گیری ماهانه | sharepoint | ۶ ماه |
| اصلاح | ۲ اقدام اصلاحی | Jira | بسته |
```

**Lab Scenario 82-B: گزارش پس از رخداد**

```markdown
# AI-2026-014

آپلود فایل حاوی ۲٬۳۰۰ رکورد مشتری در ابزار عمومی.

|---|---|
```

**Lab Scenario 82-C: چک‌لیست ممیزی**

```markdown
□ فهرست سیستم‌ها کامل است
□ طبقه‌بندی ریسک مکتوب
□ ارزیابی ریسک انجام شده
□ کنترل‌ها تعریف شده
□ شواهد اجرا موجود
□ نمونه‌گیری انجام شده
□ یافته‌ها مستند
□ اقدام اصلاحی با مالک
□ بازبینی قبلی بسته شده
```

### مقایسه و الگوهای مختلف

**مقایسهٔ سه نوع ممیزی**

| نوع | چه کسی | هدف |
|---|---|---|
| **داخلی** | تیم مستقل | یافتن شکاف |
| **ثالث** | نهاد خارجی | تأیید |
| **خودارزیابی** | خود تیم | آمادگی |

**مقایسهٔ دو رویکرد**

| | مستندمحور | شواهدمحور |
|---|---|---|
| اعتبار | کم | بالا |
| تلاش | کم | متوسط |

### اشکال شایع

**اشتباه ۱: مستند بدون شاهد**
ممیزی رد می‌کند.

**اشتباه ۲: نبود تاریخ نسخه**
کدام نسخه معتبر است؟

**اشتباه ۳: پنهان کردن رخداد**
بدتر می‌شود.

**اشتباه ۴: تمرکز بر مقصر**
علت ریشه‌ای پنهان می‌شود.

**اشتباه ۵: اقدام بدون مهلت**
اجرا نمی‌شود.

### نکات مهم (Tips & Tricks)

- **هر کنترل، سه سند.**
- **شاهد را از قبل جمع کن.**
- **رخداد را ثبت کن، حتی کوچک.**
- **بدون سرزنش، علت ریشه‌ای.**
- **هر اقدام، مالک و مهلت.**

### خلاصه فصل

- چهار نوع سند: **خط‌مشی، رویه، دستورالعمل، شاهد**.
- هر کنترل: **تعریف، اجرا، شاهد**.
- ممیزی پنج گام.
- رخداد پنج مرحله.
- **بدون شاهد، کنترل نداری.**
