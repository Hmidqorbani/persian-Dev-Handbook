## فصل ۴۱: زنجیرهٔ تأمین AI — اجزا و نقاط شکست

### مقدمه

هیچ‌کس مدل را از صفر نمی‌سازد. از مدل پایه، کتابخانه، داده، و سرویس‌های ثالث استفاده می‌کنی. **هر وابستگی، یک سطح حمله است.**

زنجیرهٔ تأمین AI، پیچیده‌تر از نرم‌افزار سنتی است، چون **داده** هم بخشی از زنجیره است.

### مفاهیم اساسی

**شش جزء زنجیره**

| جزء | مثال | ریسک |
|---|---|---|
| **مدل پایه** | مدل باز، مدل API | Backdoor، مجوز |
| **داده** | مجموعه‌داده، وب | Poisoning، حق نشر |
| **کتابخانه** | PyTorch، transformers | آسیب‌پذیری |
| **مدل امبدینگ** | بردارساز | نشت، سوگیری |
| **افزونه/ابزار** | Plugin، MCP | دسترسی بیش‌ازحد |
| **زیرساخت** | GPU، Vector DB | پیکربندی |

**چهار نقطهٔ شکست**

| نقطه | سناریو | اثر |
|---|---|---|
| **نام مشابه (Typosquatting)** | `transformrs` به‌جای `transformers` | اجرای کد |
| **مدل آلوده** | وزن با Backdoor | رفتار مخدوش |
| **وابستگی انتقالی** | کتابخانهٔ وابسته | آسیب‌پذیری |
| **افزونهٔ ثالث** | دسترسی به داده | نشت |

**مفهوم «حملهٔ زنجیرهٔ تأمین در AI»**

سه ویژگی متمایز:

| ویژگی | توضیح |
|---|---|
| **داده هم وابستگی است** | Poisoning از داده می‌آید |
| **مدل، باینری است** | قابل تعویض و کپی |
| **مجوز مبهم** | بعضی مدل‌ها استفادهٔ تجاری محدود دارند |

**نکتهٔ مهم:** حملهٔ زنجیرهٔ تأمین، **یک‌به‌چند** است. یک کتابخانهٔ آلوده، هزاران سازمان را می‌زند. این، اقتصاد حمله را برای مهاجم جذاب می‌کند.

**مفهوم «حداقل وابستگی»**

| رویکرد | ریسک |
|---|---|
| وابستگی زیاد | سطح حملهٔ بزرگ |
| وابستگی کم | قابلیت کمتر |
| **حداقل لازم** ⭐ | تعادل |

**درس:** هر وابستگی جدید، یک تصمیم امنیتی است، نه فقط فنی.

### مثال‌های عملی

**Lab Scenario 41-A: نقشهٔ زنجیره**

```markdown
# زنجیرهٔ تأمین — دستیار پشتیبانی

| جزء | منبع | نسخه | مجوز | ریسک | کنترل |
|---|---|---|---|---|---|
| مدل پایه | API فروشنده | 2026-08 | تجاری | متوسط | قرارداد |
| مدل امبدینگ | HuggingFace | 1.2 | Apache-2.0 | متوسط | بررسی |

```

**درس:** افزونهٔ با مجوز نامشخص و دسترسی بالا، بزرگ‌ترین ریسک است.

**Lab Scenario 41-B: تشخیص Typosquatting**

```python
"""
مقایسهٔ نام بسته با نام رسمی — نمونهٔ منطق
(در عمل از allowlist و ابزار تخصصی استفاده کن)
"""
from difflib import SequenceMatcher

OFFICIAL = ["transformers", "torch", "numpy", "scikit-learn", "sentence-transformers"]

def similarity(a: str, b: str) -> float:
    return SequenceMatcher(None, a, b).ratio()

def check(pkg: str, threshold: float = 0.85) -> str:
    if pkg in OFFICIAL:
        return "official"
    for o in OFFICIAL:
        s = similarity(pkg, o)
        if s >= threshold:
            return f"suspicious (شبیه {o}، {s:.2f})"
    return "unknown"

tests = ["transformers", "transformrs", "torch", "torchh", "numpy", "numppy"]
for t in tests:
    print(f"{t:20s} → {check(t)}")
```

**نکته:** این روش، **کمکی** است. کنترل اصلی، **allowlist** و قفل نسخه است.

**Lab Scenario 41-C: قفل وابستگی**

```text
# requirements.lock (نمونه)
torch==2.5.1 --hash=sha256:...
transformers==4.46.2 --hash=sha256:...
numpy==2.1.3 --hash=sha256:...
```

**درس:** نسخهٔ باز (`>=`) = ریسک. نسخهٔ قفل + hash = تکرارپذیری و امنیت.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه نوع وابستگی**

| نوع | ریسک | کنترل |
|---|---|---|
| **مستقیم** | متوسط | بررسی، قفل |
| **انتقالی** | بالا | SCA، SBOM |
| **مدل** | بالا | ارزیابی، هش |

**مقایسهٔ دو رویکرد**

| | ساخت درون | استفاده از باز |
|---|---|---|
| کنترل | بالا | کم |
| سرعت | کم | بالا |
| ریسک | کم | بالا |

### اشکال شایع

**اشتباه ۱: نسخهٔ باز در requirements**
هر نصب، نسخهٔ متفاوت.

**اشتباه ۲: مدل بدون بررسی مجوز**
استفادهٔ تجاری ممنوع، بعداً مشکل حقوقی.

**اشتباه ۳: افزونهٔ ثالث با دسترسی کامل**
سطح حملهٔ جدید.

**اشتباه ۴: نبود SBOM**
در رخداد، نمی‌دانی چه داری.

**اشتباه ۵: اعتماد به «دانلود زیاد»**
محبوبیت، تضمین امنیت نیست.

### نکات مهم (Tips & Tricks)

- **allowlist بسته، نه blacklist.**
- **قفل نسخه + hash.**
- **SBOM/ML-BOM تولید کن.**
- **مجوز مدل را بخوان.**
- **هر افزونه، یک تصمیم امنیتی.**

### خلاصه فصل

- شش جزء: **مدل، داده، کتابخانه، امبدینگ، افزونه، زیرساخت**.
- چهار نقطهٔ شکست: **نام مشابه، مدل آلوده، وابستگی، افزونه**.
- حملهٔ زنجیره، **یک‌به‌چند** است.
- حداقل وابستگی، اصل است.
- قفل نسخه + hash + SBOM.

## فصل ۴۲: مدل‌های باز و مخزن‌ها — ارزیابی قبل از استفاده

### مقدمه

مدل‌های باز، مزیت بزرگی دارند: قابل بررسی، قابل میزبانی محلی، بدون وابستگی به فروشنده. ولی همین «باز بودن»، ریسک‌های خاصی می‌آورد: مدل می‌تواند از پیش آلوده باشد، مجوزش مبهم باشد، یا رفتارش ناخواسته.

این فصل، یک چک‌لیست ارزیابی می‌دهد.

### مفاهیم اساسی

**پنج بُعد ارزیابی**

| بُعد | پرسش |
|---|---|
| **منشأ** | چه کسی ساخته، چه سابقه‌ای دارد |
| **مجوز** | استفادهٔ تجاری مجاز است؟ |
| **یکپارچگی** | hash، امضا، نسخه |
| **رفتار** | آزمون خروجی، trigger |
| **وابستگی** | کتابخانه‌ها، آسیب‌پذیری |

**مفهوم «کارت مدل» (Model Card)**

سند استاندارد که باید بخوانی:

| بخش | چه می‌گوید |
|---|---|
| **هدف** | برای چه ساخته شده |
| **دادهٔ آموزش** | منبع، حجم، محدودیت |
| **محدودیت** | کجا کار نمی‌کند |
| **سوگیری** | گروه‌های کم‌نمایندگی |
| **مجوز** | شرایط استفاده |

**نکته:** کارت مدل، **خودگزارشی** است. باید با آزمون تأیید شود.

**مفهوم «مدل مشتق» (Derivative)**

| نوع | ریسک |
|---|---|
| **Fine-tune** | رفتار ناخواسته، حفظ داده |
| **Quantized** | افت کیفیت، تغییر رفتار |
| **Merged** | ترکیب نامشخص |
| **Pruned** | حذف نورون، رفتار غیرمنتظره |

**درس:** مدل مشتق، **مدل جدید** است. باید دوباره ارزیابی شود.

**چهار آزمون سریع**

| آزمون | چه می‌سنجد |
|---|---|
| **۲۰ پرامپت واقعی** | کیفیت در دامنهٔ تو |
| **آزمون trigger** | Backdoor |
| **آزمون حفظ** | نشت دادهٔ آموزش |
| **آزمون امتناع** | سیاست ایمنی |

**Lab Scenario 42-C: آزمون trigger برای مدل باز**

```python
"""
چارچوب آزمون trigger — شبه‌کد
"""
import hashlib

def triggers(n: int = 20) -> list[str]:
    return [f"TRG-{hashlib.sha256(str(i).encode()).hexdigest()[:6]}" for i in range(n)]

def test_trigger(model, trg: str) -> bool:
    """آیا پاسخ با trigger تغییر می‌کند؟"""
    base = model.generate("یک جملهٔ خنثی بنویس.", temperature=0)
    with_trg = model.generate(f"{trg} یک جملهٔ خنثی بنویس.", temperature=0)
    return base.strip() != with_trg.strip()

# نتایج نمونه
print("۲۰ trigger آماده شد. برای هر کدام، دو اجرا و مقایسه.")
print("اگر بیش از ۳۰٪ triggerها رفتار را عوض کردند → بررسی عمیق")
```

**هشدار:** تغییر رفتار با یک رشتهٔ تصادفی، لزوماً Backdoor نیست (می‌تواند حساسیت به نویز باشد). باید **الگو** را دید، نه یک مورد.

**مقایسهٔ سه منبع مدل**

| منبع | اعتماد | کنترل |
|---|---|---|
| **سازندهٔ اصلی** | بالا | بررسی نسخه |
| **آینهٔ جامعه** | متوسط | hash |
| **ناشناس** | کم | اجتناب |

**مقایسهٔ دو رویکرد**

| | ارزیابی کامل | ارزیابی سریع |
|---|---|---|
| زمان | ۲–۵ روز | ۲ ساعت |
| مناسب | تولید | آزمایش |

### اشکال شایع

**اشتباه ۱: اعتماد به کارت مدل**
خودگزارشی است؛ آزمون لازم.

**اشتباه ۲: نادیده گرفتن مجوز**
«رایگان دانلود» ≠ «مجاز برای تجاری».

**اشتباه ۳: استفاده از آینهٔ ناشناس**
مدل می‌تواند دستکاری‌شده باشد.

**اشتباه ۴: ارزیابی مدل مشتق با معیار مدل اصلی**
مدل جدید، ارزیابی جدید.

**اشتباه ۵: نبود تاریخ انقضای تأیید**
مدل قدیمی می‌شود.

### نکات مهم (Tips & Tricks)

- **کارت مدل را بخوان، ولی باور نکن — آزمون کن.**
- **مجوز را دقیق بخوان** (تجاری/غیرتجاری/حوزه).
- **hash را با منبع رسمی مقایسه کن.**
- **مدل مشتق = مدل جدید.**
- **تأیید را تاریخ‌دار کن** (۶–۱۲ ماه).

### خلاصه فصل

- پنج بُعد: **منشأ، مجوز، یکپارچگی، رفتار، وابستگی**.
- کارت مدل، خودگزارشی است.
- مدل مشتق، ارزیابی جدید می‌خواهد.
- چهار آزمون سریع: **کیفیت، trigger، حفظ، امتناع**.
- تأیید، تاریخ انقضا دارد.

## فصل ۴۳: امنیت خط لولهٔ MLOps و CI/CD

### مقدمه

خط لولهٔ MLOps، همان اصول DevSecOps را می‌خواهد — با یک تفاوت: **داده و مدل هم مصنوع‌اند**.

این فصل، دروازه‌های امنیتی را در خط لوله می‌چیند.

### مفاهیم اساسی

**پنج دروازه**

```
Commit → Build → Test → Stage → Deploy
   ↑        ↑       ↑       ↑        ↑
  lint    SBOM   security  review   approval
```

| دروازه | کنترل |
|---|---|
| **Commit** | امضا، بازبینی، ممنوعیت راز |
| **Build** | قفل وابستگی، SBOM، reproducible |
| **Test** | آزمون امنیتی، trigger، حفظ |
| **Stage** | محیط جدا، دادهٔ ساختگی |
| **Deploy** | تأیید، canary، بازگشت‌پذیر |

**مفهوم «reproducible build»**

| ویژگی | چرا |
|---|---|
| ورودی ثابت | تکرارپذیری |
| hash خروجی | تشخیص تغییر |
| محیط قفل | جلوگیری از drift |

**مفهوم «راز در خط لوله»**

| اشتباه | درست |
|---|---|
| کلید در متغیر CI | Secret Manager |
| کلید در لاگ build | ماسک |
| کلید در artifact | حذف |

**مفهوم «مدل به‌عنوان artifact»**

```
training-job → model artifact → registry (signed) → deploy
```

هر پیکان، یک کنترل: امضا، hash، بازبینی.

**مفهوم «دروازهٔ داده»**

خط لولهٔ MLOps، داده هم جابه‌جا می‌کند:

| دروازه | کنترل |
|---|---|
| **ورود داده** | منبع، مجوز، بازبینی |
| **تبدیل** | ثبت Lineage |
| **خروجی** | hash، نسخه |

### مثال‌های عملی

**Lab Scenario 43-A: خط لولهٔ نمونه**

```yaml
# .github/workflows/ml-pipeline.yml — نمونهٔ مفهومی
name: ml-pipeline
on: [push]

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: نصب وابستگی‌های قفل‌شده
        run: pip install --require-hashes -r requirements.lock

      - name: اسکن وابستگی
        run: pip-audit -r requirements.lock

      - name: اسکن راز
        run: |
          if grep -rInE "(sk-[A-Za-z0-9]{16,}|api[_-]?key\s*=)" . ; then
            echo "راز یافت شد"; exit 1
          fi

      - name: تولید SBOM
        run: cyclonedx-py requirements requirements.lock -o sbom.json

      - name: آپلود SBOM
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

  test:
    needs: security
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: آزمون واحد
        run: pytest -q
      - name: آزمون امنیتی مدل
        run: python tests/test_guardrail.py
```

**نکته:** `--require-hashes` جلوی نصب نسخهٔ دستکاری‌شده را می‌گیرد.

**Lab Scenario 43-B: دروازهٔ استقرار**

```python
"""
دروازهٔ استقرار — تصمیم بر اساس شواهد
"""
from dataclasses import dataclass

@dataclass
class Gate:
    name: str
    passed: bool
    evidence: str

def deploy_gate(gates: list[Gate]) -> str:
    failed = [g for g in gates if not g.passed]
    if failed:
        return "BLOCKED: " + ", ".join(g.name for g in failed)
    return "APPROVED"

checks = [
    Gate("sbom", True, "sbom.json"),
    Gate("vuln_scan", True, "0 critical"),
    Gate("secret_scan", True, "0 found"),
    Gate("model_hash", True, "sha256 ok"),
    Gate("trigger_test", True, "0/20"),
    Gate("guardrail_test", False, "2 failed cases"),
]

print(deploy_gate(checks))
```

**درس:** دروازه، **داده‌محور** است، نه قضاوت شخصی.

### مقایسه و الگوهای مختلف

**مقایسهٔ دو رویکرد**

| | خط لولهٔ سریع | خط لولهٔ با دروازه |
|---|---|---|
| سرعت | بالا | کم |
| ریسک | بالا | کم |
| مناسب | MVP | تولید |

**سه سطح سخت‌گیری**

| سطح | کنترل |
|---|---|
| **پایه** | lint + تست |
| **متوسط** | + SBOM + اسکن |
| **پیشرفته** | + امضا + canary |

### اشکال شایع

**اشتباه ۱: راز در متغیر CI**
در لاگ ظاهر می‌شود.

**اشتباه ۲: نسخهٔ باز در build**
غیرقابل تکرار.

**اشتباه ۳: نبود دروازهٔ داده**
دادهٔ آلوده وارد می‌شود.

**اشتباه ۴: استقرار بدون canary**
خطا در مقیاس.

**اشتباه ۵: نبود بازگشت**
نسخهٔ قبلی در دسترس نیست.

### نکات مهم (Tips & Tricks)

- **`--require-hashes` را جدی بگیر.**
- **SBOM را artifact کن، نه گزارش.**
- **دروازهٔ استقرار، داده‌محور.**
- **canary + بازگشت سریع.**
- **کلید امضا، جدا از CI.**

### خلاصه فصل

- پنج دروازه: **Commit، Build، Test، Stage، Deploy**.
- **reproducible build** پایهٔ اعتماد است.
- مدل = artifact؛ امضا و hash لازم.
- دروازهٔ داده، به‌اندازهٔ دروازهٔ کد مهم است.
- canary + بازگشت، کاهش اثر.

## فصل ۴۴: ریسک فروشنده و ارزیابی ثالث

### مقدمه

در AI، بیشتر قابلیت‌ها از فروشنده می‌آید. و بیشتر ریسک‌ها هم. این فصل، چارچوب ارزیابی می‌دهد — با تمرکز بر چیزهایی که **واقعاً** تفاوت می‌سازند.

### مفاهیم اساسی

**پنج بُعد ارزیابی**

| بُعد | وزن | پرسش |
|---|---|---|
| **داده و حریم خصوصی** | 🔴 بالا | آموزش روی دادهٔ ما؟ |
| **امنیت** | 🔴 بالا | گواهی، کنترل، رخداد |
| **انطباق** | 🟠 متوسط | DPA، منطقه، زیرپردازنده |
| **قابلیت** | 🟠 متوسط | برای کار ما کافی است؟ |
| **تداوم** | 🟢 کم | طرح خروج |

**ده بند قراردادی حیاتی**

| # | بند |
|---|---|
| ۱ | عدم استفاده از داده برای آموزش |
| ۲ | مدت و محل نگهداری |
| ۳ | حذف به درخواست (SLA) |
| ۴ | DPA و فهرست زیرپردازنده |
| ۵ | منطقهٔ پردازش |
| ۶ | مالکیت خروجی |
| ۷ | مسئولیت در نقض |
| ۸ | SLA دسترس‌پذیری |
| ۹ | بند خروج و قالب داده |
| ۱۰ | اطلاع تغییر شرایط |

**مفهوم «ارزیابی مبتنی بر شواهد»**

| ادعا | مدرک |
|---|---|
| «امن هستیم» | SOC 2 / ISO 27001 |
| «آموزش نمی‌دهیم» | بند قرارداد + صفحهٔ سیاست |
| «۹۹٫۹٪» | گزارش وضعیت |
| «GDPR compliant» | DPA + فهرست زیرپردازنده |

**مفهوم «امتیازدهی وزن‌دار»**

```
امتیاز = Σ (وزن × امتیاز بُعد)
زیر ۳ = رد | ۳–۴ = کنترل | بالای ۴ = قبول
```

### مثال‌های عملی

**Lab Scenario 44-A: ماتریس دو فروشنده**

| معیار | وزن | A | B |
|---|---|---|---|
| عدم آموزش روی داده | ۳۰٪ | ۵ | ۳ |
| گواهی امنیتی | ۲۵٪ | ۵ | ۴ |
| DPA و انطباق | ۲۰٪ | ۴ | ۲ |
| قابلیت فارسی | ۱۵٪ | ۳ | ۵ |
| طرح خروج | ۱۰٪ | ۲ | ۴ |
| **امتیاز** | | **۴٫۱۵** | **۳٫۴۵** |

**تحلیل:** A برای دادهٔ حساس، B برای محتوای عمومی. **یک ابزار برای همه، جواب نمی‌دهد.**

**Lab Scenario 44-B: پرسش‌نامه**

```markdown
# ارزیابی فروشنده

## داده
۱) داده برای آموزش استفاده می‌شود؟ (بند)
۲) مدت نگهداری؟
۳) کشور/منطقهٔ ذخیره؟
۴) SLA حذف؟
۵) پشتیبان خارج از منطقه؟

## امنیت
۶) گواهی‌ها + تاریخ انقضا؟
۷) آخرین آزمون نفوذ؟
۸) رمزنگاری انتقال/سکون؟
۹) SLA اطلاع رخداد؟
۱۰) MFA و کنترل دسترسی؟

## انطباق
۱۱) DPA قابل امضا؟
۱۲) فهرست زیرپردازنده؟
۱۳) پشتیبانی از درخواست صاحبان داده؟

## قابلیت
۱۴) نمونهٔ خروجی فارسی
۱۵) محدودیت نرخ
۱۶) تست عملی ۱۰ پرامپت

## تداوم
۱۷) SLA دسترس‌پذیری
```

**Lab Scenario 44-C: بندهای پیشنهادی**

```text
۱. «ارائه‌دهنده داده‌های مشتری را برای آموزش، بهبود یا توسعهٔ
   مدل‌های خود استفاده نمی‌کند.»

۲. «داده حداکثر ۳۰ روز پس از پایان قرارداد حذف و گواهی حذف
   ارائه می‌شود.»
```

### مقایسه و الگوهای مختلف

**سه رویکرد خرید**

| رویکرد | مزیت | عیب |
|---|---|---|
| **تک‌فروشنده** | ساده | وابستگی |
| **چندفروشنده** | تنوع | پیچیدگی |

| | استاندارد | مذاکره‌شده |
|---|---|---|

| DPA | ممکن است نباشد | ✅ |

### اشکال شایع

**اشتباه ۱: اعتماد به صفحهٔ بازاریابی**
تعهد حقوقی نیست.

**اشتباه ۲: نادیده گرفتن زیرپردازنده**
فروشنده از سرویس‌های دیگر استفاده می‌کند.

**اشتباه ۳: نبود بند خروج**
مهاجرت فلج‌کننده.

**اشتباه ۴: SLA بدون جریمه**
توصیه است، نه تعهد.

**اشتباه ۵: ارزیابی یک‌باره**
شرایط و مالکیت تغییر می‌کند.

### نکات مهم (Tips & Tricks)

- **مدرک بخواه، نه ادعا.**
- **پنج بند حداقلی:** عدم آموزش، حذف، اطلاع رخداد، خروج، مالکیت.
- **امتیازدهی وزن‌دار** تصمیم را شفاف می‌کند.
- **برای دادهٔ حساس، فقط قرارداد مذاکره‌شده.**
- **بازبینی سالانه.**

### خلاصه فصل

- پنج بُعد: **داده، امنیت، انطباق، قابلیت، تداوم**.
- ده بند حیاتی؛ پنج بند حداقلی.
- **شاهد** بخواه، نه ادعا.
- امتیازدهی وزن‌دار، دفاع‌پذیر است.
- بند خروج را فراموش نکن.
