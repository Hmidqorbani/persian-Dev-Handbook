## فصل ۴۵: اقتصاد SOC و جای AI

### مقدمه

یک تحلیلگر SOC، روزی چند صد هشدار می‌بیند. بیشترشان بی‌خطرند. ولی یکی از آن‌ها ممکن است واقعی باشد.

این **عدم‌تقارن**، مسئلهٔ بنیادی SOC است: هزینهٔ بررسی همه (اتلاف) در برابر هزینهٔ از دست دادن یکی (فاجعه).

AI، اینجا وارد می‌شود — نه برای «جایگزینی تحلیلگر»، بلکه برای **تخصیص توجه**.

### مفاهیم اساسی

**چهار عدد کلیدی**

| معیار | معنا | هدف |
|---|---|---|
| **MTTD** | میانگین زمان تشخیص | کاهش |
| **MTTR** | میانگین زمان پاسخ | کاهش |
| **FPR** | نرخ هشدار نادرست | کاهش |
| **Alert Fatigue** | خستگی تحلیلگر | کاهش |

**مفهوم «اقتصاد توجه»**

```
ظرفیت تحلیلگر: ~۵۰ هشدار عمیق در روز
هشدارهای ورودی: ~۵۰۰ در روز
نسبت: ۱۰:۱
```

**پیامد:** ۹۰٪ هشدارها فقط «رد» می‌شوند — و همین، منبع خطاست. تحلیلگر خسته، هشدار واقعی را هم رد می‌کند.

**سه جای مداخلهٔ AI**

| جای | چه می‌کند | اثر |
|---|---|---|
| **قبل از صف** | فیلتر و رتبه‌بندی | کاهش حجم |
| **در صف** | غنی‌سازی و خلاصه | کاهش زمان |
| **بعد از تصمیم** | مستندسازی | کاهش بار اداری |

**مفهوم «AI به‌عنوان فیلتر، نه داور»**

| نقش | مناسب |
|---|---|
| رتبه‌بندی | ✅ |
| خلاصه‌سازی | ✅ |
| پیشنهاد اقدام | ⚠️ با تأیید |
| بستن خودکار | ❌ (برای موارد مشکوک) |

**نکتهٔ حیاتی:** اگر AI هشداری را «بی‌خطر» علامت بزند و آن هشدار واقعی باشد، **کسی آن را نمی‌بیند**. این «منفی کاذب خودکار» خطرناک‌ترین حالت است.

**مفهوم «هزینهٔ منفی کاذب»**

| نوع خطا | هزینه |
|---|---|
| **مثبت کاذب (FP)** | زمان تحلیلگر |
| **منفی کاذب (FN)** | نفوذ موفق |

**قاعده:** در SOC، آستانه باید به نفع **حساسیت** باشد، نه دقت.

### مثال‌های عملی

**Lab Scenario 45-A: محاسبهٔ ظرفیت**

```python
"""
محاسبهٔ اثر AI بر ظرفیت SOC
"""
def capacity(analysts: int, hours: float, min_per_alert: float, overhead: float = 0.3) -> float:
    """تعداد هشدار قابل بررسی در روز."""
    productive = analysts * hours * (1 - overhead) * 60
    return productive / min_per_alert

before = capacity(4, 6, 12)     # ۱۲ دقیقه برای هر هشدار
after  = capacity(4, 6, 5)      # با خلاصهٔ AI، ۵ دقیقه

print(f"قبل: {before:.0f} هشدار/روز")
print(f"بعد: {after:.0f} هشدار/روز")
print(f"افزایش ظرفیت: {(after/before - 1):.0%}")
```

**تفسیر:** کاهش زمان هر هشدار از ۱۲ به ۵ دقیقه، ظرفیت را ۲٫۴ برابر می‌کند — بدون استخدام.

**Lab Scenario 45-B: تصمیم دربارهٔ اتوماسیون**

| نوع هشدار | حجم | ریسک | تصمیم |
|---|---|---|---|
| اسکن پورت از IP ناشناس | بالا | کم | بستن خودکار |
| ورود ناموفق مکرر | بالا | متوسط | رتبه‌بندی + خلاصه |
| نصب نرم‌افزار | متوسط | متوسط | بازبینی |
| نشت دادهٔ احتمالی | کم | **بالا** | بازبینی اجباری |
| بدافزار شناخته‌شده | متوسط | بالا | قرنطینه + اطلاع |

**درس:** حجم بالا + ریسک کم = خودکار. ریسک بالا = انسان، همیشه.

**Lab Scenario 45-C: شاخص‌های موفقیت**

```markdown
# KPI پس از ۹۰ روز

| شاخص | قبل | هدف | اندازه‌گیری |
|---|---|---|---|
| MTTD | ۴ ساعت | < ۱ ساعت | SIEM |
| MTTR | ۱۲ ساعت | < ۶ ساعت | تیکت |
| FPR | ۶۵٪ | < ۴۰٪ | نمونه‌گیری |
| رضایت تحلیلگر | ۳٫۰ | > ۴٫۰ | نظرسنجی |
| هشدار بررسی‌شده | ۶۰٪ | > ۹۵٪ | SIEM |
```

**نکته:** «هشدار بررسی‌شده» معیار مهمی است که اغلب فراموش می‌شود.

### مقایسه و الگوهای مختلف

**سه مدل SOC**

| مدل | ویژگی | مناسب |
|---|---|---|
| **سنتی** | همه دستی | کوچک |
| **AI-assisted** ⭐ | AI رتبه‌بندی، انسان تصمیم | اکثر |
| **AI-automated** | AI تصمیم، انسان استثنا | بلوغ بالا |

**مقایسهٔ دو رویکرد**

| | تمرکز بر FP | تمرکز بر FN |
|---|---|---|
| آستانه | بالا | پایین |
| بار تحلیلگر | کم | زیاد |
| ریسک نفوذ | بالا | کم |

### اشکال شایع

**اشتباه ۱: بستن خودکار همهٔ هشدارهای «کم‌ریسک»**
یک مورد واقعی، نادیده می‌ماند.

**اشتباه ۲: سنجش فقط با FPR**
FPR پایین می‌تواند یعنی FN بالا.

**اشتباه ۳: نادیده گرفتن تحلیلگر**
ابزاری که تجربه را خراب کند، استفاده نمی‌شود.

**اشتباه ۴: اتوماسیون قبل از پایداری کیفیت**
اگر مدل ۱۵٪ خطا دارد، خودکارسازی آن را مقیاس می‌دهد.

**اشتباه ۵: نبود معیار بازگشت**
اگر AI بد عمل کرد، چه زمانی خاموش می‌شود؟

### نکات مهم (Tips & Tricks)

- **AI رتبه‌بندی کند، نه داوری.**
- **آستانه را به نفع حساسیت بگذار.**
- **«هشدار بررسی‌شده» را بسنج.**
- **تحلیلگر را در طراحی شریک کن.**
- **معیار خاموشی (Kill Switch) داشته باش.**

### خلاصه فصل

- مسئلهٔ SOC: **عدم‌تقارن هزینهٔ خطا**.
- سه جای مداخله: **قبل، در، بعد از صف**.
- AI فیلتر است، نه داور.
- **منفی کاذب خودکار**، خطرناک‌ترین حالت.
- آستانه به نفع حساسیت.

## فصل ۴۶: Triage خودکار هشدارها

### مقدمه

**Triage** یعنی تصمیم اولیه: این هشدار چقدر مهم است و چه کسی باید ببیند؟

این، پرتکرارترین و پرهزینه‌ترین کار SOC است — و مناسب‌ترین کاربرد AI.

### مفاهیم اساسی

**چهار خروجی Triage**

| خروجی | معنا | اقدام |
|---|---|---|
| **True Positive** | تهدید واقعی | پاسخ |
| **Benign** | بی‌خطر | بستن با دلیل |
| **Needs Context** | نیاز به اطلاعات | غنی‌سازی |
| **Unknown** | نامشخص | بازبینی انسانی |

**نکته:** خروجی چهارم، مهم‌ترین است. مدل باید بتواند بگوید «نمی‌دانم».

**چهار ورودی Triage**

| ورودی | مثال |
|---|---|
| **هشدار** | نوع، شدت، زمان |
| **زمینهٔ دارایی** | بحرانی بودن، مالک |
| **زمینهٔ تهدید** | IOC، کمپین |
| **تاریخچه** | هشدارهای مشابه |

**مفهوم «امتیاز ریسک ترکیبی»**

```
risk = severity × asset_criticality × threat_context × confidence
```

| عامل | بازه |
|---|---|
| severity | ۱–۵ |
| asset_criticality | ۱–۵ |
| threat_context | ۰٫۵–۲ |
| confidence | ۰–۱ |

**درس:** هشدار «بالا» روی یک سرور آزمایشی، از هشدار «متوسط» روی سرور پرداخت مهم‌تر نیست.

**مفهوم «خلاصهٔ هشدار»**

خروجی متنی که تحلیلگر می‌خواند:

```text
[خلاصه]
کاربر admin از IP جدید در کشور X، ۵ بار ورود ناموفق، سپس موفق.
دارایی: سرور پرداخت (بحرانی).
IOC: IP در ۲ کمپین قبلی دیده شده.
پیشنهاد: بازبینی فوری + بررسی نشست.
اطمینان: متوسط (۷۲٪)
```

**چرا مهم است؟** تحلیلگر به‌جای ۱۲ دقیقه خواندن، ۲ دقیقه تصمیم می‌گیرد.

### مثال‌های عملی

**Lab Scenario 46-A: موتور امتیازدهی**

```python
"""
امتیازدهی ریسک هشدار — نمونهٔ قابل اجرا
"""
from dataclasses import dataclass

@dataclass
class Alert:
    id: str
    severity: int          # 1..5
    asset_criticality: int # 1..5
    threat_context: float  # 0.5..2.0
    confidence: float      # 0..1

def risk_score(a: Alert) -> float:
    return a.severity * a.asset_criticality * a.threat_context * a.confidence

def bucket(score: float) -> str:
    if score >= 20: return "P1-فوری"
    if score >= 10: return "P2-بالا"
    if score >= 4:  return "P3-متوسط"
    return "P4-کم"

alerts = [
    Alert("A-1", 4, 5, 1.5, 0.9),   # ورود مشکوک روی سرور پرداخت
    Alert("A-2", 5, 1, 0.8, 0.6),   # بدافزار روی تست
    Alert("A-3", 2, 4, 1.0, 0.5),   # اسکن پورت روی داخلی
    Alert("A-4", 3, 3, 1.2, 0.4),   # ناهنجاری با اطمینان کم
]

for a in sorted(alerts, key=risk_score, reverse=True):
    s = risk_score(a)
    print(f"{a.id}  score={s:5.1f}  {bucket(s)}")
```

**تفسیر:** A-2 شدت ۵ دارد ولی روی دارایی کم‌اهمیت است — پایین‌تر از A-1 می‌آید. **شدت خام، گمراه‌کننده است.**

### مقایسه و الگوهای مختلف

**سه سطح Triage**

| سطح | چه می‌کند | ریسک |
|---|---|---|
| **قاعده‌محور** | if/then | شکننده |
| **ML** | دسته‌بندی | نیاز به داده |
| **LLM** | تحلیل + خلاصه | توهم |

**توصیه:** ترکیب. قاعده برای فیلتر اولیه، ML برای رتبه‌بندی، LLM برای خلاصه.

**مقایسهٔ دو رویکرد**

| | خودکار کامل | نیمه‌خودکار |
|---|---|---|
| سرعت | بالا | متوسط |
| ریسک FN | بالا | کم |
| مناسب | هشدار کم‌ریسک | همه |

### اشکال شایع

**اشتباه ۱: اتکا به شدت خام**
زمینهٔ دارایی مهم‌تر است.

**اشتباه ۲: نبود خروجی «نمی‌دانم»**
مدل مجبور می‌شود حدس بزند.

**اشتباه ۳: خلاصهٔ طولانی**
تحلیلگر نمی‌خواند.

**اشتباه ۴: نبود لینک به هشدار اصلی**
اعتماد از بین می‌رود.

**اشتباه ۵: ارزیابی با دادهٔ تمیز**
دادهٔ واقعی SOC، پرنویز است.

### نکات مهم (Tips & Tricks)

- **چهار خروجی، نه دو.**
- **`missing_info` را جدی بگیر.**
- **همیشه لینک به منبع اصلی.**
- **خلاصه حداکثر ۵ خط.**
- **با دادهٔ واقعی ارزیابی کن، نه نمونهٔ تمیز.**

### خلاصه فصل

- چهار خروجی: **TP، Benign، Needs Context، Unknown**.
- **امتیاز ترکیبی** بهتر از شدت خام.
- غنی‌سازی، نیمهٔ کار است.
- خروجی ساختاریافته، قابل پردازش است.
- همیشه لینک به منبع اصلی.

## فصل ۴۷: همبستگی و کاهش هشدار تکراری

### مقدمه

یک حمله، اغلب ده‌ها هشدار می‌سازد. تحلیلگر باید بفهمد این‌ها **یک رخداد** هستند، نه ده رخداد.

**همبستگی** (Correlation) این کار را می‌کند — و AI می‌تواند بهتر از قواعد ثابت عمل کند.

### مفاهیم اساسی

**سه سطح همبستگی**

| سطح | چه چیزی | مثال |
|---|---|---|
| **تکرار** | هشدار یکسان | همان قاعده، همان میزبان |
| **الگو** | توالی | اسکن → نفوذ → exfil |
| **موجودیت** | همان دارایی/کاربر | ۵ هشدار روی یک حساب |

**چهار تکنیک**

| تکنیک | چطور |
|---|---|
| **Deduplication** | حذف تکراری دقیق |
| **Grouping** | گروه‌بندی بر اساس موجودیت |
| **Clustering** | خوشه‌بندی آماری |
| **Sequence** | تحلیل توالی زمانی |

**مفهوم «هشدار اصلی و پیرو»**

| نوع | مثال |
|---|---|
| **اصلی (Parent)** | «نفوذ موفق» |
| **پیرو (Child)** | «اسکن پورت»، «ورود ناموفق» |

**درس:** یک «رخداد» به تحلیلگر بده، نه ده هشدار.

**مفهوم «کاهش نویز»**

| منبع نویز | راه‌حل |
|---|---|
| هشدار تکراری | Dedup |
| هشدار مرتبط | Grouping |
| هشدار بی‌اهمیت | Suppression با قاعده |
| هشدار پرت | Baseline |

**هشدار:** Suppression می‌تواند **تهدید واقعی** را هم پنهان کند. هر قاعدهٔ سرکوب، باید **تاریخ انقضا** و **مالک** داشته باشد.

### مثال‌های عملی

**Lab Scenario 47-A: گروه‌بندی بر اساس موجودیت**

```python
"""
گروه‌بندی هشدارها بر اساس موجودیت و پنجرهٔ زمانی
"""
from dataclasses import dataclass
from datetime import datetime, timedelta

@dataclass
class Alert:
    id: str
    ts: datetime
    entity: str
    rule: str

def group(alerts: list[Alert], window_min: int = 30) -> list[list[Alert]]:
    alerts = sorted(alerts, key=lambda a: a.ts)
    groups, current = [], []
    for a in alerts:
        if not current:
            current = [a]
            continue
        same_entity = a.entity == current[0].entity
        within = (a.ts - current[0].ts) <= timedelta(minutes=window_min)
        if same_entity and within:
            current.append(a)
        else:
            groups.append(current)
            current = [a]
    if current:
        groups.append(current)
    return groups

base = datetime(2026, 11, 12, 10, 0)
alerts = [
    Alert("1", base, "host-01", "port_scan"),
    Alert("2", base + timedelta(minutes=5), "host-01", "login_fail"),
    Alert("3", base + timedelta(minutes=12), "host-01", "login_success"),
    Alert("4", base + timedelta(minutes=20), "host-02", "port_scan"),
    Alert("5", base + timedelta(minutes=60), "host-01", "malware"),
]

for i, g in enumerate(group(alerts), 1):
    print(f"رخداد {i} | موجودیت={g[0].entity} | {len(g)} هشدار | {[a.rule for a in g]}")
```

**تفسیر:** پنج هشدار، سه رخداد. تحلیلگر سه چیز را بررسی می‌کند، نه پنج.

**Lab Scenario 47-B: تحلیل توالی**

```markdown
# الگوی توالی — نمونه

| ترتیب | هشدار | معنا |
|---|---|---|
| ۱ | اسکن پورت | شناسایی |
| ۲ | ورود ناموفق مکرر | تلاش دسترسی |
| ۳ | ورود موفق از IP جدید | نفوذ احتمالی |
| ۴ | ایجاد کاربر جدید | ماندگاری |

    review: "هر ۶ ماه"
```

**درس:** سرکوب بدون انقضا، یک بدهی امنیتی است.

### مقایسه و الگوهای مختلف

**مقایسهٔ سه روش**

| روش | دقت | پیچیدگی | مناسب |
|---|---|---|---|
| **قاعده** | بالا (برای الگوی شناخته‌شده) | کم | تکرار |
| **آماری** | متوسط | متوسط | ناهنجاری |
| **LLM** | متغیر | بالا | خلاصه و تفسیر |

**مقایسهٔ دو رویکرد**

| | سرکوب | گروه‌بندی |
|---|---|---|
| اثر | حذف | ادغام |
| ریسک | پنهان‌سازی | کم |
| توصیه | محدود | گسترده |

### اشکال شایع

**اشتباه ۱: سرکوب بدون انقضا**
تهدید جدید، پنهان می‌شود.

**اشتباه ۲: گروه‌بندی با پنجرهٔ بزرگ**
رخدادهای بی‌ربط، ادغام می‌شوند.

**اشتباه ۳: نادیده گرفتن موجودیت**
هشدارهای یک کاربر، پخش می‌شوند.

**اشتباه ۴: اتکا به LLM برای همبستگی**
مدل، شمارش دقیق ندارد.

**اشتباه ۵: نبود هشدار اصلی**
تحلیلگر، تصویر کامل ندارد.

### نکات مهم (Tips & Tricks)

- **گروه‌بندی بر اساس موجودیت، اول.**
- **هر سرکوب، مالک و انقضا.**
- **توالی را وزن بده.**
- **همبستگی را با قاعده شروع کن، نه LLM.**
- **یک «رخداد» بساز، نه ده هشدار.**

### خلاصه فصل

- سه سطح: **تکرار، الگو، موجودیت**.
- چهار تکنیک: **Dedup، Grouping، Clustering، Sequence**.
- **توالی** ارزش بیشتری از تک‌هشدار دارد.
- سرکوب بدون انقضا، بدهی است.
- LLM برای تفسیر، نه شمارش.

## فصل ۴۸: تشخیص ناهنجاری و UEBA

### مقدمه

امضای حمله، فقط حمله‌های **شناخته‌شده** را می‌گیرد. **تشخیص ناهنجاری** به‌دنبال چیزی است که «عادی نیست» — حتی اگر قبلاً دیده نشده باشد.

**UEBA** (User and Entity Behavior Analytics) کاربرد این ایده برای کاربران و دارایی‌هاست.

### مفاهیم اساسی

**سه نوع ناهنجاری**

| نوع | مثال | تشخیص |
|---|---|---|
| **نقطه‌ای** | یک رویداد عجیب | فاصله از میانگین |
| **زمینه‌ای** | رویداد عادی در زمان عجیب | مقایسه با زمینه |
| **جمعی** | الگوی عجیب در مجموعه | خوشه‌بندی |

**چهار مبنای Baseline**

| مبنا | مثال |
|---|---|
| **زمان** | ساعت کاری |
| **مکان** | IP، کشور |
| **حجم** | تعداد فایل |
| **رفتار** | ترتیب اقدامات |

**مفهوم «پروفایل رفتاری»**

```
کاربر X:
- ورود: ۸–۱۸، از IP داخلی
- فایل: ۱۰–۵۰ در روز
- ابزار: مرورگر، ایمیل، CRM
- ناهنجاری: ورود ۳ بامداد از کشور دیگر
```

**نکته:** پروفایل باید **به‌روز** شود. رفتار مردم عوض می‌شود (نقش جدید، سفر، دورکاری).

**مفهوم «مثبت کاذب در UEBA»**

| علت | مثال |
|---|---|
| **تغییر نقش** | دسترسی جدید |
| **سفر** | IP خارجی |
| **پروژهٔ جدید** | حجم بالای دانلود |
| **فصل** | افزایش تراکنش |

**پیامد:** UEBA بدون **زمینهٔ سازمانی**، نویز تولید می‌کند.

**مفهوم «امتیاز ناهنجاری»**

| روش | توضیح |
|---|---|
| **Z-score** | فاصله از میانگین بر حسب انحراف |
| **IQR** | خارج از چارک‌ها |
| **Isolation Forest** | جداافتادگی |
| **Autoencoder** | خطای بازسازی |

### مثال‌های عملی

**Lab Scenario 48-A: Z-score ساده**

```python
"""
تشخیص ناهنجاری با Z-score — قابل اجرا
نیاز: pip install numpy
"""
import numpy as np

# تعداد فایل‌های دانلودی روزانهٔ یک کاربر (۳۰ روز)
rng = np.random.default_rng(3)
normal = rng.normal(20, 5, 30).round().clip(0)
today = 180

mu, sd = normal.mean(), normal.std()
z = (today - mu) / sd

print(f"میانگین={mu:.1f} انحراف={sd:.1f} امروز={today} z={z:.1f}")
print("ناهنجاری شدید" if z > 5 else ("ناهنجاری" if z > 3 else "عادی"))
```

**تفسیر:** z=۳ آستانهٔ رایج است؛ z>۵ تقریباً همیشه ارزش بررسی دارد.

**Lab Scenario 48-B: Isolation Forest**

```python
"""
تشخیص ناهنجاری چندمتغیره
نیاز: pip install scikit-learn numpy
"""
import numpy as np
from sklearn.ensemble import IsolationForest

rng = np.random.default_rng(11)
# ویژگی‌ها: [فایل دانلودی, ورود ناموفق, ساعت]
normal = np.column_stack([
    rng.normal(20, 5, 200),
    rng.poisson(1, 200),
    rng.normal(11, 2, 200),
])
suspicious = np.array([[300, 12, 3], [250, 8, 2], [400, 15, 4]])

X = np.vstack([normal, suspicious])
model = IsolationForest(contamination=0.02, random_state=42).fit(X)

scores = model.decision_function(X)
preds = model.predict(X)

for i in range(len(normal), len(X)):
    print(f"ناهنجار؟ {preds[i] == -1} | score={scores[i]:.3f} | {X[i]}")
```

**نکته:** Isolation Forest **دلیل** نمی‌دهد. برای توضیح، به تحلیل ویژگی نیاز داری.

**Lab Scenario 48-C: کاهش FP با زمینه**

| سیگنال | بدون زمینه | با زمینه |
|---|---|---|
| دانلود ۳۰۰ فایل | 🚨 ناهنجاری | ✅ پروژهٔ مهاجرت داده |
| ورود از کشور دیگر | 🚨 ناهنجاری | ✅ سفر ثبت‌شده |
| ورود ۳ بامداد | 🚨 ناهنجاری | ✅ شیفت شب |
| دسترسی به سیستم جدید | 🚨 ناهنجاری | ✅ نقش جدید |

**درس:** **زمینه، نیمی از دقت است.**

### مقایسه و الگوهای مختلف

**مقایسهٔ چهار روش**

| روش | مزیت | عیب |
|---|---|---|
| Z-score | ساده، قابل توضیح | فقط تک‌متغیره |
| IQR | مقاوم به پرت | ساده |
| Isolation Forest | چندمتغیره | بدون دلیل |
| Autoencoder | الگوی پیچیده | نیاز به دادهٔ زیاد |

**مقایسهٔ دو رویکرد**

| | امضامحور | ناهنجاری‌محور |
|---|---|---|
| تهدید شناخته‌شده | ✅ | ⚠️ |
| تهدید نو | ❌ | ✅ |
| FP | کم | زیاد |
| توصیه | ترکیب | ترکیب |

### اشکال شایع

**اشتباه ۱: UEBA بدون زمینه**
نویز زیاد، اعتماد کم.

**اشتباه ۲: Baseline ثابت**
رفتار عوض می‌شود.

**اشتباه ۳: آستانهٔ خیلی حساس**
هزاران هشدار.

**اشتباه ۴: تفسیر ناهنجاری به‌عنوان حمله**
ناهنجاری = «بررسی کن»، نه «حمله است».

**اشتباه ۵: نبود بازخورد تحلیلگر**
مدل یاد نمی‌گیرد چه چیزی FP است.

### نکات مهم (Tips & Tricks)

- **Baseline را دوره‌ای بازآموزی کن.**
- **زمینهٔ سازمانی را وارد کن** (نقش، سفر، پروژه).
- **آستانه را با نرخ FP تنظیم کن.**
- **ناهنجاری = سیگنال بررسی.**
- **بازخورد تحلیلگر را ثبت کن.**

### خلاصه فصل

- سه نوع: **نقطه‌ای، زمینه‌ای، جمعی**.
- چهار مبنا: **زمان، مکان، حجم، رفتار**.
- **زمینه**، نیمی از دقت است.
- Isolation Forest بدون دلیل است.
- ناهنجاری = سیگنال، نه حکم.

## فصل ۴۹: Human-in-the-loop در SOC

### مقدمه

در SOC، «انسان در حلقه» یک انتخاب نیست — یک **ضرورت** است. چون تصمیم‌ها اثر واقعی دارند: مسدودسازی، جداسازی، اطلاع به مشتری.

ولی نظارت انسانی، اگر بد طراحی شود، **نمایشی** می‌شود.

### مفاهیم اساسی

**چهار سطح نظارت**

| سطح | نقش انسان | مناسب |
|---|---|---|
| **AI پیشنهاد، انسان تصمیم** | کامل | همهٔ موارد مهم |
| **AI اقدام، انسان تأیید** | تأیید | اقدام برگشت‌ناپذیر |
| **AI اقدام، انسان پایش** | نمونه‌گیری | کم‌ریسک |
| **AI اقدام، بدون نظارت** | — | فقط بستن هشدار تکراری |

**سه شرط نظارت مؤثر**

| شرط | نشانهٔ نقص |
|---|---|
| **اطلاعات کافی** | فقط خروجی نهایی |
| **زمان کافی** | ۵ ثانیه برای هر مورد |
| **اختیار واقعی** | رد کردن، پیامد منفی دارد |

**مفهوم «خستگی تأیید»**

| نشانه | معنا |
|---|---|
| تأیید ۹۹٪ موارد | بررسی نمی‌کند |
| زمان تصمیم < ۳ ثانیه | نگاه نمی‌کند |
| نرخ رد نزدیک صفر | اختیار واقعی ندارد |

**راه‌حل‌ها:**

| راه‌حل | اثر |
|---|---|
| نمونه‌گیری هوشمند | فقط موارد پرریسک |
| آستانهٔ اطمینان | خودکار برای مطمئن |
| چرخش نقش | کاهش خستگی |
| موارد کنترل (canary) | سنجش کیفیت |

**مفهوم «سوگیری اتوماسیون»**

انسان تمایل دارد به ماشین اعتماد کند، حتی وقتی اشتباه می‌کند.

| تکنیک مقابله | اثر |
|---|---|
| نمایش عدم‌قطعیت | آگاهی از ریسک |
| پرسش اجباری («دلیل تأیید؟») | تفکر فعال |
| موارد canary | سنجش واقعی |
| بازبینی مستقل | چشم دوم |

### مثال‌های عملی

**Lab Scenario 49-A: مسیریابی بر اساس اطمینان**

```python
"""
مسیریابی هشدار بر اساس اطمینان و ریسک
"""
def route(confidence: float, risk: str) -> str:
    if risk == "high":
        return "بازبینی اجباری (۲ نفر)"
    if confidence >= 0.95:
        return "خودکار + نمونه‌گیری ۱۰٪"
    if confidence >= 0.75:
        return "خودکار + نمونه‌گیری ۵۰٪"
    return "بازبینی انسانی"

cases = [
    (0.98, "low"), (0.88, "low"), (0.60, "low"),
    (0.99, "high"), (0.80, "medium"),
]
for c, r in cases:
    print(f"اطمینان={c:.2f} ریسک={r:6s} → {route(c, r)}")
```

**Lab Scenario 49-B: سنجش کیفیت بازبینی**

```python
"""
سنجش با موارد canary
"""
import random

def insert_canaries(batch: list[dict], rate: float = 0.05) -> list[dict]:
    n = max(1, int(len(batch) * rate))
    for i in random.sample(range(len(batch)), n):
        batch[i] = {**batch[i], "canary": True, "has_error": True}
    return batch

def detection_rate(batch: list[dict], decisions: dict) -> float | None:
    canaries = [b for b in batch if b.get("canary")]
    if not canaries:
        return None
    caught = sum(1 for b in canaries if decisions.get(b["id"]) == "reject")
    return caught / len(canaries)

batch = [{"id": i} for i in range(40)]
batch = insert_canaries(batch, 0.1)
decisions = {b["id"]: "approve" for b in batch}
decisions[batch[2]["id"]] = "reject"

print("نرخ تشخیص:", detection_rate(batch, decisions))
print("اگر < ۵۰٪ → بازبینی نمایشی است")
```

**هشدار:** canary باید **شفاف** با تیم باشد. استفادهٔ پنهانی، اعتماد را از بین می‌برد.

### مقایسه و الگوهای مختلف

**مقایسهٔ دو مدل**

| | تأیید موردی | تأیید دسته‌ای |
|---|---|---|
| دقت | بالا | پایین |
| سرعت | پایین | بالا |

**سه سبک سازمانی**

| سبک | ویژگی | ریسک |
|---|---|---|
| **محافظه‌کار** | همه بازبینی | کندی |
| **متعادل** ⭐ | ریسک‌محور | — |
| **پرخاشگر** | خودکار زیاد | FN |

### اشکال شایع

**اشتباه ۱: نظارت نمایشی**
دکمهٔ تأیید بدون بررسی.

**اشتباه ۲: نبود زمان**
۵ ثانیه برای هر مورد.

**اشتباه ۳: اختیار رد بدون حمایت**
اگر رد کردن دردسر دارد، کسی رد نمی‌کند.

**اشتباه ۴: نبود canary**
نمی‌دانی بازبینی واقعی است.

**اشتباه ۵: نبود لاگ تصمیم**
پاسخ‌گویی ممکن نیست.

### نکات مهم (Tips & Tricks)

- **آستانهٔ اطمینان + ریسک = سطح نظارت.**
- **canary شفاف بگذار.**
- **«نیاز به داده» را به‌عنوان مسیر سوم بگذار.**
- **اطمینان مدل را نشان بده.**
- **هر تصمیم را لاگ کن.**

### خلاصه فصل

- چهار سطح نظارت؛ ریسک تعیین می‌کند.
- سه شرط: **اطلاعات، زمان، اختیار**.
- **خستگی تأیید** و **سوگیری اتوماسیون**، دو دشمن.
- canary، ابزار سنجش.
- «نیاز به داده» مسیر سوم است.
