## فصل ۶۵: سوگیری اتوماسیون و اعتماد بیش‌ازحد

### مقدمه

**سوگیری اتوماسیون** (Automation Bias) یعنی تمایل انسان به پذیرش پاسخ ماشین، حتی وقتی شواهد خلافش را نشان می‌دهد.

در امنیت، این یک آسیب‌پذیری است — نه یک ویژگی شخصیتی.

### مفاهیم اساسی

**سه شکل سوگیری**

| شکل | مثال |
|---|---|
| **پذیرش کور** | «AI گفت بی‌خطر است، پس بی‌خطر است» |
| **نادیده گرفتن شواهد** | «ولی لاگ چیز دیگری می‌گوید» → «حتماً لاگ اشتباه است» |
| **عدم جست‌وجو** | «نیازی به بررسی نیست» |

**چرا رخ می‌دهد؟**

| عامل | توضیح |
|---|---|
| **بار کاری** | زمان کم، بررسی سخت |
| **اعتماد به فناوری** | «کامپیوتر اشتباه نمی‌کند» |
| **ابهام مسئولیت** | «AI تصمیم گرفت» |
| **فشار سازمانی** | «سریع‌تر ببند» |

**نکتهٔ حیاتی:** سوگیری اتوماسیون، با **دقت بالای** ابزار **بیشتر** می‌شود. چون ابزار معمولاً درست است، انسان یاد می‌گیرد اعتماد کند — و در ۵٪ موارد که اشتباه است، نمی‌بیند.

**مفهوم «نرخ پذیرش» (Acceptance Rate)**

| نرخ | تفسیر |
|---|---|
| ۹۵٪+ | احتمالاً بررسی نمی‌شود |
| ۸۰–۹۰٪ | سالم |
| < ۷۰٪ | یا ابزار ضعیف، یا بازبین سخت‌گیر |

**این معیار، ساده و افشاگر است.**

**چهار کنترل**

| کنترل | اثر |
|---|---|
| **نمایش عدم‌قطعیت** | آگاهی از ریسک |
| **پرسش اجباری** | تفکر فعال |
| **موارد canary** | سنجش واقعی |
| **بازبینی مستقل** | چشم دوم |

### مثال‌های عملی

**Lab Scenario 65-A: اندازه‌گیری نرخ پذیرش**

```python
"""
محاسبهٔ نرخ پذیرش و زمان تصمیم — شاخص سوگیری
"""
from statistics import mean

decisions = [
    # (accept?, seconds)
    (True, 2), (True, 3), (True, 1), (True, 4), (True, 2),
    (True, 3), (False, 18), (True, 2), (True, 1), (True, 3),
]

accept_rate = sum(1 for a, _ in decisions if a) / len(decisions)
fast_accepts = sum(1 for a, s in decisions if a and s < 5)

print(f"نرخ پذیرش: {accept_rate:.0%}")
print(f"پذیرش سریع (<۵s): {fast_accepts}/{len(decisions)}")
print("⚠️ نشانهٔ بررسی نمایشی" if fast_accepts / len(decisions) > 0.6 else "✅ سالم")
```

**تفسیر:** پذیرش ۹۰٪ با میانگین ۲ ثانیه، یعنی بررسی نمی‌شود.

**Lab Scenario 65-B: طراحی برای تفکر فعال**

```markdown
# سه الگوی طراحی

## ۱. پرسش اجباری
قبل از تأیید: «کدام شاهد را بررسی کردی؟» (انتخاب از فهرست)

## ۲. نمایش عدم‌قطعیت
«اطمینان: ۶۲٪ (متوسط) — ۲ مورد مشابه قبلاً مثبت کاذب بود»

## ۳. موارد canary
۵٪ موارد، خطای عمدی دارند. اگر بازبین نگرفت، بررسی نکرده.

## ۴. بازبینی مستقل
برای موارد P1، نفر دوم بدون دیدن تصمیم اول بررسی کند.
```

**Lab Scenario 65-C: سناریوی واقعی**

| مرحله | چه اتفاقی | درس |
|---|---|---|
| AI هشدار را «benign» علامت می‌زند | تحلیلگر تأیید می‌کند | اعتماد |
| ۳ هفته بعد، همان الگو در رخداد واقعی | کسی بررسی نکرده بود | FN |
| بررسی | AI روی این نوع هشدار ۸۵٪ دقت داشت | دقت ≠ کفایت |
| اصلاح | آستانه + canary + بازبینی نمونه‌ای | کنترل |

**درس:** «۸۵٪ دقت» یعنی ۱۵٪ خطا — و اگر کسی چک نکند، آن ۱۵٪ دیده نمی‌شود.

### مقایسه و الگوهای مختلف

**مقایسهٔ دو مدل**

| | اعتماد کامل | اعتماد مشروط |
|---|---|---|
| سرعت | بالا | متوسط |
| ریسک FN | بالا | کم |
| مناسب | کم‌ریسک | همه |

**مقایسهٔ دو رویکرد آموزشی**

| | «به AI اعتماد کن» | «AI را نقد کن» |
|---|---|---|
| اثر | سوگیری بیشتر | کاهش سوگیری |

### اشکال شایع

**اشتباه ۱: آموزش «اعتماد به ابزار»**
باید «نقد ابزار» آموزش داد.

**اشتباه ۲: سنجش فقط دقت**
باید **نرخ پذیرش** هم سنجید.

**اشتباه ۳: نبود زمان**
۵ ثانیه برای هر مورد = بررسی نمایشی.

**اشتباه ۴: نبود canary**
نمی‌دانی بررسی واقعی است.

**اشتباه ۵: ابهام مسئولیت**
«AI تصمیم گرفت» — نه، انسان تأیید کرد.

### نکات مهم (Tips & Tricks)

- **نرخ پذیرش را ماهانه بسنج.**
- **canary شفاف بگذار.**
- **«کدام شاهد؟» را اجباری کن.**
- **موارد P1: بازبینی مستقل.**
- **مسئولیت را صریح کن: تأییدکننده، پاسخگوست.**

### خلاصه فصل

- سوگیری اتوماسیون: **پذیرش کور** ماشین.
- با دقت بالاتر، **بیشتر** می‌شود.
- **نرخ پذیرش** شاخص کلیدی است.
- چهار کنترل: **عدم‌قطعیت، پرسش، canary، بازبینی مستقل**.
- مسئولیت، بر عهدهٔ تأییدکننده است.

## فصل ۶۶: تقویت منفی کاذب — وقتی AI تهدید را نمی‌بیند

### مقدمه

**منفی کاذب** (False Negative) یعنی تهدید واقعی که AI «بی‌خطر» تشخیص داده. در SOC، این بدترین نوع خطاست — چون تهدید **دیده نمی‌شود**.

این فصل دربارهٔ چگونگی شکل‌گیری و کاهش آن است.

### مفاهیم اساسی

**چهار منبع FN**

| منبع | مثال |
|---|---|
| **دادهٔ ناکافی** | لاگ ناقص |
| **مدل ناآشنا** | تکنیک جدید |
| **آستانهٔ بالا** | فیلتر تهاجمی |
| **سوگیری داده** | گروه کم‌نمایندگی |

**مفهوم «FN پنهان»**

FN با FP فرق دارد: FP **دیده می‌شود** (تحلیلگر وقت تلف می‌کند)، FN **دیده نمی‌شود** (تا وقتی دیر شده).

**پیامد:** معیارهای معمول (FPR، دقت) FN را پنهان می‌کنند.

**چهار تکنیک کاهش**

| تکنیک | اثر |
|---|---|
| **آستانهٔ محافظه‌کارانه** | FN کم، FP زیاد |
| **تنوع دادهٔ آموزش** | پوشش بیشتر |
| **ترکیب چند مدل** | کاهش خطای مشترک |
| **بازخورد تحلیلگر** | یادگیری از FN |

**مفهوم «هزینهٔ نامتقارن»**

```
هزینهٔ FN  >>  هزینهٔ FP
```

پس آستانه باید به نفع **حساسیت** باشد — حتی با هزینهٔ نویز بیشتر.

**مفهوم «آزمون با تهدید شناخته‌شده»**

| روش | چطور |
|---|---|
| **Replay** | اجرای رخدادهای گذشته |
| **Purple Team** | شبیه‌سازی تکنیک |
| **Atomic Red Team** | تست‌های کوچک |

**نکته:** اگر مدل روی رخدادهای گذشته هم FN بدهد، مشکل جدی است.

### مثال‌های عملی

**Lab Scenario 66-A: محاسبهٔ FN**

```python
"""
محاسبهٔ FN و هزینهٔ آن
"""
def analyze(tp: int, fp: int, fn: int, tn: int,
            cost_fp: float = 20, cost_fn: float = 5000) -> dict:
    recall = tp / (tp + fn) if (tp + fn) else 0
    fpr = fp / (fp + tn) if (fp + tn) else 0
    total_cost = fp * cost_fp + fn * cost_fn
    return {
        "recall": round(recall, 3),
        "fpr": round(fpr, 4),
        "cost_fp": fp * cost_fp,
        "cost_fn": fn * cost_fn,
        "total": total_cost,
    }

# سناریو A: آستانهٔ بالا
print("A:", analyze(tp=70, fp=20, fn=30, tn=9880))
# سناریو B: آستانهٔ پایین
print("B:", analyze(tp=95, fp=400, fn=5, tn=9500))
```

**تفسیر:** سناریو B نویز بیشتری دارد (۴۰۰ FP)، ولی هزینهٔ کل کمتر است — چون FN گران‌تر است.

**Lab Scenario 66-B: آزمون Replay**

```markdown
# رویهٔ Replay

## ورودی
- ۵۰ رخداد گذشته با برچسب تأییدشده
- ۲۵ واقعی، ۲۵ بی‌خطر

## اجرا
۱. هر رخداد را به موتور AI بده
۲. خروجی را با برچسب مقایسه کن
۳. FN را جدا کن

## معیار
- FN > ۱۰٪ → بازبینی مدل/آستانه
- FN روی تکنیک‌های ATT&CK کلیدی → بازبینی فوری

## مستندسازی
جدول: رخداد | برچسب | خروجی AI | اطمینان | تصمیم
```

**Lab Scenario 66-C: بازخورد تحلیلگر**

```python
"""
ثبت بازخورد برای بهبود — ساختار داده
"""
from dataclasses import dataclass

@dataclass
class Feedback:
    alert_id: str
    ai_verdict: str
    human_verdict: str
    reason: str

    @property
    def is_fn(self) -> bool:
        return self.ai_verdict == "benign" and self.human_verdict == "malicious"

feedbacks = [
    Feedback("A-1", "benign", "malicious", "الگوی تازه، در آموزش نبود"),
    Feedback("A-2", "benign", "benign", "—"),
    Feedback("A-3", "malicious", "benign", "FP: اسکنر مجاز"),
]

fns = [f for f in feedbacks if f.is_fn]
print(f"FN: {len(fns)}")
for f in fns:
    print(" →", f.alert_id, f.reason)
```

**درس:** هر FN، یک نمونهٔ آموزشی رایگان است — اگر ثبت شود.

### مقایسه و الگوهای مختلف

**مقایسهٔ دو آستانه**

| | محافظه‌کار | تهاجمی |
|---|---|---|
| FN | کم | زیاد |
| FP | زیاد | کم |
| مناسب | امنیت | عملیات |

**مقایسهٔ دو رویکرد**

| | تک‌مدل | ترکیب مدل‌ها |
|---|---|---|
| FN | بیشتر | کمتر |
| پیچیدگی | کم | بالا |

### اشکال شایع

**اشتباه ۱: بهینه‌سازی FPR**
FN را بالا می‌برد.

**اشتباه ۲: نبود Replay**
نمی‌دانی روی تهدید واقعی چه می‌کند.

**اشتباه ۳: نادیده گرفتن بازخورد**
FN تکرار می‌شود.

**اشتباه ۴: آستانهٔ یکسان برای همهٔ هشدارها**
ریسک‌محور نیست.

**اشتباه ۵: فرض «مدل جدید، FN ندارد»**
همه مدل‌ها دارند.

### نکات مهم (Tips & Tricks)

- **آستانه را ریسک‌محور کن:** P1 محافظه‌کارانه، P4 تهاجمی.
- **Replay را دوره‌ای اجرا کن.**
- **هر FN را ثبت کن.**
- **هزینهٔ FN را در تصمیم بگیر.**
- **Purple Team را جدی بگیر.**

### خلاصه فصل

- FN پنهان است؛ FP دیده می‌شود.
- چهار منبع: **داده، مدل، آستانه، سوگیری**.
- هزینهٔ FN >> هزینهٔ FP.
- **Replay** و **Purple Team**، ابزار سنجش.
- بازخورد تحلیلگر، ارزان‌ترین بهبود.

## فصل ۶۷: نشت داده در ابزارهای امنیتی AI

### مقدمه

ابزار امنیتی، **حساس‌ترین دادهٔ سازمان** را می‌بیند: لاگ، IOC، پروندهٔ رخداد، توپولوژی شبکه. اگر این داده به یک ابزار AI بیرونی برود، نشت در بالاترین سطح است.

### مفاهیم اساسی

**پنج نوع دادهٔ حساس در SOC**

| نوع | مثال | ریسک |
|---|---|---|
| **لاگ خام** | IP، ایمیل، URL | PII، توپولوژی |
| **IOC** | دامنهٔ C2 | افشای تحقیق |
| **پروندهٔ رخداد** | timeline، قربانی | محرمانه |
| **توپولوژی** | نقشهٔ شبکه | شناسایی |
| **اعتبار** | کلید، توکن | دسترسی |

**چهار مسیر نشت**

| مسیر | مثال |
|---|---|
| **پرامپت** | چسباندن لاگ در چت‌بات عمومی |
| **آپلود** | فایل pcap |
| **افزونه** | ابزار ثالث با دسترسی |
| **حافظه** | تاریخچهٔ گفتگو |

**مفهوم «ابزار امنیتی، هدف است»**

اگر مهاجم به ابزار AI امنیتی دسترسی بگیرد:

| دستاورد | اثر |
|---|---|
| **دیدن هشدارها** | شناسایی تشخیص‌ها |
| **دیدن IOC** | تغییر زیرساخت |
| **تغییر قاعده** | کور کردن دفاع |

**درس:** ابزار AI امنیتی، خودش یک دارایی بحرانی است.

**مفهوم «حداقل داده»**

| کار | دادهٔ لازم | دادهٔ غیرلازم |
|---|---|---|
| خلاصهٔ هشدار | نوع، شدت، دارایی | نام کاربر، محتوای ایمیل |
| تحلیل لاگ | خطا، زمان | IP کامل، مسیر |
| گزارش رخداد | timeline | نام قربانی |

### مثال‌های عملی

**Lab Scenario 67-A: ماسک کردن لاگ**

```python
"""
ماسک کردن دادهٔ حساس در لاگ قبل از ارسال به AI
"""
import re

RULES = [
    (r"[\w\.-]+@[\w\.-]+\.\w+", "[EMAIL]"),
    (r"\b(?:\d{1,3}\.){3}\d{1,3}\b", "[IP]"),
    (r"(?<!\d)\d{10,16}(?!\d)", "[NUM]"),
    (r"\b[a-f0-9]{32,64}\b", "[HASH]"),
    (r"(?i)(token|key|password)=([^\s&]+)", r"\1=[SECRET]"),
    (r"\\\\[A-Za-z0-9\-]+\\[^\s]+", "[UNC]"),
]

def mask(text: str) -> str:
    for pat, repl in RULES:
        text = re.sub(pat, repl, text)
    return text

sample = """2026-11-12 09:14 login fail user=ali@example.com src=203.0.113.45
token=abc123def456 path=\\\\fs01\\hr\\salaries.xlsx"""
print(mask(sample))
```

**هشدار:** ماسک کردن، **کامل نیست**. نام‌ها، مسیرها و زمینه، می‌توانند شناسایی کنند.

**Lab Scenario 67-B: تصمیم ابزار**

| ابزار | داده | مجاز؟ |
|---|---|---|
| چت‌بات عمومی | لاگ خام | ❌ |
| چت‌بات سازمانی | لاگ ماسک‌شده | ✅ |
| ابزار با قرارداد | IOC | ⚠️ با بررسی |
| ابزار محلی | همه | ✅ |

**Lab Scenario 67-C: چک‌لیست**

```markdown
□ داده طبقه‌بندی شده
□ ابزار مجاز برای آن سطح
□ ماسک کردن اعمال شده
□ لاگ گفتگو با AI، نگهداری کوتاه
□ حافظهٔ ابزار خاموش
□ دسترسی ابزار، حداقل
□ قرارداد با فروشنده (عدم آموزش)
```

### مقایسه و الگوهای مختلف

**مقایسهٔ سه سطح**

| سطح | ابزار | داده |
|---|---|---|
| **باز** | عمومی | ❌ |
| **سازمانی** | قرارداد | ماسک‌شده |
| **محلی** | خودت | همه |

**مقایسهٔ دو رویکرد**

| | ماسک | دادهٔ ساختگی |
|---|---|---|
| دقت | حفظ | کم |
| امنیت | متوسط | بالا |
| مناسب | تحلیل | آموزش |

### اشکال شایع

**اشتباه ۱: «ابزار امنیتی است، پس امن است»**
ابزار AI، سطح حملهٔ جدید.

**اشتباه ۲: ماسک ناقص**
ترکیب فیلدها، شناسایی می‌کند.

**اشتباه ۳: نادیده گرفتن حافظه**
گفتگوی قبلی، داده را نگه می‌دارد.

**اشتباه ۴: افزونهٔ ثالث**
دسترسی بیش‌ازحد.

**اشتباه ۵: نبود قرارداد**
داده برای آموزش استفاده می‌شود.

### نکات مهم (Tips & Tricks)

- **ابزار AI امنیتی = دارایی بحرانی.**
- **ماسک، حداقل.**
- **دادهٔ ساختگی برای آموزش.**
- **حافظه را خاموش کن.**
- **قرارداد: عدم آموزش.**

### خلاصه فصل

- پنج نوع دادهٔ حساس در SOC.
- چهار مسیر نشت.
- ابزار AI امنیتی، **هدف** است.
- **حداقل داده**، اصل اول.
- ماسک، حداقل — نه کافی.

## فصل ۶۸: دستکاری خصمانهٔ دفاع‌های AI

### مقدمه

مهاجم می‌داند سازمان از AI برای دفاع استفاده می‌کند. پس **دفاع را هدف می‌گیرد**: با دادهٔ سمی، با ورودی دستکاری‌شده، یا با سوءاستفاده از اعتماد تحلیلگر.

### مفاهیم اساسی

**چهار حمله به دفاع AI**

| حمله | مکانیزم | اثر |
|---|---|---|
| **Evasion** | ورودی طوری تغییر کند که تشخیص نبیند | FN |
| **Poisoning** | دادهٔ آموزش دستکاری شود | رفتار مخدوش |
| **Model Extraction** | کپی رفتار دفاع | طراحی حمله |
| **Alert Fatigue Attack** | تولید هشدار انبوه | پنهان‌سازی |

**مفهوم «Alert Fatigue Attack»**

مهاجم، عمداً هشدارهای بی‌خطر تولید می‌کند تا:

| مرحله | اثر |
|---|---|
| ۱. حجم بالا | تحلیلگر خسته |
| ۲. هشدارهای تکراری | آستانهٔ توجه بالا |
| ۳. حملهٔ واقعی | در نویز پنهان می‌شود |

**این حمله، ارزان و مؤثر است** — و AI می‌تواند آن را آسان‌تر کند (تولید انبوه).

**مفهوم «Evasion در برابر AI»**

| روش | مثال |
|---|---|
| **تغییر جزئی** | دستور shell با فاصله/نویسهٔ مشابه |
| **تقسیم** | عملیات در چند مرحله |
| **زمان‌بندی** | اجرا در ساعت شلوغ |
| **زبان** | تغییر زبان/رمزگذاری |

**نکته:** مدل‌های دفاعی، اغلب روی الگوهای **آشکار** آموزش دیده‌اند. تغییر کوچک، آن‌ها را دور می‌زند.

**مفهوم «اعتماد به‌عنوان سطح حمله»**

مهاجم می‌تواند:

| اقدام | هدف |
|---|---|
| تولید هشدار جعلی | انحراف توجه |
| آلوده کردن IOC | مسدودسازی مشروع |
| تغییر سند دانش | پاسخ غلط |

### مثال‌های عملی

**Lab Scenario 68-A: تشخیص Alert Fatigue Attack**

```python
"""
تشخیص انفجار هشدار — نشانهٔ حملهٔ خستگی
"""
from statistics import mean, pstdev

# هشدار در هر ساعت (۲۴ ساعت)
baseline = [40, 38, 42, 45, 50, 55, 60, 58, 52, 48, 45, 42,
            40, 38, 41, 43, 46, 50, 48, 44, 42, 40, 39, 37]
current = baseline.copy()
current[9] = 400     # انفجار
current[10] = 380

mu, sd = mean(baseline), pstdev(baseline)
for h, c in enumerate(current):
    z = (c - mu) / sd if sd else 0
    if z > 3:
        print(f"ساعت {h}: {c} هشدار | z={z:.1f} ⚠️")
```

**درس:** انفجار هشدار، خودش یک سیگنال است.

**Lab Scenario 68-B: تنوع در تشخیص**

| رویکرد | مقاومت به Evasion |
|---|---|
| امضای دقیق | کم |
| الگوی عمومی | متوسط |
| رفتار | بالا |
| ترکیب | بالا |

**توصیه:** حداقل دو روش مستقل.

**Lab Scenario 68-C: چک‌لیست مقاوم‌سازی دفاع**

```markdown
□ تشخیص، فقط امضا نیست
□ آزمون Evasion دوره‌ای
□ پایش انفجار هشدار
□ IOC از منابع معتبر
□ بازبینی سند دانش
□ آزمون Poisoning
□ آموزش تحلیلگر: «هشدار زیاد ≠ حملهٔ زیاد»
```

### مقایسه و الگوهای مختلف

**مقایسهٔ سه حمله**

| حمله | نیاز | اثر |
|---|---|---|
| Evasion | دانش تشخیص | FN |
| Poisoning | دسترسی داده | رفتار مخدوش |
| Fatigue | منابع | پنهان‌سازی |

**مقایسهٔ دو رویکرد دفاعی**

| | ایستا | تطبیقی |
|---|---|---|
| مقاومت | کم | بالا |
| نگهداری | کم | زیاد |

### اشکال شایع

**اشتباه ۱: فرض «مهاجم دفاع AI را نمی‌شناسد»**
می‌شناسد.

**اشتباه ۲: تشخیص تک‌روشی**
Evasion ساده.

**اشتباه ۳: نادیده گرفتن انفجار هشدار**
خستگی، سلاح است.

**اشتباه ۴: اعتماد به IOC بدون منبع**
مسدودسازی مشروع.

**اشتباه ۵: نبود آزمون دوره‌ای**
دفاع، کهنه می‌شود.

### نکات مهم (Tips & Tricks)

- **دو روش تشخیص مستقل.**
- **انفجار هشدار را هشدار بده.**
- **آزمون Evasion دوره‌ای.**
- **IOC با منبع.**
- **تحلیلگر را آموزش بده.**

### خلاصه فصل

- چهار حمله: **Evasion، Poisoning، Extraction، Fatigue**.
- **Alert Fatigue Attack**، ارزان و مؤثر.
- Evasion با تغییر کوچک کار می‌کند.
- تشخیص تک‌روشی، شکننده است.
- اعتماد، سطح حمله است.
