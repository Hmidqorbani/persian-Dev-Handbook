## فصل ۱: Git و GitHub چیست و چرا بدون آن‌ها نمی‌شود کار کرد

### مقدمه

تصور کن یک فایل Word داری به نام `پایان‌نامه-نهایی.docx`. یک هفته بعد می‌شود `پایان‌نامه-نهایی-واقعی.docx`. بعد `پایان‌نامه-نهایی-واقعی-اصلاح-استاد.docx`. بعد `پایان‌نامه-نهایی-واقعی-اصلاح-استاد-این-آخری.docx`. همه‌ی ما این تجربه را داریم. مشکل این است که:

- نمی‌دانی بین نسخه‌ی سوم و پنجم دقیقاً چه تغییری دادی.
- نمی‌توانی دو نفر هم‌زمان روی یک فایل کار کنند بدون اینکه یکی کار دیگری را پاک کند.
- اگر نسخه‌ی چهارم را پاک کنی، راهی برای برگشت نداری.
- هیچ‌کس نمی‌داند چه کسی، چه زمانی، چرا یک جمله را عوض کرده.

**Git** دقیقاً برای حل همین چهار مشکل ساخته شد. نه برای برنامه‌نویس‌ها؛ برای هر کسی که روی فایلی کار می‌کند و می‌خواهد تاریخش را نگه دارد. وکیل‌ها، نویسنده‌ها، تیم‌های طراحی، دانشجوها — همه از Git استفاده می‌کنند.

**GitHub** هم چیزی است روی Git: یک وب‌سایت که مخزن‌های Git را میزبانی می‌کند و لایه‌ی همکاری روی آن می‌گذارد — Issues، Pull Request، Code Review، Actions، امنیت و Copilot.

**چرا این موضوع مهم است؟** چون تقریباً هر شرکت نرم‌افزاری، از استارتاپ دو نفره تا سازمان چند هزار نفره، کارش را روی Git و معمولاً روی GitHub سازمان می‌دهد. بلد نبودن Git در سال ۲۰۲۶ مثل بلد نبودن ایمیل است: نه اینکه نشود کار کرد، بلکه همه مجبور می‌شوند دور تو بچرخند.

**کاربردهای واقعی و ملموس:**

- تیم پشتیبانی یک فروشگاه اینترنتی، متن قالب‌های پاسخ را در Git نگه می‌دارد. هر تغییر قابل ردیابی است و اگر متنی بد شد، در یک ثانیه برمی‌گردد.
- یک تیم سه‌نفره روی یک اپلیکیشن موبایل کار می‌کند. هر نفر روی شاخه‌ی خودش کار می‌کند، و PR هر کس قبل از merge توسط دو نفر دیگر بررسی می‌شود.
- یک دانشجوی ارشد، کد تحلیل داده‌ی پایان‌نامه‌اش را در مخزن عمومی می‌گذارد تا داور بتواند نتایج را بازتولید کند.
- یک شرکت، هر شب به‌طور خودکار تست‌ها را روی GitHub Actions اجرا می‌کند و اگر شکست خورد، به تیم اطلاع می‌دهد.

### مفاهیم اساسی

#### Git چیست؟ (و چه نیست)

Git یک **سیستم کنترل نسخه‌ی توزیع‌شده** (Distributed Version Control System یا DVCS) است. سه کلمه‌اش را باز کنیم:

**کنترل نسخه (Version Control):** هر تغییر را به‌عنوان یک نقطه‌ی مشخص در تاریخ ثبت می‌کند. به این نقاط **commit** می‌گوییم. هر commit می‌داند چه چیزی عوض شد، چه کسی عوض کرد، چه زمانی، و چرا (در پیام commit).

**توزیع‌شده (Distributed):** هر کسی که مخزن را clone می‌کند، **کل تاریخ** را روی سیستم خودش دارد. این تفاوت بنیادی با سیستم‌های قدیمی مثل SVN است که فقط آخرین نسخه را می‌گرفتند و تاریخ روی سرور بود. نتیجه‌اش:

- می‌توانی بدون اینترنت commit بزنی، branch بسازی، تاریخ را ببینی.
- اگر سرور از بین برود، هر clone یک نسخه‌ی کامل و سالم است.
- سرعت: تقریباً همه‌ی عملیات محلی است، پس فوری انجام می‌شود.

**سیستم (System):** Git یک ابزار خط فرمان است که فایل‌هایش را در پوشه‌ای مخفی به نام `.git` نگه می‌دارد. اگر آن پوشه را پاک کنی، تاریخ می‌رود و فقط فایل‌های معمولی می‌مانند.

Git **نیست**:

- Git یک سرویس ابری نیست. Git روی لپ‌تاپ تو اجرا می‌شود، حتی بدون اینترنت.
- Git یک رابط گرافیکی نیست. رابط‌های گرافیکی (GitHub Desktop، VS Code، Fork، Sourcetree) روی Git سوار می‌شوند.
- Git بکاپ خودکار نیست. اگر commit نکنی، چیزی ذخیره نشده.

#### GitHub چیست؟

GitHub یک **پلتفرم میزبانی مخزن** است. کار اصلی‌اش این است که یک مخزن Git را روی سرور نگه دارد تا چند نفر بتوانند با آن کار کنند. ولی از این پایه فراتر رفته و امروز یک پلتفرم کامل توسعه است:

| لایه | چه می‌دهد |
|---|---|
| **میزبانی مخزن** | نگهداری کد، تاریخ، شاخه‌ها، دسترسی |
| **همکاری** | Issues، Pull Requests، Code Review، Discussions، Projects |
| **اتوماسیون** | GitHub Actions (CI/CD)، Dependabot، webhooks |
| **امنیت** | Code Scanning، Secret Scanning، Security Advisories، Rulesets |
| **هوش مصنوعی** | Copilot (completion، chat، agent، code review) |
| **میزبانی محصول** | Pages، Packages، Releases، Codespaces |

#### تفاوت را یک بار برای همیشه یاد بگیر

```
Git                          GitHub
─────────────────────        ─────────────────────
ابزار (نرم‌افزار)             سرویس (وب‌سایت)
روی سیستم تو اجرا می‌شود      روی سرورهای مایکروسافت
بدون اینترنت کار می‌کند       بدون اینترنت کار نمی‌کند
commit، branch، merge        Issue، PR، Actions، Copilot
رایگان و متن‌باز             رایگان برای مخازن عمومی، پلن پرداختی برای خصوصی
```

یک تشبیه: **Git مثل دفترچه‌ی یادداشت شخصی توست، GitHub مثل قفسه‌ی مشترک دفتر تیم.** می‌توانی بدون قفسه هم یادداشت بنویسی؛ ولی اگر می‌خواهی دیگران ببینند و نظر بدهند، قفسه لازم است.

#### سه حالت فایل در Git

این مفهوم پایه‌ای است و اگر همین‌جا درست یاد بگیری، نصف سردرگمی‌های بعدی حذف می‌شود. Git هر فایل را در یکی از سه ناحیه می‌بیند:

```
┌─────────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│  Working Directory  │ → │  Staging Area    │ → │  Repository      │
│  (فایل‌های واقعی)     │   │  (index)         │   │  (.git)          │
└─────────────────────┘   └──────────────────┘   └──────────────────┘
        ویرایش می‌کنی           git add می‌زنی          git commit می‌زنی
```

- **Working Directory:** همان پوشه‌ای که با Explorer یا VS Code می‌بینی. اینجا فایل‌ها را ویرایش می‌کنی.
- **Staging Area (یا index):** یک «سبد خرید». فایل‌هایی که می‌خواهی در commit بعدی باشند را اینجا می‌گذاری. چرا؟ چون ممکن است ۱۰ فایل را عوض کرده باشی ولی بخواهی در دو commit منطقی جدا ثبت کنی.
- **Repository:** تاریخچه‌ی ثبت‌شده. هر commit یک نقطه‌ی بازگشت است.

تشبیه روزمره: عکاسی. Working Directory صحنه است، Staging Area انتخاب کادری است که می‌خواهی عکس بگیری، و commit دکمه‌ی شاتر.

### مثال‌های عملی

#### مثال ۱: از صفر تا اولین commit

```bash
# ۱) یک پوشه بساز و واردش شو
mkdir ~/github-lab/first-repo
cd ~/github-lab/first-repo

# ۲) به Git بگو اینجا را مدیریت کن
git init
# خروجی: Initialized empty Git repository in /home/user/github-lab/first-repo/.git/

# ۳) ببین چه خبر است
git status
# On branch main
# No commits yet
# nothing to commit (create/copy files and use "git add" to track)

# ۴) یک فایل بساز
echo "# پروژه‌ی تمرینی من" > README.md

# ۵) دوباره وضعیت را ببین
git status
# Untracked files:
#   README.md
# فایل قرمز است: Git می‌بیندش ولی ردیابی‌اش نمی‌کند

# ۶) فایل را به سبد خرید اضافه کن
git add README.md
git status
# Changes to be committed:
#   new file:   README.md
# حالا سبز است

# ۷) ثبت کن
git commit -m "docs: افزودن README اولیه"
# [main (root-commit) 3f2a1b9] docs: افزودن README اولیه
#  1 file changed, 1 insertion(+)

# ۸) تاریخ را ببین
git log --oneline
# 3f2a1b9 docs: افزودن README اولیه
```

**توضیح خط به خط:**

- `git init` پوشه‌ی `.git` را می‌سازد. از این لحظه هر تغییری در این پوشه زیر نظر Git است.
- `git status` پرکارترین دستور Git است. عادت کن قبل و بعد از هر کار آن را بزنی.
- `git add README.md` فایل را از working directory به staging می‌برد. **هیچ چیزی هنوز ذخیره نشده.**
- `git commit -m "..."` یک snapshot از staging می‌سازد. پیام باید بگوید «چه کاری انجام شد»، نه «چه فایلی عوض شد».

#### مثال ۲: یک چرخه‌ی واقعی‌تر

```bash
# یک فایل جدید و یک تغییر در فایل قبلی
echo "print('سلام')" > main.py
echo "## نصب" >> README.md

git status
# modified:   README.md
# Untracked:  main.py

# فقط README را stage کن (کامیت مستقل)
git add README.md
git commit -m "docs: افزودن بخش نصب"

# حالا main.py را جدا ثبت کن
git add main.py
git commit -m "feat: افزودن اسکریپت سلام"

git log --oneline
# a91c4d2 feat: افزودن اسکریپت سلام
# 7b3e8f0 docs: افزودن بخش نصب
# 3f2a1b9 docs: افزودن README اولیه
```

این همان «اتمیک بودن commit» است: هر commit یک تغییر منطقی. اگر بعداً بفهمی اسکریپت سلام مشکل داشت، می‌توانی فقط همان را برگردانی بدون اینکه مستندات را از دست بدهی.

#### مثال ۳: بدون staging، با `-a`

```bash
# اگر همه‌ی فایل‌های ردیابی‌شده را می‌خواهی، لازم نیست تک‌تک add کنی
git commit -am "fix: اصلاح متن"

# توجه: -a فایل‌های جدید (untracked) را شامل نمی‌شود!
```

این تله‌ی کلاسیک مبتدی‌هاست: فایل جدید ساختی، `-am` زدی، commit ثبت شد، ولی فایل جدید داخلش نیست. برای همین `git status` را قبل از commit همیشه بزن.

#### مثال ۴: دیدن تفاوت‌ها

```bash
echo "print('خداحافظ')" > main.py

git diff                    # تغییرات staging نشده
# -print('سلام')
# +print('خداحافظ')

git add main.py
git diff --staged           # تغییراتی که در commit بعدی می‌روند
```

`git diff` مثل «نسخه‌ی قبل» و «نسخه‌ی الان» را کنار هم می‌گذارد. `-` خطی که رفته، `+` خطی که آمده.

### اشکال شایع

#### ۱. «Git و GitHub یکی هستند»

شایع‌ترین اشتباه. نتیجه‌اش این می‌شود که کسی می‌گوید «Git قطع است» در حالی که اینترنتش قطع است، یا فکر می‌کند بدون حساب GitHub نمی‌تواند Git یاد بگیرد. Git کاملاً مستقل است.

#### ۲. فکر کردن اینکه commit = ذخیره‌ی خودکار

Git خودش commit نمی‌زند. اگر یک ساعت کد نوشتی و commit نزدی، همان یک ساعت در هیچ تاریخی نیست. **قاعده:** هر بار که یک واحد کار تمام شد (یک تابع، یک رفع باگ، یک بخش از مستند)، commit بزن.

#### ۳. commit با پیام «update» یا «fix»

```
✗ git commit -m "update"
✗ git commit -m "."
✗ git commit -m "fix"
✓ git commit -m "fix(auth): رفع خطای ورود با ایمیل بزرگ‌حرف"
```

شش ماه بعد، `git log` پر از `update` است و هیچ‌کس نمی‌فهمد کدام commit چه کاری کرد. پیام commit یک سرمایه‌گذاری کوچک با بازده بزرگ است.

#### ۴. commit کردن همه‌چیز با هم

یک commit که ۴۰ فایل را عوض کرده و شامل «رفع باگ + تغییر ظاهر + ارتقای کتابخانه» است، غیرقابل بازبینی است. اگر لازم شد فقط ارتقای کتابخانه را برگردانی، نمی‌توانی.

#### ۵. گذاشتن فایل‌های حساس در مخزن

```
✗ .env
✗ config/database.yml با پسورد
✗ id_rsa
✗ node_modules/
✗ *.log
```

اگر یک بار push شود، حتی اگر پاکش کنی، در تاریخ می‌ماند. در فصل ۴ و فصل ۷۳ کامل توضیح می‌دهیم چطور جلوی این را بگیریم — و اگر اتفاق افتاد چه کنیم.

#### ۶. ترس از branch

خیلی‌ها همه‌ی کار را روی `main` انجام می‌دهند چون «branch خطرناک است». در واقع branch در Git ارزان‌ترین چیز دنیاست: ۴۱ بایت. نترسیدن از branch بزرگ‌ترین قدم بلوغ با Git است.

### نکات مهم (Tips & Tricks)

- **`git status` را زیاد بزن.** قبل از add، بعد از add، قبل از commit. این عادت جلوی ۹۰٪ فاجعه‌ها را می‌گیرد.
- **`git add -p`** را یاد بگیر: به‌جای اضافه کردن کل فایل، Git تکه‌تکه نشان می‌دهد و می‌پرسی کدام تکه برود. برای کامیت‌های تمیز فوق‌العاده است.
- **`git log --oneline --graph --all`** یک نمای درختی از کل تاریخ می‌دهد. یک alias برایش بساز (فصل ۵ و ۱۹).
- **پیام commit را با فعل امری بنویس:** `add`، `fix`، `refactor` — نه `added`، `fixed`. چون جمله‌ی «این commit ... می‌کند» را کامل می‌کند.
- **اگر پشیمان شدی، Git تقریباً همیشه راه برگشت دارد.** `git reflog` شبکه‌ی نجات است (فصل ۲۲). پس جسور باش.
- **`.git` را دستی دست نزن.** فایل‌های داخلش را ویرایش نکن؛ فقط از دستورهای Git استفاده کن.

### خلاصه فصل

- **Git** ابزار کنترل نسخه‌ی توزیع‌شده و محلی است؛ **GitHub** سرویس میزبانی و همکاری روی آن.
- هر فایل در Git از سه ناحیه می‌گذرد: **Working Directory → Staging → Repository**.
- چرخه‌ی روزمره: `status` → `add` → `commit` → `log`.
- commit باید **اتمیک** و پیامش **معنادار** باشد.
- شایع‌ترین اشتباه‌ها: یکی دانستن Git و GitHub، پیام‌های بی‌معنی، commit کردن همه‌چیز با هم، و گذاشتن فایل حساس در مخزن.

**سؤالات مروری:**
1. اگر اینترنت قطع شود، کدام کارها با Git ممکن است و کدام نه؟
2. چرا Staging Area وجود دارد؟ اگر نبود چه مشکلی پیش می‌آمد؟
3. تفاوت `git add .` و `git commit -am` چیست؟

## فصل ۲: مدل ذهنی Git — همه‌چیز یک اشاره‌گر است

### مقدمه

اکثر کسانی که Git را «سخت» می‌دانند، در واقع Git را بلد نیستند — یک سری دستور حفظ کرده‌اند. لحظه‌ای که مدل ذهنی درست را بگیری، Git ساده و حتی زیبا می‌شود. این فصل همان لحظه است.

**چرا مهم است؟** چون تمام تصمیم‌های گیج‌کننده — «چرا reset کردم و کدم رفت؟»، «detached HEAD چیست؟»، «چرا rebase این‌طور کرد؟» — فقط با مدل ذهنی درست جواب می‌گیرند. بدون آن، مجبوری هر بار از یک نفر بپرسی.

**کاربرد عملی:** وقتی بدانی branch فقط یک برچسب متحرک است، دیگر از ساختن ده شاخه نمی‌ترسی. وقتی بدانی commit یک snapshot کامل است (نه diff)، می‌فهمی چرا Git این‌قدر سریع می‌تواند بین نسخه‌ها بپرد.

### مفاهیم اساسی

#### Git snapshot می‌گیرد، نه diff

بسیاری فکر می‌کنند Git تفاوت‌ها را ذخیره می‌کند (مثل SVN). در واقع Git از **هر commit یک snapshot کامل از کل درخت فایل‌ها** می‌گیرد. فقط فایل‌هایی که تغییر نکرده‌اند، دوباره ذخیره نمی‌شوند — Git به همان نسخه‌ی قبلی **اشاره** می‌کند.

```
commit A:  [README v1] [main.py v1] [utils.py v1]
commit B:  [README v1] [main.py v2] [utils.py v1]
              ↑ همان          ↑ جدید         ↑ همان
              (اشاره)                       (اشاره)
```

نتیجه: هر commit یک «عکس کامل از پروژه در آن لحظه» است. برای همین `git checkout` هر commit فوری است.

#### شیء (object) — واحد بنیادی Git

Git همه‌چیز را به‌صورت شیء ذخیره می‌کند. چهار نوع:

| نوع | چیست | مثال |
|---|---|---|
| **blob** | محتوای یک فایل | متن `main.py` |
| **tree** | یک پوشه (فهرست blob و tree) | `src/` |
| **commit** | یک snapshot + متادیتا | «چه کسی، کِی، چرا، والدها» |
| **tag** | برچسب با نام روی یک commit | `v1.0.0` |

هر شیء با هش SHA-1 (و امروز در برخی تنظیمات SHA-256) شناسایی می‌شود. همان رشته‌ی ۴۰ کاراکتری مثل `3f2a1b9c...`. این هش از محتوا محاسبه می‌شود، پس:

- محتوای یکسان = هش یکسان (ذخیره‌ی بهینه)
- تغییر محتوا = هش جدید (تغییرناپذیری تاریخ)

**نکته‌ی مهم:** هش commit فقط از محتوای فایل‌ها نیست؛ از پیام، نویسنده، زمان و **هش commit والد** هم هست. برای همین اگر یک commit قدیمی را تغییر بدهی، هش آن عوض می‌شود و همه‌ی commitهای بعدی هم هش جدید می‌گیرند. این «زنجیره» همان چیزی است که تاریخ را قابل اعتماد می‌کند — و همان چیزی که rebase را «تاریخ را بازنویسی می‌کند» می‌سازد.

#### commit یک گره در گراف است

هر commit به یک یا چند commit والد اشاره می‌کند:

```
A ← B ← C ← D
```

این یک تاریخ خطی است. وقتی merge می‌کنی، یک commit با **دو والد** ساخته می‌شود:

```
A ← B ← C ←──── M
     ↖       ↗
       X ← Y
```

`M` دو والد دارد: `C` و `Y`. برای همین Git می‌تواند گراف باشد، نه لیست. و برای همین `git log --graph` معنا دارد.

#### branch = یک اشاره‌گر متحرک

این مهم‌ترین جمله‌ی این فصل است:

> **یک branch در Git فقط یک فایل متنی کوچک است که یک هش commit را نگه می‌دارد.**

```
.git/refs/heads/main  →  محتوایش: 3f2a1b9c4d5e...
.git/refs/heads/feature  →  محتوایش: 7b3e8f0a1c2d...
```

وقتی commit می‌زنی، Git هش جدید را می‌سازد و **همان branch که رویش هستی** را به آن هش منتقل می‌کند. تمام. این تمام کاری است که branch انجام می‌دهد.

```
قبل از commit:   A ← B ← C          (main → C)
بعد از commit:   A ← B ← C ← D      (main → D)
```

پس ساختن branch یک عملیات تقریباً صفر است: فقط یک فایل ۴۱ بایتی. به همین دلیل Git می‌تواند هزاران branch داشته باشد بدون اینکه کند شود.

#### `HEAD` — «الان کجایی؟»

`HEAD` اشاره‌گری است به شاخه‌ای که رویش هستی:

```
HEAD → main → 3f2a1b9
```

- **حالت عادی (attached):** `HEAD` به یک branch اشاره می‌کند. commit می‌زنی، branch جلو می‌رود.
- **حالت detached:** `HEAD` مستقیم به یک commit اشاره می‌کند. commit بزنی، هیچ branch ای جلو نمی‌رود و commit «بی‌صاحب» می‌شود (تا وقتی با reflog پیدایش کنی).

#### مدل ذهنی نهایی — یک تصویر

```
                    HEAD
                     ↓
                    main
                     ↓
   A ← B ← C ← D ← E
        ↑
     feature
```

- `E` آخرین commit روی `main` است.
- `feature` روی `C` ایستاده — یعنی از `C` منشعب شده و هنوز commit جدیدی ندارد.
- اگر روی `feature` بروی و commit بزنی:

```
   A ← B ← C ← D ← E        (main)
            ↖
             F ← G          (feature)  ← HEAD
```

#### `origin` چیست؟

`origin` فقط یک **نام مستعار** برای آدرس یک remote است. هیچ چیز جادویی ندارد:

```bash
git remote -v
# origin  git@github.com:user/repo.git (fetch)
# origin  git@github.com:user/repo.git (push)
```

می‌توانستی اسمش را `github` یا `ali` بگذاری. `origin` فقط قرارداد رایج است.

### مثال‌های عملی

#### مثال ۱: دیدن اینکه branch واقعاً چیست

```bash
mkdir ~/github-lab/mental-model && cd ~/github-lab/mental-model
git init -q
echo "v1" > file.txt
git add . && git commit -qm "first"
echo "v2" >> file.txt
git commit -qam "second"

# ببین branch یک فایل متنی است
cat .git/refs/heads/main
# e7a3f9c1b2d4... (هش commit دوم)

# ببین HEAD چه می‌گوید
cat .git/HEAD
# ref: refs/heads/main

# لیست همه‌ی refها با هش‌شان
git show-ref
```

**توضیح:** حالا با چشم خودت دیدی که `main` فقط یک فایل است که یک هش دارد. این تمام راز است.

#### مثال ۲: ساختن branch و دیدن حرکت اشاره‌گر

```bash
git branch feature          # branch بساز، ولی به آن نرو
git switch feature          # برو رویش (Git 2.23+)
# یا: git checkout feature  (روش قدیمی)

cat .git/HEAD
# ref: refs/heads/feature

git branch -v
# * feature e7a3f9c second
#   main    e7a3f9c second
# هر دو روی همان commit هستند

echo "v3" >> file.txt
git commit -qam "third on feature"

git branch -v
# * feature 9d1c8a7 third on feature
#   main    e7a3f9c second
# feature جلو رفت، main سر جایش ماند
```

#### مثال ۳: detached HEAD — و چرا ترسناک نیست

```bash
git switch --detach HEAD~1     # برو روی commit قبلی، بدون branch
# Note: switching to 'HEAD~1'.
# You are in 'detached HEAD' state.

cat .git/HEAD
# 9d1c8a7...  ← مستقیم یک هش، نه ref

echo "آزمایش" >> file.txt
git commit -qam "experiment"

# این commit روی هیچ branch ای نیست
git log --oneline -1
# a1b2c3d experiment

# راه نجات: یک branch از همین‌جا بساز
git switch -c experiment-branch
# حالا commit صاحب دارد
```

**چرا detached HEAD اتفاق می‌افتد؟** هر وقت به‌جای یک branch، یک commit مشخص را checkout کنی: `git checkout v1.0.0`، `git checkout HEAD~3`، یا وقتی وسط rebase/interactive هستی.

**قاعده‌ی طلایی:** اگر در detached HEAD هستی و می‌خواهی کاری کنی که ارزش نگه داشتن دارد، اول `git switch -c name` بزن.

#### مثال ۴: مقایسه‌ی دو commit از دید snapshot

```bash
git diff main..feature        # تفاوت دو نوک
git diff main...feature       # تفاوت از نقطه‌ی انشعاب (سه نقطه!)
```

`..` یعنی «بین دو نقطه»، `...` یعنی «از جایی که جدا شدند». تفاوتشان در فصل ۱۵ و ۳۳ مهم می‌شود.

### مقایسه و الگوهای مختلف

#### snapshot در برابر delta

| | snapshot (Git) | delta (SVN، برخی بکاپ‌ها) |
|---|---|---|
| سرعت checkout | فوری (فقط کپی) | باید زنجیره‌ی diff اعمال شود |
| فضا | اشتراک‌گذاری blobها | فقط تفاوت‌ها |
| branch | تقریباً رایگان | سنگین |
| پیچیدگی بازیابی | کم | زیاد (اگر زنجیره بشکند) |

#### branch در برابر clone

| | branch | clone |
|---|---|---|
| چه می‌سازد | یک اشاره‌گر ۴۱ بایتی | یک کپی کامل از کل تاریخ |
| هزینه | صفر | می‌تواند صدها مگابایت باشد |
| برای چه | کار موازی روی یک مخزن | کار مستقل / fork |

بعضی‌ها برای هر ویژگی یک clone جدید می‌سازند. این کار غلط است — کند، گیج‌کننده، و دیسک‌پرکن. branch بساز.

#### `switch` در برابر `checkout`

| | `git switch` | `git checkout` |
|---|---|---|
| معرفی | Git 2.23 | از اول |
| کار | فقط عوض کردن branch | branch + فایل + commit + ... |
| خطر | کم | زیاد (اگر اشتباه بزنی فایل‌ها را می‌پرد) |
| توصیه | استفاده کن | برای بازگرداندن فایل لازم است (`git restore` بهتر است) |

### اشکال شایع

#### ۱. «branch ساختم ولی تغییراتم رفت»

تقریباً همیشه یعنی در detached HEAD commit زده‌ای، یا branch را نساخته‌ای و فقط `checkout` کرده‌ای. راه‌حل: `git reflog` (فصل ۲۲) — commit گم نمی‌شود، فقط پیدا کردنش را باید بلد باشی.

#### ۲. فکر کردن `main` «شاخه‌ی اصلی» است در Git

`main` فقط یک نام قراردادی است (قبلاً `master` بود). Git هیچ شاخه‌ای را مقدس نمی‌داند. «اصلی بودن» یک **قرارداد تیمی** است، نه ویژگی فنی. می‌توانی `main` را پاک کنی و `develop` را اصلی کنی — Git اجازه می‌دهد، ولی تیمت گیج می‌شود.

#### ۳. commit کردن روی branch اشتباه

```
✗ روی main هستی، فکر می‌کنی روی feature هستی، commit می‌زنی
```

راه‌حل فوری:

```bash
git branch feature          # branch از موقعیت فعلی بساز
git reset --hard HEAD~1     # main را یک قدم عقب ببر
git switch feature          # commit حالا روی feature است
```

پیشگیری: در prompt خط فرمان، نام branch را نشان بده. یا `git status` قبل از هر commit.

#### ۴. ترس از `reset` و `rebase` چون «تاریخ را عوض می‌کنند»

تاریخ **محلی** تو مال خودت است؛ می‌توانی هر بلایی سرش بیاوری. تاریخ **مشترک** (چیزی که push شده و دیگران دارند) را نباید عوض کنی. این تفاوت را در فصل ۱۲ و ۲۱ کامل می‌بینیم.

#### ۵. باور به اینکه merge یعنی «کد از branch دیگر می‌آید»

merge فقط اشاره‌گرها را جابه‌جا می‌کند و یک commit می‌سازد. فایل‌های working directory هم به‌روز می‌شوند، ولی هیچ چیزی «از بیرون» نمی‌آید — همه‌ی commitها از قبل در مخزن تو بودند (چون Git توزیع‌شده است).

### نکات مهم (Tips & Tricks)

- **`git log --graph --oneline --decorate --all`** — یک نگاه به گراف کامل. alias کن:
  ```bash
  git config --global alias.lg "log --graph --oneline --decorate --all"
  # حالا: git lg
  ```
- **`git branch -vv`** — همه‌ی branchها با upstream و آخرین commit. برای دیدن اینکه کدام branch عقب افتاده.
- **`git show <hash>`** — محتوای کامل یک commit (پیام + diff).
- **`git cat-file -p HEAD`** — محتوای خام شیء HEAD. برای کنجکاوی و درک عمیق.
- **قاعده‌ی ذهنی:** هر چیزی که Git می‌گوید «شاخه»، «commit»، «تگ» — همه فقط هش هستند با یک نام. اگر این را بگیری، Git دیگر جادو نیست.

### خلاصه فصل

- Git از هر commit یک **snapshot** می‌گیرد، نه diff.
- چهار نوع شیء: **blob، tree، commit، tag** — همه با هش محتوا شناسایی می‌شوند.
- تاریخ Git یک **گراف** است؛ merge یک commit با دو والد می‌سازد.
- **branch فقط یک اشاره‌گر ۴۱ بایتی** به یک commit است — ساختنش رایگان است.
- **HEAD** می‌گوید الان کجایی؛ در حالت detached به commit مستقیم اشاره می‌کند.
- `origin` فقط یک نام مستعار برای آدرس remote است.

**سؤالات مروری:**
1. چرا در Git ساختن branch ارزان است ولی در SVN گران؟
2. اگر در detached HEAD دو commit بزنی و بعد `git switch main` کنی، آن دو commit چه می‌شوند؟
3. چرا تغییر یک commit قدیمی باعث تغییر هش همه‌ی commitهای بعدی می‌شود؟

## فصل ۳: اکوسیستم GitHub — از Issues تا Actions و Copilot

### مقدمه

GitHub امروز فقط «جایی برای گذاشتن کد» نیست. یک پلتفرم کامل است که چرخه‌ی عمر نرم‌افزار را از ایده تا تولید پوشش می‌دهد. مشکل اکثر تازه‌کارها این است که نمی‌دانند چه چیزی وجود دارد، پس با ابزارهای دست‌ساز و متن‌نویسی کار می‌کنند در حالی که GitHub همان را رایگان می‌دهد.

**چرا مهم است؟** اگر نقشه‌ی کلی را نداشته باشی، در فصل‌های بعد گم می‌شوی: نمی‌دانی چرا باید Issue بسازی وقتی می‌توانی مستقیم PR بزنی؛ نمی‌دانی چرا Ruleset وقتی Branch Protection هست.

**کاربرد عملی:** یک تیم پنج‌نفره می‌تواند کل چرخه‌اش را در GitHub بگذارد: ایده → Issue → branch → PR → review → CI → merge → release → deploy. بدون هیچ ابزار اضافی.

### مفاهیم اساسی

#### نقشه‌ی اکوسیستم

```
                    ┌─────────────────────────────┐
                    │        ایده / باگ             │
                    │      (Issue / Discussion)     │
                    └──────────────┬──────────────┘
                                   ↓
                    ┌─────────────────────────────┐
                    │   برنامه‌ریزی                  │
                    │   (Projects، Milestone، Label)│
                    └──────────────┬──────────────┘
                                   ↓
                    ┌─────────────────────────────┐
                    │   کد                          │
                    │   (branch، commit، Copilot)   │
                    └──────────────┬──────────────┘
                                   ↓
                    ┌─────────────────────────────┐
                    │   بازبینی                     │
                    │   (Pull Request، Review،      │
                    │    CODEOWNERS، Merge Queue)   │
                    └──────────────┬──────────────┘
                                   ↓
                    ┌─────────────────────────────┐
                    │   کنترل خودکار                │
                    │   (Actions، Rulesets، Checks) │
                    └──────────────┬──────────────┘
                                   ↓
                    ┌─────────────────────────────┐
                    │   انتشار                      │
                    │   (Release، Packages، Pages)  │
                    └─────────────────────────────┘
                                   ↑
                    ┌─────────────────────────────┐
                    │   امنیت (در تمام مسیر)         │
                    │   Dependabot، CodeQL،         │
                    │   Secret Scanning، Rulesets   │
                    └─────────────────────────────┘
```

#### جدول کامل قابلیت‌ها

| قابلیت | چه کاری می‌کند | کجا استفاده می‌شود | فصل |
|---|---|---|---|
| **Repository** | میزبانی مخزن، شاخه‌ها، تنظیمات دسترسی | همه‌جا | ۶ |
| **Issues** | ثبت باگ، درخواست ویژگی، وظیفه | برنامه‌ریزی | ۲۹ |
| **Projects** | تخته کانبان، جدول، roadmap | مدیریت کار | ۳۱ |
| **Pull Request** | پیشنهاد تغییر + بحث + بازبینی | همکاری | ۳۳ |
| **Code Review** | نظر خط‌به‌خط، approve، request changes | کیفیت | ۳۴ |
| **Actions** | CI/CD، اتوماسیون رویدادمحور | تست، build، deploy | ۴۲ |

| **Discussions** | گفت‌وگوی بلندمدت (نه Issue) | جامعه | ۸۳ |
| **Releases** | نسخه‌بندی با asset و release notes | انتشار | ۶۲ |
| **Wiki** | مستندات سریع بدون PR | مستندات | ۸۳ |
| **Gists** | قطعه‌کد اشتراکی | یادداشت | ۸۳ |
| **Sponsors** | حمایت مالی از نگه‌دارنده | متن‌باز | ۸۳ |
| **CLI (`gh`)** | همه‌ی بالا از ترمینال | کار روزمره | ۷۶ |

#### Issue در برابر Discussion در برابر PR

| | Issue | Discussion | Pull Request |
|---|---|---|---|
| برای چه | کار مشخص و قابل بستن | گفت‌وگو و پرسش | تغییر کد |
| حالت | open/closed | answered/unanswered | draft/open/merged/closed |
| می‌تواند کد داشته باشد | نه | نه | بله |
| در Projects می‌آید | بله | بله (محدود) | بله |
| مناسب | باگ، feature | «چطور X را انجام دهم؟» | «این تغییر را merge کن» |

#### سه لایه‌ی دسترسی

```
Organization
 └── Team (مجموعه‌ای از افراد با دسترسی مشترک)
      └── Repository (با نقش: read / triage / write / maintain / admin)
```

- **Personal account:** مخزن زیر نام خودت.
- **Organization:** مثل یک شرکت. مخزن‌ها مال سازمان‌اند، نه یک نفر. اگر کارمند برود، مخزن می‌ماند.
- **Enterprise:** چند سازمان + سیاست‌های سراسری (SSO، audit log، IP allow list).

**قاعده‌ی مهم:** هر چیزی که قرار است بیش از یک نفر رویش کار کند و «مال شرکت» باشد، باید در Organization باشد نه حساب شخصی یک نفر.

### مثال‌های عملی

#### مثال ۱: یک مخزن بساز و ببین چه چیزی خودکار ساخته می‌شود

```bash
# با gh (فصل ۱۷)
gh repo create github-lab-demo --public --clone
cd github-lab-demo

ls -la
# .git/  README.md  .gitignore  LICENSE
```

GitHub موقع ساخت مخزن می‌تواند این‌ها را اضافه کند: `README.md`، `.gitignore` (بر اساس زبان)، `LICENSE`. توصیه: همیشه هر سه را اضافه کن — حتی اگر بعداً عوضشان کنی.

#### مثال ۲: یک Issue بساز و به آن branch وصل کن

روی GitHub.com:

1. تب **Issues** → **New issue**
2. عنوان: `افزودن اعتبارسنجی ایمیل در فرم ثبت‌نام`
3. توضیح: چه انتظاری داری، چطور بازتولید شود، معیار پذیرش.
4. **Create issue**

سپس از صفحه‌ی Issue، سمت راست: **Create a branch** — GitHub یک branch با نام `3-add-email-validation` می‌سازد و دستورهای checkout را نشان می‌دهد.

```bash
git fetch origin
git switch 3-add-email-validation
```

این کار ردپای Issue در branch و بعداً در PR حفظ می‌شود.

#### مثال ۳: یک PR بساز که Issue را ببندد

در توضیح PR بنویس:

```
Closes #3
```

وقتی PR merge شود، Issue خودکار بسته می‌شود. کلمات کلیدی: `Closes`، `Fixes`، `Resolves` (و ترکیب‌های `close/fix/resolve`).

#### مثال ۴: یک workflow ساده ببین (بدون توضیح عمیق — فصل ۴۲)

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm test
```

همین ۱۵ خط، هر push و هر PR را تست می‌کند. این پایه‌ی همه‌چیز است.

### مقایسه و الگوهای مختلف

#### GitHub در برابر GitLab در پوشش چرخه

| مرحله | GitHub | GitLab |
|---|---|---|
| برنامه‌ریزی | Issues + Projects | Issues + Boards + Epics |
| کد | Repo + Copilot | Repo + Duo |
| CI/CD | Actions | GitLab CI (`.gitlab-ci.yml`) |
| رجیستری | Packages | Container/ Package Registry |
| امنیت | Advanced Security (پلن) | Ultimate (SAST/DAST داخلی) |
| مستندات | Wiki + Pages | Pages + Wiki |

تفاوت فلسفی: GitLab یک محصول یکپارچه است (همه‌چیز در یک جا، تنظیمات کمتر). GitHub یک پلتفرم با اکوسیستم است (Actions Marketplace، هزاران ابزار). هر کدام برای نوعی از تیم بهتر است.

#### مخزن عمومی در برابر خصوصی

| | Public | Private |
|---|---|---|
| دیده می‌شود توسط | همه | فقط اعضای مجاز |
| Actions minutes | رایگان و نامحدود (برای مخزن عمومی) | سهمیه‌ی پلن |
| Code Scanning | رایگان | نیاز به Advanced Security |
| Secret Scanning | رایگان | رایگان (Push Protection هم) |
| مناسب | متن‌باز، نمونه‌کار، مستندات | کد تجاری، داده‌ی مشتری |

**نکته‌ی مهم:** در مخزن **عمومی**، Actions رایگان و نامحدود است. این خیلی از تیم‌های متن‌باز را نجات می‌دهد. ولی حواست باشد: هر چیزی که در مخزن عمومی push کنی، **برای همیشه عمومی است** (حتی اگر بعد پاک کنی — چون fork شده یا در کش است).

### اشکال شایع

#### ۱. ساختن همه‌چیز در حساب شخصی

```
✗ github.com/ali/company-backend   (کد شرکت زیر حساب شخصی علی)
```

اگر علی برود، دسترسی‌ها به‌هم می‌ریزد. درست: یک Organization بساز، مخزن را transfer کن.

#### ۲. استفاده از Issue به‌عنوان چت

Issue برای «کار» است. اگر می‌خواهی بپرسی «چطور این کتابخانه را تنظیم کنم؟»، Discussion یا Discussions یا Stack Overflow. Issueهای پر از گفت‌وگوی بی‌پایان، پروژه را فلج می‌کنند.

#### ۳. باز گذاشتن ۲۰۰ Issue بی‌برچسب

بدون label و milestone، Issues به یک انبار تبدیل می‌شود. حداقل: `bug`، `enhancement`، `question`، `good first issue`، `wontfix`.

#### ۴. فکر کردن Actions فقط برای تست است

Actions می‌تواند: Issue را برچسب بزند، PR را به reviewer اختصاص دهد، نسخه منتشر کند، به Slack پیام بدهد، مستندات را build کند، Docker image بسازد، سایت را deploy کند. هر رویدادی در GitHub می‌تواند trigger باشد.

#### ۵. نادیده گرفتن امنیت چون «مخزن خصوصی است»

مخزن خصوصی یعنی «عمومی نیست»، نه «امن است». کارمند سابق، لپ‌تاپ گم‌شده، dependency آلوده، secret لو رفته در CI log — همه در مخزن خصوصی هم اتفاق می‌افتند.

### نکات مهم (Tips & Tricks)

- **همیشه با `README.md` شروع کن.** حتی یک پاراگراف: این پروژه چیست، چطور اجرا شود. مخزنی که README ندارد، ۵ دقیقه بعد از ساختش رهاشده به نظر می‌رسد.
- **`LICENSE` را جدی بگیر.** بدون لایسنس، از نظر حقوقی هیچ‌کس اجازه‌ی استفاده ندارد — حتی اگر عمومی باشد.
- **Topics** را پر کن (مثل `python`، `cli`، `machine-learning`). در جست‌وجوی GitHub دیده می‌شوی.
- **`.github/` پوشه‌ی جادویی است.** هر چیزی که رفتار GitHub را تنظیم می‌کند آنجاست: `workflows/`، `ISSUE_TEMPLATE/`، `CODEOWNERS`، `dependabot.yml`، `copilot-instructions.md`.
- **در Organization، از Teams استفاده کن نه فرد.** دسترسی را به تیم بده، نه به شخص. وقتی کسی می‌آید یا می‌رود، فقط عضویت تیم عوض می‌شود.

### خلاصه فصل

- GitHub یک پلتفرم کامل چرخه‌ی عمر نرم‌افزار است، نه فقط میزبانی کد.
- مسیر اصلی: **Issue → Projects → branch → PR → Review → Actions → Merge → Release**.
- امنیت یک لایه‌ی موازی است که در تمام مسیر حضور دارد.
- **Organization** برای کار تیمی و مالکیت سازمانی؛ **حساب شخصی** برای پروژه‌های فردی.
- مخزن عمومی = Actions رایگان و نامحدود، ولی هر چیزی که push کنی برای همیشه عمومی می‌ماند.

**سؤالات مروری:**
1. چه زمانی Issue بسازی و چه زمانی Discussion؟
2. چرا مخزن شرکت باید در Organization باشد نه حساب شخصی؟
3. کدام سه فایل را موقع ساخت هر مخزن جدید باید اضافه کنی؟

## فصل ۴: حساب، پلن‌ها و امنیت اولیه

### مقدمه

این فصل کوتاه ولی حیاتی است. ۸۰٪ حوادث امنیتی در GitHub از سه چیز می‌آید: حساب بدون ۲FA، توکن با دسترسی بیش از حد، و کلیدی که در کد گذاشته شده. اگر همین فصل را درست انجام بدهی، از اکثر فاجعه‌ها در امان هستی.

**چرا مهم است؟** یک توکن لو رفته می‌تواند در چند دقیقه کل مخزن‌های تو را پاک کند، به سرورهایت نفوذ کند، و هزینه‌ی ابری روی دستت بگذارد. مهاجم‌ها به‌طور خودکار مخزن‌های عمومی را اسکن می‌کنند — معمولاً در کمتر از ۵ دقیقه بعد از push.

**کاربرد عملی:** این فصل، تنظیماتی است که یک بار انجام می‌دهی و سال‌ها سود می‌بری.

### مفاهیم اساسی

#### روش‌های احراز هویت در Git/GitHub

GitHub چهار راه برای اثبات هویتت دارد:

| روش | برای چه | امنیت | توصیه |
|---|---|---|---|
| **HTTPS + PAT** | ساده‌ترین، کار از هر جا | خوب (اگر scoped) | برای CI و اسکریپت |
| **SSH key** | کار روزمره‌ی توسعه‌دهنده | عالی | **توصیه‌ی اصلی** |
| **`gh auth login`** | CLI، تنظیم خودکار | عالی | برای `gh` |
| **Git Credential Manager** | ویندوز، یکپارچگی با GUI | خوب | برای ویندوز |

**نکته‌ی تاریخی مهم:** از اوت ۲۰۲۱، GitHub **رمز عبور حساب را برای Git قبول نمی‌کند**. اگر `git push` بزنی و پسوردت را وارد کنی، خطا می‌گیری. باید PAT یا SSH استفاده کنی.

#### PAT (Personal Access Token)

دو نوع:

| نوع | شروع با | برای چه | عمر |
|---|---|---|---|
| **Fine-grained** | `github_pat_` | دسترسی دقیق به مخزن/سازمان مشخص | تاریخ انقضا اجباری |
| **Classic** | `ghp_` | دسترسی گسترده به scopeها | قابل تنظیم |

**همیشه Fine-grained را ترجیح بده.** با آن می‌توانی بگویی: «این توکن فقط به مخزن `ali/shop-api` دسترسی read به Contents دارد، تا ۳۰ روز.» اگر لو برود، خسارتش محدود است.

یک Classic token با scope `repo` + `workflow` + `admin:org` = کلید کلیدها. اگر لو برود، همه‌چیز رفته.

#### SSH key — چطور کار می‌کند

```
┌──────────────┐                      ┌──────────────┐
│  لپ‌تاپ تو    │                      │    GitHub    │
│              │                      │              │
│  private key │ ── امضا می‌کند ──→   │  public key  │
│  (محرمانه)    │                      │  (ذخیره‌شده)  │
└──────────────┘                      └──────────────┘
                                            ↓
                                    امضا را با public key
                                    بررسی می‌کند → تأیید
```

- **private key** فقط روی سیستم تو می‌ماند. **هرگز** جایی آپلود نمی‌شود.
- **public key** را در GitHub می‌گذاری. اگر لو برود، مشکلی نیست (برای همین «public» است).

الگوریتم توصیه‌شده: **Ed25519** (کوتاه‌تر، سریع‌تر، امن‌تر از RSA). اگر سیستم قدیمی داری، `rsa` با ۴۰۹۶ بیت.

#### ۲FA — دو مرحله‌ای

از ۲۰۲۳، GitHub برای همه‌ی کسانی که کد contribute می‌کنند ۲FA را اجباری کرد. گزینه‌ها:

| روش | امنیت | راحتی | توصیه |
|---|---|---|---|
| **Passkey** | عالی (مقاوم به فیشینگ) | عالی | بهترین |
| **TOTP app** (Authenticator) | خوب | خوب | حداقل این |
| **Security key** (YubiKey) | عالی | متوسط | برای حساب‌های حساس |
| **SMS** | ضعیف (SIM swap) | راحت | فقط اگر چاره نیست |

**SMS را انتخاب نکن** اگر گزینه‌ی دیگر داری. حمله‌ی SIM swap واقعی است و در ایران هم اتفاق افتاده.

#### پلن‌ها (۲۰۲۶)

| | Free | Pro | Team | Enterprise |
|---|---|---|---|---|
| مخزن خصوصی نامحدود | ✅ | ✅ | ✅ | ✅ |
| Actions minutes (خصوصی) | ۲۰۰۰/ماه | ۳۰۰۰/ماه | ۳۰۰۰/کاربر | ۵۰۰۰۰/ماه |
| Pages | ✅ عمومی | ✅ | ✅ | ✅ |
| Code/Secret Scanning | عمومی | عمومی | عمومی | همه |
| Copilot | Free (محدود) | Pro | Business | Enterprise |
| Protected branches (عمومی) | ✅ | ✅ | ✅ | ✅ |
| Protected branches (خصوصی) | ✅ | ✅ | ✅ | ✅ |
| Rulesets (خصوصی) | ✅ | ✅ | ✅ | ✅ |
| Merge Queue | عمومی | عمومی | ✅ | ✅ |
| SSO/SAML | ❌ | ❌ | ❌ | ✅ |
| Audit log API | ❌ | ❌ | ❌ | ✅ |

**نکته:** محدودیت‌ها مرتب تغییر می‌کنند. قبل از تصمیم خرید، صفحه‌ی pricing را چک کن.

### مثال‌های عملی

#### مثال ۱: راه‌اندازی SSH از صفر (لینوکس/مک/WSL)

```bash
# ۱) کلید بساز (اگر نداری)
ls ~/.ssh/id_ed25519.pub 2>/dev/null || ssh-keygen -t ed25519 -C "ali@example.com"
# Enter برای مسیر پیش‌فرض، و یک passphrase قوی

# ۲) کلید عمومی را ببین
cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... ali@example.com

# ۳) کپی کن (مک)
pbcopy < ~/.ssh/id_ed25519.pub
# لینوکس با xclip:
# xclip -sel clip < ~/.ssh/id_ed25519.pub
```

روی GitHub: **Settings → SSH and GPG keys → New SSH key** → paste → Add.

```bash
# ۴) تست
ssh -T git@github.com
# Hi ali! You've successfully authenticated, but GitHub does not provide shell access.
```

اگر این پیام را دیدی، تمام است. اگر `Permission denied (publickey)` گرفتی، بخش «اشکال شایع» را ببین.

#### مثال ۲: SSH با چند حساب (کار + شخصی)

این یکی از پرتکرارترین مشکلات است: یک کلید برای حساب شخصی، یکی برای حساب شرکت.

`~/.ssh/config`:

```
# حساب شخصی (پیش‌فرض)
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes

# حساب شرکت
Host github-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes
```

استفاده:

```bash
# برای مخزن شخصی
git clone git@github.com:ali/personal.git

# برای مخزن شرکت — به‌جای github.com از github-work استفاده کن
git clone git@github-work:company/backend.git
```

**تله:** اگر `IdentitiesOnly yes` را نگذاری، SSH همه‌ی کلیدها را امتحان می‌کند و ممکن است با کلید اشتباه authenticate شود.

#### مثال ۳: PAT Fine-grained بساز (درست)

1. **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**
2. **Token name:** `ci-deploy-shop-api`
3. **Expiration:** ۳۰ روز (یا ۹۰ — نه «No expiration»)
4. **Resource owner:** سازمان یا حساب خودت
5. **Repository access:** Only select repositories → `shop-api`
6. **Permissions:**
   - Contents: Read and write (برای push)
   - Metadata: Read (اجباری)
   - Actions: Read (اگر می‌خواهی وضعیت workflow را ببینی)
7. **Generate token** → کپی کن → **همان لحظه** در secret manager بگذار

```bash
# تست با curl
curl -H "Authorization: Bearer github_pat_xxx" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/repos/OWNER/REPO
```

**قاعده:** توکن را هرگز در فایل، در `.env` که commit می‌شود، یا در تاریخچه‌ی shell (`~/.bash_history`) نگه ندار. برای CI از **Secrets** استفاده کن (فصل ۵۶).

#### مثال ۴: ۲FA را تنظیم کن

1. **Settings → Password and authentication**
2. **Enable two-factor authentication**
3. **Passkey** (اگر مرورگر/دستگاه پشتیبانی می‌کند) یا **Authenticator app**
4. **Download recovery codes** → در جای امن (نه در مخزن!) نگه دار

**اگر recovery codes را گم کنی و گوشی‌ات هم از دست برود، حساب قفل می‌شود.** این را جدی بگیر.

#### مثال ۵: ببین چه چیزی به چه چیزی وصل است

```bash
# SSH: کدام کلیدها به GitHub ارائه می‌شوند؟
ssh -T git@github.com -v 2>&1 | grep "Offering"

# Git: کدام remote و با چه پروتکلی؟
git remote -v

# gh: چه حساب‌هایی لاگین هستند؟
gh auth status
```

### مقایسه و الگوهای مختلف

#### SSH در برابر HTTPS

| | SSH | HTTPS + PAT |
|---|---|---|
| تنظیم اولیه | ساخت کلید + آپلود | ساخت توکن |
| انقضا | ندارد (تا وقتی پاک کنی) | اجباری |
| عبور از فایروال شرکتی | گاهی بلاک (پورت ۲۲) | تقریباً همیشه OK |
| در CI | نیاز به کلید در secret | توکن در secret |
| برای توسعه‌دهنده | ✅ بهتر | متوسط |
| برای اسکریپت/CI | متوسط | ✅ بهتر |

**اگر پورت ۲۲ بلاک است:** از `ssh.github.com:443` استفاده کن:

```
Host github.com
  HostName ssh.github.com
  Port 443
  User git
```

#### Fine-grained در برابر Classic PAT

| | Fine-grained | Classic |
|---|---|---|
| دانه‌بندی | مخزن + permission دقیق | scope گسترده |
| انقضای اجباری | ✅ | ❌ |
| نیاز به تأیید سازمان | ✅ (اگر org دارد) | بسته به سیاست |
| برای سازمان‌های زیاد | دردناک (per-org) | راحت‌تر |
| توصیه‌ی کلی | ✅ پیش‌فرض | فقط اگر مجبوری |

#### GitHub App در برابر PAT در CI

| | PAT | GitHub App |
|---|---|---|
| عمر | تا انقضا (مثلاً ۹۰ روز) | توکن یک‌ساعته، خودکار تازه |
| دسترسی | به یک کاربر وابسته | مستقل از افراد |
| rate limit | ۵۰۰۰/ساعت (per user) | ۵۰۰۰+/ساعت (per installation) |
| اگر سازنده برود | می‌شکند | کار می‌کند |
| توصیه برای سازمان | ❌ | ✅ |

**قاعده:** در سازمان، برای اتوماسیون از GitHub App یا `GITHUB_TOKEN` استفاده کن، نه PAT شخصی. PAT یعنی «اگر علی از شرکت برود، CI می‌شکند».

### اشکال شایع

#### ۱. `Permission denied (publickey)` بعد از ساخت کلید

پنج دلیل رایج، به ترتیب احتمال:

1. کلید به GitHub اضافه نشده.
2. `ssh-agent` کلید را ندارد: `ssh-add ~/.ssh/id_ed25519`
3. فایل با نام اشتباه (`id_ed25519.pub` درست است، نه `id_ed25519`).
4. مجوز فایل‌ها غلط است: `chmod 600 ~/.ssh/id_ed25519 && chmod 700 ~/.ssh`
5. remote با HTTPS تنظیم شده، نه SSH: `git remote -v` را چک کن.

#### ۲. `Support for password authentication was removed`

یعنی با HTTPS و پسورد push می‌زنی. راه‌حل: PAT بساز، یا به SSH سوییچ کن:

```bash
git remote set-url origin git@github.com:user/repo.git
```

#### ۳. توکن را در `.env` گذاشتم و commit شد

این فاجعه‌ی کلاسیک. اگر تازه اتفاق افتاده:

```bash
# ۱) فوراً توکن را revoke کن (Settings → Developer settings → Tokens → Revoke)
# ۲) بعد از پاک کردن فایل، تاریخ را هم باید پاک کنی (فصل ۹۳)
```

**ترتیب مهم است:** اول revoke، بعد پاکسازی. اگر اول پاک کنی، توکن هنوز معتبر است و مهاجم می‌تواند استفاده کند.

#### ۴. `remote: Permission to X denied to Y`

یعنی با حساب اشتباه authenticate شده‌ای. چک کن:

```bash
gh auth status
git config user.email
ssh -T git@github.com
```

#### ۵. کلید SSH را با پسورد (passphrase) ساختم و هر بار می‌پرسد

```bash
# یک بار اضافه کن به agent
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# برای دائمی شدن (macOS)
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

#### ۶. حساب قفل شد چون recovery codes را نداشتم

متأسفانه راه‌حل خودکار ندارد. باید از طریق support.github.com درخواست بازیابی بدهی و ممکن است روزها طول بکشد. **پیشگیری:** recovery codes را در یک password manager (Bitwarden، 1Password) یا پرینت در جای امن نگه دار.

### نکات مهم (Tips & Tricks)

- **`gh auth login` ساده‌ترین راه شروع است.** خودش SSH یا HTTPS را تنظیم می‌کند و توکن را در credential helper می‌گذارد.
- **`gh auth switch`** برای جابه‌جایی بین حساب‌ها بدون logout/login.
- **برای هر دستگاه یک کلید جدا بساز.** اگر لپ‌تاپ گم شد، فقط همان کلید را حذف می‌کنی.
- **کلید SSH را با passphrase بساز.** بدون آن، هر کسی که به فایل دسترسی پیدا کند، هویت تو را دارد.
- **قبل از هر `git push` به مخزن عمومی، یک بار `git status` و `git diff --staged` بزن.** ۹۰٪ لو رفتن secretها همین‌جا گرفته می‌شود.
- **Push Protection را روشن کن** (فصل ۷۳) — GitHub جلوی push کلیدهای شناسایی‌شده را می‌گیرد.
- **`git config --global user.email` باید ایمیل تأییدشده‌ی حساب GitHub باشد**، وگرنه commitها به پروفایلت وصل نمی‌شوند (و در Organization ممکن است رد شوند).

### خلاصه فصل

- GitHub دیگر پسورد را برای Git قبول نمی‌کند: **PAT یا SSH**.
- **SSH (Ed25519)** بهترین گزینه برای کار روزمره؛ **PAT Fine-grained** برای CI و اسکریپت.
- **۲FA را با passkey یا TOTP** روشن کن و recovery codes را جای امن نگه دار.
- برای چند حساب، `~/.ssh/config` با `IdentitiesOnly yes`.
- در سازمان برای اتوماسیون از **GitHub App** استفاده کن، نه PAT شخصی.
- اگر secret لو رفت: **اول revoke، بعد پاک‌سازی تاریخ**.

**سؤالات مروری:**
1. چرا GitHub پسورد را برای Git قبول نمی‌کند و جایگزین‌ها چیست؟
2. تفاوت PAT Fine-grained و Classic در چیست و کدام امن‌تر است؟
3. اگر `Permission denied (publickey)` گرفتی، به چه ترتیبی چک می‌کنی؟
