## فصل ۱: مقایسه با Netlify

### مقدمه

**Netlify** نزدیک‌ترین رقیب Vercel است و هر دو از پیشگامان «Frontend Cloud» هستند. انتخاب بین آن‌ها به نیاز پروژه بستگی دارد.

### مفاهیم اساسی

**۱. Netlify چیست؟**
پلتفرمی مشابه Vercel برای استقرار سایت‌های مدرن، با تمرکز روی JAMstack.

**۲. نقاط قوت Netlify**

| نقطهٔ قوت | توضیح |
|---|---|
| **سادگی** | رابط کاربری ساده |
| **قیمت‌گذاری شفاف** | باندل مشخص |
| **Forms** | فرم‌های آماده |
| **Identity** | احراز هویت داخلی |
| **CMS** | Netlify CMS |
| **Edge Functions** | Deno-based |

**۳. نقاط قوت Vercel**

| نقطهٔ قوت | توضیح |
|---|---|
| **Next.js** | یکپارچگی بی‌نظیر |
| **Edge Network** | شبکهٔ گسترده و سریع |
| **ISR/PPR** | بومی و بهینه |
| **Fluid Compute** | مدل اجرایی مدرن |
| **Observability** | ابزارهای پایش بهتر |
| **Image Optimization** | روی لبه |

**۴. تفاوت‌های فنی کلیدی**

| مورد | Vercel | Netlify |
|---|---|---|
| Edge Runtime | V8 (Web APIs) | Deno |
| Next.js | ✅ بومی | سازگار (adapter) |
| Storage | KV/Postgres/Blob | Blobs/DB (بیرونی) |
| Cron | ✅ داخلی | زمان‌بند بیرونی |
| Function Runtime | Node.js کامل | Node.js |

### مثال‌های عملی

**مثال ۱ — تفاوت استقرار**

```
【 Vercel 】
git push → Build → Deploy → Preview URL

【 Netlify 】
git push → Build → Deploy → Deploy Preview URL

(بسیار مشابه — تفاوت در جزئیات و ابزارها)
```

**مثال ۲ — تفاوت توابع**

```js
// Vercel (Node.js)
export default function handler(req, res) {
  res.json({ ok: true });
}
```

```js
// Netlify (Node.js)
export async function handler(event, context) {
  return {
    statusCode: 200,
    body: JSON.stringify({ ok: true }),
  };
}
```

### مقایسه و الگوهای مختلف

**Vercel در برابر Netlify**

| معیار | Vercel | Netlify |
|---|---|---|
| بهترین برای | Next.js | سایت‌های عمومی |
| قیمت‌گذاری | مصرفی | باندل |
| قیمت‌گذاری در مقیاس | ممکن است بالا رود | قابل پیش‌بینی‌تر |
| فرم آماده | ❌ | ✅ Forms |
| احراز هویت | ❌ (بیرونی) | ✅ Identity |
| شبکهٔ لبه | ✅ گسترده | ✅ خوب |
| ISR/PPR | ✅ بومی | محدود |
| تجربهٔ Next.js | ✅✅ بهترین | ✅ خوب |
| سادگی شروع | ✅ | ✅✅ |

**چه زمانی کدام؟**

| سناریو | انتخاب |
|---|---|
| پروژهٔ Next.js جدی | Vercel |
| سایت JAMstack ساده | هر دو |
| نیاز به فرم آماده | Netlify |
| نیاز به ISR/PPR | Vercel |
| بودجهٔ محدود و پیش‌بینی‌پذیر | Netlify |

### اشکال شایع

**۱. مقایسهٔ ناعادلانه بر اساس یک پروژه.**
هر پلتفرم در سناریوی خاصی بهتر است.

**۲. نادیده گرفتن هزینهٔ کل.**
قیمت‌گذاری مصرفی Vercel در مقیاس بالا می‌تواند بیشتر باشد.

**۳. فرض یکسان بودن قابلیت‌ها.**
ISR/PPR در Vercel بومی‌اند؛ در Netlify نیاز به کار اضافه.

**۴. مهاجرت بدون تست.**
همیشه قبل از مهاجرت کامل، یک Preview بسازید.

**۵. نادیده گرفتن قابلیت‌های منحصربه‌فرد.**
Forms و Identity در Netlify مزیت واقعی‌اند.

### نکات مهم (Tips & Tricks)

- برای **Next.js**، Vercel انتخاب طبیعی است.
- برای سایت **JAMstack ساده**، هر دو خوب‌اند.
- **هزینهٔ کل** را در مقیاس محاسبه کنید.
- قابلیت‌های **منحصربه‌فرد** را در تصمیم لحاظ کنید.
- قبل از مهاجرت، **Preview** بسازید.

### خلاصه فصل

- Netlify نزدیک‌ترین رقیب Vercel است.
- Vercel برای **Next.js** و **Edge Network** برتر است.
- Netlify در **فرم، Identity و پیش‌بینی هزینه** مزیت دارد.
- انتخاب به نیاز پروژه بستگی دارد.
- همیشه هزینهٔ کل و قابلیت‌های منحصربه‌فرد را بسنجید.

## فصل ۲: مقایسه با Cloudflare Pages

### مقدمه

**Cloudflare Pages** با شبکهٔ عظیم Cloudflare و قیمت رقابتی، گزینه‌ای جدی است. در این فصل، تفاوت‌ها را می‌سنجیم.

### مفاهیم اساسی

**۱. Cloudflare Pages چیست؟**
پلتفرم استقرار Cloudflare که با **Workers** یکپارچه است.

**۲. نقاط قوت Cloudflare**

| نقطهٔ قوت | توضیح |
|---|---|
| **شبکهٔ عظیم** | بزرگ‌ترین شبکهٔ لبهٔ جهان |
| **قیمت** | بسیار رقابتی، سهمیهٔ رایگان سخاوتمندانه |
| **Workers** | قدرتمند و سریع |
| **D1/KV/R2** | ذخیره‌سازی داخلی |
| **امنیت** | زیرساخت امنیتی قوی |
| **بدون هزینهٔ پهنای باند** | در پلن‌های خاص |

**۳. نقاط قوت Vercel**

| نقطهٔ قوت | توضیح |
|---|---|
| **Next.js** | یکپارچگی کامل |
| **تجربهٔ توسعه** | ابزارهای بهتر |
| **ISR/PPR** | بومی |
| **Observability** | پایش جامع |
| **Preview Workflow** | گردش کار حرفه‌ای |

**۴. تفاوت‌های فنی**

| مورد | Vercel | Cloudflare |
|---|---|---|
| Edge Runtime | V8 | V8 (Workers) |
| Next.js | ✅ بومی | adapter |
| Node.js کامل | ✅ | محدود |
| ذخیره‌سازی | KV/Postgres/Blob | KV/D1/R2 |
| Cron | ✅ | ✅ |
| قیمت پهنای باند | مصرفی | رقابتی/رایگان |

### مثال‌های عملی

**مثال ۱ — تفاوت توابع**

```js
// Cloudflare Worker
export default {
  async fetch(request, env, ctx) {
    return new Response(JSON.stringify({ ok: true }), {
      headers: { 'content-type': 'application/json' },
    });
  },
};
```

```js
// Vercel Edge Function
export const config = { runtime: 'edge' };

export default function handler(request) {
  return new Response(JSON.stringify({ ok: true }), {
    headers: { 'content-type': 'application/json' },
  });
}
```

> هر دو بر پایهٔ **Web APIs** هستند — مهاجرت نسبتاً ساده است.

**مثال ۲ — تفاوت ذخیره‌سازی**

```
【 Vercel 】          【 Cloudflare 】
KV        →          KV
Postgres  →          D1 (SQLite)
Blob      →          R2 (S3-compatible)
Edge Config →        (متغیرهای محیطی)
```

### مقایسه و الگوهای مختلف

**Vercel در برابر Cloudflare**

| معیار | Vercel | Cloudflare |
|---|---|---|
| شبکهٔ لبه | ✅ گسترده | ✅✅ بزرگ‌ترین |
| قیمت | مصرفی | ✅ رقابتی |
| Next.js | ✅✅ بومی | ✅ adapter |
| Node.js کامل | ✅ | محدود |
| ذخیره‌سازی | Marketplace | ✅ داخلی |
| DX | ✅✅ عالی | ✅ خوب |
| امنیت | ✅ خوب | ✅✅ عالی |
| مناسب برای | Next.js، اپ‌های کامل | Workers، ترافیک بالا |

**چه زمانی کدام؟**

| سناریو | انتخاب |
|---|---|
| Next.js با قابلیت‌های پیشرفته | Vercel |
| ترافیک بسیار بالا و حساس به هزینه | Cloudflare |
| نیاز به امنیت سازمانی | Cloudflare |
| اپ فول‌استک با DX عالی | Vercel |
| Workers و API سبک | Cloudflare |

### اشکال شایع

**۱. فرض سازگاری کامل Next.js.**
در Cloudflare نیاز به adapter و ممکن است برخی قابلیت‌ها محدود باشند.

**۲. نادیده گرفتن محدودیت Node.js.**
Cloudflare Workers محیط Node.js کامل نیست.

**۳. مقایسه فقط بر اساس قیمت.**
هزینهٔ مهاجرت و زمان توسعه هم مهم است.

**۴. نادیده گرفتن DX.**
ابزارهای Vercel برای Next.js بی‌رقیب‌اند.

**۵. فرض آسانی مهاجرت.**
هرچند Web APIs مشترک‌اند، جزئیات متفاوت است.

### نکات مهم (Tips & Tricks)

- برای **هزینه در مقیاس**، Cloudflare را جدی بگیرید.
- برای **Next.js پیشرفته**، Vercel بهتر است.
- **ذخیره‌سازی داخلی** Cloudflare مزیت دارد.
- مهاجرت Edge→Edge نسبتاً ساده است.
- همیشه **PoC** بسازید.

### خلاصه فصل

- Cloudflare در **شبکه، قیمت و امنیت** قوی است.
- Vercel در **Next.js و DX** برتر است.
- هر دو Edge Runtime دارند (Web APIs).
- مهاجرت Edge→Edge ساده‌تر است.
- انتخاب به **مقیاس و نوع پروژه** بستگی دارد.

## فصل ۳: مقایسه با AWS Amplify

### مقدمه

**AWS Amplify** راه‌حل Amazon برای میزبانی اپ‌های وب است و مزیت اصلی‌اش یکپارچگی با اکوسیستم عظیم AWS است.

### مفاهیم اساسی

**۱. AWS Amplify چیست؟**
مجموعه‌ای از ابزارها و سرویس‌های AWS برای ساخت و میزبانی اپ‌های وب و موبایل.

**۲. نقاط قوت AWS**

| نقطهٔ قوت | توضیح |
|---|---|
| **اکوسیستم عظیم** | صدها سرویس AWS |
| **کنترل کامل** | دسترسی به زیرساخت خام |
| **انطباق** | استانداردهای سازمانی |
| **قیمت در مقیاس** | رقابتی در حجم بالا |
| **دیتابیس** | DynamoDB، RDS، Aurora |
| **احراز هویت** | Cognito |

**۳. نقاط ضعف AWS Amplify**

| نقطهٔ ضعف | توضیح |
|---|---|
| **پیچیدگی** | منحنی یادگیری تند |
| **DX** | تجربهٔ توسعهٔ ضعیف‌تر |
| **زمان راه‌اندازی** | بیشتر |
| **مدیریت** | نیاز به دانش AWS |
| **Preview Workflow** | ضعیف‌تر |

**۴. تفاوت‌های کلیدی**

| مورد | Vercel | AWS Amplify |
|---|---|---|
| راه‌اندازی | دقیقه | ساعت/روز |
| DX | ✅✅ | متوسط |
| کنترل زیرساخت | محدود | ✅ کامل |
| مقیاس | ✅ خودکار | ✅ (با تنظیم) |
| هزینه شروع | رایگان | متغیر |
| پیچیدگی | کم | زیاد |

### مثال‌های عملی

**مثال ۱ — تفاوت استقرار**

```
【 Vercel 】
۱. اتصال مخزن
۲. Deploy
۳. تمام (۲ دقیقه)

【 AWS Amplify 】
۱. ساخت حساب AWS
۲. تنظیم IAM
۳. ساخت اپ در Amplify
۴. اتصال مخزن
۵. تنظیم build spec
۶. تنظیم دامنه (Route 53)
۷. Deploy
```

**مثال ۲ — تفاوت توابع**

```js
// AWS Lambda (Amplify)
export const handler = async (event) => {
  return {
    statusCode: 200,
    body: JSON.stringify({ ok: true }),
  };
};
```

```js
// Vercel
export default function handler(req, res) {
  res.json({ ok: true });
}
```

### مقایسه و الگوهای مختلف

**Vercel در برابر AWS Amplify**

| معیار | Vercel | AWS Amplify |
|---|---|---|
| راه‌اندازی | ✅✅ سریع | کند |
| DX | ✅✅ عالی | متوسط |
| کنترل | محدود | ✅✅ کامل |
| اکوسیستم | متمرکز | ✅✅ عظیم |
| انطباق سازمانی | متوسط | ✅✅ |
| هزینه در مقیاس بزرگ | متغیر | ✅ رقابتی |
| نگهداری | ✅ صفر | نیاز به دانش AWS |
| مناسب برای | استارتاپ، تیم کوچک | سازمان بزرگ با AWS |

**چه زمانی کدام؟**

| سناریو | انتخاب |
|---|---|
| استارتاپ سریع | Vercel |
| تیم بدون دانش AWS | Vercel |
| سازمان با زیرساخت AWS | Amplify |
| نیاز به سرویس خاص AWS | Amplify |
| پروژه با انطباق سخت | Amplify |

### اشکال شایع

**۱. انتخاب Amplify بدون دانش AWS.**
پیچیدگی می‌تواند پروژه را متوقف کند.

**۲. نادیده گرفتن هزینهٔ نگهداری.**
زیرساخت AWS نیاز به نگهداری دارد.

**۳. فرض ارزانی AWS.**
در مقیاس کوچک ممکن است گران‌تر از Vercel باشد.

**۴. نادیده گرفتن زمان توسعه.**
زمان صرف‌شده روی زیرساخت، از محصول کم می‌کند.

**۵. مهاجرت بدون برنامه.**
مهاجرت به AWS پیچیده است.

### نکات مهم (Tips & Tricks)

- اگر **دانش AWS** دارید، Amplify گزینهٔ خوبی است.
- برای **سرعت راه‌اندازی**، Vercel بهتر است.
- **هزینهٔ کل مالکیت** را حساب کنید (شامل زمان).
- اگر از قبل روی AWS هستید، Amplify یکپارچه‌تر است.
- برای پروژهٔ کوچک، پیچیدگی AWS توجیه ندارد.

### خلاصه فصل

- AWS Amplify در **کنترل، اکوسیستم و انطباق** قوی است.
- Vercel در **سرعت، DX و سادگی** برتر است.
- Amplify نیازمند **دانش AWS** است.
- انتخاب به **اندازهٔ تیم و زیرساخت موجود** بستگی دارد.
- هزینهٔ کل مالکیت را در نظر بگیرید.

<a id="فصل-۵"></a>
## فصل ۵: مهاجرت به Vercel

### مقدمه

مهاجرت به Vercel در بیشتر موارد ساده است. در این فصل، یک راهنمای گام‌به‌گام می‌سازیم.

### فرایند مهاجرت

**مرحله ۱ — آماده‌سازی**

```
- [ ] مخزن Git آماده (GitHub/GitLab/Bitbucket)
- [ ] Node.js و وابستگی‌ها به‌روز
- [ ] متغیرهای محیطی مستند شده
- [ ] Build محلی موفق
```

**مرحله ۲ — استقرار اولیه (Preview)**

```
۱. Vercel → Add New → Project
۲. مخزن را Import کنید
۳. Framework Preset را انتخاب کنید
۴. Root Directory و Build Settings را تنظیم کنید
۵. متغیرهای محیطی را وارد کنید
۶. Deploy
```

**مرحله ۳ — تست Preview**

```
- [ ] همهٔ صفحات کار می‌کنند
- [ ] API ها پاسخ می‌دهند
- [ ] دیتابیس وصل است
- [ ] احراز هویت کار می‌کند
- [ ] تصاویر لود می‌شوند
```

**مرحله ۴ — انتقال دامنه**

```
۱. Settings → Domains
۲. دامنه را اضافه کنید
۳. رکوردهای DNS را تنظیم کنید
۴. منتظر انتشار DNS بمانید
۵. SSL خودکار صادر می‌شود
```

**مرحله ۵ — Cutover**

```
۱. ترافیک را به Vercel منتقل کنید (DNS)
۲. سایت قدیمی را برای مدتی نگه دارید
۳. مانیتور کنید (Logs، Analytics، Speed Insights)
۴. پس از اطمینان، سایت قدیمی را خاموش کنید
```

### مهاجرت از Netlify

**نکات کلیدی:**

| مورد | Netlify | Vercel |
|---|---|---|
| توابع | `netlify/functions` | `api/` |
| Redirects | `_redirects` | `vercel.json` |
| Headers | `_headers` | `vercel.json` |
| Build | `netlify.toml` | `vercel.json` |
| Edge | Deno | V8 |

```js
// Netlify Function
export async function handler(event) {
  return { statusCode: 200, body: JSON.stringify({ ok: true }) };
}
```

```js
// معادل Vercel
export default function handler(req, res) {
  res.json({ ok: true });
}
```

```
# Netlify: _redirects
/old-path  /new-path  301

# Vercel: vercel.json
{
  "redirects": [
    { "source": "/old-path", "destination": "/new-path", "permanent": true }
  ]
}
```

### مهاجرت از Cloudflare Pages

**نکات کلیدی:**

| مورد | Cloudflare | Vercel |
|---|---|---|
| Workers | `functions/` | `api/` |
| KV | Cloudflare KV | Vercel KV |
| D1 | SQLite | Postgres |
| R2 | Object Storage | Blob |
| Next.js | adapter | بومی |

> مهاجرت از Cloudflare Workers به Vercel Edge Functions نسبتاً ساده است (هر دو Web APIs).

### مهاجرت از AWS Amplify

**نکات کلیدی:**

| مورد | AWS | Vercel |
|---|---|---|
| توابع | Lambda | Serverless Functions |
| دیتابیس | DynamoDB/RDS | Postgres/KV |
| احراز هویت | Cognito | سرویس بیرونی |
| فایل | S3 | Blob |
| DNS | Route 53 | Vercel DNS |

> مهاجرت از AWS پیچیده‌تر است چون سرویس‌های بیشتری درگیرند.

### چک‌لیست مهاجرت

- [ ] مخزن آماده و Build محلی موفق
- [ ] متغیرهای محیطی منتقل شده
- [ ] توابع بازنویسی شده
- [ ] Redirects/Headers منتقل شده
- [ ] دیتابیس متصل و تست شده
- [ ] احراز هویت کار می‌کند
- [ ] Preview تست شده
- [ ] دامنه منتقل شده
- [ ] SSL فعال
- [ ] مانیتورینگ راه‌اندازی شده
- [ ] سایت قدیمی خاموش شده

### نکات مهم (Tips & Tricks)

- **همیشه با Preview شروع کنید**، نه Production.
- سایت قدیمی را **موقتاً نگه دارید**.
- **Redirects** مسیرهای قدیمی را فراموش نکنید (SEO).
- مانیتورینگ را **قبل از Cutover** راه‌اندازی کنید.
- مهاجرت را در **ساعات کم‌ترافیک** انجام دهید.

### خلاصه فصل

- مهاجرت به Vercel پنج مرحله دارد: **آماده‌سازی، Preview، تست، دامنه، Cutover**.
- از Netlify و Cloudflare مهاجرت نسبتاً ساده است.
- از AWS پیچیده‌تر است.
- همیشه با **Preview** شروع کنید.
- Redirects و SEO را جدی بگیرید.

## فصل ۶: مهاجرت معکوس و قفل‌شدگی

### مقدمه

هیچ پلتفرمی برای همیشه مناسب نیست. در این فصل، مهاجرت **از** Vercel و مسئلهٔ **قفل‌شدگی (Lock-in)** را بررسی می‌کنیم.

### مفاهیم اساسی

**۱. قفل‌شدگی (Vendor Lock-in) چیست؟**
وابستگی به یک پلتفرم به‌گونه‌ای که مهاجرت سخت و پرهزینه شود.

**۲. سطوح قفل‌شدگی در Vercel**

| سطح | مثال | قفل‌شدگی |
|---|---|---|
| **کد فریم‌ورک** | Next.js | کم (همه‌جا اجرا می‌شود) |
| **توابع** | `api/*` | کم-متوسط |
| **Edge Functions** | Web APIs | کم |
| **ISR/PPR** | ویژگی‌های بومی | متوسط |
| **Storage** | KV/Postgres/Blob | متوسط |
| **Cron** | `vercel.json` | کم |
| **Analytics** | ابزار اختصاصی | کم |

**۳. چه چیزی قابل انتقال است؟**

| مورد | قابل انتقال |
|---|---|
| کد Next.js | ✅ (با adapter) |
| API ها | ✅ (بازنویسی) |
| دیتابیس | ✅ (استاندارد SQL) |
| فایل‌ها (Blob) | ✅ (دانلود/آپلود) |
| متغیرها | ✅ (دستی) |
| لاگ‌ها | ⚠️ (وابسته) |

**۴. کاهش قفل‌شدگی**

```
- از استانداردهای باز استفاده کنید (Postgres، S3-compatible)
- لایهٔ انتزاعی برای سرویس‌های اختصاصی
- پرهیز از وابستگی عمیق به API های اختصاصی
- مستندسازی وابستگی‌ها
```

**۵. چه زمانی مهاجرت از Vercel؟**

| دلیل | توضیح |
|---|---|
| هزینه در مقیاس | صورتحساب بالا |
| نیاز انطباقی | استانداردهای خاص |
| زیرساخت موجود | سازمان روی AWS/Cloudflare |
| قابلیت خاص | سرویس منحصربه‌فرد |

### مثال‌های عملی

**مثال ۱ — لایهٔ انتزاعی برای ذخیره‌سازی**

```js
// lib/storage.js — انتزاع برای آسانی مهاجرت
// امروز: Vercel Blob — فردا: S3 یا R2
export async function uploadFile(file, path) {
  // پیاده‌سازی فعلی
  const { put } = await import('@vercel/blob');
  return put(path, file, { access: 'public' });
}

export async function deleteFile(url) {
  const { del } = await import('@vercel/blob');
  return del(url);
}
```

**مثال ۲ — لایهٔ انتزاعی برای کش**

```js
// lib/cache.js — امروز Vercel KV، فردا Redis هر جای دیگر
let impl;

async function getImpl() {
  if (!impl) {
    const { kv } = await import('@vercel/kv');
    impl = kv;
  }
  return impl;
}

export async function cacheGet(key) {
  return (await getImpl()).get(key);
}

export async function cacheSet(key, value, ttlSec) {
  return (await getImpl()).set(key, value, { ex: ttlSec });
}
```

**مثال ۳ — خروج داده‌ها از Vercel**

```bash
# ۱. کد
git clone <repo>   # کد شما روی GitHub است — مستقل از Vercel

# ۲. متغیرهای محیطی
vercel env pull .env.production

# ۳. فایل‌ها (Blob)
# از Dashboard → Storage → Blob دانلود کنید
# یا با API لیست و دانلود کنید

# ۴. لاگ‌ها (اگر Drain دارید)
# از مقصد Drain بردارید
```

### مقایسه و الگوهای مختلف

**قفل‌شدگی در پلتفرم‌های مختلف**

| پلتفرم | قفل‌شدگی کد | قفل‌شدگی داده | قفل‌شدگی قابلیت |
|---|---|---|---|
| Vercel | کم | متوسط | متوسط |
| Netlify | کم | متوسط | کم |
| Cloudflare | متوسط | متوسط | متوسط |
| AWS | متوسط | متوسط | ✅ بالا |

**سه استراتژی ضد قفل‌شدگی**

| استراتژی | توضیح |
|---|---|
| **استانداردهای باز** | Postgres، S3، HTTP |
| **لایهٔ انتزاعی** | Wrapper برای سرویس‌ها |
| **مستندسازی** | ثبت وابستگی‌ها |

### اشکال شایع

**۱. وابستگی عمیق به API اختصاصی.**
مهاجرت را بسیار سخت می‌کند.

**۲. نبود مستندسازی وابستگی.**
بعداً نمی‌دانید چه چیزی وابسته است.

**۳. استفادهٔ مستقیم از SDK در همه‌جا.**
لایهٔ انتزاعی نداشته باشید، تغییر سخت می‌شود.

**۴. نگرانی افراطی از قفل‌شدگی.**
گاهی استفاده از قابلیت‌های بومی ارزشمندتر از انتزاع است.

**۵. مهاجرت بدون برنامهٔ داده.**
داده‌ها فراموش می‌شوند.

### نکات مهم (Tips & Tricks)

- **استانداردهای باز** را ترجیح دهید (Postgres، S3).
- برای سرویس‌های اختصاصی، **لایهٔ انتزاعی** بسازید.
- **وابستگی‌ها را مستند** کنید.
- نگرانی از قفل‌شدگی را با **ارزش قابلیت** بسنجید.
- برنامهٔ **خروج داده** داشته باشید.

### خلاصه فصل

- **قفل‌شدگی** یعنی سختی مهاجرت.
- کد Next.js نسبتاً قابل انتقال است.
- Storage و قابلیت‌های بومی، قفل‌شدگی متوسط دارند.
- **لایهٔ انتزاعی** و **استانداردهای باز** قفل‌شدگی را کم می‌کنند.
- نگرانی افراطی از قفل‌شدگی هم مضر است.
