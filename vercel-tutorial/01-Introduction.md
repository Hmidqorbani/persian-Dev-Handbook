## فصل ۱: Vercel چیست و چه مشکلی را حل می‌کند؟

### مقدمه

تصور کنید یک وب‌سایت ساخته‌اید و می‌خواهید آن را «روی اینترنت» بگذارید. در گذشته (و حتی امروز در روش‌های سنتی) باید این مراحل را طی می‌کردید:

1. یک سرور اجاره کنید (VPS یا هاست اشتراکی).
2. سیستم‌عامل و وب‌سرور (مثل Nginx) را نصب و تنظیم کنید.
3. فایل‌ها را با FTP یا SSH آپلود کنید.
4. SSL (قفل سبز کنار آدرس) را دستی راه‌اندازی کنید.
5. نگران باشید که اگر ترافیک زیاد شود، سرور از کار نیفتد.

هر کدام از این مراحل می‌تواند ساعت‌ها وقت بگیرد و ربطی هم به «ساختن محصول» ندارد. **Vercel** دقیقاً برای حذف همین دردسرها ساخته شده است.

**Vercel** یک پلتفرم ابری (Cloud Platform) است که به شما اجازه می‌دهد کدتان را بنویسید، با یک دستور آن را «Push» کنید، و چند ثانیه بعد سایت‌تان به‌صورت زنده و روی یک شبکه جهانی در دسترس همه باشد — بدون اینکه به سرور، Nginx، SSL یا تنظیمات شبکه دست بزنید.

### مفاهیم اساسی

**۱. Vercel دقیقاً چیست؟**
Vercel یک **Frontend Cloud** است؛ یعنی پلتفرمی که برای ساختن، استقرار (deploy) و مقیاس‌دهی وب‌سایت‌ها و اپلیکیشن‌های وب طراحی شده است. تمرکز اصلی آن روی «لایه فرانت‌اند و لبه شبکه» است، نه مدیریت سرورهای خام.

**۲. تاریخچه کوتاه (چرا مهم است؟)**
Vercel در سال ۲۰۱۵ با نام **ZEIT** توسط **Guillermo Rauch** تأسیس شد و در سال ۲۰۲۰ به Vercel تغییر نام داد. نکته کلیدی: تیم Vercel سازندهٔ **Next.js** است — محبوب‌ترین فریم‌ورک React برای ساخت اپلیکیشن‌های وب مدرن. همین موضوع باعث شده Vercel و Next.js مثل «قفل و کلید» با هم کار کنند.

**۳. فلسفه اصلی: «Git Push = Deploy»**
در Vercel، استقرار (deployment) از جنس **رویداد Git** است. یعنی:

- کد را روی GitHub (یا GitLab/Bitbucket) Push می‌کنید.
- Vercel به‌صورت خودکار تغییرات را می‌بیند، پروژه را Build می‌کند و منتشر می‌کند.
- هیچ دستور deploy دستی لازم نیست.

**۴. سه ستون اصلی Vercel**

| ستون | توضیح ساده |
|---|---|
| **Build** | کد شما را می‌گیرد و به خروجی قابل اجرا (HTML/JS/CSS/توابع) تبدیل می‌کند. |
| **Deploy** | خروجی را روی شبکه جهانی Vercel منتشر می‌کند. |
| **Scale** | به‌طور خودکار با افزایش ترافیک، منابع را زیاد می‌کند (Auto-scaling). |

**۵. چرا اسمش «Vercel» است؟**
از کلمهٔ **«Vertex»** به معنای «رأس» یا «نقطه اوج» گرفته شده است — اشاره به «لبه» شبکه و «اوج» عملکرد.

### مثال‌های عملی

**مثال ۱ — مقایسه ذهنی: هاست سنتی در برابر Vercel**

در روش سنتی، چرخه کار شما این‌طور بود:

```
کد می‌نویسی → با FTP آپلود می‌کنی → منتظر می‌مانی → سایت به‌روز می‌شود
(و اگر خراب شد، باید دستی فایل قبلی را برگردانی)
```

در Vercel:

```
کد می‌نویسی → git push → Vercel خودش Build و Deploy می‌کند
(و اگر خراب شد، با یک کلیک به نسخه قبلی برمی‌گردی)
```

**مثال ۲ — اولین برخورد با Vercel (بدون کد)**

فقط برای اینکه حس کنید چطور کار می‌کند، مراحل را ذهنی دنبال کنید (پیاده‌سازی کامل در فایل ۰۲):

```bash
# ۱. کد پروژه را روی Git قرار می‌دهید
git add .
git commit -m "first commit"
git push origin main

# ۲. Vercel به‌صورت خودکار شروع می‌کند:
#    Cloning → Installing → Building → Deploying
# ۳. چند ثانیه بعد یک آدرس زنده دارید:
#    https://my-project.vercel.app
```

**مثال ۳ — چه چیزی Vercel را «متفاوت» می‌کند؟**

فرض کنید یک فروشگاه اینترنتی دارید و در یک کمپین تبلیغاتی ترافیک شما ۱۰۰ برابر می‌شود:

- **سرور سنتی**: اگر ظرفیت کافی نباشد، سایت Down می‌شود.
- **Vercel**: به‌صورت خودکار روی صدها نقطه از جهان پاسخ می‌دهد؛ کاربر از نزدیک‌ترین نقطه سرویس می‌گیرد.

### مقایسه و الگوهای مختلف

سه روش کلی برای میزبانی وب وجود دارد:

| روش | نمونه | کنترل | پیچیدگی | مناسب برای |
|---|---|---|---|---|
| **هاست سنتی / VPS** | cPanel، DigitalOcean | بسیار زیاد | زیاد | پروژه‌هایی که به کنترل کامل سرور نیاز دارند |
| **PaaS عمومی** | Heroku، Railway | متوسط | متوسط | بک‌اندهای کلاسیک |
| **Frontend Cloud** | **Vercel**، Netlify | کم (اما کافی) | کم | وب‌سایت‌ها، اپ‌های Next.js/React، JAMstack |

**الگوی فکری مهم**: Vercel «شما را از مدیریت سرور آزاد می‌کند» تا روی کد و محصول تمرکز کنید. این همان مفهومی است که به آن **Serverless** یا «بدون سرور» می‌گویند (توضیح کامل در فصل ۳).

### اشکال شایع

**۱. «Vercel فقط برای Next.js است.»**
❌ غلط. Vercel از React، Vue، Svelte، Astro، Nuxt، Vite، پروژه‌های HTML خالص و حتی بک‌اندهای ساده Node.js پشتیبانی می‌کند. فقط Next.js بیشترین یکپارچگی را دارد.

**۲. «Vercel کاملاً رایگان است.»**
❌ دقیق‌تر: پلن **Hobby** رایگان است اما **فقط برای پروژه‌های شخصی و غیرتجاری**. برای پروژه تجاری باید پلن **Pro** بگیرید (فصل ۱۴ فایل ۱۴).

**۳. «Vercel برای بک‌اند مناسب نیست.»**
❌ نادرست. با **Serverless Functions**، **Edge Functions**، دیتابیس‌ها و Cron Jobs، می‌توانید یک بک‌اند کامل بسازید — هرچند برای برخی بارهای کاری سنگین و طولانی‌مدت، Vercel بهترین گزینه نیست.

**۴. «Vercel سایت من را هاست می‌کند و داده‌ها را نگه می‌دارد.»**
⚠️ نه دقیقاً. Vercel بیشتر روی «اجرای کد و سرو کردن محتوا» تمرکز دارد؛ داده‌های دائمی معمولاً در سرویس‌های جداگانه (Postgres، KV، Blob) نگهداری می‌شوند.

### نکات مهم (Tips & Tricks)

- **Vercel = پلتفرم، Next.js = فریم‌ورک.** این دو را با هم اشتباه نگیرید. شما می‌توانید Next.js را جای دیگری هم اجرا کنید و Vercel را با فریم‌ورک دیگری هم استفاده کنید.
- **پیش از یادگیری عمیق Vercel، یک بار با Git راحت شوید**؛ چون کل جریان کار بر پایه Git است.
- **پلن Hobby برای یادگیری کافی است.** با همان حساب رایگان می‌توانید تمام این کتابچه را تمرین کنید.
- برای پروژه‌های واقعی، از ابتدا ساختار پوشه و فایل تنظیمات را تمیز نگه دارید.

### خلاصه فصل

- Vercel یک **Frontend Cloud** است که ساخت، استقرار و مقیاس‌دهی وب‌اپ را ساده می‌کند.
- سازندهٔ Next.js است و بهترین یکپارچگی را با آن دارد.
- فلسفهٔ اصلی: **Git Push = Deploy**.
- جایگزین مدیریت دستی سرور، SSL و مقیاس‌پذیری می‌شود.
- برای مبتدی‌ها نقطه شروع عالی است؛ برای پروژه‌های جدی پلن Pro لازم می‌شود.

## فصل ۲: معماری وب مدرن — از سرور سنتی تا Edge

### مقدمه

برای اینکه بفهمید Vercel چرا این‌قدر سریع و کارآمد است، باید بدانید «وب» امروز چطور کار می‌کند. در این فصل، از یک درخواست سادهٔ مرورگر شروع می‌کنیم و تا مفاهیمی مثل **CDN** و **Edge** پیش می‌رویم. هیچ پیش‌دانش عمیقی لازم نیست.

### مفاهیم اساسی

**۱. مدل Client-Server (پایه همه چیز)**
- **Client (کارخواه)**: مرورگر شما (Chrome، Firefox).
- **Server (کارساز)**: کامپیوتری که پاسخ درخواست‌ها را می‌دهد.

وقتی آدرس یک سایت را باز می‌کنید، مرورگر یک **Request (درخواست)** می‌فرستد و سرور یک **Response (پاسخ)** برمی‌گرداند. همین!

**۲. چرخه یک درخواست (Request Lifecycle)**
```
کاربر آدرس را می‌زند
   ↓
DNS: نام دامنه به آدرس IP تبدیل می‌شود
   ↓
اتصال TCP/TLS برقرار می‌شود (HTTPS)
   ↓
درخواست HTTP ارسال می‌شود
   ↓
سرور (یا CDN) پاسخ می‌دهد (HTML/CSS/JS/داده)
   ↓
مرورگر صفحه را رندر (نمایش) می‌کند
```

**۳. سرور سنتی (Monolith)**
یک سرور مرکزی که هم صفحه را می‌سازد، هم داده را از دیتابیس می‌خواند، هم فایل‌ها را سرو می‌کند. ساده اما:
- برای کاربر دور از سرور، کند است.
- برای ترافیک زیاد، باید دستی مقیاس داد.

**۴. هاست استاتیک (Static Hosting)**
اگر سایت شما فقط فایل‌های ثابت دارد (HTML/CSS/JS)، می‌توانید آن‌ها را «از قبل ساخته» و سرو کنید. این سریع‌ترین حالت است، اما برای دادهٔ پویا کافی نیست.

**۵. CDN (Content Delivery Network)**
شبکه‌ای از سرورهای توزیع‌شده در سراسر جهان. فایل‌ها روی همهٔ آن‌ها کپی می‌شود و هر کاربر از **نزدیک‌ترین** سرور پاسخ می‌گیرد.

> **تشبیه روزمره**: CDN مثل شعبه‌های یک فروشگاه زنجیره‌ای است. به‌جای اینکه همه از یک انبار مرکزی خرید کنند، هر کس از شعبه نزدیک خانه‌اش خرید می‌کند.

**۶. Edge Computing (محاسبات لبه)**
به‌جای اجرای کد فقط در یک دیتاسنتر مرکزی، کد را روی **نقاط لبه** (همان سرورهای نزدیک به کاربر) اجرا می‌کنیم. نتیجه: تأخیر (Latency) بسیار کمتر.

**۷. Serverless**
شما کد را در قالب یک «تابع» می‌نویسید؛ پلتفرم مسئول اجرا، مقیاس و سرور است. شما فقط زمانی هزینه می‌دهید که تابع اجرا شود.

### مثال‌های عملی

**مثال ۱ — ردیابی یک درخواست واقعی**

فرض کنید کاربری از تهران سایت شما را باز می‌کند و سرور شما در آمریکا است:

- **بدون CDN**: درخواست تا آمریکا می‌رود و برمی‌گردد → تأخیر مثلاً ۲۵۰ms.
- **با CDN/Edge (مثل Vercel)**: پاسخ از نزدیک‌ترین نقطه (مثلاً فرانکفورت یا دبی) می‌آید → تأخیر مثلاً ۴۰ms.

**مثال ۲ — چهار روش رندر یک صفحه**

```jsx
// ۱. CSR — Client-Side Rendering
// صفحه در مرورگر با JavaScript ساخته می‌شود
useEffect(() => { fetch('/api/data').then(setData) }, []);
// مزیت: تعامل سریع | عیب: SEO ضعیف، بار اول کند

// ۲. SSR — Server-Side Rendering
// صفحه در هر درخواست روی سرور ساخته می‌شود
export async function getServerSideProps() {
  const data = await fetchData();
  return { props: { data } };
}

// ۳. SSG — Static Site Generation
// صفحه یک‌بار در زمان Build ساخته می‌شود
export async function getStaticProps() {
  const data = await fetchData();
  return { props: { data } };
}

// ۴. ISR — Incremental Static Regeneration
// مثل SSG، اما در بازه‌های زمانی مشخص بازسازی می‌شود
export async function getStaticProps() {
  const data = await fetchData();
  return { props: { data }, revalidate: 60 }; // هر ۶۰ ثانیه
}
```

### مقایسه و الگوهای مختلف

| روش | زمان ساخت صفحه | سرعت | SEO | داده پویا | مناسب برای |
|---|---|---|---|---|---|
| **CSR** | در مرورگر | کند در بار اول | ضعیف | ✅ | داشبوردها، اپ‌های پشت لاگین |
| **SSR** | در هر درخواست (سرور) | متوسط | عالی | ✅ | صفحات شخصی‌سازی‌شده |
| **SSG** | زمان Build | بسیار سریع | عالی | ❌ (مگر با ISR) | وبلاگ، مستندات |
| **ISR** | Build + بازسازی دوره‌ای | بسیار سریع | عالی | ✅ (با تأخیر) | فروشگاه، اخبار |

**الگوی حرفه‌ای**: در پروژه‌های واقعی معمولاً **ترکیبی** استفاده می‌شود — صفحه اصلی SSG/ISR، بخش کاربری CSR، و API ها Serverless.

### اشکال شایع

**۱. «همه چیز را CSR کنم تا ساده باشد.»**
نتیجه: بار اول کند و SEO ضعیف. برای محتوای عمومی از SSG/SSR استفاده کنید.

**۲. «CDN فقط برای فایل‌های استاتیک است.»**
امروز CDNها (و Edge Network) می‌توانند کد هم اجرا کنند — همان Edge Functions.

**۳. «Serverless یعنی سروری وجود ندارد.»**
سرور وجود دارد، اما **شما آن را مدیریت نمی‌کنید**. اسم دقیق‌ترش «Serverless برای شما» است.

**۴. نادیده گرفتن Latency کاربران بین‌المللی.**
اگر کاربران شما در چند قاره‌اند، بدون CDN/Edge تجربه‌شان ضعیف خواهد بود.

### نکات مهم (Tips & Tricks)

- **قاعده طلایی**: تا جای ممکن استاتیک، و فقط در صورت نیاز پویا.
- برای SEO، محتوای مهم باید در **HTML اولیه** باشد (SSR یا SSG).
- **Latency** را با ابزارهایی مثل Speed Insights و PageSpeed Insights اندازه بگیرید (فایل ۱۳ و ۱۰).
- معماری «JAMstack» (JavaScript + API + Markup) روی همین اصول بنا شده و Vercel بستر ایده‌آل آن است.

### خلاصه فصل

- وب بر پایهٔ چرخهٔ **درخواست → پاسخ** کار می‌کند.
- **CDN** فایل‌ها را به کاربر نزدیک می‌کند و **Edge** کد را هم نزدیک می‌آورد.
- چهار روش رندر داریم: **CSR، SSR، SSG، ISR** — هر کدام جای خودش.
- **Serverless** یعنی اجرای کد بدون مدیریت سرور.
- Vercel همین مفاهیم را به‌صورت پیش‌فرض و خودکار در اختیار شما می‌گذارد.

## فصل ۳: مفاهیم پایه — Build، Deploy، CDN، Edge، Serverless

### مقدمه

در این فصل، پنج مفهوم کلیدی را که در تمام کتابچه تکرار می‌شوند، دقیق و با مثال توضیح می‌دهیم. اگر این پنج واژه را عمیق بفهمید، بقیهٔ Vercel برایتان ساده می‌شود.

### مفاهیم اساسی

**۱. Build (ساخت)**
کد منبع شما (مثلاً JSX، TypeScript، Sass) مستقیماً توسط مرورگر قابل اجرا نیست. **Build** فرایندی است که این کد را به خروجی نهایی (HTML/CSS/JS بهینه‌شده) تبدیل می‌کند.

> **تشبیه**: Build مثل «آشپزی» است — مواد خام (کد منبع) را می‌گیرد و غذای آماده (خروجی) تحویل می‌دهد.

خروجی Build معمولاً در پوشه‌ای مثل `.next`، `dist` یا `build` قرار می‌گیرد.

**۲. Deploy (استقرار)**
فرایند «قرار دادن خروجی Build روی سرورها و قابل دسترس کردن آن برای کاربران». در Vercel هر Deploy یک **آدرس یکتا** و **تاریخچه‌ای تغییرناپذیر** دارد.

**۳. CDN (شبکه توزیع محتوا)**
همان‌طور که در فصل قبل گفتیم: شبکه‌ای جهانی از سرورها که محتوا را از نزدیک‌ترین نقطه به کاربر می‌رساند. Vercel یک **Edge Network** جهانی دارد.

**۴. Edge (لبه)**
«لبه» یعنی نزدیک‌ترین نقطهٔ شبکه به کاربر. اجرای کد در Edge یعنی کد شما روی صدها نقطه اجرا می‌شود، نه یک سرور مرکزی.

**۵. Serverless**
اجرای کد بدون مدیریت سرور. شما یک **تابع** می‌نویسید؛ پلتفرم آن را در صورت نیاز اجرا و مقیاس می‌کند.

### مثال‌های عملی

**مثال ۱ — یک Build واقعی (با Next.js)**

```bash
# نصب وابستگی‌ها
npm install

# اجرای Build
npm run build

# خروجی نمونه:
# ✓ Compiled successfully
# ✓ Generating static pages (12/12)
# Route (app)                Size     First Load JS
# ┌ ○ /                       1.2 kB   89.3 kB
# ├ ○ /about                  980 B    88.1 kB
# └ λ /api/hello              0 B      0 B
```

علامت‌ها: `○` یعنی صفحه استاتیک، `λ` یعنی تابع Serverless.

**مثال ۲ — یک تابع Serverless ساده**

فایل `api/hello.js`:

```js
// api/hello.js
// هر فایل داخل پوشه api در Vercel به یک endpoint تبدیل می‌شود
export default function handler(req, res) {
  // req: درخواست ورودی (متد، هدرها، بدنه)
  // res: پاسخ خروجی
  res.status(200).json({
    message: 'سلام از تابع Serverless!',
    time: new Date().toISOString(),
  });
}
```

پس از Deploy، این تابع در آدرس زیر در دسترس است:

```
https://your-project.vercel.app/api/hello
```

**مثال ۳ — یک Edge Function ساده**

فایل `api/geo.js` با اجرای روی Edge:

```js
// api/geo.js
export const config = { runtime: 'edge' }; // اجرا روی Edge Runtime

export default function handler(request) {
  // در Edge، به اطلاعات جغرافیایی کاربر دسترسی داریم
  const country = request.geo?.country ?? 'نامشخص';
  return new Response(
    JSON.stringify({ country }),
    { headers: { 'content-type': 'application/json' } }
  );
}
```

### مقایسه و الگوهای مختلف

**Serverless در برابر Edge**

| ویژگی | Serverless Functions | Edge Functions |
|---|---|---|
| محل اجرا | دیتاسنتر منطقه‌ای | نزدیک کاربر (Edge) |
| Runtime | Node.js (کامل) | V8/Edge (محدودتر) |
| Latency شروع | بیشتر (Cold Start) | بسیار کم |
| کتابخانه‌ها | تقریباً همه npm | محدود (Web APIs) |
| مناسب برای | کارهای سنگین، دیتابیس | تغییر پاسخ، احراز هویت، Geo |
| مدت اجرا | طولانی‌تر | کوتاه (چند ده میلی‌ثانیه) |

**CDN در برابر سرور مرکزی**

| معیار | سرور مرکزی | CDN/Edge |
|---|---|---|
| سرعت برای کاربر دور | کند | سریع |
| مقیاس‌پذیری | دستی | خودکار |
| هزینه در ترافیک بالا | بالا | بهینه |
| پیچیدگی راه‌اندازی | زیاد | تقریباً صفر |

### اشکال شایع

**۱. اشتباه گرفتن Build و Deploy.**
Build = آماده‌سازی کد؛ Deploy = منتشر کردن آن. اگر Build شکست بخورد، Deploy هرگز انجام نمی‌شود.

**۲. استفاده از Edge برای کارهای سنگین.**
Edge برای پاسخ‌های سریع و سبک است. کوئری سنگین دیتابیس یا پردازش طولانی را در Serverless انجام دهید.

**۳. تصور اینکه CDN همیشه همه چیز را کش می‌کند.**
کش بر اساس هدرها و پیکربندی شما کنترل می‌شود؛ محتوای شخصی‌سازی‌شده را نباید کش کرد.

**۴. فراموش کردن محدودیت Runtime در Edge.**
در Edge، دسترسی به `fs`، بعضی پکیج‌های Node و کتابخانه‌های سنگین وجود ندارد.

### نکات مهم (Tips & Tricks)

- **Build را همیشه محلی تست کنید** (`npm run build`) قبل از Push؛ این کار ۹۰٪ خطاهای Build در Vercel را جلوگیری می‌کند.
- برای منطق ساده و پرتکرار (مثل ریدایرکت، بررسی توکن) از **Edge** استفاده کنید.
- برای عملیات دیتابیس و منطق پیچیده از **Serverless (Node.js)** استفاده کنید.
- خروجی Build را در `.gitignore` بگذارید؛ در Vercel دوباره ساخته می‌شود.

### خلاصه فصل

- **Build** کد را به خروجی قابل اجرا تبدیل می‌کند.
- **Deploy** آن خروجی را منتشر می‌کند.
- **CDN/Edge** محتوا و کد را به کاربر نزدیک می‌کنند.
- **Serverless** اجرای کد بدون مدیریت سرور است.
- انتخاب درست بین **Edge** و **Serverless** کلید عملکرد و هزینه است.

## فصل ۴: اکوسیستم Vercel و تفاوت آن با هاست سنتی

### مقدمه

Vercel فقط «یک جا برای آپلود سایت» نیست؛ یک **اکوسیستم کامل** از ابزارهاست. در این فصل نقشهٔ کلی این اکوسیستم را می‌بینیم تا بدانید کدام بخش را کجا باید یاد بگیرید.

### مفاهیم اساسی

**۱. Deployments (استقرارها)**
هر بار که کد را Push می‌کنید، یک **Deployment** جدید ساخته می‌شود. هر Deployment یک URL یکتا و یک وضعیت (Building / Ready / Error) دارد.

**۲. Functions (توابع)**
کد سمت سرور شما: **Serverless Functions** و **Edge Functions**. (فایل ۰۵)

**۳. Storage (ذخیره‌سازی)**
سرویس‌های داده: **KV** (کلید-مقدار)، **Postgres** (رابطه‌ای)، **Blob** (فایل)، **Edge Config** (تنظیمات سریع). (فایل ۰۸)

**۴. Observability (مشاهده‌پذیری)**
**Logs**، **Analytics**، **Speed Insights** و **Drains**. (فایل ۱۳)

**۵. Security (امنیت)**
**Firewall**، **Bot Management**، **Rate Limiting**، مدیریت **Secrets** و محافظت از Deployments. (فایل ۱۲)

**۶. Developer Experience (تجربه توسعه‌دهنده)**
**Dashboard** (رابط وب)، **CLI** (خط فرمان)، **REST API** و **Integrations**.

**۷. Edge Network**
شبکهٔ جهانی که محتوا و کد را به کاربر نزدیک می‌کند.

### مثال‌های عملی

**مثال ۱ — یک اپلیکیشن کامل روی Vercel**

یک فروشگاه اینترنتی کوچک را در نظر بگیرید:

```
┌─────────────────────────────────────────────┐
│                  Vercel                      │
│                                             │
│  فرانت‌اند (Next.js)  ──  Edge Network (CDN)  │
│         │                                    │
│         ├── /api/products  → Serverless      │
│         ├── /api/cart      → KV              │
│         ├── /api/orders    → Postgres        │
│         ├── /api/upload    → Blob            │
│         └── middleware     → Edge (auth)     │
│                                             │
│  Cron: هر شب گزارش فروش → Serverless         │
│  Observability: Logs + Analytics + Insights │
└─────────────────────────────────────────────┘
```

**مثال ۲ — کار با CLI برای دیدن وضعیت پروژه**

```bash
# نصب CLI (یک‌بار)
npm i -g vercel

# ورود به حساب
vercel login

# دیدن لیست پروژه‌ها و استقرارها
vercel list

# استقرار در محیط Preview
vercel

# استقرار در محیط Production
vercel --prod
```

### مقایسه و الگوهای مختلف

**هاست سنتی در برابر Vercel**

| معیار | هاست سنتی (cPanel/VPS) | Vercel |
|---|---|---|
| راه‌اندازی | دستی، زمان‌بر | چند دقیقه |
| استقرار | FTP/SSH دستی | Git Push خودکار |
| SSL/HTTPS | دستی | خودکار |
| CDN جهانی | معمولاً ندارد/اضافه | پیش‌فرض |
| مقیاس‌پذیری | دستی | خودکار |
| Preview برای هر تغییر | ندارد | دارد |
| Rollback | دستی و پرخطر | یک‌کلیکی |
| توابع سرور | باید خودتان بنویسید | Serverless آماده |
| هزینه شروع | متغیر | رایگان (Hobby) |
| کنترل کامل سرور | ✅ | ❌ (مدیریت‌شده) |

**سه سبک کار با Vercel**

| سبک | ابزار | مناسب برای |
|---|---|---|
| Dashboard | رابط وب | کارهای بصری، دیدن لاگ‌ها |
| CLI | خط فرمان | توسعه‌دهندگان، اتوماسیون |
| REST API | کد | یکپارچه‌سازی، CI/CD سفارشی |

### اشکال شایع

**۱. فکر کردن Vercel «فقط هاست فرانت‌اند» است.**
در واقع با Functions و Storage می‌توانید کل بک‌اند را هم روی آن بسازید.

**۲. نادیده گرفتن Deploymentهای Preview.**
یکی از قدرتمندترین قابلیت‌هاست؛ برای هر تغییر یک محیط تست زنده می‌دهد.

**۳. قاطی کردن Storage با Deploy.**
داده‌های ذخیره‌شده در سرویس‌های Storage مستقل از Deploy هستند و با هر Deploy پاک نمی‌شوند (برخلاف فایل‌های محلی).

**۴. عدم استفاده از Dashboard برای رصد.**
لاگ‌ها و متریک‌ها همان‌جا هستند؛ نادیده گرفتنشان دیباگ را سخت می‌کند.

### نکات مهم (Tips & Tricks)

- ساختار ذهنی خود را این‌طور بسازید: **Deploy → Functions → Storage → Observability → Security**.
- از ابتدا نام‌گذاری پروژه‌ها و متغیرها را منظم کنید؛ در تیم‌های بزرگ حیاتی است.
- **CLI را یاد بگیرید**؛ سرعت کار شما را چند برابر می‌کند.
- از همان ابتدا **Preview Deployment** را در جریان کارتان بگنجانید.

### خلاصه فصل

- Vercel یک اکوسیستم کامل است، نه فقط هاست.
- اجزای اصلی: **Deployments، Functions، Storage، Observability، Security، DX، Edge Network**.
- در برابر هاست سنتی: راه‌اندازی سریع‌تر، امنیت خودکار، مقیاس خودکار و گردش کار Git-محور.
- سه راه کار: **Dashboard، CLI، REST API**.

## فصل ۵: آماده‌سازی ذهنی و ابزارهای مورد نیاز

### مقدمه

پیش از شروع عملی، باید ذهنیت درست و ابزارهای لازم را آماده کنید. در این فصل، دقیقاً می‌گوییم چه چیزی نصب کنید و با چه نگاهی وارد شوید.

### مفاهیم اساسی

**۱. ذهنیت Git-محور**
در Vercel، **Git منبع حقیقت است**. هر تغییری باید از طریق Git برود. این یعنی:
- تاریخچه‌ای شفاف از همهٔ تغییرات دارید.
- می‌توانید هر نسخه را برگردانید.
- کار تیمی ساده می‌شود.

**۲. ذهنیت «محیط‌ها» (Environments)**
سه محیط اصلی خواهید داشت:
- **Development**: روی کامپیوتر خودتان.
- **Preview**: برای تست هر تغییر (خودکار).
- **Production**: نسخه‌ای که کاربران می‌بینند.

**۳. ذهنیت «پیکربندی جدا از کد»**
اطلاعات حساس (کلید API، رمز دیتابیس) هرگز در کد نوشته نمی‌شوند؛ در **Environment Variables** قرار می‌گیرند (فایل ۰۷).

**۴. ابزارهای لازم**

| ابزار | نقش | سطح |
|---|---|---|
| **Node.js (LTS)** | اجرای پروژه و npm | الزامی |
| **npm** (همراه Node) | مدیریت پکیج‌ها | الزامی |
| **Git** | کنترل نسخه | الزامی |
| **حساب GitHub** | میزبانی کد | الزامی |
| **حساب Vercel** | پلتفرم | الزامی |
| **ویرایشگر کد** (VS Code) | نوشتن کد | الزامی |
| **Vercel CLI** | کار از خط فرمان | پیشنهادی |

### مثال‌های عملی

**مثال ۱ — بررسی نصب بودن ابزارها**

```bash
# نسخه Node.js (باید 18 یا بالاتر باشد)
node -v
# خروجی نمونه: v20.11.0

# نسخه npm
npm -v
# خروجی نمونه: 10.2.4

# نسخه Git
git --version
# خروجی نمونه: git version 2.43.0
```

اگر Node نصب نیست، نسخهٔ **LTS** را از سایت رسمی نصب کنید.

**مثال ۲ — نصب Vercel CLI و ورود**

```bash
# نصب سراسری CLI
npm i -g vercel

# بررسی نسخه
vercel --version

# ورود به حساب (مرورگر باز می‌شود)
vercel login

# تأیید ورود
vercel whoami
```

**مثال ۳ — تنظیم هویت Git (اگر تازه نصب کرده‌اید)**

```bash
git config --global user.name "نام شما"
git config --global user.email "you@example.com"

# بررسی
git config --list
```

### مقایسه و الگوهای مختلف

**سه راه شروع یک پروژه در Vercel**

| روش | دستور/مراحل | مناسب برای |
|---|---|---|
| **Import از Git** | در Dashboard مخزن را وصل کنید | پروژه‌های واقعی (پیشنهادی) |
| **CLI** | `vercel` در پوشه پروژه | توسعه‌دهندگان، سرعت |
| **Template** | انتخاب قالب آماده در Dashboard | شروع سریع، یادگیری |

**انتخاب نسخه Node.js**

| نسخه | وضعیت | توصیه |
|---|---|---|
| Node 18 | LTS قدیمی‌تر | سازگار با اکثر پروژه‌ها |
| Node 20 | LTS | ✅ پیشنهادی |
| Node 22 | LTS جدید | ✅ اگر پروژه پشتیبانی می‌کند |
| Node 24+ | جدید | فقط اگر وابستگی‌ها پشتیبانی کنند |

### اشکال شایع

**۱. نصب نبودن Node.js یا نسخه قدیمی.**
باعث خطاهای عجیب در Build می‌شود. همیشه از LTS استفاده کنید.

**۲. اشتباه در ایمیل/نام Git.**
Commitها با هویت اشتباه ثبت می‌شوند. یک بار درست تنظیم کنید.

**۳. کار کردن با حساب Vercel اشتباه.**
اگر چند حساب دارید، با `vercel whoami` بررسی کنید روی کدام هستید.

**۴. نادیده گرفتن فایل `.gitignore`.**
پوشه‌هایی مثل `node_modules` و `.env` هرگز نباید Commit شوند.

**۵. تصور اینکه باید همه ابزارها را از روز اول کامل بلد باشید.**
نه! با همان حداقل‌ها شروع کنید و در مسیر یاد بگیرید.

### نکات مهم (Tips & Tricks)

- یک فایل `.gitignore` استاندارد برای Node داشته باشید:

```gitignore
node_modules/
.next/
dist/
build/
.env
.env.local
.vercel
.DS_Store
```

- **VS Code** را با افزونه‌های Git، ESLint و Prettier راه‌اندازی کنید.
- **قبل از هر Push، محلی Build بگیرید** تا در Vercel غافلگیر نشوید.
- یک پروژهٔ تمرینی جداگانه بسازید تا آزادانه خرابکاری کنید و یاد بگیرید.

### خلاصه فصل

- ذهنیت درست: **Git-محور**، **محیط‌محور** و **پیکربندی جدا از کد**.
- ابزارهای الزامی: **Node.js LTS، npm، Git، GitHub، حساب Vercel، ویرایشگر کد**.
- ابزار پیشنهادی: **Vercel CLI**.
- با حداقل‌ها شروع کنید؛ در مسیر جلوتر یاد می‌گیرید.
- `.gitignore` درست، از فاجعه‌های بعدی جلوگیری می‌کند.
