## فصل ۷۶: Observability چیست و چه تفاوتی با Monitoring دارد

### مقدمه

**Monitoring** می‌گوید «چیزی خراب است». **Observability** می‌گوید «چرا».

تفاوت، در **سؤال‌هایی است که می‌توانی بپرسی** — نه در ابزار.

### مفاهیم اساسی

**تعریف:**

| معیار | Monitoring | Observability |
|---|---|---|
| سؤال | «آیا خراب است؟» | «چرا خراب است؟» |
| داده | متریک از پیش تعریف‌شده | هر داده، قابل پرسش |
| مناسب | حادثه شناخته‌شده | حادثه ناشناخته |
| رویکرد | چک‌لیست | کاوش |

**نکته کلیدی**: Monitoring برای سؤالاتی است که **از قبل می‌دانی**. Observability برای سؤالاتی که **نمی‌دانی**.

```
Monitoring: "آیا CPU بالاست؟"       (سؤال از قبل)
Observability: "چرا کاربران در برلین کند هستند؟"  (سؤال جدید)
```

**سه ویژگی سیستم قابل مشاهده:**

| ویژگی | معنا |
|---|---|
| **قابل پرسش** | می‌توانی سؤال جدید بپرسی |
| **با context** | داده به کاربر/درخواست وصل است |
| **بدون تغییر کد** | برای سؤال جدید، deploy لازم نیست |

**نکته**: اگر برای هر سؤال جدید باید کد اضافه کنی، Observability نداری.

**چهار سطح بلوغ:**

| سطح | ویژگی |
|---|---|
| ۱ | لاگ پراکنده |
| ۲ | متریک + داشبورد |
| ۳ | + trace |
| ۴ | ✅ + correlation، کاوش آزاد |

### مثال‌های عملی

**سؤال‌های واقعی در حادثه:**

```
❌ Monitoring جواب می‌دهد:
   "نرخ خطا ۱۸٪ است"

✅ Observability جواب می‌دهد:
   "خطاها فقط در endpoint /checkout هستند
    فقط برای کاربران با کارت Mastercard
    فقط از ساعت ۱۰:۰۵ شروع شد
    همه از نسخه v1.4.3
    تریس نشان می‌دهد timeout در سرویس پرداخت"
```

**تفاوت**: اولی می‌گوید «چیزی خراب است»، دومی می‌گوید «چه چیزی، کجا، برای چه کسی».

**Correlation — مهم‌ترین قابلیت:**

```
یک درخواست کاربر:
  request_id: abc-123

  در لاگ:   [abc-123] POST /checkout 500
  در متریک: http_requests_total{status="500", endpoint="/checkout"} 1
  در تریس:  trace abc-123: gateway → checkout → payment (timeout 5s)

→ می‌توانی از هر نقطه به بقیه برسی
```

**بدون correlation**: سه داده جدا، بدون ارتباط.

**مثال پیاده‌سازی:**

```python
"""افزودن request_id به همه لاگ‌ها."""
import logging
import uuid

from contextvars import ContextVar

request_id_var: ContextVar[str] = ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    """افزودن request_id به هر رکورد لاگ."""

    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True


def setup_logging() -> None:
    """پیکربندی لاگ با request_id."""
    handler = logging.StreamHandler()
    handler.setFormatter(
        logging.Formatter(
            "%(asctime)s %(levelname)s [%(request_id)s] %(name)s: %(message)s"
        )
    )
    handler.addFilter(RequestIdFilter())

    root = logging.getLogger()
    root.addHandler(handler)
    root.setLevel(logging.INFO)


def new_request_id() -> str:
    """تولید و ثبت request_id جدید."""
    rid = str(uuid.uuid4())[:8]
    request_id_var.set(rid)
    return rid
```

**نتیجه در لاگ:**

```
2026-10-17 10:05:12 INFO [abc-123] checkout: پرداخت شروع شد
2026-10-17 10:05:17 ERROR [abc-123] payment: timeout بعد از 5s
2026-10-17 10:05:17 ERROR [abc-123] checkout: خطا در پرداخت
```

**سه خط، یک درخواست، قابل ردیابی.**

### مقایسه و الگوهای مختلف

**سه رویکرد:**

| رویکرد | هزینه | قابلیت |
|---|---|---|
| لاگ فقط | ✅ کم | ⚠️ |
| لاگ + متریک | متوسط | ✅ |
| ✅ سه‌گانه | ❌ زیاد | ✅✅ |

**Observability در برابر APM:**

| معیار | Observability | APM |
|---|---|---|
| دامنه | کل سیستم | اپ |
| هزینه | متغیر | ❌ گران |
| انعطاف | ✅✅ | متوسط |

**سه سطح پیاده‌سازی:**

| سطح | چه داری |
|---|---|
| ۱ | لاگ ساختاریافته |
| ۲ | + متریک و داشبورد |
| ۳ | ✅ + تریس توزیع‌شده |

### اشکال شایع

**اشکال ۱: لاگ بدون ساختار**

`print("error")` — قابل جستجو نیست. JSON بساز.

**اشکال ۲: بدون correlation**

سه داده جدا، بدون ارتباط. request_id بگذار.

**اشکال ۳: فقط متریک**

می‌دانی خطا هست، نمی‌دانی چرا. لاگ و تریس لازم.

**اشکال ۴: Observability گران**

ذخیره همه‌چیز برای همیشه. sampling و retention.

**اشکال ۵: داشبورد بدون owner**

کهنه می‌شود. مالک تعیین کن.

**اشکال ۶: ابزار قبل از فرهنگ**

ابزار خریدی، کسی استفاده نمی‌کند. اول سؤال، بعد ابزار.

### نکات مهم (Tips & Tricks)

- **request_id** در همه لاگ‌ها.
- **لاگ ساختاریافته** (JSON).
- **سه‌گانه** با هم، نه یکی.
- **sampling** برای هزینه.
- **داشبورد با مالک.**
- **سؤال بپرس، بعد ابزار انتخاب کن.**

### خلاصه فصل

- Monitoring می‌گوید «خراب است»، Observability «چرا».
- سه ویژگی: قابل پرسش، با context، بدون تغییر کد.
- Correlation مهم‌ترین قابلیت است.
- request_id در همه لاگ‌ها.
- سه‌گانه با هم.
- ابزار بعد از سؤال.

## فصل ۷۷: سه ستون — لاگ، متریک، تریس

### مقدمه

سه نوع داده، سه هدف متفاوت. این فصل تفاوت و استفاده هر کدام را می‌آورد.

### مفاهیم اساسی

**سه ستون:**

| ستون | چه می‌گوید | حجم | هزینه |
|---|---|---|---|
| **Metrics** | «چقدر؟» | ✅ کم | ✅ کم |
| **Logs** | «چه اتفاقی؟» | ❌ زیاد | متوسط |
| **Traces** | «کجا کند است؟» | متوسط | ❌ زیاد |

**نکته**: هر سه لازم است. هیچ‌کدام جایگزین دیگری نیست.

**مقایسه دقیق:**

| سؤال | ابزار |
|---|---|
| چند درخواست در ثانیه؟ | Metric |
| چه خطایی داد؟ | Log |
| کدام سرویس کند است؟ | Trace |
| روند هفته گذشته؟ | Metric |
| کاربر X چه دید؟ | Log + Trace |
| کجا bottleneck است؟ | Trace |

### مثال‌های عملی

**Metric — نمونه:**

```
http_requests_total{method="POST", endpoint="/checkout", status="200"} 1543
http_request_duration_seconds_bucket{le="0.3"} 1480
http_request_duration_seconds_bucket{le="1.0"} 1540
```

**نکته**: متریک **aggregated** است — نمی‌دانی کدام کاربر.

**Log — نمونه (ساختاریافته):**

```json
{
  "timestamp": "2026-10-17T10:05:17.234Z",
  "level": "error",
  "request_id": "abc-123",
  "user_id": "u-456",
  "service": "payment",
  "event": "gateway_timeout",
  "duration_ms": 5000,
  "gateway": "stripe",
  "error": "connection timeout after 5000ms"
}
```

**نکته**: ساختاریافته = قابل جستجو و فیلتر.

**Trace — نمونه:**

```
Trace abc-123 (total: 5.2s)
├── gateway          [5.2s] ████████████████████████
│   ├── auth         [0.1s] █
│   ├── checkout     [5.1s] ███████████████████████
│   │   ├── inventory [0.05s]
│   │   ├── payment  [5.0s] █████████████████████ ← bottleneck
│   │   │   └── stripe-api [4.9s]
│   │   └── notify   [0.02s]
```

**نکته**: تریس، **مسیر** و **زمان هر مرحله** را نشان می‌دهد. اینجا bottleneck واضح است.

**سه سطح sampling:**

| سطح | مناسب |
|---|---|
| ۱۰۰٪ | خطاها |
| ۱۰٪ | درخواست عادی |
| ۱٪ | حجم بالا |

**نکته**: خطاها را همیشه نگه دار، موفق‌ها را sample کن.

**پیاده‌سازی تریس — مفهوم:**

```python
"""تریس ساده با context propagation."""
import time
import uuid
from contextlib import contextmanager

from opentelemetry import trace

tracer = trace.get_tracer(__name__)


@contextmanager
def span(name: str):
    """ایجاد span با ثبت زمان."""
    with tracer.start_as_current_span(name) as s:
        start = time.monotonic()
        try:
            yield s
        finally:
            elapsed = (time.monotonic() - start) * 1000
            s.set_attribute("duration_ms", elapsed)
```

**نکته**: در سیستم واقعی از OpenTelemetry استفاده کن — استاندارد باز.

### مقایسه و الگوهای مختلف

**سه مدل ذخیره:**

| مدل | مناسب |
|---|---|
| Metric در TSDB | Prometheus، VictoriaMetrics |
| Log در موتور جستجو | Loki، Elasticsearch |
| Trace در store تخصصی | Tempo، Jaeger |

**نکته**: سه سیستم جدا، با correlation از طریق ID.

**Pull در برابر Push:**

| معیار | Pull | Push |
|---|---|---|
| مدل | سرور می‌خواند | اپ می‌فرستد |
| مناسب | ✅ متریک | رویداد |
| مثال | Prometheus | OTLP |

**سه سطح هزینه:**

| سطح | راه‌حل |
|---|---|
| کم | retention کوتاه، sampling |
| متوسط | tiered storage |
| زیاد | همه‌چیز، برای همیشه |

### اشکال شایع

**اشکال ۱: لاگ برای متریک**

«تعداد درخواست را از لاگ بشمار» — کند و گران. متریک بساز.

**اشکال ۲: متریک برای جزئیات**

«کدام کاربر خطا گرفت؟» — متریک aggregate است. لاگ.

**اشکال ۳: تریس بدون sampling**

هزینه انفجاری. sampling.

**اشکال ۴: لاگ بدون سطح**

همه `INFO`، خطاها گم می‌شوند. سطح‌بندی درست.

**اشکال ۵: متریک با cardinality بالا**

`user_id` به‌عنوان label = میلیون سری. ممنوع.

**اشکال ۶: بدون correlation**

سه سیستم جدا، بدون ID مشترک. بی‌فایده.

### نکات مهم (Tips & Tricks)

- **سه‌گانه با هم**، با ID مشترک.
- **Metric برای روند، Log برای جزئیات، Trace برای مسیر.**
- **Cardinality پایین** در label.
- **Sampling** برای هزینه.
- **خطاها را همیشه نگه دار.**
- **OpenTelemetry** استاندارد باز است.

### خلاصه فصل

- سه ستون: metric (چقدر)، log (چه)، trace (کجا).
- هر سه لازم است.
- Metric aggregate، log جزئی، trace مسیر.
- Cardinality پایین در label.
- Sampling برای هزینه.
- Correlation با ID مشترک.

## فصل ۷۸: طراحی SLI و هشدار

### مقدمه

هشدار خوب، تیم را بیدار می‌کند برای چیزی که **الان باید اقدام کند**. هشدار بد، تیم را بیدار می‌کند برای هیچ.

این فصل طراحی هشدار مؤثر را می‌آورد.

### مفاهیم اساسی

**قاعده طلایی:**

```
اگر نمی‌توانی الان کاری بکنی، هشدار نده.
```

**سه نوع هشدار:**

| نوع | کانال | آستانه |
|---|---|---|
| **Page** | تلفن | SLO در خطر |
| **Ticket** | Slack/Jira | روند نگران‌کننده |
| **Log** | داشبورد | اطلاعاتی |

**نکته**: ۹۰٪ هشدارها باید Ticket باشند، نه Page.

**چهار سیگنال طلایی (یادآوری):**

| سیگنال | SLI |
|---|---|
| Latency | درصد زیر آستانه |
| Traffic | درخواست/ثانیه |
| Errors | درصد خطا |
| Saturation | مصرف ظرفیت |

### مثال‌های عملی

**هشدار خوب در برابر بد:**

```
❌ بد: CPU > 80%
  چرا: CPU بالا ممکن است طبیعی باشد
  نتیجه: هشدار کاذب

✅ خوب: SLO burn rate > 14× در ۱ ساعت
  چرا: مستقیماً به تجربه کاربر وصل است
  نتیجه: اقدام واقعی لازم
```

**نکته**: هشدار روی **علت** (CPU) نویز است. هشدار روی **اثر** (SLO) مفید است.

**سه سطح burn rate:**

```yaml
# مفهوم
alerts:
  - name: SLOBurnRateCritical
    expr: |
      (
        sum(rate(http_requests_total{status=~"5.."}[1h]))
        / sum(rate(http_requests_total[1h]))
      ) > (14 * 0.001)        # 14× بودجه
    for: 2m
    severity: page
    annotations:
      summary: "SLO در خطر جدی — ۲٪ بودجه در ۱ ساعت"

  - name: SLOBurnRateHigh
    expr: |
      (
        sum(rate(http_requests_total{status=~"5.."}[6h]))
        / sum(rate(http_requests_total[6h]))
      ) > (6 * 0.001)
    for: 15m
    severity: page

  - name: SLOBurnRateSlow
    expr: |
      (
        sum(rate(http_requests_total{status=~"5.."}[3d]))
        / sum(rate(http_requests_total[3d]))
      ) > (1 * 0.001)
    for: 1h
    severity: ticket
```

**منطق**: پنجره کوتاه + آستانه بالا = حادثه فوری. پنجره بلند + آستانه پایین = روند.

**هشدار latency:**

```
❌ بد: p99 > 500ms
   چرا: p99 نوسان دارد، هشدار کاذب زیاد

✅ خوب: درصد درخواست‌های زیر 300ms کمتر از 95٪ برای ۱۰ دقیقه
   چرا: مستقیم به SLO وصل است
```

**نکته**: percentile تکی، نویزی است. نسبت (درصد زیر آستانه) پایدارتر.

**runbook برای هر هشدار:**

```markdown
# Alert: SLOBurnRateCritical

## معنای
نرخ خطا ۱۴ برابر بودجه در ۱ ساعت گذشته.

## بررسی (۲ دقیقه)
1. آخرین deploy؟
2. کدام endpoint؟ (داشبورد)
3. خطا چیست؟ (لاگ با request_id)

## اقدام
- بعد از deploy → rollback
- dependency → بررسی وضعیت سرویس خارجی
- نامشخص → escalate

## Escalation
۱۰ دقیقه بدون پیشرفت → secondary on-call
```

**نکته**: اگر runbook نداری، هشدار نده.

### مقایسه و الگوهای مختلف

**Symptom-based در برابر Cause-based:**

| معیار | Symptom | Cause |
|---|---|---|
| چه می‌سنجد | اثر کاربر | علت فنی |
| نویز | ✅ کم | ❌ زیاد |
| مناسب | ✅ صفحه | داشبورد |

**توصیه**: صفحه روی symptom، داشبورد روی cause.

**سه سطح آستانه:**

| سطح | تنظیم |
|---|---|
| ثابت | `> 1%` |
| نسبی | `> 2× میانگین` |
| ✅ SLO-based | `> 14× burn rate` |

**Alert در برابر Anomaly Detection:**

| معیار | Alert | Anomaly |
|---|---|---|
| دقت | ✅ بالا | ❌ متوسط |
| تنظیم | دستی | خودکار |
| مناسب | SLO | کشف ناشناخته |

### اشکال شایع

**اشکال ۱: هشدار روی علت**

CPU، memory، disk — نویز زیاد. روی اثر (SLO).

**اشکال ۲: آستانه ثابت برای همه**

سرویس‌ها متفاوت‌اند. آستانه مناسب هر سرویس.

**اشکال ۳: بدون runbook**

هشدار می‌آید، کسی نمی‌داند چه کند.

**اشکال ۴: هشدار برای همه‌چیز**

alert fatigue. فقط اقدام فوری.

**اشکال ۵: بدون تست هشدار**

هشدار خراب است، نمی‌دانی. دوره‌ای تست کن.

**اشکال ۶: هشدار بدون مالک**

چه کسی پاسخ می‌دهد؟ مالک مشخص.

**اشکال ۷: آستانه خیلی حساس**

هر نوسان کوچک، هشدار. `for:` بگذار.

### نکات مهم (Tips & Tricks)

- **اگر نمی‌توانی اقدام کنی، هشدار نده.**
- **SLO-based بهتر از threshold.**
- **`for:` برای جلوگیری از نویز.**
- **runbook برای هر هشدار.**
- **صفحه فقط برای اقدام فوری.**
- **هشدارها را دوره‌ای تست کن.**

### خلاصه فصل

- هشدار خوب = اقدام فوری ممکن.
- سه نوع: page، ticket، log.
- ۹۰٪ باید ticket باشند.
- صفحه روی symptom، نه cause.
- SLO burn rate بهترین آستانه است.
- runbook برای هر هشدار.

## فصل ۷۹: پاسخ به حادثه — عملی

### مقدمه

این فصل فرآیند عملی پاسخ به حادثه را گام‌به‌گام می‌آورد — از لحظه alert تا postmortem.

### مفاهیم اساسی

**چهار مرحله:**

```
کشف → تثبیت → رفع → یادگیری
```

| مرحله | هدف | زمان |
|---|---|---|
| کشف | بدان | خودکار |
| تثبیت | کاهش اثر | دقیقه |
| رفع | علت را برطرف کن | ساعت |
| یادگیری | تکرار نشود | روز |

**نکته**: تثبیت و رفع، دو مرحله جدا هستند. اول تثبیت.

### مثال‌های عملی

**گام ۱: کشف و تأیید (۲ دقیقه)**

```
۱. alert آمد
۲. تأیید: آیا واقعی است؟
   - داشبورد را ببین
   - یک درخواست دستی بزن
۳. اگر کاذب → هشدار را اصلاح کن
۴. اگر واقعی → ادامه
```

**گام ۲: تثبیت (۵-۱۵ دقیقه)**

| وضعیت | اقدام |
|---|---|
| بعد از deploy | rollback |
| feature flag فعال | flag off |
| ترافیک بالا | scale up |
| dependency خراب | circuit breaker |
| نامشخص | rollback آخرین تغییر |

**قاعده**: اگر نمی‌دانی، **آخرین تغییر را برگردان**.

**گام ۳: اعلام**

```
#incident کانال بساز:
  - شدت (SEV1/2/3)
  - IC
  - به‌روزرسانی هر ۵ دقیقه
```

**قالب اعلام:**

```
🔴 SEV1 — checkout-api
تأثیر: ۱۸٪ درخواست‌های checkout خطا
شروع: 10:05
IC: @sara
وضعیت: rollback در حال اجرا
```

**گام ۴: رفع**

```
بعد از تثبیت:
  ۱. علت را پیدا کن (بدون فشار)
  ۲. رفع کن
  ۳. تأیید کن (smoke test)
  ۴. اعلام رفع
```

**گام ۵: یادگیری**

```
۴۸ ساعت بعد:
  postmortem بنویس
  اقدام تعریف کن
  پیگیری کن
```

**درخت تصمیم سریع:**

```
alert آمد
├── آیا واقعی است؟
│   ├── نه → هشدار را اصلاح کن
│   └── بله ↓
├── آیا بعد از deploy است؟
│   ├── بله → rollback فوری
│   └── نه ↓
├── آیا feature flag مربوط است؟
│   ├── بله → flag off
│   └── نه ↓
├── آیا ترافیک غیرعادی است؟
│   ├── بله → scale / rate limit
│   └── نه ↓
└── آخرین تغییر را برگردان، بعد دیباگ کن
```

**این درخت، در ساعت ۳ بامداد نجات‌بخش است.**

### مقایسه و الگوهای مختلف

**سه مدل پاسخ:**

| مدل | مناسب |
|---|---|
| Hero | ❌ تیم کوچک، غیرپایدار |
| IC model | ✅ توصیه |
| Automated | ✅ برای حادثه شناخته‌شده |

**نکته**: خودکارسازی پاسخ (auto-rollback) برای حادثه‌های شناخته‌شده بهترین است — سریع‌تر از انسان.

**سه سطح خودکارسازی:**

| سطح | مثال |
|---|---|
| Alert | فقط اطلاع |
| Assisted | پیشنهاد اقدام |
| ✅ Automated | auto-rollback |

**Communication در برابر Debugging:**

| معیار | Communication | Debugging |
|---|---|---|
| چه کسی | IC | Ops Lead |
| کجا | #incident | #incident-debug |
| هدف | هماهنگی | حل |

**نکته**: تفکیک این دو، کلید IC مؤثر است.

### اشکال شایع

**اشکال ۱: دیباگ قبل از تثبیت**

سرویس ۱ ساعت خراب. اول rollback.

**اشکال ۲: بدون IC**

هر کس چیزی می‌کند. هماهنگی صفر.

**اشکال ۳: بحث فنی در کانال اصلی**

IC نمی‌تواند هماهنگ کند. کانال جدا.

**اشکال ۴: بدون به‌روزرسانی**

ذی‌نفعان نگران. هر ۵ دقیقه.

**اشکال ۵: بدون scribe**

خط زمانی گم می‌شود.

**اشکال ۶: رفع بدون تأیید**

«درست شد» بدون smoke test. ممکن است برنگردد.

**اشکال ۷: بدون postmortem**

تکرار می‌شود.

### نکات مهم (Tips & Tricks)

- **اول تثبیت، بعد رفع.**
- **اگر نمی‌دانی، آخرین تغییر را برگردان.**
- **IC تعیین کن.**
- **کانال جدا برای دیباگ.**
- **هر ۵ دقیقه به‌روزرسانی.**
- **auto-rollback برای حادثه شناخته‌شده.**

### خلاصه فصل

- چهار مرحله: کشف، تثبیت، رفع، یادگیری.
- تثبیت و رفع جدا هستند.
- اگر نمی‌دانی، rollback.
- IC + کانال جدا.
- هر ۵ دقیقه به‌روزرسانی.
- postmortem در ۴۸ ساعت.

## فصل ۸۰: ظرفیت و کارایی

### مقدمه

**ظرفیت** و **کارایی** دو روی یک سکه‌اند: چقدر می‌توانیم تحمل کنیم، و چقدر خوب کار می‌کنیم.

این فصل اصول را می‌آورد — مفهومی، نه ابزارمحور.

### مفاهیم اساسی

**سه مفهوم:**

| مفهوم | معنا |
|---|---|
| **Capacity** | حداکثر بار قابل تحمل |
| **Utilization** | درصد استفاده |
| **Headroom** | ظرفیت آزاد |

**قاعده ۸۰٪ (یادآوری نظریه صف):**

```
استفاده ۸۰٪ → انتظار ۵×
استفاده ۹۰٪ → انتظار ۱۰×
استفاده ۹۵٪ → انتظار ۲۰×
```

**نکته**: headroom ۲۰٪ لازم است — نه برای بیکاری، برای جریان.

**سه نوع محدودیت:**

| نوع | مثال |
|---|---|
| **عمودی** | CPU، memory یک سرور |
| **افقی** | تعداد instance |
| **وابستگی** | DB، سرویس خارجی |

**نکته**: اغلب، گلوگاه **وابستگی** است، نه سرور خودت.

### مثال‌های عملی

**محاسبه ظرفیت:**

```
سرویس فعلی:
  ۴ instance
  هر کدام ۵۰۰ req/s
  ظرفیت کل: ۲۰۰۰ req/s
  بار فعلی: ۱۲۰۰ req/s
  استفاده: ۶۰٪  ✅ سالم

پیش‌بینی رشد: ۳۰٪ در ۶ ماه
بار آینده: ۱۵۶۰ req/s
استفاده: ۷۸٪  ⚠️ نزدیک حد

اقدام: ۲ instance اضافه → ۳۰۰۰ req/s → استفاده ۵۲٪
```

**نکته**: ظرفیت را برای **آینده** برنامه‌ریزی کن، نه امروز.

**Load testing — سه نوع:**

| نوع | هدف | مدت |
|---|---|---|
| **Load** | رفتار در بار عادی | ۱ ساعت |
| **Stress** | نقطه شکست | تا شکست |
| **Soak** | نشت حافظه | ۲۴ ساعت |

**نکته**: Soak test اغلب فراموش می‌شود — و نشت حافظه فقط در ۲۴ ساعت ظاهر می‌شود.

**نتیجه load test — نمونه:**

```
بار (req/s)  p50    p95    p99    خطا
────────────────────────────────────────
500          45ms   120ms  200ms  0%
1000         50ms   150ms  280ms  0%
1500         65ms   220ms  450ms  0.1%
1800         90ms   400ms  900ms  0.5%
2000         150ms  1200ms 3000ms 2%
2100         timeout       >10s   18%   ← نقطه شکست

ظرفیت ایمن: ۱۵۰۰ req/s (۷۵٪ نقطه شکست)
```

**نکته**: نقطه شکست، جایی است که p99 انفجاری می‌شود.

**بهینه‌سازی — سه سطح:**

| سطح | اثر | هزینه |
|---|---|---|
| کد | ✅✅ | متوسط |
| معماری | ✅✅✅ | ❌ زیاد |
| زیرساخت | ✅ | ❌ زیاد |

**توصیه**: اول کد (N+1، الگوریتم)، بعد معماری (cache، async)، آخر زیرساخت (سرور بیشتر).

**مثال N+1:**

```python
# ❌ N+1: ۱ + N کوئری
users = User.query.all()          # ۱ کوئری
for u in users:
    print(u.orders)               # N کوئری

# ✅ ۲ کوئری
users = User.query.options(joinedload(User.orders)).all()
```

**اثر**: برای ۱۰۰۰ کاربر، از ۱۰۰۱ کوئری به ۱ کوئری. **۱۰۰۰ برابر سریع‌تر.**

### مقایسه و الگوهای مختلف

**Scale up در برابر Scale out:**

| معیار | Scale up | Scale out |
|---|---|---|
| روش | سرور قوی‌تر | سرور بیشتر |
| حد | ✅ دارد | ✅ ندارد |
| پیچیدگی | ✅ کم | متوسط |
| مناسب | شروع | مقیاس |

**Cache در برابر بهینه‌سازی:**

| معیار | Cache | بهینه‌سازی |
|---|---|---|
| سرعت اثر | ✅ فوری | متوسط |
| پیچیدگی | ⚠️ invalidation | ✅ |
| مناسب | خواندن زیاد | هر دو |

**سه سطح headroom:**

| سطح | headroom |
|---|---|
| سرویس حیاتی | ۵۰٪ |
| سرویس عادی | ✅ ۲۰٪ |
| batch | ۵٪ |

### اشکال شایع

**اشکال ۱: استفاده ۱۰۰٪**

صف بی‌نهایت. headroom بگذار.

**اشکال ۲: ظرفیت برای امروز**

رشد را حساب کن. ۶ ماه آینده.

**اشکال ۳: بدون load test**

«فکر می‌کنیم کافی است» — تست کن.

**اشکال ۴: بهینه‌سازی زیرساخت قبل از کد**

۲ برابر سرور، به‌جای رفع N+1.

**اشکال ۵: نادیده گرفتن وابستگی**

سرور خودت خوب، DB گلوگاه.

**اشکال ۶: بدون soak test**

نشت حافظه در ۲۴ ساعت ظاهر می‌شود.

**اشکال ۷: ظرفیت بدون پایش**

نمی‌دانی چقدر استفاده می‌شود.

### نکات مهم (Tips & Tricks)

- **headroom ۲۰٪** حداقل.
- **ظرفیت برای ۶ ماه آینده.**
- **load test سه‌گانه**: load، stress، soak.
- **اول کد، بعد معماری، آخر زیرساخت.**
- **وابستگی را ببین** — اغلب گلوگاه آنجاست.
- **ظرفیت را پایش کن.**

### خلاصه فصل

- سه مفهوم: capacity، utilization، headroom.
- headroom ۲۰٪ برای جریان لازم است.
- سه نوع محدودیت: عمودی، افقی، وابستگی.
- load test سه‌گانه.
- اول کد بهینه کن.
- ظرفیت برای آینده.
