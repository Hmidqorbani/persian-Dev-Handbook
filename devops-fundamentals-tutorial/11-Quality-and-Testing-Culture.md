## فصل ۵۸: کیفیت به‌عنوان مسئولیت مشترک

### مقدمه

در مدل سنتی، **تیم QA** مسئول کیفیت بود. توسعه‌دهنده کد می‌نوشت، QA تست می‌کرد، باگ برمی‌گشت.

در DevOps، کیفیت **مسئولیت مشترک** است — و این تغییر، بنیادی است.

### مفاهیم اساسی

**مدل سنتی در برابر DevOps:**

| معیار | سنتی | DevOps |
|---|---|---|
| مسئول کیفیت | تیم QA | ✅ همه |
| تست | بعد از توسعه | همزمان |
| بازخورد | روز-هفته | دقیقه |
| دیوار | «این باگ شماست» | «چطور سیستم اجازه داد؟» |

**چرا مدل سنتی شکست می‌خورد:**

```
توسعه‌دهنده: "کار من نوشتن کد است"
    ↓
باگ در QA کشف می‌شود
    ↓
"این باگ شماست، برگردانده شد"
    ↓
توسعه‌دهنده عصبانی، QA عصبانی
    ↓
(بازی blame)
```

**نتیجه**: کیفیت پایین، رابطه خراب.

**«Quality is Free» — اصل کروسبی:**

> کیفیت اضافه نیست؛ **عدم کیفیت** گران است.

| هزینه کیفیت | هزینه عدم کیفیت |
|---|---|
| تست، review، خودکارسازی | بازکاری، hotfix، از دست دادن مشتری |
| ✅ قابل پیش‌بینی | ❌ تصاعدی |

**نکته**: کیفیت سرمایه‌گذاری است، نه هزینه.

**چهار سطح مسئولیت:**

| سطح | چه کسی |
|---|---|
| طراحی | کل تیم |
| پیاده‌سازی | توسعه‌دهنده |
| تست | توسعه‌دهنده + خودکار |
| پایش | همه (on-call مشترک) |

### مثال‌های عملی

**تغییر نقش QA:**

| قبل | بعد |
|---|---|
| تست دستی | طراحی استراتژی تست |
| پیدا کردن باگ | جلوگیری از باگ |
| گلوگاه release | توانمندسازی تیم |
| «دروازه» | «مربی کیفیت» |

**نکته**: QA حذف نمی‌شود؛ **نقشش عوض می‌شود** — از «تست‌کننده» به «مهندس کیفیت».

**Definition of Done با کیفیت:**

```
[ ] کد نوشته شد
[ ] تست واحد دارد
[ ] تست integration دارد (اگر لازم)
[ ] در staging تست شد
[ ] در production است
[ ] متریک/alert دارد
[ ] در حادثه قابل دیباگ است (لاگ کافی)
```

**نکته**: آخرین مورد را اکثر تیم‌ها فراموش می‌کنند — و در حادثه پشیمان می‌شوند.

**«Shift Left» در کیفیت:**

```
        هزینه رفع باگ
   ┌──────────────────────────┐
   │                          │
   │                    ●     │  production
   │              ●           │  staging
   │        ●                 │  CI
   │   ●                      │  review
   │ ●                        │  کدنویسی
   └──────────────────────────┘
```

هر چه زودتر، ارزان‌تر. و **تست خودکار**، تنها راه عملی است.

### مقایسه و الگوهای مختلف

**سه مدل کیفیت:**

| مدل | مسئول | نتیجه |
|---|---|---|
| QA-centric | تیم QA | ❌ دیوار |
| Dev-centric | توسعه‌دهنده | ⚠️ بهتر، ولی تعصب |
| ✅ Shared | همه | ✅✅ |

**سه سطح تست:**

| سطح | چه کسی | چه چیزی |
|---|---|---|
| خودکار | CI | regressions |
| اکتشافی | QA/Dev | سناریوهای جدید |
| کاربر | production | واقعیت |

**نکته**: تست خودکار جای اکتشافی را نمی‌گیرد. هر دو لازم.

**«Testing Trophy» در برابر «Pyramid»:**

| مدل | تمرکز |
|---|---|
| Pyramid | unit زیاد |
| Trophy | integration زیاد |
| مناسب | سیستم‌های توزیع‌شده |

### اشکال شایع

**اشکال ۱: QA به‌عنوان دروازه**

QA آخر خط، همه باگ‌ها را می‌گیرد. گلوگاه و خصومت.

**اشکال ۲: «تست کار QA است»**

توسعه‌دهنده تست نمی‌نویسد، کیفیت پایین. مسئولیت مشترک.

**اشکال ۳: کیفیت = تست بیشتر**

تست بدون استراتژی، کند و بی‌اثر. استراتژی مهم‌تر از تعداد.

**اشکال ۴: QA حذف شد**

«ما DevOps هستیم، QA لازم نیست» — نقش عوض می‌شود، حذف نمی‌شود.

**اشکال ۵: کیفیت به‌عنوان فاز**

«فاز تست» در انتها. کیفیت باید در هر مرحله باشد.

**اشکال ۶: معیار کیفیت = باگ کم**

اگر باگ کم معیار باشد، باگ گزارش نمی‌شود.

### نکات مهم (Tips & Tricks)

- **مسئولیت مشترک** — نه QA تنها.
- **QA را به مهندس کیفیت تبدیل کن**، نه حذف.
- **Definition of Done تا production.**
- **Shift left** با تست خودکار.
- **تست اکتشافی را حفظ کن.**
- **معیار کیفیت را چندبعدی کن.**

### خلاصه فصل

- کیفیت مسئولیت مشترک است، نه تیم QA.
- کیفیت سرمایه‌گذاری است، عدم کیفیت گران است.
- QA حذف نمی‌شود، نقشش عوض می‌شود.
- Shift left: زودتر، ارزان‌تر.
- تست خودکار + اکتشافی، هر دو لازم.
- Definition of Done تا production.

## فصل ۵۹: استراتژی تست

### مقدمه

بدون استراتژی، تیم یا تست نمی‌نویسد یا تست بی‌معنی می‌نویسد. این فصل چارچوب تصمیم می‌دهد: چه چیزی، کجا، چقدر تست شود.

### مفاهیم اساسی

**هرم تست — با اعداد واقعی:**

```
        ╱╲          E2E: 5-10 تست
       ╱  ╲         (سناریوهای حیاتی)
      ╱────╲
     ╱ Intg ╲       Integration: 50-100 تست
    ╱────────╲      (تعامل اجزا)
   ╱  Unit    ╲     Unit: 500-2000 تست
  ╱────────────╲    (منطق)
```

| سطح | سرعت | پایداری | هزینه نگهداری |
|---|---|---|---|
| Unit | میلی‌ثانیه | ✅✅ | ✅ کم |
| Integration | ثانیه | ✅ | متوسط |
| E2E | دقیقه | ❌ | ❌ زیاد |

**نکته**: هرم برعکس (بیشتر E2E) = تست کند و شکننده. تیم دور می‌زند.

**سه سؤال استراتژی:**

| سؤال | جواب |
|---|---|
| چه چیزی حیاتی است؟ | E2E برای آن |
| چه چیزی پیچیده است؟ | Unit برای منطق |
| چه چیزی یکپارچه است؟ | Integration برای مرزها |

**«تست چه چیزی را تضمین می‌کند؟» — سؤال کلیدی:**

```
❌ بد: "تست می‌کنیم که کد اجرا شود"
✅ خوب: "تست می‌کنیم که تخفیف ۱۰٪ روی ۱۰۰، ۹۰ بدهد"
```

### مثال‌های عملی

**تخصیص تست برای یک سرویس:**

| بخش | نوع تست | تعداد |
|---|---|---|
| محاسبه قیمت | Unit | ۵۰ |
| اعتبارسنجی ورودی | Unit | ۳۰ |
| API endpoint | Integration | ۲۰ |
| DB queries | Integration | ۱۵ |
| مسیر خرید کامل | E2E | ۳ |
| پرداخت | E2E + Mock | ۵ |

**نکته**: پرداخت هم E2E (مسیر کامل) هم Mock (سناریوهای خطا).

**تست خوب در برابر بد:**

```python
# ❌ بد: تست نامشخص، وابسته به پیاده‌سازی
def test_discount():
    result = apply_discount(100, 0.1)
    assert result == 90  # چرا ۹۰؟


# ✅ خوب: نامشخص‌کننده رفتار
def test_ten_percent_discount_reduces_total_by_ten_percent():
    """تخفیف ۱۰٪ باید ۱۰٪ از مبلغ کم کند."""
    assert apply_discount(Decimal("100"), Decimal("0.10")) == Decimal("90")


def test_discount_never_makes_total_negative():
    """تخفیف بیش از ۱۰۰٪ نباید مبلغ منفی بدهد."""
    assert apply_discount(Decimal("100"), Decimal("1.5")) == Decimal("0")
```

**قاعده**: نام تست باید **رفتار** را بگوید، نه **پیاده‌سازی**.

**الگوی AAA:**

```python
def test_expired_coupon_is_rejected():
    # Arrange — آماده‌سازی
    coupon = Coupon(code="OLD", expires_at=date(2020, 1, 1))

    # Act — اجرا
    result = validate_coupon(coupon, today=date(2026, 10, 17))

    # Assert — بررسی
    assert result.is_valid is False
    assert result.reason == "expired"
```

**سه بخش، قابل خواندن.**

### مقایسه و الگوهای مختلف

**سه مدل استراتژی:**

| مدل | تمرکز | مناسب |
|---|---|---|
| Pyramid | Unit زیاد | منطق پیچیده |
| Trophy | Integration زیاد | سیستم‌های توزیع‌شده |
| Honeycomb | Integration + contr. | میکروسرویس |

**BDD در برابر TDD:**

| معیار | BDD | TDD |
|---|---|---|
| زبان | Given/When/Then | assert |
| مخاطب | کسب‌وکار | توسعه‌دهنده |
| مناسب | قابلیت | منطق |

**سه سطح پوشش:**

| سطح | معنا | کافی؟ |
|---|---|---|
| Line coverage | خط اجرا شد | ❌ |
| Branch coverage | هر شاخه | ✅ بهتر |
| Mutation score | تست باگ را می‌گیرد | ✅✅ |

**نکته**: پوشش خط، کیفیت را نمی‌گوید. mutation score می‌گوید.

**Mutation Testing — چطور کار می‌کند:**

```
کد اصلی:  if x > 10: return "big"
تغییر:    if x >= 10: return "big"   ← mutation

اگر تست همچنان پاس شد → تست ضعیف است (این تغییر را نگرفت)
```

**Mutation score ۸۰٪ بهتر از line coverage ۹۵٪ است.**

### اشکال شایع

**اشکال ۱: هرم برعکس**

بیشتر E2E، کند و شکننده. هرم را رعایت کن.

**اشکال ۲: تست برای پوشش**

تست بدون assert، یا assert بی‌معنا. پوشش بالا، کیفیت صفر.

**اشکال ۳: تست وابسته به پیاده‌سازی**

refactor می‌کنی، ۱۰۰ تست می‌شکند. تست رفتار را بسنج، نه پیاده‌سازی.

**اشکال ۴: تست نامشخص**

`test_discount` — چه چیزی را تست می‌کند؟ نام باید رفتار را بگوید.

**اشکال ۵: تست بدون سناریوی خطا**

فقط مسیر خوش‌بینانه. خطاها بیشترین باگ را دارند.

**اشکال ۶: تست E2E برای همه‌چیز**

«E2E همه‌چیز را پوشش می‌دهد» — کند، شکننده، گران.

### نکات مهم (Tips & Tricks)

- **هرم را رعایت کن** — unit زیاد، E2E کم.
- **نام تست = رفتار.**
- **AAA برای خوانایی.**
- **سناریوی خطا را فراموش نکن.**
- **پوشش خط، کیفیت نیست.**
- **تست رفتار، نه پیاده‌سازی.**

### خلاصه فصل

- هرم: unit زیاد، integration متوسط، E2E کم.
- سه سؤال: حیاتی، پیچیده، یکپارچه.
- نام تست باید رفتار را بگوید.
- AAA برای ساختار.
- پوشش خط کیفیت نیست؛ mutation score بهتر.
- سناریوی خطا ضروری است.

## فصل ۶۰: تست خودکار در CI

### مقدمه

تست خودکار بدون CI، نیمه‌کاره است. و تست در CI بدون سرعت، استفاده نمی‌شود.

این فصل طراحی زنجیره تست در pipeline را می‌آورد.

### مفاهیم اساسی

**زنجیره تست — از سریع به کند:**

| مرحله | زمان | چه چیزی |
|---|---|---|
| Static | ۵ ثانیه | lint، format |
| Type | ۱۵ ثانیه | type check |
| Unit | ۱ دقیقه | منطق |
| Integration | ۵ دقیقه | تعامل |
| E2E | ۲۰ دقیقه | مسیر کامل |

**قاعده**: هر مرحله باید **مستقل fail شود** — نه اینکه ۲۰ دقیقه صبر کنی تا lint fail شود.

**سه سطح اجرا:**

| سطح | کجا | فرکانس |
|---|---|---|
| Local | pre-commit | هر commit |
| CI (MR) | pipeline | هر push |
| CI (full) | pipeline | شبانه |

**نکته**: تست‌های کند (E2E) در MR اجرا نکن — شبانه کافی است.

### مثال‌های عملی

**pipeline تست بهینه:**

```yaml
# مفهوم — قابل تطبیق با هر ابزار
stages: [validate, test, e2e]

lint:
  stage: validate
  script: [ruff check .]
  # ۱۰ ثانیه

typecheck:
  stage: validate
  script: [mypy app/]
  # ۲۰ ثانیه

unit:
  stage: test
  needs: []
  script: [pytest tests/unit -x --timeout=60]
  # ۱ دقیقه
  artifacts:
    reports:
      junit: report-unit.xml

integration:
  stage: test
  needs: [unit]
  script: [pytest tests/integration --timeout=300]
  # ۵ دقیقه

e2e:
  stage: e2e
  needs: [integration]
  script: [pytest tests/e2e --timeout=600]
  # ۲۰ دقیقه
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_PIPELINE_SOURCE == "schedule"
```

**نکته**: `-x` (توقف در اولین خطا) برای بازخورد سریع‌تر در توسعه. در CI می‌توانی حذف کنی تا همه خطاها را ببینی.

**تست موازی — تقسیم:**

```bash
# ۴ نسخه موازی
pytest --splits 4 --group $CI_NODE_INDEX
```

**اثر**: تست ۸ دقیقه‌ای، به ۲.۵ دقیقه می‌رسد.

**نکته**: تقسیم باید **متعادل** باشد. `pytest-split` بر اساس زمان قبلی تقسیم می‌کند.

**تست انتخابی (برای monorepo):**

```
تغییر در services/auth/ → فقط تست‌های auth اجرا شود
تغییر در libs/common/  → تست همه سرویس‌هایی که از آن استفاده می‌کنند
```

**اثر**: از ۲۰ دقیقه به ۳ دقیقه.

**گزارش تست در MR:**

```
✅ ۵۴۲ تست پاس
❌ ۳ تست شکست:
   tests/test_pricing.py::test_discount_negative
   tests/test_pricing.py::test_rounding
   tests/test_api.py::test_expired_coupon
⏱️ ۱ دقیقه ۲۳ ثانیه
📊 پوشش: ۸۷٪ (+۰.۳٪)
```

**این گزارش، بازخورد قابل اقدام است.**

### مقایسه و الگوهای مختلف

**سه استراتژی اجرا:**

| استراتژی | زمان | پوشش |
|---|---|---|
| Smoke | ۲ دقیقه | حداقلی |
| Full | ۲۰ دقیقه | کامل |
| Selective | ۵ دقیقه | تغییر‌یافته |

**توصیه**: smoke در MR، full شبانه، selective برای monorepo.

**تست در برابر build:**

| ترتیب | مزیت |
|---|---|
| تست قبل از build | ✅ بازخورد سریع |
| build قبل از تست | ❌ اتلاف منابع |

**نکته**: اگر build گران است، اول تست کن.

**سه سطح cache تست:**

| سطح | مناسب |
|---|---|
| Dependency cache | ✅ همیشه |
| Test result cache | ⚠️ محدود |
| Build cache | ✅ |

### اشکال شایع

**اشکال ۱: تست E2E در MR**

۲۰ دقیقه صبر برای هر push. توسعه‌دهنده دور می‌زند.

**اشکال ۲: تست سریالی**

unit و integration پشت هم. موازی کن.

**اشکال ۳: تست بدون timeout**

تست گیر می‌کند، pipeline ۱ ساعت. `--timeout` بگذار.

**اشکال ۴: تست وابسته به ترتیب**

«این تست بعد از آن تست کار می‌کند». ایزوله کن.

**اشکال ۵: تست وابسته به شبکه**

«سرور خارجی down بود». mock یا سرویس محلی.

**اشکال ۶: گزارش تست بدون جزئیات**

`exit code 1` — کدام تست؟ کدام خط؟

**اشکال ۷: تست با داده مشترک**

دو تست همزمان، داده را خراب می‌کنند. هر تست داده خودش.

### نکات مهم (Tips & Tricks)

- **سریع‌ترین اول.**
- **E2E فقط شبانه/main.**
- **موازی‌سازی با تقسیم.**
- **`--timeout` برای هر تست.**
- **تست ایزوله** — بدون وابستگی ترتیب.
- **گزارش junit** برای MR.
- **انتخابی برای monorepo.**

### خلاصه فصل

- زنجیره تست: static → type → unit → integration → E2E.
- هر مرحله مستقل fail شود.
- E2E در MR اجرا نکن.
- موازی‌سازی و تقسیم.
- timeout الزامی.
- گزارش قابل اقدام.

## فصل ۶۱: تست در production

### مقدمه

تست در production ترسناک به نظر می‌رسد، ولی در واقع **واقعی‌ترین تست** است. اگر درست انجام شود، ریسک را کم می‌کند، نه زیاد.

این فصل تکنیک‌های امن را می‌آورد.

### مفاهیم اساسی

**چرا در production تست می‌کنیم:**

| دلیل | توضیح |
|---|---|
| محیط واقعی | داده، مقیاس، شبکه واقعی |
| فقط اینجا | برخی باگ‌ها فقط در مقیاس ظاهر می‌شوند |
| بازخورد نهایی | کاربر واقعی |

**نکته**: این **جایگزین** تست در staging نیست؛ **مکمل** است.

**پنج تکنیک امن:**

| تکنیک | ریسک | توضیح |
|---|---|---|
| **Smoke test** | ✅ صفر | بررسی سلامت |
| **Synthetic monitoring** | ✅ صفر | تست مصنوعی دوره‌ای |
| **Canary** | ✅ کم | درصدی از ترافیک |
| **Shadow traffic** | ✅ صفر | کپی ترافیک، بدون تأثیر |
| **Chaos engineering** | ⚠️ کنترل‌شده | تزریق خرابی |

### مثال‌های عملی

**Smoke test — بعد از deploy:**

```bash
#!/usr/bin/env bash
# smoke.sh — بررسی سلامت بعد از deploy
set -euo pipefail

BASE="${1:?URL لازم است}"
FAIL=0

check() {
  local name="$1" path="$2" expect="${3:-200}"
  code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 10 "$BASE$path")
  if [ "$code" = "$expect" ]; then
    echo "✅ $name"
  else
    echo "❌ $name (HTTP $code، انتظار $expect)"
    FAIL=1
  fi
}

check "health"        "/healthz"
check "readiness"     "/ready"
check "homepage"      "/"
check "api list"      "/api/links"
check "404"           "/nonexistent" 404

exit $FAIL
```

**نکته**: smoke test باید **< ۶۰ ثانیه** باشد و **بدون تغییر داده**.

**Synthetic monitoring — تست دوره‌ای:**

```
هر ۵ دقیقه، از ۳ منطقه جغرافیایی:
  ۱. GET /healthz → انتظار 200
  ۲. POST /api/links → انتظار 201
  ۳. GET /{code} → انتظار 307

اگر fail → alert
```

**مزیت**: مشکل را قبل از کاربر کشف می‌کنی.

**Shadow traffic — بدون ریسک:**

```
ترافیک واقعی ──┬──► نسخه فعلی (پاسخ به کاربر)
               │
               └──► نسخه جدید (پاسخ دور ریخته می‌شود)

مقایسه: پاسخ‌ها یکسان است؟
  ✅ → نسخه جدید آماده
  ❌ → تفاوت را بررسی کن
```

**مزیت**: با ترافیک واقعی تست می‌کنی، بدون تأثیر.

**Chaos Engineering — اصول:**

```
۱. حالت عادی (baseline) را تعریف کن
۲. فرضیه بساز: "اگر یک Pod بمیرد، سرویس سالم می‌ماند"
۳. در محیط کنترل‌شده آزمایش کن
۴. اگر شکست، سیستم را تقویت کن
```

**شروع امن**:

| سطح | آزمایش |
|---|---|
| ۱ | خاموش کردن یک Pod در staging |
| ۲ | تأخیر شبکه در staging |
| ۳ | خرابی در production، ساعات کاری |

**نکته**: هرگز بدون observability کامل، chaos در production.

**Feature flag — تست با کاربران واقعی:**

```
۱. deploy با flag خاموش
۲. فعال برای تیم داخلی
۳. فعال برای ۱٪ کاربران
۴. بررسی متریک
۵. گسترش یا خاموش
```

### مقایسه و الگوهای مختلف

**سه سطح تست production:**

| سطح | ریسک | بازخورد |
|---|---|---|
| Smoke | ✅ صفر | سلامت |
| Synthetic | ✅ صفر | عملکرد |
| Canary | ✅ کم | واقعی |

**تست در برابر پایش:**

| معیار | تست | پایش |
|---|---|---|
| سؤال | «کار می‌کند؟» | «چطور کار می‌کند؟» |
| زمان | دوره‌ای | پیوسته |
| مناسب | deploy | عملیات |

**توصیه**: هر دو. smoke بعد از deploy، پایش پیوسته.

**Chaos در برابر Game Day:**

| معیار | Chaos | Game Day |
|---|---|---|
| خودکار | ✅ | ❌ |
| مشارکت | ❌ | ✅ تیم |
| مناسب | پیوسته | فصلی |

### اشکال شایع

**اشکال ۱: smoke test که داده می‌سازد**

هر deploy یک رکورد جدید. داده را آلوده می‌کند. از endpoint read-only استفاده کن.

**اشکال ۲: تست روی کاربر واقعی بدون flag**

کاربر باگ می‌بیند. همیشه canary یا flag.

**اشکال ۳: chaos بدون observability**

نمی‌دانی چه شد. اول observability.

**اشکال ۴: chaos در production بدون تیم آماده**

تیم غافلگیر می‌شود. اطلاع‌رسانی و on-call.

**اشکال ۵: synthetic monitoring با همان مسیر کاربر**

اگر مسیر عوض شد، monitoring می‌شکند. مسیر پایدار انتخاب کن.

**اشکال ۶: نادیده گرفتن smoke failure**

«همیشه fail می‌دهد، مهم نیست» — پس چرا داری؟

### نکات مهم (Tips & Tricks)

- **Smoke test < ۶۰ ثانیه، read-only.**
- **Synthetic monitoring از چند منطقه.**
- **Canary قبل از ۱۰۰٪.**
- **Chaos فقط با observability کامل.**
- **Feature flag برای تست با کاربر.**
- **smoke failure را جدی بگیر.**

### خلاصه فصل

- production واقعی‌ترین تست است.
- پنج تکنیک: smoke، synthetic، canary، shadow، chaos.
- smoke < ۶۰ ثانیه، بدون تغییر داده.
- canary قبل از ۱۰۰٪.
- chaos فقط با observability.
- feature flag برای تست تدریجی.

## فصل ۶۲: تست‌های شکننده و بدهی تست

### مقدمه

**تست شکننده (Flaky)** بدتر از نبود تست است: اعتماد را نابود می‌کند. اگر تست گاهی fail شود، تیم یاد می‌گیرد همه را ignore کند.

این فصل تشخیص و درمان را می‌آورد.

### مفاهیم اساسی

**تعریف:**

> تست شکننده: تستی که با همان کد، گاهی پاس و گاهی fail می‌شود.

**چرا بد است:**

| اثر | توضیح |
|---|---|
| بی‌اعتمادی | «دوباره اجرا کن» |
| پنهان‌کاری | باگ واقعی نادیده گرفته می‌شود |
| کندی | retry، انتظار |
| فرسودگی | تیم عصبانی |

**نرخ قابل قبول:**

```
Flaky rate < ۲٪
اگر بیشتر → مشکل جدی
```

**پنج علت رایج:**

| علت | مثال | راه‌حل |
|---|---|---|
| **زمان** | `sleep(1)` کافی نیست | wait صریح |
| **ترتیب** | تست B به A وابسته | ایزوله |
| **داده مشترک** | دو تست یک رکورد | داده جدا |
| **شبکه** | سرور خارجی کند | mock |
| **همزمانی** | race condition | قفل، wait |

### مثال‌های عملی

**مشکل ۱: وابستگی به زمان**

```python
# ❌ شکننده
def test_token_expires():
    token = create_token(ttl_seconds=1)
    time.sleep(1.5)              # ممکن است کافی نباشد
    assert not token.is_valid()


# ✅ پایدار
def test_token_expires():
    now = datetime(2026, 1, 1, 12, 0, 0)
    token = create_token(ttl_seconds=60, created_at=now)

    assert token.is_valid(at=now + timedelta(seconds=30))
    assert not token.is_valid(at=now + timedelta(seconds=61))
```

**نکته**: زمان را **تزریق** کن، نه اینکه منتظر بمانی.

**مشکل ۲: وابستگی به ترتیب**

```python
# ❌ شکننده — تست ۲ به تست ۱ وابسته
def test_1_create_user():
    create_user("alice")

def test_2_get_user():
    assert get_user("alice") is not None   # اگر ۱ اجرا نشود، fail


# ✅ پایدار — هر تست مستقل
@pytest.fixture
def alice():
    user = create_user("alice")
    yield user
    delete_user(user)

def test_get_user(alice):
    assert get_user("alice") is not None
```

**مشکل ۳: همزمانی**

```python
# ❌ شکننده
def test_counter_concurrent():
    counter = Counter()
    threads = [Thread(target=lambda: counter.increment()) for _ in range(10)]
    for t in threads: t.start()
    for t in threads: t.join()
    assert counter.value == 10     # ممکن است race بدهد


# ✅ پایدار — با قفل یا تست ترتیبی
def test_counter_sequential():
    counter = Counter()
    for _ in range(10):
        counter.increment()
    assert counter.value == 10
```

**نکته**: اگر race را تست می‌کنی، تست را تکرار کن (۱۰۰ بار) تا مطمئن شوی.

**مشکل ۴: انتظار برای شرط**

```python
# ❌ شکننده
def test_async_job():
    start_job()
    time.sleep(5)                  # ممکن است کافی نباشد
    assert job_status() == "done"


# ✅ پایدار — polling با timeout
def test_async_job():
    start_job()
    deadline = time.monotonic() + 30

    while time.monotonic() < deadline:
        if job_status() == "done":
            return
        time.sleep(0.5)

    pytest.fail("job در ۳۰ ثانیه تمام نشد")
```

**الگوی polling، پایدارترین راه برای async است.**

**درمان شکنندگی — پنج گام:**

```
۱. تشخیص: تست را ۱۰۰ بار اجرا کن
۲. قرنطینه: از pipeline اصلی خارج کن
۳. ثبت issue با جزئیات
۴. رفع در بازه مشخص (۱ هفته)
۵. بازگرداندن
```

**نکته**: `retry` راه‌حل نیست — مسکّن است. باگ پنهان می‌شود.

### مقایسه و الگوهای مختلف

**سه رویکرد به تست شکننده:**

| رویکرد | نتیجه |
|---|---|
| retry | ❌ پنهان‌کاری |
| حذف | ❌ پوشش از دست |
| ✅ قرنطینه + رفع | ✅ |

**سه سطح بدهی تست:**

| سطح | نشانه |
|---|---|
| سبک | ۱-۲ تست شکننده |
| متوسط | ۵-۱۰٪ |
| سنگین | > ۲۰٪، تیم ignore می‌کند |

**تست در برابر کد:**

| معیار | کد | تست |
|---|---|---|
| مالکیت | تیم | تیم |
| بازبینی | ✅ | ⚠️ اغلب نه |
| نگهداری | ✅ | ❌ |

**نکته**: تست هم کد است. باید بازبینی و نگهداری شود.

### اشکال شایع

**اشکال ۱: retry به‌عنوان راه‌حل**

«۳ بار retry می‌کنیم» — باگ واقعی پنهان می‌شود.

**اشکال ۲: حذف تست شکننده**

پوشش از دست می‌رود. قرنطینه کن، رفع کن.

**اشکال ۳: تست با sleep ثابت**

`time.sleep(5)` — گاهی کافی، گاهی نه. polling.

**اشکال ۴: تست وابسته به ترتیب**

`pytest-randomly` استفاده کن تا مشکل را پیدا کنی.

**اشکال ۵: تست با داده production**

داده عوض می‌شود، تست می‌شکند. داده ساختگی.

**اشکال ۶: تست بدون مالک**

هیچ‌کس مسئول نیست، شکننده می‌ماند.

**اشکال ۷: تست کند**

تست ۵ دقیقه‌ای، توسعه‌دهنده locally اجرا نمی‌کند.

### نکات مهم (Tips & Tricks)

- **Flaky < ۲٪** — هدف.
- **قرنطینه، نه حذف.**
- **`retry` مسکّن است، نه درمان.**
- **polling به‌جای sleep.**
- **زمان را تزریق کن.**
- **`pytest-randomly` برای پیدا کردن وابستگی ترتیب.**
- **تست هم کد است** — بازبینی و مالک.

### خلاصه فصل

- تست شکننده بدتر از نبود تست است.
- نرخ قابل قبول < ۲٪.
- پنج علت: زمان، ترتیب، داده، شبکه، همزمانی.
- polling به‌جای sleep.
- قرنطینه + رفع، نه retry یا حذف.
- تست هم کد است.
