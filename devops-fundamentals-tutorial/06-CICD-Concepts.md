## فصل ۳۰: یکپارچه‌سازی پیوسته — CI واقعاً چه حل می‌کند

### مقدمه

**CI (Continuous Integration)** را همه می‌شناسند و اکثراً اشتباه می‌فهمند. تصور رایج: «CI یعنی Jenkins/GitLab CI داریم». ولی CI یک **عمل سازمانی** است، نه یک سرور.

این فصل نشان می‌دهد CI چه دردی را درمان می‌کند.

### مفاهیم اساسی

**مشکل اصلی: «ادغام جهنمی» (Integration Hell)**

قبل از CI، تیم‌ها ماهی یک‌بار branchها را merge می‌کردند:

```
هفته ۱-۴: هر کس روی branch خودش کار می‌کند
هفته ۵: merge → ۴۰۰ تعارض، ۳ روز رفع، ۵۰ باگ جدید
هفته ۶: تلاش برای تست → محیط کار نمی‌کند
هفته ۷-۸: دیباگ
```

**چرا؟** چون هر branch جداگانه «کار می‌کرد»، ولی **ترکیبشان** تست نشده بود.

**CI سه چیز را تضمین می‌کند:**

| تضمین | معنا |
|---|---|
| **ادغام مکرر** | هر تغییر کوچک، سریع merge می‌شود |
| **تست خودکار** | هر merge، تست می‌شود |
| **بازخورد سریع** | نتیجه در دقیقه، نه روز |

**قاعده طلایی CI:**

```
هر کسی که کد را می‌شکند، همان لحظه می‌فهمد.
```

اگر بازخورد ۲ روز بعد بیاید، کسی که شکست، در ذهنش جای دیگری است.

**چهار عمل CI (نه ابزار):**

| عمل | توضیح |
|---|---|
| **Trunk-based** | همه به main merge می‌کنند، branch کوتاه |
| **خودکارسازی** | build و test خودکار |
| **سریع** | نتیجه در < ۱۰ دقیقه |
| **اجباری** | merge بدون سبز، ممکن نیست |

**نکته**: اگر یکی از این چهار نباشد، CI Theater داری.

### مثال‌های عملی

**مقایسه عددی — با و بدون CI:**

| معیار | بدون CI | با CI |
|---|---|---|
| فرکانس merge | ماهانه | روزانه |
| تعارض در هر merge | ۴۰+ | ۰-۲ |
| زمان رفع تعارض | ۳ روز | ۱۵ دقیقه |
| باگ کشف‌شده در merge | ۵۰ | ۲ |
| اعتماد به main | ❌ | ✅ |

**چرخه CI در عمل:**

```
توسعه‌دهنده: git push
    ↓ (۱۰ ثانیه)
CI: کد را می‌گیرد
    ↓ (۳۰ ثانیه)
CI: lint + type check
    ↓ (۲ دقیقه)
CI: تست واحد
    ↓ (۵ دقیقه)
CI: تست integration
    ↓
نتیجه: ✅ سبز / ❌ قرمز با جزئیات
```

**کل: ۸ دقیقه.** توسعه‌دهنده همان‌جا نتیجه را می‌بیند.

**«main همیشه سبز» — چطور اجرا می‌شود:**

```
قاعده:
  ۱. هیچ‌کس مستقیم به main push نمی‌کند
  ۲. merge فقط با pipeline سبز
  ۳. اگر main قرمز شد، بالاترین اولویت تیم است
  ۴. کسی روی main قرمز کار جدید شروع نمی‌کند
  ۵. رفع در < ۳۰ دقیقه یا rollback
```

**چرا مهم است**: اگر main قرمز باشد، همه بازخوردها بی‌معنا می‌شوند. نمی‌دانی شکست جدید است یا قدیمی.

### مقایسه و الگوهای مختلف

**CI در برابر CI Tool:**

| معیار | CI (عمل) | CI Tool |
|---|---|---|
| چیست | روش کار | ابزار |
| لازم | ✅ | ✅ |
| کافی | ❌ (ابزار هم لازم) | ❌ (عمل هم لازم) |

**سه سطح CI:**

| سطح | ویژگی |
|---|---|
| ۱ | build خودکار |
| ۲ | + تست خودکار |
| ۳ | + ادغام مکرر و اجباری |

**Trunk-Based در برابر Feature Branch:**

| معیار | Trunk-Based | Feature Branch |
|---|---|---|
| عمر branch | < ۱ روز | ۱-۳ روز |
| ادغام | ✅ مکرر | متوسط |
| نیاز به flag | ✅ | ❌ |
| CI لازم | ✅✅ سریع | متوسط |

### اشکال شایع

**اشکال ۱: CI داریم ولی ماهی یک‌بار merge می‌کنیم**

ابزار CI، عمل CI نیست. ادغام مکرر لازم است.

**اشکال ۲: pipeline قرمز و کسی اهمیت نمی‌دهد**

اگر main قرمز بماند، CI بی‌فایده است. فرهنگ «main سبز» لازم.

**اشکال ۳: pipeline ۴۰ دقیقه**

توسعه‌دهنده منتظر نمی‌ماند، کار دیگری می‌کند، context را از دست می‌دهد. هدف: < ۱۰ دقیقه.

**اشکال ۴: تست flaky**

«دوباره اجرا کن، درست می‌شود» — اعتماد از بین می‌رود. قرنطینه کن.

**اشکال ۵: merge بدون سبز**

«این بار استثناست» — یک بار، همیشه می‌شود.

**اشکال ۶: CI فقط روی main**

باید روی هر MR اجرا شود، قبل از merge.

### نکات مهم (Tips & Tricks)

- **main سبز، اولویت شماره یک.**
- **pipeline زیر ۱۰ دقیقه** — وگرنه استفاده نمی‌شود.
- **تست flaky را قرنطینه کن.**
- **merge بدون سبز ممنوع** — بدون استثنا.
- **هر push، بازخورد در دقیقه.**
- **branch کوتاه** — با feature flag.

### خلاصه فصل

- CI عمل سازمانی است، نه ابزار.
- مشکل اصلی: ادغام جهنمی.
- سه تضمین: ادغام مکرر، تست خودکار، بازخورد سریع.
- چهار عمل: trunk-based، خودکارسازی، سریع، اجباری.
- main سبز، اولویت اول.
- ابزار بدون عمل = CI Theater.

## فصل ۳۱: تحویل در برابر استقرار پیوسته

### مقدمه

دو حرف CD دو معنا دارد و این اشتباه، منبع سردرگمی زیادی است:

| مخفف | معنا |
|---|---|
| **CD** | Continuous **Delivery** |
| **CD** | Continuous **Deployment** |

تفاوتشان یک تصمیم است: **آیا انسان دکمه را می‌زند یا نه؟**

### مفاهیم اساسی

**تفاوت دقیق:**

| معیار | Continuous Delivery | Continuous Deployment |
|---|---|---|
| آماده انتشار | ✅ همیشه | ✅ همیشه |
| انتشار | تأیید انسانی | خودکار |
| فرکانس | روزانه-هفتگی | چند بار در روز |
| ریسک | کم | ✅ کم (اگر درست) |
| نیاز به تست | ✅ قوی | ✅✅ خیلی قوی |

**تعریف دقیق:**

- **Delivery**: هر تغییر سبز، **قابل انتشار** است. یک دکمه، و منتشر می‌شود. تصمیم انسانی.
- **Deployment**: هر تغییر سبز، **منتشر می‌شود**. بدون دخالت.

**نکته مهم**: Delivery پیش‌نیاز Deployment است. نمی‌توانی بدون Delivery، Deployment داشته باشی.

**چرا Delivery برای اکثر سازمان‌ها بهتر است:**

| دلیل | توضیح |
|---|---|
| انطباق | بعضی صنایع تأیید انسانی لازم دارند |
| کنترل | تیم می‌خواهد زمان‌بندی داشته باشد |
| ریسک | اگر تست کامل نیست، تأیید کمک می‌کند |
| بازاریابی | انتشار هماهنگ با کمپین |

### مثال‌های عملی

**Continuous Delivery — جریان:**

```
commit → CI → build → staging → smoke test
                                    ↓
                            ✅ آماده انتشار
                                    ↓
                          [دکمه: Deploy to production]
                                    ↓
                              deploy → verify
```

**Continuous Deployment — جریان:**

```
commit → CI → build → staging → smoke test
                                    ↓
                              deploy (خودکار)
                                    ↓
                              verify → alert
```

**پیش‌نیازهای Deployment (سخت‌گیرانه):**

| پیش‌نیاز | چرا |
|---|---|
| تست خودکار قوی | بدون انسان، تست تنها محافظ است |
| Observability کامل | باید سریع بفهمی خراب شد |
| rollback خودکار | برگشت باید بی‌درد باشد |
| Canary | ریسک محدود |
| Feature flag | رفتار قابل خاموش کردن |
| فرهنگ بدون سرزنش | وگرنه کسی ریسک نمی‌کند |

**نکته**: بدون این شش، Deployment خودکار = فاجعه خودکار.

**مسیر تکامل:**

```
مرحله ۱: deploy دستی، نادر
    ↓
مرحله ۲: deploy خودکار به staging
    ↓
مرحله ۳: deploy با تأیید به production (Delivery)
    ↓
مرحله ۴: deploy خودکار با canary (Deployment)
```

**هیچ مرحله‌ای را نمی‌توان پرش کرد.**

### مقایسه و الگوهای مختلف

**Delivery در برابر Deployment — جدول تصمیم:**

| اگر… | پس… |
|---|---|
| صنعت regulated | Delivery |
| تیم تازه‌کار | Delivery |
| تست قوی + observability | Deployment |
| محصول با کمپین هماهنگ | Delivery |
| SaaS داخلی | Deployment |

**سه مدل تأیید:**

| مدل | توضیح | مناسب |
|---|---|---|
| تأیید دستی کامل | کلیک | شروع |
| تأیید زمان‌بندی | پنجره مشخص | سازمان با انطباق |
| بدون تأیید | خودکار | ✅ بالغ |

**Deployment خودکار در برابر «deploy همه‌چیز با هم»:**

| معیار | خودکار کامل | دسته‌ای |
|---|---|---|
| ریسک | ✅ کم (کوچک) | ❌ بالا |
| بازخورد | ✅ سریع | ❌ کند |
| rollback | ✅ آسان | ❌ سخت |

### اشکال شایع

**اشکال ۱: Deployment بدون Delivery**

«همه‌چیز خودکار است» ولی نمی‌توانی هر لحظه deploy کنی (چون تست ضعیف است). این Deployment نیست، هرج‌ومرج است.

**اشکال ۲: Delivery بدون آمادگی**

«دکمه را زدیم، ۲ ساعت downtime». Delivery یعنی **آماده**، نه **قابل تلاش**.

**اشکال ۳: تأیید به‌عنوان جایگزین تست**

«ما تأیید داریم، پس تست لازم نیست» — تأیید انسانی، ۱۰۰٪ خطا را نمی‌گیرد.

**اشکال ۴: پرش از staging**

«staging شبیه production نیست، مستقیم به production می‌رویم» — اگر staging شبیه نیست، درستش کن.

**اشکال ۵: Deployment بدون canary**

همه‌چیز یک‌باره. یک باگ = ۱۰۰٪ کاربران.

### نکات مهم (Tips & Tricks)

- **Delivery پیش‌فرض اکثر سازمان‌ها** — Deployment بعد از بلوغ.
- **شش پیش‌نیاز Deployment** را چک کن قبل از فعال‌سازی.
- **تأیید انسانی را حذف نکن تا تست قوی شود.**
- **canary را قبل از Deployment کامل پیاده کن.**
- **rollback خودکار، شرط لازم است.**

### خلاصه فصل

- CD دو معنا: Delivery (تأیید انسانی) و Deployment (خودکار).
- Delivery پیش‌نیاز Deployment است.
- Deployment نیاز به تست قوی، observability، rollback، canary، flag، فرهنگ.
- مسیر تکامل چهار مرحله‌ای، بدون پرش.
- Delivery برای اکثر سازمان‌ها نقطه شروع درست است.

## فصل ۳۲: Pipeline به‌عنوان محصول

### mمقدمه

اکثر تیم‌ها pipeline را «چیزی که یک بار نوشتیم» می‌بینند. تیم‌های بالغ آن را **محصول** می‌بینند: مشتری دارد (توسعه‌دهنده)، کیفیت دارد، نگهداری می‌خواهد، و باید ساده باشد.

این تغییر نگاه، کیفیت pipeline را متحول می‌کند.

### مفاهیم اساسی

**pipeline به‌عنوان محصول — چهار ویژگی:**

| ویژگی | معنا |
|---|---|
| **مشتری** | توسعه‌دهنده |
| **SLA** | سرعت و قابلیت اعتماد |
| **نگهداری** | مالک، بازبینی، بهبود |
| **تجربه** | پیام خطا، سرعت، شفافیت |

**چهار متریک کیفیت pipeline:**

| متریک | هدف |
|---|---|
| **زمان اجرا** | < ۱۰ دقیقه (MR) |
| **نرخ شکست کاذب** (flaky) | < ۲٪ |
| **زمان تا بازخورد** | < ۱ دقیقه برای اولین خطا |
| **نرخ استفاده** | > ۹۵٪ (کسی دور نمی‌زند) |

**نکته**: اگر توسعه‌دهنده‌ها pipeline را دور می‌زنند (`--no-verify`، merge بدون سبز)، pipeline محصول بدی است.

**سه اصل طراحی:**

| اصل | معنا |
|---|---|
| **سریع‌ترین بازخورد اول** | lint قبل از تست |
| **شکست زودهنگام** | ارزان‌ترین چک اول |
| **پیام واضح** | بگو چه کار کند |

### مثال‌های عملی

**ترتیب بهینه مراحل — بر اساس زمان و ارزش:**

```
❌ ترتیب بد:
  ۱. تست E2E (۲۰ دقیقه)
  ۲. تست واحد (۲ دقیقه)
  ۳. lint (۱۰ ثانیه)

✅ ترتیب خوب:
  ۱. lint (۱۰ ثانیه)          ← سریع‌ترین، ارزان‌ترین
  ۲. type check (۳۰ ثانیه)
  ۳. تست واحد (۲ دقیقه)
  ۴. build (۳ دقیقه)
  ۵. تست integration (۵ دقیقه)
  ۶. تست E2E (۲۰ دقیقه، فقط main)
```

**چرا**: اگر lint شکست بخورد، ۱۰ ثانیه بعد می‌فهمی — نه ۲۰ دقیقه بعد.

**پیام خطای خوب در برابر بد:**

```
❌ بد:
  Job failed: exit code 1

✅ خوب:
  ❌ تست شکست خورد: tests/test_pricing.py::test_discount
     انتظار: 90
     دریافت: 95
     فایل: app/pricing.py:42
     راهنما: تخفیف باید قبل از مالیات اعمال شود
```

**قاعده**: پیام خطا باید بگوید **چه**، **کجا**، **چرا**.

**مالکیت pipeline:**

```
مالک: تیم (نه یک نفر)
بازبینی: هر ۳ ماه
تغییر: با MR و review (مثل کد)
مستندات: README در مخزن
```

**نکته**: pipeline که کسی جرأت تغییرش را ندارد، محصول بدی است.

**بهبود تدریجی — سه سؤال هر سه ماه:**

```
۱. کدام مرحله بیشترین زمان را می‌گیرد؟  → بهینه کن
۲. کدام مرحله بیشترین شکست کاذب دارد؟  → رفع یا حذف
۳. کدام مرحله کسی نمی‌فهمد چرا هست؟    → حذف یا مستند
```

### مقایسه و الگوهای مختلف

**pipeline به‌عنوان زیرساخت در برابر محصول:**

| معیار | زیرساخت | محصول |
|---|---|---|
| مالک | تیم پلتفرم | تیم توسعه |
| تغییر | نادر | مکرر |
| تجربه | ❌ نادیده | ✅ اولویت |
| مناسب | ❌ | ✅ |

**سه سطح بلوغ pipeline:**

| سطح | ویژگی |
|---|---|
| ۱ | کار می‌کند (گاهی) |
| ۲ | سریع و قابل اعتماد |
| ۳ | ✅ تجربه خوب، خودخدمت |

**Monolithic در برابر Modular:**

| معیار | یک فایل | include/component |
|---|---|---|
| سادگی شروع | ✅ | متوسط |
| مقیاس | ❌ | ✅ |
| آستانه | ~۳۰۰ خط | بعد از آن |

### اشکال شایع

**اشکال ۱: pipeline ۴۵ دقیقه و کسی شکایت نمی‌کند**

توسعه‌دهنده کار دیگری می‌کند، context از دست می‌رود. باید شکایت کند.

**اشکال ۲: پیام خطای مبهم**

`exit code 1` بدون جزئیات. توسعه‌دهنده باید دیباگ کند.

**اشکال ۳: pipeline بدون مالک**

هر کس تغییرش می‌دهد، هیچ‌کس نگه‌داری نمی‌کند.

**اشکال ۴: مراحل بی‌فایده**

«این مرحله را ۳ سال پیش اضافه کردیم، نمی‌دانیم چرا». حذف کن.

**اشکال ۵: تست E2E اول**

۲۰ دقیقه صبر، بعد lint شکست می‌خورد.

**اشکال ۶: pipeline فقط برای «کارشناسان»**

توسعه‌دهنده جدید نمی‌تواند مرحله اضافه کند. مستند و ساده کن.

### نکات مهم (Tips & Tricks)

- **pipeline را محصول ببین** — مشتری، SLA، نگهداری.
- **سریع‌ترین چک اول.**
- **پیام خطا: چه، کجا، چرا.**
- **هر سه ماه بازبینی کن** — مرحله بی‌فایده را حذف.
- **pipeline را با MR تغییر بده** — مثل کد.
- **زمان اجرا را اندازه بگیر و هدف بگذار.**

### خلاصه فصل

- pipeline محصول است: مشتری، SLA، نگهداری، تجربه.
- چهار متریک: زمان، flaky، بازخورد، استفاده.
- سریع‌ترین و ارزان‌ترین چک اول.
- پیام خطا باید قابل اقدام باشد.
- هر سه ماه بازبینی و حذف مراحل بی‌فایده.

## فصل ۳۳: دروازه‌های کیفیت

### مقدمه

**دروازه کیفیت (Quality Gate)** نقطه‌ای است که pipeline می‌گوید «اینجا نمی‌گذرم». بدون دروازه، pipeline فقط **گزارش** می‌دهد؛ با دروازه، **اجرا** می‌کند.

این فصل تفاوت دروازه مؤثر و دروازه نمایشی را نشان می‌دهد.

### مفاهیم اساسی

**سه نوع دروازه:**

| نوع | چه چیزی را می‌گیرد |
|---|---|
| **Blocking** | merge را متوقف می‌کند |
| **Warning** | هشدار می‌دهد، ولی می‌گذرد |
| **Informational** | فقط گزارش |

**قاعده طلایی:**

```
هر دروازه‌ای که می‌توان دور زد، دور زده می‌شود.
```

اگر merge با pipeline قرمز ممکن باشد، دیر یا زود کسی این کار را می‌کند.

**پنج دروازه رایج:**

| دروازه | چه چیزی | شدت |
|---|---|---|
| **تست** | تست شکست خورده | ✅ Blocking |
| **پوشش** | کاهش پوشش | Warning |
| **امنیت** | آسیب‌پذیری Critical | ✅ Blocking |
| **کارایی** | کاهش performance | Warning |
| **بازبینی** | تأیید انسانی | ✅ Blocking |

**نکته**: دروازه زیاد = pipeline کند و تیم ناراضی. حداکثر ۳-۴ دروازه Blocking.

### مثال‌های عملی

**درخت تصمیم برای دروازه:**

```
آیا این مشکل می‌تواند به production برسد و آسیب بزند؟
├── بله، جدی → Blocking
├── بله، کم → Warning
└── نه → Informational (یا حذف)
```

**مثال — پوشش تست:**

| وضعیت | اقدام |
|---|---|
| پوشش از ۸۰٪ به ۷۹٪ | Warning |
| پوشش از ۸۰٪ به ۵۰٪ | ✅ Blocking |
| پوشش جدید صفر | ✅ Blocking |

**قاعده**: دروازه روی **روند** باشد، نه **عدد مطلق**. تیم با ۵۰٪ پوشش هم می‌تواند جلو برود، ولی نه با کاهش.

**Baseline — چطور دروازه را در پروژه موجود پیاده کنیم:**

```
مشکل: ۲۰۰۰ یافته امنیتی قدیمی، دروازه همه MRها را بلاک می‌کند

راه‌حل:
  ۱. یافته‌های فعلی را baseline کن (allowlist با تاریخ)
  ۲. دروازه فقط روی یافته‌های جدید اعمال شود
  ۳. هر ماه baseline را کوچک‌تر کن
  ۴. هدف: baseline صفر در ۶ ماه
```

**بدون baseline**: تیم دور می‌زند. **با baseline**: تیم بهبود می‌دهد.

**دروازه انسانی — approval:**

| تعداد تأیید | مناسب |
|---|---|
| ۰ | ❌ هرگز |
| ۱ | ✅ اکثر |
| ۲ | کد حساس |
| ۳+ | ❌ گلوگاه |

**نکته**: تأیید زیاد، MR را هفته‌ها باز نگه می‌دارد. کیفیت از تست می‌آید، نه از تعداد تأیید.

### مقایسه و الگوهای مختلف

**دروازه سخت در برابر نرم:**

| معیار | سخت | نرم |
|---|---|---|
| دور زدن | ❌ | ✅ |
| پذیرش | ❌ کند | ✅ سریع |
| کیفیت | ✅ | ⚠️ |

**توصیه**: سخت برای امنیت و تست، نرم برای سبک.

**سه سطح اجرای دروازه:**

| سطح | مکان |
|---|---|
| محلی | pre-commit hook |
| CI | pipeline |
| سرور | protected branch |

**نکته**: دروازه محلی، سریع‌ترین بازخورد را می‌دهد (ولی قابل دور زدن است). دروازه سرور، قابل اعتماد است.

**دروازه در برابر انگیزه:**

| رویکرد | نتیجه |
|---|---|
| فقط دروازه | تیم دور می‌زند |
| فقط انگیزه | ناسازگار |
| ✅ دروازه + توضیح چرا | پذیرش |

### اشکال شایع

**اشکال ۱: دروازه‌ای که دور زده می‌شود**

merge با قرمز ممکن است = دروازه نمایشی. `Pipelines must succeed` را روشن کن.

**اشکال ۲: دروازه بیش از حد سخت**

تیم fork می‌زند، pipeline را دور می‌زند، یا استعفا می‌دهد.

**اشکال ۳: دروازه بدون توضیح**

«چرا نمی‌توانم merge کنم؟» — تیم باید بداند چرا. پیام واضح.

**اشکال ۴: دروازه روی عدد مطلق**

«پوشش باید ۸۰٪ باشد» در پروژه‌ای با ۳۰٪ = تیم هرگز merge نمی‌کند. روند را بسنج.

**اشکال ۵: دروازه کند**

دروازه‌ای که ۲۰ دقیقه طول می‌کشد، عملاً مانع است.

**اشکال ۶: دروازه بدون baseline**

پروژه موجود با ۲۰۰۰ یافته، هرگز سبز نمی‌شود.

### نکات مهم (Tips & Tricks)

- **حداکثر ۳-۴ دروازه Blocking.**
- **روند را بسنج، نه عدد مطلق.**
- **Baseline برای پروژه موجود.**
- **پیام واضح** — بگو چرا و چه کار کند.
- **دروازه سریع** — وگرنه دور زده می‌شود.
- **توضیح بده چرا** — پذیرش لازم است.

### خلاصه فصل

- دروازه سه نوع: Blocking، Warning، Informational.
- هر دروازه‌ای که دور زده شود، دور زده می‌شود.
- حداکثر ۳-۴ دروازه Blocking.
- روند را بسنج، نه عدد.
- baseline برای پروژه موجود.
- دروازه + توضیح = پذیرش.

## فصل ۳۴: معماری Pipeline

### مقدمه

pipeline ساده شروع می‌شود و بزرگ می‌شود. بدون معماری، به یک فایل ۲۰۰۰ خطی تبدیل می‌شود که هیچ‌کس نمی‌فهمد.

این فصل الگوهای معماری pipeline را می‌آورد — مفهومی، نه ابزارمحور.

### مفاهیم اساسی

**چهار مرحله منطقی:**

| مرحله | هدف | زمان هدف |
|---|---|---|
| **Validate** | سریع‌ترین چک‌ها | < ۱ دقیقه |
| **Test** | اطمینان از صحت | < ۵ دقیقه |
| **Build** | ساخت artifact | < ۵ دقیقه |
| **Deploy** | رساندن | < ۱۰ دقیقه |

**سه الگوی معماری:**

| الگو | توضیح | مناسب |
|---|---|---|
| **Monolithic** | یک فایل، همه jobها | پروژه کوچک |
| **Staged** | مرحله‌ای، سریالی | پیش‌فرض |
| **DAG** | گراف وابستگی | ✅ پروژه بزرگ |

**تفاوت Staged و DAG:**

```
Staged:            DAG:
lint ─┐            lint ──┐
test ─┼─ build      test ──┼─ build ─┬─ deploy:staging
      │                    │         └─ deploy:prod
      └─ deploy          (موازی)      (وابستگی دقیق)
```

DAG می‌تواند ۳۰-۵۰٪ سریع‌تر باشد، چون منتظر مراحل بی‌ربط نمی‌ماند.

### مثال‌های عملی

**معماری pipeline برای یک سرویس:**

```
┌─────────────────────────────────────────────────────┐
│ Validate (موازی، ۳۰ ثانیه)                          │
│  ├─ lint                                            │
│  ├─ format check                                    │
│  └─ type check                                      │
└──────────────────┬──────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────┐
│ Test (موازی، ۳ دقیقه)                                │
│  ├─ unit tests                                      │
│  ├─ integration tests                               │
│  └─ security scan                                   │
└──────────────────┬──────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────┐
│ Build (۳ دقیقه)                                     │
│  └─ docker build + push                             │
└──────────────────┬──────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────┐
│ Deploy (فقط main/tag)                               │
│  ├─ staging (خودکار)                                │
│  └─ production (تأیید)                              │
└─────────────────────────────────────────────────────┘
```

**معماری برای Monorepo:**

```
Parent pipeline
├─ detect-changes (تعیین کدام سرویس عوض شد)
├─ trigger: auth-service   (فقط اگر auth عوض شد)
├─ trigger: billing        (فقط اگر billing عوض شد)
└─ trigger: gateway        (فقط اگر gateway عوض شد)
```

**مزیت**: هر سرویس pipeline خودش، مستقل. شکست یکی، بقیه را متوقف نمی‌کند.

**معماری برای کتابخانه (چند نسخه):**

```
matrix:
  ├─ python 3.10 + django 4.2
  ├─ python 3.11 + django 4.2
  ├─ python 3.12 + django 4.2
  ├─ python 3.10 + django 5.0
  ├─ python 3.11 + django 5.0
  └─ python 3.12 + django 5.0
```

**نکته**: matrix ۶ job موازی می‌سازد، ولی اگر Runner کم باشد، صف می‌شوند.

### مقایسه و الگوهای مختلف

**Staged در برابر DAG:**

| معیار | Staged | DAG |
|---|---|---|
| سادگی | ✅ | متوسط |
| سرعت | ❌ | ✅ |
| پیش‌بینی | ✅ | متوسط |
| مناسب | < ۱۰ job | ۱۰+ job |

**سه سطح تقسیم pipeline:**

| سطح | ابزار |
|---|---|
| job | `needs` |
| فایل | `include` |
| pipeline | parent-child |

**آستانه‌ها:**

| اندازه | اقدام |
|---|---|
| < ۳۰۰ خط | یک فایل |
| ۳۰۰-۱۰۰۰ | include |
| ۱۰۰۰+ | parent-child |

**Cache در برابر Artifact (یادآوری):**

| معیار | Cache | Artifact |
|---|---|---|
| هدف | سرعت | داده |
| تضمین | ❌ | ✅ |
| مناسب | dependency | build output |

### اشکال شایع

**اشکال ۱: pipeline سریالی**

همه‌چیز پشت هم. ۲۰ دقیقه به‌جای ۸ دقیقه.

**اشکال ۲: مرحله بی‌فایده**

«این مرحله را ۳ سال پیش اضافه کردیم». حذف کن.

**اشکال ۳: pipeline غول**

فایل ۲۰۰۰ خطی. هیچ‌کس نمی‌فهمد.

**اشکال ۴: build برای هر محیط**

«build جدا برای staging و production». یک‌بار build کن.

**اشکال ۵: deploy در pipeline MR**

MR باید تست کند، نه deploy به production.

**اشکال ۶: pipeline تکراری**

هر push، دو pipeline (branch + MR). `workflow` rules لازم.

### نکات مهم (Tips & Tricks)

- **سریع‌ترین چک اول.**
- **موازی‌سازی با `needs`.**
- **یک‌بار build، همه‌جا استفاده.**
- **آستانه ۳۰۰ خط** برای تقسیم فایل.
- **pipeline MR ≠ pipeline main.**
- **`workflow` rules** برای جلوگیری از تکراری.

### خلاصه فصل

- چهار مرحله: Validate، Test، Build، Deploy.
- سه الگو: Monolithic، Staged، DAG.
- DAG ۳۰-۵۰٪ سریع‌تر است.
- Monorepo با parent-child.
- آستانه ۳۰۰ خط برای تقسیم.
- یک‌بار build، همه‌جا استفاده.

## فصل ۳۵: ضدالگوها و سنجش CI/CD

### مقدمه

این فصل جمع‌بندی است: چه کاری نکن، و چطور بفهمی CI/CD واقعاً کار می‌کند.

### ضدالگوها

**هفت ضدالگوی CI/CD:**

| ضدالگو | نشانه | نتیجه | راه‌حل |
|---|---|---|---|
| **CI Theater** | ابزار داریم، ادغام مکرر نه | شکست بزرگ | trunk-based |
| **Pipeline قرمز مزمن** | «همیشه چند تا fail داریم» | بی‌اعتمادی | main سبز |
| **Retry همه‌چیز** | `retry: 3` سراسری | باگ پنهان | قرنطینه flaky |
| **Pipeline ۴۰ دقیقه** | کسی منتظر نمی‌ماند | دور زدن | موازی‌سازی |
| **Snowflake** | هر پروژه pipeline خودش | نگهداری جهنمی | component |
| **Deploy دستی «موقت»** | «فقط این بار» | همیشه | خودکارسازی |
| **Gate نمایشی** | merge با قرمز ممکن | بی‌فایده | `Pipelines must succeed` |

**نشانه‌های هشدار زودهنگام:**

```
[ ] کسی در ماه گذشته pipeline را دور زده
[ ] میانگین زمان pipeline > ۱۵ دقیقه
[ ] نرخ flaky > ۵٪
[ ] کسی نمی‌داند کدام مرحله چرا هست
[ ] pipeline فقط یک نفر می‌فهمد
[ ] deploy به production کمتر از هفتگی
```

اگر دو مورد یا بیشتر، مشکل جدی داری.

### سنجش CI/CD

**پنج متریک:**

| متریک | هدف | چطور اندازه بگیر |
|---|---|---|
| **Pipeline duration** | < ۱۰ دقیقه (MR) | داده CI |
| **Flaky rate** | < ۲٪ | نسبت شکست‌های تکرارشونده |
| **Feedback time** | < ۱ دقیقه (اولین خطا) | زمان تا اولین شکست |
| **Deploy frequency** | روزانه+ | تعداد deploy |
| **MTTR** | < ۱ ساعت | زمان رفع |

**محاسبه Flaky Rate:**

```
flaky = تست‌هایی که در ۱۰ اجرا، هم پاس و هم fail می‌شوند
نرخ = تعداد flaky / کل تست‌ها

مثال: ۳ تست از ۲۰۰ = ۱.۵٪ ✅
```

**محاسبه Feedback Time:**

```
زمان از push تا اولین خطای گزارش‌شده
هدف: < ۶۰ ثانیه (lint/type اول)

مثال: lint در ۱۰ ثانیه، تست در ۳ دقیقه
  → اگر lint شکست، بازخورد ۱۰ ثانیه ✅
```

### مثال‌های عملی

**گزارش ماهانه CI/CD:**

```
متریک                    ماه قبل   این ماه   هدف
─────────────────────────────────────────────────
Pipeline duration (p50)   12 دقیقه  8 دقیقه   < 10
Pipeline duration (p95)   25 دقیقه  15 دقیقه  < 20
Flaky rate                4.2٪      1.8٪      < 2٪
Deploy frequency          6/ماه     14/ماه    روزانه
MTTR                      4 ساعت    1.5 ساعت  < 1 ساعت
─────────────────────────────────────────────────
اقدام: موازی‌سازی تست integration
نتیجه: از ۱۲ به ۸ دقیقه
```

**پرسشنامه سلامت CI/CD:**

```
۱. آیا merge بدون pipeline سبز ممکن است؟        (بله = ❌)
۲. آیا main در ۳۰ روز گذشته قرمز بوده؟          (بیش از ۱ روز = ⚠️)
۳. آیا کسی در ۳ ماه گذشته pipeline را دور زده؟   (بله = ⚠️)
۴. آیا زمان pipeline < ۱۰ دقیقه است؟            (نه = ⚠️)
۵. آیا تست flaky دارید؟                          (بیش از ۲٪ = ⚠️)
۶. آیا pipeline مالک مشخص دارد؟                  (نه = ⚠️)
۷. آیا deploy به production حداقل هفتگی است؟     (نه = ⚠️)
```

### مقایسه و الگوهای مختلف

**سه سطح بلوغ CI/CD:**

| سطح | ویژگی | DORA |
|---|---|---|
| ۱ | CI داریم، deploy دستی | Low |
| ۲ | CI/CD خودکار، تست متوسط | Medium/High |
| ۳ | + canary، flag، observability | ✅ Elite |

**سنجش برای بهبود در برابر ارزیابی:**

| معیار | بهبود | ارزیابی |
|---|---|---|
| چه کسی می‌بیند | تیم | مدیریت |
| هدف | یادگیری | رتبه‌بندی |
| نتیجه | ✅ | ❌ دستکاری |

### اشکال شایع

**اشکال ۱: سنجش بدون اقدام**

داشبورد زیبا، هیچ تغییری. هر متریک باید اقدام داشته باشد.

**اشکال ۲: فقط زمان pipeline**

سریع ولی بی‌اعتماد، بی‌فایده است. flaky را هم بسنج.

**اشکال ۳: مقایسه با تیم دیگر**

context متفاوت. با خودت مقایسه کن.

**اشکال ۴: نادیده گرفتن دور زدن**

اگر تیم دور می‌زند، مشکل pipeline است نه تیم. بپرس چرا.

**اشکال ۵: هدف گذاشتن روی عدد بدون توان تغییر**

«pipeline باید ۵ دقیقه شود» بدون منابع. frustrate می‌کند.

### نکات مهم (Tips & Tricks)

- **پنج متریک را ماهانه ببین.**
- **Flaky rate را جدی بگیر** — اعتماد را نابود می‌کند.
- **دور زدن را نشانه طراحی بد بدان، نه بدی تیم.**
- **هر متریک، یک اقدام.**
- **با خودت مقایسه کن.**
- **پرسشنامه سلامت را هر سه ماه پر کن.**

### خلاصه فصل

- هفت ضدالگو؛ CI Theater و pipeline قرمز مزمن رایج‌ترین.
- پنج متریک: duration، flaky، feedback، deploy freq، MTTR.
- Flaky > ۲٪ = مشکل جدی.
- دور زدن pipeline = نشانه طراحی بد.
- سنجش برای بهبود، نه ارزیابی.
- هر متریک، یک اقدام.
