## فصل ۹۲: از کجا شروع کنیم

### مقدمه

بزرگ‌ترین سؤال در DevOps این نیست «چه ابزاری»، بلکه **«از کجا شروع کنم؟»**.

این فصل چارچوب انتخاب نقطه شروع را می‌دهد.

### مفاهیم اساسی

**سه اصل شروع:**

| اصل | معنا |
|---|---|
| **از درد شروع کن** | نه از ابزار |
| **کوچک شروع کن** | یک تیم، یک سرویس |
| **سریع نتیجه بده** | ۹۰ روز، نه ۹ ماه |

**نکته**: تحول‌هایی که از «ابزار» شروع می‌شوند، به «ابزار» ختم می‌شوند.

**چهار نقطه شروع ممکن:**

| نقطه | مناسب وقتی |
|---|---|
| **CI/CD** | deploy دستی و کند است |
| **Observability** | نمی‌دانید production چه شکلی است |
| **Platform** | ۵+ تیم، هر کدام ابزار خودش |
| **Team structure** | هماهنگی بین تیم‌ها فلج‌کننده است |

**نکته**: معمولاً **CI/CD** بهترین شروع است — سریع‌ترین نتیجه، کم‌ترین مقاومت.

**درخت تصمیم:**

```
بزرگ‌ترین درد شما چیست؟
├── "deploy هفته‌ها طول می‌کشد"        → CI/CD
├── "نمی‌دانیم production چه شکلی است"  → Observability
├── "هر تیم ابزار خودش را دارد"         → Platform
├── "هماهنگی بین تیم‌ها فلج‌کننده است"  → Team structure
└── "همه‌چیز"                          → CI/CD (سریع‌ترین برد)
```

### مثال‌های عملی

**انتخاب نقطه شروع — سه سناریو:**

**سناریو ۱: استارتاپ ۲۰ نفره**

```
وضعیت: deploy دستی، هفتگی، با stress
درد: سرعت
انتخاب: CI/CD
اولین قدم: pipeline برای یک سرویس (۲ هفته)
نتیجه ۹۰ روز: deploy روزانه، Lead Time از ۵ روز به ۱
```

**سناریو ۲: سازمان ۲۰۰ نفره**

```
وضعیت: ۱۵ تیم، ۱۵ روش متفاوت
درد: ناسازگاری
انتخاب: Platform + Team structure
اولین قدم: یک مسیر طلایی برای Python API
نتیجه ۹۰ روز: ۳ تیم از قالب استفاده می‌کنند
```

**سناریو ۳: سازمان با حادثه مکرر**

```
وضعیت: ۵ حادثه در ماه، MTTR ۶ ساعت
درد: پایداری
انتخاب: Observability + SRE basics
اولین قدم: SLO + alert درست
نتیجه ۹۰ روز: MTTR ۲ ساعت، حادثه ۲ در ماه
```

**«اولین ۱۰٪» — چه چیزی را اول بساز:**

| اولویت | چه چیزی | زمان |
|---|---|---|
| ۱ | pipeline برای یک سرویس | ۲ هفته |
| ۲ | Lead Time اندازه‌گیری | ۱ روز |
| ۳ | main سبز (اجباری) | ۱ هفته |
| ۴ | deploy خودکار به staging | ۲ هفته |
| ۵ | observability پایه | ۲ هفته |

**نکته**: این پنج مورد، **پایه** هستند. بقیه بعد.

**تیم پایلوت — سه معیار انتخاب:**

| معیار | چرا |
|---|---|
| **درد واقعی** | انگیزه |
| **رهبر باز** | پذیرش |
| **سرویس متوسط** | نه خیلی حیاتی، نه بی‌اهمیت |

**نکته**: تیم پایلوت نباید **حیاتی‌ترین** سرویس باشد — ریسک.

### مقایسه و الگوهای مختلف

**سه استراتژی شروع:**

| استراتژی | مزیت | عیب |
|---|---|---|
| **Top-down** | بودجه، اختیار | ❌ مقاومت |
| **Bottom-up** | ✅ پذیرش | ❌ محدود |
| **Hybrid** | ✅✅ | نیاز به حمایت |

**توصیه**: Bottom-up با حمایت مدیریت.

**سه سطح دامنه:**

| سطح | زمان نتیجه |
|---|---|
| یک تیم | ۱-۳ ماه |
| یک دپارتمان | ۶-۱۲ ماه |
| کل سازمان | ۱۸-۳۶ ماه |

**نکته**: از یک تیم شروع کن. موفقیت، بقیه را جذب می‌کند.

**«پایلوت» در برابر «همه‌جا»:**

| معیار | پایلوت | همه‌جا |
|---|---|---|
| ریسک | ✅ کم | ❌ زیاد |
| یادگیری | ✅ زیاد | ❌ کم |
| سرعت | ✅ | ❌ |

### اشکال شایع

**اشکال ۱: از ابزار شروع کردیم**

«Kubernetes بیاوریم» — بدون درد مشخص. شکست.

**اشکال ۲: همه‌جا همزمان**

۲۰ تیم، ۲۰ پروژه. هیچ‌کدام تمام نمی‌شود.

**اشکال ۳: پایلوت روی حیاتی‌ترین سرویس**

ریسک بالا، مقاومت. سرویس متوسط.

**اشکال ۴: بدون متریک baseline**

«بهتر شد» — از کجا می‌دانی؟

**اشکال ۵: انتظار نتیجه در ۳۰ روز**

تغییر ۳-۶ ماه. صبر.

**اشکال ۶: بدون حمایت مدیریت**

تیم پایلوت موفق می‌شود، بقیه کپی نمی‌کنند. حمایت لازم.

### نکات مهم (Tips & Tricks)

- **از درد شروع کن**، نه ابزار.
- **CI/CD بهترین شروع** است.
- **یک تیم پایلوت** — نه همه.
- **baseline قبل از شروع.**
- **۹۰ روز برای اولین نتیجه.**
- **حمایت مدیریت** از روز اول.

### خلاصه فصل

- سه اصل: از درد، کوچک، سریع.
- چهار نقطه شروع؛ CI/CD معمولاً بهترین.
- پنج مورد «اولین ۱۰٪».
- تیم پایلوت: درد، رهبر باز، سرویس متوسط.
- از یک تیم شروع، موفقیت جذب می‌کند.
- baseline قبل از شروع.

## فصل ۹۳: مدل بلوغ DevOps

### mمقدمه

مدل بلوغ به تو می‌گوید **کجایی** و **قدم بعدی چیست**. بدون آن، یا از جای اشتباه شروع می‌کنی یا مرحله‌ای را می‌پری.

### مفاهیم اساسی

**پنج سطح بلوغ:**

| سطح | نام | ویژگی |
|---|---|---|
| **۰** | سنتی | deploy دستی، تیم‌های جدا |
| **۱** | تکرارپذیر | CI، deploy اسکریپتی |
| **۲** | تعریف‌شده | CI/CD استاندارد، متریک |
| **۳** | مدیریت‌شده | SLO، platform، self-service |
| **۴** | بهینه‌شده | بهبود مستمر، پیش‌بینی |

**نکته**: بیشتر سازمان‌ها در سطح ۱-۲ هستند. سطح ۴ نادر است.

**شاخص‌های هر سطح:**

**سطح ۰ — سنتی:**
```
[ ] deploy دستی
[ ] تیم Dev و Ops جدا
[ ] بدون تست خودکار
[ ] Lead Time > ۱ ماه
[ ] حادثه بدون postmortem
```

**سطح ۱ — تکرارپذیر:**
```
[ ] CI روی هر merge
[ ] تست خودکار (بخشی)
[ ] deploy با اسکریپت
[ ] Lead Time ۱-۴ هفته
[ ] main معمولاً سبز
```

**سطح ۲ — تعریف‌شده:**
```
[ ] CI/CD استاندارد برای همه
[ ] deploy خودکار به staging
[ ] متریک DORA اندازه‌گیری می‌شود
[ ] Lead Time < ۱ هفته
[ ] postmortem برای SEV1
```

**سطح ۳ — مدیریت‌شده:**
```
[ ] SLO تعریف‌شده
[ ] Error budget
[ ] Platform با golden path
[ ] Lead Time < ۱ روز
[ ] on-call مشترک
```

**سطح ۴ — بهینه‌شده:**
```
[ ] بهبود مستمر مبتنی بر داده
[ ] پیش‌بینی ظرفیت
[ ] self-service کامل
[ ] Lead Time < ۴ ساعت
[ ] CFR < ۱۰٪
```

### مثال‌های عملی

**ارزیابی سریع — ۱۰ سؤال:**

```
به هر سؤال ۰ (نه)، ۱ (تا حدی)، ۲ (بله) بده:

۱. هر merge، تست خودکار اجرا می‌شود؟        ___
۲. deploy بدون دخالت دستی ممکن است؟          ___
۳. Lead Time اندازه‌گیری می‌شود؟              ___
۴. main همیشه سبز است؟                       ___
۵. rollback در < ۱۵ دقیقه ممکن است؟          ___
۶. SLO تعریف شده دارید؟                      ___
۷. postmortem بدون سرزنش دارید؟              ___
۸. توسعه‌دهنده لاگ production می‌بیند؟        ___
۹. محیط با کد ساخته می‌شود؟                  ___
۱۰. تیم مالک کل چرخه است؟                    ___

امتیاز:
  ۰-۵   → سطح ۰-۱
  ۶-۱۰  → سطح ۱-۲
  ۱۱-۱۵ → سطح ۲-۳
  ۱۶-۲۰ → سطح ۳-۴
```

**نقشه راه بر اساس سطح:**

| سطح فعلی | قدم بعدی | زمان |

| ۰ | CI + تست خودکار | ۳ ماه |

**نکته**: **یک سطح در هر مرحله**. پرش، شکست.

## فصل ۹۴: ارزیابی وضعیت فعلی

### مقدمه

قبل از هر تغییری، باید بدانی **کجایی**. ارزیابی بدون داده، حدس است.

این فصل روش ارزیابی عملی را می‌آورد.

### مفاهیم اساسی

**چهار بُعد ارزیابی:**

| بُعد | چه می‌سنجد |
|---|---|
| **فنی** | CI/CD، تست، معماری |
| **فرآیندی** | جریان، متریک |
| **فرهنگی** | همکاری، مالکیت |
| **سازمانی** | ساختار، اختیار |

**نکته**: ارزیابی فقط فنی، تصویر ناقص می‌دهد. چهار بُعد لازم.

**سه روش جمع‌آوری:**

| روش | کیفیت | زمان |
|---|---|---|
| داده سیستم | ✅✅ | ✅ کم |
| مصاحبه | ✅✅ | ❌ زیاد |
| پرسشنامه | متوسط | ✅ کم |

**توصیه**: داده + مصاحبه با ۱۰ نفر.

### مثال‌های عملی

**ارزیابی فنی — داده‌های قابل استخراج:**

```
از GitLab/GitHub:
  - تعداد MR در ماه
  - median زمان merge
  - تعداد pipeline موفق/ناموفق
  - flaky rate

از deployment:
  - تعداد deploy در ماه
  - زمان deploy
  - rollbackها

از incident:
  - تعداد حادثه
  - MTTR
```

**محاسبه از داده موجود:**

```python
"""محاسبه Lead Time از داده موجود (مفهومی)."""
from datetime import datetime

import requests

API = "https://gitlab.com/api/v4"
TOKEN = "glpat-xxx"


def lead_times(project: str, limit: int = 50) -> list[float]:
    """Lead Time برای MRهای merge‌شده، به روز."""
    resp = requests.get(
        f"{API}/projects/{project}/merge_requests",
        headers={"PRIVATE-TOKEN": TOKEN},
        params={"state": "merged", "per_page": limit},
        timeout=30,
    )
    resp.raise_for_status()

    result = []
    for mr in resp.json():
        created = datetime.fromisoformat(mr["created_at"].replace("Z", "+00:00"))
        merged = datetime.fromisoformat(mr["merged_at"].replace("Z", "+00:00"))
        result.append((merged - created).total_seconds() / 86400)
    return result


def median(xs: list[float]) -> float:
    """میانه."""
    s = sorted(xs)
    n = len(s)
    return s[n // 2] if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2


if __name__ == "__main__":
    times = lead_times("12345")
    print(f"Lead Time median: {median(times):.1f} روز")
    print(f"بیشترین: {max(times):.1f} روز")
```

**ارزیابی فرهنگی — پرسشنامه ۱۰ سؤالی:**

```
۱ = کاملاً مخالف، ۵ = کاملاً موافق

۱. وقتی deploy شکست می‌خورد، درباره سیستم حرف می‌زنیم
۲. توسعه‌دهنده‌ها لاگ production را می‌بینند
۳. توسعه‌دهنده‌ها در on-call شریک‌اند
۴. اشتباه گزارش‌شده، تنبیه نمی‌شود
۵. postmortem می‌نویسیم و پیگیری می‌کنیم
۶. می‌توانم بگویم «نمی‌دانم» بدون ترس
۷. تصمیم‌ها مستند می‌شوند
۸. تیم‌ها اطلاعات را به اشتراک می‌گذارند
۹. آزمایش و شکست کوچک تشویق می‌شود
۱۰. از حادثه‌ها یاد می‌گیریم

امتیاز ۴۰-۵۰: قوی · ۲۵-۳۹: متوسط · < ۲۵: نیاز جدی
```

**مصاحبه — پنج سؤال کلیدی:**

```
۱. آخرین deploy چطور بود؟ چه چیزی سخت بود؟
۲. آخرین حادثه چطور بررسی شد؟
۳. اگر فردا یک نفر از تیم برود، چه می‌شود؟
۴. بزرگ‌ترین اتلاف وقت شما چیست؟
۵. اگر یک چیز را می‌توانستی عوض کنی، چه بود؟
```

**نکته**: سؤال ۵، بهترین نقطه شروع را می‌دهد.

## فصل ۹۵: نقشه راه ۹۰ روزه

### mمقدمه

نقشه ۹۰ روزه، اولین قدم عملی است: کوتاه‌تر از برنامه سالانه (قابل اجرا)، بلندتر از sprint (قابل نتیجه).

### مفاهیم اساسی

**ساختار سه ماهه:**

| ماه | تمرکز | خروجی |
|---|---|---|
| **۱** | پایه و اندازه‌گیری | baseline + CI |
| **۲** | اولین بهبود | deploy خودکار |
| **۳** | تثبیت و گسترش | نتیجه قابل نمایش |

**نکته**: هر ماه، **یک خروجی قابل نمایش**. نه «در حال انجام».

**قاعده «یک اقدام در ماه»:**

```
ماه ۱: CI + تست برای یک سرویس
ماه ۲: deploy خودکار به staging
ماه ۳: اندازه‌گیری + گزارش

اگر سه کار همزمان: نمی‌دانی کدام مؤثر بود
```

### مثال‌های عملی

**نقشه ۹۰ روزه — تیم پایلوت:**

**ماه ۱ — پایه:**

```
هفته ۱:
  [ ] تیم پایلوت انتخاب
  [ ] baseline: Lead Time، Deploy Freq، CFR
  [ ] ابزار بررسی

هفته ۲:
  [ ] pipeline اولیه (lint + test)
  [ ] main سبز (اجباری)

هفته ۳:
  [ ] تست پوشش به ۶۰٪
  [ ] cache و سرعت pipeline (< ۱۰ دقیقه)

هفته ۴:
  [ ] گزارش ماه ۱ به مدیریت
  [ ] retro تیم
```

**ماه ۲ — اولین بهبود:**

```
هفته ۵:
  [ ] build ایمیج در CI
  [ ] registry

هفته ۶:
  [ ] deploy خودکار به staging
  [ ] smoke test

هفته ۷:
  [ ] Lead Time جدید اندازه‌گیری
  [ ] گلوگاه بعدی

هفته ۸:
  [ ] گزارش ماه ۲
```

**ماه ۳ — تثبیت و گسترش:**

```
هفته ۹:
  [ ] deploy به production (با تأیید)
  [ ] rollback تست‌شده

هفته ۱۰:
  [ ] observability پایه (متریک + alert)
  [ ] runbook

هفته ۱۱:
  [ ] تیم دوم شروع می‌کند (کپی)
  [ ] مستندسازی

هفته ۱۲:
  [ ] گزارش نهایی: قبل/بعد
  [ ] نقشه ۹۰ روز بعد
```

**گزارش قبل/بعد — نمونه:**

```
متریک              قبل       بعد       تغییر
─────────────────────────────────────────────
Lead Time          24 روز    6 روز     −۷۵٪
Deploy Frequency   4/ماه     18/ماه    +۳۵۰٪
Pipeline duration  —         8 دقیقه   —
CFR                22٪       16٪       −۲۷٪
MTTR               6 ساعت    2 ساعت    −۶۷٪
─────────────────────────────────────────────
```

**این گزارش، بهترین استدلال برای گسترش است.**

**سه دام نقشه ۹۰ روزه:**

| دام | نتیجه |
|---|---|
| **خیلی بلندپروازانه** | هیچ‌کدام تمام نمی‌شود |
| **بدون متریک** | نمی‌دانی موفق شد |
| **بدون تیم دوم** | گسترش نمی‌یابد |

### مقایسه و الگوهای مختلف

**۹۰ روز در برابر ۳۰ روز در برابر ۱ سال:**

| بازه | مزیت | عیب |
|---|---|---|
| ۳۰ روز | ✅ سریع | ❌ سطحی |
| **۹۰ روز** | ✅✅ نتیجه واقعی | — |
| ۱ سال | ✅ جامع | ❌ دیر |

**سه مدل نقشه:**

| مدل | مناسب |
|---|---|
| خروجی‌محور | ✅ توصیه |
| فعالیت‌محور | ❌ |
| ابزارمحور | ❌ |

**نکته**: «deploy خودکار» (خروجی) بهتر از «یادگیری Terraform» (فعالیت).

**OKR در برابر نقشه:**

| معیار | OKR | نقشه |
|---|---|---|
| سطح | هدف | اقدام |
| بازه | فصلی | ۹۰ روز |

### اشکال شایع

**اشکال ۱: نقشه ۲۰ موردی**

هیچ‌کدام تمام نمی‌شود. حداکثر ۵ مورد.

**اشکال ۲: بدون baseline**

«بهتر شد» — از چه به چه؟

**اشکال ۳: فعالیت به‌جای خروجی**

«یادگیری Docker» — چه چیزی تحویل دادی؟

**اشکال ۴: بدون گزارش**

مدیریت نمی‌داند، حمایت نمی‌کند.

**اشکال ۵: بدون گسترش**

تیم پایلوت موفق، بقیه بی‌خبر. مستند و آموزش.

**اشکال ۶: نقشه بدون بازبینی**

هر ماه بازبینی و تنظیم.

### نکات مهم (Tips & Tricks)

- **baseline قبل از شروع.**
- **گزارش ماهانه.**
- **گسترش از ماه ۳.**
- **بازبینی ماهانه.**

### خلاصه فصل

- ۹۰ روز: پایه، بهبود، تثبیت.
- هر ماه، یک خروجی قابل نمایش.
- یک اقدام در ماه.
- گزارش قبل/بعد، بهترین استدلال.
- گسترش از ماه ۳.
- بازبینی ماهانه.

## فصل ۹۶: موانع سازمانی و سیاسی

### مقدمه

موانع فنی ساده‌اند. موانع **سازمانی** سخت‌اند: انگیزه‌های متناقض، قلمرو، ترس از دست دادن قدرت.

این فصل واقع‌بینانه‌ترین بخش کتاب است.

### مفاهیم اساسی

**پنج مانع اصلی:**

| مانع | نشانه |
|---|---|
| **انگیزه متناقض** | Ops پاداش «حادثه صفر»، Dev پاداش «سرعت» |
| **قلمرو** | «این مال تیم ماست» |
| **ترس از شفافیت** | «اگر عدد بد نشان دهیم، بودجه کم می‌شود» |
| **مدیریت میانی** | «نقش من چه می‌شود؟» |
| **بودجه متمرکز** | هر تغییر نیاز به تأیید |

**نکته**: این‌ها **عقلانی** هستند. هر کس منافع خودش را دنبال می‌کند.

**قاعده**: **سیستم را عوض کن، نه افراد را.**

### مثال‌های عملی

**مانع ۱: انگیزه متناقض**

```
وضعیت:
  Ops: پاداش = "حادثه صفر"
  Dev: پاداش = "قابلیت بیشتر"

نتیجه:
  Ops تغییر را بلاک می‌کند (منطقی!)
  Dev عصبانی می‌شود

راه‌حل:
  پاداش مشترک: "Lead Time + CFR"
  هر دو منافع مشترک دارند
```

**نکته**: رفتار «غیرهمکارانه» Ops، در سیستم غلط **عقلانی** است.

**مانع ۲: قلمرو**

```
وضعیت:
  "تیم DB مالک schema است، هیچ‌کس نباید تغییر دهد"
  نتیجه: هر migration ۲ هفته

راه‌حل:
  تیم DB استاندارد می‌سازد، تیم محصول اجرا می‌کند
  (guardrail، نه gate)
```

**مانع ۳: ترس از شفافیت**

```
وضعیت:
  "اگر متریک بد نشان دهیم، مدیر عصبانی می‌شود"
  نتیجه: داده پنهان، مشکل باقی

راه‌حل:
  مدیر باید اول شفافیت را پاداش دهد
  "ممنون که گفتی" — نه "چرا این‌قدر بد؟"
```

**نکته**: اولین واکنش مدیر به خبر بد، فرهنگ را تعیین می‌کند.

**مانع ۴: مدیریت میانی**

```
وضعیت:
  "اگر تیم‌ها خودمختار شوند، من چه کاره‌ام؟"
  نتیجه: مقاومت پنهان

راه‌حل:
  نقش جدید: chapter lead، coach، platform owner
  (مسئولیت جدید، نه حذف)
```

**نکته**: هر کسی باید جای خودش را در ساختار جدید ببیند.

**مانع ۵: بودجه متمرکز**

```
وضعیت:
  هر ابزار جدید: ۶ ماه فرآیند خرید
  نتیجه: تیم با ابزار رایگان کار می‌کند، ناسازگار

راه‌حل:
  بودجه تیمی + استاندارد
```

**پنج استراتژی غلبه:**

| استراتژی | مناسب |
|---|---|
| **داده** | انگیزه متناقض |
| **پایلوت** | قلمرو |
| **شفافیت تدریجی** | ترس |
| **نقش جدید** | مدیریت میانی |
| **حمایت اجرایی** | بودجه |

### مقایسه و الگوهای مختلف

**سه رویکرد به مقاومت:**

| رویکرد | نتیجه |
|---|---|
| **اجبار** | ❌ مقاومت پنهان |
| **متقاعد کردن** | متوسط |
| **تغییر سیستم** | ✅✅ |

**نکته**: اگر انگیزه‌ها عوض نشوند، متقاعد کردن موقتی است.

**سه سطح مداخله:**

| سطح | مثال | دوام |
|---|---|---|
| فرد | آموزش | ❌ |
| تیم | فرآیند | متوسط |
| ✅ سیستم | انگیزه، ساختار | ✅✅ |

**سه نوع مقاومت:**

| نوع | نشانه | پاسخ |
|---|---|---|
| **فعال** | مخالفت علنی | ✅ گفتگو |
| **منفعل** | «فراموش کردم» | ⚠️ انگیزه |
| **پنهان** | «موافقم» ولی کاری نمی‌کند | ❌ سیستم |

**نکته**: مقاومت پنهان خطرناک‌ترین است — چون دیده نمی‌شود.

### اشکال شایع

**اشکال ۱: برچسب «مقاومت در برابر تغییر»**

افراد احمق نیستند. منافعشان متفاوت است. بفهم چرا.

**اشکال ۲: اجبار**

مقاومت پنهان. بدتر از قبل.

**اشکال ۳: نادیده گرفتن مدیریت میانی**

مهم‌ترین مانع. نقش جدید بده.

**اشکال ۴: بدون حمایت اجرایی**

تیم پایلوت موفق، گسترش ناممکن.

**اشکال ۵: شفافیت ناگهانی**

«همه متریک‌ها را نشان می‌دهیم» — ترس. تدریجی.

**اشکال ۶: تغییر انگیزه بدون توضیح**

«چرا پاداش من عوض شد؟» — توضیح بده.

### نکات مهم (Tips & Tricks)

- **سیستم را عوض کن، نه افراد.**
- **داده** برای متقاعد کردن.
- **پایلوت** برای اثبات.
- **نقش جدید** برای مدیریت میانی.
- **حمایت اجرایی** از روز اول.
- **اولین واکنش به خبر بد** فرهنگ را تعیین می‌کند.

### خلاصه فصل

- پنج مانع: انگیزه، قلمرو، ترس، مدیریت میانی، بودجه.
- رفتار «غیرهمکارانه» در سیستم غلط عقلانی است.
- سه سطح مداخله؛ سیستم پایدارترین.
- مقاومت پنهان خطرناک‌ترین است.
- نقش جدید برای مدیریت میانی.
- سیستم را عوض کن.

## فصل ۹۷: مدیریت تغییر

### مقدمه

تغییر فنی ساده است. تغییر **انسانی** سخت. این فصل چارچوب‌های مدیریت تغییر را می‌آورد.

### مفاهیم اساسی

**مدل کاتز — سه شرط:**

```
تغییر = توانایی × فرصت × انگیزه

اگر یکی صفر باشد، نتیجه صفر
```

| شرط | مثال | اگر نباشد |
|---|---|---|
| **توانایی** | آموزش | نمی‌توانند |
| **فرصت** | وقت، ابزار | نمی‌شود |
| **انگیزه** | پاداش، معنا | نمی‌خواهند |

**نکته**: اکثر برنامه‌ها فقط **توانایی** (آموزش) می‌دهند و بقیه را فراموش می‌کنند.

**مدل کاتز-لوین — سه مرحله:**

| مرحله | چه کاری |
|---|---|
| **Unfreeze** | نیاز به تغییر را نشان بده |
| **Change** | تغییر را اجرا کن |
| **Refreeze** | تغییر را تثبیت کن |

**نکته**: **Refreeze** اغلب فراموش می‌شود — و همه‌چیز برمی‌گردد.

**هشت گام کاتتر:**

| گام | معنا |
|---|---|
| ۱ | فوریت را ایجاد کن |
| ۲ | اتحاد هدایتگر بساز |
| ۳ | چشم‌انداز روشن |
| ۴ | ارتباط گسترده |
| ۵ | توانمندسازی |
| ۶ | پیروزی‌های کوتاه‌مدت |
| ۷ | تثبیت و گسترش |
| ۸ | نهادینه کردن |

**نکته**: گام ۶ (پیروزی کوتاه‌مدت) حیاتی است — انگیزه می‌دهد.

### مثال‌های عملی

**گام ۱: فوریت — چطور بسازی**

```
❌ بد: "ما باید DevOps داشته باشیم"
✅ خوب: "Lead Time ما ۲۴ روز است، رقیب ۲ روز.
        در ۶ ماه گذشته ۳ مشتری به‌خاطر سرعت از دست دادیم."
```

**نکته**: داده + پیامد کسب‌وکار، فوریت می‌سازد.

**گام ۲: اتحاد هدایتگر**

```
ترکیب لازم:
  - یک مدیر ارشد (حمایت)
  - یک مدیر میانی (اجرا)
  - ۲-۳ نفر فنی معتبر (اعتماد)
  - یک نفر از تیم‌های مقاوم (شنیدن)

نکته: بدون مدیر ارشد، تغییر در دیوار سازمان می‌ماند
```

**گام ۶: پیروزی کوتاه‌مدت**

```
ماه ۱: pipeline برای یک سرویس
  ↓
گزارش: "deploy از ۳۰ دقیقه به ۵ دقیقه"
  ↓
جشن کوچک، داستان در جلسه عمومی
  ↓
انگیزه برای ماه ۲
```

**نکته**: پیروزی باید **قابل مشاهده، مشخص و سریع** باشد.

**گام ۸: نهادینه کردن**

```
تغییر تثبیت می‌شود وقتی:
  - در onboarding باشد
  - در Definition of Done باشد
  - در ارزیابی عملکرد باشد
  - در ابزار اجباری باشد (guardrail)
```

**نکته**: اگر تغییر فقط «توصیه» باشد، برمی‌گردد.

**سه سطح ارتباط:**

| سطح | مخاطب | محتوا |
|---|---|---|
| استراتژیک | مدیران | چرا، نتیجه کسب‌وکار |
| تاکتیکی | مدیران میانی | چه، کِی، نقش من |
| عملیاتی | تیم‌ها | چطور، کمک |

**نکته**: اگر فقط سطح عملیاتی را پوشش دهی، مدیران میانی مانع می‌شوند.

### مقایسه و الگوهای مختلف

**سه مدل تغییر:**

| مدل | مناسب |
|---|---|
| **Kotter** | ✅ تحول بزرگ |
| **ADKAR** | تغییر فردی |
| **Katz** | تشخیص سریع |

**ADKAR — پنج مرحله فردی:**

| مرحله | معنا |
|---|---|
| **A**wareness | می‌دانم چرا |
| **D**esire | می‌خواهم |
| **K**nowledge | می‌دانم چطور |
| **A**bility | می‌توانم |
| **R**einforcement | ادامه می‌دهم |

**نکته**: اگر کسی در مرحله Awareness گیر کرده، آموزش (Knowledge) بی‌فایده است.

**سه سرعت تغییر:**

| سرعت | دوام |
|---|---|
| Big Bang | ❌ کم |
| تدریجی | ✅ زیاد |
| ✅ مرحله‌ای با پیروزی | ✅✅ |

### اشکال شایع

**اشکال ۱: فقط آموزش**

توانایی بدون فرصت و انگیزه. تغییر نمی‌شود.

**اشکال ۲: بدون فوریت**

«چرا باید عوض شویم؟» — پاسخ روشن نیست.

**اشکال ۳: بدون حمایت ارشد**

تغییر در دیوار می‌ماند.

**اشکال ۴: بدون پیروزی کوتاه‌مدت**

انگیزه تمام می‌شود.

**اشکال ۵: بدون Refreeze**

برمی‌گردد.

**اشکال ۶: ارتباط فقط عملیاتی**

مدیران میانی مانع می‌شوند.

**اشکال ۷: نادیده گرفتن ADKAR**

آموزش به کسی که «نمی‌خواهد» بی‌فایده است.

### نکات مهم (Tips & Tricks)

- **توانایی + فرصت + انگیزه** — هر سه.
- **فوریت با داده.**
- **حمایت ارشد** از روز اول.
- **پیروزی کوتاه‌مدت** در ماه ۱.
- **Refreeze** — در onboarding و ارزیابی.
- **سه سطح ارتباط.**

### خلاصه فصل

- Katz: توانایی × فرصت × انگیزه.
- Lewin: Unfreeze، Change، Refreeze.
- Kotter: هشت گام؛ پیروزی کوتاه‌مدت حیاتی.
- ADKAR برای تغییر فردی.
- ارتباط در سه سطح.
- بدون Refreeze، برمی‌گردد.
