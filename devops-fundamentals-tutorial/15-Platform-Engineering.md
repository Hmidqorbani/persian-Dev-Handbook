## فصل ۸۱: از DevOps به Platform Engineering

### مقدمه

DevOps گفت: «شما بسازید، شما اجرا کنید». ایده درست بود، ولی در مقیاس یک مشکل داشت:

**هر تیم، چرخ را از نو اختراع کرد.**

پنجاه تیم، پنجاه pipeline متفاوت، پنجاه روش deploy، پنجاه روش مدیریت secret. نتیجه: پیچیدگی انفجاری و بار شناختی غیرقابل تحمل.

**Platform Engineering** پاسخ به این مشکل است.

### مفاهیم اساسی

**مشکل مقیاس:**

```
تیم ۱: "ما Kubernetes را این‌طور راه انداختیم"
تیم ۲: "ما روش دیگری"
تیم ۳: "ما اصلاً K8s نداریم"
...
تیم ۵۰: ???

نتیجه:
  - ۵۰ روش متفاوت
  - هیچ‌کس نمی‌تواند بین تیم‌ها جابه‌جا شود
  - هر تیم، ۶ ماه یادگیری
  - امنیت ناسازگار
```

**راه‌حل: پلتفرم**

```
تیم پلتفرم: یک راه درست می‌سازد
    ↓
تیم‌های محصول: از آن استفاده می‌کنند
    ↓
نتیجه: استاندارد، امن، سریع
```

**تعریف:**

> **Platform Engineering** طراحی و ساخت ابزارها و جریان‌های خودخدمتی برای تیم‌های توسعه است، تا بار شناختی آن‌ها کم شود و بتوانند مستقل و سریع تحویل دهند.

**نکته کلیدی**: پلتفرم **بار شناختی (cognitive load)** را کم می‌کند — این معیار اصلی موفقیت است.

**سه نوع بار شناختی:**

| نوع | مثال |
|---|---|
| **Intrinsic** | پیچیدگی ذاتی مسئله (دامنه) |
| **Extraneous** | پیچیدگی ابزار (قابل حذف) |
| **Germane** | یادگیری مفید |

**پلتفرم، extraneous را حذف می‌کند** — نه intrinsic را.

### مثال‌های عملی

**قبل از پلتفرم — تجربه توسعه‌دهنده جدید:**

```
روز ۱:  ساخت حساب ابر (تیکت، ۲ روز)
روز ۳:  یادگیری Terraform (۱ هفته)
روز ۱۰: ساخت کلاستر (۳ روز، با ۵ خطا)
روز ۱۳: یادگیری Helm (۳ روز)
روز ۱۶: اولین deploy (با کمک یک نفر)
روز ۲۰: کشف اینکه secret اشتباه مدیریت شده
...
هفته ۶: اولین deploy موفق به production
```

**بعد از پلتفرم:**

```
روز ۱:  درخواست سرویس جدید (فرم ۵ فیلدی)
روز ۱:  سرویس ساخته شد (pipeline، محیط، monitoring)
روز ۲:  اولین commit → deploy خودکار به staging
روز ۳:  deploy به production
```

**تفاوت**: ۶ هفته در برابر ۳ روز.

**این تفاوت، ارزش پلتفرم است.**

**سه سطح پلتفرم:**

| سطح | چه چیزی |
|---|---|
| ۱ | CI/CD استاندارد |
| ۲ | + محیط self-service |
| ۳ | ✅ + observability، امنیت، هزینه |

**نکته**: از سطح ۱ شروع کن. سطح ۳ نیاز به تیم کامل دارد.

### مقایسه و الگوهای مختلف

**DevOps در برابر Platform:**

| معیار | DevOps | Platform |
|---|---|---|
| پیام | «خودت انجام بده» | «ما آسانش می‌کنیم» |
| مقیاس | ❌ برای ۵ تیم | ✅ برای ۵۰ تیم |
| بار شناختی | ❌ زیاد | ✅ کم |
| آزادی | ✅ زیاد | ⚠️ محدود (در مسیر طلایی) |

**نکته**: Platform **آزادی مطلق** را محدود می‌کند، ولی **آزادی مؤثر** را زیاد می‌کند.

**سه مدل اشتباه:**

| مدل | چرا غلط |
|---|---|
| «تیم زیرساخت با نام جدید» | محصول نیست، مشتری ندارد |
| «پلتفرم = Kubernetes» | K8s ابزار است، نه پلتفرم |
| «پلتفرم = پورتال» | UI بدون پشتِ کارآمد، بی‌فایده |

**سه سطح بلوغ:**

| سطح | ویژگی |
|---|---|
| ۱ | ابزار مشترک، بدون استاندارد |
| ۲ | استاندارد + self-service |
| ۳ | ✅ + محصول‌محور + متریک |

### اشکال شایع

**اشکال ۱: پلتفرم بدون مشتری**

تیم پلتفرم چیزی می‌سازد که کسی نمی‌خواهد. با تیم‌ها حرف بزن.

**اشکال ۲: پلتفرم به‌عنوان دروازه**

«باید از پلتفرم استفاده کنی» — بدون ارزش. اختیاری شروع کن.

**اشکال ۳: پلتفرم برای «همه‌چیز»**

از روز اول همه‌چیز. یک مسیر طلایی بساز، بعد گسترش.

**اشکال ۴: تیم پلتفرم بدون SRE**

پلتفرم خودش یک محصول production است. on-call لازم.

**اشکال ۵: پلتفرم بدون مستند**

توسعه‌دهنده نمی‌داند چطور استفاده کند. مستند = محصول.

**اشکال ۶: پلتفرم به‌عنوان پروژه**

«۶ ماه می‌سازیم، بعد تحویل» — پلتفرم محصول است، تکامل مستمر.

### نکات مهم (Tips & Tricks)

- **بار شناختی را کم کن** — معیار اصلی.
- **اختیاری شروع کن** — ارزش ثابت کن.
- **یک مسیر طلایی** بساز.
- **با تیم‌ها حرف بزن** — مشتری.
- **پلتفرم خودش production است** — on-call.
- **مستند = محصول.**

### خلاصه فصل

- Platform پاسخ به مشکل مقیاس DevOps است.
- بار شناختی extraneous را حذف می‌کند.
- سه سطح: CI/CD، محیط، observability.
- Platform آزادی مطلق را محدود، آزادی مؤثر را زیاد می‌کند.
- پلتفرم محصول است، نه پروژه.
- اختیاری شروع کن.

## فصل ۸۲: پلتفرم به‌عنوان محصول

### مقدمه

پلتفرم اگر **محصول** نباشد، همان تیم زیرساخت قدیمی است با نام جدید.

این فصل اصول محصول‌سازی را به پلتفرم اعمال می‌کند.

### مفاهیم اساسی

**پلتفرم به‌عنوان محصول — پنج اصل:**

| اصل | معنا |
|---|---|
| **مشتری** | توسعه‌دهنده |
| **ارزش** | حل مشکل واقعی |
| **کشف** | مصاحبه، بازخورد |
| **تکامل** | نسخه‌بندی، بهبود |
| **سنجش** | adoption، رضایت |

**تفاوت تیم زیرساخت و تیم پلتفرم:**

| معیار | زیرساخت | پلتفرم |
|---|---|---|
| نگاه به توسعه‌دهنده | درخواست‌دهنده | ✅ مشتری |
| موفقیت | «سیستم کار می‌کند» | «توسعه‌دهنده سریع‌تر است» |
| تصمیم | فنی | ✅ محصولی |
| ارتباط | تیکت | ✅ گفتگو |

**نکته**: پلتفرم بدون مشتری راضی، شکست خورده — حتی اگر از نظر فنی عالی باشد.

**سه نوع مشتری:**

| مشتری | نیاز |
|---|---|
| توسعه‌دهنده | سرعت، سادگی |
| SRE/Ops | پایداری، observability |
| امنیت/انطباق | کنترل، audit |

**نکته**: همه را راضی کن، ولی **توسعه‌دهنده** اولویت اول است.

### مثال‌های عملی

**کشف نیاز — سه روش:**

| روش | فرکانس | کیفیت |
|---|---|---|
| مصاحبه | ماهانه | ✅✅ |
| بررسی تیکت‌ها | هفتگی | ✅ |
| مشاهده (shadowing) | فصلی | ✅✅✅ |

**مشاهده، بهترین روش است:**

```
یک روز با توسعه‌دهنده بنشین و ببین:
  - کجا گیر می‌کند؟
  - چه کاری تکراری است؟
  - چه چیزی را دوست ندارد؟

این، ۱۰ برابر بهتر از نظرسنجی است.
```

**«Jobs to be Done» برای پلتفرم:**

```
توسعه‌دهنده می‌خواهد:
  "وقتی قابلیت جدیدی نوشتم،
   بتوانم مطمئن شوم در production کار می‌کند،
   بدون اینکه با زیرساخت درگیر شوم."

پلتفرم باید این job را انجام دهد — نه اینکه ابزار بدهد.
```

**نکته**: توسعه‌دهنده **Kubernetes نمی‌خواهد**؛ می‌خواهد سرویسش اجرا شود.

**نقشه راه محصول:**

```
Q1: مسیر طلایی برای یک نوع سرویس (Python API)
    - CI/CD استاندارد
    - محیط staging خودکار
    - متریک پایه

Q2: گسترش به Node.js
    + observability کامل
    + secret management

Q3: self-service محیط
    + review app
    + canary deploy

Q4: هزینه و بهینه‌سازی
    + FinOps
    + کارایی
```

**نکته**: هر فصل، **یک ارزش مشخص** برای مشتری.

**بازخورد — سه کانال:**

| کانال | فرکانس |
|---|---|
| جلسه ماهانه با تیم‌ها | ماهانه |
| کانال Slack #platform | پیوسته |
| نظرسنجی رضایت | فصلی |

### مقایسه و الگوهای مختلف

**پلتفرم به‌عنوان محصول در برابر پروژه:**

| معیار | محصول | پروژه |
|---|---|---|
| پایان | ❌ ندارد | ✅ دارد |
| معیار | adoption | تحویل |
| تیم | دائمی | موقت |
| تکامل | مستمر | ❌ |

**Push در برابر Pull در پلتفرم:**

| معیار | Push | Pull |
|---|---|---|
| روش | «باید استفاده کنی» | «استفاده می‌کنند چون بهتر است» |
| پذیرش | ❌ مقاومت | ✅ |
| مناسب | انطباق | ✅ اکثر |

**سه سطح adoption:**

| سطح | معیار |
|---|---|
| ۱ | < ۲۰٪ تیم‌ها |
| ۲ | ۲۰-۶۰٪ |
| ۳ | ✅ > ۶۰٪ |

### اشکال شایع

**اشکال ۱: پلتفرم بدون مصاحبه**

«فکر می‌کنیم این را می‌خواهند» — بپرس.

**اشکال ۲: پلتفرم اجباری**

مقاومت، دور زدن. اختیاری شروع کن.

**اشغال ۳: پلتفرم بدون مستند**

توسعه‌دهنده نمی‌داند. مستند = محصول.

**اشکال ۴: پلتفرم بدون پشتیبانی**

توسعه‌دهنده گیر می‌کند، کسی نیست. کانال پشتیبانی.

**اشکال ۵: پلتفرم بدون معیار**

نمی‌دانی موفق است یا نه. adoption و رضایت.

**اشکال ۶: پلتفرم برای «همه‌چیز»**

از روز اول همه‌چیز. یک مسیر، بعد گسترش.

### نکات مهم (Tips & Tricks)

- **مشاهده** بهترین روش کشف است.
- **Jobs to be Done** را بفهم.
- **اختیاری شروع کن.**
- **مستند و پشتیبانی** = محصول.
- **adoption و رضایت** را اندازه بگیر.
- **هر فصل، یک ارزش.**

### خلاصه فصل

- پلتفرم محصول است: مشتری، ارزش، کشف، تکامل، سنجش.
- توسعه‌دهنده مشتری اولویت اول است.
- مشاهده بهترین روش کشف نیاز است.
- Jobs to be Done، نه ابزار.
- اختیاری شروع کن.
- adoption معیار موفقیت است.

## فصل ۸۳: Internal Developer Platform

### mمقدمه

**IDP (Internal Developer Platform)** لایه‌ای است که زیرساخت را انتزاع می‌کند: توسعه‌دهنده با آن کار می‌کند، نه با Kubernetes و Terraform.

این فصل اجزا و طراحی IDP را می‌آورد.

### مفاهیم اساسی

**پنج لایه IDP:**

```
┌─────────────────────────────────────┐
│ ۵. رابط کاربری (پورتال، CLI)        │
├─────────────────────────────────────┤
│ ۴. قالب‌ها و مسیرهای طلایی          │
├─────────────────────────────────────┤
│ ۳. ارکستراسیون (CI/CD، محیط)        │
├─────────────────────────────────────┤
│ ۲. انتزاع زیرساخت (IaC)             │
├─────────────────────────────────────┤
│ ۱. زیرساخت (K8s، ابر، شبکه)         │
└─────────────────────────────────────┘
```

**نکته**: توسعه‌دهنده با لایه ۵ کار می‌کند. لایه‌های ۱-۴ پنهان‌اند.

**چهار جزء اصلی:**

| جزء | کار |
|---|---|
| **Service Catalog** | فهرست سرویس‌ها و مالک |
| **Templates** | قالب سرویس جدید |
| **Self-service** | محیط، DB، secret |
| **Observability** | متریک، لاگ، تریس یکجا |

### مثال‌های عملی

**تجربه توسعه‌دهنده با IDP:**

```
۱. در پورتال: "New Service"
   - نام: payment-api
   - زبان: Python
   - نوع: API
   - مالک: تیم پرداخت

۲. IDP می‌سازد:
   ✓ مخزن Git با ساختار استاندارد
   ✓ pipeline (lint، test، build، deploy)
   ✓ محیط staging
   ✓ متریک و داشبورد
   ✓ alert پایه
   ✓ مستند runbook

۳. توسعه‌دهنده: git clone → کد بنویس → push
   ↓
۴. deploy خودکار به staging
```

**نکته**: توسعه‌دهنده **هیچ‌کدام** از این‌ها را دستی نساخت.

**Service Catalog — نمونه:**

```yaml
# catalog/payment-api.yaml
apiVersion: platform.acme.com/v1
kind: Service
metadata:
  name: payment-api
  owner: team-payments
spec:
  type: api
  language: python
  tier: critical          # تأثیر روی SLO و on-call
  repository: acme/payment-api
  environments:
    - name: staging
      autoDeploy: true
    - name: production
      autoDeploy: false
      requiresApproval: true
  slo:
    availability: 99.95%
    latencyP99: 300ms
  dependencies:
    - postgres: payments-db
    - redis: payments-cache
  oncall: team-payments
```

**مزیت**: یک فایل، همه‌چیز. و قابل audit.

**قالب سرویس — ساختار:**

```
templates/python-api/
├── template.yaml          ← تعریف ورودی‌ها
├── skeleton/
│   ├── app/
│   ├── tests/
│   ├── Dockerfile
│   ├── .gitlab-ci.yml
│   └── README.md
└── docs/
    └── getting-started.md
```

**`template.yaml`:**

```yaml
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: python-api
  title: Python API Service
spec:
  parameters:
    - title: اطلاعات سرویس
      properties:
        name:
          type: string
          pattern: "^[a-z][a-z0-9-]{2,30}$"
        owner:
          type: string
        description:
          type: string
        tier:
          type: string
          enum: [critical, standard, internal]
  steps:
    - id: fetch
      action: fetch:template
      input:
        url: ./skeleton
        values:
          name: ${{ parameters.name }}
    - id: publish
      action: publish:gitlab
      input:
        repoUrl: gitlab.com?owner=acme&repo=${{ parameters.name }}
```

### مقایسه و الگوهای مختلف

**IDP در برابر پورتال:**

| معیار | IDP | پورتال |
|---|---|---|
| دامنه | کل تجربه | فقط UI |
| شامل | قالب، ارکستراسیون، زیرساخت | نمایش |
| مناسب | ✅ | جزء IDP |

**سه مدل ساخت:**

| مدل | مناسب |
|---|---|
| Build (خودت بساز) | سازمان بزرگ |
| Buy (Backstage، Port) | ✅ اکثر |
| Hybrid | ✅ توصیه |

**سه سطح IDP:**

| سطح | چه داری |
|---|---|
| ۱ | قالب + CI/CD استاندارد |
| ۲ | + self-service محیط |
| ۳ | ✅ + catalog + observability یکجا |

### اشکال شایع

**اشکال ۱: IDP = پورتال زیبا**

UI بدون پشت کارآمد. اول اتوماسیون، بعد UI.

**اشکال ۲: قالب بدون نگهداری**

قالب کهنه می‌شود، سرویس‌های جدید مشکل دارند. مالک و نسخه.

**اشکال ۳: IDP اجباری**

مقاومت. اختیاری + ارزش.

**اشکال ۴: IDP برای همه زبان‌ها از روز اول**

یک زبان، بعد گسترش.

**اشکال ۵: بدون catalog**

نمی‌دانی چه سرویسی داری، مالکش کیست.

**اشکال ۶: IDP بدون observability**

توسعه‌دهنده باید ۵ ابزار را چک کند. یکجا کن.

### نکات مهم (Tips & Tricks)

- **اول اتوماسیون، بعد UI.**
- **یک قالب، یک زبان** برای شروع.
- **Service Catalog** از روز اول.
- **قالب با نسخه و مالک.**
- **IDP اختیاری** — ارزش ثابت کن.
- **observability یکجا.**

### خلاصه فصل

- IDP پنج لایه دارد؛ توسعه‌دهنده با لایه ۵ کار می‌کند.
- چهار جزء: catalog، templates، self-service، observability.
- قالب = یک فایل، همه‌چیز.
- اول اتوماسیون، بعد پورتال.
- یک زبان برای شروع.
- catalog از روز اول.

---

## فصل ۸۴: مسیر طلایی

### مقدمه

**Golden Path** (یا Golden Journey) یک مسیر **توصیه‌شده و آسان** برای انجام یک کار رایج است — نه اجباری، ولی آن‌قدر خوب که کسی نخواهد جای دیگری برود.

این مفهوم، قلب طراحی پلتفرم است.

### مفاهیم اساسی

**تعریف:**

> Golden Path: یک راه استاندارد، پشتیبانی‌شده و آسان برای انجام یک کار رایج — با امکان خروج، ولی بدون دلیل برای خروج.

**سه ویژگی:**

| ویژگی | معنا |
|---|---|
| **آسان‌تر** | از راه دستی ساده‌تر |
| **پشتیبانی‌شده** | تیم پلتفرم کمک می‌کند |
| **قابل خروج** | اجباری نیست |

**نکته**: اگر مسیر طلایی **سخت‌تر** از راه دستی باشد، کسی استفاده نمی‌کند.

**سه نوع Golden Path:**

| نوع | مثال |
|---|---|
| **Service creation** | ساخت سرویس جدید |
| **Deployment** | deploy به production |
| **Incident response** | پاسخ به حادثه |

### مثال‌های عملی

**Golden Path برای deploy:**

```
مسیر دستی (بدون پلتفرم):
  ۱. SSH به سرور
  ۲. git pull
  ۳. docker build
  ۴. docker compose up
  ۵. بررسی لاگ
  ⏱️ ۳۰ دقیقه، ۵ مرحله، ۳ نقطه خطا

Golden Path:
  ۱. git push (یا merge به main)
  ⏱️ ۵ دقیقه، خودکار، با rollback
```

**نکته**: Golden Path باید **کوتاه‌تر و امن‌تر** باشد.

**Golden Path با خروج — چطور:**

```
✅ توصیه: "از قالب ما استفاده کن"
❌ اجبار: "باید از قالب ما استفاده کنی"

اگر تیمی دلیل موجه دارد:
  - ثبت استثنا (با دلیل)
  - پشتیبانی محدود
  - بازبینی فصلی
```

**نکته**: خروج باید **ممکن ولی گران‌تر** باشد — نه ممنوع.

**مستند Golden Path — ساختار:**

```markdown
# Golden Path: ساخت API جدید

## چه زمانی استفاده کن
- API ساده با PostgreSQL
- تیم می‌خواهد سریع شروع کند

## چه زمانی استفاده نکن
- نیاز به GPU
- دیتابیس غیر PostgreSQL
- latency زیر ۱۰ms

## مراحل
۱. در پورتال "New Service" بزن
۲. فرم را پر کن (۵ فیلد)
۳. منتظر بمان (~۲ دقیقه)
۴. git clone و شروع کن

## چه چیزی خودکار می‌گیری
- مخزن با ساختار استاندارد
- pipeline کامل
- محیط staging
- متریک و alert
- runbook پایه

## چطور deploy کنم
merge به main → خودکار به staging
tag → production (با تأیید)

## اگر مشکل داشتم
#platform-support در Slack
```

**نکته**: بخش «چه زمانی استفاده نکن» مهم‌ترین است — جلوی استفاده اشتباه را می‌گیرد.

**سنجش Golden Path:**

| متریک | هدف |
|---|---|
| Time to First Deploy | < ۱ روز |
| Adoption | > ۷۰٪ سرویس جدید |
| رضایت | > ۴/۵ |
| خروج | < ۱۰٪ |

### مقایسه و الگوهای مختلف

**Golden Path در برابر استاندارد اجباری:**

| معیار | Golden Path | اجباری |
|---|---|---|
| پذیرش | ✅ داوطلبانه | ❌ مقاومت |
| نوآوری | ✅ حفظ | ❌ کم |
| استانداردسازی | ✅ بالا | ✅✅ |

**نکته**: Golden Path استانداردسازی **با رضایت** است.

**سه سطح Golden Path:**

| سطح | پوشش |
|---|---|
| ۱ | یک نوع سرویس |
| ۲ | چند نوع |
| ۳ | ✅ همه نیازهای رایج |

**Paved Road در برابر Golden Path:**

| معیار | Paved Road | Golden Path |
|---|---|---|
| معنا | همان | همان |
| منشأ | Netflix | Backstage |

**نکته**: دو نام برای یک مفهوم.

### اشکال شایع

**اشکال ۱: Golden Path سخت‌تر از دستی**

کسی استفاده نمی‌کند. باید **آسان‌تر** باشد.

**اشکال ۲: Golden Path اجباری**

مقاومت، دور زدن. اختیاری.

**اشکال ۳: بدون مسیر خروج**

تیم با نیاز خاص، گیر می‌کند. خروج ممکن.

**اشکال ۴: Golden Path بدون مستند**

توسعه‌دهنده نمی‌داند. مستند کامل.

**اشکال ۵: Golden Path بدون پشتیبانی**

گیر می‌کند، کسی نیست. کانال پشتیبانی.

**اشکال ۶: Golden Path کهنه**

قالب ۲ سال پیش. نگهداری و نسخه.

**اشکال ۷: Golden Path برای همه‌چیز**

پیچیده می‌شود. یک مسیر، بعد گسترش.

### نکات مهم (Tips & Tricks)

- **آسان‌تر از دستی** — شرط لازم.
- **اختیاری، با خروج ممکن.**
- **«چه زمانی استفاده نکن»** را بنویس.
- **Time to First Deploy** را اندازه بگیر.
- **نگهداری و نسخه.**
- **پشتیبانی واقعی.**

### خلاصه فصل

- Golden Path: مسیر توصیه‌شده، آسان، پشتیبانی‌شده.
- باید آسان‌تر از دستی باشد.
- اختیاری، با خروج ممکن.
- مستند با «چه زمانی استفاده نکن».
- Time to First Deploy معیار است.
- نگهداری = محصول.

## فصل ۸۵: خودخدمتی و ابزار

### مقدمه

**Self-service** هدف نهایی پلتفرم است: توسعه‌دهنده بدون تیکت، بدون انتظار، کارش را انجام دهد.

این فصل سطوح و ابزار را می‌آورد.

### مفاهیم اساسی

**سه سطح خودخدمتی:**

| سطح | مثال | زمان انتظار |
|---|---|---|
| **Manual** | تیکت به تیم | ❌ روزها |
| **Scripted** | اسکریپت مشترک | ساعت‌ها |
| **✅ Self-service** | پورتال/CLI | دقیقه‌ها |

**نکته**: تفاوت اصلی، **زمان انتظار** است.

**چهار حوزه خودخدمتی:**

| حوزه | مثال |
|---|---|
| **Service** | ساخت سرویس جدید |
| **Environment** | محیط موقت |
| **Data** | DB، bucket |
| **Access** | دسترسی، secret |

### مثال‌های عملی

**قبل و بعد — درخواست DB:**

**قبل:**
```
۱. تیکت به تیم DB
۲. انتظار ۲ روز
۳. جلسه ۳۰ دقیقه‌ای برای تنظیمات
۴. انتظار ۱ روز
۵. DB آماده

⏱️ ۳ روز، ۲ نفر درگیر
```

**بعد:**
```
۱. در پورتال: "New Database"
۲. فرم: نام، اندازه، محیط
۳. ۲ دقیقه بعد: DB آماده، connection string در secret

⏱️ ۲ دقیقه، صفر نفر درگیر
```

**این تفاوت، ارزش پلتفرم است.**

**CLI در برابر پورتال:**

| معیار | CLI | پورتال |
|---|---|---|
| سرعت | ✅✅ | متوسط |
| کشف‌پذیری | ❌ | ✅✅ |
| اتوماسیون | ✅✅ | ❌ |
| مناسب | توسعه‌دهنده باتجربه | تازه‌کار |

**توصیه**: هر دو. CLI برای سرعت، پورتال برای کشف.

**مثال CLI (مفهومی):**

```bash
# ساخت سرویس جدید
platform create service payment-api \
  --template python-api \
  --owner team-payments \
  --tier critical

# ساخت محیط موقت
platform create environment \
  --service payment-api \
  --branch feature/retry \
  --ttl 3d

# دیدن وضعیت
platform status payment-api

# دیدن لاگ
platform logs payment-api --env production --tail 100
```

**نکته**: CLI باید **ساده و قابل کشف** باشد (`--help` خوب).

**Guardrails در برابر Gates:**

| معیار | Guardrail | Gate |
|---|---|---|
| چه می‌کند | مسیر امن می‌دهد | جلوی کار را می‌گیرد |
| تجربه | ✅ روان | ❌ انتظار |
| مثال | قالب امن | تأیید مدیر |

**نکته**: پلتفرم باید **guardrail** باشد، نه **gate**.

**مثال guardrail:**

```
❌ Gate: "برای ساخت DB باید تأیید مدیر بگیری"
✅ Guardrail: "DB با رمزنگاری، backup خودکار، دسترسی محدود ساخته می‌شود"
```

**دومی امن‌تر است** و کسی را معطل نمی‌کند.

### مقایسه و الگوهای مختلف

**سه مدل دسترسی:**

| مدل | امنیت | سرعت |
|---|---|---|
| Gate | ✅ | ❌ |
| Guardrail | ✅✅ | ✅ |
| آزاد | ❌ | ✅✅ |

**توصیه**: Guardrail.

**سه سطح بلوغ self-service:**

| سطح | ویژگی |
|---|---|
| ۱ | تیکت |
| ۲ | اسکریپت |
| ۳ | ✅ پورتال/CLI |

**Build در برابر Buy:**

| جزء | توصیه |
|---|---|
| CI/CD | ✅ Buy (GitLab و...) |
| قالب | Build |
| Catalog | Buy (Backstage) |
| IaC | Buy (Terraform) |

**نکته**: چیزهای عمومی را بخر، چیزهای خاص سازمان را بساز.

### اشکال شایع

**اشکال ۱: self-service بدون guardrail**

توسعه‌دهنده DB عمومی می‌سازد. guardrail امن.

**اشکال ۲: پورتال بدون CLI**

توسعه‌دهنده باتجربه کند می‌شود. هر دو.

**اشکال ۳: self-service پیچیده**

فرم ۲۰ فیلدی = کسی استفاده نمی‌کند. ساده کن.

**اشکال ۴: بدون مستند**

توسعه‌دهنده نمی‌داند چه گزینه‌ای دارد. مستند و `--help`.

**اشکال ۵: self-service بدون بازخورد**

«درخواست ثبت شد» و بعد هیچ. وضعیت را نشان بده.

**اشکال ۶: ساخت همه‌چیز از صفر**

CI/CD خودت نساز. buy.

### نکات مهم (Tips & Tricks)

- **Self-service هدف است** — زمان انتظار را کم کن.
- **CLI + پورتال** هر دو.
- **Guardrail، نه Gate.**
- **فرم ساده** — ۵ فیلد.
- **وضعیت را نشان بده.**
- **عمومی را بخر، خاص را بساز.**

### خلاصه فصل

- سه سطح: manual، scripted، self-service.
- چهار حوزه: service، environment، data، access.
- CLI برای سرعت، پورتال برای کشف.
- Guardrail بهتر از Gate است.
- فرم ساده، بازخورد واضح.
- عمومی را بخر.

---

## فصل ۸۶: سنجش موفقیت پلتفرم

### مقدمه

پلتفرم بدون سنجش، پروژه‌ای است که نمی‌دانی موفق است یا نه.

این فصل متریک‌های درست را می‌آورد.

### مفاهیم اساسی

**چهار دسته متریک:**

| دسته | مثال |
|---|---|
| **Adoption** | چند تیم استفاده می‌کنند |
| **Velocity** | چقدر سریع‌تر شدند |
| **Satisfaction** | راضی‌اند؟ |
| **Reliability** | پلتفرم پایدار است؟ |

**نکته**: adoption بالا بدون رضایت = اجبار. رضایت بدون adoption = بی‌فایده.

**پنج متریک کلیدی:**

| متریک | هدف |
|---|---|
| **Adoption rate** | > ۷۰٪ سرویس جدید |
| **Time to First Deploy** | < ۱ روز |
| **Lead Time (تیم‌ها)** | کاهش ۳۰٪ |
| **NPS/رضایت** | > ۴/۵ |
| **Platform SLO** | ۹۹.۹٪ |

### مثال‌های عملی

**داشبورد پلتفرم:**

```
┌──────────────────────────────────────────────┐
│ Adoption                                     │
│   سرویس‌های جدید با قالب:      ۷۸٪ (↑)      │
│   تیم‌های فعال:                ۳۴/۴۰        │
│                                              │
│ Velocity                                     │
│   Time to First Deploy:       ۶ ساعت (↓)    │
│   Lead Time (median):         ۲ روز (↓ ۴۵٪) │
│                                              │
│ Satisfaction                                 │
│   NPS:                        +42 (↑)        │
│   رضایت قالب:                 4.3/5          │
│                                              │
│ Reliability                                  │
│   Platform uptime:            99.94٪         │
│   Incidents (۳۰ روز):         ۱              │
└──────────────────────────────────────────────┘
```

**نکته**: چهار دسته با هم. یکی گمراه می‌کند.

**محاسبه Adoption:**

```
سرویس‌های جدید در ۹۰ روز: ۲۳
از این ۲۳، ساخته‌شده با قالب: ۱۸
Adoption = 18/23 = 78٪ ✅
```

**محاسبه Time to First Deploy:**

```
برای هر سرویس جدید:
  از "درخواست" تا "اولین deploy موفق به staging"

median = ۶ ساعت ✅ (هدف < ۱ روز)
```

**نظرسنجی رضایت — سه سؤال:**

```
۱. چقدر از پلتفرم راضی هستی؟ (۱-۵)
۲. چه چیزی بیشترین درد است؟ (متنی)
۳. چه چیزی را حذف می‌کردی؟ (متنی)
```

**نکته**: سؤال سوم اغلب مفیدترین است.

**Platform SLO:**

```
پلتفرم خودش یک سرویس است:
  - CI/CD در دسترس باشد
  - پورتال در دسترس باشد
  - deploy کار کند

SLO: 99.9٪
اگر پلتفرم خراب شود، همه تیم‌ها متوقف می‌شوند
```

**نکته**: پلتفرم با ۵۰ تیم، **تک‌نقطه شکست** است. SLO بالاتر لازم.

### مقایسه و الگوهای مختلف

**سه نوع متریک:**

| نوع | مثال | دستکاری |
|---|---|---|
| **Adoption** | ٪ استفاده | ⚠️ (اجبار) |
| **Outcome** | Lead Time | ✅ سخت |
| **Satisfaction** | NPS | متوسط |

**نکته**: Outcome بهترین است — سخت دستکاری می‌شود.

**Adoption در برابر Value:**

| معیار | Adoption | Value |
|---|---|---|
| چه می‌گوید | استفاده می‌شود | بهتر شد |
| دستکاری | ✅ آسان | ❌ سخت |
| مناسب | شروع | ✅ بلوغ |

**سه سطح بلوغ سنجش:**

| سطح | چه داری |
|---|---|
| ۱ | تعداد کاربر |
| ۲ | + adoption |
| ۳ | ✅ + outcome + رضایت |

### اشکال شایع

**اشکال ۱: فقط adoption**

اجبار adoption را بالا می‌برد. رضایت هم بسنج.

**اشکال ۲: فقط رضایت**

«همه راضی‌اند» ولی کسی استفاده نمی‌کند. adoption.

**اشکال ۳: بدون baseline**

«Lead Time بهتر شد» — از چه به چه؟

**اشکال ۴: مقایسه تیم‌ها**

«تیم A سریع‌تر است» — context متفاوت. جمع کل.

**اشکال ۵: متریک بدون اقدام**

داشبورد زیبا، هیچ تغییری.

**اشکال ۶: نادیده گرفتن Platform SLO**

پلتفرم خراب، همه متوقف. خودش را بسنج.

### نکات مهم (Tips & Tricks)

- **چهار دسته با هم.**
- **Outcome مهم‌تر از adoption.**
- **baseline قبل از هدف.**
- **Platform SLO** برای خود پلتفرم.
- **سؤال «چه حذف می‌کردی»** مفیدترین است.
- **هر متریک، یک اقدام.**

### خلاصه فصل

- چهار دسته: adoption، velocity، satisfaction، reliability.
- پنج متریک کلیدی.
- adoption بدون رضایت = اجبار.
- Outcome سخت‌تر دستکاری می‌شود.
- Platform خودش SLO دارد.
- baseline قبل از هدف.
