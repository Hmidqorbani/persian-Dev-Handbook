## فصل ۹۸: رهبری در تحول DevOps

### مقدمه

تحول DevOps بدون رهبری، اتفاق نمی‌افتد. ولی «رهبری» به‌معنای «دستور دادن» نیست؛ به‌معنای **ساختن شرایط** است.

این فصل رفتارهای رهبری مؤثر را می‌آورد.

### مفاهیم اساسی

**پنج رفتار رهبری مؤثر:**

| رفتار | مثال |
|---|---|
| **مدل‌سازی** | خودش postmortem می‌نویسد |
| **حمایت** | بودجه و اختیار می‌دهد |
| **حذف مانع** | فرآیند تأیید را ساده می‌کند |
| **پرسیدن** | «چه چیزی سخت است؟» |
| **صبر** | ۲-۳ سال، نه ۳ ماه |

**نکته**: رهبری DevOps بیشتر **حذف مانع** است تا **افزودن دستور**.

**سه نوع رهبر:**

| نوع | رفتار | نتیجه |
|---|---|---|
| **Command** | دستور می‌دهد | ❌ مقاومت |
| **Laissez-faire** | رها می‌کند | ❌ هرج‌ومرج |
| ✅ **Servant** | مانع را برمی‌دارد | ✅ |

**نکته**: در تحول، رهبر «خدمتکار» تیم است — شرایط را می‌سازد، نه مسیر را دیکته می‌کند.

### مثال‌های عملی

**رفتار ۱: مدل‌سازی — مهم‌ترین**

```
❌ رهبر می‌گوید: "شما باید بدون سرزنش باشید"
   ولی در حادثه: "کی این را deploy کرد؟"

✅ رهبر می‌گوید: "چه چیزی در سیستم این را ممکن کرد؟"
   و در حادثه اول خودش این را می‌پرسد
```

**نکته**: **اولین واکنش رهبر به خبر بد**، فرهنگ را تعیین می‌کند — نه سخنرانی‌ها.

**رفتار ۲: حمایت — سه شکل**

| شکل | مثال |
|---|---|
| بودجه | ابزار، آموزش |
| زمان | ۲۰٪ برای بهبود |
| اختیار | تیم می‌تواند تصمیم بگیرد |

**نکته**: حمایت بدون **اختیار**، توهم است.

**رفتار ۳: حذف مانع — نمونه**

```
تیم: "برای deploy باید ۳ تأیید بگیریم، ۲ هفته طول می‌کشد"
رهبر: (با تیم امنیت حرف می‌زند) "چرا این تأییدها لازم است؟"
    → کشف: یکی از سه تأیید، تکراری است
    → حذف یک تأیید: ۲ هفته به ۱ هفته

نکته: رهبر مانع را برمی‌دارد، تیم کار نمی‌کند
```

**رفتار ۴: پرسیدن — پنج سؤال**

```
۱. بزرگ‌ترین اتلاف وقت شما چیست؟
۲. چه چیزی را اگر حذف کنیم، زندگی بهتر می‌شود؟
۳. کجا گیر می‌کنید؟
۴. چه چیزی را نمی‌توانید تصمیم بگیرید؟
۵. اگر یک چیز را عوض می‌کردید، چه بود؟
```

**نکته**: این سؤالات، **نقشه راه** را می‌دهند — بهتر از هر مشاور.

**رفتار ۵: صبر — واقعیت**

```
ماه ۱:  تیم پایلوت شروع
ماه ۳:  اولین نتیجه
ماه ۶:  تیم دوم
ماه ۱۲: نیمی از سازمان
ماه ۲۴: فرهنگ عوض شده

اگر در ماه ۳ انتظار فرهنگ جدید داری: ناامید می‌شوی
```

### مقایسه و الگوهای مختلف

**رهبری سنتی در برابر DevOps:**

| معیار | سنتی | DevOps |
|---|---|---|
| تصمیم | متمرکز | ✅ توزیع‌شده |
| کنترل | فرآیند | ✅ نتیجه |
| خطا | ❌ سرزنش | ✅ یادگیری |
| نقش | دستوردهنده | ✅ تسهیل‌کننده |

**سه سطح حمایت:**

| سطح | کافی؟ |
|---|---|
| گفتن «حمایت می‌کنم» | ❌ |
| بودجه دادن | متوسط |
| ✅ بودجه + اختیار + زمان | ✅ |

**رهبر فنی در برابر رهبر سازمانی:**

| معیار | فنی | سازمانی |
|---|---|---|
| اعتماد | ✅ فنی | متوسط |
| اختیار | ❌ محدود | ✅ زیاد |
| نیاز | ✅ هر دو | ✅ هر دو |

**نکته**: بهترین حالت، **جفت** — یک رهبر فنی معتبر + یک حامی سازمانی.

### اشکال شایع

**اشکال ۱: حمایت کلامی بدون عمل**

«ما DevOps می‌خواهیم» ولی بودجه صفر. بدبینی.

**اشکال ۲: تفویض بدون اختیار**

«شما مسئول هستید» ولی هر تصمیم نیاز به تأیید.

**اشکال ۳: سرزنش در حادثه اول**

فرهنگ برای همیشه خراب می‌شود.

**اشکال ۴: انتظار نتیجه سریع**

۳ ماه، بعد «DevOps کار نمی‌کند».

**اشکال ۵: رهبر بدون دانش فنی**

نمی‌داند چه مانعی را بردارد. مشاور لازم.

**اشکال ۶: تغییر رهبر**

رهبر عوض شد، تحول متوقف. نهادینه کن.

### نکات مهم (Tips & Tricks)

- **مدل‌سازی، مهم‌ترین رفتار.**
- **اولین واکنش به خبر بد**، فرهنگ را تعیین می‌کند.
- **حمایت = بودجه + اختیار + زمان.**
- **مانع را بردار**، نه دستور بده.
- **پنج سؤال** بپرس.
- **صبر ۲-۳ سال.**

### خلاصه فصل

- پنج رفتار: مدل‌سازی، حمایت، حذف مانع، پرسیدن، صبر.
- رهبری = حذف مانع، نه افزودن دستور.
- حمایت بدون اختیار توهم است.
- اولین واکنش به خبر بد حیاتی است.
- جفت رهبر فنی + سازمانی بهترین است.
- صبر ۲-۳ سال.

## فصل ۹۹: ایمنی روانی

### مقدمه

**ایمنی روانی (Psychological Safety)** — اصطلاح Amy Edmondson — یعنی: باور به اینکه می‌توانی سؤال بپرسی، اشتباه کنی، یا مخالفت کنی، بدون ترس از تنبیه یا تحقیر.

این، **پیش‌نیاز** یادگیری است. بدون آن، هیچ‌کدام از اصول DevOps کار نمی‌کند.

### مفاهیم اساسی

**چهار سطح ایمنی:**

| سطح | معنا |
|---|---|
| **Inclusion safety** | می‌توانم عضو باشم |
| **Learner safety** | می‌توانم سؤال بپرسم |
| **Contributor safety** | می‌توانم مشارکت کنم |
| **Challenger safety** | می‌توانم مخالفت کنم |

**نکته**: سطح چهارم سخت‌ترین است — مخالفت با وضع موجود.

**چهار رفتار ایمنی‌ساز:**

| رفتار | ضدرفتار |
|---|---|
| **اعتراف به خطا** | پنهان‌کاری |
| **پرسیدن** | «باید بدانی» |
| **مخالفت** | «همه موافقند» |
| **درخواست کمک** | «خودم انجام می‌دهم» |

**نکته**: اگر در جلسه‌ای **هیچ مخالفتی** نیست، یا ایمنی صفر است یا تفکر گروهی.

**ماتریس ایمنی × عملکرد (Edmondson):**

```
        عملکرد بالا
             │
  Comfort    │  ✅ Learning
  (راحت،     │  (چالش + ایمنی)
   بدون      │
   چالش)     │
  ───────────┼─────────── ایمنی
  Apathy     │  Anxiety
  (بی‌تفاوت) │  (ترس، بدون یادگیری)
             │
        عملکرد پایین
```

**نکته**: فقط ایمنی کافی نیست؛ **چالش** هم لازم است. ایمنی بدون چالش = راحتی.

### مثال‌های عملی

**ایمنی پایین — نشانه‌ها:**

```
[ ] کسی در جلسه سؤال نمی‌پرسد
[ ] همه همیشه موافقند
[ ] خطاها دیر گزارش می‌شوند
[ ] «نمی‌دانم» گفته نمی‌شود
[ ] کسی داوطلب on-call نمی‌شود
[ ] در retro همه می‌گویند «همه‌چیز خوب بود»
```

اگر سه مورد یا بیشتر: ایمنی پایین.

**چطور ایمنی بسازیم — پنج اقدام:**

**۱) رهبر اول اعتراف کند**

```
"من دیروز یک اشتباه کردم: X. این را یاد گرفتم: Y."
```

**نکته**: وقتی رهبر (که «قدرت» دارد) اعتراف می‌کند، به همه سیگنال می‌دهد که امن است.

**۲) سؤال را پاداش بده**

```
❌ "این را باید می‌دانستی"
✅ "سؤال خوبی است، بگذار توضیح بدهم"
```

**۳) خطا را جدا از فرد ببین**

```
❌ "علی اشتباه کرد"
✅ "فرآیند اجازه داد این اشتباه رخ دهد"
```

**۴) «نمی‌دانم» را عادی کن**

```
رهبر: "من نمی‌دانم، بیایید با هم پیدا کنیم"
```

**۵) مخالفت را دعوت کن**

```
"کسی مخالفتی دارد؟ اگر نه، بگذار یک نقش مخالف بازی کنم..."
```

**نکته**: دعوت صریح به مخالفت، تفکر گروهی را می‌شکند.

**مثال retro ایمن در برابر ناامن:**

```
❌ retro ناامن:
  "همه‌چیز خوب بود"
  "فقط کمی فشار داشتیم"
  (هیچ اقدام)

✅ retro ایمن:
  "deploy ما ۳ بار شکست خورد، چون تست integration نداشتیم"
  "من نمی‌دانستم چطور دیباگ کنم، کمک خواستم"
  "پیشنهاد: تست integration اضافه کنیم"
  (۲ اقدام با مالک)
```

**تفاوت**: صداقت، که فقط با ایمنی ممکن است.

### مقایسه و الگوهای مختلف

**ایمنی روانی در برابر راحتی:**

| معیار | ایمنی | راحتی |
|---|---|---|
| چالش | ✅ | ❌ |
| صداقت | ✅ | ⚠️ |
| عملکرد | ✅✅ | ❌ |

**نکته**: ایمنی بدون چالش، «Comfort Zone» است.

**سه مدل فرهنگ (Westrum):**

| نوع | ویژگی | عملکرد |
|---|---|---|
| **Pathological** | ترس، پنهان‌کاری | ❌ |
| **Bureaucratic** | قوانین، حفاظت | متوسط |
| ✅ **Generative** | یادگیری، مأموریت | ✅✅ |

**نکته**: Westrum نشان داد نوع فرهنگ، پیش‌بین قوی عملکرد است.

**ایمنی در برابر مسئولیت:**

| معیار | ایمنی | مسئولیت |
|---|---|---|
| خطا | ✅ گفتگو | ✅ رفع |
| رفتار مخرب | ❌ نادیده | ✅ برخورد |
| تعادل | ✅ Just Culture | ✅ |

### اشکال شایع

**اشکال ۱: ایمنی = بدون مسئولیت**

«هر کاری بکنی اشکالی ندارد» — بی‌نظمی. Just Culture.

**اشکال ۲: ایمنی بدون چالش**

تیم راحت، ولی پیشرفت صفر. چالش لازم.

**اشکال ۳: ایمنی فقط در تیم**

مدیریت سرزنش می‌کند. ایمنی دوام نمی‌آورد.

**اشکال ۴: اعلام ایمنی بدون رفتار**

«اینجا امن است» ولی اولین سؤال، سرزنش است.

**اشکال ۵: نادیده گرفتن سکوت**

«کسی مخالفتی ندارد» — شاید ترس است. دعوت کن.

**اشکال ۶: ایمنی به‌عنوان پروژه**

یک کارگاه، بعد فراموش. رفتار روزمره لازم.

### نکات مهم (Tips & Tricks)

- **رهبر اول اعتراف کند.**
- **سؤال را پاداش بده.**
- **خطا را از فرد جدا کن.**
- **«نمی‌دانم» را عادی کن.**
- **مخالفت را دعوت کن.**
- **ایمنی + چالش**، نه یکی.

### خلاصه فصل

- ایمنی روانی پیش‌نیاز یادگیری است.
- چهار سطح؛ سطح چهارم (مخالفت) سخت‌ترین.
- ایمنی بدون چالش = راحتی.
- Westrum: فرهنگ generative بهترین عملکرد.
- رهبر اول اعتراف کند.
- Just Culture: ایمنی + مسئولیت.

## فصل ۱۰۰: سنجش فرهنگ

### مقدمه

«فرهنگ سنجیدنی نیست» — غلط است. می‌توان سنجید، به شرطی که درست سنجیده شود.

این فصل روش‌های عملی را می‌آورد.

### مفاهیم اساسی

**چهار نوع داده:**

| نوع | مثال | کیفیت |
|---|---|---|
| **پرسشنامه** | امتیاز ایمنی | متوسط |
| **رفتاری** | تعداد postmortem | ✅ |
| **متنی** | بازخورد آزاد | ✅✅ |
| **مشاهده** | جلسات | ✅✅ |

**نکته**: پرسشنامه تنها کافی نیست — **رفتار واقعی** را ببین.

**پنج شاخص رفتاری قابل اندازه‌گیری:**

| شاخص | معنا |
|---|---|
| **نرخ گزارش خطا** | خطاها گزارش می‌شوند؟ |
| **تعداد postmortem** | حادثه بررسی می‌شود؟ |
| **نرخ اقدامات انجام‌شده** | اقدامات پیگیری می‌شوند؟ |
| **زمان تا گزارش** | خطا چقدر زود گزارش می‌شود؟ |
| **تنوع نظر در retro** | مخالفت وجود دارد؟ |

### مثال‌های عملی

**پرسشنامه ایمنی — ۷ سؤال:**

```
۱ = کاملاً مخالف، ۵ = کاملاً موافق

۱. اگر اشتباهی کنم، به‌جای سرزنش، دنبال علت می‌گردیم
۲. می‌توانم بدون ترس سؤال بپرسم
۳. می‌توانم با تصمیم‌ها مخالفت کنم
۴. «نمی‌دانم» گفتن پذیرفته است
۵. کمک خواستن نشانه ضعف نیست
۶. خطاها را زود گزارش می‌کنیم
۷. از حادثه‌ها یاد می‌گیریم و اقدام می‌کنیم

امتیاز ۲۸-۳۵: ایمنی بالا
۱۸-۲۷: متوسط
< ۱۸: نیاز جدی
```

**نکته**: این پرسشنامه را **بی‌نام** اجرا کن — وگرنه داده واقعی نمی‌گیری.

**شاخص رفتاری — تحلیل postmortem:**

```
آخرین ۱۰ postmortem را بررسی کن:

| مورد | سؤال |
|---|---|
| نام فرد مقصر ذکر شده؟ | ❌ نباید |
| اقدام با مالک دارد؟ | ✅ باید |
| اقدام انجام شده؟ | ✅ باید |
| «چه خوب پیش رفت» دارد؟ | ✅ باید |
| در ۴۸ ساعت نوشته شده؟ | ✅ باید |
```

**اگر ۳ مورد از ۵ خوب بود**: فرهنگ در مسیر درست.

**تحلیل متن retro:**

```
جمع‌آوری یادداشت‌های retro در ۳ ماه:

❌ نشانه‌های منفی:
  - "همه‌چیز خوب بود" (تکرار)
  - "کمبود وقت" (تکرار، بدون اقدام)
  - هیچ مخالفتی

✅ نشانه‌های مثبت:
  - مسائل مشخص با جزئیات
  - پیشنهادهای متفاوت
  - اقدامات انجام‌شده
```

**مشاهده — چک‌لیست جلسه:**

```
در یک جلسه بنشین و ببین:

[ ] چند نفر سؤال پرسیدند؟
[ ] کسی مخالفت کرد؟
[ ] کسی «نمی‌دانم» گفت؟
[ ] وقتی خطا مطرح شد، واکنش چه بود؟
[ ] چه کسی بیشترین صحبت را کرد؟ (تنوع؟)
```

**نکته**: مشاهده، **دقیق‌ترین** داده است — چون رفتار واقعی است، نه نظر.

**گزارش فرهنگ — قالب:**

```
# فرهنگ — [تیم/سازمان] — Q3

## پرسشنامه ایمنی
امتیاز: ۲۴/۳۵ (متوسط)
ضعیف‌ترین: مخالفت (۲.۸/۵)
قوی‌ترین: کمک خواستن (۴.۱/۵)

## شاخص‌های رفتاری
postmortem در ۹۰ روز: ۶
اقدامات انجام‌شده: ۱۴/۲۰ (۷۰٪)
میانگین زمان نوشتن: ۳ روز ✅

## مشاهده
- در ۴ جلسه، ۲ مخالفت ثبت شد (بهبود از ۰)
- ۳ نفر «نمی‌دانم» گفتند ✅

## روند
Q1: ۱۹  →  Q2: ۲۲  →  Q3: ۲۴  ⬆️

## اقدام بعدی
- دعوت صریح به مخالفت در retro
- تمرین «نقش مخالف» در جلسات طراحی
```

### مقایسه و الگوهای مختلف

**سه روش سنجش:**

| روش | هزینه | دقت |
|---|---|---|
| پرسشنامه | ✅ کم | متوسط |
| مشاهده | ❌ زیاد | ✅✅ |
| شاخص رفتاری | ✅ کم | ✅ |

**توصیه**: هر سه، با وزن بیشتر روی رفتار.

**سنجش در برابر قضاوت:**

| معیار | سنجش | قضاوت |
|---|---|---|
| هدف | بهبود | ارزیابی |
| نتیجه | ✅ اعتماد | ❌ پنهان‌کاری |
| سؤال | «چرا؟» | «چقدر؟» |

**نکته**: اگر فرهنگ را برای **ارزیابی تیم** بسنجی، داده خراب می‌شود.

**سه سطح گزارش:**

| سطح | مخاطب |
|---|---|
| تیم | خودشان |
| مدیریت | روند |
| سازمان | الگو |

### اشکال شایع

**اشکال ۱: پرسشنامه بدون نام‌نویسی**

داده واقعی نمی‌گیری. بی‌نام کن.

**اشکال ۲: فقط پرسشنامه**

نظر ≠ رفتار. رفتار را ببین.

**اشکال ۳: سنجش برای قضاوت**

«تیم شما فرهنگ ضعیفی دارد» — پنهان‌کاری.

**اشکال ۴: یک‌بار سنجش**

روند مهم است. هر فصل.

**اشکال ۵: بدون اقدام**

«امتیاز ۲۴ است» و هیچ کاری نکردن.

**اشکال ۶: نادیده گرفتن سیگنال‌های ضعیف**

«کسی داوطلب on-call نمی‌شود» — نشانه فرهنگ.

### نکات مهم (Tips & Tricks)

- **بی‌نام** برای داده واقعی.
- **رفتار را ببین**، نه فقط نظر.
- **مشاهده دقیق‌ترین است.**
- **هر فصل** سنجش.
- **برای بهبود، نه قضاوت.**
- **روند مهم‌تر از عدد.**

### خلاصه فصل

- چهار نوع داده: پرسشنامه، رفتاری، متنی، مشاهده.
- پنج شاخص رفتاری.
- پرسشنامه بی‌نام.
- مشاهده دقیق‌ترین است.
- هر فصل، روند را ببین.
- برای بهبود، نه قضاوت.

## فصل ۱۰۱: شکست‌های رایج تحول

### مقدمه

۷۰٪ تحول‌های سازمانی شکست می‌خورند. این فصل الگوهای شکست را می‌آورد — تا تشخیص بدهی و زودتر اصلاح کنی.

### مفاهیم اساسی

**هفت شکست رایج:**

| شکست | نشانه |
|---|---|
| **ابزارگرایی** | «Kubernetes آوردیم، DevOps داریم» |
| **تیم DevOps جدا** | شکاف سوم |
| **بدون حمایت ارشد** | تیم پایلوت موفق، گسترش صفر |
| **Big Bang** | همه‌جا همزمان، هیچ‌کدام تمام |
| **بدون متریک** | «بهتر شد» بدون داده |
| **فرهنگ نادیده** | ابزار خوب، همکاری بد |
| **بدون Refreeze** | بعد از ۶ ماه، همه‌چیز برگشت |

**نکته**: بیشتر شکست‌ها **سازمانی** هستند، نه فنی.

### مثال‌های عملی

**شکست ۱: ابزارگرایی**

```
چه شد:
  شرکت ۲ میلیون خرج Kubernetes کرد
  تیم‌ها آموزش دیدند
  ولی: deploy هنوز دستی، هماهنگی همان، فرهنگ همان

نتیجه: پیچیدگی بیشتر، سود صفر

درس: ابزار بدون فرآیند و فرهنگ، فقط پیچیدگی می‌آورد
```

**شکست ۲: تیم DevOps جدا**

```
چه شد:
  "تیم DevOps" ۵ نفره ساخته شد
  Dev و Ops قبلی سر جایشان
  تیم DevOps: واسط بین آن دو

نتیجه:
  شکاف Dev/Ops → شکاف Dev/DevOps/Ops
  تحویل کندتر (سه لایه هماهنگی)

درس: DevOps تیم نیست، نحوه کار است
```

**شکست ۳: بدون حمایت ارشد**

```
چه شد:
  تیم پایلوت عالی کار کرد
  Lead Time از ۲۰ به ۴ روز
  ولی: تیم‌های دیگر گفتند "ما وقت نداریم"
  مدیریت: "خوب است، ادامه بدهید" (بدون بودجه)

نتیجه: پایلوت جزیره‌ای، گسترش صفر

درس: بدون حمایت ارشد و بودجه، موفقیت تکثیر نمی‌شود
```

**شکست ۴: Big Bang**

```
چه شد:
  ۲۰ تیم، ۲۰ پروژه همزمان
  همه‌چیز: CI/CD + K8s + observability + platform

نتیجه:
  هیچ‌کدام تمام نشد
  تیم‌ها فرسوده
  مدیریت: "DevOps کار نمی‌کند"

درس: یک تیم، یک قدم، یک نتیجه
```

**شکست ۵: بدون متریک**

```
چه شد:
  ۶ ماه کار
  "حس می‌کنیم بهتر شدیم"
  مدیریت: "چه نتیجه‌ای؟"
  پاسخ: "خب... pipeline داریم"

نتیجه: بودجه قطع شد

درس: baseline از روز اول، گزارش ماهانه
```

**شکست ۶: فرهنگ نادیده**

```
چه شد:
  CI/CD عالی، pipeline ۵ دقیقه
  ولی: در حادثه، "کی deploy کرد؟"
  توسعه‌دهنده‌ها خطا را پنهان می‌کنند

نتیجه: ابزار خوب، استفاده بد
        (تیم pipeline را دور می‌زند)

درس: ابزار بدون فرهنگ، دور زده می‌شود
```

**شکست ۷: بدون Refreeze**

```
چه شد:
  تحول موفق، ۱۸ ماه
  رهبر تحول رفت
  هیچ‌چیز نهادینه نشده بود

نتیجه: در ۶ ماه، همه‌چیز برگشت

درس: در onboarding، ارزیابی، ابزار — نهادینه کن
```

### مقایسه و الگوهای مختلف

**سه دسته شکست:**

| دسته | درصد |
|---|---|
| سازمانی (حمایت، فرهنگ) | ۶۰٪ |
| فرآیندی (Big Bang، بدون متریک) | ۳۰٪ |
| فنی (ابزار اشتباه) | ۱۰٪ |

**نکته**: **فنی کم‌ترین سهم** را دارد — ولی بیشترین توجه را می‌گیرد.

**سه سطح تشخیص:**

| سطح | نشانه |
|---|---|
| زودهنگام | ماه ۳: کسی استفاده نمی‌کند |
| میانه | ماه ۹: متریک بهتر نشد |
| دیرهنگام | ماه ۱۸: برگشت |

**سه مدل پیشگیری:**

| مدل | اقدام |
|---|---|
| پایلوت | ✅ اثبات قبل از گسترش |
| متریک | ✅ زود تشخیص |
| Refreeze | ✅ تثبیت |

### اشکال شایع

**اشکال ۱: تشخیص دیرهنگام**

۱۸ ماه بعد کشف می‌کنی. متریک ماهانه بگذار.

**اشکال ۲: انکار**

«تیم‌ها همکاری نمی‌کنند» — شاید طراحی بد است.

**اشکال ۳: تغییر مسیر مداوم**

هر ماه رویکرد جدید. هیچ‌کدام فرصت نمی‌یابد.

**اشکال ۴: سرزنش تیم‌ها**

«فرهنگ بد است» — رهبری را ببین.

**اشکال ۵: توقف کامل**

«کار نکرد، رها کنیم». بازگشت به عقب.

**اشکال ۶: نادیده گرفتن موفقیت کوچک**

تیم پایلوت موفق، ولی کسی نمی‌داند. داستان بگو.

### نکات مهم (Tips & Tricks)

- **۶۰٪ شکست‌ها سازمانی‌اند.**
- **متریک ماهانه** برای تشخیص زودهنگام.
- **پایلوت** قبل از گسترش.
- **Refreeze** از روز اول.
- **داستان موفقیت** را پخش کن.
- **اگر تیم‌ها دور می‌زنند، طراحی را ببین.**

### خلاصه فصل

- هفت شکست: ابزارگرایی، تیم جدا، بدون حمایت، Big Bang، بدون متریک، فرهنگ، بدون Refreeze.
- ۶۰٪ سازمانی، ۱۰٪ فنی.
- متریک ماهانه برای تشخیص.
- پایلوت و Refreeze پیشگیری می‌کنند.
- دور زدن تیم = طراحی بد.
- داستان موفقیت را پخش کن.

## فصل ۱۰۲: پایداری تغییر

### مقدمه

تغییر آسان است؛ **ماندگار کردنش** سخت. این فصل آخرین و مهم‌ترین بخش است.

### مفاهیم اساسی

**چهار ستون پایداری:**

| ستون | معنا |
|---|---|
| **نهادینه‌سازی** | در فرآیند و ابزار |
| **مالکیت** | کسی مسئول است |
| **متریک** | روند پایش می‌شود |
| **فرهنگ** | رفتار عادی شده |

**نکته**: اگر یکی نباشد، تغییر در ۶-۱۲ ماه برمی‌گردد.

**چرخه پایداری:**

```
تغییر → تثبیت → نهادینه → فرهنگ → (پایدار)
```

### مثال‌های عملی

**ستون ۱: نهادینه‌سازی — پنج جا**

| جا | مثال |
|---|---|
| **Onboarding** | «روز اول: این‌طور deploy می‌کنیم» |
| **Definition of Done** | «در production است» |
| **ارزیابی عملکرد** | «همکاری، نه فقط تحویل» |
| **ابزار** | guardrail، نه سند |
| **فرآیند** | در جریان کار، نه جدا |

**نکته**: اگر تغییر در **onboarding** نباشد، نسل بعد نمی‌داند.

**ستون ۲: مالکیت**

```
هر عنصر تغییر، یک مالک:

| عنصر | مالک |
|---|---|
| pipeline استاندارد | Platform team |
| SLO | تیم سرویس |
| postmortem | IC |
| فرهنگ | همه (ولی یک هماهنگ‌کننده) |
```

**نکته**: مالکیت بدون نام = مالکیت بدون مالک.

**ستون ۳: متریک پایدار**

```
ماهانه:
  - Lead Time
  - Deploy Frequency
  - CFR
  - MTTR
  - امتیاز فرهنگ

فصلی:
  - مرور روند
  - تنظیم اهداف
```

**نکته**: اگر متریک متوقف شود، توجه متوقف می‌شود.

**ستون ۴: فرهنگ — سه نشانه عادی‌شدن**

```
[ ] کسی درباره «چرا DevOps» نمی‌پرسد (عادی شده)
[ ] تیم جدید، خودکار این‌طور کار می‌کند
[ ] رفتار قدیمی «عجیب» به نظر می‌رسد
```

**نکته**: وقتی رفتار جدید **پیش‌فرض** شد، فرهنگ عوض شده.

**نشانه‌های رگرسیون:**

```
[ ] deploy دوباره دستی شد
[ ] متریک‌ها دیگر گزارش نمی‌شوند
[ ] postmortem متوقف شد
[ ] «استثنا» رایج شد
[ ] نفر کلیدی رفت، دانش رفت
```

**اگر دو مورد یا بیشتر**: خطر رگرسیون.

### مقایسه و الگوهای مختلف

**سه سطح پایداری:**

| سطح | مدت |
|---|---|
| تثبیت موقت | ۳-۶ ماه |
| نهادینه | ۱-۲ سال |
| ✅ فرهنگ | ۳+ سال |

**نکته**: فرهنگ، **آخرین** مرحله است — و طولانی‌ترین.

**Push در برابر Pull در پایداری:**

| معیار | Push | Pull |
|---|---|---|
| روش | اجبار | ✅ ارزش |
| دوام | ❌ | ✅✅ |

**سه مدل نگهداری:**

| مدل | مناسب |
|---|---|
| متمرکز | ❌ (گلوگاه) |
| توزیع‌شده | ✅ |
| ترکیبی | ✅✅ |

### اشکال شایع

**اشکال ۱: توقف پس از موفقیت**

«تمام شد» — و رگرسیون شروع می‌شود.

**اشکال ۲: بدون مالک**

هر کس، هیچ‌کس. مالک تعیین کن.

**اشکال ۳: متریک متوقف**

توجه متوقف. ماهانه ادامه بده.

**اشکال ۴: نادیده گرفتن onboarding**

نسل بعد نمی‌داند. اولین روز آموزش بده.

**اشکال ۵: رهبر کلیدی رفت**

دانش رفت. مستند و توزیع کن.

**اشکال ۶: «استثنا» رایج شد**

یک استثنا، همیشه استثنا. محکم بایست.

### نکات مهم (Tips & Tricks)

- **پنج جای نهادینه‌سازی** را چک کن.
- **هر عنصر، یک مالک.**
- **متریک ماهانه** ادامه بده.
- **Onboarding** حیاتی است.
- **نشانه‌های رگرسیون** را پایش کن.
- **«استثنا» را رد کن.**

### خلاصه فصل

- چهار ستون: نهادینه، مالکیت، متریک، فرهنگ.
- اگر یکی نباشد، برمی‌گردد.
- پنج جای نهادینه‌سازی.
- هر عنصر، یک مالک.
- Onboarding حیاتی است.
- فرهنگ آخرین و طولانی‌ترین مرحله است.
