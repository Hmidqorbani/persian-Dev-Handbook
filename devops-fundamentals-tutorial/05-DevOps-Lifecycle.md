## فصل ۲۴: نگاه کلان به چرخه حیات

### mمقدمه

DevOps را معمولاً با یک **چرخه بی‌پایان** نشان می‌دهند: Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → (بازگشت). این تصویر مفید است ولی خطرناک: ممکن است فکر کنی این هشت مرحله **متوالی** هستند.

در واقع همه‌شان **همزمان و پیوسته** جریان دارند. این فصل نقشه را می‌دهد.

### مفاهیم اساسی

**هشت مرحله و سؤال اصلی هر کدام:**

| مرحله | سؤال | خروجی |
|---|---|---|
| **Plan** | چه چیزی بسازیم؟ | backlog، تصمیم |
| **Code** | چطور بسازیم؟ | کد، تست |
| **Build** | چطور بسته‌بندی کنیم؟ | artifact |
| **Test** | کار می‌کند؟ | گزارش، اطمینان |
| **Release** | آماده انتشار است؟ | نسخه |
| **Deploy** | چطور برسانیم؟ | سرویس به‌روز |
| **Operate** | سالم است؟ | سرویس در حال کار |
| **Monitor** | چطور می‌فهمیم؟ | متریک، alert |

**نکته حیاتی — دو حلقه، نه یک چرخه:**

```
حلقه درونی (دقیقه‌ها):  Code → Build → Test
حلقه بیرونی (روزها):    Plan → ... → Monitor → Plan
```

حلقه درونی باید **سریع** باشد (دقیقه). حلقه بیرونی **کامل** (روز/هفته).

**سه ویژگی چرخه سالم:**

| ویژگی | معنا |
|---|---|
| **پیوسته** | هر مرحله در هر لحظه در حال اجراست |
| **قابل مشاهده** | می‌دانی هر آیتم کجاست |
| **قابل بازگشت** | هر مرحله می‌تواند برگردد |

> **تشبیه روزمره**: چرخه DevOps مثل **گردش خون** است، نه مثل **خط تولید**. خون در همه رگ‌ها همزمان جریان دارد؛ خط تولید از اول به آخر می‌رود.

### مثال‌های عملی

**چرخه در یک تیم ۵ نفره — چه چیزی واقعاً اتفاق می‌افتد:**

```
۰۹:۰۰  Plan: standup، تصمیم درباره اولویت
۰۹:۱۵  Code: دو نفر روی feature A، یکی روی باگ B
۰۹:۴۵  Build: push → CI خودکار
۰۹:۵۰  Test: تست‌ها سبز، MR باز
۱۰:۳۰  Release: MR review، merge
۱۰:۳۵  Deploy: staging خودکار
۱۱:۰۰  Operate: staging تست دستی
۱۴:۰۰  Monitor: متریک staging بررسی
۱۵:۰۰  Plan: بازخورد staging → تنظیم اولویت
```

**نکته**: در یک روز، **همه هشت مرحله** اتفاق افتاد — نه در هشت هفته.

**مدل «خط تولید» در برابر «جریان»:**

| معیار | خط تولید | جریان |
|---|---|---|
| ترتیب | سریال | موازی |
| WIP | زیاد | کم |
| بازخورد | در انتها | در هر نقطه |
| مناسب | تولید انبوه | نرم‌افزار |

**نقشه جریان ارزش — نسخه DevOps:**

```
[ایده] ──► [backlog] ──► [کد] ──► [CI] ──► [review] ──► [staging] ──► [prod] ──► [کاربر]
   │            │           │        │          │            │           │
   └────────────┴───────────┴────────┴──────────┴────────────┴───────────┘
                          بازخورد در همه نقاط
```

### مقایسه و الگوهای مختلف

**چرخه DevOps در برابر چرخه سنتی:**

| معیار | سنتی | DevOps |
|---|---|---|
| مرحله | waterfall | پیوسته |
| بازخورد | در انتها | در هر نقطه |
| مالکیت | تیم جدا | مشترک |
| تغییر | استثنا | عادی |

**سه مدل نمایش چرخه:**

| مدل | مزیت | عیب |
|---|---|---|
| دایره (infinity loop) | ✅ شهودی | ممکن است متوالی فهمیده شود |
| زنجیره ارزش | ✅ واقع‌گرا | خشک |
| خط با بازخورد | ✅ دقیق | پیچیده |

**نکته**: هیچ نمایشی کامل نیست. مهم است که **بازخورد** و **مالکیت مشترک** را ببینی.

**سه سطح بلوغ چرخه:**

| سطح | ویژگی |
|---|---|
| ۱ | مراحل جدا، دستی |
| ۲ | خودکار در بخش‌هایی |
| ۳ | پیوسته و قابل مشاهده |

### اشکال شایع

**اشکال ۱: چرخه را متوالی دیدیم**

«اول همه Plan، بعد همه Code» — همان waterfall با اسم جدید.

**اشکال ۲: مرحله‌ای که مالک ندارد**

معمولاً Operate و Monitor. «کار تیم ops است» — دیوار برمی‌گردد.

**اشکال ۳: بازخورد فقط در انتها**

بازخورد بعد از ۶ ماه، بی‌فایده است.

**اشکال ۴: مرحله‌ای را حذف کردیم**

«ما Release نداریم، deploy می‌کنیم» — اگر معنی‌اش «تصمیم انتشار نداریم» باشد، خطرناک است.

**اشکال ۵: چرخه را کامل و بی‌نقص خواستیم**

از یک مرحله شروع کن، بعد گسترش بده.

### نکات مهم (Tips & Tricks)

- **چرخه را روی تخته بکش و بچسبان** — تیم باید ببیند.
- **برای هر مرحله، مالک مشخص کن** (حتی اگر مشترک است).
- **زمان هر مرحله را اندازه بگیر** — گلوگاه پیدا می‌شود.
- **دو حلقه را جدا نگه دار** — درونی سریع، بیرونی کامل.
- **از مرحله‌ای شروع کن که دردش بیشتر است.**

### خلاصه فصل

- هشت مرحله: Plan، Code، Build، Test، Release، Deploy، Operate، Monitor.
- پیوسته‌اند، نه متوالی.
- دو حلقه: درونی (دقیقه) و بیرونی (روز).
- هر مرحله باید مالک داشته باشد.
- بازخورد در همه نقاط، نه فقط انتها.

## فصل ۲۵: Plan و Code

### مقدمه

**Plan** یعنی تصمیم بگیریم چه بسازیم؛ **Code** یعنی بسازیم. در DevOps این دو مرحله تغییر مهمی کرده‌اند: **تصمیم نزدیک‌تر به اجرا** و **کد به‌عنوان تنها منبع حقیقت**.

### مفاهیم اساسی

**Plan — چهار فعالیت:**

| فعالیت | خروجی |
|---|---|
| کشف نیاز | مسئله روشن |
| اولویت‌بندی | ترتیب |
| تخمین | اندازه |
| تعریف Done | معیار پذیرش |

**تعریف Done در DevOps — تغییر مهم:**

| سنتی | DevOps |
|---|---|
| کد نوشته شد | کد در production است |
| تست پاس شد | در حال استفاده است |
| مستند شد | متریک دارد |

این تغییر، کل زنجیره را به هم می‌زند: «Done» یعنی **ارزش تحویل شد**، نه «کار تمام شد».

**Code — چهار اصل:**

| اصل | معنا |
|---|---|
| **کوچک** | تغییر کوچک، MR کوچک |
| **قابل تست** | هر تغییر، تست دارد |
| **قابل خواندن** | دیگران می‌فهمند |
| **قابل بازگشت** | rollback آسان |

**نکته**: «قابل بازگشت» فقط برای deploy نیست؛ برای کد هم هست. feature flag، branch by abstraction.

### مثال‌های عملی

**Plan مؤثر — سه سؤال قبل از شروع:**

```
۱. چه مشکلی را حل می‌کند؟  (نه: چه قابلیتی می‌سازیم)
۲. چطور می‌فهمیم حل شد؟    (متریک)
۳. کوچک‌ترین نسخه چیست؟    (MVP، قابل انتشار)
```

**مثال:**

| بد | خوب |
|---|---|
| «صفحه تنظیمات بسازیم» | «کاربران نمی‌توانند اعلان را خاموش کنند و شکایت می‌کنند» |
| معیار: ندارد | معیار: ۵۰٪ کاربران از تنظیمات استفاده کنند |
| نسخه: کامل | نسخه: فقط کلید خاموش/روشن اعلان |

**Code — ساختار تعریف Done:**

```
Definition of Done:
  [ ] کد نوشته و merge شد
  [ ] تست واحد دارد (پوشش ≥ ۸۰٪)
  [ ] تست integration دارد (اگر لازم)
  [ ] در staging deploy و تست شد
  [ ] در production deploy شد
  [ ] متریک/لاگ دارد
  [ ] مستند شد (اگر رفتار عمومی عوض شد)
```

**نکته**: آخرین سه مورد را اکثر تیم‌ها فراموش می‌کنند — و همین‌ها تفاوت DevOps با Agile است.

**Feature flag — کد بدون انتشار:**

```python
"""انتشار کد بدون فعال‌سازی قابلیت."""
import os

FEATURES = {
    "new_checkout": os.getenv("FEATURE_NEW_CHECKOUT", "false") == "true",
}


def is_enabled(name: str) -> bool:
    """آیا قابلیت فعال است؟"""
    return FEATURES.get(name, False)


# در کد
if is_enabled("new_checkout"):
    return new_checkout_flow(cart)
return legacy_checkout(cart)
```

**چرا مهم است**: می‌توانی کد را merge کنی (ریسک merge صفر) بدون این‌که رفتار عوض شود. بعد تدریجی فعال کنی.

**Branch by Abstraction — برای تغییرات بزرگ:**

```python
# مرحله ۱: انتزاع بساز
class PaymentGateway(Protocol):
    def charge(self, amount: int) -> bool: ...

# مرحله ۲: پیاده‌سازی جدید اضافه کن، ولی از قدیمی استفاده کن
# مرحله ۳: سوییچ کن (با flag)
# مرحله ۴: قدیمی را حذف کن
```

**مزیت**: چهار MR کوچک به‌جای یک MR ۲۰۰۰ خطی.

### مقایسه و الگوهای مختلف

**Plan سنتی در برابر DevOps:**

| معیار | سنتی | DevOps |
|---|---|---|
| افق | سالانه | دوهفته |
| تغییر | ❌ سخت | ✅ عادی |
| مالک | PM | تیم |
| بازخورد | کم | ✅ مستمر |

**سه مدل برنامه‌ریزی:**

| مدل | مناسب |
|---|---|
| Roadmap فصلی | جهت کلی |
| Sprint/Iteration | تعهد کوتاه |
| Kanban پیوسته | ✅ جریان |

**توصیه**: roadmap برای جهت، Kanban برای اجرا.

**Code review در برابر pair programming:**

| معیار | Review | Pairing |
|---|---|---|
| زمان | بعد از کد | همزمان |
| کیفیت | ✅ | ✅✅ |
| هزینه | کم | زیاد |
| مناسب | پیش‌فرض | کار حساس |

### اشکال شایع

**اشکال ۱: Plan بدون معیار موفقیت**

«صفحه تنظیمات بساز» بدون «چطور بفهمیم موفق بود». نتیجه: نمی‌دانی ارزش داشت یا نه.

**اشکال ۲: Done = merge شده**

کار در main است ولی در production نیست. ارزش صفر.

**اشکال ۳: Feature flag بدون تاریخ انقضا**

بدهی فنی خاموش. هر flag باید تاریخ حذف داشته باشد.

**اشکال ۴: تغییر بزرگ بدون انتزاع**

MR ۲۰۰۰ خطی، review سطحی، ریسک بالا.

**اشکال ۵: Plan از تیم جدا**

PM برنامه می‌ریزد، تیم اجرا می‌کند، بازخورد برنمی‌گردد.

### نکات مهم (Tips & Tricks)

- **سه سؤال Plan** را در هر ticket بگذار.
- **Definition of Done را تا production ببر.**
- **Feature flag با تاریخ انقضا** — در کد کامنت بگذار.
- **تغییر بزرگ را با انتزاع بشکن.**
- **تیم در Plan شریک باشد** — تخمین و تصمیم.

### خلاصه فصل

- Plan: کشف، اولویت، تخمین، تعریف Done.
- Done در DevOps = در production.
- Code: کوچک، تست‌پذیر، خوانا، قابل بازگشت.
- Feature flag کد را از انتشار جدا می‌کند.
- Branch by abstraction تغییر بزرگ را می‌شکند.

## فصل ۲۶: Build و Test

### مقدمه

**Build** کد را به artifact تبدیل می‌کند؛ **Test** اطمینان می‌دهد کار می‌کند. این دو مرحله، قلب حلقه درونی هستند و باید در **دقیقه** تمام شوند.

### مفاهیم اساسی

**Build — چهار اصل:**

| اصل | معنا |
|---|---|
| **تکرارپذیر** | همان ورودی، همان خروجی |
| **سریع** | دقیقه، نه ساعت |
| **ایزوله** | وابسته به محیط نمی‌باشد |
| **قابل کشف** | artifact قابل ردیابی |

**«Artifact» چیست؟** خروجی فیزیکی build: ایمیج Docker، فایل jar، بسته tar، فایل wheel.

**قاعده طلایی**: **یک‌بار build کن، همه‌جا استفاده کن.**

```
❌ build در staging، build جدا در production
✅ build یک‌بار → همان artifact در همه محیط‌ها
```

چرا؟ چون build مجدد می‌تواند متفاوت باشد (dependency عوض شده، cache متفاوت). و آن‌وقت staging چیزی را تست کرده که در production نیست.

**Test — هرم تست:**

```
        ╱╲
       ╱E2E╲        کم، کند، شکننده
      ╱──────╲
     ╱Integration╲  متوسط
    ╱──────────────╲
   ╱   Unit Tests    ╲  زیاد، سریع، پایدار
  ╱────────────────────╲
```

| سطح | تعداد | سرعت | هزینه نگهداری |
|---|---|---|---|
| Unit | زیاد (۷۰٪) | میلی‌ثانیه | کم |
| Integration | متوسط (۲۰٪) | ثانیه | متوسط |
| E2E | کم (۱۰٪) | دقیقه | ❌ زیاد |

**نکته**: هرم برعکس (بیشتر E2E) = تست کند و شکننده.

### مثال‌های عملی

**Build تکرارپذیر — سه شرط:**

| شرط | چطور |
|---|---|
| Dependency قفل‌شده | `package-lock.json`، `poetry.lock`، `go.sum` |
| Base image pin‌شده | `python:3.12.7-slim` نه `python:latest` |
| Build در محیط یکسان | Docker |

```dockerfile
# ❌ غیرتکرارپذیر
FROM python:3
RUN pip install -r requirements.txt   # نسخه‌ها ممکن است عوض شوند

# ✅ تکرارپذیر
FROM python:3.12.7-slim@sha256:abc123...
COPY requirements.txt .
RUN pip install --no-cache-dir --require-hashes -r requirements.txt
```

**`--require-hashes`** تضمین می‌کند همان بسته‌ای نصب شود که تست کردی.

**تست سریع — اصول:**

```python
"""تست واحد سریع، بدون I/O."""
from decimal import Decimal

from app.pricing import apply_discount


def test_discount_10_percent():
    # بدون DB، بدون شبکه، بدون فایل
    assert apply_discount(Decimal("100"), Decimal("0.10")) == Decimal("90")


def test_discount_cannot_exceed_total():
    assert apply_discount(Decimal("100"), Decimal("1.5")) == Decimal("0")
```

**نکته**: تست واحد که DB لازم دارد، تست واحد نیست — integration است.

**تست integration — با سرویس واقعی:**

```python
"""تست integration با PostgreSQL واقعی."""
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker


@pytest.fixture(scope="module")
def db():
    engine = create_engine("postgresql://test:test@localhost:5432/test")
    Base.metadata.create_all(engine)
    Session = sessionmaker(bind=engine)
    yield Session()
    Base.metadata.drop_all(engine)


def test_create_link(db):
    from app.models import ShortLink
    link = ShortLink(code="abc123", target_url="https://example.com")
    db.add(link)
    db.commit()
    assert db.query(ShortLink).count() == 1
```

**چرا SQLite کافی نیست**: رفتار (قفل، type، transaction) متفاوت است. تست با SQLite می‌تواند مشکل production را نگیرد.

**تست‌های شکننده (Flaky) — تشخیص و درمان:**

| نشانه | علت | راه‌حل |
|---|---|---|
| گاهی پاس، گاهی fail | وابستگی به زمان | clock را mock کن |
| فقط در CI fail | ترتیب تست | ایزوله کن |
| بعد از مدتی fail | داده انباشته | داده را پاک کن |
| تصادفی | race condition | wait صریح |

**قاعده**: تست flaky را **قرنطینه** کن (از pipeline اصلی خارج، با issue). هرگز `retry` نگذار به‌عنوان راه‌حل.

### مقایسه و الگوهای مختلف

**هرم در برابر Honeycomb:**

| مدل | توضیح |
|---|---|
| Pyramid | unit زیاد، E2E کم |
| Honeycomb | integration بیشتر (نزدیک به production) |
| Trophy | integration محور، unit کمتر |

**توصیه مدرن**: pyramid برای منطق پیچیده، honeycomb برای سیستم‌های توزیع‌شده.

**سه استراتژی تست در CI:**

| استراتژی | زمان | پوشش |
|---|---|---|
| Smoke | ۲ دقیقه | حداقلی |
| Full | ۲۰ دقیقه | کامل |
| Selective | ۵ دقیقه | تغییر‌یافته |

**توصیه**: smoke در MR، full شبانه، selective برای monorepo.

**Test Double — پنج نوع:**

| نوع | کاربرد |
|---|---|
| Dummy | پر کردن پارامتر |
| Stub | پاسخ ثابت |
| Spy | ثبت فراخوانی |
| Mock | انتظار رفتار |
| Fake | پیاده‌سازی ساده (in-memory DB) |

### اشکال شایع

**اشکال ۱: build غیرتکرارپذیر**

`latest` در base image، dependency بدون lock. staging و production متفاوت.

**اشکال ۲: build جدا برای هر محیط**

staging چیزی را تست کرد که در production نیست.

**اشکال ۳: هرم برعکس**

بیشتر E2E، کند و شکننده. تیم تست را دور می‌زند.

**اشکال ۴: تست flaky با retry «حل» شد**

باگ واقعی پنهان شد. قرنطینه کن.

**اشکال ۵: تست کند**

CI ۴۰ دقیقه. توسعه‌دهنده locally اجرا نمی‌کند.

**اشکال ۶: پوشش تست را هدف کردیم**

پوشش ۹۰٪ با تست‌های بی‌معنی. پوشش معیار کیفیت نیست، فقط نشانگر.

### نکات مهم (Tips & Tricks)

- **یک‌بار build، همه‌جا استفاده.**
- **Base image را با digest pin کن.**
- **تست واحد < ۱ دقیقه** برای کل مجموعه.
- **تست flaky را قرنطینه کن**، نه retry.
- **پوشش تست را هدف نکن** — کیفیت تست مهم‌تر از تعداد.
- **تست integration با DB واقعی** برای منطق DB.

### خلاصه فصل

- Build: تکرارپذیر، سریع، ایزوله، قابل کشف.
- یک‌بار build، همه‌جا استفاده.
- هرم تست: unit زیاد، E2E کم.
- تست flaky را قرنطینه کن.
- پوشش تست، معیار کیفیت نیست.
- تست واحد نباید I/O داشته باشد.

## فصل ۲۷: Release و Deploy

### مقدمه

**Release** تصمیم می‌گیرد چه چیزی منتشر شود؛ **Deploy** آن را می‌رساند. جدا کردن این دو، یکی از مهم‌ترین پیشرفت‌های DevOps است.

این فصل نشان می‌دهد چرا و چطور.

### مفاهیم اساسی

**تفکیک Release و Deploy:**

| مفهوم | معنا | سؤال |
|---|---|---|
| **Deploy** | کد را روی محیط بگذار | «آیا می‌توانیم برسانیم؟» |
| **Release** | قابلیت را برای کاربر فعال کن | «آیا باید فعال شود؟» |

**قبل از DevOps**: این دو یکی بودند — deploy = release. یعنی هر deploy، ریسک کاربری داشت.

**بعد از DevOps**: جدا شدند. می‌توانی ۱۰ بار در روز deploy کنی و هیچ قابلیتی را فعال نکنی.

**چهار استراتژی انتشار:**

| استراتژی | توضیح | rollback | ریسک |
|---|---|---|---|
| **Rolling** | تدریجی، نسخه جدید جای قدیم | متوسط | متوسط |
| **Blue-Green** | دو محیط کامل، سوییچ | ✅ فوری | کم |
| **Canary** | درصدی از ترافیک | ✅✅ | ✅ کم |
| **Feature Flag** | کد هست، رفتار خاموش | ✅✅ فوری | ✅✅ |

**ترکیب توصیه‌شده**: Canary + Feature Flag.

### مثال‌های عملی

**Canary — گام به گام:**

```
۰۹:۰۰  deploy نسخه جدید با ۵٪ ترافیک
۰۹:۱۵  بررسی: نرخ خطا 0.1٪ (طبیعی) ✅
۰۹:۱۵  افزایش به ۲۵٪
۰۹:۳۰  بررسی: نرخ خطا 0.2٪ (طبیعی) ✅
۰۹:۳۰  افزایش به ۵۰٪
۰۹:۴۵  بررسی: نرخ خطا 0.3٪ (طبیعی) ✅
۰۹:۴۵  افزایش به ۱۰۰٪
۱۰:۰۰  پایان — نسخه جدید کامل
```

**اگر در گام دوم خطا بالا می‌رفت:**

```
۰۹:۳۰  نرخ خطا 8٪ ❌
۰۹:۳۰  rollback فوری → ترافیک به نسخه قبل
۰۹:۳۱  تأثیر: فقط ۲۵٪ کاربران، ۱۵ دقیقه
```

**مقایسه با deploy همه‌یک‌باره**: تأثیر ۱۰۰٪ کاربران، چند ساعت.

**Feature Flag — چرخه کامل:**

```
۱. کد با flag خاموش merge می‌شود (ریسک صفر)
۲. deploy به production (رفتار عوض نمی‌شود)
۳. فعال‌سازی برای تیم داخلی (dogfooding)
۴. فعال‌سازی برای ۵٪ کاربران
۵. فعال‌سازی برای ۵۰٪
۶. فعال‌سازی برای ۱۰۰٪
۷. حذف flag و کد قدیمی
```

**مزیت**: هر مرحله قابل توقف و بازگشت است، بدون deploy.

**استراتژی انتخاب — درخت تصمیم:**

```
آیا می‌توانی رفتار را با flag کنترل کنی؟
├── بله → Feature Flag (+ Canary)
└── نه ↓
آیا rollback فوری حیاتی است؟
├── بله → Blue-Green یا Canary
└── نه → Rolling
```

**Release checklist (حداقلی):**

```
[ ] artifact همان است که در staging تست شد (digest یکسان)
[ ] migration backward-compatible است
[ ] rollback تست شده است
[ ] متریک/alert برای نسخه جدید آماده است
[ ] تیم در دسترس است (نه جمعه شب)
[ ] برنامه ارتباط با کاربر (اگر لازم)
```

### مقایسه و الگوهای مختلف

**Rolling در برابر Blue-Green:**

| معیار | Rolling | Blue-Green |
|---|---|---|
| منابع | ✅ کم | ❌ ۲× |
| rollback | متوسط | ✅ فوری |
| پیچیدگی | ✅ کم | متوسط |
| مناسب | اکثر | حساس |

**Canary در برابر A/B Testing:**

| معیار | Canary | A/B |
|---|---|---|
| هدف | کاهش ریسک | یادگیری |
| معیار | خطا، latency | رفتار کاربر |
| مدت | دقیقه-ساعت | روز-هفته |

**سه مدل زمان‌بندی انتشار:**

| مدل | مناسب |
|---|---|
| Continuous | SaaS بالغ |
| Scheduled (پنجره) | سازمان با انطباق |
| On-demand | تیم با ریسک‌گریزی |

### اشکال شایع

**اشکال ۱: Release = Deploy**

هر deploy ریسک کاربری دارد. جدا کن.

**اشکال ۲: Canary بدون متریک**

«canary گذاشتیم» ولی نمی‌دانی سالم است یا نه. متریک و آستانه لازم.

**اشکال ۳: Flag بدون حذف**

۱۰۰ flag در کد، هیچ‌کس نمی‌داند کدام فعال است.

**اشکال ۴: Migration ناسازگار**

کد جدید با schema قدیم کار نمی‌کند → rollback غیرممکن.

**راه‌حل: expand-contract:**

```
مرحله ۱ (expand): ستون جدید اضافه کن، هر دو را بنویس
مرحله ۲ (migrate): داده را منتقل کن
مرحله ۳ (contract): ستون قدیم را حذف کن
```

هر مرحله، deploy جدا. در هر لحظه، rollback ممکن است.

**اشکال ۵: deploy جمعه شب**

تیم در دسترس نیست. قاعده: پنجشنبه/جمعه deploy نکن (یا با on-call کامل).

**اشکال ۶: artifact متفاوت در staging و production**

digest را مقایسه کن. باید یکی باشد.

### نکات مهم (Tips & Tricks)

- **Release و Deploy را جدا کن.**
- **Canary با آستانه مشخص** — «اگر خطا > ۱٪، rollback».
- **Feature flag با تاریخ انقضا.**
- **Migration با expand-contract.**
- **digest را مقایسه کن** بین محیط‌ها.
- **rollback را تمرین کن** — نه فقط طراحی.

### خلاصه فصل

- Release (تصمیم) ≠ Deploy (رساندن).
- چهار استراتژی: Rolling، Blue-Green، Canary، Flag.
- Canary + Flag ترکیب توصیه‌شده.
- Migration باید backward-compatible باشد.
- artifact باید یکسان باشد (digest).
- rollback را تمرین کن.

## فصل ۲۸: Operate و Monitor

### مقدمه

این دو مرحله، **نقطه کور** اکثر تیم‌های DevOps هستند. ابزار می‌سازند، deploy می‌کنند، ولی نمی‌دانند در production چه می‌گذرد.

این فصل نشان می‌دهد Operate و Monitor چه معنایی دارند و چطور مالکیت مشترک را ممکن می‌کنند.

### مفاهیم اساسی

**Operate — چهار فعالیت:**

| فعالیت | معنا |
|---|---|
| **نگهداری** | وصله، به‌روزرسانی، ظرفیت |
| **پاسخ به حادثه** | تشخیص، رفع، بازیابی |
| **ظرفیت** | مقیاس، هزینه |
| **تغییر پیکربندی** | تنظیم، feature flag |

**Monitor — چهار سیگنال (Golden Signals):**

| سیگنال | سؤال |
|---|---|
| **Latency** | چقدر طول می‌کشد؟ |
| **Traffic** | چقدر بار داریم؟ |
| **Errors** | چند درصد شکست می‌خورد؟ |
| **Saturation** | چقدر ظرفیت مصرف شده؟ |

این چهار، حداقل لازم برای هر سرویس است.

**تفکیک Monitoring و Observability:**

| معیار | Monitoring | Observability |
|---|---|---|
| سؤال | «آیا خراب است؟» | «چرا خراب است؟» |
| داده | متریک از پیش تعریف‌شده | هر داده، قابل پرسش |
| مناسب | حادثه شناخته‌شده | حادثه ناشناخته |

**نکته**: Monitoring می‌گوید «چیزی خراب است». Observability می‌گوید «چرا». هر دو لازم است.

### مثال‌های عملی

**مالکیت مشترک — on-call:**

```
مدل سنتی:
  Ops تنها on-call است
  Dev شب می‌خوابد
  نتیجه: Ops نمی‌داند کد چطور کار می‌کند، Dev نمی‌داند production چه شکلی است

مدل DevOps:
  چرخه مشترک: Dev + Ops
  Dev یاد می‌گیرد production چه شکلی است
  Ops یاد می‌گیرد کد چطور کار می‌کند
  نتیجه: هر دو بهتر می‌شوند
```

**چرا on-call مشترک مؤثرترین مکانیزم است:**

| اثر | توضیح |
|---|---|
| بازخورد فوری | Dev درد واقعی را حس می‌کند |
| طراحی بهتر | «این کد را طوری بنویسم که شب بیدار نشوم» |
| احترام | Dev می‌فهمد Ops چه فشار دارد |
| دانش | هر دو سیستم را می‌شناسند |

**داشبورد حداقلی هر سرویس:**

```
┌──────────────────────────────────────────────┐
│ سرویس: auth-api                              │
├──────────────────────────────────────────────┤
│ Latency p50: 45ms   p95: 180ms   p99: 400ms  │
│ Errors: 0.2٪  (SLO: < 1٪)                   │
│ Traffic: 1.2k req/s                          │
│ Saturation: CPU 45٪  Memory 62٪              │
├──────────────────────────────────────────────┤
│ SLO: 99.9٪ — مصرف‌شده: 12٪ از بودجه          │
│ آخرین deploy: ۲ ساعت پیش (v1.4.2)            │
│ حادثه باز: ۰                                  │
└──────────────────────────────────────────────┘
```

**این داشبورد، حداقل است.** اگر نداری، کور هستی.

**پاسخ به حادثه — چهار گام:**

| گام | هدف | زمان |
|---|---|---|
| **تشخیص** | alert فعال شد | خودکار |
| **کاهش اثر** | rollback، flag off، scale up | دقیقه |
| **ریشه‌یابی** | چرا؟ | ساعت |
| **یادگیری** | postmortem | روز |

**نکته حیاتی**: **اول کاهش اثر، بعد ریشه‌یابی.** کاربران نباید منتظر بمانند تا تو بفهمی چرا.

### مقایسه و الگوهای مختلف

**سه مدل on-call:**

| مدل | مزیت | عیب |
|---|---|---|
| Ops-only | ✅ تمرکز | ❌ دیوار |
| Dev-only | ✅ مالکیت | ❌ فرسودگی |
| مشترک | ✅✅ | نیاز به آموزش |

**سه سطح alerting:**

| سطح | کانال | آستانه |
|---|---|---|
| Page (فوری) | تلفن | SLO در خطر |
| Notify | Slack | روند نگران‌کننده |
| Log | داشبورد | اطلاعاتی |

**قاعده**: فقط چیزهایی که **الان باید اقدام کنی** page می‌شوند.

**سه مدل مالکیت production:**

| مدل | توضیح |
|---|---|
| You build it, you run it | ✅ کامل |
| You build it, we run it | ❌ دیوار |
| You build it, platform runs it | ✅ مدرن (فایل ۱۵) |

### اشکال شایع

**اشکال ۱: Dev به production دسترسی ندارد**

نمی‌تواند دیباگ کند، پس نمی‌فهمد. حداقل: خواندن لاگ و متریک.

**اشکال ۲: alert برای همه‌چیز**

۵۰۰ alert در روز = همه ignore. فقط SLO و خطای بحرانی.

**اشکال ۳: ریشه‌یابی قبل از کاهش اثر**

«بگذار بفهمم چرا» در حالی که سرویس خراب است. اول rollback.

**اشکال ۴: داشبورد بدون owner**

هر کس ساخته، هیچ‌کس نگه‌داری نمی‌کند، کهنه می‌شود.

**اشکال ۵: on-call بدون آموزش**

توسعه‌دهنده تنها، بدون runbook = شب وحشتناک.

**اشکال ۶: Monitoring بدون Observability**

می‌دانی خطا هست، نمی‌دانی چرا. لاگ و trace لازم.

### نکات مهم (Tips & Tricks)

- **چهار سیگنال طلایی** را برای هر سرویس داشته باش.
- **on-call مشترک** — بهترین سرمایه‌گذاری فرهنگی.
- **اول کاهش اثر، بعد ریشه‌یابی.**
- **alert فقط برای اقدام فوری.**
- **runbook برای هر alert** — وگرنه alert بی‌فایده است.
- **Dev باید لاگ production را ببیند.**

### خلاصه فصل

- Operate: نگهداری، حادثه، ظرفیت، پیکربندی.
- Monitor: چهار سیگنال طلایی.
- Monitoring می‌گوید «خراب است»، Observability می‌گوید «چرا».
- on-call مشترک، مؤثرترین مکانیزم مالکیت.
- اول کاهش اثر، بعد ریشه‌یابی.
- alert فقط برای اقدام فوری.

## فصل ۲۹: حلقه بازخورد به Plan

### مقدمه

چرخه با Monitor تمام نمی‌شود؛ با **بازگشت به Plan** کامل می‌شود. این حلقه، تفاوت بین «تحویل دادن» و «یاد گرفتن» است.

این فصل آخرین مرحله — و مهم‌ترین — را می‌سازد.

### مفاهیم اساسی

**سه نوع بازخورد از production:**

| نوع | منبع | سؤال |
|---|---|---|
| **فنی** | متریک، لاگ، حادثه | سیستم سالم است؟ |
| **محصول** | رفتار کاربر، تبدیل | ارزش تولید شد؟ |
| **سازمانی** | DORA، رضایت تیم | فرآیند خوب است؟ |

**نکته**: اکثر تیم‌ها فقط فنی را می‌بینند. محصول و سازمانی را فراموش می‌کنند.

**چرخه یادگیری کامل:**

```
Plan → ... → Monitor
  ▲              │
  │              ▼
  └───── تحلیل ──┘
         (چه چیزی یاد گرفتیم؟)
```

**بدون این مرحله**: همان قابلیت اشتباه دوباره ساخته می‌شود، همان باگ برمی‌گردد.

### مثال‌های عملی

**جلسه ماهانه — دستور کار ۴۵ دقیقه:**

```
۱. متریک‌های DORA (۱۰ دقیقه)
   - Lead Time، Deploy Freq، CFR، Recovery
   - روند نسبت به ماه قبل

۲. حادثه‌ها (۱۰ دقیقه)
   - چند حادثه؟ کدام تکرار شد؟
   - اقدامات postmortem انجام شد؟

۳. بازخورد محصول (۱۰ دقیقه)
   - قابلیت‌های منتشرشده: استفاده شد؟
   - چه چیزی باید متوقف شود؟

۴. یک اقدام (۱۰ دقیقه)
   - بزرگ‌ترین مشکل چیست؟
   - یک اقدام با مالک و مهلت

۵. مرور اقدام ماه قبل (۵ دقیقه)
   - انجام شد؟ اثر داشت؟
```

**قاعده**: حداکثر **یک اقدام** در ماه. تمرکز، مؤثرتر از فهرست بلند است.

**مثال واقعی — بازخورد محصول:**

```
قابلیت منتشرشده: "تنظیمات اعلان"
متریک: ۲٪ کاربران از آن استفاده کردند
تحلیل:
  - کاربران نمی‌دانند وجود دارد؟
  - یا نیاز ندارند؟
  - یا پیدا نمی‌کنند؟

اقدام: ۲ هفته بعد، لینک در ایمیل اعلان
نتیجه: استفاده از ۲٪ به ۱۸٪

درس: مشکل در کشف بود، نه در قابلیت
```

**این درس، فقط با بازخورد محصول به دست می‌آید** — نه با متریک فنی.

**بازخورد سازمانی — پرسشنامه تیم:**

```
۱. آیا می‌توانیم بدون مانع deploy کنیم؟          (۱-۵)
۲. آیا ابزارها کار ما را آسان می‌کنند؟           (۱-۵)
۳. آیا از کارمان یاد می‌گیریم؟                   (۱-۵)
۴. آیا در تصمیم‌ها شریک هستیم؟                   (۱-۵)
۵. آیا on-call منصفانه است؟                      (۱-۵)
۶. آیا برای بهبود وقت داریم؟                     (۱-۵)

امتیاز < ۳ در هر مورد = سیگنال هشدار
```

### مقایسه و الگوهای مختلف

**سه مدل بازخورد:**

| مدل | فرکانس | عمق |
|---|---|---|
| داشبورد پیوسته | لحظه‌ای | کم |
| جلسه ماهانه | ماهانه | متوسط |
| بازبینی فصلی | فصلی | ✅ عمیق |

**توصیه**: هر سه، با اهداف متفاوت.

**سه دام در بازخورد:**

| دام | نتیجه |
|---|---|
| فقط متریک فنی | محصول اشتباه، سیستم سالم |
| فقط بازخورد کاربر | سیستم شکننده |
| هیچ‌کدام | حرکت کور |

**Vanity در برابر Actionable (یادآوری):**

| Vanity | Actionable |
|---|---|
| «۱۰۰۰ بازدید» | «نرخ تکمیل ثبت‌نام» |
| «۹۹.۹٪ آپ‌تایم» | «SLO مصرف‌شده» |

### اشکال شایع

**اشکال ۱: چرخه بدون حلقه**

Plan تا Monitor، بدون بازگشت. همان اشتباه تکرار می‌شود.

**اشکال ۲: بازخورد بدون اقدام**

«کاربران شکایت کردند» بدون تغییر. بدتر از ندانستن.

**اشکال ۳: اقدام زیاد**

۱۰ اقدام در ماه، صفر انجام‌شده. یک اقدام، انجام‌شده.

**اشکال ۴: فقط بازخورد فنی**

سیستم سالم، محصول بی‌استفاده. ارزش صفر.

**اشکال ۵: جلسه بدون داده**

«حس می‌کنم بهتر شدیم» — عدد بیاور.

**اشکال ۶: بازخورد از تیم گرفته نشد**

تیم ناراضی، فرسوده، ولی متریک‌ها خوب. فروپاشی نزدیک است.

### نکات مهم (Tips & Tricks)

- **جلسه ماهانه ۴۵ دقیقه‌ای** — ثابت، در تقویم.
- **یک اقدام در ماه** — با مالک و مهلت.
- **بازخورد محصول را جدی بگیر** — متریک فنی کافی نیست.
- **تیم را بپرس** — رضایت، پیش‌بین قوی ماندگاری است.
- **اقدام ماه قبل را مرور کن** — وگرنه فراموش می‌شود.
- **داده بیاور، نه حس.**

### خلاصه فصل

- سه نوع بازخورد: فنی، محصول، سازمانی.
- چرخه بدون حلقه، تکرار اشتباه است.
- جلسه ماهانه: DORA، حادثه، محصول، یک اقدام.
- حداکثر یک اقدام در ماه.
- بازخورد محصول را فراموش نکن.
- داده بیاور، نه حس.
