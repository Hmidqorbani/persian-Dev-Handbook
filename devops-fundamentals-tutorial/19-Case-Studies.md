## فصل ۱۰۳: چطور مطالعه موردی بخوانیم

### مقدمه

مطالعه موردی می‌تواند الهام‌بخش باشد یا گمراه‌کننده. تفاوت در **نحوه خواندن** است.

این فصل چارچوب خواندن انتقادی را می‌آورد — چون بدون آن، «Netflix این‌طور می‌کند» بهانه می‌شود، نه درس.

### مفاهیم اساسی

**چهار سؤال برای هر مطالعه موردی:**

| سؤال | چرا |
|---|---|
| **context چه بود؟** | مقیاس، صنعت، زمان |
| **چه مشکلی حل می‌کردند؟** | نه «چه ابزاری» |
| **چه چیزی قابل انتقال است؟** | اصل، نه ابزار |
| **چه چیزی غیرقابل انتقال است؟** | مقیاس، بودجه، استعداد |

**نکته**: بیشتر شکست‌ها از **کپی ابزار** بدون **context** می‌آید.

**سه سطح درس:**

| سطح | مثال | قابلیت انتقال |
|---|---|---|
| **اصل** | «تغییر کوچک، ریسک کم» | ✅✅ |
| **روش** | «canary deploy» | ✅ |
| **ابزار** | «Spinnaker» | ❌ |

**نکته**: اصل را بگیر، ابزار را نه.

**هشدار «بقای بازمانده»:**

```
می‌بینیم Netflix موفق شد و X کار می‌کند
نمی‌بینیم ۱۰۰ شرکت که X را کردند و شکست خوردند
```

**نکته**: موفقیت‌ها دیده می‌شوند، شکست‌ها نه. محتاط باش.

### مثال‌های عملی

**تحلیل یک ادعا:**

```
ادعا: "Amazon هر ۱۱.۶ ثانیه deploy می‌کند"

سؤالات:
۱. این عدد برای چه چیزی است؟ (deploy به production، همه سرویس‌ها)
۲. چند سرویس؟ (هزاران)
۳. هر deploy چقدر تغییر است؟ (کوچک)
۴. آیا این هدف ماست؟ (شاید نه)

درس قابل انتقال: تغییر کوچک و مکرر، ریسک را کم می‌کند
درس غیرقابل انتقال: عدد ۱۱.۶ ثانیه
```

**قالب تحلیل:**

```markdown
## [شرکت]

### Context
- اندازه: ...
- صنعت: ...
- زمان تحول: ...
- وضعیت شروع: ...

### مشکل
- ...

### چه کردند
- ...

### نتیجه (با عدد)
- ...

### چه چیزی قابل انتقال است
- ...

### چه چیزی قابل انتقال نیست
- ...

### اگر ما بخواهیم اعمال کنیم
- اولین قدم: ...
```

### مقایسه و الگوهای مختلف

**سه نوع مطالعه موردی:**

| نوع | منبع | اعتبار |
|---|---|---|
| **مستند رسمی** | SRE Book، blog شرکت | ✅ |
| **کتاب** | Accelerate، Phoenix Project | ✅✅ |
| **بازاریابی** | case study فروشنده | ❌ |

**نکته**: case study فروشنده، **ابزار** را می‌فروشد، نه درس.

**سه سطح تعمیم:**

| سطح | خطر |
|---|---|
| تعمیم کامل | ❌ زیاد |
| بدون تعمیم | ❌ بی‌فایده |
| ✅ تعمیم اصول | ✅ |

**مقایسه با بنچمارک:**

| معیار | مطالعه موردی | بنچمارک |
|---|---|---|
| عمق | ✅✅ | ❌ |
| مقایسه | ❌ | ✅ |
| مناسب | یادگیری | ارزیابی |

### اشکال شایع

**اشکال ۱: کپی کورکورانه**

«Google SRE دارد، ما هم باید». context متفاوت.

**اشکال ۲: نادیده گرفتن مقیاس**

Netflix با ۲۰۰ میلیون کاربر. تو با ۲۰۰۰.

**اشکال ۳: بقای بازمانده**

فقط موفقیت‌ها را دیدیم.

**اشکال ۴: نادیده گرفتن زمان**

تحول ۵ سال طول کشید، نه ۵ ماه.

**اشکال ۵: تمرکز روی ابزار**

«Spinnaker» — به‌جای اصل.

**اشکال ۶: نادیده گرفتن شکست‌ها**

هر موفقیت، شکست‌های زیادی داشت.

### نکات مهم (Tips & Tricks)

- **چهار سؤال** بپرس.
- **اصل را بگیر، ابزار را نه.**
- **مقیاس را ببین.**
- **بقای بازمانده را یادآوری کن.**
- **case study فروشنده را باور نکن.**
- **«اولین قدم ما چه می‌شود؟»** بپرس.

### خلاصه فصل

- چهار سؤال: context، مشکل، قابل انتقال، غیرقابل انتقال.
- سه سطح درس: اصل، روش، ابزار.
- اصل را بگیر.
- بقای بازمانده را در نظر بگیر.
- مقیاس و زمان را ببین.
- case study فروشنده، تبلیغ است.

## فصل ۱۰۴: Amazon — از دو پیتزا تا API

### mمقدمه

Amazon یکی از بنیان‌گذاران DevOps است. داستانش درباره **ساختار سازمانی** و **API-محوری** است.

### Context

| مورد | مقدار |
|---|---|
| اندازه | صدها هزار کارمند |
| صنعت | خرده‌فروشی، ابر |
| زمان تحول | ۲۰۰۲-۲۰۱۰ |
| وضعیت شروع | monolith، deploy کند |

### مشکل

```
۲۰۰۰: monolith بزرگ، همه تیم‌ها روی یک کدبیس
  - هر تغییر: هماهنگی گسترده
  - deploy: هفته‌ها
  - scaling: سخت
```

### چه کردند

**۱) قانون دو پیتزا (۲۰۰۲)**

```
تیم نباید بزرگ‌تر از دو پیتزا باشد (۵-۹ نفر)
  ↓
تیم‌های کوچک، خودمختار
  ↓
هر تیم، مالک یک سرویس
```

**۲) API-محوری (Jeff Bezos، ۲۰۰۲)**

> «همه تیم‌ها باید از طریق API ارتباط برقرار کنند. هیچ ارتباط دیگری مجاز نیست.»

```
نتیجه:
  - هر تیم، یک سرویس با API
  - ارتباط از طریق interface، نه کد مشترک
  - تیم‌ها می‌توانند مستقل deploy کنند
```

**۳) «You build it, you run it» (Werner Vogels، ۲۰۰۶)**

```
هر تیم:
  - سرویس را می‌سازد
  - deploy می‌کند
  - on-call است
  ↓
نتیجه: مالکیت کامل، بازخورد فوری
```

**۴) Automate everything**

```
همه‌چیز خودکار:
  - infrastructure (EC2، S3)
  - deploy (Apollo)
  - testing
```

### نتیجه

| متریک | قبل | بعد |
|---|---|---|
| Deploy frequency | ماهانه | هر ۱۱.۶ ثانیه (همه سرویس‌ها) |
| تعداد سرویس | ۱ | هزاران |
| تیم | بزرگ | هزاران تیم کوچک |
| زمان deploy | هفته | دقیقه |

**نکته**: عدد «۱۱.۶ ثانیه» برای **همه سرویس‌ها** با هم است — نه یک سرویس.

### چه چیزی قابل انتقال است

| اصل | چرا |
|---|---|
| **تیم کوچک** | ✅ هماهنگی کم |
| **API-محوری** | ✅ استقلال |
| **مالکیت کامل** | ✅ بازخورد |
| **خودکارسازی** | ✅ مقیاس |

### چه چیزی قابل انتقال نیست

| مورد | چرا |
|---|---|
| عدد ۱۱.۶ ثانیه | مقیاس متفاوت |
| ساختار هزاران تیم | نیاز به ابزار و فرهنگ |
| بودجه AWS | متفاوت |
| استخدام بهترین‌ها | متفاوت |

### درس کلیدی

> **ساختار سازمانی، معماری را تعیین می‌کند.**

Amazon ابتدا **سازمان** را عوض کرد (تیم کوچک، API)، بعد معماری خودش آمد.

## فصل ۱۰۵: Netflix — فرهنگ آزادی و مسئولیت

### mمقدمه

Netflix داستان **فرهنگ** است: آزادی زیاد، مسئولیت زیاد. و ابزارهایی که برای مقیاس ساخته شد.

### Context

| مورد | مقدار |
|---|---|
| اندازه | ~۱۳٬۰۰۰ کارمند |
| صنعت | استریم |
| زمان تحول | ۲۰۰۸-۲۰۱۵ |
| وضعیت شروع | datacenter، monolith |

### مشکل

```
۲۰۰۸: انتقال به ابر (AWS)
  - monolith نمی‌تواند مقیاس دهد
  - datacenter گران
  - نیاز به انعطاف
```

### چه کردند

**۱) فرهنگ — «Freedom and Responsibility»**

```
اسلاید معروف فرهنگ Netflix:
  - Judge by impact, not hours
  - Adequate performance gets a generous severance
  - No approval needed for decisions
  - Context, not control
```

**نکته**: «Context, not control» — رهبر context می‌دهد، تصمیم را به تیم می‌سپارد.

**۲) Chaos Engineering — Chaos Monkey**

```
ایده: اگر خرابی اجتناب‌ناپذیر است، برایش آماده شو
    ↓
Chaos Monkey: تصادفی instanceها را می‌کشد
    ↓
نتیجه: تیم‌ها سیستم مقاوم می‌سازند
```

**نکته**: این ابزار، **فرهنگ** را تغییر داد: «خرابی، بخشی از کار است».

**۳) میکروسرویس**

```
monolith → صدها میکروسرویس
  - هر تیم، چند سرویس
  - deploy مستقل
  - fault isolation
```

**۴) ابزارهای ساخته‌شده**

| ابزار | کار |
|---|---|
| **Spinnaker** | deploy چند‌ابری |
| **Chaos Monkey** | تزریق خرابی |
| **Hystrix** | circuit breaker |
| **Eureka** | service discovery |

**نکته**: این‌ها را **ساختند** چون چیزی نبود. تو ممکن است نیاز نداشته باشی.

### نتیجه

| متریک | قبل | بعد |
|---|---|---|
| Deploy frequency | هفتگی | هزاران در روز |
| Availability | ۹۹٪ | ۹۹.۹۹٪ |
| زمان بازیابی | ساعت | دقیقه |
| Datacenter | خودشان | AWS |

### چه چیزی قابل انتقال است

| اصل | چرا |
|---|---|
| **Context, not control** | ✅ مقیاس‌پذیر |
| **Chaos engineering** | ✅ آمادگی |
| **مالکیت سرویس** | ✅ |
| **Fault isolation** | ✅ |

### چه چیزی قابل انتقال نیست

| مورد | چرا |
|---|---|
| «Generous severance» | فرهنگ و قوانین متفاوت |
| Spinnaker | ابزار، نه اصل |
| بودجه AWS | متفاوت |
| استخدام top-of-market | متفاوت |

### درس کلیدی

> **آزادی بدون مسئولیت، هرج‌ومرج است. مسئولیت بدون آزادی، بوروکراسی.**

Netflix هر دو را با هم داد — و فرهنگ را صریح تعریف کرد.

## فصل ۱۰۶: Etsy — تحول تدریجی

### mمقدمه

Etsy داستان **تحول تدریجی و انسانی** است. برخلاف Amazon و Netflix، Etsy یک شرکت متوسط بود که با **فرهنگ** شروع کرد، نه ابزار.

### Context

| مورد | مقدار |
|---|---|
| اندازه | ~۱۰۰۰ کارمند |
| صنعت | بازار آنلاین صنایع دستی |
| زمان تحول | ۲۰۰۹-۲۰۱۲ |
| وضعیت شروع | deploy دستی، ۲ بار در سال |

### مشکل

```
۲۰۰۹:
  - deploy: ۲ بار در سال، ۱۲ ساعت، شبانه
  - همه در یک اتاق، استرس
  - ۲۰٬۰۰۰ خط تغییر در هر deploy
  - باگ زیاد
```

**نکته**: این وضعیت برای یک شرکت ۱۰۰۰ نفره، **فاجعه** بود.

### چه کردند

**۱) Chad Dickerson به‌عنوان CTO**

```
اولین کار: با تیم‌ها حرف زد
کشف: مشکل فنی نیست، فرهنگ است
```

**۲) «Continuous Deployment Day»**

```
ایده: یک روز، فقط deploy تمرین کنیم
    ↓
اولین بار: ۱ deploy در روز
    ↓
هدف: ۲۵ deploy در روز
```

**نکته**: با **تمرین** شروع کردند، نه ابزار. ابزار بعد آمد.

**۳) کاهش batch**

```
۲۰٬۰۰۰ خط در هر deploy
    ↓
تغییرات کوچک، مکرر
    ↓
نتیجه: deploy سریع‌تر، ریسک کمتر
```

**۴) فرهنگ — «Blameless Postmortem»**

```
اولین postmortem‌ها با ترس
    ↓
CTO: "چه چیزی در سیستم خراب بود؟"
    ↓
نتیجه: صداقت، یادگیری
```

**۵) ابزار بعد از فرهنگ**

```
Deployinator (ابزار داخلی، ساده)
  - یک دکمه
  - همه می‌توانند بزنند
```

**نکته**: ابزار **ساده** بود — یک دکمه. ولی **فرهنگ** تغییر کرده بود.

### نتیجه

| متریک | ۲۰۰۹ | ۲۰۱۲ |
|---|---|---|
| Deploy frequency | ۲/سال | ۵۰+/روز |
| زمان deploy | ۱۲ ساعت | ۵ دقیقه |
| اندازه تغییر | ۲۰٬۰۰۰ خط | کوچک |
| حادثه | زیاد | کم |
| استرس تیم | بالا | پایین |

### چه چیزی قابل انتقال است

| اصل | چرا |
|---|---|
| **تمرین قبل از ابزار** | ✅✅ |
| **کاهش batch** | ✅✅ |
| **postmortem بدون سرزنش** | ✅ |
| **ابزار ساده** | ✅ |

### چه چیزی قابل انتقال نیست

| مورد | چرا |
|---|---|
| Deployinator | ابزار ساده، خودت بساز |
| اندازه تیم | متفاوت |
| فرهنگ اولیه | متفاوت |

### درس کلیدی

> **تحول از فرهنگ شروع می‌شود، ولی با تمرین عملی تثبیت می‌شود.**

Etsy نشان داد که لازم نیست Google باشی.

## فصل ۱۰۷: Google، Flickr و دیگران

### Google — SRE

**Context:**

| مورد | مقدار |
|---|---|
| اندازه | صدها هزار کارمند |
| صنعت | جستجو، ابر |
| شروع SRE | ۲۰۰۳ |

**مشکل:**

```
سیستم‌های بزرگ، پیچیده
  - on-call فرسوده
  - ops دستی، غیرقابل مقیاس
  - نیاز به مهندسی، نه اپراتوری
```

**چه کردند:**

| اصل | توضیح |
|---|---|
| **SRE = مهندسی** | کد بنویس، نه تیکت |
| **SLO** | هدف عددی برای پایداری |
| **Error Budget** | بودجه خطا |
| **Toil < ۵۰٪** | نصف وقت برای بهبود |
| **Blameless postmortem** | یادگیری |

**نتیجه:** SRE به استاندارد صنعت تبدیل شد.

**قابل انتقال:** SLO، Error Budget، toil budget، postmortem.

**غیرقابل انتقال:** مقیاس، بودجه، استعداد.

---

### Flickr — اولین جرقه

**Context:**

| مورد | مقدار |
|---|---|
| اندازه | ~۵۰ مهندس |
| صنعت | اشتراک عکس |
| زمان | ۲۰۰۹ |

**مشکل:**

```
deploy: هفته‌ای یک‌بار، با استرس
  - Dev و Ops جدا
  - محیط متفاوت
```

**چه کردند (سخنرانی معروف ۲۰۰۹):**

| عامل | توضیح |
|---|---|
| **محیط یکسان** | dev شبیه prod |
| **خودکارسازی** | deploy خودکار |
| **اعتماد** | Dev و Ops یک تیم |
| **تغییر کوچک** | batch کوچک |
| **rollback آسان** | بازگشت سریع |

**نتیجه:** ۱۰+ deploy در روز، در سال ۲۰۰۹.

**قابل انتقال:** پنج عامل — همه با هم.

**غیرقابل انتقال:** تقریباً هیچ — چون ابزار خاصی نداشتند.

## فصل ۱۰۸: درس‌های مشترک و آنچه قابل کپی نیست

### مقدمه

این فصل جمع‌بندی است: چه چیزی در همه موارد مشترک است، و چه چیزی **واقعاً** قابل کپی نیست.

### پنج درس مشترک

**۱) ساختار سازمانی اول**

| شرکت | چه کردند |
|---|---|
| Amazon | تیم کوچک، API |
| Netflix | context not control |
| Etsy | CTO با تیم‌ها حرف زد |
| Google | SRE به‌عنوان تیم مهندسی |

**درس**: قبل از ابزار، **سازمان** را ببین.

**۲) تغییر کوچک، ریسک کم**

| شرکت | قبل | بعد |
|---|---|---|
| Amazon | batch بزرگ | کوچک |
| Etsy | ۲۰٬۰۰۰ خط | کوچک |
| Netflix | هفتگی | پیوسته |

**درس**: batch کوچک، **همه‌جا** کار می‌کند.

**۳) فرهنگ قبل از ابزار (ولی با تمرین)**

| شرکت | ترتیب |
|---|---|
| Etsy | فرهنگ → تمرین → ابزار |
| Netflix | فرهنگ صریح → ابزار |
| Amazon | ساختار → API → ابزار |

**درس**: ابزار بدون فرهنگ، دور زده می‌شود. فرهنگ بدون تمرین، شعار است.

**۴) زمان: ۳-۵ سال**

| شرکت | مدت |
|---|---|
| Amazon | ۸ سال |
| Netflix | ۷ سال |
| Etsy | ۳ سال |
| Google SRE | ۵+ سال |

**درس**: هیچ‌کدام ۶ ماهه نبود. صبر، بخشی از روش است.

**۵) اندازه‌گیری از روز اول**

| شرکت | متریک |
|---|---|
| Amazon | deploy frequency |
| Netflix | availability، MTTR |
| Etsy | deploy frequency، حادثه |
| Google | SLO |

**درس**: بدون متریک، نمی‌دانی موفق شدی.

### آنچه قابل کپی نیست

**۱) مقیاس**

```
Netflix: ۲۰۰M کاربر، هزاران سرویس
تو: ۱۰k کاربر، ۵ سرویس

ابزار Netflix برای تو overkill است
```

**۲) استعداد**

```
Amazon: بهترین مهندسان جهان
تو: تیم متوسط، با انگیزه

راه‌حل: ساده‌تر، مستندتر، خودکارتر
```

**۳) بودجه**

```
Google: بودجه نامحدود برای SRE
تو: محدود

راه‌حل: شروع کوچک، ROI نشان بده
```

**۴) فرهنگ اولیه**

```
Netflix: فرهنگ خاص از روز اول
تو: فرهنگ متفاوت

راه‌حل: از فرهنگ خودت شروع کن، نه کپی
```

**۵) صنعت**

```
Capital One: regulated (finance)
تو: شاید SaaS

محدودیت‌ها متفاوت
```

### چه چیزی **واقعاً** قابل کپی است

| اصل | چرا |
|---|---|
| **تغییر کوچک** | ✅ جهانی |
| **مالکیت مشترک** | ✅ جهانی |
| **بازخورد سریع** | ✅ جهانی |
| **postmortem بدون سرزنش** | ✅ جهانی |
| **متریک** | ✅ جهانی |
| **SLO** | ✅ جهانی |
| **خودکارسازی تکراری** | ✅ جهانی |

**نکته**: این هفت مورد، در **هر** مقیاس و صنعتی کار می‌کنند.

### جدول نهایی — چه چیزی برای چه کسی

| اندازه سازمان | اولویت |
|---|---|
| < ۲۰ نفر | CI/CD + تغییر کوچک |
| ۲۰-۱۰۰ | + متریک + postmortem |
| ۱۰۰-۵۰۰ | + SLO + platform پایه |
| ۵۰۰+ | + team topologies + SRE |

**نکته**: از سطح خودت شروع کن، نه از سطح Netflix.

### اشکال شایع

**اشکال ۱: «Netflix این‌طور می‌کند»**

مقیاس متفاوت. اصول را بگیر.

**اشکال ۲: کپی ابزار**

Spinnaker برای ۵ سرویس = overkill.

**اشکال ۳: انتظار ۶ ماه**

۳-۵ سال. صبر.

**اشکال ۴: نادیده گرفتن فرهنگ**

ابزار بدون فرهنگ، دور زده می‌شود.

**اشکال ۵: بدون متریک**

نمی‌دانی موفق شدی.

**اشکال ۶: شروع از سطح بالا**

Netflix-level از روز اول = شکست.

### نکات مهم (Tips & Tricks)

- **پنج درس مشترک** را به خاطر بسپار.
- **هفت اصل جهانی** را کپی کن.
- **مقیاس خودت** را ببین.
- **۳-۵ سال** صبر.
- **از سطح خودت** شروع کن.
- **متریک از روز اول.**

### خلاصه فصل

- پنج درس: ساختار، batch کوچک، فرهنگ+تمرین، زمان، متریک.
- پنج چیز غیرقابل کپی: مقیاس، استعداد، بودجه، فرهنگ، صنعت.
- هفت اصل جهانی.
- جدول اولویت بر اساس اندازه.
- از سطح خودت شروع کن.
- صبر ۳-۵ سال.
