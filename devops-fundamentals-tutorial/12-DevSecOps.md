## فصل ۶۳: Shift Left — امنیت چپ‌گرا

### مقدمه

در مدل سنتی، تیم امنیت در **انتهای** چرخه می‌آید: یک گزارش ۸۰ صفحه‌ای می‌دهد و تیم توسعه باید سه ماه کار را بازبینی کند. نتیجه: یا نادیده گرفته می‌شود یا انتشار را ماه‌ها عقب می‌اندازد.

**Shift Left** یعنی امنیت را به سمت چپ خط زمان ببریم — همان‌جا که کد نوشته می‌شود.

### مفاهیم اساسی

**خط زمان و هزینه:**

```
Plan → Code → Build → Test → Release → Deploy → Operate
  ↑      ↑       ↑       ↑        ↑
  ارزان‌تر ─────────────────────────────► گران‌تر
```

| مرحله کشف | هزینه نسبی رفع |
|---|---|
| طراحی | ۱× |
| کدنویسی | ۶× |
| CI | ۱۵× |
| staging | ۳۰× |
| production | ۱۰۰× |

**نکته**: امنیت در production، ۱۰۰ برابر گران‌تر است. و علاوه بر هزینه، **اعتماد** هم از دست می‌رود.

**سه دلیل شکست مدل سنتی:**

| دلیل | توضیح |
|---|---|
| **دیر است** | کشف بعد از ساخت |
| **گلوگاه است** | تیم امنیت کوچک، تقاضا زیاد |
| **خصمانه است** | «شما اشتباه کردید» |

**سه اصل Shift Left:**

| اصل | معنا |
|---|---|
| **خودکار** | امنیت در pipeline، نه جلسه |
| **سریع** | بازخورد در دقیقه |
| **آموزشی** | «چطور رفع کنم»، نه فقط «اشتباه است» |

### مثال‌های عملی

**مقایسه دو مدل:**

**مدل سنتی:**
```
توسعه ۳ ماه → QA ۲ هفته → تیم امنیت ۳ هفته → گزارش
    ↓
"۴۷ آسیب‌پذیری، ۱۲ مورد بحرانی"
    ↓
توسعه ۲ ماه رفع → بازبینی امنیت ۲ هفته
    ↓
انتشار: ۶ ماه تأخیر
```

**مدل Shift Left:**
```
هر commit → اسکن خودکار (۲ دقیقه)
    ↓
"۱ آسیب‌پذیری بحرانی در src/auth.py:42 — SQL injection"
    ↓
رفع در ۱۰ دقیقه (همان روز)
    ↓
انتشار: بدون تأخیر
```

**تفاوت**: ۱۰ دقیقه در برابر ۶ ماه.

**چهار لایه امنیت در pipeline:**

| لایه | ابزار | زمان |
|---|---|---|
| **کد** | SAST، lint امنیتی | ۱-۳ دقیقه |
| **Dependency** | SCA | ۱ دقیقه |
| **Artifact** | Container scan، SBOM | ۲-۳ دقیقه |
| **اپ زنده** | DAST | ۱۰-۶۰ دقیقه |

**نکته**: هر لایه، مرحله متفاوتی از زنجیره را پوشش می‌دهد. هیچ‌کدام کافی نیست.

**بازخورد امنیتی خوب در برابر بد:**

```
❌ بد:
  [HIGH] CWE-89 detected in src/auth.py

✅ خوب:
  [HIGH] SQL Injection در src/auth.py:42
  کد: cursor.execute(f"SELECT * FROM users WHERE name='{name}'")
  مشکل: ورودی کاربر مستقیم در query
  رفع: از پارامتر استفاده کن:
    cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
  مرجع: https://owasp.org/Top10/A03_2021-Injection/
```

**تفاوت**: دومی در ۱۰ دقیقه رفع می‌شود، اولی در ۱ ساعت جستجو.

### مقایسه و الگوهای مختلف

**Shift Left در برابر Shield Right:**

| معیار | Shift Left | Shield Right |
|---|---|---|
| تمرکز | جلوگیری | تشخیص و پاسخ |
| مثال | SAST | WAF، SIEM |
| مناسب | ✅ پایه | مکمل |

**نکته**: هر دو لازم. Shift Left تنها کافی نیست (کد همیشه باگ دارد).

**سه مدل تیم امنیت:**

| مدل | توضیح | نتیجه |
|---|---|---|
| Gatekeeper | تأیید نهایی | ❌ گلوگاه |
| Consulting | مشاوره | ✅ بهتر |
| ✅ Embedded | security champion در تیم | ✅✅ |

**«Security Champion» — مؤثرترین مدل:**

```
هر تیم یک نفر:
  - آموزش امنیت می‌بیند
  - اولین مرجع امنیتی تیم است
  - با تیم امنیت مرکزی ارتباط دارد
  - ۲۰٪ وقتش برای امنیت

مزیت: مقیاس‌پذیر، بدون گلوگاه
```

**سه سطح بلوغ:**

| سطح | ویژگی |
|---|---|
| ۱ | اسکن در انتها، دستی |
| ۲ | اسکن خودکار در CI |
| ۳ | ✅ امنیت در طراحی، champion، SLA |

### اشکال شایع

**اشکال ۱: اسکن بدون triage**

۱۰۰۰ یافته، هیچ‌کس نگاه نمی‌کند. نویز = بی‌اعتمادی.

**اشکال ۲: امنیت به‌عنوان دروازه**

تیم امنیت همه MRها را تأیید می‌کند. گلوگاه.

**اشکال ۳: بازخورد مبهم**

«CWE-89 detected» — توسعه‌دهنده نمی‌داند چه کند.

**اشکال ۴: اسکن کند**

۳۰ دقیقه در هر MR. تیم دور می‌زند.

**اشکال ۵: امنیت فقط در release**

کشف دیر، رفع گران.

**اشکال ۶: تیم امنیت جدا**

«ما امنیت را به تیم امنیت سپردیم» — دیوار جدید.

### نکات مهم (Tips & Tricks)

- **چهار لایه، همه لازم.**
- **بازخورد قابل اقدام** — کد، مشکل، رفع.
- **security champion** در هر تیم.
- **اسکن سریع** — < ۳ دقیقه.
- **triage هفتگی** — وگرنه نویز.
- **Shift Left + Shield Right** با هم.

### خلاصه فصل

- Shift Left: امنیت زودتر، ارزان‌تر.
- هزینه رفع در production ۱۰۰ برابر است.
- چهار لایه: کد، dependency، artifact، اپ زنده.
- بازخورد باید قابل اقدام باشد.
- security champion مقیاس‌پذیرترین مدل است.
- Shift Left تنها کافی نیست.

## فصل ۶۴: امنیت به‌عنوان کد

### مقدمه

**Security as Code** یعنی سیاست‌های امنیتی در مخزن، با نسخه، review و تست — نه در سر یک نفر یا سند PDF.

این تغییر، امنیت را از «دانش شخصی» به «دارایی سازمانی» تبدیل می‌کند.

### مفاهیم اساسی

**چهار سطح Security as Code:**

| سطح | مثال |
|---|---|
| **Policy** | OPA، Sentinel |
| **Infrastructure** | Terraform با کنترل امنیتی |
| **Pipeline** | اسکن در CI |
| **Application** | قواعد SAST سفارشی |

**«Policy as Code» — مهم‌ترین سطح:**

```
قاعده امنیتی → کد → تست → اعمال خودکار
```

**مزیت**: قاعده یک‌بار نوشته می‌شود، در همه پروژه‌ها اعمال می‌شود، و قابل audit است.

**سه نوع سیاست:**

| نوع | مثال |
|---|---|
| **Preventive** | «bucket عمومی ممنوع» |
| **Detective** | «اگر رمز قدیمی بود، هشدار» |
| **Corrective** | «رمز را خودکار rotate کن» |

**نکته**: Preventive بهترین است — جلوی مشکل را می‌گیرد.

### مثال‌های عملی

**سیاست با OPA/Rego:**

```rego
# policy/no_public_s3.rego
package terraform.s3

deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_s3_bucket"
    resource.change.after.acl == "public-read"
    msg := sprintf("❌ bucket %s نباید عمومی باشد", [resource.address])
}

deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_s3_bucket"
    not resource.change.after.server_side_encryption_configuration
    msg := sprintf("❌ bucket %s باید رمزنگاری داشته باشد", [resource.address])
}
```

```bash
# در CI
terraform plan -out=tfplan
terraform show -json tfplan > plan.json
conftest test plan.json -p policy/
```

**نکته**: اگر سیاست نقض شود، pipeline متوقف می‌شود — حتی اگر کسی اشتباه بنویسد.

**سیاست Kubernetes با OPA Gatekeeper:**

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-team-label
spec:
  match:
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment"]
  parameters:
    labels: ["team", "cost-center"]
```

**اثر**: هر Deployment بدون label تیم، رد می‌شود.

**سیاست شبکه — NetworkPolicy:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  # هیچ قاعده‌ای = همه ترافیک بلاک
```

**نکته**: «default deny» امن‌ترین شروع است. بعد قاعده اضافه کن.

**قواعد SAST سفارشی:**

```yaml
# .semgrep/security.yml
rules:
  - id: no-hardcoded-secret
    patterns:
      - pattern: |
          $KEY = "..."
      - metavariable-regex:
          metavariable: $KEY
          regex: (?i)(password|secret|token|api_key)
    message: "راز hardcoded — از متغیر محیطی استفاده کن"
    languages: [python]
    severity: ERROR
    metadata:
      cwe: "CWE-798: Use of Hard-coded Credentials"

  - id: sql-string-format
    patterns:
      - pattern: |
          $CURSOR.execute(f"...")
    message: "SQL با f-string — از پارامتر استفاده کن"
    languages: [python]
    severity: ERROR
    metadata:
      cwe: "CWE-89: SQL Injection"
```

**مزیت**: قواعد مخصوص کدبیس خودت، در مخزن، با review.

### مقایسه و الگوهای مختلف

**سه روش اعمال سیاست:**

| روش | دور زدن | مناسب |
|---|---|---|
| مستند | ✅ آسان | ❌ |
| CI check | ✅ (تغییر YAML) | ✅ |
| Policy engine | ❌ | ✅✅ |

**نکته**: سیاستی که در `CONTRIBUTING.md` است، وجود ندارد. باید **اجرا** شود.

**سه سطح اجرا:**

| سطح | ابزار |
|---|---|
| Infrastructure | OPA، Sentinel، Checkov |
| Kubernetes | Gatekeeper، Kyverno |
| Application | Semgrep، CodeQL |

**Policy در برابر Scan:**

| معیار | Policy | Scan |
|---|---|---|
| چه می‌کند | جلوگیری | کشف |
| زمان | قبل از اعمال | بعد از ساخت |
| مناسب | ✅ پیشگیرانه | تشخیص |

### اشکال شایع

**اشکال ۱: سیاست بدون تست**

سیاست غلط، همه‌چیز را بلاک می‌کند. سیاست را با مثال تست کن.

**اشکال ۲: سیاست خیلی سخت**

تیم دور می‌زند. از preventive ساده شروع کن.

**اشکال ۳: سیاست بدون استثنا**

گاهی استثنا لازم است. مکانیزم exception با تاریخ انقضا.

**اشکال ۴: سیاست در مخزن پروژه**

تیم می‌تواند تغییرش دهد. در مخزن جدا، با دسترسی محدود.

**اشکال ۵: سیاست بدون مستند**

«چرا بلاک شد؟» — پیام واضح و لینک به دلیل.

**اشکال ۶: سیاست بدون بازبینی**

قاعده ۲ سال پیش، هنوز منطقی است؟ سالانه بازبینی.

### نکات مهم (Tips & Tricks)

- **سیاست را اجرا کن**، نه فقط مستند.
- **Preventive بهترین است** — جلوگیری.
- **پیام واضح** — چرا و چطور رفع.
- **استثنا با تاریخ انقضا.**
- **سیاست در مخزن جدا.**
- **سیاست را تست کن.**

### خلاصه فصل

- Security as Code: سیاست در مخزن، با نسخه و review.
- چهار سطح: policy، infrastructure، pipeline، application.
- Preventive > Detective > Corrective.
- Policy engine قابل دور زدن نیست.
- پیام واضح و استثنا با انقضا.
- سیاست را تست و بازبینی کن.

## فصل ۶۵: زنجیره تأمین نرم‌افزار

### مقدمه

کدی که می‌نویسی، تنها بخش کوچکی از نرم‌افزاری است که اجرا می‌شود. ۷۰-۹۰٪ آن **dependency** و **base image** است.

**Supply Chain Security** یعنی بتوانی اثبات کنی: این artifact از کجا آمد، چه چیزی داخلش است، و کسی دستکاری‌اش نکرده.

### مفاهیم اساسی

**چهار ستون:**

| ستون | سؤال | ابزار |
|---|---|---|
| **SBOM** | چه چیزی داخلش است؟ | Syft، CycloneDX |
| **Scanning** | چه آسیب‌پذیری دارد؟ | Trivy، Grype |
| **Signing** | چه کسی ساخت؟ | Cosign، Sigstore |
| **Provenance** | چطور ساخته شد؟ | SLSA، in-toto |

**حمله‌های زنجیره تأمین واقعی:**

| حادثه | چه شد |
|---|---|
| **SolarWinds (2020)** | کد مخرب در build pipeline |
| **event-stream (2018)** | پکیج npm مخرب |
| **Log4Shell (2021)** | آسیب‌پذیری در dependency همه‌جا |
| **xz-utils (2024)** | backdoor در maintainer |
| **Colors.js (2022)** | maintainer عمداً خراب کرد |

**درس**: dependency، سطح حمله است.

**SBOM — فهرست مواد:**

```
SBOM = Software Bill of Materials
     = لیست همه اجزا و نسخه‌ها
```

| فرمت | توضیح |
|---|---|
| **SPDX** | استاندارد Linux Foundation |
| **CycloneDX** | استاندارد OWASP |

**نکته**: SBOM پاسخ به «آیا ما Log4j داریم؟» است — در ۵ دقیقه، نه ۵ روز.

### مثال‌های عملی

**تولید SBOM:**

```bash
# با Syft
syft registry.gitlab.com/acme/app:v1.4.2 -o cyclonedx-json=sbom.json

# بررسی: آیا پکیج خاصی هست؟
jq -r '.components[] | select(.name == "log4j-core") | .version' sbom.json
```

**اسکن SBOM:**

```bash
grype sbom:sbom.json --fail-on critical --output table
```

**امضای artifact با Cosign (keyless):**

```bash
# امضا با OIDC (بدون کلید خصوصی)
cosign sign --yes registry.gitlab.com/acme/app:v1.4.2

# تأیید
cosign verify \
  --certificate-identity-regexp "https://gitlab.com/acme/.*" \
  --certificate-oidc-issuer "https://gitlab.com" \
  registry.gitlab.com/acme/app:v1.4.2
```

**نکته**: keyless ساده‌تر است — کلید خصوصی ندارد که لو برود.

**SLSA — سطوح بلوغ:**

| سطح | معنا |
|---|---|
| **SLSA 1** | build خودکار، provenance موجود |
| **SLSA 2** | build service امضاشده |
| **SLSA 3** | ✅ build ایزوله، غیرقابل دستکاری |
| **SLSA 4** | بازبینی دو‌نفره، hermetic |

**نکته**: اکثر سازمان‌ها در سطح ۱-۲ هستند. هدف: ۳.

**provenance — نمونه:**

```json
{
  "_type": "https://in-toto.io/Statement/v0.1",
  "subject": [{"name": "app", "digest": {"sha256": "9f8e7d6..."}}],
  "predicateType": "https://slsa.dev/provenance/v0.2",
  "predicate": {
    "builder": {"id": "https://gitlab.com/acme/ci"},
    "buildType": "https://gitlab.com/ci/pipeline",
    "invocation": {
      "configSource": {
        "uri": "git+https://gitlab.com/acme/app@refs/heads/main",
        "digest": {"sha1": "a1b2c3d"}
      }
    },
    "metadata": {
      "buildStartedOn": "2026-10-17T09:30:00Z",
      "completeness": {"parameters": true, "environment": true}
    }
  }
}
```

**این فایل می‌گوید**: این artifact از کدام commit، با کدام pipeline، کِی ساخته شد.

**زنجیره تأیید کامل:**

```
۱. build در CI ایزوله
۲. SBOM تولید
۳. اسکن (بدون critical)
۴. امضا با Cosign
۵. push به registry
۶. deploy فقط اگر امضا معتبر باشد
```

**گام ۶ — مهم‌ترین:**

```yaml
deploy:
  script:
    - cosign verify --certificate-identity-regexp "..." "$IMAGE"
    - kubectl set image deployment/app app="$IMAGE"
```

بدون این، امضا بی‌فایده است.

### مقایسه و الگوهای مختلف

**سه سطح Supply Chain Security:**

| سطح | چه داری |
|---|---|
| ۱ | lockfile + SBOM |
| ۲ | + اسکن خودکار + pin |
| ۳ | ✅ + امضا + تأیید + SLSA 3 |

**Pin در برابر range:**

| روش | مثال | تکرارپذیری |
|---|---|---|
| Range | `requests>=2.0` | ❌ |
| Pin | `requests==2.32.3` | ✅ |
| Hash | `--require-hashes` | ✅✅ |

**توصیه**: pin + hash برای production.

**سه مدل اعتماد به base image:**

| مدل | امنیت |
|---|---|
| `latest` | ❌❌ |
| tag | متوسط |
| ✅ digest | ✅✅ |

### اشکال شایع

**اشکال ۱: SBOM تولید شد، استفاده نشد**

فایل در artifact، هیچ‌کس نمی‌خواند. از آن برای پاسخ به حادثه استفاده کن.

**اشکال ۲: امضا بدون تأیید**

امضا کردیم، ولی deploy امضا را چک نمی‌کند. بی‌فایده.

**اشکال ۳: dependency بدون lockfile**

هر build، نسخه متفاوت. `package-lock.json` را commit کن.

**اشکال ۴: base image با `latest`**

فردا چیز دیگری است. digest pin.

**اشکال ۵: نادیده گرفتن transitive dependency**

`requests` امن است، ولی dependency آن نیست. SCA کل درخت را اسکن می‌کند.

**اشکال ۶: اعتماد به پکیج بدون بررسی**

typosquatting: `reqeusts` به‌جای `requests`. نام را چک کن.

### نکات مهم (Tips & Tricks)

- **lockfile + hash pin.**
- **SBOM تولید و نگه دار** (۱ سال).
- **base image با digest.**
- **امضا + تأیید** — هر دو.
- **SLSA 3 هدف** باشد.
- **SCA برای transitive** — نه فقط مستقیم.

### خلاصه فصل

- Supply chain، سطح حمله واقعی است.
- چهار ستون: SBOM، scanning، signing، provenance.
- SBOM پاسخ سریع به حادثه است.
- امضا بدون تأیید بی‌فایده است.
- pin + hash برای تکرارپذیری.
- SLSA 3 هدف بلوغ.

## فصل ۶۶: مدیریت آسیب‌پذیری

### مقدمه

اسکن بدون مدیریت، نویز است. مدیریت یعنی: اولویت‌بندی، تخصیص، رفع، و بستن — با SLA.

این فصل چرخه کامل را می‌آورد.

### مفاهیم اساسی

**چرخه شش‌مرحله‌ای:**

```
کشف → ارزیابی → اولویت‌بندی → تخصیص → رفع → تأیید
```

**اولویت‌بندی — چهار عامل:**

| عامل | وزن |
|---|---|
| **Severity** (CVSS) | ✅ |
| **Exploitability** | ✅✅ |
| **Reachability** | ✅✅✅ |
| **Exposure** | ✅✅ |

**نکته کلیدی**: CVSS 9.5 در کدی که استفاده نمی‌کنی، کمتر از CVSS 6.5 در endpoint عمومی اهمیت دارد.

**SLA پیشنهادی:**

| Severity | زمان رفع |
|---|---|
| Critical | ۷ روز |
| High | ۳۰ روز |
| Medium | ۹۰ روز |
| Low | ۱۸۰ روز |

**نکته**: SLA بدون اندازه‌گیری، وجود ندارد.

### مثال‌های عملی

**محاسبه اولویت واقعی:**

```
یافته A:
  CVE-2024-1234، CVSS 9.8
  پکیج: lib-foo
  آیا در کد استفاده می‌شود؟ خیر (dependency transitive بی‌استفاده)
  آیا قابل دسترسی از اینترنت؟ خیر
  → اولویت: پایین

یافته B:
  CVE-2024-5678، CVSS 7.5
  پکیج: web-framework
  آیا در کد استفاده می‌شود؟ بله (همه endpointها)
  آیا قابل دسترسی از اینترنت؟ بله
  → اولویت: ✅ بالا (بالاتر از A!)
```

**این تفکیک، تفاوت بین triage و شمارش است.**

**فرمول اولویت ساده:**

```
اولویت = Severity × Reachability × Exposure × Exploitability

A: 9.8 × 0 × 0 × 1 = 0        ← پایین
B: 7.5 × 1 × 1 × 1 = 7.5      ← بالا
```

**گردش کار triage هفتگی:**

```
دوشنبه ۱۰:۰۰ — ۳۰ دقیقه
  ۱. یافته‌های جدید Critical/High
  ۲. هر کدام: تأیید / رد / allowlist
  ۳. issue بساز برای تأییدشده‌ها
  ۴. وضعیت SLA را ببین
  ۵. اقدام هفته گذشته را مرور کن
```

**نکته**: بدون این جلسه، یافته‌ها انباشته می‌شوند.

**allowlist با تاریخ انقضا:**

```
# .security-allowlist.txt
# CVE | تاریخ انقضا | دلیل | تأییدکننده
CVE-2024-1234|2027-01-01|کد آسیب‌پذیر استفاده نمی‌شود|@security-team
CVE-2024-5678|2026-12-01|فقط در dev dependency|@security-team
```

و در gate، تاریخ را چک کن:

```bash
if [[ "$expiry" < "$(date +%F)" ]]; then
  echo "❌ allowlist منقضی: $cve"
  exit 1
fi
```

**نکته**: allowlist دائمی، بدهی امنیتی است.

**گزارش ماهانه:**

```
# گزارش امنیت — مهر ۱۴۰۵

| شدت | باز | رفع‌شده | میانگین زمان رفع |
|---|---|---|---|
| Critical | ۰ | ۳ | ۴ روز |
| High | ۲ | ۸ | ۱۸ روز |
| Medium | ۱۲ | ۱۵ | — |

SLA:
  Critical: ۳/۳ در SLA ✅
  High: ۶/۸ در SLA ⚠️

اقدام: تخصیص ۲۰٪ ظرفیت هفته آینده به High
```

### مقایسه و الگوهای مختلف

**سه مدل triage:**

| مدل | چه کسی | مقیاس |
|---|---|---|
| متمرکز | تیم امنیت | ❌ |
| توزیع‌شده | هر تیم | ✅ |
| ترکیبی | امنیت برای policy، تیم برای رفع | ✅✅ |

**Dismiss در برابر Allowlist:**

| معیار | Dismiss | Allowlist |
|---|---|---|
| سطح | یک یافته | قاعده |
| Audit | ✅ | متوسط |
| انقضا | ✅ | ✅ (دستی) |

**سه سطح گزارش:**

| سطح | مخاطب | فرکانس |
|---|---|---|
| MR | توسعه‌دهنده | هر MR |
| داشبورد | تیم امنیت | پیوسته |
| ماهانه | مدیریت | ماهانه |

### اشکال شایع

**اشکال ۱: ۵۰۰۰ یافته، فلج**

اولویت‌بندی. Critical با reachability بالا اول.

**اشکال ۲: Dismiss بدون دلیل**

Audit شکست می‌خورد. دلیل الزامی.

**اشکال ۳: SLA بدون اندازه‌گیری**

«۷ روز» ولی کسی نمی‌داند چقدر طول می‌کشد.

**اشکال ۴: تیم امنیت گلوگاه**

triage توزیع کن.

**اشکال ۵: نادیده گرفتن transitive**

فقط dependency مستقیم اسکن شد.

**اشکال ۶: allowlist بی‌پایان**

بدهی انباشته. تاریخ انقضا.

**اشکال ۷: یافته‌های قدیمی رها**

«۳ سال پیش کشف شد، هنوز باز». بازبینی فصلی.

### نکات مهم (Tips & Tricks)

- **Reachability مهم‌تر از CVSS.**
- **SLA با اندازه‌گیری.**
- **allowlist با انقضا.**
- **triage هفتگی ثابت.**
- **Dismiss با دلیل.**
- **گزارش ماهانه به مدیریت.**

### خلاصه فصل

- مدیریت = triage + اولویت + رفع + بستن.
- چهار عامل اولویت؛ reachability مهم‌ترین.
- SLA: Critical ۷، High ۳۰، Medium ۹۰ روز.
- allowlist با تاریخ انقضا.
- triage هفتگی ثابت.
- گزارش ماهانه با اندازه‌گیری SLA.

## فصل ۶۷: مدل تهدید و طراحی امن

### مقدمه

امنیت واکنشی (اسکن، وصله) کافی نیست. باید **قبل از نوشتن کد** فکر کنی: «چه چیزی می‌تواند اشتباه شود؟»

این **مدل تهدید (Threat Modeling)** است.

### مفاهیم اساسی

**چهار سؤال مدل تهدید:**

| سؤال | مثال |
|---|---|
| **چه چیزی می‌سازیم؟** | یک API پرداخت |
| **چه چیزی می‌تواند اشتباه شود؟** | افشای داده کارت |
| **چه کار می‌کنیم؟** | رمزنگاری، tokenization |
| **چقدر خوب کار کردیم؟** | تست، بازبینی |

**STRIDE — شش دسته تهدید:**

| حرف | تهدید | مثال |
|---|---|---|
| **S**poofing | جعل هویت | توکن دزدیده‌شده |
| **T**ampering | دستکاری | تغییر قیمت در request |
| **R**epudiation | انکار | «من این تراکنش را نکردم» |
| **I**nformation disclosure | افشا | لاگ شامل رمز |
| **D**enial of service | اختلال | flood |
| **E**levation of privilege | افزایش دسترسی | کاربر عادی → admin |

**نکته**: STRIDE برای هر جزء سیستم (کاربر، API، DB، لاگ) بررسی می‌شود.

**اصل «دفاع در عمق»:**

```
لایه ۱: اعتبارسنجی ورودی
لایه ۲: احراز هویت
لایه ۳: مجوز
لایه ۴: رمزنگاری
لایه ۵: لاگ و پایش
```

اگر یک لایه شکست، بقیه محافظت می‌کنند.

### مثال‌های عملی

**مدل تهدید یک API — جدول:**

| جزء | تهدید | STRIDE | کنترل |
|---|---|---|---|
| Login | جعل هویت | S | MFA، rate limit |
| Create order | دستکاری قیمت | T | قیمت سمت سرور |
| Delete user | افزایش دسترسی | E | مجوز + audit |
| Logs | افشای رمز | I | mask کردن |
| Public API | DoS | D | rate limit، WAF |
| Payment | انکار | R | audit log امضاشده |

**نکته**: هر ردیف، یک تصمیم طراحی.

**اصل حداقل دسترسی — مثال:**

```yaml
# ❌ بد: همه‌چیز
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
rules:
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]

# ✅ خوب: فقط لازم
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch"]
```

**نکته**: هر دسترسی اضافه، سطح حمله است.

**اعتبارسنجی ورودی — اصل:**

```python
"""هر ورودی، غیرقابل اعتماد است."""
from pydantic import BaseModel, Field, HttpUrl


class CreateLinkRequest(BaseModel):
    """درخواست ساخت لینک — با اعتبارسنجی سخت‌گیرانه."""

    url: HttpUrl                                    # نوع + فرمت
    code: str | None = Field(
        default=None,
        min_length=3,
        max_length=16,
        pattern=r"^[A-Za-z0-9]+$",                  # فقط حروف و عدد
    )
    expires_days: int = Field(default=0, ge=0, le=365)
```

**نکته**: `pattern` جلوی injection در `code` را می‌گیرد. Pydantic خودکار 422 برمی‌گرداند.

**امنیت در طراحی — سه پرسش:**

```
۱. اگر این endpoint عمومی باشد، چه می‌شود؟
۲. اگر ورودی مخرب باشد، چه می‌شود؟
۳. اگر این سرویس در دسترس نباشد، چه می‌شود؟
```

**هر پرسش، یک تصمیم طراحی.**

### مقایسه و الگوهای مختلف

**مدل تهدید در برابر pen test:**

| معیار | Threat Model | Pen Test |
|---|---|---|
| زمان | طراحی | بعد از ساخت |
| هزینه | ✅ کم | ❌ زیاد |
| عمق | طراحی | پیاده‌سازی |
| مناسب | ✅ هر قابلیت | سالانه |

**سه سطح مدل تهدید:**

| سطح | زمان | عمق |
|---|---|---|
| سریع | ۱۵ دقیقه | STRIDE روی یک قابلیت |
| متوسط | ۱ ساعت | جریان داده |
| کامل | ۱ روز | همه اجزا |

**توصیه**: سریع برای هر قابلیت، کامل برای قابلیت‌های حساس.

**سه چارچوب:**

| چارچوب | تمرکز |
|---|---|
| STRIDE | دسته تهدید |
| PASTA | ریسک‌محور |
| LINDDUN | حریم خصوصی |

### اشکال شایع

**اشکال ۱: مدل تهدید فقط برای «سیستم‌های حساس»**

همه سیستم‌ها داده دارند. حتی یک blog.

**اشکال ۲: مدل تهدید یک‌بار**

قابلیت جدید = تهدید جدید. هر تغییر، بازبینی.

**اشکال ۳: مدل تهدید بدون اقدام**

جدول زیبا، بدون کنترل. هر تهدید، یک تصمیم.

**اشکال ۴: فقط تهدید خارجی**

insider threat هم وجود دارد. دسترسی داخلی را هم ببین.

**اشکال ۵: اعتماد به ورودی**

«کاربر همیشه درست وارد می‌کند» — نه.

**اشکال ۶: امنیت به‌عنوان مرحله آخر**

«بعد از ساخت، امن‌اش می‌کنیم» — گران و ناکارآمد.

### نکات مهم (Tips & Tricks)

- **مدل تهدید ۱۵ دقیقه‌ای** برای هر قابلیت.
- **STRIDE** برای هر جزء.
- **هر تهدید، یک کنترل.**
- **دفاع در عمق.**
- **حداقل دسترسی.**
- **ورودی همیشه غیرقابل اعتماد.**

### خلاصه فصل

- مدل تهدید: قبل از کد فکر کن.
- چهار سؤال + STRIDE.
- دفاع در عمق، حداقل دسترسی.
- ورودی غیرقابل اعتماد.
- هر تهدید، یک کنترل.
- هر تغییر، بازبینی تهدید.

## فصل ۶۸: فرهنگ امنیت بدون ترس

### مقدمه

امنیت اغلب با ترس کار می‌کند: «اگر این کار را بکنی، اخراج می‌شوی». نتیجه: پنهان‌کاری، نه امنیت.

این فصل فرهنگ امنیت سالم را می‌سازد.

### مفاهیم اساسی

**فرهنگ ترس در برابر فرهنگ یادگیری:**

| معیار | ترس | یادگیری |
|---|---|---|
| گزارش خطا | ❌ پنهان | ✅ باز |
| سؤال | ❌ «نمی‌دانم» ممنوع | ✅ تشویق |
| حادثه | «مقصر کی؟» | «چه سیستم؟» |
| نتیجه | ❌ شکننده | ✅ مقاوم |

**چرا ترس کار نمی‌کند:**

```
ترس → پنهان‌کاری → آسیب‌پذیری پنهان → حادثه بزرگ‌تر
```

**«Just Culture» در امنیت:**

| رفتار | پاسخ |
|---|---|
| خطای انسانی ساده | دلداری + بهبود سیستم |
| رفتار ریسکی (می‌دانستم) | آموزش |
| رفتار مخرب (عمدی) | برخورد |

**نکته**: بدون تفکیک، «no blame» به «no accountability» تبدیل می‌شود.

**چهار رفتار فرهنگی امنیت:**

| رفتار | نشانه |
|---|---|
| **گزارش آسان** | فرم ساده، بدون ترس |
| **پاداش گزارش** | «ممنون که گفتی» |
| **یادگیری از خطا** | postmortem امنیتی |
| **آموزش مستمر** | نه فقط سالانه |

### مثال‌های عملی

**گزارش آسیب‌پذیری — کانال‌های مختلف:**

| کانال | برای چه |
|---|---|
| Security email | گزارش خارجی |
| Issue محرمانه | گزارش داخلی |
| Bug bounty | محققان |
| Slack #security | سؤال سریع |

**نکته**: کانال گزارش باید **کم‌اصطکاک** باشد. اگر فرم ۱۰ فیلدی باشد، کسی گزارش نمی‌دهد.

**پاداش گزارش — سه مدل:**

| مدل | مزیت | عیب |
|---|---|---|
| تقدیر عمومی | ✅ فرهنگ | ❌ کافی نیست |
| پاداش مالی | ✅ انگیزه | ❌ ممکن است بازی شود |
| Recognition + آموزش | ✅✅ | نیاز به مدیریت |

**«Security Champion» — برنامه:**

```
هر تیم یک نفر:
  - ۲ روز آموزش در سال
  - ۲۰٪ وقت برای امنیت
  - اولین مرجع تیم
  - ارتباط با تیم امنیت مرکزی

مزیت: مقیاس‌پذیر، بدون گلوگاه
```

**آموزش مؤثر در برابر بی‌اثر:**

| بی‌اثر | مؤثر |
|---|---|
| ویدیوی ۲ ساعته سالانه | ۱۰ دقیقه ماهانه، واقعی |
| «قوانین را رعایت کن» | «این حمله چطور کار می‌کند» |
| آزمون چندگزینه‌ای | تمرین عملی |

**نکته**: آموزش کوتاه و مکرر، مؤثرتر از بلند و نادر است.

**postmortem امنیتی — نمونه:**

```markdown
# حادثه امنیتی: افشای کلید API

**تاریخ**: ۱۴۰۵/۰۷/۱۵ | **کشف**: ۴ ساعت پس از افشا

## چه شد
یک کلید API در commit اشتباهی push شد و در مخزن عمومی قرار گرفت.

## چطور کشف شد
اسکن خودکار Secret Detection در MR بعدی، کلید را در تاریخ پیدا کرد.

## چرا اتفاق افتاد
- پیش‌فرض: کلید در فایل config بود
- pre-commit hook نصب نبود
- مخزن برای ۴ ساعت عمومی بود

## اقدامات
| اقدام | مالک | مهلت |
|---|---|---|
| pre-commit hook اجباری | @ali | ۱ هفته |
| چرخش همه کلیدها | @sara | ۳ روز |
| بازبینی دسترسی مخازن | @security | ۲ هفته |

## درس
کلید در فایل، همیشه خطر است. متغیر محیطی از روز اول.
```

**نکته**: بدون سرزنش، با اقدام مشخص.

### مقایسه و الگوهای مختلف

**سه سطح بلوغ فرهنگ امنیت:**

| سطح | ویژگی |
|---|---|
| ۱ | ترس، پنهان‌کاری |
| ۲ | گزارش، بدون پاداش |
| ۳ | ✅ یادگیری، champion، آموزش |

**سه مدل آموزش:**

| مدل | فرکانس | اثر |
|---|---|---|
| سالانه | ۱ بار | ❌ کم |
| فصلی | ۴ بار | متوسط |
| ✅ ماهانه ۱۰ دقیقه | ۱۲ بار | ✅✅ |

**سه سطح شفافیت:**

| سطح | چه چیزی |
|---|---|
| ۱ | فقط تیم امنیت |
| ۲ | + مدیریت |
| ۳ | ✅ + همه (بدون جزئیات حساس) |

### اشکال شایع

**اشکال ۱: ترس به‌عنوان ابزار**

پنهان‌کاری. بدتر از ندانستن.

**اشکال ۲: آموزش سالانه ۲ ساعته**

فراموش می‌شود. کوتاه و مکرر.

**اشکال ۳: گزارش پیچیده**

فرم ۱۰ فیلدی = کسی گزارش نمی‌دهد.

**اشکال ۴: بدون پاداش**

«ممنون» کافی نیست. تقدیر و شناخت لازم.

**اشکال ۵: امنیت به‌عنوان «کار تیم امنیت»**

مسئولیت مشترک. champion در تیم.

**اشکال ۶: سرزنش در حادثه**

پنهان‌کاری برمی‌گردد.

### نکات مهم (Tips & Tricks)

- **گزارش آسان** — کم‌اصطکاک.
- **پاداش گزارش** — تقدیر + آموزش.
- **آموزش کوتاه و مکرر.**
- **champion در هر تیم.**
- **Just Culture** — مسئولیت + یادگیری.
- **postmortem بدون سرزنش.**

### خلاصه فصل

- فرهنگ ترس، پنهان‌کاری می‌سازد.
- Just Culture: مسئولیت + یادگیری.
- گزارش باید آسان باشد.
- آموزش کوتاه و مکرر مؤثرتر است.
- security champion مقیاس‌پذیر است.
- postmortem با اقدام، بدون سرزنش.
