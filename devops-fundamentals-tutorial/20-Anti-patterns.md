## فصل ۱۰۹: DevOps Theater

### مقدمه

**DevOps Theater** یعنی: **ظاهر** DevOps بدون **جوهر** آن. همه ابزارها و مراسم هست، ولی تحویل همان‌قدر کند و پرحادثه است.

این خطرناک‌ترین ضدالگوست — چون **به نظر می‌رسد کار می‌کند**.

### مفاهیم اساسی

**شش نشانه DevOps Theater:**

| نشانه | چه می‌بینی | چه غایب است |
|---|---|---|
| **CI بدون ادغام مکرر** | pipeline هست | merge ماهانه |
| **CD بدون deploy** | deploy خودکار به staging | production |
| **متریک بدون اقدام** | داشبورد زیبا | تغییر |
| **مراسم بدون تغییر** | daily، retro | اقدام |
| **فرهنگ بدون رفتار** | شعار روی دیوار | postmortem واقعی |
| **ابزار بدون استفاده** | Kubernetes، Terraform | تیم از آن استفاده نمی‌کند |

**نکته**: Theater را با **نتیجه** تشخیص بده، نه با **فعالیت**.

**سه سطح Theater:**

| سطح | نشانه |
|---|---|
| ۱ | ابزار خریدیم، کسی استفاده نمی‌کند |
| ۲ | ابزار استفاده می‌شود، نتیجه ندارد |
| ۳ | ✅ نتیجه دارد، ولی ناپایدار |

### مثال‌های عملی

**مثال ۱: CI Theater**

```
چه داریم:
  ✅ GitLab CI
  ✅ pipeline برای همه پروژه‌ها
  ✅ تست خودکار

چه غایب است:
  ❌ merge ماهی یک‌بار (چون branch بلندعمر)
  ❌ pipeline قرمز نادیده گرفته می‌شود
  ❌ کسی تست را locally اجرا نمی‌کند

نتیجه: همان ادغام جهنمی، با ظاهر مدرن
```

**تشخیص**: `git log --merges` بزن. اگر merge ماهانه است، Theater.

**مثال ۲: Kubernetes Theater**

```
چه داریم:
  ✅ K8s cluster
  ✅ Helm charts
  ✅ GitOps

چه غایب است:
  ❌ deploy هنوز از طریق تیکت
  ❌ تیم‌ها نمی‌دانند K8s چیست
  ❌ rollback دستی و سخت
  ❌ observability ندارد

نتیجه: پیچیدگی K8s، سرعت قبل
```

**تشخیص**: از یک توسعه‌دهنده بپرس «چطور deploy می‌کنی؟» اگر جواب «تیکت می‌دهم» بود، Theater.

**مثال ۳: متریک Theater**

```
چه داریم:
  ✅ داشبورد DORA
  ✅ Lead Time، CFR، MTTR
  ✅ گزارش ماهانه

چه غایب است:
  ❌ هیچ اقدامی بر اساس متریک
  ❌ کسی متریک را در جلسه نگاه نمی‌کند
  ❌ هدف تعریف نشده

نتیجه: عدد زیبا، بدون تغییر
```

**تشخیص**: بپرس «آخرین باری که متریک باعث تغییر شد، کِی بود؟»

### مقایسه و الگوهای مختلف

**Theater در برابر تحول واقعی:**

| معیار | Theater | واقعی |
|---|---|---|
| تمرکز | فعالیت | نتیجه |
| سنجش | ابزار نصب شده | Lead Time |
| رفتار | همان | عوض شده |
| زمان | ✅ سریع | ❌ کند |

**نکته**: Theater **سریع** است (ابزار بخر)، تحول واقعی **کند** (فرهنگ عوض کن). به همین دلیل Theater رایج است.

**سه دلیل Theater:**

| دلیل | توضیح |
|---|---|
| **فشار برای «نتیجه سریع»** | ابزار سریع است |
| **فروشندگان** | ابزار می‌فروشند |
| **ندیدن تفاوت** | نمی‌دانند تفاوت چیست |

**سه سطح درمان:**

| سطح | اقدام |
|---|---|
| تشخیص | متریک نتیجه را ببین |
| اولویت | از یک تیم شروع |
| فرهنگ | رفتار را عوض کن |

### اشکال شایع

**اشکال ۱: Theater را موفقیت دانستیم**

«pipeline داریم» ≠ «سریع تحویل می‌دهیم».

**اشکال ۲: ابزار خریدیم و رها کردیم**

آموزش، حمایت، استفاده — همه لازم.

**اشکال ۳: مراسم بدون اقدام**

daily، retro، postmortem — بدون خروجی.

**اشکال ۴: متریک برای نمایش**

داشبورد برای مدیریت، نه برای بهبود.

**اشکال ۵: ترس از اعتراف**

«ما Theater داریم» — سخت است، ولی اولین قدم.

**اشکال ۶: Theater را به تیم نسبت دادیم**

تیم ابزار را دارد، ولی فرآیند و اختیار ندارد. **سیستم** Theater است.

### نکات مهم (Tips & Tricks)

- **نتیجه را بسنج**، نه فعالیت.
- **«چطور deploy می‌کنی؟»** از یک توسعه‌دهنده بپرس.
- **«آخرین تغییر بر اساس متریک؟»** بپرس.
- **Theater سریع است، تحول کند.**
- **از یک تیم شروع کن.**
- **اعتراف، اولین قدم.**

### خلاصه فصل

- Theater: ظاهر بدون جوهر.
- شش نشانه: CI بدون ادغام، CD بدون deploy، متریک بدون اقدام، ...
- Theater سریع است، تحول کند.
- نتیجه را بسنج، نه فعالیت.
- از یک تیم شروع کن.
- اعتراف اولین قدم است.

## فصل ۱۱۰: ابزارگرایی و تیم DevOps

### مقدمه

دو ضدالگوی مرتبط که بیشترین آسیب را می‌زنند:

| ضدالگو | مشکل |
|---|---|
| **ابزارگرایی** | ابزار به‌جای مسئله |
| **تیم DevOps** | شکاف سوم |

### مفاهیم اساسی

**ابزارگرایی — سه نشانه:**

| نشانه | مثال |
|---|---|
| **ابزار قبل از مسئله** | «Kubernetes بیاوریم» بدون درد مشخص |
| **ابزار به‌جای فرآیند** | «Jenkins داریم، پس CI داریم» |
| **ابزار به‌جای فرهنگ** | «Slack داریم، پس شفافیم» |

**نکته**: ابزار **تسریع‌کننده** است، نه **علت**. فرهنگ بد را سریع‌تر بد می‌کند.

**تیم DevOps — چرا ضدالگوست:**

```
قبل:
  Dev ──[دیوار]── Ops

بعد (اشتباه):
  Dev ──[دیوار]── DevOps ──[دیوار]── Ops

نتیجه: دو دیوار، سه لایه هماهنگی
```

**نکته**: تیم DevOps **شکاف را حل نمی‌کند**؛ **یک شکاف اضافه می‌کند**.

**سه نقش مشروع (در برابر تیم DevOps):**

| نقش | مشروع؟ |
|---|---|
| **Platform Engineer** | ✅ (محصول می‌سازد) |
| **SRE** | ✅ (مهندسی پایداری) |
| **DevOps Engineer** | ⚠️ (بستگی به تعریف) |
| **تیم DevOps** | ❌ (شکاف سوم) |

**نکته**: تفاوت در **مالکیت** است: Platform مالک ابزار، تیم DevOps مالک «هماهنگی».

### مثال‌های عملی

**ابزارگرایی — داستان واقعی:**

```
شرکت ۵۰۰ نفره:
  - ۲ میلیون خرج K8s + ابزار
  - ۱۸ ماه پیاده‌سازی
  - آموزش ۲۰۰ مهندس

نتیجه:
  - deploy هنوز ۲ هفته (فرآیند تأیید عوض نشد)
  - حادثه همان‌قدر (observability نداشتند)
  - تیم ناراضی (پیچیدگی بیشتر)

درس: ابزار، مسئله نبود
```

**تیم DevOps — داستان واقعی:**

```
شرکت ۲۰۰ نفره:
  - تیم DevOps ۶ نفره ساختند
  - Dev و Ops قبلی سر جایشان
  - تیم DevOps: "واسط" بین آن دو

نتیجه:
  - Dev درخواست می‌دهد → DevOps → Ops
  - ۳ لایه هماهنگی
  - Lead Time از ۲ هفته به ۳ هفته (!)
  - تیم DevOps فرسوده (فقط هماهنگی)

درس: واسط، شکاف را عمیق‌تر می‌کند
```

**راه‌حل — تبدیل تیم DevOps:**

| از | به |
|---|---|
| هماهنگ‌کننده | Platform team (محصول) |
| واسط | SRE (مشاور) |
| «ما deploy می‌کنیم» | «ما ابزار deploy می‌دهیم» |

**نکته**: تیم DevOps موجود را **حذف نکن**؛ **مأموریتش را عوض کن**.

### مقایسه و الگوهای مختلف

**ابزارگرایی در برابر مسئله‌محوری:**

| معیار | ابزارگرایی | مسئله‌محوری |
|---|---|---|
| شروع | ابزار | درد |
| سنجش | نصب شد؟ | درد کم شد؟ |
| نتیجه | ❌ | ✅ |

**سه مدل تیم فنی:**

| مدل | مالکیت | نتیجه |
|---|---|---|
| Siloed | جدا | ❌ |
| DevOps team | هماهنگی | ❌ |
| ✅ Platform/SRE | ابزار/پایداری | ✅ |

**ابزار در برابر فرآیند در برابر فرهنگ:**

| سطح | اثر |
|---|---|
| ابزار | ⚠️ کم |
| فرآیند | ✅ متوسط |
| فرهنگ | ✅✅ زیاد |

**نکته**: ابزار **آخرین** است، نه اولین.

### اشکال شایع

**اشکال ۱: «ابزار ما قدیمی است»**

مشکل معمولاً فرآیند است، نه ابزار.

**اشکال ۲: تیم DevOps برای «حل مشکل»**

شکاف اضافه می‌کند.

**اشکال ۳: ابزار بدون آموزش**

خریدیم، کسی نمی‌داند. اتلاف.

**اشکال ۴: ابزار بدون فرآیند**

pipeline داریم، ولی تأییدیه ۵ نفره. Theater.

**اشکال ۵: تیم DevOps بدون اختیار**

«هماهنگ کنید» بدون قدرت. رنج.

**اشکال ۶: ابزار برای «مدرن بودن»**

«همه دارند» استدلال نیست.

### نکات مهم (Tips & Tricks)

- **از درد شروع کن**، نه ابزار.
- **ابزار تسریع‌کننده است**، نه علت.
- **تیم DevOps نساز** — Platform یا SRE.
- **تیم موجود را تبدیل کن**، نه حذف.
- **فرآیند و فرهنگ قبل از ابزار.**
- **«چه دردی را حل می‌کند؟»** بپرس.

### خلاصه فصل

- ابزارگرایی: ابزار به‌جای مسئله.
- تیم DevOps: شکاف سوم.
- ابزار تسریع‌کننده است.
- Platform و SRE مشروع‌اند، تیم DevOps نه.
- تیم موجود را تبدیل کن.
- از درد شروع کن.

## فصل ۱۱۱: ضدالگوهای CI/CD

### مفاهیم اساسی

**ده ضدالگوی CI/CD:**

| ضدالگو | نشانه | نتیجه |
|---|---|---|
| **Pipeline قرمز مزمن** | «همیشه چند تا fail» | بی‌اعتمادی |
| **Retry همه‌چیز** | `retry: 3` سراسری | باگ پنهان |
| **Pipeline ۴۰ دقیقه** | کسی منتظر نمی‌ماند | دور زدن |
| **Test flaky** | «دوباره اجرا کن» | بی‌اعتمادی |
| **Snowflake pipeline** | هر پروژه YAML خودش | نگهداری جهنمی |
| **Deploy دستی «موقت»** | «فقط این بار» | همیشه |
| **Gate نمایشی** | merge با قرمز ممکن | بی‌فایده |
| **Cache به‌جای artifact** | «فایل نیست» | خطا |
| **Secret در YAML** | رمز در فایل | لو رفتن |
| **`latest` tag** | ایمیج `latest` | غیرقابل تکرار |

### مثال‌های عملی

**ضدالگو ۱: Pipeline قرمز مزمن**

```
وضعیت:
  main همیشه ۲-۳ تست fail دارد
  "می‌دانیم، مشکل قدیمی است"
  توسعه‌دهنده‌ها ignore می‌کنند

نتیجه:
  وقتی شکست واقعی رخ می‌دهد، کسی نمی‌فهمد
  → باگ به production می‌رود

درمان:
  ۱. تست‌های شکسته را قرنطینه کن
  ۲. main سبز (اجباری)
  ۳. رفع در ۲۴ ساعت
```

**ضدالگو ۲: Retry همه‌چیز**

```yaml
# ❌ بد
default:
  retry: 3        # برای همه jobها، همه خطاها

# نتیجه: تست شکست‌خورده هم retry می‌شود
# → باگ واقعی پنهان می‌شود
```

```yaml
# ✅ خوب
default:
  retry:
    max: 1
    when: [runner_system_failure, stuck_or_timeout_failure]
```

**نکته**: `retry` برای خطای **زیرساخت** است، نه خطای **کد**.

**ضدالگو ۳: Pipeline ۴۰ دقیقه**

```
وضعیت:
  pipeline ۴۰ دقیقه
  توسعه‌دهنده push می‌کند، کار دیگری می‌کند
  context از دست می‌رود
  merge را به تعویق می‌اندازد

نتیجه: Lead Time بیشتر، نه کمتر

درمان:
  - needs (DAG)
  - parallel
  - cache
  - ایمیج سفارشی
  - هدف: < ۱۰ دقیقه
```

**ضدالگو ۴: Snowflake pipeline**

```
وضعیت:
  ۵۰ پروژه، ۵۰ YAML متفاوت
  هر کدام روش خودش
  هیچ‌کس نمی‌تواند بین تیم‌ها جابه‌جا شود

درمان:
  - CI/CD component
  - قالب مشترک
  - golden path
```

**ضدالگو ۵: Gate نمایشی**

```
وضعیت:
  "Pipelines must succeed" خاموش
  merge با pipeline قرمز ممکن
  گاهی "استثنا" می‌زنند

نتیجه: gate وجود ندارد

درمان:
  - روشن کن
  - بدون استثنا
```

### مقایسه و الگوهای مختلف

**سه دسته ضدالگو:**

| دسته | مثال | اثر |
|---|---|---|
| **سرعت** | pipeline کند | دور زدن |
| **اعتماد** | flaky، قرمز مزمن | بی‌اعتمادی |
| **تکرارپذیری** | latest، بدون lock | غیرقابل بازتولید |

**نکته**: اعتماد، مهم‌ترین است. pipeline بی‌اعتماد، استفاده نمی‌شود.

**سه سطح درمان:**

| سطح | اقدام |
|---|---|
| سریع | `needs`، cache |
| متوسط | component، تست |
| عمیق | بازطراحی |

### اشکال شایع

**اشکال ۱: pipeline کند را «طبیعی» دانستیم**

«همیشه ۴۰ دقیقه بوده». مشکل است.

**اشکال ۲: flaky را با retry «حل» کردیم**

مسکّن. باگ پنهان.

**اشکال ۳: بدون مالک**

هر کس تغییر می‌دهد، هیچ‌کس نگه‌داری نمی‌کند.

**اشکال ۴: مراحل بی‌فایده**

«۳ سال پیش اضافه کردیم». حذف کن.

**اشکال ۵: secret در YAML**

«موقت است». همیشه می‌ماند.

**اشکال ۶: `latest` در production**

غیرقابل rollback.

### نکات مهم (Tips & Tricks)

- **main سبز، اولویت اول.**
- **`retry` هدفمند.**
- **pipeline < ۱۰ دقیقه.**
- **component برای چند پروژه.**
- **Gate بدون استثنا.**
- **مالک pipeline.**

### خلاصه فصل

- ده ضدالگو؛ قرمز مزمن و flaky بدترین.
- اعتماد، مهم‌ترین دارایی pipeline است.
- `retry` برای زیرساخت، نه کد.
- pipeline < ۱۰ دقیقه.
- Gate بدون استثنا.
- مالک تعیین کن.

## فصل ۱۱۲: ضدالگوهای سازمانی

### مفاهیم اساسی

**هشت ضدالگوی سازمانی:**

| ضدالگو | نشانه | نتیجه |
|---|---|---|
| **DevOps team** | تیم جدا | شکاف سوم |
| **Center of Excellence** | تیم «بهترین‌ها» | ❌ گلوگاه |
| **Matrix organization** | دو رئیس | ❌ سردرگمی |
| **Shared services** | تیم مشترک برای همه | ❌ صف |
| **Big Bang transformation** | همه‌جا همزمان | ❌ هیچ‌کدام |
| **KPI متناقض** | Dev سرعت، Ops پایداری | ❌ تضاد |
| **بودجه متمرکز** | هر تغییر: تأیید | ❌ کندی |
| **Outsourced DevOps** | «برون‌سپاری» | ❌ دانش نمی‌ماند |

### مثال‌های عملی

**ضدالگو ۱: Center of Excellence**

```
ایده: تیمی از «بهترین‌ها» که استاندارد تعریف کند
واقعیت:
  - تیم CoE استاندارد می‌نویسد
  - تیم‌ها اجرا نمی‌کنند (مالکیت ندارند)
  - CoE گلوگاه تأیید می‌شود

درمان: Platform team (محصول می‌سازد، نه سند)
```

**ضدالگو ۲: Matrix organization**

```
وضعیت:
  توسعه‌دهنده دو رئیس دارد: مدیر فنی + مدیر محصول
  هر تصمیم: دو تأیید
  اولویت‌ها متناقض

نتیجه: فلج، فرسودگی

درمان: یک مالک، اولویت روشن
```

**ضدالگو ۳: KPI متناقض**

```
وضعیت:
  Dev: پاداش "قابلیت تحویل‌شده"
  Ops: پاداش "حادثه صفر"
  امنیت: پاداش "صفر یافته"

نتیجه:
  Dev می‌خواهد تغییر
  Ops می‌خواهد ثبات
  امنیت می‌خواهد توقف
  → تضاد ساختاری

درمان: KPI مشترک (Lead Time + CFR)
```

**نکته**: رفتار «مقاوم» در سیستم متناقض، **عقلانی** است.

**ضدالگو ۴: Outsourced DevOps**

```
وضعیت:
  "DevOps را به پیمانکار سپردیم"
  پیمانکار pipeline می‌سازد
  بعد از قرارداد: هیچ‌کس نمی‌داند چطور کار می‌کند

درمان:
  - دانش باید درون‌سازمانی بماند
  - پیمانکار برای ظرفیت، نه مالکیت
  - مستندسازی الزامی
```

### مقایسه و الگوهای مختلف

**سه مدل سازمانی:**

| مدل | هماهنگی | مناسب |
|---|---|---|
| Functional | ❌ زیاد | کوچک |
| Matrix | ❌ سردرگمی | ❌ |
| ✅ Stream-aligned | کم | ✅ |

**Center of Excellence در برابر Platform:**

| معیار | CoE | Platform |
|---|---|---|
| خروجی | سند، استاندارد | ✅ محصول |
| مالکیت | ❌ | ✅ |
| پذیرش | ❌ کم | ✅ بالا |

**نکته**: CoE **می‌گوید** چه کار کن؛ Platform **می‌سازد** چه کار کن.

**سه سطح درمان:**

| سطح | اقدام |
|---|---|
| سریع | KPI مشترک |
| متوسط | ساختار تیم |
| عمیق | مدل عملیاتی |

### اشکال شایع

**اشکال ۱: تیم جدید برای هر مشکل**

DevOps team، CoE، Transformation Office — همه شکاف اضافه می‌کنند.

**اشکال ۲: KPI بدون بازبینی**

۵ سال پیش تعریف شد، هنوز متناقض.

**اشکال ۳: برون‌سپاری بدون انتقال دانش**

قرارداد تمام، دانش رفت.

**اشکال ۴: Matrix بدون تصمیم‌گیر**

دو رئیس، هیچ‌کدام مالک.

**اشکال ۵: Shared services بدون SLA**

تیم مشترک، صف بی‌نهایت.

**اشکال ۶: Big Bang**

همه‌جا، هیچ‌کدام.

### نکات مهم (Tips & Tricks)

- **تیم جدید نساز** — ساختار موجود را تغییر بده.
- **KPI مشترک**، نه متناقض.
- **یک مالک** برای هر تصمیم.
- **برون‌سپاری با انتقال دانش.**
- **Platform به‌جای CoE.**
- **تدریجی، نه Big Bang.**

### خلاصه فصل

- هشت ضدالگو؛ DevOps team و KPI متناقض رایج‌ترین.
- CoE گلوگاه می‌شود؛ Platform محصول می‌سازد.
- Matrix بدون مالک، فلج می‌کند.
- KPI متناقض، تضاد ساختاری می‌سازد.
- برون‌سپاری بدون دانش، شکست.
- تیم جدید نساز.

## فصل ۱۱۳: ضدالگوهای فرهنگی

### مفاهیم اساسی

**هفت ضدالگوی فرهنگی:**

| ضدالگو | نشانه | نتیجه |
|---|---|---|
| **Blame culture** | «مقصر کی؟» | پنهان‌کاری |
| **Hero culture** | «فقط علی می‌تواند» | شکنندگی، فرسودگی |
| **Bus factor 1** | یک نفر همه‌چیز می‌داند | ریسک بحرانی |
| **Knowledge hoarding** | «اگر من تنها باشم، امنم» | شکنندگی |
| **Meeting culture** | ۵ جلسه در روز | وقت صفر |
| **Perfectionism** | «آماده نیست» | هرگز منتشر نمی‌شود |
| **Change fatigue** | «هر ماه یک تحول» | بدبینی |

### مثال‌های عملی

**ضدالگو ۱: Hero culture**

```
وضعیت:
  علی تنها کسی است که می‌داند سیستم چطور کار می‌کند
  علی هر حادثه را حل می‌کند
  علی قهرمان است، پاداش می‌گیرد

نتیجه:
  - علی خسته می‌شود
  - اگر برود، فاجعه
  - کسی دیگر یاد نمی‌گیرد
  - علی انگیزه ندارد مستند کند (قدرتش است)

درمان:
  - مستندسازی در Definition of Done
  - rotation on-call
  - پاداش برای انتقال دانش، نه فقط حل
```

**نکته**: Hero culture **قهرمان را پاداش می‌دهد** و **سیستم را جریمه می‌کند**.

**ضدالگو ۲: Perfectionism**

```
وضعیت:
  "این قابلیت آماده نیست، ۳ ماه دیگر"
  بعد: "هنوز آماده نیست"
  هیچ‌وقت منتشر نمی‌شود

نتیجه: ارزش صفر

درمان:
  - MVP کوچک
  - feature flag
  - انتشار تدریجی
```

**نکته**: «کامل» دشمن «خوب» است.

**ضدالگو ۳: Change fatigue**

```
وضعیت:
  ماه ۱: "Agile بیاوریم"
  ماه ۳: "DevOps بیاوریم"
  ماه ۵: "Platform بیاوریم"
  ماه ۷: "دوباره Agile"

نتیجه: بدبینی، بی‌اعتمادی

درمان:
  - یک تحول در زمان
  - ۱۸-۳۶ ماه
  - نتیجه نشان بده
```

**ضدالگو ۴: Meeting culture**

```
وضعیت:
  daily (15m) + sync (30m) + planning (1h) + retro (1h)
  + 3 جلسه هماهنگی (2h)
  = ۵ ساعت جلسه در روز

نتیجه: ۳ ساعت برای کار

درمان:
  - جلسات را حذف یا async
  - "این جلسه چه خروجی دارد؟"
```

### مقایسه و الگوهای مختلف

**Hero در برابر تیم:**

| معیار | Hero | تیم |
|---|---|---|
| سرعت اولیه | ✅ | متوسط |
| پایداری | ❌ | ✅ |
| ریسک | ❌ بالا | ✅ کم |

**سه سطح bus factor:**

| سطح | ریسک |
|---|---|
| ۱ نفر | ❌ بحرانی |
| ۲ نفر | ⚠️ |
| ۳+ | ✅ |

**نکته**: Bus factor را اندازه بگیر: «اگر X فردا برود، چه می‌شود؟»

**Perfectionism در برابر MVP:**

| معیار | Perfectionism | MVP |
|---|---|---|
| زمان | ❌ طولانی | ✅ سریع |
| بازخورد | ❌ دیر | ✅ زود |
| ریسک | ❌ بالا | ✅ کم |

### اشکال شایع

**اشکال ۱: Hero را تشویق کردیم**

پاداش قهرمانی، سیستم را خراب می‌کند.

**اشکال ۲: دانش به‌عنوان قدرت**

فرهنگ سازمانی. پاداش معکوس لازم.

**اشکال ۳: جلسات بی‌هدف**

«همیشه بوده». حذف کن.

**اشکال ۴: کمال‌گرایی**

«آماده نیست» — هرگز.

**اشکال ۵: تحول ماهانه**

بدبینی. یک تحول، ۲ سال.

**اشکال ۶: Blame پنهان**

«چرا تست نکردی؟» در لفافه.

### نکات مهم (Tips & Tricks)

- **Bus factor را اندازه بگیر.**
- **مستندسازی در DoD.**
- **پاداش برای انتقال دانش.**
- **جلسات را بازبینی کن.**
- **MVP، نه کامل.**
- **یک تحول در زمان.**

### خلاصه فصل

- هفت ضدالگو؛ Hero culture و blame بدترین.
- Hero culture قهرمان را پاداش، سیستم را جریمه می‌کند.
- Bus factor ۱ = ریسک بحرانی.
- جلسات بی‌هدف، وقت را می‌خورند.
- کمال‌گرایی، دشمن انتشار.
- یک تحول در زمان.

## فصل ۱۱۴: چطور ضدالگو را تشخیص دهیم

### مقدمه

تشخیص، اولین قدم درمان است. این فصل ابزارهای تشخیص را می‌آورد.

### مفاهیم اساسی

**پنج روش تشخیص:**

| روش | چه می‌یابد |
|---|---|
| **پرسشنامه** | الگوهای کلی |
| **مصاحبه** | جزئیات، دلیل |
| **مشاهده** | رفتار واقعی |
| **داده** | متریک عینی |
| **بازبینی postmortem** | فرهنگ |

**نکته**: داده + مشاهده، دقیق‌ترین ترکیب.

### مثال‌های عملی

**پرسشنامه ضدالگو — ۱۵ سؤال:**

```
به هر سؤال بله/خیر جواب بده:

CI/CD:
۱. آیا merge بدون pipeline سبز ممکن است؟
۲. آیا در ۳ ماه گذشته کسی pipeline را دور زده؟
۳. آیا میانگین زمان pipeline > ۱۵ دقیقه است؟
۴. آیا نرخ تست flaky > ۵٪ است؟

سازمان:
۵. آیا تیمی به نام "DevOps" دارید که واسط است؟
۶. آیا KPI تیم‌ها متناقض است؟
۷. آیا هر تغییر نیاز به ۳+ تأیید دارد؟

فرهنگ:
۸. آیا در حادثه اول «مقصر کی؟» پرسیده می‌شود؟
۹. آیا bus factor = ۱ در بخش حیاتی دارید؟
۱۰. آیا در retro همه می‌گویند «همه‌چیز خوب بود»؟

انتشار:
۱۱. آیا deploy به production کمتر از هفتگی است؟
۱۲. آیا rollback بیش از ۳۰ دقیقه طول می‌کشد؟
۱۳. آیا migration بدون rollback plan انجام می‌شود؟

ابزار:
۱۴. آیا ابزاری دارید که کسی استفاده نمی‌کند؟
۱۵. آیا ابزار جدید در ۶ ماه گذشته بدون نتیجه اضافه شده؟

امتیاز:
  ۰-۳: سالم
  ۴-۷: هشدار
  ۸+: ❌ نیاز جدی
```

**مشاهده — چک‌لیست یک روز:**

```
یک روز با تیم بنشین و ببین:

[ ] چند بار کسی منتظر چیزی بود؟
[ ] چند بار context switch شد؟
[ ] چند جلسه بود؟ چند تا خروجی داشت؟
[ ] وقتی خطا رخ داد، واکنش چه بود؟
[ ] چه کسی تصمیم گرفت؟ چقدر طول کشید؟
[ ] چند بار «باید از X بپرسیم» گفته شد؟
```

**نکته**: مشاهده، چیزهایی را نشان می‌دهد که هیچ پرسشنامه‌ای نمی‌گیرد.

**تحلیل داده — پنج متریک:**

```bash
# ۱. فرکانس merge
git log --merges --since="3 months ago" --oneline | wc -l

# ۲. اندازه MR
git log --since="3 months ago" --shortstat | \
  awk '{add+=$4; del+=$6} END {print "میانگین خط:", (add+del)/NR}'

# ۳. مدت pipeline
# از API CI

# ۴. فرکانس deploy
# از تاریخ deploy

# ۵. MTTR
# از incident log
```

**بازبینی postmortem — پنج معیار:**

| معیار | سالم | ناسالم |
|---|---|---|
| نام مقصر | ❌ ندارد | ✅ دارد |
| اقدام | ✅ با مالک | ❌ ندارد |
| «چه خوب پیش رفت» | ✅ دارد | ❌ ندارد |
| زمان نوشتن | < ۴۸ ساعت | هفته‌ها |
| پیگیری | ✅ انجام شد | ❌ فراموش |

### مقایسه و الگوهای مختلف

**تشخیص داخلی در برابر خارجی:**

| معیار | داخلی | خارجی |
|---|---|---|
| صداقت | ⚠️ | ✅ |
| زمینه | ✅ | ❌ |
| هزینه | ✅ | ❌ |

**توصیه**: داخلی + facilitator خارجی برای مصاحبه.

**سه سطح تشخیص:**

| سطح | زمان | خروجی |
|---|---|---|
| سریع | ۱ ساعت | پرسشنامه |
| متوسط | ۱ هفته | + مصاحبه |
| عمیق | ۱ ماه | + مشاهده |

**تشخیص در برابر سرزنش:**

| معیار | تشخیص | سرزنش |
|---|---|---|
| هدف | بهبود | ارزیابی |
| لحن | ✅ | ❌ |
| نتیجه | ✅ اعتماد | ❌ پنهان‌کاری |

### اشکال شایع

**اشکال ۱: تشخیص برای سرزنش**

«تیم شما ضدالگو دارد» — مقاومت. سیستم را ببین.

**اشکال ۲: فقط پرسشنامه**

نظر ≠ رفتار. مشاهده لازم.

**اشکال ۳: بدون داده**

«حس می‌کنیم» — عدد بیاور.

**اشکال ۴: یک‌بار تشخیص**

هر ۶ ماه تکرار کن.

**اشکال ۵: تشخیص بدون درمان**

گزارش زیبا، بدون تغییر.

**اشکال ۶: نادیده گرفتن سیگنال ضعیف**

«کسی داوطلب on-call نمی‌شود» — نشانه.

### نکات مهم (Tips & Tricks)

- **پرسشنامه + مشاهده + داده.**
- **مشاهده دقیق‌ترین است.**
- **برای بهبود، نه سرزنش.**
- **هر ۶ ماه.**
- **هر تشخیص، یک اقدام.**
- **سیگنال‌های ضعیف را ببین.**

### خلاصه فصل

- پنج روش تشخیص.
- پرسشنامه ۱۵ سؤالی.
- مشاهده، چیزهایی می‌بیند که پرسشنامه نه.
- داده عینی، بحث را تمام می‌کند.
- برای بهبود، نه سرزنش.
- هر تشخیص، یک اقدام.
