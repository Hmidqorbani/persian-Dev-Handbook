## فصل ۱: UX برای خروجی غیرقطعی

> **سطح**: سطح ۳ — این فصل اولین مهارت سطح ۳ را می‌سازد: طراحی تجربه‌ی کاربری برای قابلیتی که کندی متغیر، عدم قطعیت و خطای فازی دارد — streaming، لغو، ویرایش‌پذیری و صداقت درباره‌ی چیزی که مدل است و نیست.

### مقدمه

تا این‌جا مسئله‌ها مهندسی بودند؛ از این فصل، مسئله «کاربر واقعی» است. و کاربر واقعی، با چیزهایی رو‌به‌رو می‌شود که در دموی خودت ندیدی:

- دکمه را می‌زند و **سه ثانیه** صبر می‌کند — یا سی ثانیه.
- جواب می‌گیرد که **معقول است ولی ممکن است غلط باشد** — و نمی‌داند کدام بخش.
- وسط جوابِ طولانی **پشیمان می‌شود** و دکمه‌ی لغو می‌خواهد.
- جواب را می‌خواهد **تغییر بدهد**، نه فقط بخواند.

تفاوت «دموی خوب» و «قابلیتی که کاربر روی آن حساب می‌کند»، اکثراً در همین لایه است. فلسفه‌ی کل فصل یک جمله دارد:

> **UX قابلیت AI، یعنی صادق بودن درباره‌ی ماهیت مدل: کندی متغیر، خروجی احتمالاتی، خطای ممکن — و دادن کنترل به کاربر در همه‌ی این‌ها.**

هر وعده‌ای که رابط کاربری بدهد («این پاسخ قطعی است»، «همیشه جواب می‌دهیم») باید بعداً شکسته شود؛ هر صداقتی (منبع‌نمایی، لغو، ویرایش) اعتماد می‌سازد. این فصل الگوهای عملی این صداقت است.

### مفاهیم اساسی

#### تفاوت ذاتی با UXهای عادت‌شده

| ویژگی قابلیت AI | انتظار کاربر از وب معمولی | طراحی لازم |
|---|---|---|
| تأخیر متغیر (۲–۳۰ ثانیه) | زیر ۵۰۰ میلی‌ثانیه | streaming + مدیریت انتظار |
| خروجی احتمالاتی | خروجی قطعی (جست‌وجو = لیست ثابت) | نمایش منبع، تمایز داده/حدس |
| خطای فازی («نمی‌توانم این را تضمین کنم») | خطای باینری (موفق/شکست) | پیام صادقانه + مسیر جایگزین |
| طول خروجی نامعلوم | فرم مشخص | لغو + ویرایش‌پذیری |

#### Streaming: مهم‌ترین اهرم ادراک سرعت

واقعیت فیزیکی: تولید توکن‌به‌توکن است (فایل ۰۲ فصل ۶) و جواب کامل ممکن است چند ثانیه طول بکشد. streaming یعنی **کاربر از همان ثانیه‌ی اول محتوا را می‌بیند** — تأخیر ادراکی از «۳۰ ثانیه‌ی خالی» به «شروع فوری + جریان» تبدیل می‌شود. حتی اگر جمعِ زمان یکسان باشد، تجربه فرق اساسی دارد.

معماری عملی: مدل streaming می‌دهد → بک‌اند تو به فرانت رله می‌کند (معمولاً با SSE یا WebSocket):

```text
مدل ──(توکن‌ها)──► بک‌اند تو ──(SSE/WebSocket)──► فرانت‌اند ──► رندر تدریجی
```

کلید از بک‌اند، همیشه (فایل ۰۱) — فرانت هرگز مستقیم به ارائه‌دهنده وصل نمی‌شود.

و یک استثنای مهم که تیم‌ها جا می‌اندازند: **خروجی ساخت‌یافته streaming نمی‌خواهد.** JSON نیمه‌تمیز قابل parse نیست؛ اگر مصرف‌کننده کد است (فایل ۰۴)، یکجا بگیر؛ streaming مال «متن رو به انسان» است.

#### مدیریت انتظار: صادق بودن در انتظار

وقتی streaming ممکن نیست (پردازش سنگین، batch، fallback):

- **وضعیت واقعی نشان بده**: «در حال خواندن اسناد...» بهتر از اسپینر همیشه‌ی «در حال پردازش...» است — مراحل پیپ‌لاین (فایل ۰۵) قابل نمایش‌اند.
- **زمان‌بندی صادقانه**: «معمولاً کمتر از ۳۰ ثانیه» — و اگر طولانی شد، پیام به‌روزرسانی.
- **اسکلتون محتوا** به‌جای اسپینر عمومی: کاربر می‌داند چه شکلی می‌آید.

#### لغو (Cancellation): کنترل کاربر

کاربر باید بتواند وسط تولید، کار را قطع کند — و لغو دو لایه دارد:

1. **فرانت**: قطع اتصال استریم و رندر.
2. **بک‌اند**: توقف فراخوانی مدل (abort) تا توکن‌های باقی‌مانده پرداخت نشوند — و ثبت در trace که لغو شده.

نکته‌ی صادقانه: لغو بلافاصله همیشه تضمین نیست (تا نوبت API برگردد، بخشی توکن خورده)؛ در پیام لغو، وعده‌ی «صفر هزینه» نده.

#### ویرایش‌پذیری: مدل پیشنهاد می‌دهد، کاربر تصمیم می‌گیرد

شاید مهم‌ترین الگوی اعتماد در محصولات موفق: خروجی AI به‌عنوان **پیش‌نویس قابل ویرایش** ارائه شود، نه متن نهایی:

- جواب چت‌بات: دکمه‌ی «کپی/بازنویسی/نمایش منابع».
- متن تولیدی: ادیتور قابل ویرایش + «دوباره تولید کن».
- عملیات: پیش‌نمایش + تأیید (همان dry-run فایل ۰۴ و ۰۶ — این‌جا صورت UX‌اش است).

این الگو هم مسئولیت را درست می‌کند (کاربر ویرایش کرده = تأیید ضمنی) و هم توهم‌زایی را بی‌ضررتر (کاربر قبل از ارسال، حدس‌ها را می‌بیند و اصلاح می‌کند).

#### نمایش عدم قطعیت و منابع

- **ارجاع اجباری در RAG** (فایل ۰۵) در UI قابل کلیک: کاربر روی [1] می‌زند و سند اصلی را می‌بیند — راستی‌آزمایی در دست کاربر.
- **تمایز داده از حدس**: عدد از دیتابیس (از ابزار آمد) در برابر جمله‌ی استنتاجی — حداقل با گروه‌بندی بصری یا برچسب.
- **مسیر «در مستندات نیست»** (فایل ۰۵) را طراحی کن: دکمه‌ی «ارجاع به پشتیبانی انسانی» — ارجاعِ درست، بهتر از جوابِ نصفه است.

### مثال‌های عملی

#### مثال ۱: رله‌ی streaming از بک‌اند به مرورگر (SSE)

بک‌اند (پایتون، بدون فریم‌ورک سنگین):

```python
"""stream_relay.py — رله‌ی استریم مدل به مرورگر با SSE.
اجرا: uvicorn stream_relay:app  (pip install fastapi uvicorn openai)"""
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from openai import OpenAI

app = FastAPI()
client = OpenAI()

SYSTEM = "پاسخ‌ها را کوتاه و به فارسی بده."


def token_stream(question: str):
    """توکن‌های مدل را به‌صورت قالب SSE بیرون می‌دهد."""
    stream = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "system", "content": SYSTEM},
                  {"role": "user", "content": question}],
        stream=True,                       # فایل ۰۲ فصل ۶
    )
    for chunk in stream:
        piece = chunk.choices[0].delta.content
        if piece:
            yield f"data: {piece}\n\n"     # قالب SSE: هر تکه با data: و خط خالی
    yield "data: [DONE]\n\n"               # نشانه‌ی پایان برای فرانت


@app.get("/ask")
def ask(q: str):
    return StreamingResponse(
        token_stream(q),
        media_type="text/event-stream",    # فرانت جریان را زنده می‌خواند
        headers={"Cache-Control": "no-cache"},
    )
```

فرانت‌اند (بدون فریم‌ورک، فقط fetch و DOM):

```javascript
// ask.mjs — خواندن جریان SSE و رندر تدریجی
const answerEl = document.getElementById("answer");
answerEl.textContent = "";

// AbortController: دکمه‌ی لغو همین‌جا وصل می‌شود
const controller = new AbortController();
window.stopButton.onclick = () => controller.abort();   // لغو — مثال ۲

const response = await fetch(`/ask?q=${encodeURIComponent(question)}`, {
  signal: controller.signal,
});
const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  // هر پیام SSE با خط خالی تمام می‌شود؛ بافر را بر اساس آن بشکن
  const parts = buffer.split("\n\n");
  buffer = parts.pop();                      // تکه‌ی ناقص آخر می‌ماند
  for (const part of parts) {
    const text = part.replace(/^data: /, "").trim();
    if (text === "[DONE]") continue;
    answerEl.textContent += text;            // رندر تدریجی — کاربر همان لحظه می‌بیند
  }
}
```

این دو تکه، اسکلت همه‌ی چت‌بات‌های دنیاست. نکات مهندسی داخل کد: بافرِ شکستن SSE (تکه‌ها به مرز پیام نمی‌خورند)، و `AbortController` که مثال بعد کاملش می‌کند.

#### مثال ۲: لغو واقعی — فرانت و بک‌اند

```javascript
// لغو از سمت فرانت: اتصال را قطع کن و UI را بازگردان
cancelButton.onclick = () => {
  controller.abort();
  answerEl.textContent += "\n[لغو شد]";        // وضعیت صادقانه، نه حذفِ بی‌سروصدا
  cancelButton.hidden = true;
};
```

```python
# سمت بک‌اند: ردیابی لغو و توقف فراخوانی مدل (best-effort)
from fastapi import Request

@app.get("/ask")
def ask(q: str, request: Request):
    def token_stream(question: str):
        try:
            stream = client.chat.completions.create(..., stream=True)
            for chunk in stream:
                piece = chunk.choices[0].delta.content
                if piece:
                    yield f"data: {piece}\n\n"
            yield "data: [DONE]\n\n"
        except Exception:
            # قطع شدن اتصال سمت کلاینت این‌جا می‌آید؛ فراخوانی را رها کن
            if await_is_disconnected(request):     # شِمای helper — بسته به فریم‌ورک
                stream.close()                     # توکن‌های باقی‌مانده آزاد می‌شوند
            return
```

در production، ردیابی دقیقِ لغو به فریم‌ورک وابسته است؛ اصل، ثابت است: **قطع اتصال → بستن فراخوانی مدل → ثبت در trace** (فایل ۰۶) که «لغو کاربر» بوده، نه خطا.

#### مثال ۳: الگوهای وضعیت — سه حالت که هر قابلیت AI باید داشته باشد

هر قابلیت AI، سه وضعیتِ غیر از «نتیجه» دارد و هر سه باید طراحی شوند:

```text
۱. در حال کار      → streaming یا اسکلتون + مرحله‌ی واقعی («در حال جست‌وجوی اسناد…»)
۲. نتیجه           → پیش‌نویس قابل ویرایش + منابع [n] قابل کلیک + «دوباره تولید»
۳. ناموفق/خالی     → پیام صادقانه («این مورد در مستندات نیست» یا «سرویس در دسترس نیست»)
                     + دکمه‌ی «تلاش دوباره» + مسیر جایگزین (ارجاع انسانی)
```

قاعده‌ی یک‌خطی برای هجوم: **هر جا تو در دموی خودت «همیشه خوب جواب می‌گیرم»، همان‌جا یک حالت طراحی‌نشده است.** لیست حالت‌ها را در سند قابلیت بنویس؛ فایل ۱۱ (پروژه) همین الگو را کامل اجرا می‌کند.

### مقایسه و الگوهای مختلف

#### streaming در برابر blocking — جدول تصمیم

| معیار | streaming | blocking (یکجا) |
|---|---|---|
| مصرف‌کننده | انسان در UI | کد، batch، pipeline |
| ادراک سرعت | شروع فوری | انتظار کامل |
| پیچیدگی | SSE/WebSocket + حالت‌ها | ساده |
| خروجی ساخت‌یافته (JSON) | نامناسب — نیمه‌تمیز parse نمی‌شود | مناسب |
| حکم | **متن رو به کاربر** | **داده رو به کد** |

و برای خواندنی‌های طولانی، الگوی میانی: **blocking با پیش‌نمایش** — جواب کوتاه فوری (از مدل ارزان) + جواب کامل بعداً (وصل‌کردن به notification).

#### ترتیب اعمال UX: از ارزان‌ترین بهساز به گران‌ترین

| ارتقا | هزینه | اثر ادراکی |
|---|---|---|
| streaming | کم (فایل ۰۲ فصل ۶ + رله) | بزرگ — اول همین |
| حالت‌های خطا و لغو | کم–متوسط | بزرگ در اعتماد |
| ویرایش‌پذیری + «دوباره تولید» | متوسط | بزرگ در کنترل کاربر |
| منبع‌نمایی قابل کلیک | متوسط (پایه‌اش از فایل ۰۵) | بزرگ در RAG |
| ترتیب محو تدریجی/انیمیشن‌ها | کم | خوشایند ولی کم‌اثر — آخر |

### اشکال شایع

**۱. لودینگ ابدی.**
اسپینری که هیچ‌وقت حالت «ناموفق» نمی‌شود — چون timeout و پیام شکست طراحی نشده. هر انتظار، سقف زمان و مسیر بعد از آن دارد (fallback کامل در فایل ۰۹).

**۲. خروجی غیرقابل ویرایش.**
متن نهایی‌شده که کاربر فقط کپی می‌کند — توهم‌زایی را بدون مهار می‌گذارد و کاربر را مجبور به «یا همه یا هیچ» می‌کند. پیش‌نویس قابل ویرایش، الگوی پیش‌فرض.

**۳. ادعای قطعیت.**
بدون منبع، بدون تمایز داده/حدس، با لحن «دقیق» — کاربر اعتماد می‌کند، مدل یک‌بار خطا می‌کند، اعتماد همیشه می‌رود. صادق بودن از اول، ارزان‌تر از جبران است.

**۴. پیام خطای فنی.**
«OpenAI API Error 429» به کاربر — نه معنا دارد نه راه‌حل. ترجمه‌ی خطا به زبان کاربر + گام بعدی («چند لحظه بعد تلاش کن» یا «به پشتیبانی ارجاع شد»).

**۵. لغو نصفه‌نیمه.**
فرانت قطع می‌کند، بک‌اند تا تمام توکن‌ها را می‌خواند و می‌پردازد — نیم‌پردازشِ لغو‌شده در لاگ «موفق» ثبت می‌شود. لغو باید در هر دو لایه و در trace یکدست باشد.

**۶. درخواست‌های موازیِ بلا نشده.**
کاربر دکمه را پنج بار می‌زند (چون حالت «در حال کار» گویا نبوده) — پنج فراخوانی مدل. قفل‌کردن دکمه در حالت در حال کار + dedupe سمت بک‌اند.

### نکته‌های مهم (Tips & Tricks)

- اولین تکه‌ی استریم را **تا حد امکان زود** بفرست؛ حتی یک «در حال فکر کردن...» از سر بک‌اند، ادراک سرعت را عوض می‌کند.
- در چت‌بات، **جواب‌های کوتاه را تشویق کن** (پرامپت + قالب): پاسخ دوخطی streaming، هم ارزان‌تر است هم UX بهتری دارد.
- دکمه‌ی «دوباره تولید» را **همراه با ویرایش‌پذیری** بگذار — ترکیب، حسِ کنترل کامل می‌دهد و خطای‌های تک‌ران را جبران می‌کند.
- برای RAG، **منبع را همان خط جواب نشان بده** نه در انتها — کاربر هم‌زمان می‌خواند و راستی‌آزمایی می‌کند.
- feedback سبک بگذار (👍/👎 روی هر پاسخ) — همین سیگنال‌ها، dataset eval (فایل ۰۷) و نمونه‌های production تو می‌شوند.
- متن‌های UI را **قابل تغییر در config** نگه‌دار؛ پیام‌های AI (اعتماد، محدودیت) پرتغییرند و نباید deploy بخواهند.

### خلاصه‌ی فصل

- فلسفه: **صداقت درباره‌ی ماهیت مدل** — کندی متغیر، خروجی احتمالاتی، خطای ممکن — و کنترل کاربر در همه.
- **streaming** برای متن رو به انسان؛ **blocking** برای داده رو به کد — جدول تصمیم حفظ شود.
- سه حالت طراحی‌نشده = دموی مرده: **در حال کار، نتیجه، ناموفق** — هرکدام با پیام و مسیر.
- **لغو دو لایه** دارد (فرانت + بک‌اند) و در trace ثبت می‌شود؛ وعده‌ی صفر‌هزینه نده.
- **ویرایش‌پذیری + منبع‌نمایی** دو بزرگ‌ترین سازنده‌ی اعتماد‌اند — مدل پیش‌نویس می‌دهد، کاربر تصمیم می‌گیرد.

### مقدمه

فصل قبل الگوهای تعامل را ساخت (streaming، لغو، ویرایش)؛ این فصل تصمیم سطح بالاتر است: **قابلیت AI در کدام جای محصول زندگی می‌کند؟** سه گزینه‌ی اصلی دارد — داخل جریان کار کاربر (embedded)، به‌عنوان گفتگوی باز (chat)، یا در پس‌زمینه بدون حضور کاربر (async) — و انتخاب بین آن‌ها، تأثیر مستقیم روی هزینه، انتظار کاربر و معماری دارد.

و نیمه‌ی دوم فصل، نیمه‌ای که کمتر گفته می‌شود: **کجا AI نگذاریم.** هر قابلیت AI هزینه (فایل ۰۹)، تأخیر، عدم قطعیت و ریسک امنیتی (فایل ۰۷) دارد؛ گذاشتن AI در جایی که یک query ساده کار را می‌کند، همه‌ی این‌ها را بابت صفر اثر می‌خرد. تصمیم‌های منفیِ آگاهانه، بخشی از مهندسی سطح ۳ است.

### مفاهیم اساسی

#### سه الگوی یکپارچه‌سازی

| الگو | شکل | کاربرد مثال | ویژگی کلیدی |
|---|---|---|---|
| **Embedded (درون جریان کار)** | AI یک قابلیت درون UI است: خلاصه‌سازی، پیشنهاد، استخراج | «خلاصه‌ی این تیکت»، «کامل کن»، دستیار فرم | تعامل کوتاه، زمینه‌ی مشخص، خروجی جای‌گذاری‌شده |
| **Chat (گفتگوی باز)** | پنل/صفحه‌ی گفتگو با ابزارها | دستیار پشتیبانی، جست‌وجوی طبیعی | ورودی آزاد، چندنوبته، خروجی غیرقابل پیش‌بینی |
| **Background/Async (پس‌زمینه)** | پردازش بدون انتظار کاربر | استخراج از هزار فاکتور، تحلیل شبانه، ایندکس‌سازی | صف، وضعیت job، بدون streaming |

معیارهای انتخاب — سه سؤال:

1. **کاربر باید صبر کند؟** صبر لحظه‌ای با streaming → embedded/chat؛ صبر نمی‌کند → async.
2. **ورودی باز است یا مشخص؟** مشخص و قالب‌دار → embedded؛ باز → chat.
3. **خروجی مستقیم استفاده می‌شود یا پردازش می‌شود؟** نمایش → chat/embedded؛ ذخیره/تحول → async.

اکثر محصولات بالغ ترکیبی‌اند: چند embedded مشخص + یک chat عمومی + چند job پس‌زمینه‌ای.

#### معماری بک‌اند: خطوط قرمز ثابت

از فایل ۰۱ و ۰۴ تا این‌جا، این‌ها قانون‌اند و این‌جا در جای معماری می‌نشینند:

```text
فرانت‌اند ──► API خودت ──► لایه‌ی قابلیت AI ──► ارائه‌دهنده
                    (کلیدها این‌جا)         (پرامپت/ابزار/گاردها)
```

- **کلید فقط در بک‌اند**؛ فرانت به endpoint خودت وصل است.
- **لایه‌ی قابلیت، مستقل از فرانت**: پرامپت‌ها (فایل ۰۳)، ابزارها (فایل ۰۴)، گاردها (فایل ۰۷) سمت سرور می‌مانند — فرانت فقط «درخواست» می‌فرستد.
- **قابلیت AI = قابلیت معمولی**: feature flag، لاگ، تست، نسخه — همان حقوق بقیه‌ی کد (فایل ۰۳ فصل ۴).

#### async: صف، وضعیت، اتمام

پردازش پس‌زمینه سه قطعه می‌خواهد که در sync نداری:

```text
۱. صف (job store)      → کارها وارد و مصرف می‌شوند (sqlite تا worker واقعی)
۲. worker              → پردازش با مدل؛ خطا را retry می‌کند (فایل ۰۹)
۳. وضعیت job           → کاربر/فرانت می‌پرسد: «تمام شد؟» (polling یا رویداد)
```

بدون این سه، async یعنی «فرستادم و امیدوارم» — که در فاکتورهای هزارتایی، خبر بدی است.

#### کجا AI نگذاریم — جدول تصمیم

| وضعیت | تصمیم | چرا |
|---|---|---|
| محاسبه/منطق قطعی (مالی، قواعد) | کد سنتی | دقیق، ارزان، تست‌پذیر (فایل ۰۱ فصل ۱) |
| جایی که query/فرم ساده کافی است | UI معمولی | AI تأخیر و هزینه اضافه با صفر اثر |
| حجم عظیم با کیفیت ادراکی مهم | async + ارزیابی سخت | هزینه‌ی کنترل‌شده |
| داده‌ی فوق‌حساس بدون مجوز ارائه‌دهنده | mask یا self-host یا نه | فایل ۰۷ و ۰۳ این فصل |
| «جذاب به نظر می‌رسد» بدون مسئله واقعی | نه | هزینه بدون ارزش — سؤال «کدام مسئله؟» |

قاعده‌ی نهایی: **AI ابزار مسئله است، نه ویژگی محصول.** «در产品 ما AI هم هست» ارزشی نیست؛ «این کار حالا ۱۰ برابر سریع‌تر است» ارزش است.

### مثال‌های عملی

#### مثال ۱: job queue ساده با SQLite — الگوی کامل async

```python
"""job_queue.py — پردازش پس‌زمینه: صف، worker، وضعیت. (دموی الگو؛ در مقیاس: Celery/queue واقعی)"""
import json
import sqlite3
import time
import threading
from openai import OpenAI

client = OpenAI()
DB = "jobs.db"

def _conn():
    conn = sqlite3.connect(DB, timeout=10)
    conn.row_factory = sqlite3.Row
    return conn

def setup() -> None:
    with _conn() as conn:
        conn.executescript("""
        CREATE TABLE IF NOT EXISTS jobs (
            id INTEGER PRIMARY KEY,
            kind TEXT NOT NULL,            -- نوع پردازش (مثلاً summarize_doc)
            payload TEXT NOT NULL,         -- داده‌ی ورودی (JSON)
            status TEXT NOT NULL DEFAULT 'pending',  -- pending/running/done/failed
            result TEXT,
            created_at REAL NOT NULL,
            updated_at REAL NOT NULL
        );
        """)

def enqueue(kind: str, payload: dict) -> int:
    """API برای فرانت/سرویس‌ها: کار را می‌گذارد و سریع job_id می‌دهد."""
    now = time.time()
    with _conn() as conn:
        cur = conn.execute(
            "INSERT INTO jobs (kind, payload, created_at, updated_at) "
            "VALUES (?, ?, ?, ?)", (kind, json.dumps(payload, ensure_ascii=False), now, now))
        return cur.lastrowid

def job_status(job_id: int) -> dict:
    """endpoint وضعیت: فرانت این را polling می‌کند (یا رویداد می‌فرستد)."""
    with _conn() as conn:
        row = conn.execute("SELECT status, result FROM jobs WHERE id = ?",
                           (job_id,)).fetchone()
        if row is None:
            return {"error": "not_found"}
        return {"status": row["status"],
                "result": json.loads(row["result"]) if row["result"] else None}


def worker_loop(poll_seconds: float = 1.0) -> None:
    """worker: کارهای pending را می‌برد، پردازش می‌کند، وضعیت می‌گذارد."""
    while True:
        with _conn() as conn:
            row = conn.execute(
                "SELECT * FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 1"
            ).fetchone()
            if row is None:
                time.sleep(poll_seconds)
                continue
            conn.execute("UPDATE jobs SET status='running', updated_at=? WHERE id=?",
                         (time.time(), row["id"]))

        try:
            payload = json.loads(row["payload"])
            # این‌جا منطق قابلیت AI می‌نشیند — مثال: خلاصه‌سازی
            response = client.chat.completions.create(
                model="gpt-4o-mini", temperature=0,
                messages=[
                    {"role": "system", "content": "خلاصه‌ی حداکثر سه‌جمله‌ای به فارسی بده."},
                    {"role": "user", "content": payload["text"]},
                ],
            )
            result = response.choices[0].message.content
            with _conn() as conn:
                conn.execute("UPDATE jobs SET status='done', result=?, updated_at=? WHERE id=?",
                             (json.dumps(result, ensure_ascii=False), time.time(), row["id"]))
        except Exception as exc:                      # خطا → failed با پیام؛ retry در فایل ۰۹
            with _conn() as conn:
                conn.execute("UPDATE jobs SET status='failed', result=?, updated_at=? WHERE id=?",
                             (json.dumps({"error": str(exc)}), time.time(), row["id"]))


if __name__ == "__main__":
    setup()
    threading.Thread(target=worker_loop, daemon=True).start()

    job_id = enqueue("summarize_doc", {"text": "متن طولانی سند اول..."})
    print(f"job {job_id} ثبت شد")
    while (status := job_status(job_id))["status"] in ("pending", "running"):
        time.sleep(0.5)
    print(f"وضعیت: {status}")
```

چهار نکته‌ی معماری در این دموی ساده: کاربر **سریع job_id می‌گیرد** (انتظار مدیریتی‌شده)، وضعیت **قابل پرس‌وجوست**، خطا **وضعیت دارد نه سکوت**، و worker **جدا از request web** است (timeout وب به پردازش ضربه نمی‌زند). در مقیاس، sqlite به صف واقعی (Celery، SQS، Redis) تبدیل می‌شود — ساختار مفهومی یکسان.

#### مثال ۲: الگوی embedded — قابلیت درون جریان کار

بدون کد فرانت، قرارداد embedded را ببین — خلاصه‌سازی تیکت در نرم‌افزار پشتیبانی:

```text
کاربر تیکت را باز می‌کند
   → دکمه‌ی «خلاصه کن» (فقط وقتی متن > آستانه؛ برای تیکت کوتاه نمی‌خواهیم)
   → POST /api/tickets/123/summary  (بک‌اند خودت)
        → متن تیکت از دیتابیس خودت می‌آید (کاربر هر چیزی نمی‌فرستد — فصل ۳)
        → mask PII + پرامپت فایل‌محور (فایل ۰۳) + قالب خروجی (فایل ۰۴)
   → پاسخ در UI: بلوک پیش‌نویس قابل ویرایش + ذخیره با دکمه‌ی تأیید کاربر
```

سه تصمیم الگوی embedded که در این خط دیده می‌شوند: **زمینه از سمت سرور ساخته می‌شود** (نه اینکه کلاینت هرچی خواست بفرستد)، **خروجی پیش‌نویس قابل تأیید است** (فصل ۱)، و **دکمه‌ی قابلیت، شرط نمایش دارد** (ارزش فقط در متن طولانی).

#### مثال ۳: سند تصمیم «کجا AI» — الگوی سند معماری

برای هر محصول، این جدول را (یک بار، با تیم) پر کن — بعداً همه‌ی درخواست‌های «AI اضافه کنیم؟» به همین برمی‌گردد:

```text
| فرایند محصول          | ماهیت            | تصمیم        | الگو    |
|------------------------|-------------------|---------------|----------|
| پاسخ به سؤال محصول    | متن باز + مستندات | AI ✅         | Chat+RAG |
| خلاصه‌ی تیکت‌های بلند   | متن بلند→کوتاه    | AI ✅         | Embedded |
| استخراج فاکتورهای PDF  | حجم زیاد، دسته‌ای  | AI ✅         | Async    |
| محاسبه‌ی مالیات        | قطعی و قانونی     | کد سنتی ❌     | —        |
| جست‌وجوی کاربر در سفارش | query ساخت‌یافته  | فرم معمولی ❌  | —        |
```

و برای هر ردیف ✅، سه ستون اجباری: متریک eval (فایل ۰۷)، الگوی UX (فصل ۱)، و بودجه/ریسک (فایل ۰۹) — تصمیم بدون این سه، میل است نه مهندسی.

### مقایسه و الگوهای مختلف

#### سه الگو در یک جدول — خلاصه‌ی فصل

| معیار | Embedded | Chat | Async |
|---|---|---|---|
| انتظار کاربر | لحظه‌ای (streaming) | لحظه‌ای (streaming) | صفر — بعداً چک می‌کند |
| ورودی | مشخص و قالب‌دار | آزاد | ساخت‌یافته/دسته‌ای |
| کنترل کیفیت | آسان‌تر (زمینه‌ی مشخص) | سخت‌تر (ورودی باز) | متوسط + ارزیابی batch |
| هزینه‌ی کنترل | آسان (سقف هر قابلیت) | نیازمند سقف گفتگو (فایل ۰۹) | batch pricing (فایل ۰۹) |
| ریسک امنیتی | کوچک‌تر (ورودی محدود) | بزرگ‌تر (فایل ۰۷) | متوسط (داده‌ی انبوه) |
| مناسب برای | قابلیت‌های مشخص | دستیار عمومی | پردازش انبوه |

قاعده‌ی انتخاب که بالا آمد را حفظ کن: **صبر؟ ورودی باز؟ مصرف نمایشی؟** — سه جواب، الگو را می‌دهد.

#### قابلیت جدید: مسیر عرضه‌ی مسئولانه

```text
ایده → سند تصمیم (کجا AI + سه ستون اجباری)
     → نمونه‌سازی با dataset کوچک (فایل ۰۷ فصل ۲)
     → eval حداقلی + چک‌لیست امنیتی (فایل ۰۷ فصل ۴)
     → feature flag → عرضه‌ی محدود (تیم داخلی → درصدی از کاربران)
     → مانیتورینگ (فایل ۰۹) → عرضه‌ی کامل
```

این مسیر همان مسیر هر قابلیت معمولی است — AI استثنا نیست؛ فقط ارزیابی‌اش متفاوت است.

### اشکال شایع

**۱. فراخوانی مدل sync در request وب.**
«دکمه را زد، handler ما ۴۰ ثانیه مدل صبر کرد» — timeout وب، تجربه‌ی بد، و سرویس درگیر. آستانه‌ی عملی: هر فراخوانی بالای چند ثانیه → streaming (فصل ۱) یا async (مثال ۱).

**۲. قابلیت AI بدون feature flag.**
اولین release از مریضیِ خروجی مدل، کل کاربران را می‌بیند. flag + عرضه‌ی تدریجی، از روز اول — و امکان خاموش‌کردن فوری در حادثه (فایل ۰۹).

**۳. AI در همه‌چیز.**
هیجان launch، هر فرم را چت‌بات می‌کند. جدول تصمیم (مثال ۳) و سؤال «کدام مسئله؟» — هر جا جواب محکم نیامد، نگذار.

**۴. async بدون وضعیت.**
کار در صف است، کاربر و حتی خودِ تیم نمی‌دانند کجاست. وضعیت job (مثال ۱) جزء API عمومی قابلیت است، نه جزئیات داخلی.

**۵. زمینه را کلاینت می‌سازد.**
فرانت هرچی خواست می‌فرستد (متن دلخواه، id های دلخواه) — هم امنیت (فایل ۰۷) هم هزینه را خراب می‌کند. قاعده: **داده از منبع سرور، ورودی از کاربر** — مرز روشن.

**۶. فراموشی «منفی‌ها» در review.**
جلسه‌ی roadmap فقط چیزهای AI‌دار دارد؛ چیزی که حذف AI شد را کسی نمی‌پرسد. جدول تصمیم، ستون «نه» را هم رسمی می‌کند — و آن را قابل دفاع می‌کند.

### نکته‌های مهم (Tips & Tricks)

- قابلیت‌های embedded را **دورهمیِ یک هدف** نگه‌دار: هر قابلیت، یک مسئله‌ی مشخصِ یک کاربر مشخص — قابلیت «همه‌کاره» معمولاً هیچ‌کاره می‌ماند.
- برای chat عمومی، **دامنه را در UI اعلام کن** («من دستیار سفارش‌های شما هستم») — هم انتظار کاربر را مدیریت می‌کند هم سطح حمله (فایل ۰۷) را کوچک‌تر.
- در async، **batch API ارائه‌دهنده‌ها** را برای کارهای غیرفوری چک کن — معمولاً نصف قیمت است (فایل ۰۹) و برای شبانه‌ها ایده‌آل.
- وضعیت job را **به رویداد وصل کن** وقتی مقیاس شد (WebSocket/webhook به‌جای polling) — الگوی همین فصل، فقط انتقال.
- هر قابلیت AI یک **«قابل‌خاموش‌شدن»** باشد: flag خاموش = قابلیت به حالت قبلی (بدون AI) برمی‌گردد — fallback در سطح قابلیت، نه فقط در سطح فراخوانی (فایل ۰۹).
- اندازه‌گیری **اثر** را از اول بگذار: زمان صرفه‌جویی‌شده، نرخ استفاده، بازخورد — عددِ «AI کمکی کرد» فقط از سنجش می‌آید، نه از حس.

### خلاصه‌ی فصل

- سه الگو: **Embedded** (قابلیت مشخص درون جریان کار)، **Chat** (ورودی باز + ابزار)، **Async** (پردازش پس‌زمینه با صف/وضعیت) — انتخاب با سه سؤال: صبر؟ ورودی باز؟ مصرف نمایشی؟
- معماری ثابت: **کلید و منطق در بک‌اند، فرانت به API خودت** — قابلیت AI حقوق قابلیت معمولی را دارد (flag، تست، نسخه).
- async یعنی **صف + worker + وضعیت** — نه «فرستادم و امیدوارم».
- **کجا AI نگذاریم** هم‌قد کجا بگذاریم: قطعی‌ها به کد سنتی، ساده‌ها به فرم — و تصمیم منفی را در سند معماری رسمی کن.
- عرضه‌ی مسئولانه: **سند تصمیم → eval → flag → تدریجی → مانیتور** — فایل‌های ۰۷ و ۰۹ این مسیر را تکمیل می‌کنند.

## فصل ۳: حریم خصوصی و داده‌ی کاربر

> **سطح**: سطح ۳ — این فصل مرزِ «داده‌ی کاربر» را در معماری AI می‌سازد: چه داده‌ای به ارائه‌دهنده می‌رود، با چه مجوزی، با چه ماسکی و با چه شفافیتی — چون یک فراخوانی مدل، یک انتقال داده‌ی بیرونی است.

### مقدمه

یک حقیقت ساده که از فایل ۰۱ با تو همراه بوده، حالا بار سنگین حقوقی و اعتمادی می‌گیرد: **هر فراخوانی API مدل، ارسال داده به یک سرویس بیرونی است.** وقتی کاربر تیکتش را می‌نویسد و سیستم تو برای خلاصه‌سازی آن را به ارائه‌دهنده می‌فرستد، یک داده‌ی شخصی از مرز محصولت عبور کرده است.

این فصل درباره‌ی مدیریت درستِ همین عبور است: در طراحی، در کد و در روایت با کاربر. و خبر خوب: بیش‌تر ابزارهایش را قبلاً داری — ماسک PII (فایل ۰۷ فصل ۴)، حداقل‌سازی زمینه (فایل ۰۳ فصل ۳)، لاگ mask‌شده (فایل ۰۷). این‌جا آن‌ها را در چارچوب «حریم خصوصی محصول» می‌چینیم.

نکته‌ی مهم قانونی: این فایل **الگوهای مهندسی** می‌دهد، نه مشاوره‌ی حقوقی — الزامات (GDPR، مقررات محلی، سیاست سازمان) را با کارشناس مربوط نهایی کن؛ کار تو به‌عنوان مهندس، ساختنِ سیستمِ قابل‌انطباق است.

### مفاهیم اساسی

#### چهار سؤال که هر قابلیت AI باید جواب داشته باشد

قبل از نوشتن هر خط کدِ قابلیت AI، این چهار سؤال را (در سند قابلیت) جواب بده:

1. **چه داده‌ای می‌رود؟** — متن کاربر؟ محتویات حساب؟ تاریخچه؟ (حداقل‌سازی از همین‌جا شروع می‌شود)
2. **کجا می‌رود؟** — کدام ارائه‌دهنده، کدام منطقه، با چه قراردادی؟
3. **چقدر می‌ماند؟** — retention policy API آن ارائه‌دهنده چیست؟ (بسیاری مسیرهای zero-retention دارند — در منابع)
4. **به کاربر گفته شده؟** — داخل UI، در سیاست حریم خصوصی، آیا opt-out دارد؟

این چهار جواب، «تعهد حریم خصوصی» قابلیت توست — و پایه‌ی جواب‌دادن به تیم حقوقی، مشتری سازمانی و کاربر نگران.

#### طبقه‌بندی داده — مجوز ارسال

| طبقه | مثال | مجوز پیش‌فرض |
|---|---|---|
| عمومی | متن مستندات عمومی، سؤال فنی | ارسال آزاد |
| داخلی | متن تیکت، عنوان سفارش | ارسال با mask PII + قاعده‌ی حداقل |
| محرمانه | متن مکاتبات، داده‌های مالی شخصی | mask سخت یا مجاز ویژه (DPA/zero-retention) |
| فوق‌حساس | سلامت، هویت کامل، شماره کارت | هرگز خام به ارائه‌دهنده — mask کامل، ابزار داخلی، یا اصلاً به مدل نرو |

قاعده‌ی کاربردی: هر قابلیت، بالاترین طبقه‌ی داده‌ای که مصرف می‌کند را تعیین کند و طبقه، ماسک و مسیر ارسال را تعیین کند — نه اینکه هر توسعه‌دهنده‌ای قضاوت لحظه‌ای بکند.

#### سه اصل عملی

1. **حداقل‌سازی (Minimization)**: فقط چیزی که وظیفه لازم دارد. خلاصه‌سازِ تیکت، متن تیکت را می‌گیرد — نه تاریخچه‌ی کامل حساب کاربر. (همان مهندسی زمینه‌ی فایل ۰۳، این‌بار با انگیزه‌ی حریم خصوصی.)
2. **پسودونیم‌سازی (Masking)**: PII با جایگزین پایدار — مدل می‌تواند رفرنس کند («کاربر EMAIL_1 گفته...»)، داده لو نمی‌رود (فایل ۰۷ فصل ۴، تابع mask_pii).
3. **شفافیت (Transparency)**: کاربر بداند کجای محصول AI است، داده‌اش کجا می‌رود، و گزینه‌ای داشته باشد. شفافیت هم الزام است هم — در عمل — سازنده‌ی اعتماد و رضایت کاربر.

#### self-host: جواب لایه‌ی آخر

فایل ۰۲ فصل ۵ گفت self-host پیش‌فرض نیست؛ این‌جا دوباره به‌عنوان گزینه‌ی حریم خصوصی می‌آید: برای داده‌ی فوق‌حساس که الزامِ «هرگز بیرون نمی‌رود» دارد، مدل متن‌باز روی زیرساخت خودت (یا ارائه‌دهنده‌ی با منطق داده‌ی مورد تایید سازمان) آخرین گزینه است — با هزینه‌ی زیرساختی که فایل ۰۲ محاسبه کرد. ترتیب درست تصمیم: **mask → قرارداد/zero-retention → self-host** — نه برعکس.

### مثال‌های عملی

#### مثال ۱: پایپ‌لاین حریم خصوصی قابلیت — ماسک + حداقل + علامت‌گذاری

```python
"""privacy_pipeline.py — قابلیت خلاصه‌ساز تیکت با سه اصل: حداقل، ماسک، شفافیت."""
import json
import re
import time
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"

# ── ماسک PII (همان الگوی فایل ۰۷ فصل ۴ — نسخه‌ی فشرده) ──
PII = {
    "email": re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"),
    "phone": re.compile(r"\b(?:0|98|0098)?9\d{9}\b"),
    "card":  re.compile(r"\b\d{4}[ -]?\d{4}[ -]?\d{4}[ -]?\d{4}\b"),
}

def mask_pii(text: str) -> str:
    counters: dict[str, int] = {}
    for name, pattern in PII.items():
        def repl(m: re.Match, _name=name) -> str:
            counters[_name] = counters.get(_name, 0) + 1
            return f"{_name.upper()}_{counters[_name]}"
        text = pattern.sub(repl, text)
    return text


# ── حداقل‌سازی: فقط فیلدهایی که وظیفه لازم دارد ──
def build_minimal_context(ticket: dict) -> str:
    """از رکورد کامل تیکت، فقط «متن» و «دسته» می‌آید — نه ایمیل، نه تاریخ خرید، نه مبلغ."""
    body = mask_pii(ticket["body"])
    return f"دسته‌ی تیکت: {ticket['category']}\nمتن تیکت:\n{body}"


def summarize_ticket(ticket: dict) -> str:
    context = build_minimal_context(ticket)

    response = client.chat.completions.create(
        model=MODEL,
        temperature=0,
        messages=[
            {"role": "system", "content":
             "تیکت پشتیبانی را در حداکثر سه جمله خلاصه کن. "
             "به‌جای داده‌های شخصی ماسک‌شده (EMAIL_1 و…) از همین برچسب‌ها استفاده کن."},
            {"role": "user", "content": context},
        ],
    )
    summary = response.choices[0].message.content

    # لاگ با برچسب طبقه‌ی داده — برای audit حریم خصوصی (فایل ۰۹)
    log_privacy_event(
        feature="ticket_summary",
        data_class="internal",
        sent_fields=["category", "body(masked)"],
        provider=MODEL,
    )
    return summary


def log_privacy_event(**fields: str) -> None:
    """لاگ ساخت‌یافته‌ی «چه چیزی کجا رفت» — قابل ممیزی، بدون خودِ داده."""
    entry = {"ts": time.time(), **fields}
    print(json.dumps(entry, ensure_ascii=False))   # در واقعیت: log structued سرویس لاگ


if __name__ == "__main__":
    ticket = {
        "id": 123,
        "category": "shipping",
        "body": "سلام، من علی رضایی هستم (ali@example.com، 09121234567). "
                "سفارش ORD-1001 دو هفته است نرسیده.",
        "customer_full_history": "...",   # ⛔ این فیلد عمداً نمی‌آید
        "total_lifetime_spent": 125_000_000,  # ⛔ همین‌طور
    }
    print(summarize_ticket(ticket))
```

سه اصل در سه تابع: `build_minimal_context` (حداقل — دو فیلد، نه رکورد کامل)، `mask_pii` (پسودونیم‌سازی — مدل با برچسب کار می‌کند)، `log_privacy_event` (ممیزی — چه رفت، کجا، با چه برچسبی؛ بدون خودِ داده). توجه کن که خروجی مدل هم با برچسب‌هاست — ماسک فقط ورودی نیست، قرارداد کل جریان است.

#### مثال ۲: شفافیت در UI — الگوی پیام و opt-out

بدون کد سنگین، قرارداد سه‌جایی که شفافیت باید بنشیند:

```text
۱. نقطه‌ی قابلیت (نزدیک دکمه‌ی «خلاصه کن»):
   «این خلاصه با هوش مصنوعی ساخته می‌شود؛ متن تیکت برای پردازش به سرویس [نام] ارسال می‌شود
    و ذخیره نمی‌شود.»

۲. تنظیمات کاربر:
   [✓] استفاده از هوش مصنوعی در قابلیت‌های پیشنهادی
   (خاموش = قابلیت‌ها با روش سنتی/دستی کار می‌کنند — fallback قابلیت، فصل ۲)

۳. سیاست حریم خصوصی (خلاصه‌ی AI):
   کدام قابلیت‌ها، کدام سرویس، retention چه، آموزش مدل نه (با قرارداد مربوطه)
```

قاعده‌ی UX: **اعلام در نقطه‌ی استفاده، نه فقط در انتهای سیاست هفت‌صفحه‌ای.** کاربر در لحظه‌ی استفاده حقِ دانستن دارد — و دکمه‌ی opt-out باید قابلیت را واقعاً به مسیر جایگزین ببرد، نه اینکه فقط گزینه‌ی قشنگی باشد.

#### مثال ۳: ممیزی — پاسخ به «چه داده‌ای کجا رفته؟»

سؤالی که روزی (از حقوقی، از مشتری سازمانی، از کاربر) می‌آید و بدون زیرساخت، جوابش هفته است:

```python
"""privacy_audit.py — از لاگ‌های ساخت‌یافته، گزارش ممیزی بگیر."""
import json
from pathlib import Path

LOG_PATH = Path("privacy_events.jsonl")   # log_privacy_event در مثال ۱ این‌جا append می‌کند

def audit_report(feature: str | None = None) -> dict:
    rows = [json.loads(line) for line in
            LOG_PATH.read_text(encoding="utf-8").splitlines() if line.strip()]
    if feature:
        rows = [r for r in rows if r["feature"] == feature]

    by_class: dict[str, int] = {}
    for r in rows:
        by_class[r["data_class"]] = by_class.get(r["data_class"], 0) + 1

    return {
        "total_calls": len(rows),
        "by_data_class": by_class,
        "features": sorted({r["feature"] for r in rows}),
        "providers": sorted({r["provider"] for r in rows}),
    }

# جواب سؤال ممیزی در یک ثانیه:
# print(audit_report("ticket_summary"))
# → {'total_calls': 1543, 'by_data_class': {'internal': 1543}, 'providers': ['gpt-4o-mini']}
```

الگو: **هر عبور داده، یک رویداد ساخت‌یافته** — نه متن داده، فقط متادیتا. با این لاگ، «چه داده‌ای کجا رفته» گزارش است، نه حفاری.

### مقایسه و الگوهای مختلف

#### سه استراتژی داده در برابر ارائه‌دهنده

| استراتژی | مکانیزم | هزینه/پیچیدگی | مناسب برای |
|---|---|---|---|
| **ارسال با ماسک** (پیش‌فرض این فصل) | mask PII + حداقل‌سازی + قرارداد استاندارد | کم | اکثر قابلیت‌ها |
| **قرارداد/zero-retention** | DPA با ارائه‌دهنده + endpoint های نگه‌نداشتن | حقوقی/مالی | مشتریان سازمانی |
| **self-host** | مدل متن‌باز روی زیرساخت خودت | زیاد (فایل ۰۲ فصل ۵) | داده‌ی فوق‌حساس با الزام بماندن |

ترتیب تصمیم همان که گفتم: mask → قرارداد → self-host — هر پله فقط وقتی که پله‌ی قبلی الزام را برآورده نکرد.

#### مرزهای لاگ — سه مکان، سه قاعده

| مکان | قاعده |
|---|---|
| لاگ trace (فایل ۰۶/۰۹) | متن پرامپت/پاسخ فقط mask‌شده یا hash؛ همیشه |
| لاگ قابلیت (مثال ۱) | فقط متادیتا — بدون محتوا |
| ذخیره‌ی گفتگو برای eval | با مجوز کاربر + mask + retention محدود |

و یک نکته که همیشه جا می‌ماند: **خروجی مدل هم داده است** — پاسخی که از داده‌ی کاربر ساخته شده، همان طبقه‌ی داده را دارد؛ لاگ و ذخیره‌ی خروجی هم مشمول قواعد است.

### اشکال شایع

**۱. ارسال رکورد کامل.**
«بگذار کل آبجکت کاربر را بفرستیم، مدل خودش می‌فهمد» — نقطه‌ی اوج نقض حداقل‌سازی: هزینه (فایل ۰۹)، نویز (فایل ۰۳)، و حریم خصوصی، هر سه با هم. `build_minimal_context` الگوی درست.

**۲. لاگ بدون ماسک.**
trace با متن کامل تیکت‌ها و ایمیل‌ها — برای دیباگ عالی، برای ممیزی فاجعه. ماسک در لاگ، همان‌قدر اجباری است که در ارسال.

**۳. شفافیت «قشنگی».**
اعلام در سیاست، بدون opt-out کارا؛ یا opt-out که قابلیت را فقط مخفی می‌کند ولی داده همچنان جایی می‌رود. opt-out باید مسیر جایگزین واقعی باشد (فصل ۲، «قابل‌خاموش‌شدن»).

**۴. فراموشی تاریخچه‌ی گفتگو.**
چت‌بات چندنوبتی، هر نوبت **کل تاریخچه** را می‌فرستد (فایل ۰۲ فصل ۲) — یعنی داده‌ی نوبت‌های قبلی هم هر بار عبور می‌کند. retention و mask در تاریخچه هم اعمال شود؛ گفتگوهای قدیمی حذف‌شده، از پرامپت هم بیرون بروند.

**۵. داده‌ی کاربر در پرامپت‌های تیمی.**
همکار پرامپت را دیباگ می‌کند و متن واقعی کاربر را در Slack/ایمیل/issue کپی می‌کند — نشت از مسیر انسانی. قانون تیمی: **نمونه‌ها فقط mask‌شده**؛ dataset eval هم از لاگ mask‌شده می‌آید (فایل ۰۷).

**۶. قرارداد ارائه‌دهنده را فرض گرفتن.**
«قطعاً آموزش نمی‌دهند» — فرض، قرارداد نیست. retention و آموزش را از مستندات/قرارداد همان لحظه بگیر و در سند قابلیت ثبت کن؛ ارائه‌دهنده‌ها تغییر می‌کنند.

### نکته‌های مهم (Tips & Tricks)

- برای هر قابلیت، **چهار سؤال ابتدای فصل را در سند قابلیت** جواب داده باش — سند حریم خصوصی قابلیت، ده خط بیشتر نیست و در ممیزی طلاست.
- ماسک را **پایدار نگه‌دار در گفتگو**: `EMAIL_1` در کل session همان کاربر باشد، تا مدل بتواند رفرنس کند و تجربه طبیعی بماند (مثل مثال ۱).
- طبقه‌بندی داده را **در نوع ورودی قابلیت اجباری کن**: هر endpoint AI، فیلد `data_class` در schema ورودی‌اش دارد — برچسب‌زدن، خودکار می‌شود.
- برای داده‌ی فوق‌حساس، **طراحیِ بدون مدل** را هم در گزینه‌ها بگذار: خیلی از کارها با الگوریتم/دست‌انسان بدون مدل حل می‌شوند — «به مدل نرو» هم یک استراتژی حریم خصوصی است.
- در launch قابلیت‌های AI، **یک پرسش آماده داشته باش**: «اگر این داده فردا در خبرها باشد، می‌توانیم توضیح بدهیم چه شد؟» — اگر جواب نه است، معماری مشکل دارد، نه حق‌وقوق.
- سند حریم خصوصی محصول و مستندات ارائه‌دهنده را **فصلی مرور کن** — policyها تغییر می‌کنند و «فرضِ قبلی» ریسک جدید می‌شود.

### خلاصه‌ی فصل

- هر فراخوانی مدل = **عبور داده از مرز محصول**؛ چهار سؤال اجباری هر قابلیت: **چه؟ کجا؟ چقدر می‌ماند؟ گفته شده؟**
- طبقه‌بندی داده مجوز ارسال را تعیین می‌کند: **عمومی آزاد، داخلی با ماسک، محرمانه با قرارداد، فوق‌حساس هرگز خام.**
- سه اصل عملی: **حداقل‌سازی** (فقط فیلدهای لازم)، **پسودونیم‌سازی پایدار** (برچسب‌های قابل رفرنس)، **شفافیت در نقطه‌ی استفاده** با opt-out واقعی.
- لاگ‌ها هم مرز دارند: **ماسک در trace، متادیتای ممیزی برای هر عبور** — و خروجی مدل هم داده است.
- ترتیب استراتژی: **mask → قرارداد/zero-retention → self-host**؛ و «به مدل نرو» هم گزینه‌ی مشروع است.

## فصل ۴: MCP — پروتکل استاندارد اتصال ابزارها

> **سطح**: سطح ۳ — این فصل استانداردسازی لایه‌ی ابزار را می‌سازد: MCP چیست، چه مشکلی را حل می‌کند، چطور با ابزارهای فایل ۰۴ ارتباط دارد و کِی در محصول تو جا می‌شود — آخرین تکه‌ی معماری سطح ۳.

### مقدمه

در فایل ۰۴ ابزار ساخت: توابع + Schema + dispatcher. یک مشکل ساختاری دارد که در دمو نمی‌بینی و در دنیای واقعی بزرگ می‌شود: **هر اپلیکیشن AI، ابزارها را به شکل خودش تعریف و وصل می‌کند.** شرکت‌ها و ابزارهای محبوب (دیتابیس، GitHub، Slack، فایل‌ها) هر کدام باید N بار برای N محصولِ متفاوت integration شوند — مضربی که انسان‌ساعت می‌خورد.

**MCP (Model Context Protocol)** — پروتکل متن‌بازی که از ۲۰۲۴ رایج شد — جواب همین مضرب است: یک قرارداد استاندارد برای اینکه **برنامه‌های AI (کلاینت‌ها) به ابزارها و منابع داده (سرورها) وصل شوند.** یک‌بار MCP server برای ابزار X بنویسی (یا از جامعه استفاده کنی)، هر کلاینت MCP-سازگاری (ادیتورها، اپ‌های دسکتاپ AI، محصول خودت) می‌تواند آن را ببیند و استفاده کند — بدون integration اختصاصی.

نکته‌ی روشن‌کننده از منظر این کتابچه: **MCP چیز مفهومی جدیدی ندارد** — ابزار، Schema، description، گارد — همه را در فایل ۰۴ یاد گرفتی. MCP همان مفاهیم را **استاندارد‌شده و شبکه‌ای** می‌کند: به‌جای توابع داخل کد، سرورهای اتصال‌پذیر. پس این فصل سبک است — تو نصفش را بلدی.

### مفاهیم اساسی

#### معماری MCP: سه نقش

```text
Host          → برنامه‌ی AI (ادیتور کد، اپ دسکتاپ، محصول خودت) که مدل را اجرا می‌کند
  └─ Client   → اتصال‌دهنده درون Host؛ با هر Server یک گفتگوی استاندارد دارد
       └─ Server → برنامه‌ای که قابلیت‌ها را به‌شکل استاندارد عرضه می‌کند
                    (ابزارها، منابع داده، قالب‌های پرامپت)
```

سه primitive اصلی که سرور عرضه می‌کند:

| Primitive | چیست | معادل آشنای تو |
|---|---|---|
| **Tools** | عملیاتی که مدل (با اجازه) فراخوانی می‌کند | ابزارهای فایل ۰۴ — همین |
| **Resources** | داده‌های قابل خواندن (فایل، سند، رکورد) | زمینه‌ی فایل ۰۳، منابع RAG فایل ۰۵ |
| **Prompts** | قالب‌های پرامپت آماده | فایل‌های پرامپت فایل ۰۳ فصل ۴ |

ببین: کل پروتکل، استانداردسازیِ سه چیزی است که در پنج فایل گذشته ساختی. ارزشش در **interop** است: سرورِ تو، کلاینتِ هرکسی؛ کلاینتِ تو، سرورِ هرکسی.

#### MCP چه چیزی را حل می‌کند؟

قبل: `N قابلیت × M ابزار = N×M integration` — هر محصول، هر ابزار، جدا.
بعد: `N + M` — هر ابزار یک‌بار MCP server می‌شود؛ هر محصول یک‌بار کلاینت.

مصادیق عملی که همین حالا معنا دارند:

- **داخل محصول تو**: به‌جای dispatcher دست‌ساز (فایل ۰۴)، از client MCP استفاده کنی و به serverهای آماده‌ی ابزارهای محبوب وصل شوی.
- **انتشار قابلیت‌های محصول**: دستیارهای کاربران (ادیتورها، اپ‌های دسکتاپ AI) به داده‌ی محصول تو از طریق MCP server تو وصل می‌شوند — integration که جامعه می‌سازد.
- **داخلی سازمان**: ابزارهای داخلی (دیتابیس، CRM) یک‌بار به MCP درمی‌آیند؛ هر قابلیت AI از همان استفاده می‌کند.

#### MCP با گاردهای قبلی چه می‌کند؟ — همه‌چیز سر جایش است

قاعده‌های کلیدی که این کتابچه ساخته، در MCP هم دقیقاً برقرارند:

- **مدل تصمیم می‌گیرد، کد تو اجرا می‌کند** (فایل ۰۴ فصل ۲): فراخوانی ابزار در host تو تفسیر و اجرا می‌شود؛ گاردها و تأیید انسانی همان‌جا.
- **داده‌ی بیرونی = دستور مشکوک** (فایل ۰۷ فصل ۳): خروجی ابزار (از هر MCP serverی، حتی رسمی) داده است — تگ، قاعده‌ی «داده=داده» و پالایش اعمال شود.
- **least privilege** (فایل ۰۷): هر server/ابزار، حداقل دسترسی؛ server ثالث = dependency امنیتی، gate کن.
- **تأیید انسانی برای عمل حساس**: نمایش درخواست ابزار به کاربر قبل از اجرا — همان صف تأیید فایل ۰۶، این‌جا UX هاست است.

#### کِی MCP، کِی direct؟

| موقعیت | پیشنهاد |
|---|---|
| ابزارهای داخلیِ خودت، یک محصول، کنترل کامل | **direct** (فایل ۰۴) — ساده‌تر، دیباگ شفاف‌تر |
| اتصال به ابزارهای محبوب که جامعه server دارند | **MCP client** — integration آماده |
| عرضه‌ی قابلیت‌های محصول به اکوسیستم دستیارها | **MCP server** — انتشار رسمی |
| سازمان با چند قابلیت AI و ابزارهای مشترک | MCP به‌عنوان لایه‌ی استاندارد داخلی |

قاعده: MCP **لایه‌ی استانداردِ اتصال** است، نه الزام معماری — جایی که interop ارزش دارد، بگیر؛ جایی که یک‌بازیگر است، direct ساده‌تر و امن‌تر است.

### مثال‌های عملی

#### مثال ۱: MCP server برای ابزارهای فروشگاه — با SDK رسمی پایتون

```python
"""shop_mcp_server.py — سرور MCP با SDK رسمی پایتون.
نصب: pip install "mcp[cli]"
اجرای آزمایشی: mcp dev shop_mcp_server.py  (داخل MCP Inspector)"""
import sqlite3
from mcp.server.fastmcp import FastMCP

# hostها (ادیتور/اپ‌های AI) به این سرور وصل می‌شوند و این ابزارها را می‌بینند
mcp = FastMCP("shop-tools")

DB = "shop.db"


def _read(sql: str, params: tuple = ()) -> list[dict]:
    """همان گاردهای فایل ۰۴ فصل ۴ — MCP امنیت را حذف نمی‌کند، منتقل می‌کند."""
    if not sql.strip().lower().startswith("select"):
        raise ValueError("فقط SELECT")
    conn = sqlite3.connect(DB, timeout=5)
    try:
        cur = conn.execute(sql, params)
        rows = cur.fetchmany(20)
        cols = [d[0] for d in cur.description]
        return [dict(zip(cols, r)) for r in rows]
    finally:
        conn.close()


@mcp.tool()
def get_customer_orders(email: str) -> str:
    """سفارش‌های یک مشتری با ایمیل او را برمی‌گرداند. برای سؤال‌های وضعیت سفارش."""
    rows = _read(
        "SELECT id, status, total_toman, created_at FROM orders "
        "WHERE customer_email = ? ORDER BY created_at DESC",
        (email,),
    )
    return json.dumps({"orders": rows}, ensure_ascii=False)


@mcp.tool()
def get_product_info(name: str) -> str:
    """قیمت و موجودی محصول با بخشی از اسمش. برای سؤال‌های قیمت/موجودی."""
    import json
    rows = _read(
        "SELECT name, price_toman, stock FROM products WHERE name LIKE ? LIMIT 5",
        (f"%{name}%",),
    )
    return json.dumps({"products": rows}, ensure_ascii=False)


if __name__ == "__main__":
    mcp.run()   # حمل‌ونقل پیش‌فرض (stdio) — برای hostهای لوکال
```

سه چیز را در این کد ببین:

1. **آشنایی**: `@mcp.tool()` با docstring — دقیقاً همان «تابع + description» فایل ۰۴؛ SDK خودش Schema می‌سازد (مثل Pydantic → Schema فایل ۰۴ فصل ۱).
2. **گاردها منتقل شده‌اند**: `_read` با SELECT-only و سقف سطر — MCP هیچ‌کدام از این‌ها را حذف نمی‌کند.
3. **ابزار-سروریس شدن**: همین فایل، هم در Inspector رسمی، هم در ادیتورها و اپ‌های MCP-سازگار (به‌عنوان سرور) قابل اتصال است — یک‌بار نوشتی، همه‌جا استفاده شد. (توجه: importهای بالای تابع دوم را در فایل واقعی به بالای فایل منتقل کن.)

#### مثال ۲: گارد MCP در host — همان تأیید انسانی

host تو (محصولت) که client MCP دارد، فراخوانی ابزار را دریافت می‌کند؛ گاردها این‌جا می‌نشینند — همان dispatcher فایل ۰۴، حالا روی ابزارهای استاندارد:

```python
# شِمای host-side — در محصول واقعی، client SDK مخصوص را ببین
def on_tool_call(server_name: str, tool_name: str, args: dict) -> dict:
    # ۱) whitelist: کدام server/ابزار مجاز است؟ (نصب MCP = دادن اعتماد نیست)
    if (server_name, tool_name) not in ALLOWED_TOOLS:
        return {"error": "tool_not_allowed"}

    # ۲) رده‌ی ریسک (فایل ۰۴ فصل ۳): خواندنی آزاد، نوشتنی تأیید
    if tool_name in RISKY_TOOLS:
        if not user_confirms(server_name, tool_name, args):   # UI تأیید
            return {"error": "user_denied"}

    # ۳) اجرا + trace ساخت‌یافته (فایل ۰۶ فصل ۴)
    trace_tool_call(server_name, tool_name, args)
    return mcp_client.call_tool(server_name, tool_name, args)
```

پیام اصلی: **MCP استاندارد اتصال است، نه استاندارد اعتماد.** server اضافه‌شده به host، یک dependency با دسترسی است — whitelist، رده‌بندی و trace، همه‌ی گاردهای این کتابچه، همین‌جا اعمال می‌شوند.

#### مثال ۳: تصمیم MCP در سند معماری — الگوی ردیف‌ها

```text
| ابزار/قابلیت            | مصرف‌کننده‌ها          | تصمیم                    |
|--------------------------|------------------------|---------------------------|
| ابزارهای سفارش (داخلی)  | قابلیت‌های خود محصول   | direct (فایل ۰۴)          |
| مستندات GitHub سازمان    | تیم dev + دستیارها     | MCP client به server رسمی |
| APIهای محبوب ثالث        | همه‌ی قابلیت‌ها         | MCP client (جامعه)        |
| داده‌ی محصول برای مشتریان | دستیارهای کاربران      | MCP server انتشار رسمی    |
```

این جدول را به جدول «کجا AI» فصل ۲ اضافه کن — تصمیم لایه‌ی اتصال، بخشی از سند معماری قابلیت است.

### مقایسه و الگوهای مختلف

#### Direct tools در برابر MCP

| معیار | direct (فایل ۰۴) | MCP |
|---|---|---|
| پیچیدگی | صفر — تابع و dispatcher | protocol + SDK + transport |
| interop | فقط کد خودت | هر host/client سازگار |
| دیباگ | شفاف کامل | + لایه‌ی پروتکل (و Inspector رسمی کمک می‌کند) |
| گاردها | کد خودت | host-side (تو) + قواعد سرور |
| جامعه | — | serverهای آماده برای ابزارهای محبوب |
| حکم | **یک‌محصولی، کنترل کامل** | **multi-مصرف‌کننده‌ای، استانداردسازی** |

و در سطح مفهوم: MCP برای ابزارها همان کاری است که HTTP برای وب‌سایت‌ها کرد — قبل: scrape اختصاصی؛ بعد: استاندارد مشترک. ارزش، در استاندارد است.

### اشکال شایع

**۱. «MCP امن است چون رسمی است».**
پروتکل استاندارد است؛ serverها برنامه‌های معمولی‌اند با باگ و بدخواهی احتمالی. server ثالث = dependency با دسترسی — فایل ۰۷ (زنجیره‌ی عرضه) و least privilege اعمال شود.

**۲. نصب server = اعتماد کامل به همه‌ی ابزارهایش.**
host با whitelist و رده‌بندی ریسک کار می‌کند (مثال ۲) — «همه‌ی ابزارهای همه‌ی سرورها فعال» پیش‌فرضِ خطرناک است.

**۳. همه‌چیز را به MCP می‌برند.**
یک محصول، سه ابزار داخلی — direct ساده‌تر و امن‌تر است. MCP ابزار interop است؛ مصرفش باید با ارزش interop توجیه شود.

**۴. خروجی سرور به‌عنوان دستور.**
همان حمله‌ی غیرمستقیم فایل ۰۷، این‌بار از مسیر MCP: داده‌ی منبع (سند، تیکت) می‌تواند دستور داشته باشد؛ قاعده‌ی «داده=داده» و تگ‌گذاری در host، بدون استثنا.

**۵. فراموشی نسخه و transport.**
پروتکل جوان است؛ نسخه‌ها و transportها (stdio، remote) تغییر می‌کنند. نسخه‌ی SDK/protocol را pin کن و changelog رسمی را دنبال کن — همان نظم dependency فایل ۰۶ فصل ۳.

### نکته‌های مهم (Tips & Tricks)

- اول با **MCP Inspector** (ابزار رسمی تست سرور) سرورت را امتحان کن — بدون هیچ hostی، ابزارها و schemaها را می‌بینی و دیباگ می‌کنی.
- MCP server را **لایه‌ای بالای همان ابزارهای تو** بنویس: توابع گارد‌دارِ فایل ۰۴ را دوباره بنویس، فقط expose کن — یک منبع حقیقت، دو صورت مصرف.
- برای سرورهای سازمانی: **auth، سقف نرخ و لاگ مستقل** — server تو الان سرویس عمومی است؛ قواعد فایل ۰۹ رویش اعمال می‌شود.
- docstring ابزارهای MCP را با همان کیفیت descriptionهای فایل ۰۴ بنویس — مدلِ host، همین را می‌بیند.
- MCP را در سند معماری با جدول تصمیم (مثال ۳) ثبت کن — و مرورش را فصلی به dependency-check اضافه کن.
- منبع‌های MCP (Resources) را برای RAG هم ببین: منابع استاندارد، یعنی خط لوله‌ی فایل ۰۵ می‌تواند از هر سرور منبع‌دار تغذیه شود.

### خلاصه‌ی فصل

- MCP = **قرارداد استاندارد اتصال برنامه‌های AI به ابزار/منابع** — مضرب N×M را به N+M می‌رساند.
- سه primitive: **Tools** (فایل ۰۴)، **Resources** (زمینه‌ی فایل ۰۳/۰۵)، **Prompts** (فایل ۰۳) — همه‌ی مفاهیم، تو بلدی؛ استانداردسازی جدید است.
- **MCP امنیت را حذف نمی‌کند**: whitelist host، رده‌ی ریسک، تأیید انسانی، trace — همه‌ی گاردهای این کتابچه، host-side اعمال می‌شوند.
- تصمیم با جدول: **یک‌بازیگر → direct؛ interop → MCP client؛ انتشار به اکوسیستم → MCP server.**
- server ثالث = **dependency با دسترسی** — مثل هر dependency دیگری gate و version می‌خواهد.
