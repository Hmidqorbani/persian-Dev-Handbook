## فصل ۱: خروجی ساخت‌یافته با JSON و Schema

> **سطح**: سطح ۲ — این فصل نخستین ابزار حرفه‌ای «اتصال مدل به کد» را می‌سازد: اجبار مدل به خروجی JSON با شکل تضمین‌شده، اعتبارسنجی با Pydantic/Zod و الگوی بازتولید در صورت خطا — پایه‌ی استخراج داده، ابزارها و ایجنت‌ها.

### مقدمه

فصل ۳ فایل قبلی دیدی: پرامپت‌نویسی برای «مصرف انسانی» را یاد گرفتی. اما در محصول واقعی، مصرف‌کننده‌ی خروجی مدل معمولاً **کد توست**، نه چشم کاربر: استخراج فاکتور به JSON، دسته‌بندی تیکت به enum، استخراج فیلدهای رزومه به ساختار. و برای کد، «معمولاً JSON می‌دهد» همان «هرگز کار نمی‌کند» است — یک بک‌تیک اضافه دور JSON، یک کلید جاافتاده یا یک کامنت وسط آرایه، کل پایپ‌لاین را می‌اندازد.

راه‌حل، گذر از «تقاضای پرامپتی» به «تضمین سازوکاری» است: مدل‌های امروزی مدهای رسمی خروجی JSON دارند که ساختار را **در سطح inference** تضمین می‌کنند — مدل ذاتاً نمی‌تواند چیزی خارج از Schema تولید کند. این فصل هر دو لایه را می‌سازد: تضمینِ سازوکار (mode) و اعتبارسنجیِ نهایی (Pydantic/Zod) — چون در فصل ۴ فایل ۰۲ دیدی که این دو مسئله‌ی متفاوت‌اند: Schema شکل را تضمین می‌کند، نه صحت محتوا.

### مفاهیم اساسی

#### سه سطح اطمینان در خروجی JSON

| سطح | مکانیزم | چه تضمینی می‌دهد | چه تضمینی نمی‌دهد |
|---|---|---|---|
| ۱. پرامپتی | «فقط JSON بده» در متن | هیچ — مدل گاهی متن اضافه می‌گذارد | هر چیزی |
| ۲. JSON mode | `response_format={"type": "json_object"}` | خروجی JSON معتبر است | شکل فیلدها و مقادیر |
| ۳. Structured Output | JSON Schema سخت‌گیرانه | **ساختار دقیق: فیلدها، نوع‌ها، enum** | درستی محتوا (مقدار قدیمی‌ست؟ قیمت واقعی؟) |

قاعده: **همیشه بالاترین سطحی که ارائه‌دهنده‌ات می‌دهد را بگیر**؛ سطح ۱ فقط برای مدل‌هایی است که سطح ۲ ندارند. و حتی در سطح ۳، لایه‌ی اعتبارسنجی نهایی (Pydantic/Zod) را حذف نکن — به دلایل زیر.

#### JSON Schema: قرارداد رسمی با مدل

Schema چیزی است که به مدل می‌گویی «خروجی دقیقاً این شکل باشد»:

- **نوع هر فیلد**: string، integer، boolean، آرایه، آبجکت تو در تو.
- **enum**: فهرست بسته‌ی مقادیر مجاز — بهترین دوست تو در دسته‌بندی.
- **required و optional**: در حالت سخت‌گیرانه (strict)، «اختیاری» یعنی «نوعش nullable است» نه «کلید نباشد» — این ظرافت پایین‌تر با مثال می‌آید.
- **description فیلدها**: جایی که به مدل می‌گویی «amount_toman یعنی مبلغ کل به تومان، بدون واحدها» — نسخه‌ی machine-readable همان توضیح‌های پرامپتی فصل ۱ فایل قبل.

طراحی Schema خوب خودش یک مهارت است: فیلد کم و دقیق بهتر از فیلد زیاد و حاشیه‌ای؛ enum به‌جای string آزاد هرجا می‌شود؛ و اسم فیلدهای انگلیسی واضح (کد تو باید parse کند، فارسی بودن کلیدها مزیت نیست — مقادیر فارسی‌اند، کلیدها انگلیسی).

#### لایه‌ی اعتبارسنجی: چرا بعد از Schema هم Pydantic؟

دو دلیل که کد حرفه‌ای حتی با Structured Output هم validate می‌کند:

1. **منطق کسب‌وکار در Schema جا نمی‌شود**: `amount >= 0`، `date` با فرمت مشخص، آرایه‌ی غیرخالی — Schema نوع را می‌دهد، قواعد دامنه را Pydantic/Zod می‌دهد.
2. **بریدگی خروجی**: اگر سقف توکن خروجی کم باشد، JSON نصفه می‌آید و parse شکست می‌خورد — خطای صریح بهتر از داده‌ی غلطِ بی‌صدا.

Pydantic (پایتون) و Zod (تایپ‌اسکریپت) هر دو همین کار را می‌کنند: parse + validate + تبدیل به شیء type-safe — و پایتونش حتی می‌تواند خودش Schema تولید کند.

#### الگوی بازتولید (Retry with Feedback)

وقتی اعتبارسنجی شکست خورد، دو راه داری: fail سریع (خطا به بالا) یا یک تلاش بازتولید با بازخوردِ خطا. الگوی دوم معمولاً کافی و به‌صرفه است: متن JSON تولیدشده و متن خطای اعتبارسنجی را به مدل برگردان و بگو «اصلاح کن». یک دور بیشتر معمولاً لازم نیست — اگر بعد از دو دور هنوز خراب است، مشکل Schema یا پرامپت است، نه شانس.

### مثال‌های عملی

#### مثال ۱: استخراج فاکتور با Structured Output + Pydantic

```python
"""extract_invoice.py — استخراج ساخت‌یافته با JSON Schema سخت‌گیرانه + Pydantic."""
from pydantic import BaseModel, Field, field_validator
from openai import OpenAI

client = OpenAI()


# ── لایه ۱: قرارداد با کد (اعتبارسنجی قواعد کسب‌وکار) ──
class Invoice(BaseModel):
    vendor: str = Field(description="نام فروشنده")
    amount_toman: int | None = Field(description="مبلغ کل به تومان؛ اگر صریح نیست null")
    date: str | None = Field(description="تاریخ فاکتور به همان شکلی که در متن آمده")
    category: str = Field(description="دسته‌ی خرید")

    @field_validator("amount_toman")
    @classmethod
    def amount_must_be_positive(cls, v: int | None) -> int | None:
        if v is not None and v < 0:
            raise ValueError("مبلغ منفی معنی ندارد — احتمالاً خطا در استخراج")
        return v


# ── لایه ۲: قرارداد با مدل (تضمین ساختار در سطح inference) ──
INVOICE_SCHEMA = {
    "type": "object",
    "properties": {
        "vendor": {
            "type": "string",
            "description": "نام فروشنده یا شرکت صادرکننده",
        },
        "amount_toman": {
            "type": ["integer", "null"],
            "description": "مبلغ کل به تومان فقط اگر عدد صریح در متن است؛ وگرنه null",
        },
        "date": {
            "type": ["string", "null"],
            "description": "تاریخ به همان فرمتی که در متن آمده؛ وگرنه null",
        },
        "category": {
            "type": "string",
            "enum": ["office", "travel", "software", "other"],
            "description": "دسته‌ی خرید از میان مقادیر مجاز",
        },
    },
    "required": ["vendor", "amount_toman", "date", "category"],
    "additionalProperties": False,  # در حالت strict اجباری است
}


def extract_invoice(text: str) -> Invoice:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,
        messages=[
            {"role": "system", "content": "تو مبدل دقیق فاکتور به داده ساخت‌یافته هستی. حدس زدن ممنوع؛ هر فیلدی که در متن صریح نیست null بده."},
            {"role": "user", "content": text},
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {"name": "invoice", "strict": True, "schema": INVOICE_SCHEMA},
        },
    )
    # لایه ۱ اعمال می‌شود — اگر مدل قواعد دامنه را شکست، این‌جا خطای صریح داریم
    return Invoice.model_validate_json(response.choices[0].message.content)


if __name__ == "__main__":
    sample = """
    فاکتور خرید
    فروشنده: شرکت نمونه‌تجهیز
    مبلغ کل: 4,850,000 تومان
    تاریخ: 1405/03/12
    شرح: خرید ۲ لپ‌تاپ و ۳ مانیتور برای اتاق جلسات
    """
    invoice = extract_invoice(sample)
    print(invoice.model_dump_json(indent=2))
```

دو نکته‌ی ظریف این کد را دیده‌ای؟

1. **در strict mode، «اختیاری» با nullable می‌سازیم**: `amount_toman` و `date` از `required` خارج نشده‌اند؛ نوعشان `["integer", "null"]` است. این همان قرارداد strict است: همه‌ی کلیدها همیشه باشند، مقدار ممکن است null باشد — و اتفاقاً برای استخراج داده، این رفتار بهتر است: «نبودن» صریح است، نه کلیدِ گم‌شده.
2. **تفکیک دو لایه‌ی قرارداد**: Schema به مدل گفت ساختار و enum؛ Pydantic گفت «مبلغ منفی یعنی خطا» — قواعد دامنه‌ای که جایشان Schema نیست.

#### مثال ۲: الگوی بازتولید با بازخورد خطا

وقتی اعتبارسنجی شکست، به‌جای fail فوری، یک دور اصلاح‌محور:

```python
"""retry_extract.py — یک تلاش بازتولید با بازخورد خطای اعتبارسنجی."""
from pydantic import BaseModel, ValidationError
from openai import OpenAI

client = OpenAI()


class Complaint(BaseModel):
    category: str  # باید یکی از سه دسته باشد
    severity: int  # 1 تا 5
    summary: str


ALLOWED = ["shipping", "billing", "quality"]


def extract_with_retry(text: str) -> Complaint:
    instruction = (
        f"این شکایت را استخراج کن. category فقط یکی از {ALLOWED}؛ "
        "severity عدد 1 تا 5؛ summary یک جمله. فقط JSON."
    )
    messages = [
        {"role": "system", "content": "فقط JSON معتبر بده؛ هیچ متن دیگری ننویس."},
        {"role": "user", "content": f"{instruction}\n\nمتن:\n{text}"},
    ]

    last_error = ""
    for attempt in range(2):  # یک تلاش اصلی + یک تلاش اصلاح
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            temperature=0,
            messages=messages,
        )
        raw = response.choices[0].message.content.strip()

        try:
            return Complaint.model_validate_json(raw)
        except ValidationError as exc:
            last_error = str(exc)
            # بازخورد خطا را به مکالمه اضافه کن و از مدل اصلاح بخواه
            messages.append({"role": "assistant", "content": raw})
            messages.append({
                "role": "user",
                "content": f"JSON قبلی این خطا را دارد:\n{last_error}\nاصلاحش کن؛ فقط JSON.",
            })

    raise RuntimeError(f"بعد از دو تلاش، خروجی معتبر نشد. آخرین خطا: {last_error}")


if __name__ == "__main__":
    print(extract_with_retry("سفارشم دو هفته است نرسیده و پشتیبانی هم جواب نمی‌دهد!"))
```

الگوی مهم: **خطا به مدل برمی‌گردد، نه به بالای برنامه** — و توجه کن که `severity` محدوده دارد که در JSON mode ساده قابل تضمین نبود؛ دقیقاً همین‌جا Pydantic جای خودش را نشان می‌دهد.

#### مثال ۳: نسخه‌ی TypeScript با Zod

همان منطق در اکوسیستم Node:

```typescript
// extract_invoice.mts — npm install openai zod
import OpenAI from "openai";
import { z } from "zod";

const client = new OpenAI();

// لایه ۱: قرارداد با کد
const Invoice = z.object({
  vendor: z.string(),
  amountToman: z.number().int().nullable(),
  date: z.string().nullable(),
  category: z.enum(["office", "travel", "software", "other"]),
});
type Invoice = z.infer<typeof Invoice>;

const text = `
فاکتور خرید
فروشنده: شرکت نمونه‌تجهیز
مبلغ کل: 4,850,000 تومان
تاریخ: 1405/03/12
`;

const response = await client.chat.completions.create({
  model: "gpt-4o-mini",
  temperature: 0,
  messages: [
    { role: "user", content: `این فاکتور را استخراج کن. مبلغی که در متن نیست null بده.\n\n${text}` },
  ],
  response_format: { type: "json_object" }, // JSON تضمین‌شده؛ Schema دقیق بسته به ارائه‌دهنده
});

const raw = JSON.parse(response.choices[0].message.content!);
const parsed = Invoice.safeParse(raw);

if (!parsed.success) {
  // لایه ۱ شکست: fail صریح، نه داده‌ی بدِ بی‌صدا
  throw new Error(`خروجی نامعتبر: ${parsed.error.message}`);
}

const invoice: Invoice = parsed.data;
console.log(invoice);
```

الگوها یکسان‌اند؛ فقط کتابخانه‌ی اعتبارسنجی فرق دارد. هر زبانی که کار می‌کنی، دنبال همین سه تکه بگرد: mode/Schema در API + اعتبارسنجی + بازتولید.

### مقایسه و الگوهای مختلف

#### چهار راه گرفتن ساختار از مدل

| راه | تضمین ساختار | پیچیدگی | مناسب برای |
|---|---|---|---|
| پرامپتِ «فقط JSON» | هیچ | صفر | نمونه‌سازی سریع، مدل‌هایی بدون mode |
| JSON mode | فقط JSON بودن | کم | ساختار آزاد با شکل ساده |
| Structured Output (Schema) | ساختار کامل + enum | متوسط | پیش‌فرض تولید (production) |
| Tool call به‌عنوان قالب | ساختار کامل (پارامتر ابزار) | متوسط | وقتی هم‌زمان ابزار هم می‌خواهی (فصل بعد) |

نکته‌ی جذاب: راه چهارم واقعاً رایج است — برخی ارائه‌دهنده‌ها Structured Output با ابزار پیاده می‌کنند: یک «ابزار» تعریف می‌کنی که اسمش مثل «submit_invoice» است و پارامترهایش Schema توست. مکانیزم یکی است؛ بسته‌بندی فرق دارد.

#### کجا Schema، کجا رشته‌ی آزاد؟

| فیلد | نوع درست | چرا |
|---|---|---|
| دسته/وضعیت/سطح | `enum` | فضای حدس را می‌بندد؛ تست‌پذیر |
| مبلغ، تعداد، سن | عدد + nullable | محاسبه‌پذیر؛ «نمی‌دانم» صریح |
| تاریخ | رشته (به فرمت قیدشده در description) | تبدیل تاریخ را به کد بسپار؛ مدل فرمت را حفظ کند |
| خلاصه/توضیح | رشته‌ی آزاد با محدودیت طول در description | متن است دیگر |
| نشانه‌های پیچیده (لیست، تو در تو) | آبجکت/آرایه‌ی تو در تو | پشتیبانی می‌شود؛ فقط عمق را عاقلانه نگه دار |

### اشکال شایع

**۱. «پارس شد، پس درست است.»**
پارس موفق یعنی شکل درست است. مقدارِ استخراج‌شده از متنِ بد یا حدسِ مدل همچنان غلط است — برای درستی محتوا، همان استراتژی‌های فایل ۰۲ (فصل ۴): تزریق داده، قید «حدس ممنوع»، فیلدهای nullable به‌جای حدس، و ارزیابی نمونه‌ای (فایل ۰۷).

**۲. Schema اغراق‌آمیز.**
بیست فیلد با تو در توی چهار لایه، هم خروجی را کُند و پرهزینه می‌کند هم خطای اعتبارسنجی را کثیف. Schema را از کوچک شروع کن و فقط با نیاز واقعی بزرگ کن.

**۳. فیلد اختیاری بدون nullable.**
در strict mode، فیلدی که در `required` نیست ولی nullable هم نیست، خروجی را می‌شکند. قرارداد: **هر فیلدِ ممکن‌الغیب، نوعِ null-پذیر و داخل required.**

**۴. اعداد و تاریخ‌های فارسی.**
«۴٬۸۵۰٬۰۰۰» با جداکننده‌ی فارسی، `int` نمی‌شود. دو راه‌حل: description صریح («عدد بدون جداکننده») + نرمال‌سازی در کد قبل از validate؛ و تاریخ را همان‌طور که در متن آمده نگه دار و تبدیلش را در کد انجام بده.

**۵. بریدگی خروجی.**
پاسخ بلند + سقف توکن کم = JSON نصفه. `finish_reason` را چک کن و اگر `length` بود، یعنی Schema بزرگ است یا سقف کم — نه اینکه retry بی‌معنی بزنی.

**۶. تکیه بر retry برای پوشش Schema بد.**
بازتولید دردِ خروجی‌های بدِ شانسی را می‌گیرد؛ دردِ طراحی بد را نمی‌گیرد. اگر خطای اعتبارسنجی الگودار و تکراری است، مشکل Schema یا description است — پرامپت را درست کن، نه شانس را.

### نکته‌های مهم (Tips & Tricks)

- Pydantic می‌تواند **Schema را از مدل تولید کند** (`.model_json_schema()`) — یک منبع حقیقت (single source of truth): کلاس را می‌نویسی، هم اعتبارسنجی داری هم Schema برای API.
- فیلد `confidence` اختیاری اضافه کن وقتی کیفیت ورودی‌ها نامطمئن است — مدل به خودش نمره بدهد و کد تو برای موارد کم‌اطمینان مسیر مرور انسانی برود (پیوند به فایل ۰۸).
- برای آرایه‌های بزرگ، **سقف تعداد را در description بگو** («حداکثر ۱۰ مورد») و در کد هم چک کن — دفاع دولایه.
- خروجی ساخت‌یافته + **few-shot قالب نمونه** با هم تداخل ندارند؛ وقتی مدل پایدارتر شد، نمونه‌ها را کم کن و هزینه‌ی توکن را پس بگیر.
- در لاگ، **خروجی خام (raw) قبل از validate** را نگه دار — خطای اعتبارسنجی فردا بدون raw قابل دیباگ نیست (پایه‌ی observability فایل ۰۹).
- مدهای ساخت‌یافته بین ارائه‌دهنده‌ها اسم و جزئیات متفاوت دارند (OpenAI: `response_format` با `json_schema`؛ Anthropic: با تعریف ابزار؛ Gemini: `responseSchema`) — الگو یکی است؛ از مستنداتِ ارائه‌دهنده‌ی خودت اسم دقیق را بگیر.

### خلاصه‌ی فصل

- سه سطح اطمینان: **پرامپتی، JSON mode، Structured Output** — همیشه بالاترین سطح ممکن؛ تضمین سازوکار بهتر از تقاضای پرامپتی.
- دو لایه‌ی قرارداد: **Schema** (ساختار و enum، تضمین‌شده توسط مدل) + **Pydantic/Zod** (قواعد دامنه، تضمین‌شده توسط کد تو).
- در strict mode، اختیاری یعنی **nullable و داخل required** — «نبودن» باید صریح باشد.
- الگوی بازتولید: **خطای اعتبارسنجی را با متن JSON بد به مدل برگردان** — یک دور کافی؛ الگوهای تکراری یعنی Schema بد.
- پارس موفق ≠ محتوا درست؛ **مدل مبدل ساختار است، منبع حقیقت نیست.**

## فصل ۲: ابزارها و Tool Calling

> **سطح**: سطح ۲ — این فصل قلب اتصال مدل به دنیای واقعی را می‌سازد: Tool Calling — مدل چه می‌بیند، چه تصمیمی می‌گیرد، کد تو چه اجرا می‌کند و چرخه‌ی کامل نتیجه‌گیری — پایه‌ی RAG، ایجنت‌ها و همه‌ی قابلیت‌های سطح ۳.

### مقدمه

تا این‌جا مدل فقط «حرف می‌زد»: می‌گفت، استخراج می‌کرد، دسته‌بندی می‌کرد. اما واقعی‌ترین نیاز محصولات چیزی دیگر است: **مدل باید کار انجام دهد** — سفارش مشتری را از دیتابیس بگیرد، وضعیت مرسوله را از API بخواند، یا وقت جلسه را در تقویم بگذارد.

**Tool Calling (یا Function Calling)** دقیقاً همین پل است، و مهم‌ترین جمله‌ی این فصل را اول بگو تا همه‌چیز روی آن بنا شود:

> **مدل ابزارها را «اجرا» نمی‌کند؛ فقط «درخواست فراخوانی» می‌دهد. تصمیم با مدل است، اجرا با کد تو.**

این تفکیک از نظر مهندسی معجزه است: هوشِ تصمیم‌گیری (کدام ابزار، با چه پارامترها) از مدل می‌آید؛ قدرت، امنیت و کنترل (اجرا، دسترسی، تأیید) صددرصد از کد تو. مدل هرگز به دیتابیس تو دسترسی ندارد — فقط اسم ابزارها و Schemaهایشان را می‌بیند و متنِ «لطفاً این تابع را با این آرگومان‌ها صدا بزن» تولید می‌کند. کد تو تصمیم می‌گیرد اجرا کند یا نه — و در فصل بعد می‌بینی که این «یا نه» جای کل معماری امنیتی است.

### مفاهیم اساسی

#### چرخه‌ی Tool Calling: چهار قدم که باید حفظ باشی

```text
۱. درخواست + تعریف ابزارها
   کد تو: پیام کاربر + فهرست ابزارها (اسم + Schema پارامترها) → به مدل

۲. تصمیم مدل
   مدل جواب می‌دهد: «ابزار get_order_status را با {"order_id": "1234"} صدا بزن»
   (این جواب معمولیِ API است — فقط به‌جای content، tool_calls دارد)

۳. اجرای واقعی توسط کد تو
   کد تو: پارامترها را parse می‌کند، تابع واقعی را اجرا می‌کند، نتیجه می‌گیرد
   (اینجا امنیت، timeout، تأیید انسانی و هر گارد دیگری جا دارد)

۴. برگرداندن نتیجه به مدل
   کد تو: نتیجه را با نقش tool به تاریخچه اضافه می‌کند و دوباره به مدل می‌دهد
   مدل: با نتیجه‌ی واقعی، جواب نهایی کاربر را می‌سازد
```

نکته‌ی ساختاری: قدم‌های ۲ تا ۴ ممکن است چند بار تکرار شوند — مدل می‌تواند پشت هم چند ابزار بخواهد (اول دیتابیس، بعد API، بعد جواب). به همین دلیل پیاده‌سازی واقعی همیشه یک **حلقه** است، نه یک if — کد کامل پایین‌تر.

#### آناتومی تعریف ابزار

```python
{
    "type": "function",
    "function": {
        "name": "get_order_status",           # اسم: فعل_موضوع؛ واضح و منحصربه‌فرد
        "description": (                       # مهم‌ترین خط: راهنمای «کی صدا بزند»
            "وضعیت سفارش را برمی‌گرداند. برای سؤال‌های "
            "«سفارشم کجاست؟» و «کِی می‌رسد؟» استفاده کن."
        ),
        "parameters": {                        # همان JSON Schema فصل قبل
            "type": "object",
            "properties": {
                "order_id": {"type": "string", "description": "شناسه‌ی سفارش، مثل ORD-1234"}
            },
            "required": ["order_id"],
            "additionalProperties": False,
        },
    },
}
```

`description` این‌جا همان پرامپت فصل‌های قبل است: **تنها چیزی که مدل برای تصمیم گرفتن «کدام ابزار» دارد.** پرامپت بد = انتخاب ابزار بد؛ description ضعیف = ابزارِ درست دست‌نخورده می‌ماند و مدل یا سراغ ابزار غلط می‌رود یا توهم می‌زند.

#### tool_choice: کنترل سطح دخالت

| مقدار | رفتار | کِی |
|---|---|---|
| `auto` | مدل خودش تصمیم می‌گیرد ابزار بخواهد یا مستقیم جواب بدهد | پیش‌فرض چت‌بات‌ها |
| `required` | حتماً یک ابزار بخواهد | پایپ‌لاین‌هایی که «جواب آزاد» قبول ندارند |
| `none` | ابزارها را نادیده بگیر | گفتگوی معمولی بدون ابزار |
| نام ابزار خاص | حتماً همان ابزار | قالب‌گیری اجباری خروجی (الگوی فصل قبل) |

#### طراحی یک ابزار خوب — پنج قاعده

1. **دامنه‌محور، نه عمومی**: `get_order_status` بهتر از `run_sql`. ابزار دامنه‌محور، امن‌تر، تست‌پذیرتر و راحت‌ترِ مدل است.
2. **description = چه می‌دهد + کِی استفاده شود + کِی نه**: سه جمله کافی است.
3. **خروجی برای مدل، نه برای کاربر**: کوتاه، ساخت‌یافته (JSON کوچک)، بدون داده‌ی حشو — هر توکن ابزار به پنجره‌ی فصل ۳ می‌ریزد.
4. **خطا به مدل برگردد، نه crash**: `{"error": "order_not_found"}` بهتر از exception است؛ مدل با خطا هم می‌تواند تصمیم بگیرد (دوباره بپرسد، مسیر جایگزین، اعتراف به کاربر).
5. **بدنه‌ی جانبی (side effect) متمایز**: ابزارهای خواندن بی‌خطرند؛ ابزارهای نوشتن (ایمیل، بازپرداخت، حذف) باید در لایه‌ی تأیید جدا بروند — موضوع اصلی فصل بعد.

### مثال‌های عملی

#### مثال ۱: چرخه‌ی کامل با یک ابزار — قابل اجرا

```python
"""tool_loop.py — چرخه‌ی کامل Tool Calling با حلقه و گارد دورها."""
import json
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"
MAX_TOOL_ROUNDS = 5  # گارد حلقه بی‌پایان


# ── اجرای واقعی: این تابع از دنیای واقعی داده می‌گیرد (اینجا: دموی ثابت) ──
def get_weather(city: str) -> dict:
    fake_db = {"شیراز": {"temp_c": 31, "condition": "آفتابی"},
               "تهران": {"temp_c": 24, "condition": "مه‌آلود"}}
    if city in fake_db:
        return fake_db[city]
    return {"error": f"اطلاعات هوای «{city}» در دسترس نیست"}


TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "دما و وضعیت هوای فعلی یک شهر را برمی‌گرداند. برای سؤال‌های هواشناسی استفاده کن.",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "نام شهر"}
                },
                "required": ["city"],
                "additionalProperties": False,
            },
        },
    }
]

# dispatcher: اسم ابزار → تابع واقعی؛ نقطه‌ی گارد و لاگ
def run_tool(name: str, args: dict) -> dict:
    if name == "get_weather":
        return get_weather(**args)
    return {"error": f"ابزار ناشناخته: {name}"}


def chat(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]

    for round_no in range(MAX_TOOL_ROUNDS):
        response = client.chat.completions.create(
            model=MODEL,
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",  # مدل خودش تصمیم می‌گیرد ابزار بخواهد یا نه
        )
        msg = response.choices[0].message

        if not msg.tool_calls:      # مدل جواب نهایی را ساخت — تمام
            return msg.content

        # ۱) درخواست ابزار مدل را به تاریخچه اضافه کن (الزامی)
        messages.append(msg)

        # ۲) هر درخواست را اجرا و نتیجه را با نقش tool برگردان
        for tool_call in msg.tool_calls:
            args = json.loads(tool_call.function.arguments or "{}")
            print(f"[چرخه {round_no + 1}] مدل خواست: {tool_call.function.name}({args})")
            try:
                output = run_tool(tool_call.function.name, args)
            except Exception as exc:  # خطای ابزار → به مدل، نه crash
                output = {"error": str(exc)}
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": json.dumps(output, ensure_ascii=False),
            })

    return "پاسخ نیازمند ابزارهای بیشتری بود و از حد مجاز گذشت."


if __name__ == "__main__":
    print(chat("هوای شیراز الان چطوره؟ کارش ندارم فقط کنجکاوم."))
```

چند نکته که بدونشان کد نمی‌خند:

- **پیام مدل با tool_calls باید به تاریخچه برگردد** (مثل جواب‌های assistant در فایل ۰۲) — فراموشی‌اش، خطای API مبهم می‌سازد.
- نتیجه‌ی ابزار با نقش `tool` و `tool_call_id` مرتبط با همان درخواست برگردد — اگر چند ابزار در یک چرخه خواسته شده باشند، id مرزشان است.
- `json.dumps(..., ensure_ascii=False)` برای متن فارسی؛ وگرنه به‌هم‌ریخته‌ی escape می‌بینی.

#### مثال ۲: چند ابزار — و تصمیم مدل

```python
"""multi_tools.py — دو ابزار؛ مدل انتخاب می‌کند کدام را (و کدام را نه)."""
import json
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"


def get_weather(city: str) -> dict:
    return {"temp_c": 31, "condition": "آفتابی"}  # دمو


def get_time(city: str) -> dict:
    return {"local_time": "14:30", "timezone": "Asia/Tehran"}  # دمو


TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "دما و وضعیت هوای فعلی شهر. فقط برای سؤال‌های هواشناسی.",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
                "additionalProperties": False,
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "get_time",
            "description": "ساعت محلی فعلی شهر. فقط برای سؤال‌های زمان.",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
                "additionalProperties": False,
            },
        },
    },
]

TOOL_FUNCS = {"get_weather": get_weather, "get_time": get_time}


def run_tool(name: str, args: dict) -> dict:
    return TOOL_FUNCS[name](**args)


def chat(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]
    for _ in range(5):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS, tool_choice="auto"
        )
        msg = response.choices[0].message
        if not msg.tool_calls:
            return msg.content
        messages.append(msg)
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments or "{}")
            output = run_tool(tc.function.name, args)
            messages.append({
                "role": "tool", "tool_call_id": tc.id,
                "content": json.dumps(output, ensure_ascii=False),
            })
    return "از حد ابزارها گذشت."


if __name__ == "__main__":
    # تست: سه سؤال با سه مسیر متفاوت — این‌ها باید در تست‌های ثابت‌ات بمانند
    for q in (
        "هوای تهران چطوره؟",
        "الان تو شیراز ساعت چنده؟",
        "معنی کلمه‌ی satiety چیست؟",   # بدون نیاز به ابزار — مدل باید مستقیم جواب دهد
    ):
        print(f"س: {q}\nج: {chat(q)}\n")
```

سؤال سوم تستِ مهمی است: **مدل نباید به هر قیمتی ابزار بخواهد.** اگر مدل برای «معنی satiety» هم هوای تهران را پرسید، descriptionهای تو نقص دارند — «فقط برای سؤال‌های هواشناسی» را جدی بنویس.

### مقایسه و الگوهای مختلف

#### Tool Calling در برابر راه‌های دیگر «دانستن»

| نیاز | راه‌حل درست | چرا |
|---|---|---|
| مدل از داده‌ی خصوصی **بخواند و تفسیر کند** | ابزار (query) یا RAG (فایل ۰۵) | مدل نباید منبع باشد؛ باید مصرف‌کننده |
| مدل داده‌ای **به‌روز و محاسباتی** بخواهد | ابزار | حافظه‌اش قدیمی و تقریبی است |
| خروجی **ساخت‌یافته از متن ورودی** | Structured Output (فصل قبل) | تبدیل است، نه عمل |
| مدل **کاری انجام دهد** (ایمیل، بازپرداخت) | ابزار + لایه‌ی تأیید (فصل بعد) | عمل حساس نباید خودکارِ مطلق باشد |

#### Tool Calling بومی در برابر پروتکل متنی

| معیار | بومی (tools=...) | متنی (خودت قرارداد بگذاری: «اگر خواستی X، خطی به شکل CALL:X{...} بده») |
|---|---|---|
| قابلیت اطمینان | بالا؛ مدل روی آن آموزش دیده | شکننده؛ parse دستی |
| انعطاف | مطابق قابلیت ارائه‌دهنده | هر جا بومی نیست |
| پیشنهاد | **پیش‌فرض** | فقط fallback برای مدل‌های خیلی قدیمی |

#### بومیِ ارائه‌دهنده‌ها — الگو یکی، اسم‌ها فرق دارند

| ارائه‌دهنده | مفهوم | ظرافت |
|---|---|---|
| OpenAI | `tools` + پیام‌های `tool` | `tool_call_id` الزامی |
| Anthropic | `tools` + بلوک‌های `tool_use`/`tool_result` در content | نتیجه داخل بلوک content می‌آید |
| Gemini | `functionDeclarations` + `functionResponse` | ساختار inline در history |

برنامه‌ی عملی: **با ارائه‌دهنده‌ی اصلی خودت عمیق شو** و چون فایل ۰۱ دیدی که الگو یکسان است، مهاجرت فقط ترجمه‌ی syntax است. (و MCP — لایه‌ی استاندارد بالای همه‌ی این‌ها — موضوع فایل ۰۸ است.)

### اشکال شایع

**۱. اجرای هر ابزارِ درخواستی بدون قید.**
مدل تصمیم‌گیر است، نه مجری مطلق: هر فراخوانی از dispatcher تو می‌گذرد — همان‌جا whitelist، سقف نرخ، تأیید انسانی و لاگ می‌نشینند (فصل بعد). dispatcher گشاد = هر توهم مدل، یک عمل واقعی.

**۲. description ضعیف یا اشغال.**
«get_data: داده می‌گیرد» — مدل نمی‌داند کِی از این و کِی از آن. description ضعیف، محتمل‌ترین علت «ابزار درست را صدا نمی‌زند» است؛ بهبودش ارزان‌ترین fix دنیاست.

**۳. خروجی سنگین به مدل برگرداندن.**
پرس‌وجویی که ۵۰۰ رکورد برمی‌گرداند، مستقیم به پنجره‌ی فصل ۳ فایل ۰۲ ریخته می‌شود: هزینه و نویز. سقف سطر (مثلاً ۲۰) و انتخاب فیلدهای ضروری در خود ابزار.

**۴. فراموشی append کردن درخواست یا نتیجه.**
تاریخچه باید هر دو را داشته باشد: پیام مدل با tool_calls و پیام‌های tool با نتیجه‌ها. نقص هر کدام، خطای مبهمِ 400 می‌سازد که دیباگش ساعت می‌برد.

**۵. crash کردن ابزار در برابر صحبت‌کردن با خطا.**
exception دست‌نخورده، کل چرخه را می‌کشد؛ `{"error": ...}` به مدل، مسیر جایگزین می‌دهد («ایمیل نداشت، بگو بگذار با شماره سفارش امتحان کنم»). خطا داده است، نه فاجعه.

**۶. اسم‌های گیج‌کننده یا هم‌پوشان.**
دو ابزار `get_user` و `fetch_user` با رفتار فرق‌دار، مدل را (و راستش را بخواهی هم‌تیمی‌ات را) گیج می‌کند. یک دامنه، یک اسم؛ هم‌پوشانی را با description مرزکشی کن یا ادغام کن.

### نکته‌های مهم (Tips & Tricks)

- **dispatcher واحد** نگه دار: نقطه‌ی مرکزی برای whitelist، لاگ، سنجه‌ها و گاردها — پراکنده‌سازی اجرا، از امنیت می‌کشد (فایل ۰۷).
- خروجی ابزار را به‌صورت **JSON کوچک با کلیدهای توصیفی** برگردان؛ اگر مدل برای فهمیدن کلیدها نیاز به توضیح دارد، کلیدها را بازنام‌گذاری کن.
- خطاهای ابزار را **منطقه‌مند کن** (`"error": "not_found"`، `"rate_limited"`, `"timeout"`) — مدل برای هر کدام تصمیم متفاوت می‌گیرد.
- `MAX_TOOL_ROUNDS` از روز اول — حلقه‌ی ابزار بدون گارد، فقط یک راه خوش‌بینانه به صورت‌حساب توست (فایل ۰۹).
- تست ابزارها مثل تست توابع: **بدون مدل** — unit test مستقیم روی توابع واقعی؛ تست انتخاب مدل، جداگانه با eval (فایل ۰۷).
- برای هر چرخه، یک **trace لاگ کن**: درخواست‌ها، ابزارهای خواسته‌شده، خروجی‌ها و زمان‌ها — این trace پایه‌ی observability فایل ۰۹ است.

### خلاصه‌ی فصل

- **مدل تصمیم می‌گیرد، کد تو اجرا می‌کند** — هوش از مدل، کنترل و امنیت از تو؛ این تفکیک پایه‌ی همه‌چیز است.
- چرخه: **تعریف ابزار → درخواست مدل (tool_calls) → اجرا توسط کد → نتیجه با نقش tool → جواب نهایی**؛ در عمل یک **حلقه** با گارد دورها.
- **description ابزار = پرامپتِ انتخاب ابزار**؛ قاعده‌های طراحی: دامنه‌محور، خروجی کوچک، خطا به‌عنوان داده.
- `tool_choice` پیچ کنترل است: **auto** برای چت، **required/نام ابزار** برای پایپ‌لاین قالب‌دار.
- dispatcher واحد + گاردها = جای امنیتی که فصل بعد روش وسعت می‌دهد.

## فصل ۳: الگوهای عملی ابزارها

> **سطح**: سطح ۲ — این فصل از «یک ابزار در دمو» به «سیستم ابزار در محصول» می‌رود: چندابزاری با ترکیب، تأیید انسانی برای عملیات حساس، گاردهای حلقه و استانداردهای ساخت ابزار — جایی که دموی فصل قبل به معماری تبدیل می‌شود.

### مقدمه

چرخه‌ی فصل قبل با ابزار «خواندنی» بی‌خطر بود: هوای شیراز که چیز خراب نمی‌کند. اما محصول واقعی ابزارهای **نوشتنی** دارد: ایمیل بفرست، بازپرداخت کن، رکورد حذف کن. خطای مدل در ابزار خواندنی یک جواب بد است؛ خطای مدل در ابزار نوشتنی یک **فاجعه‌ی عملیاتی** است — ایمیل توهین‌آمیز به مشتری اصلی، بازپرداخت هزار دلاری به آدرس اشتباه.

این فصل درباره‌ی هم‌زیستی امن این دو نوع است: معماری‌ای که مدل آزادانه بخواند، اما هر نوشتن از فیلترهای آگاهانه بگذرد. سه ستون می‌سازیم: **گاردهای حلقه** (جلوی رفتارهای افراطی)، **تأیید انسانی** (human in the loop برای عملیات حساس) و **استاندارد ساخت ابزار** (که تیم بتواند ابزار اضافه کند بدون ترس).

### مفاهیم اساسی

#### طبقه‌بندی ابزارها بر اساس ریسک — اولین قدم طراحی

قبل از نوشتن هر ابزار، رده‌اش را مشخص کن؛ هر رده، لایه‌ی حفاظتی خودش را دارد:

| رده | مثال | لایه‌ی حفاظتی |
|---|---|---|
| **فقط‌خواندنی** | وضعیت سفارش، قیمت، جست‌وجو | whitelist + سقف خروجی |
| **نوشتنِ برگشت‌پذیر** | یادداشت به تیکت، ذخیره‌ی draft | لاگ + بازنگری در UI |
| **نوشتنِ حساس** | ارسال ایمیل، بازپرداخت، حذف | **تأیید انسانی** یا dry-run + audit کامل |
| **بیرون‌زننده به دنیای واقعی** | پرداخت، تماس با API ثالثِ هزینه‌دار | تأیید اجباری + سقف نرخ/مبلغ سخت |

قاعده‌ی کلیدی: **سقف مجاز را در کدِ ابزار قفل کن، نه در پرامپت.** «حداکثر بازپرداخت ۵۰۰ هزار تومان کن» در پرامپت، توصیه است؛ در کد، دیوار است. مدل هر دو را می‌خواند، اما فقط دیوار غیرقابل مذاکره است.

#### تأیید انسانی: Human in the Loop

سه سطح پیاده‌سازی:

1. **تأیید تعاملی** (دمو/ابزار داخلی): اجرا متوقف می‌شود، انسان y/N می‌زند — این فصل همین را می‌سازد.
2. **صف تأیید** (محصول واقعی): درخواست عمل حساس در UI به‌عنوان کارت «در انتظار تأیید» می‌نشیند؛ جواب تأیید به چرخه‌ی ایجنت برمی‌گردد.
3. **dry-run + گزارش**: اجرا شبیه‌سازی می‌شود («چه می‌شد اگر؟») و خروجی، متن پیشنهادیِ آماده‌ی ارسال انسانی است — نه خودِ ارسال.

نکته‌ی ظریف که تیم‌ها جا می‌مانند: **ردّ تأیید هم باید به مدل برگردد.** اگر انسان گفت «نه»، مدل باید بداند (`{"error": "user_denied"}`) تا مسیر جایگزین برود یا به کاربر توضیح دهد — نه اینکه در سکوت منتظر نتیجه‌ای بماند که هرگز نمی‌آید.

#### گاردهای حلقه‌ی ابزار

حلقه‌ی فصل قبل سه گارد می‌خواهد تا در محصول امن شود:

- **سقف دورها** (`MAX_TOOL_ROUNDS`): جلوی حلقه‌ی بی‌پایان — مدلِ گیرکرده در «ابزار خراب شد، دوباره امتحان کن».
- **سقف نرخ ابزار**: هر ابزار حداکثر n بار در یک چرخه — جلوی اسپمِ یک ابزار.
- **سقف هزینه/داده در خود ابزار**: LIMIT دیتابیس، timeout شبکه، سقف مبلغ — آخرین دیوار.

و زیر همه: **trace کامل** — هر درخواست ابزار و هر خروجی، لاگ ساخت‌یافته (پایه‌ی فایل ۰۹).

#### استاندارد «یک ابزار خوب» — چک‌لیست طراحی

- اسم دامنه‌محور و description سه‌جزئی (چه می‌دهد / کِی بله / کِی نه) — فصل قبل.
- پارامترهای محدود و توصیف‌دار؛ مقدارهای حساس از context بیرون کشیده می‌شوند نه از پرامپت.
- خروجی کوچک، JSON، با کلیدهای معنادار.
- خطاها به‌عنوان داده (`{"error": "...", "reason": "..."}`)، هرگز exception خام.
- قفلِ سقف‌ها (نرخ، حجم، مبلغ) در بدنه‌ی ابزار.
- unit test مستقل از مدل + ثبت در whitelist ریسک.

### مثال‌های عملی

#### مثال ۱: ایجنت ابزارمحور با تأیید انسانی — کامل

```python
"""agent_with_approval.py — چند ابزار + تأیید انسانی برای عملیات حساس."""
import json
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"
MAX_TOOL_ROUNDS = 5

# ── ابزارهای فقط‌خواندنی ──
def get_order(order_id: str) -> dict:
    demo = {"ORD-1001": {"status": "sent", "total_toman": 2_450_000,
                         "email": "ali@example.com"}}
    return demo.get(order_id, {"error": "order_not_found"})

def get_refund_policy() -> dict:
    return {"rule": "مرجوعی تا ۱۴ روز با پلمب سالم؛ بازپرداخت ۳ روز کاری"}

# ── ابزار حساس: فقط با تأیید اجرا می‌شود ──
def refund_order(order_id: str, amount_toman: int) -> dict:
    # در دنیای واقعی: فراخوانی API پرداخت؛ این‌جا دمو
    return {"ok": True, "order_id": order_id, "refunded_toman": amount_toman}

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_order",
            "description": "وضعیت و مبلغ سفارش. برای هر سؤال درباره‌ی سفارش اول این را بزن.",
            "parameters": {
                "type": "object",
                "properties": {"order_id": {"type": "string"}},
                "required": ["order_id"],
                "additionalProperties": False,
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "get_refund_policy",
            "description": "قواعد مرجوعی و بازپرداخت. قبل از هر صحبت از بازپرداخت بزن.",
            "parameters": {"type": "object", "properties": {},
                            "required": [], "additionalProperties": False},
        },
    },
    {
        "type": "function",
        "function": {
            "name": "refund_order",
            "description": "بازپرداخت سفارش. فقط بعد از تأیید شرایط سیاست و به میزان مبلغ سفارش.",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string"},
                    "amount_toman": {"type": "integer", "description": "مبلغ بازپرداخت به تومان"},
                },
                "required": ["order_id", "amount_toman"],
                "additionalProperties": False,
            },
        },
    },
]

TOOL_FUNCS = {"get_order": get_order, "get_refund_policy": get_refund_policy,
              "refund_order": refund_order}
RISKY_TOOLS = {"refund_order"}          # هر چیزی این‌جا بنشیند، تأیید می‌خواهد
HARD_LIMITS = {"refund_order": 5_000_000}  # سقف مبلغ — در کد، نه در پرامپت


def run_tool(name: str, args: dict) -> dict:
    # گارد ۱: whitelist
    if name not in TOOL_FUNCS:
        return {"error": "unknown_tool"}

    # گارد ۲: سقف‌های سخت در کد — مدل نمی‌تواند از این‌ها رد شود
    if name in HARD_LIMITS and args.get("amount_toman", 0) > HARD_LIMITS[name]:
        return {"error": "limit_exceeded",
                "message": f"سقف مجاز بازپرداخت {HARD_LIMITS[name]} تومان است"}

    # گارد ۳: تأیید انسانی برای ابزارهای حساس
    if name in RISKY_TOOLS:
        print("\n--- درخواست عملیات حساس ---")
        print(f"ابزار: {name}")
        print(f"پارامترها: {json.dumps(args, ensure_ascii=False)}")
        ok = input("تأیید می‌کنی؟ [y/N] ").strip().lower() == "y"
        if not ok:
            # ردّ تأیید هم باید به مدل برسد تا مسیر جایگزین برود
            return {"error": "user_denied",
                    "message": "کاربر انسانی این عملیات را تأیید نکرد"}

    return TOOL_FUNCS[name](**args)


def agent(user_message: str) -> str:
    messages = [{"role": "system", "content": (
        "تو عامل پشتیبانی هستی. برای هر ادعا درباره‌ی سفارش/سیاست، از ابزارها استفاده کن؛ "
        "حدس نزن. برای بازپرداخت: اول سیاست را بخوان، بعد مبلغ دقیق سفارش را، بعد درخواست بده."
    )}, {"role": "user", "content": user_message}]

    for round_no in range(MAX_TOOL_ROUNDS):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS, tool_choice="auto"
        )
        msg = response.choices[0].message
        if not msg.tool_calls:
            return msg.content

        messages.append(msg)
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments or "{}")
            print(f"[چرخه {round_no + 1}] {tc.function.name}({args})")
            output = run_tool(tc.function.name, args)   # همه‌ی گاردها این‌جاست
            messages.append({
                "role": "tool", "tool_call_id": tc.id,
                "content": json.dumps(output, ensure_ascii=False),
            })
    return "درخواست پیچیده‌تر از حد ابزارهای فعلی است؛ به تیم انسانی ارجاع می‌شود."


if __name__ == "__main__":
    print(agent("سفارش ORD-1001 گیر کرده و این‌همه معطلی را نمی‌بخشم؛ پولم را پس بده."))
```

مسیر این سناریو را دنبال کن: مدل اول سیاست را می‌خواند، بعد سفارش را، بعد درخواست بازپرداخت می‌دهد — و درخواستش، با هرچه باشد، **دو دیوار** دارد: سقف مبلغ در کد (غیرقابل مذاکره) و تأیید انسانی (قابل مذاکره توسط تو، نه مدل). اگر تأیید ندهی، مدل پیام `user_denied` را می‌بیند و با کاربر صحبت دیگری می‌کند — نه اینکه بی‌جواب معلق شود.

#### مثال ۲: trace ساخت‌یافته — قبل از اینکه عذاب بکشی

```python
"""tool_trace.py — لاگ ساخت‌یافته‌ی هر چرخه؛ پایه‌ی دیباگ و observability."""
import json
import time
from datetime import datetime, timezone

TRACE: list[dict] = []

def traced_tool_call(name: str, args: dict, runner) -> dict:
    entry = {
        "ts": datetime.now(timezone.utc).isoformat(),
        "tool": name,
        "args": args,
    }
    start = time.perf_counter()
    try:
        output = runner(name, args)
        entry["status"] = "ok" if "error" not in output else "tool_error"
        entry["output"] = output
    except Exception as exc:
        entry["status"] = "exception"
        entry["output"] = {"error": str(exc)}
        output = entry["output"]
    entry["ms"] = round((time.perf_counter() - start) * 1000, 1)
    TRACE.append(entry)
    return output

# پایان هر درخواست کاربر: کل TRACE را ذخیره کن
def save_trace(session_id: str) -> None:
    with open(f"traces/{session_id}.json", "w", encoding="utf-8") as f:
        json.dump(TRACE, f, ensure_ascii=False, indent=2)
```

این چهل خط، هم‌زمان چهار درد را بند می‌آورد: دیباگ «چرا مدل این ابزار را خواست؟»، سنجه‌ی تأخیر هر ابزار، آمار نرخ خطاها، و مستندِ audit برای عملیات حساس. در فایل ۰۹ این را به داشبورد واقعی وصل می‌کنیم؛ این‌جا فقط سبکش را تمرین کن.

#### مثال ۳: ابزار ترکیبی — از چند منبع، یک پاسخ

الگوی رایج محصول: مدل چند ابزار را **ترتیبی** صدا می‌زند و نتیجه‌ها را ترکیب می‌کند. این را با همین `agent()` فصل قبل می‌بینی؛ نکته‌ی جدید، طراحی سؤال است که ترکیب را راه بیندازد:

```text
سؤال کاربر (به agent):
«سفارش ORD-1001 مال چه کسی است، وضعیتش چیست، و آیا شرایط مرجوعی دارد؟»
```

مدل خودش ترتیب را می‌چیند: `get_order` → `get_refund_policy` → جواب ترکیبی. درخواست‌های ترکیبی را در مجموعه‌ی تست‌هایت نگه دار — **ترکیب چند ابزار، جایی است که فرق مدل‌ها بیشترین است** و eval (فایل ۰۷) باید شاملش باشد.

### مقایسه و الگوهای مختلف

#### سه الگوی کنترل عملیات حساس

| الگو | مکانیزم | تأخیر | امنیت | کِی |
|---|---|---|---|---|
| **تأیید انسانی** | توقف + تأیید صریح | بالا (انتظار انسان) | بالاترین | عملیات پولی/تخریبی، حجم کم |
| **dry-run + پیش‌نویس** | اجرای شبیه‌سازی، خروجی برای انسان | متوسط | بالا | ایمیل/متن‌های خروجی |
| **قفل سخت + لاگ** | سقف در کد، بدون تأیید | صفر | متوسط (سقف‌دار) | عملیات برگشت‌پذیر پرتکرار |

الگوی ترکیبی واقعی محصولات: خواندن‌ها آزاد + نوشتنِ برگشت‌پذیر قفل‌سخت + نوشتنِ حساس صف تأیید. با رشد اعتماد (که **با ارزیابی فایل ۰۷ اندازه می‌گیرد، نه با حس**)، موارد را از ستون تأیید به ستون قفل‌سخت منتقل کن.

#### ابزار درشت در برابر ابزار ریز

| معیار | ابزار درشت («مدیریت سفارش») | ابزار ریز (get_order، refund_order، update_address) |
|---|---|---|
| تعداد فراخوانی | کم | بیشتر |
| کنترل گارد | سخت (یک تابع همه‌کاره) | دقیق — هر ابزار گارد خودش |
| انتخاب مدل | سخت‌تر؛ description کلی | راحت‌تر؛ هر ابزار مأموریت واضح |
| توصیه | برای دموی سریع | **پیش‌فرض محصول** |

قاعده: **ابزارِ ریز با گاردِ دقیق.** ابزار درشت یعنی تصمیم‌های ریز (اجازه؟ چقدر؟) که باید مدل بدهد — یعنی دیوارها به توصیه تبدیل می‌شوند.

### اشکال شایع

**۱. گاردها در پرامپت، نه در کد.**
«هرگز بیش از X بازپرداخت نکن» در system، توصیه‌ای است که مدل در فشارِ درخواستِ کاربر (یا یک injection — فایل ۰۷) می‌تواند بی‌خیالش شود. سقف‌های مادی فقط در کدِ ابزار.

**۲. ردّ تأیید بی‌صدا.**
انسان «نه» گفت و کد فقط return None کرد؛ مدل منتظر نتیجه می‌ماند، حلقه تمام می‌شود، کاربر «هیچی نشد» می‌بیند. ردّ = داده (`user_denied`) تا مدل توضیح یا مسیر جایگزین بدهد.

**۳. حلقه‌ی بی‌گارد.**
مدل در باگِ «ابزار error می‌دهد → دوباره امتحان کن» اسیر می‌شود: ده دور، صد دور... سقف دورها و سقف نرخ هر ابزار، از روز اول.

**۴. ابزارهایی که همه‌چیز را برمی‌گردانند.**
`get_order` که کل رکورد با تاریخچه‌ی کامل و فیلدهای مدیریتی برمی‌گرداند: توکن‌خور، نویزساز و نقض حریم خصوصی. خروجی ابزار را مثل API public طراحی کن: فقط فیلدهای لازم.

**۵. اعتماد اولیه به مدل «قوی‌تر از قبلاً».**
«الان مدل‌ها خوبند، تأیید انسانی را حذف کنیم» — تصمیمی که باید با داده‌ی ارزیابی (فایل ۰۷) و نرخ خطای واقعی از trace (فایل ۰۹) گرفته شود، نه با نسخه‌ی جدید مدل. حذف لایه‌ی حفاظتی برگشت‌ناپذیرترین اشتباه این فصل است.

**۶. تست ابزار فقط از طریق مدل.**
اگر unit test ابزار نداری، هر بار «ابزار خراب بود» و «مدل بد انتخاب کرد» را قاطی می‌کنی. ابزار توابع کد معمولی‌اند: تست مستقیم؛ انتخاب مدل، eval جدا.

### نکته‌های مهم (Tips & Tricks)

- فهرست `RISKY_TOOLS` را **بصری و متمرکز** نگه دار؛ هر ابزار جدید باید صریح تصمیم‌گیری شود که کدام رده است — «default به رده‌ی حساس» نگرش درست رویارویی ابزار جدید است.
- برای ابزارهای حساس، در description هم شفاف باش («فقط پس از خواندن سیاست») — مدل مسیر درست را خودش می‌چیند و گاردها کم‌تر لازم می‌شوند؛ ولی یادت باشد description قاعده است، دیوار نیست.
- در trace، **نسخه‌ی پرامپت و مدل** را هم ثبت کن (فصل ۴ فایل ۰۳) — سه ماه بعد، «رفتار عجیب» را می‌توانی به قطعه‌ی دقیقی نسبت بدهی.
- تأیید تعاملی (input) را **فقط برای دمو/CLI** ببین؛ در وب‌اپ، همان منطق به صف تأیید در UI تبدیل می‌شود (فایل ۰۸ معماری‌اش را می‌دهد).
- برای ابزارهای هزینه‌دار (API ثالث)، **cache خواندنی‌ها** بگذار (فایل ۰۹ کاملش می‌کند) — همان سؤال هوای تهران در یک دقیقه، نباید ده بار API بیرونی را صدا بزند.
- سناریوهای ترکیبی (چند ابزار در یک درخواست) را **در eval اجباری** کن؛ خواندنِ خوبِ تک‌ابزاری، تضمین ترکیب نیست.

### خلاصه‌ی فصل

- ابزارها را **بر اساس ریسک طبقه‌بندی کن**: فقط‌خواندنی آزاد، نوشتنِ برگشت‌پذیر قفل‌سخت، نوشتنِ حساس تأیید انسانی.
- سقف‌های مادی **در کد ابزار قفل می‌شوند، نه در پرامپت** — دیوار در برابر توصیه.
- سه گارد حلقه: **سقف دورها، سقف نرخ ابزار، سقف در خود ابزار**؛ و trace ساخت‌یافته زیر همه.
- ردّ تأیید انسانی هم **داده است** (`user_denied`) — مدل باید بداند تا مسیر جایگزین برود.
- **ابزار ریز با گارد دقیق** پیش‌فرض محصول است؛ ابزار درشت، تصمیم‌ها را به مدل واگذار می‌کند.
- استاندارد ابزار خوب: description سه‌جزئی، خروجی کوچک JSON، خطا به‌عنوان داده، unit test مستقل.

## فصل ۴: اتصال مدل به دیتابیس و API

> **سطح**: سطح ۲ — این فصل ابزارها را به منابع واقعی محصول وصل می‌کند: ابزارهای دامنه‌محور روی دیتابیس و APIهای داخلی، با گاردهای خواندن امن — همان چیزی که دستیار «بلد نیست، بلد است بپرسد» به دستیار «می‌داند» تبدیل می‌کند.

### مقدمه

دو فصل قبل معماری ابزار را ساختیم؛ این فصل اولین مصرف‌کننده‌ی جدی‌اش را می‌سازیم: **داده‌ی واقعی محصول** — دیتابیس و APIهای داخلی. این‌جا دستیار پشتیبانی از «آقای محترم، وضعیت سفارش را از ایمیلتان چک می‌کنم» به «سفارش ORD-1001 دیروز ارسال شده و فردا می‌رسد» ارتقا می‌یابد.

یک تصمیم معماری این فصل را تعیین می‌کند و از اول بگویم: **ابزارهای دامنه‌محور، نه ابزار عمومیِ اجرای SQL.** وسوسه‌ی «یک ابزار run_sql بگذاریم که هر چیزی را بپرسد» قوی است و تقریباً همیشه اشتباه: هم امنیت را به عهده‌ی حدس‌زدن مدل می‌گذارد (فایل ۰۷ نشان می‌دهد چرا این قمار برنده نمی‌شود)، هم کیفیت را (مدل باید شِمای جدول‌ها را بداند، joinها را حدس بزند، و پرس‌وجوهای غلط اجرا شوند). ابزار دامنه‌محور، یعنی بدهی شناختی مدل کم است و گاردها دقیق‌اند.

### مفاهیم اساسی

#### الگوی ابزار دیتابیس‌محور

هر نیاز واقعی کاربر، یک یا چند ابزار دامنه‌محور:

```text
نیاز کاربر: «سفارش‌های من کجاست؟»     → get_customer_orders(email)
نیاز کاربر: «قیمت X چنده؟»            → get_product_price(name)
نیاز کاربر: «آیا Y موجود است؟»        → همان get_product_price (فیلد stock)
```

هر ابزار این پنج ویژگی را دارد:

1. **SQL آماده‌شده از قبل** (توسط تو، در کد) — مدل فقط پارامترها را می‌دهد، نه متن SQL.
2. **پارامترها parametrized** (`?`) — نه الحاق رشته؛ جلوی injection از مسیر ورودی کاربر.
3. **فقط SELECT** — گاردِ شروع با `select` (و باز هم: حساب‌های دیتابیس فقط-خواندنی).
4. **سقف سطر** (LIMIT داخلی) و **timeout** — پرس‌وجوی ۹۰ ثانیه‌ایِ یک‌میلیون‌ردیفی، تجربه‌ی هیچ‌کس را بهتر نمی‌کند.
5. **خروجی فشرده** — فقط ستون‌های لازم، حداکثر چند ده رکورد.

#### الگوی ابزار API-محور

همان پنج ویژگی + دو جزء API-خاص:

- **کلیدها از متغیر محیطی** (فایل ۰۱) — هرگز در کد.
- **خطا به‌عنوان داده**: 404 = `{"error": "not_found"}`، قطعی شبکه = `{"error": "unreachable"}` — مدل باید بتواند تصمیم بگیرد، نه اینکه exception چرخه را بکشد.
- **timeout صریح** — فایل ۰۲ فصل ۶ را یادت هست؛ در ابزارها حتی مهم‌تر است، چون حلقه‌ی مدل با ابزارهای کند، تجربه را فلج می‌کند.

#### خواندن ترکیبی: قدرت واقعی این معماری

وقتی ابزارها دامنه‌محورند، مدل می‌تواند **ترکیب‌های هوشمند** بسازد: «این مشتری کیست، چه خریده، و آیا سیاست مرجوعی شاملش می‌شود؟» → سه ابزار، ترتیبی، با استدلال بین‌ابزاری. این چیزی است که با یک پرامپتِ «همه‌چیز را بدان» هرگز نمی‌شد — و همان چیزی است که در eval (فایل ۰۷) باید صریحاً تست شود.

#### کِی RAG، کِی ابزار دیتابیس؟

سؤالی که خیلی زود می‌آید و جواب کوتاهش را همین‌جا بدهیم (فایل ۰۵ کاملش می‌کند):

| داده | راه درست |
|---|---|
| داده‌ی ساخت‌یافته‌ی عملیاتی (سفارش، موجودی، کاربر) | **ابزار** — پرس‌وجوی دقیق، عدد درست |
| متن‌های نیمه‌ساخت‌یافته‌ی بزرگ (مستندات، مقالات، تیکت‌های قدیمی) | **RAG** — جست‌وجوی معنایی |
| هر دو در یک پاسخ | هر دو به‌عنوان ابزار — مدل ترکیب می‌کند |

و ابزارها:

```python
"""db_tools.py — ابزارهای دامنه‌محور فقط‌خواندنی روی دیتابیس."""
import json
import sqlite3
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"
DB_PATH = "shop.db"
MAX_ROWS = 20  # سقف سخت — در خود ابزار، نه در پرامپت


def _read_query(sql: str, params: tuple = ()) -> list[dict]:
    """گاردهای خواندن امن: فقط SELECT، سقف سطر، timeout."""
    if not sql.strip().lower().startswith("select"):
        raise ValueError("گارد: فقط SELECT")
    conn = sqlite3.connect(DB_PATH, timeout=5)  # timeout هم گارد است
    try:
        cur = conn.execute(sql, params)          # params → جلوی injection
        rows = cur.fetchmany(MAX_ROWS)           # سقف سطر در سطح cursor
        cols = [d[0] for d in cur.description]
        return [dict(zip(cols, row)) for row in rows]
    finally:
        conn.close()


def get_customer_orders(email: str) -> dict:
    try:
        rows = _read_query(
            "SELECT id, status, total_toman, created_at FROM orders "
            "WHERE customer_email = ? ORDER BY created_at DESC",
            (email,),
        )
        return {"orders": rows, "count": len(rows)}
    except Exception as exc:
        return {"error": str(exc)}


def get_product_info(name: str) -> dict:
    try:
        rows = _read_query(
            "SELECT name, price_toman, stock FROM products WHERE name LIKE ?",
            (f"%{name}%",),
        )
        return {"products": rows}
    except Exception as exc:
        return {"error": str(exc)}
```

و چرخه‌ی مدل — همان الگوی حلقه‌ی فصل ۲، حالا با ابزارهای واقعی:

```python
"""db_agent.py — دستیار فروش با ابزارهای دیتابیس."""
import json
from openai import OpenAI
from db_tools import get_customer_orders, get_product_info

client = OpenAI()
MODEL = "gpt-4o-mini"

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_customer_orders",
            "description": "سفارش‌های یک مشتری با ایمیل او. برای سؤال‌های «سفارش‌های من» استفاده کن.",
            "parameters": {
                "type": "object",
                "properties": {"email": {"type": "string", "description": "ایمیل مشتری"}},
                "required": ["email"],
                "additionalProperties": False,
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "get_product_info",
            "description": "قیمت و موجودی محصول با بخشی از اسمش. برای سؤال قیمت/موجودی.",
            "parameters": {
                "type": "object",
                "properties": {"name": {"type": "string", "description": "بخشی از نام محصول"}},
                "required": ["name"],
                "additionalProperties": False,
            },
        },
    },
]

TOOL_FUNCS = {"get_customer_orders": get_customer_orders,
              "get_product_info": get_product_info}


def run_tool(name: str, args: dict) -> dict:
    if name not in TOOL_FUNCS:
        return {"error": "unknown_tool"}
    return TOOL_FUNCS[name](**args)


def agent(user_message: str) -> str:
    messages = [{"role": "system", "content": (
        "دستیار فروش هستی. برای هر ادعای داده‌ای (قیمت، موجودی، سفارش) "
        "حتماً از ابزارها استفاده کن؛ از حافظه‌ی خودت قیمت و وضعیت نگو."
    )}, {"role": "user", "content": user_message}]

    for _ in range(5):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS, tool_choice="auto"
        )
        msg = response.choices[0].message
        if not msg.tool_calls:
            return msg.content
        messages.append(msg)
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments or "{}")
            output = run_tool(tc.function.name, args)
            messages.append({
                "role": "tool", "tool_call_id": tc.id,
                "content": json.dumps(output, ensure_ascii=False),
            })
    return "این درخواست را نمی‌توانم با ابزارهای فعلی کامل کنم."


if __name__ == "__main__":
    print(agent("سلام، سفارش‌های من کجاست؟ ایمیلم ali@example.com است."))
    print("\n---")
    print(agent("هدفون بی‌سیم مدل X موجود هست و قیمتش چنده؟"))
```

اجرا کن و دو رفتار را ببین: مدل **قبل از جواب دادن ابزار زده** (به‌خاطر قید system)، و برای سؤال دوم، فقط از داده‌ی واقعی دیتابیس گفته — نه حافظه‌اش که ممکن است قیمت را غلط بلد باشد.

#### مثال ۲: ابزار HTTP با مدیریت خطای کامل

```python
"""api_tools.py — ابزار فراخوانی API داخلی؛ خطا داده است، نه فاجعه."""
import os
import requests  # pip install requests
from openai import OpenAI

client = OpenAI()

API_BASE = os.environ.get("INTERNAL_API_BASE", "https://api.example.com")
API_TOKEN = os.environ["INTERNAL_API_TOKEN"]  # از محیط — هرگز در کد


def get_order_status(order_id: str) -> dict:
    try:
        resp = requests.get(
            f"{API_BASE}/orders/{order_id}",
            headers={"Authorization": f"Bearer {API_TOKEN}"},
            timeout=10,  # گارد: ابزار کند، حلقه‌ی مدل را نمی‌خواباند
        )
        if resp.status_code == 404:
            return {"error": "order_not_found"}          # منطقی و قابل تصمیم
        if resp.status_code == 429:
            return {"error": "rate_limited"}             # مدل می‌تواند صبر/مسیر جایگزین
        resp.raise_for_status()
        data = resp.json()
        # خروجی فشرده: فقط چیزی که مدل لازم دارد
        return {"status": data.get("status"),
                "eta": data.get("eta"),
                "total_toman": data.get("total")}
    except requests.Timeout:
        return {"error": "timeout"}
    except requests.RequestException as exc:
        return {"error": "unreachable", "detail": str(exc)}
```

الگوی قابل حمل در این تابع: timeout صریح، ترجمه‌ی کدهای خطا به داده‌ی منطقه‌مند، برش خروجی به فیلدهای مفید — هر سه، از فصل ۲ به ارث رسیده و حالا روی HTTP اعمال شده‌اند.

### مقایسه و الگوهای مختلف

#### ابزار دامنه‌محور در برابر ابزار عمومی SQL

| معیار | دامنه‌محور (پیش‌فرض این فصل) | عمومی (`run_sql` با متن آزاد) |
|---|---|---|
| امنیت | سطح حمله کوچک؛ SQL از قبل audit شده | مدل SQL تولید می‌کند؛ هر باگش اجرا می‌شود |
| کیفیت | پرس‌وجوی تست‌شده؛ خروجی فشرده | joinهای حدسی؛ خروجی ناپایدار |
| نگه‌داری | تغییر قاعده = تغییر یک تابع | هر تغییر schema، رفتار مدل را می‌شکند |
| انعطاف | فقط سناریوهای طراحی‌شده | هر سناریو — نظری |
| حکم | **پیش‌فرض محصول** | فقط با گاردهای سنگین و شِمای ثابت، در تیم‌های خبره |

و یک نکته برای انعطاف‌خواه‌ها: نیازهای جدید = ابزارهای جدید — اضافه‌کردن یک ابزار دامنه‌محور، ده دقیقه است و هرگز به اندازه‌ی ریسکِ SQL آزاد هزینه ندارد.

#### جدول تصمیم: مسیر دسترسی به داده‌ی محصول

| موقعیت | الگوی پیشنهادی |
|---|---|
| پرس‌وجوی عملیاتی ساخت‌یافته | ابزار دامنه‌محور (این فصل) |
| جست‌وجو در متن‌های بزرگ غیرساخت‌یافته | RAG (فایل ۰۵) |
| اطلاعات عمومی تازه‌ی وب | ابزار جست‌وجوی وب (ارائه‌دهنده یا ثالث) |
| ترکیب چند منبع در یک پاسخ | چند ابزار + استدلال مدل (فصل ۳) |

### اشکال شایع

**۱. ابزار run_sql باز.**
با هر استدلالی («انعطاف!»): مدل SQL می‌سازد، گاهی UPDATE می‌کند، گاهی cross-join هزارردیفی می‌زند، و یک روز متنی که «دستور اجرا کن» دارد از مسیر injection می‌رسد (فایل ۰۷). جای این ابزار در پروژه‌ی تو: هیچ‌جا — حداقل تا فایل‌های ۰۷ و ۰۹ که معیارهای ریسک را می‌دهند.

**۲. بدون LIMIT و timeout.**
پرس‌وجوی خوب هم در روز شلوغ، تیبل بزرگ، ده ثانیه می‌گیرد؛ حلقه‌ی مدل چند بار صدا می‌زند؛ کاربر به «در حال پردازش...» نگاه می‌کند و فاکتور می‌آید. سقف سطر و timeout، بخشی از تعریفِ «ابزار» است.

**۳. پارامترها با الحاق رشته.**
`f"SELECT ... WHERE email = '{email}'"` — ورودی کاربر (یا خروجی حدس مدل) مستقیم داخل SQL. همیشه parametrized: `?` (sqlite/db-api) یا prepared statement.

**۴. خروجی API کامل به مدل.**
پاسخ خام API با ۴۰ فیلد و دیتای کاربرانِ دیگر: توکن‌خور و **نقض حریم خصوصی** (فایل ۰۸). ابزار برش می‌زند به فیلدهای مرتبطِ سؤال — داده‌ی یک کاربر فقط با احرازِ مرتبط بودن به مدل برسد.

**۵. کلیدها و URLهای داخلی در لاگ‌های trace.**
trace فصل ۳ عالی است تا وقتی Authorization header را هم لاگ نکند. قبل از لاگ، فیلدهای حساس را mask کن — این قاعده در فایل ۰۹ تکرار و کامل می‌شود.

**۶. دست‌زدن به دیتابیس اصلی با حسابِ پراختیار.**
حتی با ابزارهای دامنه‌محور، حساب اتصال باید **فقط‌خواندنی و حداقلی** باشد (least privilege) — دیوار دوم اگر مدل/کد خطا کرد (فایل ۰۷ این لایه‌بندی را کامل می‌کند).

### نکته‌های مهم (Tips & Tricks)

- ابزارهای دیتابیسی را **با دیتابیس واقعی‌نما در unit test** تست کن (sqlite در حافظه) — بدون مدل، سریع و قطعی.
- برای سؤال‌های ترکیبی رایج، **ابزار ترکیبی از پیش‌ساخته** هم مفید است («سفارش + وضعیت پرداخت در یک جواب») — کمتر فراخوانی، خروجی یکدست؛ ولی مطابق قاعده‌ی فصل ۳، ریزبودن را پیش‌فرض بگیر.
- خروجی اعداد دیتابیس را **همان‌طور که هست** بده (2450000) و قالب‌بندی فارسی را به مرحله‌ی نمایش بسپار — مدل بین «2,450,000» و «۲٬۴۵۰٬۰۰۰» قاطی می‌شود و عدد را خراب می‌کند.
- متادیتای تازگی را در خروجی ابزار بگذار (`{"as_of": "2026-10-01"}`) — مدل می‌تواند در جوابش بگوید «به داده‌ی امروز»، هم‌راستا با فصل ۳ فایل ۰۲.
- هر ابزار جدید را اول **دستی و خارج از مدل** امتحان کن (خروجی درست؟ گاردها؟) و بعد به TOOLS اضافه کن — همان چرخه‌ی دیباگ فصل ۵ فایل ۰۳، این‌بار برای ابزار.
- در product real، ابزارهای دیتابیسی معمولاً روی **نسخه‌ی replica فقط‌خواندنی** وصل می‌شوند — حتی خطای مدل هم دیتای اصلی را آزار نمی‌دهد.

### خلاصه‌ی فصل

- **ابزارهای دامنه‌محور، نه SQL عمومی**: SQL از قبل نوشته و audit شده؛ مدل فقط پارامتر می‌دهد.
- پنج گارد اجباری ابزار دیتابیسی: **SELECT-only، پارامترهای parametrized، LIMIT داخلی، timeout، خروجی فشرده.**
- ابزار API: **کلید از محیط، timeout صریح، خطا به‌عنوان داده‌ی منطقه‌مند، برش خروجی.**
- قدرت واقعی، در **ترکیب ابزارها** توسط مدل است — و همین ترکیب‌ها باید در eval باشند.
- مرز RAG و ابزار دیتابیس: **متنِ بزرگ غیرساخت‌یافته → RAG؛ داده‌ی عملیاتی ساخت‌یافته → ابزار** — و در محصول واقعی هر دو کنار هم‌اند.
- حداقل‌کاری حساب اتصال و replica فقط‌خواندنی: **دفاع در عمق**، نه امید به بی‌خطایی مدل.
